## 一、Windows 首启“先只有邮箱登录，过一会儿才出现短信验证码登录”的根因

### 现象到机制

1. 登录页要先取云端的注册 / 登录策略（`GET /v1/meta`，里面的 `phone_login` 决定显示不显示“验证码登录”）。
2. 界面在策略取到之前（`null`）按**旧流程**渲染——只有邮箱 + 密码（`SmsCodeFields.tsx` 第 62 批写法：“未取到之前也按旧流程显示，取到后再补上手机号一栏”）。所以策略一迟到，律师先看到的就是只有邮箱登录的页面，过一阵子页面变样。
3. 策略请求只能经**出站闸门**发出（“唯一出口”设计，内核本身不联网），闸门是**按需拉起**的独立 Node 进程。
4. 安装包形态下，闸门拉起前要 `await runtimeReady()`：等主进程把**随包运行时的全部文件**逐个算完 SHA-256（复核 B4-R15 的防篡改闸口）。
5. Windows 运行时是 **3,665 个文件、约 680 MB**（`kwl-egress.exe`、`kwl-host.exe`、`kwl-parse.exe`、`node.exe` 各 104 MB，onnxruntime、DirectML、skia 等 DLL，OCR 模型），在 Windows 上首次逐个读取还要叠加 Defender 实时扫描——这一步就是“等一段时间”的主体。macOS 是本机 SSD、没有实时扫描，同一步骤快得多，所以 Mac 上几乎看不出来。
6. 闸门拉起前内核还要**同步**整读整算一次 104 MB 的 `kwl-egress.exe` 摘要（`readFileSync` + `createHash`），这段时间内核事件循环卡住，界面的其他调用也得等。

### 两个放大问题

- **“取不到”被当成“旧云端”**：内核 `account.registration_meta` 在已激活模式下 `catch → { legacy: true }`，界面 `.catch(() => setMeta({ legacy: true }))`。网络一抖或闸门超时（15 秒），这次打开就整个只剩邮箱登录，而且不会再变。
- **没有加载态**：律师无法区分“还在取”与“云端没开验证码登录”。

### 修复（都在架构与状态管理层）

| 层 | 改动 |
|---|---|
| 主进程 `main.cjs` / `runtime-paths.cjs` | 全量核对改为**先核闸门闭包**（它自己的 Node 与 `egress-gate/` 入口，约 105 MB、2 个文件），通过即发 `kernel.runtime_verified {scope:"gate"}`；其余文件随后照常核对，不符照旧有序关闭内核并提示修复。安全性不变：闸门只装载这两个文件，运行时目录的“清单外文件”启动时已同步核对。 |
| 内核 `child-env.ts` / `gate-host.ts` | `runtimeReady("gate")` 只等闸门闭包；Agent 宿主、解析进程、W 执行域照旧等全量。 |
| 内核 `kernel-gate.ts` | 闸门重核 Node 摘要改为**流式**（不再卡事件循环）；并发启动共用同一次。 |
| 内核 `onboarding.ts` / `index.ts` | 内核一启动就**预取**策略（顺带把闸门拉起来），界面第一次调用接上同一个请求（in-flight 共用，结果记 20 秒）。 |
| 内核策略接口 | 取不到如实报错（`provider_unavailable`，带原因代码）；云端答了但没有策略才是 legacy（旧云端照旧流程，兼容不变）。 |
| 界面 `SmsCodeFields.tsx` / `AuthShell.tsx` | 三态：取策略中 → 与表单同高的骨架“正在取得登录方式…”；取到 → 表单（首屏即是最终形态，不再变样）；取不到 → “暂时取不到登录方式 · 原因 · 重试”，并按 5 / 10 / 20 / 40 / 60 秒退避自动再试。 |
| 证据事件 | `MAIN_RUNTIME_VERIFIED {scope, files, ms}`、`KERNEL_GATE_STARTED {ms, since_boot_ms}`、`KERNEL_REGISTRATION_META {outcome, ms, reason}`；验收驱动另记“登录页首屏”用时与是否出现骨架。 |

没有用固定延时、没有硬编码登录方式、没有强制刷新。
