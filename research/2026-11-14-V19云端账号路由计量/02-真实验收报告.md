## 4. 计量对账

对账脚本（会话 scratchpad `reconcile.py`）：控制面账本 `usage/2026-11.jsonl` ↔ 网关预写日志 `meter.jsonl` 里的结算记录，按请求编号逐条比对 token（输入、缓存、输出）、上游请求编号、上游型号。

（§5 任务结束后的最终数字见 §5.2。）

- 不重复计费：同一请求编号重发 → 控制面 `duplicates`，不入账（用例 + 实测：网关重启重放发件箱不重复）。
- 不漏计：每个“预占”都有“结算”（`reserve_without_settle = 0`）；网关重启从 `meter.ack` 重放未确认的回报。
- 并发超限：领租约时按“租户余量、上限余量、窗口余量、个人余量 − 在途”取最小，余量不够这次所需即 402；超出幅度至多是“实际 − 预占”。
- 跨用户混淆：账本行带账号、成员、设备、席位；按律所 / 账号查询各自独立（用例）。
- 与 MaaS 后台对账：每行记 MaaS 返回的请求编号（形如 `20261114052924…`），可与 MaaS 日志逐条对；本批没有 MaaS 后台权限，未做这一步。

### 5.1 过程

|---|---|---|---|
| 时间（北京） | 13:32～13:51 | 13:59～14:12（中间两次等律师选择 / 批准计划） | 任务页“用时 39 分 59 秒 · 81 步” |
| 模型请求（账本行） | 24（21 真实用量、1 估算、2 次 MaaS 429） | 19（全部真实用量） | 43 |
| token（输入 / 其中缓存命中 / 输出） | 1,839,447 / 1,497,088（81%）/ 33,871 | 1,429,347 / 1,262,336（88%）/ 40,343 | 3,268,794 / 2,759,424（84%）/ 74,214，合计 **3,343,008** |
| 按测试价目（**非真实报价**） | 售价 ¥3.41、成本 ¥1.70 | 售价 ¥2.58、成本 ¥1.29 | 售价 ¥5.98、成本 ¥2.99 |

1. **第一次运行**：律师确认论点、批准计划后起草，交出律师函（Word）与两张 Excel；第 24 次请求时网关按试用套餐 5 小时窗口拒绝（402），任务停下。任务页当时写“AI 服务连不上”——文案缺陷，已修（§5.3）。
2. **运营调额度**：控制台“套餐与额度 → 试用”改为每席位每期 2,000 万 token、窗口 50%，确认框列出影响后保存；律师端“设置 → 管理 → 用量”刷新即从 31% 变为 **9.4%**（187.3 万 / 2,000 万），窗口 19%，并注明其中 1 次是估算。
3. **重新运行**：助手重新读材料，问了三件事（收函对象、违约金是否暂计、宽限期几天），律师选推荐项；再给计划、批准；起草 → 本机计算 → 核对引用 → 独立复核 → 按复核意见修改 → 复核人回看。
4. **结果：部分完成**。复核人回看发现“必须改”第 1 条没落实：第一次运行留下的《依据与发送前核对-催款.xlsx》写的是 10 日付款期限，重新运行时律师选了 7 日，新出的核对表与律师函正文都是 7 日，但旧表只改了标题、仍保留按 10 日算的届满示例。任务页顶部只列这一条（重新运行后上一次的额度暂停不再列——同时修的显示缺陷，§5.3）。
   这是**重新运行把上一次的交付件带进本次成果**造成的冲突，属内核执行管线的问题，不在本批范围；记作遗留（§8 第 9 条）。按此前的约定（重新运行会污染质量评估），这一单不用于评质量。
5. **成果能否打开**：经与律师点“下载”同一个内核方法（`artifacts.download`，还原代号、套文书版式）取出全部 12 个文件——律师函 Word 3 个版本（macOS `textutil` 解析通过、无残留代号）、Excel 6 个（zip 完整、各 XML 部件可解析）、草稿与复核意见 Markdown 3 个（UTF-8 有效）。没有在 Microsoft Word / Excel 里实开（本机未装）。

### 5.2 计量

- **账本 ↔ 网关预写日志**（`reconcile.py`，全栈当日全部请求，含冒烟、并发、路由测试）：账本 61 行、网关结算记录 61 条，逐条匹配 61，输入 / 缓存 / 输出 token、上游请求编号、上游型号**0 处不一致**；同一请求编号重复 0；有预占无结算 0。
- **账本 ↔ 律师端 ↔ 控制台**：本所账本合计 3,343,008 token / 43 次；律师端“用量”显示已用 3,343,008（16.7%）、43 次、约 ¥5.98，与账本一致。律师端另显示 3.5% “进行中”——是网关手上还没到期的租约余量（5 分钟内到期归还），任务已结束时仍显示，属可理解但略显多余的状态。
- **不计费的请求**：两次 MaaS 429、路由失败 503、上游 404 各行 `usage = null`、金额 0；被网关在本机拒绝的（401、400 未登记别名、402 额度）不进账本。
- **估算 1 行**：第一次运行中的 81,056 输入 token 一行是取 usage 的缺陷造成的（§5.3 第 1 条，已修）；修后网关重启，重新运行的 19 行与并发、路由测试的全部请求都是上游真实用量（`usage_source = upstream`）。

### 5.3 发现并已修的缺陷

- **流式用量被记成“估算”**：一次 2,270 token 输出的工具调用流（超过 64 KiB，网关只留尾部取 usage），尾部截断点恰好落在“{”上，取 usage 的函数把整段当 JSON 解析失败后直接放弃，没再逐行找末尾那行真实 usage，退回按字符估算——输入记成 81,056 token，比前后两次真实值（4.8～5.6 万）高约五成。已改为解析失败继续逐行扫（并兼容 `data:` 后不带空格），补回归用例；之后的请求见 §5.2。
- **检索路径**：样例与旧手册的 `search_base` 写 `…/v1/search`，检索服务只认 `/search`，照文档部署律师端检索会一律 404。已改为两种都收。
- **未定价时总览显示 ¥0.00**：已改为“未定价”。
- **额度规则生效时，任务页说“AI 服务连不上”**：第一次运行做到第 24 次模型请求时，网关按试用套餐的 5 小时频率窗口返回 402 `quota_burst`（规则真实生效，不是故障），
  但执行器只认上游的 429 / 5xx 文案，把它归成“AI 服务连不上，这一步没有完成”，律师会以为是网络问题。已把本产品自己的四种额度原因（频率窗口、个人额度、律所上限、本期额度用完）
  和“模型未定价”分别写成“任务暂停 + 什么时候恢复 / 找谁加量”，时间线步骤标题改为“AI 额度暂时用到限制，这一步暂停”；补用例（内核 1 条、桌面端 1 条）。
- **试用套餐缺省额度对真实任务太小**：缺省 600 万 token、5 小时窗口 40%（240 万），而真实一单约 190 万 token（11-12 的 57 单中位；本单第一次运行 24 次请求 187 万，其中 81% 是缓存命中），
  一单还没做完就被窗口拦下。缺省改为 2,000 万 token、窗口 50%（约 5 单 / 5 小时、约 10 单 / 期）；标准 / 专业 / 旗舰的 token 数不变（沿用第 40 批），
  但说明里的“每月约 80 / 200 / 480 单”是按第 40 批“每单 50～70 万 token”的估计写的，与实测差约 3 倍，改为约 25 / 65 / 160 单。手册补了按实测定额度的说明。
  **本栈的试用套餐是在运营控制台里改的**（套餐与额度 → 试用 → 每席位每期 2000 万、窗口 50% → 确认框列出影响 → 保存），律师端“用量”立即从 31% 变为 9.4%（187.3 万 / 2,000 万），窗口 19%。
- **重新运行后，“还有没做完的地方”仍列上一次的失败**：重新运行跑完后，任务页顶部仍写“AI 额度暂时用到限制”“任务没有完成：402……”，其实那是第一次运行的事。每次运行都会记一条“已收到任务”，现在只看最后一次运行之后的步骤；补用例（桌面端 1 条），界面实看只剩真正没落实的那一条。
- **控制台“缺省 max_tokens”输入范围与控制面不一致**：控制台允许 1～1,000,000，控制面只收 256～262,144，填 100 会在保存时才报错。控制台字段改为同一范围并在标签上写明。
- **估算行的说明写成“中途断开”**：上游没给出用量有两种原因（客户端断开、上游流里没有 usage），律师端统一写成“中途断开”不对；改为“AI 服务没给出用量、按已收到的内容估算”。

| 运营接口 | 签名覆盖完整路径含查询串（只签路径不签查询串 → 401）；POST 带查询串 404；CSV 防公式注入（单引号） |
| 路由改投 | 网关本机白名单外的上游不用；跨厂商切换须显式打开 |
| 传输 | 生产入口只收 HTTPS；签名服务只收指定 CA 签发、URI SAN 在名单内的客户端证书；客户端钉住叶子公钥 + 备用公钥 |

## 8. 遗留问题与风险

1. **服务器部署演练未做**：本机 colima 虚机是 Ubuntu 24.04（有 systemd、openssl），但没有 Node 24 与 nginx，安装要从 nodejs.org 与 Ubuntu 源下载，待你同意后照手册在虚机里走一遍（含 systemd、nginx、防火墙）。
2. **联网检索不可用**：MaaS 的 `/v1/tools/search` 在 111 毫秒内失败。要确认原因得直接调一次上游（你此前要求这类调用先问）；不提供时检索上游须另配。
3. **Windows 真机未验**：安装包仍走 GitHub Actions `windows-desktop`（仓库变量 `KWL_RELEASE_JSON`）。
4. **用量账本是控制面本机文件**：单实例可靠；控制面一主多备前要换成数据库表或共享存储。
5. **找回密码没有邮件 / 短信通道**：靠运营发重置码；接 SMTP 需要服务账号。
6. **D-186 安全取舍**：账号新电脑入组靠人工核对 12 位核对码（没有邀请码本机段的自动核对）。
7. **价格是测试值**：真实售价与 MaaS 成本价待商务填写；迁移来的 token 套餐额度标“待商务确认”。
8. **试用套餐每账号 1 台电脑**（有意：试用防共享）；标准套餐缺省 2 台。
9. **重新运行会把上一次的交付件带进本次成果**：本次验收里第一次运行的 10 日期限核对表与重新运行的 7 日决定冲突，复核抓到了但修改轮没改干净（§5.1）。属内核执行管线，建议单独一批处理（重新运行时把上一次的交付件标为“已被取代”或让律师选是否沿用）。
10. **tokens 套餐把缓存命中的输入按 1 个 token 计**：真实任务八成以上输入是缓存命中，同样单数下 tokens 套餐比金额套餐“显得贵”；标准 / 专业 / 旗舰的 token 数待商务按实测（一单约 190 万 token）重新确认，或定价后改金额套餐。
11. **租约余量显示为“进行中”**：任务结束后最多 5 分钟内律师端仍显示一小段“进行中”。
