## §1 关键判断（第一性原理）

1. **身份分两层，不推翻律所根。** 现在“谁”= 律所根签发的设备证书，云端只转运——这一层保护团队共享密钥分发与律所策略，不能让云端随意铸设备（否则被攻破的云端能把自己加进团队共享）。新加的是**账号层**：邮箱 + 密码，云端是唯一可信来源，决定“谁能用、用多少、在哪几台电脑上用”。账号与律所成员一一对应；设备证书仍由律所根签。
2. **账号把门开在席位令牌上。** 模型调用全程凭席位令牌；云端只在“账号有效 + 本设备有有效会话”时签发席位令牌，并通过网关订阅下发“暂停设备”，退出登录、停用账号、解绑设备 15 秒内在网关生效（席位令牌本身 72～96 小时，不能只靠到期）。
3. **一把尺子。** 取消“每千 token 4 单位”的固定折算。额度单位只有两种可核验的：**token**（上游 usage 原样）或**金额**（按我方价目表 × 实际 usage，区分未缓存输入、缓存输入、输出）。百分比 = 实际消耗 ÷ 我方配置的额度，分母来源写明（套餐每席位额度 / 管理员设的个人上限）。
4. **逐请求一条账，云端一处入账。** 网关把每个请求的 usage 带着请求编号报给控制面，控制面按价目表重算费用、按请求编号去重、写只追加的用量账本（独立于状态快照），额度判定与账单都从这一份账出——不会出现两套数字。
5. **路由可改，流量去向不能被控制面单方面改。** 路由表由运营在控制台配、经签名订阅下发；网关本机配置**上游主机白名单**，名单外的路由不用。上游密钥在**浏览器里用网关公钥加密**后才提交，控制面只存密文与尾号，看不到明文。
6. **不加新的长连接与第三方依赖。** 复用：设备签名、控制面通道、签名订阅（15 秒）、租约（硬停）、运营签名、cloud-serve 单进程单角色。

### 2.2 接口（`/v1/auth/*`；桌面端经控制面通道，无设备身份时不带设备签名）

| 方法 | 路径 | 鉴权 | 体 / 应答 |
|---|---|---|---|
| POST | `/v1/auth/register` | 无（按来源限速） | `{email, password, name, org_name?, code?, client?}` → `AuthResult` |
| POST | `/v1/auth/login` | 无；已激活设备可同时带设备签名头（绑定本机） | `{email, password, client?}` → `AuthResult` |
| GET | `/v1/auth/me` | `x-kwl-session`（桌面）或 `Authorization: Bearer`（网页） | `{account, onboarding, devices[], sessions[]}` |
| POST | `/v1/auth/logout` | 会话 | `{ok}`；本设备进“暂停设备” |
| POST | `/v1/auth/password` | 会话 | `{current, next}`；吊销其他会话 |
| POST | `/v1/auth/password-reset/request` | 无（限速） | `{email}` → 恒 202；配了邮件通道才真发 6 位码（15 分钟、5 次） |
| POST | `/v1/auth/password-reset/confirm` | 无（限速） | `{email, code, password}`；`code` 也可以是运营发的一次性重置码；吊销全部会话 |
| POST | `/v1/auth/sessions/{sid}/revoke` | 会话（只能本人的） | `{ok}` |
| POST | `/v1/auth/devices/{device_id}/unbind` | 会话 + `{password}` | 吊销该设备（现有吊销机制）+ 吊销绑在它上面的会话 |

```
AuthResult = {
  session_token,                    // 只此一次
  session: { sid, kind, idle_expires_at },
  account: { aid, email, name, role, status, tid, org: { slug, name }, member_slug },
  onboarding: Onboarding
}
Onboarding = {
  state: "ready"                  // 本机已是这个账号的设备
       | "needs_founder_setup"    // 律所根尚未登记：本机做创始开通（附 claim）
       | "needs_device_join"      // 账号已有别的设备：本机申请入组，由已有的管理员设备批准（附 claim、device_id）
       | "pending_approval"       // 本机已申请、等批准
       | "device_limit"           // 设备已满：列出已绑设备，可先解绑
       | "device_mismatch",       // 本机已激活的是另一个成员：要先退出旧身份（本批不做“换人”）
  claim?: { kind: "founder"|"member", tid, activation_id, claim_secret, firm: {slug,name}, member: {slug,name,role} },
  device_id?: string, devices_used: number, device_limit: number
}
```

错误代码（应答 `{error:{code,message}}`，文案律师能看懂；不区分“邮箱不存在 / 密码错”）：
`auth_invalid`（401）、`account_locked`（423，附 `retry_after_s`）、`account_disabled`（403）、`registration_closed`（403）、`code_invalid`（400）、`email_invalid`、`email_taken`（409）、`password_weak`（400，附 `rules`）、`session_invalid` / `session_expired`（401）、`device_limit`（409）、`rate_limited`（429）。

密码规则：10–128 位、同时含字母与数字、不等于邮箱前缀、不在常见弱口令表。登录失败：同账号 15 分钟内 10 次锁 15 分钟；同来源每分钟 20 次。scrypt 在 worker 之外同步执行约 50 ms，按来源限速兜住。

### 2.3 注册方式（运营在控制台设 `registration`：`open` / `code` / `closed`）

| 方式 | 条件 | 结果 |
|---|---|---|
| 自助注册 | `registration=open`，不带码 | 新建个人律所 `ten_<slug>`（试用套餐、1 席、`trial_days` 天），账号为创始管理员 → `needs_founder_setup` |
| 凭开通码注册 | 运营给律所负责人的 20 位开通码 | 该律所的创始管理员 → `needs_founder_setup` |
| 凭邀请码注册 | 律所管理员在客户端发的 36 位邀请码 | 该律所成员 → `needs_device_join`（沿用现有入组：核对码 + 管理员批准 + 本机核对段 HMAC） |
| 运营代建 | 控制台为某律所建账号 | 返回一次性“设置密码码”，交本人；首次登录即 `needs_founder_setup` 或 `needs_device_join` |

### 2.4 设备

- 账号的设备 = 该成员名下登记过的设备证书。第一台沿用 `dev_<律所>_<成员>`；**同一账号的第 2～9 台为 `dev_<律所>_<成员>_D<n>`**（成员标识只许小写，大写 `D` 不会与成员标识混淆）。
- 设备上限：账号 `device_limit` → 套餐 `device_limit`（缺省 2）。超过即 `device_limit`。
- **D-186（偏离）**：账号新设备入组（`needs_device_join`、无邀请码）没有“邀请码本机秘密段”，批准结果的自动核对（admin_mac）用不上，改为**人工核对码**：新设备显示 12 位核对码，批准方（本人另一台管理员设备，或律所管理员）在“待批准”里核对后批准；批准后新设备显示律所核对码，与已有设备“设置 → 账号与团队”里的核对码比对。凭邀请码入组的路径不变。
- 解绑：账号本人（输入密码）或运营 → 现有吊销（设备进吊销集、网关拒绝）+ 绑在该设备上的会话吊销。
- 异常设备：控制台按“最近报到超过 30 天”“客户端版本过旧”“会话被吊销后仍有请求（网关拒绝计数）”标出，可一键吊销。

### 2.5 账号闸（席位令牌与网关）

- 租户 `accounts_required`：本批之后开通的租户缺省 `true`；之前的读回为 `false`（运营可在控制台打开）。
- `true` 时：`POST /v1/seat-token`（以及 support/notify/relay 专用凭据）要求请求带 `x-kwl-session`，会话有效、账号 `active`、账号成员 = 证书成员、会话设备 = 证书设备（会话设备为空则此时绑定）。否则 401 `session_required` / `session_invalid` / 403 `account_disabled`。
- 网关订阅 `kwl-gateway-feed` 加 `suspended_devices: {tid, device_id}[]`：该设备没有有效会话（退出登录、会话过期、账号停用）。网关对其令牌回 401 `seat_session_inactive`。重新登录即移出。
- 桌面端：所有控制面请求附 `x-kwl-session`（闸门白名单加这个头）；收到 `session_*`、`account_disabled`、网关 `seat_session_inactive` → 内核进入 `login_required`，界面出“登录已失效，请重新登录”（不重启内核、本机功能照常，AI 暂停）。

## §3 工作线 C：API 路由

### 3.1 登记（控制面状态 `routing`）

```
Provider {
  id: /^[a-z][a-z0-9-]{1,31}$/, label, vendor (如 "csi-maas"), base_url (https, 无用户名口令), enabled,
  key_sealed: SealedKey | null, key_hint: "…abcd" | null, key_set_at, key_set_by,
  max_concurrency: number (每网关实例, 缺省 64), header_timeout_ms?, idle_timeout_ms?,
  probe_requested_at: string | null
}
ModelRoute {
  alias: "legal/k3" | "legal/k2.6" | 运营新增 /^[a-z0-9][a-z0-9._/-]{1,47}$/,
  label, enabled, is_default (至多一个),
  targets: [{ provider, model, priority (小者先) }] (1–4 个),
  allow_cross_vendor: false, default_max_tokens: 8192
}
PriceTable { version: n, effective_at, items: { [alias]: { input, cached_input, output, cost_input, cost_cached_input, cost_output } } }  // 元/百万 token，可为 null（未定价）
```

- 客户端写死别名 `legal/k3`（主任务）与 `legal/k2.6`（子任务），**别名不改名**，路由只改“别名 → 上游与型号”。首次启动从网关本机配置导入一份（`upstream.base_url` + 当前型号）作初始路由。
- 价目表每次修改生成新版本，账本行记价目版本；控制面保留全部历史版本。

### 3.2 上游密钥（浏览器加密，控制面看不到明文）

```
SealedKey = { alg: "ECDH-P256+HKDF-SHA256+A256GCM", kid, epk: b64u(65 字节未压缩公钥), iv: b64u(12), ct: b64u(密文+16 字节标签) }
shared = ECDH(临时私钥, 网关路由公钥)                // 32 字节
key    = HKDF-SHA256(ikm=shared, salt="kwl-upstream-key/1", info=provider.id, 32 字节)
ct     = AES-256-GCM(key, iv, utf8(明文密钥), aad = "kwl-upstream-key/1\n" + provider.id)
```

- 网关路由密钥对（P-256）由 `cloud-init-secrets` 生成：私钥 `routing-key.pem` 只给网关；公钥 SPKI（base64）写进控制台 `config.json` 的 `routing_public_key`（及其 `routing_key_id`）。控制台提交前在浏览器里加密，同时只把“…”+ 末 4 位作为 `key_hint`。
- 网关解封失败的上游记为 `key_unusable`，不用。

### 3.3 下发与健康

- `GET /v1/feed/routing`（服务间凭据）→ 签名信封 `kwl-routing-feed`：`{version, issued_at, providers[], models[], prices}`。网关每 15 秒取一次，按版本原子替换；取不到沿用上一版。首次取不到 = 用本机配置的兜底上游。
- 网关本机配置 `routing.allow_hosts`（生产必填）：路由里的主机不在名单内 → 该上游状态 `blocked_by_allowlist`，不用。
- 健康：被动（连续 3 次连接失败 / 5xx / 429 / 头超时 → 熔断 30 秒 → 半开放 1 个请求）+ 主动（每 60 秒 `GET {base}/models`，带密钥）；运营点“测试连接”→ 置 `probe_requested_at`，网关下一轮立即探测。
- 网关每 15 秒 `POST /v1/feed/routing-health`（服务间凭据）：`{holder, at, providers: {[id]: {state: "up"|"degraded"|"down"|"blocked_by_allowlist"|"key_unusable"|"disabled", latency_ms, last_ok_at, last_error, consecutive_failures, inflight, probed_at}}}`。控制面只存最近一份（按 holder），供控制台显示。
- 切换：同一别名的目标按优先级；**只在还没给客户端写出任何字节之前**切换（连接失败、5xx、429、头超时），至多 3 次；跨 `vendor` 只在 `allow_cross_vendor=true` 时；4xx（除 429）不切换。全部 429 时把上游 `Retry-After` 回给客户端。

## §4 工作线 D：用量、额度与计费

### 4.1 单位

- `quota_unit = "tokens"`：消耗 = 上游 usage 的 `prompt_tokens + completion_tokens`。
- `quota_unit = "cny"`：消耗 = 价目表售价 ×（未缓存输入、缓存输入、输出），内部整数**微元**（1 元 = 1,000,000）；1 元/百万 token = 1 微元/token，所以 `charge = round((in−cached)·p_in + cached·p_cached + out·p_out)`。
- 每条账本行**同时**记 token 明细、售价金额 `value_micro`、成本 `cost_micro`、价目版本；额度只看租户所选单位。

### 4.2 账本（只追加，独立于状态快照）

- `<data_dir>/control-plane/usage/YYYY-MM.jsonl`（北京时间月）；每批 settle 先追加 + fsync，再应答网关。启动时扫当月与上月：重建请求编号去重集、本期聚合（租户、账号、模型、日、小时桶）。
- 行：
```
{ v:1, request_id, client_request_id, upstream_request_id, at, started_at, period,
  tid, aid, uid, sid, dev, alias, provider, upstream_model, stream, qa,
  status, outcome: "ok"|"client_gone"|"upstream_error"|"timeout"|"blocked",
  usage: {input, cached, output, reasoning} | null, usage_source: "upstream"|"drained"|"estimated"|"none",
  unit, charge, value_micro, cost_micro, price_version, latency_ms, attempts: [{provider, status, ms}] }
```
- `usage_source`：上游给的 = `upstream`；客户端断开后网关继续读完上游拿到的 = `drained`；拿不到时按已转发内容估算 = `estimated`（界面标“估算”）；上游出错 = `none`（不扣客户额度，成本记 0 并标明可能有上游计费）。

### 4.3 额度

- 套餐（控制面状态，控制台可改；首次从配置 `billing` 导入）：
```
Plan { id, label, note?, quota_unit: "tokens"|"cny", seat_quota (每席位每期，tokens 为整数，cny 为元),
       period: "month"|"week", burst: {hours: 5, pct: 1–100} | null, seat_price_cny | null,
       boost_price_factor, device_limit (缺省 2), alert_thresholds (缺省 [80, 100]),
       enforce_seat_quota: boolean (缺省 false), models: string[] | null }
```
- 租户本期总额度 = 席位 × `seat_quota`（或 `allowance_override`）+ 本期加量；`cap_pct` 照旧（管理员在客户端设、运营只能调低）。
- 个人：账号 `quota_limit`（运营设）> 套餐 `enforce_seat_quota` 时的每席位额度；都没有则个人只显示“占每席位额度的比例（参考，不限）”。
- 滚动窗口（与 Kimi 的 5 小时频率窗口同构）：`burst` 配了即“任意 5 小时内至多用本期总额度的 pct%”，按小时桶算。
- 租约改为**按席位**：`lease {tid, sid, holder, need_estimate:{alias,input,output}, want?, ttl_ms?}` → `{lease_id, unit, units, expires_at, limited_by: null|"cap"|"allowance"|"burst"|"seat", price_version, allowed_aliases|null}`；可发放 = min(租户余量−在途, 上限余量−在途, 窗口余量−在途, 个人余量−在途)。
- 回报：`settle {tid, lease_id, holder, records: UsageRecord[], final}` → `{ok, accepted, duplicates, closed}`。控制面按请求编号去重、按价目版本重算 charge、写账本、更新聚合与租约在途。
- 告警：跨过 `alert_thresholds`（租户与账号各记一次/期）、到上限、额度用完、异常（账号 1 小时消耗 > 租户本期总额度 5% 且 > 其近 7 日小时均值 10 倍）、上游不可用。存最近 500 条，控制台可确认。

### 4.4 客户端视图（`GET /v1/quota`，签名信封 `kwl-quota-view`）

```
{ tid, issued_at, unit, plan: {id,label}, period: {kind, start, resets_at},
  firm: { used_ratio, remaining_ratio, in_flight_ratio, paused: null|"cap"|"allowance"|"burst", cap_pct, boost_pct,
          used, total }   // used/total 只给管理员与合伙人；成员为 null
  burst: { hours, used_ratio, resets_at } | null,
  own: { used_ratio, denominator: "account_limit"|"seat_quota", enforced, used, total, requests, value_cny, estimated_share },
  history: [{ period, used_ratio, legacy: boolean }],
  models: [{ alias, label, share }],
  by_member?: [{ uid, used_ratio_of_firm, used, requests }]  // 管理员与合伙人
}
```

### 4.5 计费

- 本期账单（每租户）：席位费 = 席位 × `seat_price_cny`；加量费 = 席位费 × 加量% × 系数；应收 = 二者之和；用量价值 = Σ`value_micro`；成本 = Σ`cost_micro`；毛利 = 应收 − 成本。价未配的项显示“未定价”，不估。
- 导出 CSV：账单、逐请求明细（按筛选）。

### 4.6 历史迁移

- 旧“单位”账本：本期旧用量冻结为 `legacy_used_ratio`（= 旧已用 ÷ 旧总额度，比例无单位），新账本从迁移时起计，本期比例 = 旧比例 + 新消耗 ÷ 新总额度；历史各月只保留比例（标“旧计量”）。
- `scripts/usage-backfill.mjs`：读网关 `meter.jsonl` 的 settle 行（有真实 token），按当前价目表写入账本（`price_version: "backfill"`），之后本期旧比例清零——有真实数据就用真实数据。
- 旧套餐（`seat_monthly_units`）读回为 `quota_unit: "tokens"`、`seat_quota = 旧单位 × 250`：这是把**已经卖出去的套餐承诺**按原口径（`legal/k3` 每千 token 4 单位）翻译成 token 额度，不用于换算任何用量；控制台提示待商务确认。

## §5 工作线 A：运营控制台（重做）

- 技术：同源静态页、原生 ES 模块、外置 CSS、无构建依赖；`scripts/build-ops-console.mjs` 把 `packages/design-tokens/src/tokens.css` 与页面拼成 `apps/ops-console/dist/`（部署只拷这个目录）。鉴权不变（运营私钥在浏览器内存里签名）。
- 信息架构（左侧导航，顶栏是部署名、全局搜索、刷新时间、运营编号）：
  1. **总览**：本期平台用量（token、用量价值、成本、请求数）、需要关注（告警、即将用完、上游异常）、7/30 日趋势、上游健康。
  2. **客户**：律所列表（套餐、席位、本期用量%、预计用完日、到期、状态）→ 详情（概览、成员与账号、设备、用量、套餐与额度、账单、开通与订阅、操作记录）。
  3. **账号**：搜索邮箱/姓名/律所；状态、最近登录、设备数；详情（设备、会话、用量、个人上限）；停用/启用、发重置码、强制下线、解绑设备。
  4. **设备**：跨律所设备表（版本、最近报到、状态、标记的异常），吊销。
  5. **模型与路由**：上游（地址、密钥尾号、健康、延迟、测试连接）、模型别名（目标与优先级、启停、默认）、价目表（版本历史）。
  6. **用量**：按日/模型/律所/账号的分布，逐请求明细（请求编号检索、筛选、导出），对账提示（估算行、上游错误、待对账租约）。

  8. **计费**：本期账单、历史月份、导出。
  9. **系统**：部署信息、运营名册（只读）、运营访问记录、客户端版本分布、邮件通道状态。

## §6 工作线 E：部署与验收

- 部署：Ubuntu 24.04 + Node 24 + 每角色一个 systemd 单元（cp-signer、control-plane、gateway；检索等按需）+ nginx 只托管控制台静态页；TLS 终止在各服务进程（现有约束）。在本机 Linux 虚机（colima）按手册真实走一遍。
