## 一、设计判断与理由

第 68 批的页面是“一个大数字 + 一根条 + 一张明细表”。用户的评价是内容空洞、留白无效、没有视觉重心、美感不足。逐条看原因：

1. **信息只回答了“用了多少”**。律师打开这页其实想知道四件事：还能用多少、什么时候恢复、照这个节奏够不够、用在了哪。旧页只回答了第一件；第二件藏在条下的小字里；第三、四件没有。
2. **视觉重心是一根细条**。28px 的数字（令牌上限）配一根贯穿全宽的条，右边大面积空着。条上的“今天”刻度是全页唯一说节奏的地方，但要自己比长度。
3. **明细表成了页面主体**。“用在”列几乎全是“任务”，信息量低，却占了首屏一半。

这次的判断：

- **重心改成“两道同心环”**。外环粗，是额度已用（实色）加进行中预留（浅色）；内环细，是本期时间已过，末端一个点表示“此刻”。外环比内环短就是宽裕，长就是偏快，不用读数字也能比。百分比放在环心。字号受令牌限制最大只有 28px，靠 160px 的环撑起重量，而不是另起一个字号。
- **环旁三个读数，回答“还剩、何时恢复、够不够”**。剩余（另说预留或受限原因）、距重置（“4 天后”大字，日期小字）、节奏（宽裕 / 偏紧 / 偏快 / 已用完 / 还没用，加一句依据，例如“按日均 3.8% 估算，约 11 月 29 日用完”）。节奏是真实计量算出的判断，不是装饰。
- **“每天用了多少”是新增的唯一一张图**。本期每天一根柱，同一分母；今天用 Kimi 蓝，其余中性灰；没用的日子画基线点，今天之后的日子画浅点。虚线是“每天用多少恰好期末用完”（1 ÷ 本期天数），柱子高过虚线就是那天用得比均匀快。悬停或键盘聚焦一根柱，标题右侧的读数换成那一天（日期 · 百分比 · 调用次数，任务与问答分开）。读数固定在标题行，不用浮层，截图里也看得到。
- **“用在哪”与“套餐”并排成两张小卡**，占一行，不再各占一整屏宽。用途用一根分段条（任务蓝、问答灰）加两行数字，两者相加等于环心的已用。按模型用细条，按计入额度排序。套餐卡只放套餐名、说明（去金额）、可用模型、“需要更多额度：请联系客户经理或客服”，管理员多一句“团队用量与上限请在云端控制台管理”。不做假购买入口。
- **最近记录降为页尾的精简列表**。按日分组，组头带当天合计（“40 次 · 计入 4.4%”，来自按日聚合，与柱子同一口径）；首屏 6 条，再往前从云端账本翻页。
- **颜色克制**。只有额度与“今天”用 Kimi 蓝，其余一律中性灰；状态色只给状态句、节奏圆点与用超时的环。深色模式全部走令牌。

## 三、数据口径（每个数字从哪来）

全部来自控制面 `/v1/quota` 签名信封（内核 `quota.status` 原样透传）与 `/v1/quota/usage` 翻页；比例都以 **personalDenom**（个人上限 > 单席位律所总额度含加量 > 每席位额度）为分母，不出现金额、点数、token 数。

| 界面数字 | 字段 / 算法 |
|---|---|
| 环心“已用 4.5%”、环外圈实色 | `personal.used_ratio`（= usedIn(本人本期账本) + 迁移前已用，÷ personalDenom） |
| 环外圈浅色（预留） | `personal.in_flight_ratio`（本人席位在途租约） |
| 剩余 95% | personalView().left = 1 − 已用 − 预留，被额度 / 律所上限 / 个人额度卡住时取 `personal.remaining_ratio`（5 小时窗口不压低月度剩余，单独一行）；fmtLeft 向下取整 |
| 重置“4 天后”“12 月 1 日 00:00” | `period.resets_at`（北京时间） |
| 内环、“本月时间已过 85%” | (now − `period.start`) ÷ (`resets_at` − `start`) |
| 节奏 | 日均 = 已用 ÷ max(1 天, now − max(本期开始, 第一次有调用那天 0 点))；期末 = 已用 + 日均 × 剩余时间；≤85% 宽裕、≤100% 偏紧、>100% 偏快并给出 now + (1 − 已用) ÷ 日均 那天；已用 ≥100%（且分母是真限制）= 已用完；0 = 还没用。旧云端没有 daily：只按本期开始算，不报日均 |
| 每日柱高、读数百分比 | `personal.daily[].ratio`（云端按北京日聚合，splitRatios 保证各日之和 = used_ratio） |
| 读数调用次数（任务 · 问答） | `daily[].requests`、`daily[].qa_requests` |
| 均匀线 3.3% / 天 | 1 ÷ 本期天数（同一分母） |
| 用在哪：任务 / 问答 | `personal.by_kind.task/qa.{ratio, requests}`（两者之和 = used_ratio） |
| 用在哪：按模型 | `own_models[].used_ratio`（各模型之和 = used_ratio）、`requests`；旧云端只有 `share`（处理量份额） |
| 最近记录组头合计 | 同日的 `daily[]`（与柱子同一口径） |
| 最近记录每行 | `own_recent` / 翻页 `rows[].charge_ratio`（ratio_basis = personal，不再折算）；未计入原因按 partial / pending / outcome |
| 5 小时频率限制 | `burst.used_ratio`（窗口分母）、`burst.resets_at`；仅单席位 |

真实账号（本机栈、试用、单席位、2026-11-26 13:10）实测：`used_ratio 0.0448`；`daily = [{2026-11-26, 0.0448, 19 次, 问答 2}]`；`by_kind task 0.0434 + qa 0.0014 = 0.0448`；`own_models K3 used_ratio 0.0448`；三者与大数字逐位相等。

## 四、接口变更（云端）

只追加、不改已有字段：

- `GET /v1/quota` 的 `personal` 追加
  - `daily: { day: "YYYY-MM-DD", ratio, requests, qa_requests }[]`：本期、本人、只含有调用的日子，北京日期升序；
  - `by_kind: { task: { ratio, requests }, qa: { ratio, requests } }`；
- `own_models[]` 每项追加 `used_ratio`（计入本人额度的比例）。
- 口径：与 `used_ratio` 同一分母（personalDenom）、同一计费口径（`usedIn(quota_unit, Agg)`，账本同一批行）。用 `splitRatios`（逐份累加后取相邻舍入之差）折比例，各日之和、任务 + 问答、各模型之和都**恰好**等于 used_ratio（迁移前的已用 legacy 作起点偏移，不分到天）。
- 实现：`usage-ledger.ts` 新增“成员 × 用途 × 日”索引 `byMemberKindDay` 与 `memberDaily()`、导出纯函数 `splitRatios()`；`server.ts` 只动 `/v1/quota` 的 personal 段与 own_models 一行。
- 内核 `control-plane/client.ts` 的 `QuotaView` 与桌面 `api.ts` 的 `QuotaStatus` 同步追加可选类型（内核原样透传，无白名单）。
- 旧云端兼容：没有 `daily` → 每日用量卡整块不显示（不拿 own_recent 20 条拼）；没有 `by_kind` → 用在哪只显示按模型；`own_models` 没有 `used_ratio` → 按模型改写“（占处理量）”用 share；节奏只按本期开始算、不报日均。

## 八、遗留

1. **最近记录的“用在”仍只有任务 / 问答**，没有任务名或事项简称。云端账本只有元数据（不该知道事项名）；要做得在本机把 `client_request_id` 对回运行记录：控制面在 own_recent / 翻页行里带上 `client_request_id`（内核自己生成的编号，不敏感），内核按本机运行日志换成“金额测算 · 锐川诉禾丰”。涉及内核与闸门白名单，本批没做。
2. **试用到期日**（V41 评审提过）：quota 信封没有许可到期时刻，套餐卡只能写“自助注册试用 14 天”。需要控制面在 `plan` 里追加 `trial_ends_at`。
3. **新账号月中注册**：本期开始到注册日之间的日子也画成“没用”的基线点；quota 里没有注册日，暂不区分。
4. **节奏是线性估算**：只按日均推期末，不考虑周末；文案写了“按日均 … 估算”。
5. 字号受 7 级令牌限制，环心大字仍是 28px（V41 建议 44～48px）；靠 160px 的环补重量，没有另起令牌。
6. 未在 Electron 正式包与 Windows 上看过，只在网页形态（vite + 开发桥）验证。
