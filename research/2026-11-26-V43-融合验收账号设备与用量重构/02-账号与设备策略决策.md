# 02 账号与设备策略：达到电脑数上限时怎么办（第 69 批，D-297）

## 1. 问题

每个账号能同时使用的电脑数由云端设定（账号单独设的 > 套餐 > 缺省；第 68 批 D-295）。律师在第 N+1 台电脑上登录时，两种做法：

- **A 自动替换**：云端自动移除一台旧电脑（例如最久没用的），新电脑直接登录；
- **B 用户选择**：列出已登记的电脑，由律师选一台移除，再继续。

第 66 批曾用 A（个人账号满 20 台滚动吊销，D-293），第 68 批改为 B 的雏形（逐行“移除”按钮，D-295）。本批从第一性原理重新比较，并把选定的方案做完整。

## 2. 比较

| 维度 | A 自动替换 | B 用户选择（本批做法） |
|---|---|---|
| 用户体验 | 新电脑上零操作；但被替换的那台在律师不知情时掉线，律师回到那台电脑只看到“已退出”，不知原因 | 多一步“选一台、点移除”。本批把这一步降到**一次点击**：默认预选最久没用、不在登录中的一台，主按钮直接“移除并继续” |
| 用户自主权 | 系统替律师决定掉哪台；“最久没用”不等于“不再用”（出差两周的办公室电脑最久没用，却是主力机） | 律师看见每台电脑（Mac / Windows、最近使用、是否登录中）后自己决定 |
| 账号安全 | 拿到密码或验证码的人可以**悄悄挤掉真主人的电脑**，真主人只看到被踢下线；被挤掉的电脑在云端吊销后不能再用这个账号登录（见 §4），等于盗用者能让真主人的电脑失效 | 移除是一次显式、可审计的操作（审计 `device.unbind`）；列表里出现陌生电脑本身就是盗用信号；正在登录的电脑标“登录中”并提示会立即停用 |
| 业务连续性 | 被替换的电脑可能正在跑 20 分钟的起草任务，任务中途失去 AI；律师在另一台电脑上不知道发生了什么 | 正在使用的电脑不会被默认选中；选中时明确提示“那台电脑正在使用，移除后立即停用；那里的资料如还要用，先在那台电脑上备份” |
| 实现复杂度 | 云端一处逻辑；但要额外做“被挤掉”的通知与解释，否则体验不可接受 | 云端已有就地移除（第 68 批一次性票据）；本批只补列表信息与界面 |

**结论：B，用户选择 + 默认预选。** 它在体验上接近 A（一次点击），在安全、自主权与业务连续性上明显优于 A。A 的唯一优势“零操作”在这个产品里不成立：被替换的那台电脑上的这个账号是**终局停用**（§4），这种后果必须由律师本人确认，不能由系统替他做。

## 3. 落到代码的部分

| 位置 | 改动 |
|---|---|
| 云端 `server.ts` `deviceSummaries` | 电脑数已满（登录时的 onboarding、自动登记时的 409）与 `/v1/auth/me` 的设备列表，每台补：平台（这个账号在那台电脑上最近一次会话报的 platform）、最近使用时刻（会话级）、是否登录中；按最近使用从新到旧；不含 IP、网段等定位信息 |
| 云端编号空间 | 团队成员的设备编号原来只在 1～9 里取、吊销过的不复用——换过 9 台（含已移除）后即使在用的远不到上限，也回“已满”且**列表为空**，无处可移除（与云端配置无关的隐性上限）。改与个人账号同一空间（_D999）；同时在用几台仍只由 `deviceLimitOf` 管 |
| 内核 | 把云端设定的上限 `device_limit` 带给界面；客户端**不另设任何上限**（全仓检索 `device_limit` 只有展示与转发） |
| 界面 `DeviceLimitList` | 整卡“电脑数已达上限”：一句“这个账号最多同时在 N 台电脑上使用”（N 来自云端）→ 单选列表（电脑类型、最近使用、版本、“登录中”）→ 默认预选 → “移除并继续” → 一句后果说明 → “返回登录”。开通页与重新登录页（换账号）共用；重新登录页里外层标题让位，一张卡只有一个标题 |
| 界面 设置 → 账号 | “我的电脑”列表同一说法（Mac 电脑 / Windows 电脑），第 10 台起编号显示正确 |
| 被移除的电脑 | 见 §4 |

## 4. 真实验收中发现的问题：被移除的电脑

本机全链路栈上：D 只许 1 台、已在电脑 ws-d 上使用；在 ws-main 上登录 D → 选中 ws-d（“Mac 电脑 · 登录中 · 最近使用 刚刚”）→ 移除并继续 → D 在 ws-main 打开。回到 ws-d：

1. 界面照常显示工作区，直到下一次同步（≤10 分钟）或下一次用 AI；
2. 用 AI 时报“出站闸门拦截：这台电脑已被**律所**停用……请联系本所管理员”——对个人账号是错的（是他本人在另一台电脑上移除的）；
3. 退出后用 D 重新登录：被拒，“这台电脑已被律所停用，不能再使用中软服务”。而第 68 批的移除确认写的是“之后在那台电脑上重新登录即可再用”——**与实际不符**。

根因：移除 = 云端吊销那台电脑的设备证书。第 68 批安全复核 U-1 有意规定“同一账号在已被移除的电脑上不签名重登不算成功”；吊销后的电脑也不再备份、不再导出明文（复核 R2A-16、R15A-04：防止丢失电脑上的案卷被复制）。吊销是终局的，这是正确的安全设计。

处置（本批）：**不改安全设计，改为如实告知并给出可做的事**。
- 移除确认：“移除后那台电脑上的这个账号随即停用（不能再用 AI、备份或导出）；那里的资料如还要用，先在那台电脑上备份。”（正在登录的：“那台电脑正在使用，移除后立即停用；……”）——后果在做决定时说清；
- 被移除的电脑：内核在设备已吊销时把要重新登录的原因报为 `device_revoked`，整窗页面标题“这台电脑已从账号移除”，一句“这个账号不能再在这台电脑上使用，本机资料仍加密保存在这里。可以登录其他账号。”，直接给其他账号的登录框；
- 文案去掉“律所停用 / 联系本所管理员”的说法（个人账号是本人移除；团队账号由管理员移除，“已从账号移除”两者都对）。

遗留（建议下一批）：被本人误移除的电脑想恢复使用，目前只能作为新电脑重新登记（新的空工作区），旧工作区的资料要靠移除前做的备份恢复。若要支持“在原工作区上重新登记”，需要在内核为同一账号的已吊销档案换发新设备身份并重新包裹事项密钥，属于安全设计变更，要单独评审。
