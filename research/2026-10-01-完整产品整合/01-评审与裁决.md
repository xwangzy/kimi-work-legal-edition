## 2. 评审标准

用同一把尺子评八个维度，每个维度回答一个具体问题：

| 维度 | 具体问题 |
|---|---|
| ① 前提契合 | 是否符合已明确的前提：中软自建托管 SaaS、本机 exe（类似 Kimi Work 桌面版）、借用 Kimi Work 设计、后端接入 Kimi Code 部分能力、席位收费、token 为成本、四类入口、按角色定义价值、逐场景交付件与验收、内容与数据资产 |
| ② 律师价值与功能效果 | 律师为什么天天用、合伙人为什么付钱；交付件能否进入真实工作流；第一次使用多久见到价值 |
| ③ 交付件与验收 | 每个场景是否有文件级规格、可执行的验收方法（样本、分母、标注、判定、置信区间）与失败降级 |
| ④ 工程可行性 | 复杂度与阶段是否匹配；关键路径是否识别；外部依赖是否有探针与替代；人力与周期是否算得过来 |
| ⑤ 安全、合规与可信 | 数据流是否如实；权限、隔离、注入、恢复、签发与标识是否可验证；合规是否落成可交付的动作 |
| ⑥ 内容与数据资产 | 谁生产本所标准与方法、产能多少、质量线、法源权利、长期壁垒 |
| ⑦ 商业闭环 | 版本、价格、额度、成本、毛利、盈亏、渠道、谈判清单是否成套且算得过账 |
| ⑧ 组织与可执行 | 编制、路线、阶段门、30 天行动是否能直接开工 |

## 4. E（astra v1.1，09-30）评审

### 4.1 优点

1. **措辞与证据纪律是全部材料里最好的。** 每个数字都标为假设或待测目标；区分“当前 demo / 待实现 / 可售”；删除“零幻觉”“国内唯一”“下载即可交付”等口径。对一家香港上市公司，这直接关系到对外披露与销售承诺的风险，应整体继承。
2. **可信交付的状态语义完整。** 引用分“来源真实 / 版本与元数据 / 支持命题 / 律师确认”四个独立维度；生成方无权写“已核验”；签发绑定最终字节 hash；受众版本先生成后签发；外部变化触发影响分析与更正，不改写历史签发件。
3. **工程契约达到生产级。** 领域对象与权威记录、接口示意、Run/Attempt 与租约 fencing、幂等键、外部副作用 UNKNOWN 对账、取消传播、备份恢复后重放撤权与删除——这是多租户法律 SaaS 不出事故的底座。
4. **验收设计最严谨。** 300 个独立业务任务（120/60/60/30/30）、数据族隔离、双标盲审与第三方仲裁、按文档簇重采样的置信区间、稳定性重复运行、G2 再加 60 个新任务；专项测试单列不进分母。D 的评测集（合同 60 份覆盖 24 套 Playbook）样本过薄，E 的批评成立。
5. **数据去向如实。** 五种处理模式分别命名；化名映射表按模式明确位置；“不能为了提高召回自动降低保密策略”。
6. **权利分层清楚。** Kimi Work 设计与标识、Kimi Code 源码、Kimi 企业 API、法律数据与连接器四类权利分别落实，不互相推导。
7. **统一云端执行，单一内核。** 不在律师电脑上再维护一套通用 Agent 内核与第二套恢复、预算、密钥体系，测试面与安全面减半。Hosted Agents 不一概否定，设 H1–H8 准入门做对照 PoC。
8. **36 个原场景逐卡落地。** 每卡写清角色、入口、输入、边界、交付、复核、验收、阶段；刑事四场景归入受限研究，理由充分。
9. **经济口径诚实。** 补上 K3 缓存写入、重试、OCR、法源、支持、折扣与渠道；区分平均席位与年末 ARR；明示第三年仍亏损。
10. **服务运营闭环完整。** 开通、额度、SLA、RPO/RTO、质量事故、删除回执、退出迁移都有定义。

## 5. D（opus v3.0，09-28）评审

### 5.1 优点

1. **产品完整、具体。** 角色—价值矩阵含工作、关键时刻、指标、触点与付费逻辑；四端一云写到宿主版本与平台能力边界；信息架构与交互规则（计划先行、失败说人话、双向联动、导出前受众检查）；一个事项在四端之间流转的完整故事。
2. **入口技术细节扎实。** Word 三层（直出修订稿 / COM / Office.js）、WPS 安装与 Mac 边界、IM 五条路径与平台限额（文件只在单聊收、5 分钟下载链接、每小时 1,000 条推送等）、个人微信只接收主动导出的文件。
3. **内容与数据资产可执行。** A–G 资产地图与归属；法源“官方原文自建为底、授权检索补覆盖”、Source Registry；Playbook 结构与 24→40→60 的产能；确定性规则库；67 类要素式模板；评测与任务环境；联合后训练的条款要点；方法资产保护。
4. **商业方案成套。** 四个版本与价格、价格锚点表、对 Kimi 企业版的销售对比表、价格验证与备选档、单位经济、三情景盈亏与资金需求、与月之暗面的 P0–P2 谈判清单。
5. **合规落到功能。** TC260 部署指引逐条对照、AIGC 隐式标识实现规格、应用登记默认准备、《律师法》2026 修正后的新条号、判例对产品的要求、刑事材料政策。
6. **Kimi Code 源码级风险清单。** 2.1.1 回滚加固、遥测默认开启、ACP 只代理文本文件读写、Hook 失败放行、Windows 问题；补丁优先级。
7. **6 周 demo 计划与十项探针**，并给出极具说服力的标准演示用例（《律师法》第三十八条已改为第四十一条，核验拦截并提示改引）。

### 5.2 缺点与工程风险

| # | 问题 | 对功能效果或可行性的影响 | v4.0 处理 |

| D9 | 案号“12345/1111”被写成幻觉拦截规律 | 可能误拦真实案号 | 只作低置信提示，存在性以授权来源核验 |

## 6. 争议点逐项裁决

“采用”指进入 v4.0 基线；“新增”指两份都没有、本轮补上。

| # | 议题 | E（astra v1.1） | D（opus v3.0） | v4.0 裁决与理由 |
|---|---|---|---|---|

| 律所管理系统（iCourt、法蝉等）没有公开 API，核心流程独立跑通 | 不把关键路径押在第三方 | 第 2 篇 §6 |

**不沿用**：插件包 + 独立 Companion（客户端是自有的）；L1/L2/L3 授权分层与 OEM 依赖；网关作“分成账本”、Token 分成作收入；托管执行推迟到 V2（IM 与批量离不开云端执行）；采集官方法规站点建库；“律所自己买 K3 自训承担不起”的断言；“刑事材料本地 Agent 即可处理”（本地 Agent + 云端模型不等于本地处理）。

## 10. v4.0 的整合原则

1. **E 的纪律 + D 的完整度。** 措辞、状态、门禁、样本、数据去向用 E；体验、入口、内容、商业、合规动作、demo 用 D。
2. **一个内核、一个事实库。** 所有入口共用云端事项、权限、成果、权益与审计；律师电脑上不跑第二套通用 Agent。
3. **桌面价值不打折。** 用本机能力层承接“类似 Kimi Work 桌面版”：挂载事项文件夹、本机原件模式、在 Word/WPS 里直接落修订、离线阅读。
4. **按交付件定义完成，按证据决定上架。** 生产、Beta、模板三档由后台登记，销售资料与产品内同源。
5. **把钱花在关键路径。** 关键路径依次是：月之暗面数据条款与配额 → 材料解析与锚点 → 文书引擎与宿主修订 → 规则包与评测 → 试点交付 → 收费运营。渠道扩展、第二家 IM、Hosted Agents 不挤占它。
6. **分阶段拨款、设止损线。** 每个阶段门同时看质量、安全、付费意愿与单位经济，任何一项不过就收缩范围或停止。
