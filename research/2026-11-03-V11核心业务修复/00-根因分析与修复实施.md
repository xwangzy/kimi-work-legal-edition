## 1. 问题清单与根因（已证实 / 待验证）

### 1.1 “要文书却交了 Excel / 没交 Word 却显示已完成”（P0，已证实，已修）

根因不是提示词写得不够，而是**交付格式没有作为结构化约束一路传到结算**：

| # | 失败情形（确定性用例复现） | 根因 | 提交 |
|---|---|---|---|
| F1 | 首页自由描述“帮我起草一份股权转让协议”，助手没加载方法、只交一张表 → 记“已完成” | 没加载方法时主交付物为 null，整段核对跳过 | `d5e2ec7` |
| F2 | 起诉状只交表（已记部分完成），追问“补出起诉状”只答文字 → 记“已完成” | 追问不带方法与主交付物，追问提示词方法行为空 | `d5e2ec7` |
| F3 | 回稿重审卡（主交付物《变更清单》.xlsx）+ 律师写“给我 Word”，只交表 → 记完成 | 律师点名的格式在快照里不存在，无从核对 | `d5e2ec7` |
| F4 | “出 Word / 给我 Excel / 不要 Excel / 要 PDF”全链路没有结构化字段 | 同上 | `d5e2ec7` |
| F5 | 原地记录客户同意或重新估价后发起，`primary_output` 丢失：尽调“发现与报告”退回《尽调清单》.xlsx；修订说明“致对方”变成致客户版（露底线风险） | RunSheet 两处手抄发起选项漏了 primaryOutput（界面走查也复现） | `d5e2ec7` |
| F6 | 成果已入库、结算前中断，按检查点恢复后直接记“已完成” | 检查点分支跳过主交付物核对 | `d5e2ec7` |
| F7 | 受限命令行写出的“合同.docx”其实是改名的表格，被算作“已交出 Word” | 只查外取引用，没查主部件 | `d5e2ec7` |
| F8 | “帮我起草起诉状，违约金分段计算”被建议成只出 Excel 的“金额测算”卡 | 只认“起草一份”，不带量词时取不到要交付的短语 | `ee14483` |
| D10 | 律师点名要法律意见书，顾问答复卡的主交付物仍是《顾问答复》 | 卡上写了却没有选项与 primaryBy | `ee14483` |

修法：`deliverableRequest`（纯函数、规则写明）只认三类结构化信号——点名格式（要的动作 + 格式词、并列、“不要 / 只要”排除；提到材料格式不算）、改原件（勾选了 .docx 且有改原件动作；“修改建议”“改了哪些”不算）、起草文书（起草 / 出具 + 文书名，后接清单 / 表 / 目录不算）。发起时写进快照，`requiredDeliverables` 合并方法主交付物、点名格式、文书意图与追问继承的上一轮缺失项；提示词的【交付要求】与结算核对同源。**失败方向是安全的**：误判只会多要一份交付件（记“部分完成”），不会把表格当文书放行。

待验证（环境受阻）：加【交付要求】后模型是否改用 `docx.render_report` / `docx.revise` 交 Word；自由描述时模型先加载哪个方法（F11：“处理一下对方回稿”可能先加载 redraft-review）。

未修：F9（“对方回稿了，按我们的意见把回稿改好，给我 Word”建议成回稿重审卡，需产品确认 doc-revise 与“回稿”排除词的优先级；F3/F4 修好后至少不会再显示完成）；F10（起草合同只交附件《起草说明》.docx 也算“已交出 Word”，按文件名匹配不可靠，建议把方法 outputs 写进快照后排除非主交付物）。

## 3. Skills 与工作流：本轮做了什么、没做什么

- 做了：把“交付什么”从提示词里的一句话变成快照里的结构化约束，由内核在结算时强制核对（§1.1）；把“法律依据核验”在提取与判定两端补到一票否决类问题清零（§1.2）；修订引擎在复杂结构下守住“只改该改的”（§1.3）。

## 4. 律师级文书质量评价

**本轮没有新的模型生成文书，因此没有新评分。** V10 的 18 份独立律师评分（13～18 / 24，无一可交付，短板为分析深度）仍是最近一次真实质量数据。本轮修复对质量的预期影响：
- 编造或过时的依据、案号不再以“已核”进入签发版（直接降低“虚构法律依据”一票否决风险）；
- 文书类任务不再以表格或纯文字记“完成”（降低“不可用文件 / 交付类型错误”）；
- 修订稿在交叉引用、两轮修订、分节、合并单元格下不再写坏（降低“格式保真度 / 人工修改成本”）。
以上是机制层面的改进，**能否把评分拉到可交付须真实模型复测**。
