## 3. 工作线 A：界面与体验

### 3.1 方法库：从卡片墙改成目录（P1）

**问题（main，综合 6.1：美学 6 / 架构 5.5 / 焦点 5 / 层级 6 / 留白 6.5 / 效率 6 / 品牌 7.5）。** 48 张等大的卡片按业务线平铺，后面再把 33 个方法模板重复列一遍（其中 32 个就是上面的卡）；不能搜；页首一张整宽的“自由描述任务”卡抢在目录前面；页面叫“方法与模板”，侧栏叫“方法库”。

**改法。**
- 一份目录：业务线 → **办案阶段**（诉讼：接案与案情 → 起诉与应诉 → 庭审 → 执行与汇报 → 劳动争议；非诉：合同 / 交易与尽调；企业法务：合同与合规 / 纠纷应对 / 劳动用工；通用：研究与意见 / 文书加工）。阶段名在左侧成一列，随滚动停在顶部。
- 每个方法一行（与首页场景行同一种写法）：图标 + 名称 + 得到什么 + 需要什么；悬停图标反色、出现“开始”。
- 页首搜索（标题、交付件、需要的材料、常用说法都能搜，多个词都要命中，跨业务线）；业务线胶囊带数量；“本所范本”在胶囊行右端。
- “通用方法模板”一节撤掉；“自由描述任务”收成目录后的一行出口，搜不到时也是它。
- 分组只是展示顺序（`lib/method-catalog.ts`），没列进阶段表的新卡自动落到该线末尾的“其他”，用例会提醒。

文件：`pages/Methods.tsx`（重写）、`lib/method-catalog.ts`（新）、`styles-methods.css`（新）。

### 3.3 开始面板：三段，任何任务都有上传入口（P0，与 §4 一起看）

**问题（main，起诉状空事项，综合 5.6）。** 只有“拟受理法院”和“补充要求（可选）”；没有材料的事项连“添加文件”都不显示（`ScenarioStart.tsx` 原第 295 行：只有“卡片强制材料”或“事项已有材料”时才渲染材料区）；两只并排的描边盒子“你给什么 / 你得到什么”。

## 4. 工作线 B：法律 Skills 的开工前收集（P0）

### 4.1 证据：缺口在三层

审计 A（33 个方法、48 张卡全部覆盖，逐条带行号）与一单真实基线：

- **界面**：起诉状卡只有 `court` 一个字段、`minMaterials: 0`。这是当初写进文件头的设计原则——“只保留 ≤ 3 个字段，其余由 Agent 在计划阶段追问”。
- **内核**：Agent 任务发起前不检查事项是不是空的，提示词里也不说。
- **方法**：先读事实与材料，再“一次问清不超过 3 问”，成文前再等一次论点确认——律师至少等两轮。
- **真实基线**（`01-…` §1）：空事项“软件著作权侵权（原告）”起草起诉状，2 分 10 秒后助手拿《民法典》第 577 条（合同违约）来列论点，并自述“为避免把‘软件’公司名称误当成软件开发合同纠纷…”——它只能凭事项名称猜。

审计还查出：卡上收的字段都进了提示词（没有收了不用的），但字段名与方法声明的参数大面积对不上且无用例；8 张卡的“你得到什么”与方法实际交付物不一致。

### 4.2 原则改了（D-219）

取代“≤ 3 个字段，其余由 Agent 追问”：

1. 律师开工前就知道、又决定文书怎么写的，开始面板直接收：没有材料时的案情、逐项请求、不可逆期限的起算日、只有律师能定的取舍；
2. 读完材料才知道的（材料之间的矛盾、合同里几种计息口径）才在任务中问，并且和论点确认并成一次；
3. 事项里已有的（立场、当事人名称、阶段、事件时点）不重复收；
4. 不给每张卡堆大表单：必填项和两三个高频项直接显示，其余收进“更多选项”。

### 4.3 落地

**数据模型（`lib/scenarios.ts`，最小改动）。** 字段多一种 `list`（逐项）与三个可选属性 `goalOnly`（只进任务说明、不作方法参数——方法参数每项至多 300 字，长文字会被截断）、`more`、`help`；卡片多一个可选的 `brief`（案情入口）。`values`、`buildGoal`、`skillArgsOf` 的签名都没变。

**案情存成材料（审计 A 的建议，采纳）。** 律师写的案情在开始时存成本事项的一份材料《案情说明（律师口述）日期.txt》，用途标“我方”，任务说明里只写一句指向它。理由：事实的引文要回链到材料（`facts.submit` 的 `quote` 与 `document_version_id`）；材料走现成的令牌化与发送摘要；下一个任务直接能用。按“律师陈述、待确认”对待，不进证据目录——这条写进了签名分发的工作准则第 6 条。勾了别的材料时它一并勾上；一份都没勾（＝可读全部）时不单独勾，免得把范围缩成只有这一份。

**八张卡可以直接写案情**：起诉状、仲裁申请书、律师函、金额测算（“或直接告诉我本金与日期”原来没地方写）、案情分析、两张访谈卡（原来至少要一份材料）、代理词（没有笔录时的庭审要点）。其中案情分析与两张访谈卡的最少材料数由 1 改 0。

**起诉状卡**：案情 + 逐项诉讼请求 + 拟受理法院 + 更多选项（管辖依据、财产保全、当事人信息）。仲裁申请书：仲裁请求改逐项 + 当事人信息。律师函：加“要求对方做什么”“发函名义”。

**预检**：没有材料、没有任何事实、也没写案情时，面板不让开始（纯函数 `caseGap`）；事实数读不到时不拦。

**内核【开工前已知】（D-220）。** 提示词【任务】后加一行，数字由内核自己从库里算（不信任界面传值）：本次指定材料几份、本事项共几份（读不出文字的几份）、已确认事实几条、待确认几条；固定句“任务说明与方法参数里律师已经写明的不再问”；空事项时再加“案情以任务说明为准，不必先查材料目录；任务说明里也没有案情的，第一步就一次问清，不要先起草”。只有数字与固定句，与任务说明走同一条令牌化路径；追问不加。

**方法正文（重新签名打包，33 个方法、53 个文件）。**
- 工作准则第 6 条补三段：开始时写明的不再问；一次任务里打断律师以一次为宜（有论点确认步骤的并进那一次）；《案情说明（律师口述）》的处理口径。

**契约用例（新）。** `apps/desktop/test/b55-skill-contract.test.ts`：卡片会传出的字段键都在方法参数里声明（每卡不超过 8 项）；卡片“你得到什么”与方法交付物对得上（主交付物必须一致）；7 个文书方法的 `outline.submit`、`citations.verify`、`docx.render_report` 步骤与专属管辖判断一条没少。首轮查出的 8 张卡已全部改成与方法一致，豁免清单为空。
