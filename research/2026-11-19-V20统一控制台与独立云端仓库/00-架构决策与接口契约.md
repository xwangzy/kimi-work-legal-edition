## §1 双控制台：现状与结论

**现状（证据见审计）**：代码里网页控制台只有一个 `apps/ops-console`，但“管理控制台”实际有两套，再加一套命名混乱：

| | 运营控制台（网页） | 律所管理（Windows 客户端“设置 → 管理”） |
|---|---|---|
| 使用者 | 中软运营 | 律所管理员、合伙人 |
| 身份 | 运营名册（安全管理员签发）+ 私钥签名或第 45 批密码（凭据文件） | 律所根签发的管理员设备证书 |
| 接口 | `/v1/ops/*` | 设备签名接口（`/v1/quota/cap`、`/v1/invitations`、`/v1/join-requests/*`、`/v1/drafts*`…） |
| 密码/会话/锁定 | `ops-auth/password.ts`：5 次锁、30 分钟/8 小时、内存会话 | `accounts.ts`：10 次锁、12 小时/7 天、持久会话 |

文档里同一个网页又叫“云端控制台（额度台）”（部署-云端控制台与桌面端对接.md 标题）与“运营控制台”（页面标题），开发脚本两套（`dev-ops-console.mjs` 5480、`demo-launch.mjs` 8790）。

**问题**：
1. 两套人员身份、两套密码/会话/锁定实现，策略数值不一致；凭据文件两个写者无锁（审计 cloud §9-7）。
2. 律所管理员要做的账号停用、下线、设备数、个人上限只有中软运营能做（`/v1/ops/accounts/*`），律所自己没有入口；月度上限两个入口写同一字段。
3. 运营权限没有角色，读接口一律 `tenant.read`；密码登录单因素、无复核（cloud §9-4、§9-8）。
4. 每给律所管理加一个云端功能就要改客户端白名单并发新客户端（client §9-11）。

**结论（D-192）**：**一套云端控制台 + 一个后端（控制面）+ 一套账号体系 + 分角色分区**，不保留独立运营入口。
- 一个登录页：律师、律所管理员、中软人员都用邮箱 + 密码；中软人员必须两步验证。
- 三个分区按身份出现：**我的**（所有账号）、**本所**（律所 admin/partner）、**平台运营**（中软人员，按角色出现子页）。
- 平台运营接口仍只对运维网段开放（生产入口 `ops.allow_cidrs`）；控制台本身可对公网开放，网段外的中软人员登录被拒（`staff_network`）。
- **必须留在客户端的**（依赖律所根私钥、管理员设备签名或本机密钥纪元）：批准入组、策略/连接器签名与发布、停用电脑（本机纪元递增）、生成邀请码、恢复包与备份、离所交接。网页“本所”只读展示这些状态并写明“在管理员电脑上完成”。
- **迁到网页的**：本所用量（按成员/模型/日）、月度上限、成员账号停用/启用/下线/重置码/设备数/个人上限、本所账单、待批准列表（只读）。客户端里的同名功能保留（不删，避免已装客户端退化），之后以网页为主。

## §2 统一账号（D-193）

### 2.1 两种记录、一套机制
- **成员账号** `AccountRecord`（第 44 批，不改语义）：绑定律所 `tid` + 成员 `member_slug` + 律所角色 `admin|partner|lawyer|assistant`。
- **平台人员** `StaffRecord`（新，控制面状态 `staff`，随快照封装落盘）：`{aid: "stf_<16>", email, name, roles: PlatformRole[], status, disabled_reason, pw, pw_changed_at, created_at, created_by, last_login_at, failed, mfa: {totp: {secret_sealed|secret, enabled_at} | null, pending: {...} | null, recovery: string[] (HMAC)}}`。
- 两种记录**共用**：邮箱唯一（跨两表）、密码规则与 scrypt、会话表与令牌 `kws1.`、登录失败锁定（统一为同账号 15 分钟内 10 次锁 15 分钟 + 按来源每分钟 20 次）、一次性码（设置/重置）、登录审计。删除 `ops-auth/password.ts` 的控制面用法（文件保留给旧部署读取的说明见 §7 迁移）。
- 平台人员**不能**登录桌面客户端（`client.platform !== "web"` → 403 `staff_client_forbidden`），**不能**调成员接口（`sessionOf` 只认成员账号）；成员账号不能获得平台角色。

### 2.2 角色与权限（RBAC）
权限名沿用 `OPS_PERMISSIONS` 并新增读权限与人员权限：`account.read`、`usage.read`、`billing.read`、`route.read`、`system.read`、`staff.manage`、`settings.manage`、`account.support`。

| 角色 | 中文 | 权限 |
|---|---|---|
| `sysadmin` | 系统管理员 | staff.manage、settings.manage、route.manage、tenant.purge + 全部读 |
| `operator` | 客户运营 | tenant.manage、tenant.terminate、quota.manage、quota.cap、plan.manage、account.manage、account.support、device.revoke + tenant/account/usage/billing/route.read |
| `issuer` | 开通专员 | activation.issue + tenant.read、account.read |
| `finance` | 财务 | tenant.read、usage.read、billing.read |
| `support` | 客服 | account.support + tenant.read、account.read、usage.read |
| `viewer` | 只读 | 全部读 |

- 一人 1–3 个角色；`operator` 与 `issuer` 互斥（沿用 tenant.manage ⟂ activation.issue 的职责分离）。
- 至少保留一名有效 `sysadmin`；不能停用自己、不能去掉自己的 `sysadmin`。
- `opsSpec` 的读接口按域改权限：账号 → account.read，用量 → usage.read，账单 → billing.read，路由 → route.read，系统/访问记录 → system.read，其余 tenant.read。

### 2.3 两步验证（TOTP，RFC 6238，SHA-1、6 位、30 秒、±1 步）
- 策略 `console.staff_mfa`：`required`（生产缺省）| `optional`（开发）。
- 登录：密码对 → 已启用 TOTP 的应答 `{mfa_required: true, mfa_token, methods: ["totp","recovery"]}`（`mfa_token` 5 分钟、一次性、只存摘要）→ `POST /v1/auth/mfa/verify` 换会话。未启用且策略 required → 发**受限会话**（`session.restricted = "mfa_enroll"`），只能调 me / mfa 设置 / logout。
- 启用：`POST /v1/auth/mfa/totp/setup` → `{secret, otpauth_uri}`；`POST /v1/auth/mfa/totp/enable {code}` → `{recovery_codes: string[8]}`（只此一次，服务端只存 HMAC）。
- 同一 TOTP 步不得重复使用（记最后一次用过的步号）；TOTP 失败计入登录失败锁定。
- **复核**：危险操作（staff.manage、settings.manage、route.manage 的写、tenant.terminate、tenant.purge）要求本会话 10 分钟内复核过：`POST /v1/auth/reauth {password, code}` → `{reauth_until}`；否则 401 `reauth_required`，控制台弹复核框后重试。
- 平台人员会话：闲置 30 分钟、绝对 12 小时；令牌放 `sessionStorage`，`Authorization: Bearer`（不用 Cookie，无 CSRF 面）。

### 2.4 首个系统管理员与找回（取消私钥文件）
- 控制面配置 `console.bootstrap_admin {email, name}`：启动时若没有有效 `sysadmin`，建该人员（无密码）+ 24 小时设置码，写 `<data_dir>/control-plane/bootstrap-admin.txt`（0600，只含邮箱、设置码、到期），日志只写文件路径。本人在控制台“首次设置”用设置码设密码 → 登录 → 绑定 TOTP。用过即删文件。
- 全部系统管理员失联：有服务器 shell 的人写 `<data_dir>/control-plane/admin-recovery.request`（内容：邮箱），控制面 30 秒内处理：给该 `sysadmin` 发新设置码（清除 TOTP、吊销会话）写入 `bootstrap-admin.txt`，删请求文件，记审计。服务器 shell 即信任根。
- 运营名册、`ops-cli roster/keygen/password` 不再用于控制台登录；`ops-cli` 保留 `call`（给 support/relay/notify 的命令行运维接口签名）与 `roster-*`（这三个服务的名册）。

### 2.5 客户端最低版本
- 控制面配置 `clients.min_version`（semver）：`/v1/auth/login`、`/v1/auth/register` 带的 `client.version` 低于它 → 426 `client_outdated` `{min_version}`，文案“客户端版本过旧，请升级到 x.y.z 或以上”。已登录的旧客户端：`/v1/seat-token` 同样 426。
- `GET /v1/meta`（无鉴权）→ `{api: "kwl-cp/2", min_client_version, registration, staff_mfa}`。

### 2.6 注册缺省收紧（审计 cloud §9-3）
- `settings.registration` 缺省改为 `code`（凭开通码/邀请码注册）；`open` 要运营显式打开，并显示风险提示。读回旧状态保持原值。

## §3 接口契约（控制台用到的全部）

所有应答错误体 `{error: {code, message, ...extra}}`，`message` 是律师/运营看得懂的中文。网页一律 `Authorization: Bearer kws1.…`。

### 3.1 `/v1/auth/*`（公开 + 会话）
| 方法 路径 | 体 → 应答 |
|---|---|
| POST /v1/auth/login | `{email, password, client:{version?, platform:"web"}}` → `AuthResult` 或 `{mfa_required, mfa_token, methods}` |
| POST /v1/auth/mfa/verify | `{mfa_token, code}`（code 为 6 位 TOTP 或 12 位恢复码）→ `AuthResult` |
| POST /v1/auth/register | 不变（网页注册后 `onboarding.state` 为 needs_founder_setup/needs_device_join 时，控制台提示“在 Windows 客户端用此账号登录完成开通/入组”） |
| POST /v1/auth/password-reset/request, /confirm | 不变；`/confirm` 也接受平台人员的设置码 |
| GET /v1/auth/me | 成员：`{kind:"member", account, onboarding, devices, sessions, firm:{tid,slug,name,role}}`；人员：`{kind:"staff", account:{aid,email,name,roles,perms,status,mfa:{enabled,required,recovery_left}}, sessions, restricted: null|"mfa_enroll"}` |
| POST /v1/auth/logout, /password, /sessions/{sid}/revoke, /devices/{id}/unbind | 不变（两种记录都适用，unbind 只对成员） |
| POST /v1/auth/mfa/totp/setup | → `{secret, otpauth_uri}` |
| POST /v1/auth/mfa/totp/enable | `{code}` → `{ok, recovery_codes}` |
| POST /v1/auth/mfa/totp/disable | `{password, code}`（策略 required 时 403 `mfa_required_by_policy`） |
| POST /v1/auth/reauth | `{password, code?}` → `{ok, reauth_until}` |
| GET /v1/meta | 见 §2.5 |

### 3.4 `/v1/ops/*`（平台人员会话 + 角色权限 + 运维网段）
- 现有全部运营接口与应答**不变**（控制台页面沿用），只换鉴权：Bearer 会话 → 人员 → 角色权限 → `opsSpec.perm` 检查 → 危险操作检查复核 → 先记访问审计再执行（审计 `operator` 记 `stf_…` 与邮箱）。
- 删除：`/v1/ops/login`、`/v1/ops/logout`、`/v1/ops/password`；`/v1/ops/me` 改为返回人员身份（同 me.account）。
- 新增人员管理（staff.manage）：`GET /v1/ops/staff`、`POST /v1/ops/staff {email,name,roles}` → `{staff, setup_code, expires_at}`、`POST /v1/ops/staff/{aid}/roles {roles}`、`/disable`、`/enable`、`/reset {reset_mfa}` → `{setup_code}`。
- 新增 `GET /v1/ops/roles` → 角色表（中文名、说明、权限），给控制台渲染。
- `GET /v1/ops/routing` 增加 `routing_key: {kid, spki_b64, fingerprint}`（控制台用它加密上游密钥，不再读静态 config.json；审计 cloud §9-5）。
- `GET /v1/ops/settings` / `PUT` 增加 `staff_mfa`（只读显示）与 `clients.min_version`。

## §4 计量修补（网关，D-194）
1. **流中途中断（idle 超时、上游流错误）且已向客户端写出内容**：上游已经计了这部分 token，原来账本里成本也是 0——对不上 MaaS 账单。改为：按已转发内容估算 usage（`usage_source: "estimated"`，`outcome` 保持 timeout/upstream_error），账本行标 `partial: true`；**不扣律师额度、计费金额 0**（产品对律师的承诺：“因软件或服务出错没做完的不计入用量”），**成本按估算记入**，对账时单列“服务出错的已产生成本”。未写出任何字节的仍不计费、不记成本（上游通常不计）。
2. **重试不会双计（核实，不改代码）**：闸门每次请求都生成新编号 `kwlg_<uuid>`（`egress-gate/src/server.ts:421`），网关再生成 `kwlgw_<uuid>`，账本按后者去重；内核重试的是“未写出字节的 429/5xx/超时”（不计费）或“客户端断开后网关读完的请求”（按真实 usage 计，上游确实算了两次）。原定的 `retry_of` 标注不做（相同 `client_request_id` 不会出现）。
3. 账本目录可配置 `usage_dir`（生产入口），`state_store=postgres` 且未把账本放共享存储时启动告警（文档写明：账本须单实例或共享存储，P3：账本入库）。

## §5 客户端（D-195）
1. 发起任务前检查：需要重新登录 / 额度暂停（allowance、cap、burst、个人上限）→ 不排队，直接提示原因与办法；本机流程（不调用 AI）不受影响。
2. 错误文案去术语：`控制面：<code>`、`席位令牌…`、`出站闸门…`、`budget_points…`、执行器括号里的原始错误、`开发形态`（试用版写“试用版”）→ 全部改为律师能看懂的话；技术细节只进诊断。

## §6 独立云端仓库（D-196）
- 新仓库 `kimi-work-legal-cloud`（本机 git 仓库），由 monorepo 的清单 `platform/cloud-repo/manifest.json` 导出：`services/*`、`apps/console`、共享契约包 `packages/{firm-trust,seat-token,keys,ops-auth,blob-store,design-tokens}`、云端脚本、`deploy/`（systemd、nginx、配置样例）、`docs/`、云端测试、`.github/workflows/ci.yml`（Linux：类型检查、全部云端用例、控制台打包、生产入口冒烟）。
- 契约：`CONTRACT.md` 列出 API 版本 `kwl-cp/2`、客户端依赖的路径白名单、签名头、令牌格式、信封类型、错误码；共享契约包两端单一来源（monorepo），导出时记 `SOURCE.json`（源提交 + 每文件 sha256），云端仓库 CI 校验不得 import 客户端包。
- 为什么不是“从 monorepo 删掉云端代码”：81 个客户端联调用例在进程内拉起云端服务、并行分支（v16-b41 等）未合并，硬拆会让客户端用例与分支全部断开；先“单一来源 + 导出仓库 + 契约校验”，第二阶段（客户端联调改为对接云端仓库发布版）再把源迁过去。
