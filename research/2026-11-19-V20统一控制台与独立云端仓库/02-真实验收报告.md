## 3. 部署演练（虚机，从零）

环境：本机新建的 lima 虚机 `kwl-deploy`，Ubuntu 24.04.5、arm64、2 vCPU、4 GB，无预装软件，用完 `limactl delete kwl-deploy` 删除。
网络：vzNAT 网段 192.168.64.0/24 当作“运维网段”，服务器地址 192.168.64.2。

逐步结果见《部署手册》第 12 节。要点：

1. **踩到并修好的问题**：
   - Ubuntu 云镜像缺 `libatomic1`，Node 起不来。
   - nginx 1.24 不认 `http2 on;`。
   - `install.sh` 在 nginx 配置检查失败时仍报“安装完成”。
   - `upgrade.sh` 不会重装 systemd 单元和 nginx 配置。
2. **生产入口**：签名服务（mTLS）、控制面、网关、检索四个 systemd 服务，`healthcheck.sh` 全部通过。
3. **运维网段**：同一个 `/v1/ops/overview`，经回环转发访问得 404，经运维网段访问得 401（要登录）。访问日志的 `net` 字段分别是 `127.0.0.0/24`、`192.168.64.0/24`。
4. **控制台（浏览器）**：
   - 首个系统管理员：引导文件里的设置码 → 设密码 → 受限会话绑定两步验证 → 8 个恢复码。用过后引导文件自动删除。
   - 系统管理员新建客户运营和开通专员，需要复核；两人各自首次设置并绑定两步验证。三种角色看到的导航不同。
   - 客户运营开通律所；他的“发创始开通码”按钮是禁用的；开通专员发码成功。
   - 路由公钥指纹在控制台显示“已核对”，与服务器上公钥的 SHA-256 一致。
   - 中软 MaaS 真实密钥在控制台录入：从钥匙串读进浏览器，在浏览器里加密，控制面只存尾号 `…2pe6` 和密文。之后第一次探测 `up`、116 ms。
5. **升级、回滚、恢复**：
   - `upgrade.sh v1.0.0`（从 rc1）：8.5 秒，先自动备份。
   - `rollback.sh`：回到 rc1 后，三位人员仍能用密码和动态码登录。
   - 再升级回 v1.0.0。
   - `rollback.sh <提交> --restore <备份>`：校验和 → 停服务 → 数据目录改名留底 → 解包 → 起服务，健康检查全过；人员、路由密钥、律所都在。
6. **客户端指向虚机**：用客户端仓库的 `make-release-config` 在线生成 `release.json`，三个服务各两把钉住值，公钥表齐全；再用安装包同一份 `loadReleaseConfig` 转成内核环境。注册时提示“连不上中软服务”。

   查明原因：客户端出站闸门只信任公共根证书，加上钉住值，不读额外 CA，闸门子进程只拿到 `PATH`。演练环境没有公网域名，只能用内部 CA 签对外证书。这是**正确的安全行为**，已作为硬性要求写进手册：控制面、网关、检索必须用公共 CA 证书。律师端联调因此改在第 4 节的本机全链路栈上做。

### 4.1 真实起草任务（律师函 / 催告函 · 催款律师函）

**第一次（v1.0.0，暴露缺陷）**：新建事项时没填四项依据，在确认页点“记录客户同意并开始”。任务 2 秒内失败，律师看到的是“AI 服务连不上”。

根因有两层：
- 网关的二次检查按控制面订阅的**事项匿名摘要**判断依据是否齐备。客户端在发起前已把新摘要推给控制面，但网关本地订阅最多晚 15 秒，于是按旧摘要拒绝：`403 basis_incomplete`。
- 执行器没有这类拒绝的文案，落进了笼统的“连不上”。

这是原有设计里的时序缺口，第 44 批的验收没撞上，因为那次在新建事项时就填了依据。

修复（`76366eb`，独立仓库 v1.0.1）：
- 网关凡是按摘要要拒绝时，先即时刷新一次订阅再判定。订阅刷新自带单飞和 1 秒最小间隔，不会被请求放大。补了用例：旧摘要刷新后放行、刷新后仍不齐就拒绝、正常请求不触发刷新。
- 执行器对依据、端点、数据级别三类拒绝，给出“事项设置”方向的准确说法。

## 5. 遗留与风险（如实）

1. **Windows 真机未验证**：用同一份客户端代码的开发形态（Node 内核 + 浏览器界面）替代；安装包仍走 GitHub Actions `windows-desktop` 构建。
2. **公网证书（certbot）与签名服务账本外送（对象存储）在演练中未执行**：没有公网域名，也没有对象存储。手册里的命令按官方用法写，要在真实服务器上补做一次。
3. **未推送**：monorepo 改动都是本地分支提交，没有合并 main；独立云端仓库只在本机。推 GitHub 需要你先 `gh auth login`，再由你确认。
4. **用量账本仍是控制面本机文件**：试点只跑单实例；一主多备前要把账本放共享存储或改成入库（P3）。
5. **迟到的回报会改写已出账月份**：还没有“关账”和调整行（P3）。
6. **律所管理员网页端不能批准入组、签策略、停用电脑**：这些依赖律所根私钥或管理员设备签名，按设计留在客户端，网页只显示状态和指引。
7. **检索上游**：中软 MaaS 的 `/v1/tools/search` 仍返回失败（第 44 批已记），律师端“法律检索”在确认地址前不可用。
8. **support、relay、notify 三个可选服务**的运营接口仍用名册加私钥签名，只给命令行运维用，不是登录。
9. **单任务预计用量**不再显示折算比例；任务实际花了多少 token，要等内核记录逐任务用量后才能显示（P2）。
10. **人员两步验证只支持 TOTP**；律师账号的两步验证、WebAuthn、短信或邮件通道没做（P3/P4）。
11. **账号被停用或下线后，内核要到下一次同步（缺省 10 分钟）才把界面切到“需要重新登录”**；这期间 AI 请求已被网关当场拒绝，提示也已改成人话。可以考虑让内核收到网关的 `account_disabled` 时立即切状态（P2）。
12. **虚机演练环境**：lima 虚机 `kwl-deploy` 已停机，数据保留，停在 v1.0.3。再用时执行 `limactl start kwl-deploy`，不要了执行 `limactl delete kwl-deploy`。
