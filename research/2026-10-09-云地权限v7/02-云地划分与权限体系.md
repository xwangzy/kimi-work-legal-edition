# 第 2 篇　云地划分与权限体系（v7.0 核心篇）

版本 7.0 · 2026-10-09 · 本篇是 v7.0 的“宪法”：每项能力的**来源**、在哪里执行、能碰到什么数据、谁能打开它、从哪个渠道能触发它、断网或关机时怎么降级，都以本篇为准。第 3–5 篇的产品、技术、合规与商业设计从本篇推出。证据见同目录 `调研-S0`（Kimi Code 源码）、`调研-S1`（Kimi 能力来源）、`调研-S2`（主流产品权限与本机沙箱）、`调研-S3`（检索供应商、加密协作先例、国内法律 AI 与律协动态），以及 v6 的 `调研-R1`～`R4`。

---

## 1. 一句话

**端上全能力，沙箱定边界；云上补能力，控制归云；案卷在所，推理过境。**

- **端上全能力**：律师电脑上运行完整的 Kimi Code——也就是 Kimi Work 的内核与它自带的本机后端 kap-server。文件读写、Shell 与 Python、子 Agent 与集群、目标模式、计划模式、技能、MCP、定时、联网检索、网页抓取全部可用，不再像 v5/v6 那样把内置工具关掉、只留法律工具。
- **沙箱定边界**：Agent 能碰什么，由“事项沙箱”决定——原件只读、工作区可写、其他事项与系统目录不可见、代码没有直接网络、一切出网经出站闸门；确认弹窗只用于“跨边界”的动作。没有“完全访问”这一档。
- **云上补能力**：我们从月之暗面只买 API token。Kimi Work 靠 Kimi 会员云服务提供的那部分能力——托管检索与抓取、元典/天眼查等数据源、手机遥控中继、账号、插件市场与更新——只买 token 拿不到，由中软云端按同一协议补位。
- **控制归云**：身份、席位、策略、计量、通知、提醒、分发、运营审计与管理控制台在中软云端控制面；策略在律师电脑与网关上执行。
- **案卷在所，推理过境**：客户内容明文只在律所侧（律师电脑、律所执行器、律所自有存储）持久保存与处理；云端只见过境的推理片段与检索查询（不落盘），以及端到端加密的协作数据与遥控数据（中软无密钥）。

## 2. 为什么还要改：v5 与 v6 的划分各错在哪里

### 2.1 v5：一个维度决定全部位置

v5 只问“谁持有案卷明文”，答对了（律所），却把它推成“云端只提供 token、其余全部在律所侧”。v6 第 1 篇 §2.2 已列出它造成的十七个问题：所内节点成了隐性必需品、身份与控制台在局域网、IM 与提醒依赖常开机器、共享文件夹同步、方法资产下发终端、计量可篡改等。这些诊断 v7 全部接受。

### 2.2 v6：修好了“控制面”，留下四个错误

v6 把身份、控制台、通知、提醒、计量、同步汇合点放回云端，方向正确。但它仍有四个结构性错误，正是“云端执行与本地执行的权限、功能划分”仍不对的原因：

| # | 错误 | 表现 | 后果 |
|---|---|---|---|
| **E1** | **漏了“能力来源”维度** | 把“云端只有 token”当成可以成立的前提，没有清点 Kimi Code 自己依赖的另外八类月之暗面云服务（`调研-S0` §2）。只买 token 时，Kimi Code 的 **WebSearch 工具根本不会注册**（`webSearchTool.ts:117`），元典/天眼查数据源插件要 Kimi 会员登录，手机遥控要经 `code-rc.kimi.com` 中继 | v6 只能用替代品绕开缺口：联网研究改成“律师逐条确认派生查询 → 云端公开沙箱”，手机遥控改成“IM 内 H5 解密签发”。两者都比原生能力更难用、工程风险更高（U4、U18 等未决项） |
| **E2** | **用“删能力”代替“定边界”** | v5/v6 都把 Kimi Code 内置工具全部关掉（`[tools] enabled = ["mcp__legal__*"]`、注入拒绝式进程服务，见 `platform/third_party/PATCHES.md`），v6 再用 WebAssembly Python、默认关闭的隔离浏览器补回一小部分 | 发行版比律师每月花几百元就能买到的 Kimi Work 标准版**更弱**：不能跑代码处理表格与流水、不能派子 Agent 并行、不能自主联网研究、没有目标模式与文件历史。“完整接入 Kimi Code 的后端功能、能力、特性”落空。主流产品的答案是“沙箱 × 审批”两层（Claude Code、Codex、CodeBuddy Code，`调研-S2` Q4），不是删工具 |
| **E3** | **用密码学对抗一个密码学挡不住的对手** | 为防“中软篡改”，v6 加了律所根密钥治理仪式、根签名策略与设备证书、6 位确认码、24 小时观察期、2-of-3 恢复卡 + 中软第 4 片 + 72 小时冷静期、Merkle 透明日志 + 设备间树头比对 + 第三方见证、盲化订阅主题、IM 内 H5 解密签名、网关思考内容密封 | 中软同时下发客户端二进制与 H5 脚本、运营看得到化名片段的推理网关——**对“恶意的中软”，这些机制挡不住一次恶意更新**；它们真正防住的是“中软云端被攻破”与“中软员工越权浏览”，而这两类威胁用一套简单的端到端加密就能防住。代价是约 40–60 人周（含测试与红队）、一批依赖平台能力的未决项（U4、U11、U14、U18 等）、小所首日的“治理仪式”，以及“密钥丢了案卷就丢了”的运营风险 |
| **E4** | **没有给“云 → 本机”的触发渠道单独定权限** | IM 指令、手机、定时、执行器、云端服务都能让律师电脑上的 Agent 干活，但 v6 只按“本机任务档位”管理 | Kimi Code 的远程控制在源码里是“把本机后端整个经中继暴露给远端”（`remote-control.ts:591-690`）；WorkBuddy 把远程任务限定在“助理专属文件夹、单会话”（`调研-S2` Q1.4）。律所必须有一张“远程渠道权限表” |

此外，v6 的经济结果比 v5 更差（同席位基准经营谷底加深约 1,020 万元），其中相当一部分来自 E3 的机制。

**v7 对 E3 的修正不是“取消全部律所侧信任锚”**（对抗式审阅 B5 指出那会让“攻破控制面”退化为只靠内控）：取消的是治理仪式、律所根密钥证书链、确认码、观察期、透明日志见证这类重仪式；保留并简化为**轻量律所侧校验锚**——管理员账户公钥在成员客户端首次固定、放宽类策略与连接器登记须律所管理员设备签名、策略与公钥目录版本单调、账户公钥变更须核对安全码后才重新包裹事项密钥（§8.2、§8.11）。

### 2.3 v6 做对的、v7 原样保留的

控制面在云、零服务器默认可用；律所执行器只出站、可选；IM 三种接入模式（R3 一手核验）；期限提醒云端调度、与 Agent 执行解耦；法律推理网关（方法资产服务端组装、权威计量、事项策略二次检查、内容安全、对模型方隐去律所身份）；数据分级（L0–L4，L3 区分法定敏感与当事人限制）；四层策略最严者胜出；管理员默认拿不到事项内容、不做会话回放；停服三项承诺；如实口径与禁用词。

### 3.2 要保护什么、防谁、用什么防

| 威胁 | 主要防线 | 防线性质 |
|---|---|---|
| 外部攻击者攻破中软云端（被动窃取数据库与存储） | 云端不持久化客户明文；协作与遥控数据端到端加密，密钥不在云端 | 密码学 |
| 攻击者控制中软控制面（主动篡改：替换公钥、放宽或回放策略、登记外泄连接器） | 律所侧校验锚：管理员公钥首次固定、放宽类策略与连接器登记须律所管理员设备签名、版本单调、账户公钥变更须核对安全码 | 密码学 + 律所侧校验；**残余**：成员首次入组时对管理员公钥的首次信任（律所版默认当面或电话核对安全码） |
| 中软运维人员越权浏览 | 同上 + 双人运维、最小权限、访问审计 | 密码学 + 内控 |
| 中软推送被篡改的客户端（被迫或恶意） | 代码签名、版本与哈希公开、第三方安全审计、律所版可选“延迟更新 + 哈希核对”、合同与上市公司责任 | **内控与合同**（如实说明：密码学挡不住发布客户端的一方） |
| 月之暗面 | 企业协议（排除服务优化、ZDR、不训练）、以中软组织身份调用、化名与标识符遮蔽 | 合同 + 数据最小化 |
| 检索与数据商 | 查询去标识、按次最小化、DPA | 合同 + 数据最小化 |
| IM 平台 | 卡片不含文件名与事项名、文件由律师电脑直取 | 数据最小化 |
| 律所内部越权（伦理墙、管理员） | 事项密钥只分发给事项成员；管理员默认不持事项密钥 | 密码学 |
| 提示注入导致外泄 | 沙箱进程无直接网络；出站闸门检查每一次出网；跨边界动作确认；对外发送与签发不是工具 | 技术 |
| 提示注入导致破坏 | 原件只读；工作区文件历史与快照可回滚；沙箱限制可写范围 | 技术 |
| 设备丢失或被盗 | 设备密钥受 TPM/钥匙串保护；静态加密；远程吊销；密钥轮换 | 技术 |
| **密钥丢失导致案卷丢失** | 个人恢复码、律所恢复码、可选中软托管恢复、每周增量导出 | 运营（v6 低估了这一条） |

这张表决定了 v7 的密码学边界：**端到端加密防“云端被动窃取、云端人员越权、律所内部越权”；律所侧校验锚防“控制面被主动篡改”；对“发布客户端的一方”，靠签名、审计与合同，并如实说明**。不再为后者叠加只在理论上成立的机制。

### 3.3 决定位置的五问

1. **能力来源在哪？** 只在月之暗面云的（模型、工具 REST）→ 经中软 MaaS 与网关；只能由中软跨律所提供的（检索补位、法源与数据商、方法资产、账号）→ 中软云；开源可运行的（Kimi Code 全部本机能力）→ 跟着数据走。
2. **碰不碰客户内容明文？会不会持久化？** 持久化只在律所侧；云端只允许过境（内存中处理、不落盘、逐类披露）或密文。
3. **要不要常在线、能被外部唤醒？** 要 → 云端承接“信令、排队、提醒、卡片”；真正需要明文的执行回到律师电脑或律所执行器。
4. **要不要一个律师改不了的锚？** 计量、许可、方法资产 → 云端。
5. **要不要本机资源？** 文件、Office、离线、算力 → 本机。

### 3.4 五条划分规则（另加一条非功能约束）

| # | 规则 | 由哪一问推出 | 典型能力 |
|---|---|---|---|
| **R1 案卷在所** | 客户内容与事项描述的**明文持久化与 Agent 处理**默认只在律所侧；云端只允许过境（推理片段、检索查询、IM 文字指令）且不落盘，或只存端到端加密的密文；每一类过境都进数据去向卡 | 问 2 | 材料、成果、映射表、会话转录、内容级审计 |
| **R2 能力补位** | 凡 Kimi Work 靠 Kimi 云服务提供、而我们只买 token 拿不到的能力，由中软云端**按 Kimi Code 已有协议**补位，引擎不改；凡 Kimi Code 能在本机原样运行的能力，**一律保留**，不删 | 问 1 | 检索与抓取、数据源、遥控中继、账号、分发 |
| **R3 控制归云** | 不碰明文、但要常在线或要防律师篡改的能力放中软控制面；策略在端侧与网关执行 | 问 3、4 | 身份、席位、策略、计量、通知、提醒、分发、运营审计 |
| **R4 沙箱放权** | Agent 的权限边界由“事项沙箱”（文件、进程、网络）与数据级别决定；沙箱内的动作按运行模式自动执行，**确认只用于跨边界动作**；不靠删工具保安全；没有“完全访问” | 问 2、5 | 文件工具、Shell/Python、子 Agent、联网 |
| **R5 远程降权、人签发** | 经 IM、手机、定时、执行器、云端发起的任务，权限不高于发起人在本机界面的权限，且默认只产草稿；对外发送、签发、删改原件、改权限永远是人在本机或已登记设备上完成 | — | 远程渠道权限表（§8.7） |
| **N 断云可用** | 中软云端不可达时，本机能力照常（本机解锁靠设备密钥与离线 30 天许可）；推理与检索在网关可达时不受控制面影响 | 问 5 | 降级模式（§10） |

## 4. Kimi Code 的云端依赖与补位（能力来源清单）

| # | Kimi Code 依赖的月之暗面云服务 | 支撑的能力 | 只买 token 能否获得 | v7 补位方式 | 位置 | 引擎是否需改 |
|---|---|---|---|---|---|---|
| 1 | 开放平台模型 `api.moonshot.cn/v1` | 推理 | **能** | 律师电脑 → 本机模型代理（出站闸门）→ 中软法律推理网关 → 中软 MaaS 法律分组 → 月之暗面 | 云-网关 | 否（provider `base_url` 指向本机代理） |

| 4 | Kimi 账号 OAuth `auth.kimi.com` | 登录、会员额度 | 否 | 中软 IAM（企业微信/钉钉/飞书扫码、手机号、OIDC/SAML/SCIM）；Kimi Code 侧用宿主身份与网关令牌，不走 Kimi OAuth | 云-控制面 | 否 |
| 5 | 官方数据源插件 `kimi-datasource`（元典法律、天眼查、Wind 等） | 法规案例、工商信息、金融数据 | 否（读取 Kimi OAuth 凭据） | **中软法源服务**：自签元典/法律之星/企查查或天眼查等合同，以 MCP（http）接入；凭据只在云端；按律所计量 | 云-法源 | 否（MCP 配置） |
| 6 | 远程控制中继 `code-rc.kimi.com` | 手机遥控桌面 | 否（且中继在 TLS 终止后可见全部往来） | **中软遥控中继，端到端加密**：手机与本人电脑配对时交换公钥，中继只转发密文帧；隧道**终止于桌面主进程的“遥控网关”**，只暴露 §8.7 白名单接口，远端不能直达 kap-server（上游隧道会带本机令牌转发全部路由，含终端与运行模式切换） | 云-中继 + 本机主进程 | 是（ZP-8：上游隧道转发改为宿主回调） |
| 7 | 插件市场与更新 `code.kimi.com/kimi-code` | 插件安装、自动更新 | 否 | 中软签名分发 + 律所批准的插件目录（`KIMI_CODE_PLUGIN_MARKETPLACE_URL`）；客户端由中软签名更新 | 云-控制面 | 否 |
| 8 | 内容 CDN `cdn.kimi.com`（WebBridge、Computer Use 二进制） | 真实浏览器控制、桌面操控 | 否 | 不用。浏览器能力用发行版自带的隔离浏览器；真实浏览器控制默认关闭（§8.4 T6） | — | 否 |
| 9 | 遥测 `telemetry-logs.kimi.com` | 产品分析 | — | 关闭上游遥测；中软只采运营元数据（开通协议约定、可关） | 云-控制面 | 否（配置） |

结论：**中软云端的“补位”工作量集中在 2、5、6 三项，且 2、3 可直接复用月之暗面自己的工具 REST 接口**——这既保持了“我们的上游只有月之暗面”这一采购关系，也让 Kimi Code 的联网能力原样可用。

## 5. 主流产品怎么划分（v7 增量）

v6 已用 R1/R2 核验了 14 个产品的“控制面在云、执行面可插拔”。本轮聚焦**权限设定与本机隔离**（`调研-S2`），结论如下：

| 产品 | Agent 循环 | 本机权限档 | 本机隔离（Windows / macOS） | 远程与 IM | 管理员锁定 | 对 v7 的含义 |
|---|---|---|---|---|---|---|
| Kimi Work | 本机（Kimi Code） | 默认 / 手动允许 / 全部；“默认”下修改覆盖文件、运行代码前确认；“全部”须用户自担风险 | 未查到 OS 级沙箱 | 手机 Kimi App 遥控（同账号配对，任务在电脑执行，审批同时推到电脑与手机）；Kimi Code 同款功能明写“统一走 Kimi 中转服务”、无端到端加密 | 未查到（企业版只有席位管理） | 发行版要补：沙箱、远程降权、遥控端到端加密、管理员锁定 |
| 腾讯 WorkBuddy | 本机；WMA 云端托管（10 月进企业端，截至 10-09 未见公告） | 默认 / 完全访问；Ask/Plan；“不建议在处理客户资料或唯一副本时开启完全访问” | 官方只有营销式“Bash 沙箱”表述；同门 CodeBuddy Code 写明 **Linux bubblewrap、macOS Seatbelt，Windows 计划中** | IM 助理：远程任务**固定在“助理专属文件夹”、单会话**，电脑须开机 | 桌面端未查到；企业版有 IP 白名单、模型白名单、会话回放 | “远程任务只在专属区域”可直接借鉴；会话回放不借鉴 |
| 千问办公 | 桌面本机 / 网页云端 | 输入框“自动审批模式”（1.2.0）；电脑操控“每次询问 / 自动执行” | **“安全工作环境”= 下载镜像在本机虚拟机里跑（Windows VM 服务）** | 钉钉/飞书扫码自动建应用；开放 / 配对两种准入 | 企业 Hooks（**超时或不可达即放行**） | 律所 Hooks 必须对高风险事件“失败即拒绝” |
| Claude Code / Cowork | 本机或云端（Cowork 10-06 起默认云端，Enterprise 须 owner 开启） | default / acceptEdits / plan / auto / dontAsk / bypassPermissions；v2.1.283（09-25）起终端默认 `auto`；managed settings 可锁定并禁用 auto 与 bypass | Claude Code：macOS Seatbelt、Linux/WSL2 bubblewrap，**原生 Windows 不沙箱**（须 WSL2）；Cowork 本机会话跑在 Hyper-V / Apple Virtualization 虚拟机，Windows 须管理员开启 VMP | 云端会话经代理回取已连接文件夹；遥控在组织策略关闭后断开（v2.1.286 修复） | 可锁定（最严者胜出）；hooks 可设 `onFailure: "block"`（v2.1.295，10-08） | 沙箱 × 审批两层；管理员可锁；hook 失败即拒绝 |
| OpenAI Codex | 本机或云（协调与执行分离） | read-only / workspace-write / danger-full-access × 审批策略；默认无网络 | **Windows 原生三种沙箱**：`mxc`（Microsoft Execution Containers，Windows 11、无需管理员，按路径与网络策略隔离，10-08 推荐）；`elevated`（管理员一次性预配：专用低权限沙箱用户 + 防火墙规则 + ACL）；`unelevated`（受限令牌 + ACL，网络隔离较弱）；实现开源于 `codex-rs/windows-sandbox-rs` | 不同设备间不互相授予访问 | 企业可禁止回退到弱实现 | Windows 本机沙箱**可做**，且有开源实现可参照 |

三条共性：**①本机权限都是“工作区边界 + 跨边界确认”两层；②OS 级隔离在 macOS/Linux 已成熟；在 Windows 上，Claude Code 不沙箱、WorkBuddy/CodeBuddy/Kimi Code 上游尚无实现、千问办公与 Cowork 用本机虚拟机（须管理员），只有 Codex 做到了原生进程级沙箱（含无需管理员的实现）；③远程触发一律被限制在更小的范围（WorkBuddy 的专属文件夹、Cowork 的已连接文件夹、Dispatch 已停用）。** 律所的 Windows 笔记本是我们必须自己啃下、且已被证明可以啃下的工程点（§8.5、第 4 篇 §5）。

## 7. 数据分级与去向矩阵

### 7.1 分级（沿用 v6，规则微调）

| 级别 | 定义 | 例子 | 怎么标 |
|---|---|---|---|
| **L0 公开** | 已公开、无保密义务 | 法律法规、公开裁判文书、上市公告、企业公示信息 | 来源识别；律师可标 |
| **L1 律所内部** | 律所自己的、非客户的 | 范本、本所覆盖层、培训材料、内部制度 | 方法与知识库 |
| **L2 客户一般** | 委托事项中的材料与成果 | 合同、函件、案卷、意见书 | 事项内默认 |
| **L3a 法定敏感** | 律协指引列明的敏感信息、高敏事项 | 生物识别、医疗健康、金融账户、行踪轨迹、未满十四周岁未成年人信息；刑事卷宗；负责人标“高敏” | 化名引擎识别 + 事项密级 |
| **L3b 当事人限制** | 当事人书面要求不上云或不用 AI | 委托合同或告知回执中明确拒绝 | 事项头显示“当事人限制”；**任何管理员都不能放开** |
| **L4 涉密禁入** | 国家秘密与涉密载体 | 带密级标志的材料、律所判定的涉密事项 | 检测到即**拒绝导入**，提示按涉密载体制度线下处理 |

v6 的“L0d 派生公开查询（律师逐条确认）”在 v7 中不再是一个级别，而是出站闸门对**检索查询**这一去向的处理规则（§8.6）：不含直接标识符、也不含当事人词典实体的查询自动放行；含实体的查询按事项级别与运行模式确认或改写；L3 事项逐条确认；L3b 禁止。

### 7.2 去向矩阵（✓ 允许；○ 策略或确认后可；✗ 禁止）

| | E1 本机沙箱 | E2 执行器 | 推理·标准 | 推理·私有 | 联网检索查询 | 本机网页抓取 | 法源查询 | 协作中继 | 遥控中继 | IM 收发文件 | E4 云执行 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| L0 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| L1 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ○ |
| L2 | ✓ | ○ 逐事项 | ✓ 同意为“已同意/无需”；“待取得”只用本机能力 | ✓ | ✓ 自动去标识；含当事人实体须确认或改写 | ✓ URL 不得含事项信息 | ✓ 去标识 | ✓（律所可改自有存储） | ✓ | ✓ 配对 | ○ G3 三重开启 |
| L3a | ✓ | ○ 默认否 | ○ 管理员显式放开并留痕，化名强制 | ✓ | ○ 逐条确认 | ✓ 同上 | ✓ 去标识 | ✓（律所可要求只用执行器或自有存储） | ○ 默认只通知 | ○ 默认只通知 | ✗ |
| L3b | ✓ | ○ 默认否 | **✗ 不可放开** | ✓（当事人只拒绝云端时） | ✗ | ○ | ✗ | **✗** 只本机、执行器或自有存储 | ✗ | ✗ | ✗ |
| L4 | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

**图像与扫描件**：默认先在本机 OCR 得到文本、经化名后再送模型；把图像原样送多模态模型（Kimi Code 的 ReadMediaFile 会把图片以 base64 放入消息）是**跨边界动作**：L2 须确认，L3a/L3b 禁止——图像里的身份证、印章页、病历无法化名，且直接上传的图像不在月之暗面 ZDR 覆盖内（`调研-S1` Q3.9）。

“混合任务”按步骤拆分由出站闸门执行，而不是交给模型自行判断：例如“结合本案事实做类案研究”——Agent 在本机起草检索式，闸门剔除直接标识符并匹配当事人词典，命中实体时按 §8.6 处理；检索结果回到事项，再与事实结合起草（推理走标准端点、化名）。

## 8. 权限体系

### 8.1 三条不变式

1. **Agent ≤ 委托人**：Agent 能读写的数据不超过发起人在该事项的权限；能用的能力不超过“中软基线 ∩ 律所策略 ∩ 事项策略 ∩ 运行模式”。
2. **远程 ≤ 本机**：经 IM、手机、定时、执行器、云端发起的任务，权限不超过发起人在本机界面上的权限，并按 §8.7 再降一档。
3. **云端组件 ≤ 职责**：每个云端组件只拿到完成职责所需的最少数据，且不持久化客户内容明文。

### 8.2 四层策略与六个强制点

```text
中软基线（写死在客户端与网关，任何人不可改）
  对外发送/签发/删改原件/改权限不是 Agent 工具 · L4 禁入 · L3b 不上云 · 沙箱不可关闭 · 无“完全访问”
  · 出站目的地类别根集 · 远程与定时任务只产草稿 · 任何工具不得绕过出站闸门出网 · 每一次工具调用都经宿主策略裁决
    └─ 律所策略（管理员在云端控制台编写 → 控制面签名下发；放宽类变更另须律所管理员设备签名 → 端侧与网关执行）
         允许的运行模式与执行位置 · 模型端点 · 工具与连接器上限 · 数据级别规则 · 检索与抓取白名单
         · IM 与遥控策略 · 导出与标识策略 · 律所 Hooks
         └─ 事项策略（事项负责人在客户端设置，事项账本内保存；匿名摘要同步到网关）
              密级 · 当事人同意状态 · 允许的端点与执行位置 · 是否授权执行器 · 是否允许 IM/遥控收发文件
              └─ 任务运行模式（发起人选择，§8.3）
                   └─ 单次确认（发起人或在线审批人）
```

| 强制点 | 管什么 | 挡得住 | 挡不住（如实） |
|---|---|---|---|
| ① 事项沙箱（OS 级） | Agent 进程的文件、进程、网络 | 注入后的越界读写、绕过闸门直接联网 | 沙箱逃逸类漏洞（靠补丁与红队） |
| ② 本机策略引擎（宿主策略） | 工具可见性（`[tools] enabled` 动态生成）；**对每一次工具调用裁决**——补丁 ZP-4 在引擎策略链首位插入宿主策略，上游“默认放行”清单（Read、Agent、AgentSwarm、Skill、CreateGoal、WebSearch、FetchURL 等）与 git 目录内自动放行写入一律改为由宿主裁决（ZP-14）；运行模式由策略引擎决定，界面与遥控送来的 `permission_mode`/yolo 在主进程代理处剥离 | 越权工具调用、子 Agent 与集群越权、预算超限、切换 yolo | 被篡改的客户端 |
| ③ 出站闸门 | 经闸门的每一次出网：目的地、数据级别、化名与标识符、图像载荷、去向记录；闸门是客户端唯一的对外出口（A 级 OS 强制，其余等级应用层 + 代理兜底） | 外泄到未批准目的地、未化名片段出站、图像直送 | 语义层面的“隐写式”外泄（残余风险，靠泛化、确认与审计）；B/C 级下被攻破进程绕过应用层约束 |
| ④ 能力网关 | 推理/检索/法源的二次检查、内容安全、权威计量 | 误配置、旧客户端、已吊销设备、L3/涉密事项的请求 | 冒报其他事项 ID 的被篡改终端（由异常检测事后发现） |
| ⑤ 控制面 | 身份、席位、设备吊销、渠道开关、策略分发 | 离职与丢机后的继续使用 | 离线 30 天内的已解锁设备 |
| ⑥ 事项密钥 | 谁能解密事项 | 管理员与非成员（伦理墙） | 持有恢复材料的人（对他们，伦理墙是内控而非密码学） |

**律所策略的完整性（轻量律所侧校验锚）**：v6 用“律所根密钥 + 治理仪式 + 透明日志”；v7 不要根证书链与仪式，但保留四个律所侧可验证的锚——①**管理员公钥固定**：成员客户端在入组时固定律所管理员账户公钥（律所版默认当面或电话核对安全码，团队版首次信任 + 可选核对）；②**放宽类变更须管理员设备签名**：允许云端执行、放开 L3a、开放新运行模式、登记新的连接器或出站地址等，客户端只认带律所管理员账户签名（团队版 1 名、律所版 2 名）的策略，控制面签名不足以放宽；③**版本单调与时效**：策略与公钥目录带单调版本号与有效期，客户端拒收低于已见版本者，过期回退到“中软基线 + 最严模板”，防扣留与回放；④**变更可见**：每次变更写入运营审计、即时通知全体管理员、客户端对放宽显示横幅。收紧类变更只需控制面签名。

**律所 Hooks（律所版）**：律所可登记自有 HTTP 服务（DLP、利冲、档案），由本机策略引擎在“发起任务、工具调用前、出站前、任务结束”四个时点同步调用，只能拒绝或加审批、不能放宽。与千问办公的 fail-open 不同（`调研-S2` Q2.4），**出站前与高风险工具调用前的 Hook 超时或不可达时按“拒绝”处理**，其余时点按律所策略选择。不依赖 Kimi Code 自带的 hooks（其失败即放行，`2026-10-01-kimi-code-repo-facts.md` §9）。

### 8.3 运行模式：四档 + 计划开关

| 模式 | 对标 | 沙箱内动作（读写工作区、运行代码、子 Agent） | 跨边界动作（§8.6） | 预算 |
|---|---|---|---|---|
| **问答** | WorkBuddy“问一问”；只读 | 只读；不写、不运行代码 | 逐项确认 | — |
| **手动** | Kimi Work“手动允许” | 每一步确认 | 逐项确认 | 任务预算 |
| **默认** | Kimi Work“默认” | **自动执行**（沙箱保证可回滚、无网络） | 逐项确认，可选“本任务内一直允许” | 任务预算 |
| **自动** | Kimi Work“全部”，但仍在沙箱与闸门之内 | 自动 | 律所白名单内自动（去标识通过的检索、白名单域名抓取、只读连接器），其余确认 | 预算硬上限；产物只为草稿 |

- **计划开关**：任何模式都可叠加“先出计划”（Kimi Code 计划模式）；新用户与 Agent 开放任务默认开启。
- **没有“完全访问”**：不存在关闭沙箱或出站闸门的档位。Kimi Work 的“全部”与 WorkBuddy 的“完全访问”要求用户自担风险（WorkBuddy 官方明确不建议在处理客户资料或唯一副本时开启，`调研-S2` Q1.2）；律所执业场景不能靠一句声明转移这种风险。
- **比 Kimi Work 更顺手的一点**：Kimi Work“默认”档在运行代码、修改文件前都要问；v7 因为代码跑在无网络的沙箱里、原件只读、工作区可回滚，**默认档下这些动作直接执行**，只在真正跨边界时才打断律师。
- 档位由上层约束：律所策略禁止的档位不出现在选择器里（不显示灰色“申请开启”）；远程与定时任务的档位上限见 §8.7。

### 8.5 事项沙箱：Agent 的硬边界

| 维度 | 规则 | 实现要点（详见第 4 篇 §5） |
|---|---|---|
| 文件 | 每个事项一个工作区，分三区：**原件区只读**（导入的原件按内容寻址加密保存；沙箱只看到本任务所需原件的**只读解密副本**，任务结束清除；律师挂载的本机文件夹**本身从不暴露给沙箱**，避免挂载了上级目录时其他事项被读到）；**工作区读写**（草稿、表格、脚本、中间产物；文件历史与快照可回滚）；**交付区只由人发布**（Agent 写不进去）。其他事项、用户目录、系统目录、其他应用数据**不可见** | 注入受限 `IHostFileSystem`（v5 ZP-6 扩展为三区）；进程级再由 OS 沙箱限定可访问路径 |
| 进程 | Bash/Python/Node 只在沙箱进程内运行；随包分发 Python（含 docx/xlsx/pptx/pdf、pandas、matplotlib 等）与便携 bash；不允许在线安装依赖（律所策略可开中软镜像白名单） | 注入沙箱化 `IHostProcessService`（替代 v5 的“拒绝式进程服务”）；Windows 方案见第 4 篇 §5 |
| 网络 | **沙箱进程没有直接网络**。Agent 的联网只能经 WebSearch、FetchURL、浏览器工具与 MCP，这些工具运行在沙箱外，全部经出站闸门 | 与上游 PR #4115 的思路一致（沙箱 + 出网代理 + 域名白名单），但我们在工具层而不是 Shell 层放行网络 |
| 凭据与回环 | 沙箱内没有任何令牌：模型、检索、法源令牌只在闸门里；kap-server 令牌只在内存（经 `authTokenService` 注入，不写明文令牌文件）；沙箱进程环境变量用白名单（PATH、指向事项临时目录的 HOME、LANG、PYTHON*），不继承宿主环境；**沙箱对 127.0.0.1/::1 不可达**（A 级防火墙含回环、B 级 LPAC 不授回环、A′ 探针专测），闸门与内核的回环端点要求每进程凭据 | 上游 `hostProcessService` 默认透传整个 `process.env`、kap-server 令牌默认落明文文件——两处均须替换 |
| 资源 | CPU、内存、单次运行时长、工作区磁盘配额 | Windows 作业对象 / macOS 与 Linux 资源限制 |
| 不可关闭 | 律所与律师都不能关闭沙箱；设备只能达到 C/D 级时按下表降级 | 首次启动自检 |

**设备隔离等级**（Windows 五档 A/A′/B/C/D，D 为无沙箱的降级档；客户端首次启动自检，等级显示在设备页与控制台，律所策略可按事项级别要求最低等级）。**产品决策**：若设计合作律所中达不到 A/B 的设备超过 20%，开通流程改为默认引导一次管理员授权以获得 A 级，否则该设备只用“手动”模式：

| 等级 | 平台与做法 | 是否需要管理员 | 文件隔离 | 网络隔离 | 允许 |
|---|---|---|---|---|---|
| **A** | Windows：律所 IT 一次性预配（或安装时提权）专用低权限沙箱用户 + 出站防火墙阻断 + ACL 工作区边界 + 作业对象（参照 Codex `elevated`）；macOS：Seatbelt；Linux 执行器：bubblewrap + 独立网络命名空间 | Windows 需要一次 | 强 | 强（无直接网络） | 全部事项级别、全部模式（G0 探针 2 通过后） |
| **A′** | Windows 11 兼容设备：Microsoft Execution Containers（参照 Codex `mxc`，按路径与网络策略隔离） | 否 | 强（待验证） | 强（待验证；托管网络须放行回环，沙箱不启用网络） | 候选：Windows 11 逐机自检，显式选择失败不回退；微软一手文档未查到，G1 探针确认后才等同 A |
| **B** | Windows 无管理员：AppContainer/LPAC（不授予网络能力即无网络；客户端为便携运行时与工作区目录授予 ACL）+ 作业对象 | 否 | 强（默认无访问） | 强（能力级，不授予即无网络） | 候选：依赖便携 bash 与 Python 在 LPAC 内通过兼容性探针（公开资料未见 LPAC 承载通用 Shell 的 Agent 实现）；未通过则 Bash 只在 A 级可用、B 级只开放 Python，或降 C |
| **C** | Windows 无管理员且 B 不可用：受限令牌 + ACL 写边界 + 作业对象（参照 Codex `unelevated`）| 否 | 弱（**读取不受限**，磁盘上挂载的明文文件夹可被读） | 弱 | 代码执行须逐次确认（“手动”）；**只限 L0/L1**；L2 须律所策略显式接受弱隔离并在事项头标注；“自动”模式不可用 |
| **D** | 无法建立沙箱 | — | — | — | 只用“手动”模式，T2 代码执行不可用 |

### 8.6 出站闸门与“跨边界动作”

**目的地类别根集**（中软基线；律所只能在类别内登记具体地址）：①中软能力网关（推理）②中软检索服务 ③中软法源服务 ④中软中继（密文）⑤中软控制面（元数据）⑥公开网页（抓取与隔离浏览器）⑦律所批准的连接器与律所自有服务 ⑧IM 平台 ⑨中软分发（更新、法规库增量）。其他一律拒绝。

| 去向 | 闸门规则 | 记入数据去向卡 |
|---|---|---|
| 推理 | 按事项同意状态放行；当事人词典 + 实体识别 + 直接标识符遮蔽（化名在本机模型代理里**双向替换**：发给模型的是化名，模型返回的工具调用参数在交给引擎前还原，保证 Agent 写回文件、执行 Edit/Bash 时用的是真名）；L3a 强制化名且须管理员放开；L3b 拒绝 | 段落数、字数、化名数、请求 ID |
| 检索查询 | 剔除直接标识符；匹配当事人词典与实体识别；**L2 事项的检索式默认先自动泛化**（去实体、金额区间化、去项目代号），律师可在任务开始时一次性批准“本任务检索泛化后放行”；命中实体或长度、熵超阈值的查询逐条确认；L3a 逐条确认；L3b 禁止；**所有**查询原文（含自动放行的）记在本机事项账本，云端不留 hash 以外的痕迹，且不把 hash 当作“不可见”的证据 | 查询条数（原文在本机） |
| 网页抓取 | 必须经闸门 `/fetch`（上游本机回落已删除，ZP-11）；只允许 http(s) GET；域名按律所白名单与“公开官方站点基线”放行，新域名确认；**搜索引擎与可回显查询参数的站点不允许经抓取访问**（检索一律走 WebSearch 工具）；URL 查询串与路径中出现当事人实体、直接标识符或可疑长编码串即拦截；返回内容标为“不可信外部内容”再交给模型 | 域名、字节数 |
| 隔离浏览器 | 白名单站点；表单提交确认，**表单输入同样做实体匹配**；不登录、不导入 Cookie、不下载可执行文件 | 域名、提交次数 |
| 图像载荷 | 推理请求中的 `image_url`/data URI 单独识别：L2 须确认、L3 拦截 | 图像张数 |
| 本机渲染与文档 | 桌面与移动端渲染 Agent 产出的 Markdown/HTML 时实行严格内容安全策略（不加载外部图片、样式与脚本），HTML 预览放在无网络的隔离框架中；Agent 生成的 DOCX/XLSX/PPTX 交给 Word/WPS 打开前剥离外部关系（远程模板、外链图片） | — |
| 法源查询 | 去标识；按数据商 Source Registry 规则（缓存、展示、送模型、导出） | 条数 |
| 连接器 | 只把不高于连接器“可接收级别”的数据交给它 | 调用次数 |
| 中继 | 只出密文 | 加密事件数 |
| IM | 卡片模板不含文件名、事项名、客户名与案情 | 消息数 |

**“默认”模式下需要确认的跨边界动作**：①检索查询命中当事人实体或超阈值（L2 未批准“泛化后放行”时）；②抓取新域名或在浏览器里提交表单；③连接器的写入或按次计费调用；④跨事项读取（T7）；⑤创建定时任务（T8）；⑥超出任务预算；⑦图像原样送模型；⑧任何把数据交给“可接收级别”低于该数据的去向。沙箱内的读写与代码执行不打断律师。

### 8.7 远程渠道权限（云 → 本机）

| 渠道 | 身份与配对 | 能发起 | 运行模式上限 | 能审批 | 不能 | 数据经过中软时的形态 |
|---|---|---|---|---|---|---|
| 本机界面 | 本人设备 | 全部 | 律所允许的最高档 | 本人事项内全部 | — | — |
| Word/WPS 加载项 | 本机命名管道 | 当前文档相关任务 | 默认 | 当前文档相关 | 跨事项 | — |
| **手机遥控本人电脑** | 手机与本人电脑扫码配对，配对密钥只在两端 | 本人事项的任务；看进度与产物预览；向“收件区”上传附件 | **默认**（不可切到自动） | T4/T5 确认（与桌面同时推送） | 签发、对外发送、导出、改权限、T6 写入与计费、T7、T8；L3b 事项 | 中继只见密文 |
| IM 机器人（M1/M2/M3） | 已绑定的律所成员（配对模式；禁用“所有人可对话”） | 把文件放进“收件区”、发起模板任务、查进度 | 问答或计划 | 无（转手机遥控或电脑） | 用任意文字直接驱动 Agent；群聊收文件 | M1：文字指令与文件名过境中软；文件由电脑直取 |
| 定时任务（本机或执行器） | 创建人 | 预设模板任务 | 默认；遇到确认即暂停等人 | 无 | 跨边界动作自动通过 | — |
| 律所执行器 | 执行器证书 + 逐事项授权 | 代发起人执行已授权事项的任务 | 发起时的模式，最高“默认”；遇确认回推发起人 | 无 | 未授权事项、L3b | — |
| 中软云端服务 | — | 推送通知与提醒 | — | — | **在律师电脑上发起任何读取事项内容的动作** | — |
| 中软支持 | 律所逐次授权的远程协助 | — | — | — | 通过系统取得事项密钥 | 屏幕共享全程留痕 |

**强制点：桌面主进程的“遥控网关”**。遥控隧道与 IM 指令都终止于主进程，不直达 kap-server；网关只暴露白名单接口——列出本人事项与会话、发起模板任务或“默认”档任务、查看进度与产物预览、回答提问、对 T4/T5 确认作答、上传到收件区；请求中的 `permission_mode`、yolo、运行时与工作区参数一律丢弃；kap-server 的终端、配置、会话 Agent 配置、工作区（加目录、信任）、插件、文件系统打开与定位（会启动本机程序）、任意路径联想、关机、遥控、OAuth 等路由对远端一律不可达。渲染进程经同一主进程代理访问 kap-server，适用本机界面的白名单。

**收件区**：经手机、IM 进来的文件先进入本人的“收件区”（借鉴 WorkBuddy 远程任务固定在“助理专属文件夹”），由律师在电脑或手机遥控里归入事项后才进入该事项的沙箱；收件区里只做本机能力（本机解析、规则分类、文件信息），**送模型的问答须先归入事项、取得同意状态**。

### 8.8 子 Agent、集群、目标与定时

- 子 Agent（Agent 工具）继承父会话的事项、沙箱、运行模式与预算份额，不能升级模式；子 Agent 的审批经 SDK 会话级桥接汇入同一审批队列（不依赖受 #4070 影响的 hook）。
- Agent 集群（AgentSwarm）：并发与 token 预算由律所策略设上限（建议默认并发 ≤ 8，单任务点数上限内）；Kimi Work 的“最多 300 个子 Agent”不作为默认值——它是成本问题，不只是安全问题。
- 目标模式：必须设预算；超时或超预算暂停并通知。
- 定时任务：按 §8.7 的“定时”渠道运行；期限提醒**不**用 Agent 定时（由云端调度，§9 #44）。

### 8.11 密钥与恢复：“看不见的端到端加密”

| 项 | v7 设计 | 相对 v6 |
|---|---|---|
| 账户密钥 | 每位成员一对账户密钥（P-256，签名与加密各一）；私钥保存在设备安全存储（Windows TPM/DPAPI、macOS 钥匙串、手机 Keystore/Secure Enclave），在本人设备之间安全传递 | 取消“设备证书由律所根密钥签发” |
| 新设备加入 | 用本人已登记设备扫码批准：二维码含一次性配对秘密，**不经中软服务器**，两端据此建立加密信道传递账户密钥（WhatsApp 多设备、1Password 设备配对同类做法，服务器干扰配对会被两端发现，`调研-S3` Q2）；或输入开通时打印的**个人恢复码**；本人其他设备与管理员收到通知；律所版可要求“新设备须管理员批准” | 取消 6 位确认码与 24 小时观察期 |
| 事项密钥 | 每事项一把，包裹给成员账户公钥、律所恢复公钥、（授权时）律所执行器 | 不变 |
| **事项目录密钥** | 律所一把：加密事项名称、成员与审计摘要；授予主任、风控、利冲等角色；持有人变更或离职时由在线持有人设备轮换并重新包裹（新纪元加密新内容，旧纪元密钥包裹给新持有人以便查阅历史），轮换写入运营审计 | 替代 v6 的审计密钥与纪元 |
| 律所恢复 | 开通向导生成律所恢复密钥对。**律所版默认 2-of-3 分片**（三张恢复卡）；团队版默认“1 张律所恢复码 + 一名在线管理员设备确认”两个因素才能动用；可选中软托管（HSM，释放须两名管理员**以各自管理员设备签名**请求——管理员身份由律所侧固定的公钥判定，不由控制面断言——+ 72 小时冷静期 + 通知全体管理员与受影响事项负责人；动用记录在律所侧留痕） | 取消“治理仪式”；默认门限按版本区分 |
| 公钥分发 | 控制面分发、客户端缓存；**管理员公钥在入组时固定**；成员账户公钥只在账户恢复时才会变化（新设备经扫码继承同一账户密钥），**一旦变化，须事项负责人或管理员核对安全码后才重新包裹事项密钥**；高敏事项可要求入组时即核对安全码。如实说明：恶意服务器理论上可在**首次**分发时提供不实公钥——1Password 白皮书附录 C 同样承认这一点且未强制核验；v7 的做法不低于行业头部 | 取消 Merkle 透明日志与第三方见证（律所版 G3 可选） |
| 策略完整性 | 收紧类：控制面签名；**放宽类与连接器登记：律所管理员设备签名**（团队版 1 名、律所版 2 名）；版本单调与时效；变更审计、全体管理员即时通知、放宽横幅 | 取消律所根密钥证书链与仪式，保留管理员签名这一轻量锚 |
| 签发 | 签发人账户签名密钥对确切文件 hash 签名；证明包可离线验证；可选 RFC 3161 时间戳 | 不变 |
| 移动 | 移动 App 作为本人设备加入（扫码批准），密钥在 Secure Enclave/StrongBox | 取消 IM 内 H5 解密与签名 |
| 删除 | 轮换并销毁事项密钥（加密擦除） | 不变 |
| 国密 | 算法套件可替换（SM2/SM3/SM4），按客户与密评要求切换 | 不变 |

设计取向与 1Password（Recovery Group：建库时把库密钥另加密给恢复组公钥）、Bitwarden（Account Recovery：成员密钥加密给组织公钥）、Proton（组织密钥）等企业端到端加密产品一致：**用户看不到密钥，只看到“扫码登录”“恢复码”“管理员恢复”三件事**（`调研-S3` Q2）。与它们相同，若律所恢复码全部遗失且无在线成员，事项不可恢复——开通向导与每季度检查提醒保管，并默认开启每周增量导出。

### 8.12 审计：可见动作，不见内容

| 层 | 内容 | 存放 | 谁能看 |
|---|---|---|---|
| 运营审计 | 登录、设备、席位、策略变更、模型/检索/法源调用元数据（席位、匿名事项 ID、模板、token、耗时）、连接器调用计数 | 控制面（≥ 6 个月） | 管理员、负责人、风控 |
| AI 使用摘要 | 事项代号、操作人、动作类型（审查、检索、抓取、导出、签发、跨边界确认）、外发字节数、时间、对象 hash | 律所侧生成，事项目录密钥加密后经中继同步 | 主任、风控、利冲；可选导出到律所 SIEM |
| 事项内容审计 | 会话转录、工具调用、确认记录、数据去向明细、检索查询原文 | 事项账本与 Kimi Code 会话存储，事项密钥加密 | 事项成员 |

这既满足深圳律协 2026 指引第 22 条“保留使用记录”与上海律协“记录输入、生成与修改过程”的要求（内容级记录在律所侧，可调阅），又不破坏伦理墙。

### 8.13 本机数据的保留、删除与终端可见性

| 问题 | 做法 |
|---|---|
| Kimi Code 的会话转录、文件历史与快照、导出包落盘为明文 | 加密落盘清单：`IFileSystemStorageService`（转录、会话索引等 27 处，`调研-S0` §8）、文件历史与快照所用的 `IBlobStore`/`IAtomicDocumentStore`、会话导出 ZIP、插件存储与工作区别名——全部按事项密钥加密或置于已加密的事项目录；kap-server 令牌只在内存；其余直连 `node:fs` 的路径逐一核对（探针 17） |
| 工作区在任务期间是明文目录（Bash/Python 需要真实文件，与 Kimi Work 相同） | 工作区目录只对本人与沙箱身份授权；事项关闭或闲置超过律所策略时限（默认 8 小时）后**封存**为密文并删除明文，再次打开时还原；客户端检测 BitLocker/设备加密/FileVault 并在未开启时提示，律所策略可要求开启后才能处理 L3 事项 |
| 记录散落在各台电脑 | 会话、工具调用、去向记录都作为事项事件写入事项账本，经中继在成员设备间同步 |
| 保留期与删除 | 律所策略规定保留期（审计 ≥ 6 个月）；到期以“轮换并销毁事项密钥”删除 |
| 诉讼保全与归档 | 事项可设“保全”，冻结删除；结案导出开放格式（事件 JSON Lines + 原始文件 + 签名） |
| 设备离职与丢失 | 吊销设备 → 轮换受影响事项密钥；已解密到本机的明文无法远程收回，如实告知；可选“密钥租约”（N 天不联网则本地密文不可读） |
| 终端安全软件 | 沙箱进程不是虚拟机，不妨碍律所 EDR 监控；提供进程、出站域名与代码签名清单供律所加白（这是兼容性说明，不是发行版提供的安全控制） |

## 10. 降级模式

| 情况 | 仍然可用 | 不可用或排队 | 界面怎么说 |
|---|---|---|---|
| 律师电脑断网 | 阅读、检索本机材料、法条核验、比对、代码执行、文书生成、离线签发 | 推理、联网检索、案例核验、同步、遥控、IM | “离线：模型与联网步骤已排队，联网后自动继续” |
| 中软控制面不可达 | 全部本机能力；推理与检索（网关离线验证席位令牌、缓存事项策略摘要、计量先写预写日志） | 新设备登录、同步信令、通知、IM、提醒推送 | “协作服务暂不可用，本机工作不受影响” |
| 能力网关或 MaaS 不可达 | 全部本机能力 | 模型与联网检索 | “模型通道繁忙，已排队”；**不自动切换到其他厂商** |
| 律师电脑关机 | 期限提醒、公开监测、他人协作；有执行器时已授权事项的任务 | 本人事项的内容任务；手机遥控 | IM 卡片“你的电脑离线，任务将在上线后处理” |
| 设备隔离等级降为 C 或 D | 手动模式下的阅读、起草与工作流（C 级可逐次确认运行代码） | 自动模式；D 级不能运行代码 | “本机隔离环境受限，已限制为手动模式” |
| 许可到期未续 | **退出模式**：阅读、检索、导出、签名验证永久可用 | 模型、同步、新任务 | “许可已到期：可继续查看与导出全部事项” |
| 中软停止服务 | 同退出模式 | 协作与标准端点推理 | 停服三项承诺：≥ 180 天通知与导出期、客户端退出模式、每周增量导出 |

**凭据时效与断云降级**：

| 凭据 | 有效期 | 过期后 |
|---|---|---|
| 席位令牌（网关离线验签） | ≥ 72 小时，在线时自动续期 | 推理与检索暂停（排队），本机能力照常 |
| 许可（端侧离线验签） | 30 天 | 进入退出模式：阅读、检索、导出、签名验证可用 |
| 律所策略 | 默认 30 天有效期 | 回退“中软基线 + 最严模板” |
| 设备本地解锁 | 设备密钥，不依赖云端 | — |

即：控制面停机不超过 72 小时，推理与检索不受影响；超过 72 小时但不足 30 天，本机能力照常、模型步骤排队；超过 30 天进入退出模式。

## 11. 关键流程

### 11.1 首日：零服务器开通（约 20 分钟）

```text
① 主任（或管理合伙人）用企业微信/钉钉/飞书扫码开通 → 开通向导生成律所恢复密钥，打印“律所恢复码”（保险柜）
   → 选择是否开启中软托管恢复、是否把事项目录密钥授予风控 → 选择律所策略模板（推荐模板默认最严）
② 成员扫码登录 → 客户端生成账户密钥与设备密钥 → 打印本人“个人恢复码” → 设备隔离自检（显示 A/A′/B/C/D）
③ 拖入第一份合同 → 本机解析 → 默认模式下 Agent 在沙箱里跑审查、计算违约金、生成修订稿
   → 推理经网关（化名）→ 修订卡 → 在 Word/WPS 打开
```

### 11.2 合同审查（标准生产档 + Agent 增强）

S1 确定性工作流先跑（v5 已实现，质量与验收沿用）；律师在修订卡上追问时进入 Agent：Agent 可读工作区、在沙箱里用 Python 核算金额与期限、派子 Agent 并行核对条款、联网检索监管口径（查询去标识）；所有产物进工作区为草稿，律师确认后由人发布到交付区。

### 11.3 联网研究

```text
律师：“研究股权转让中未实缴出资股东的补足责任，近三年上海判例”
→ Agent 起草检索式 → 出站闸门：无直接标识符、无当事人实体 → 自动放行到中软检索服务（search_pro，限定法律官方站点）
→ 结果作为“不可信外部内容”进入上下文 → FetchURL 抓取全文（白名单域名自动）
→ 法源服务核验案例存在性 → 结论与引用四态进工作区
若检索式含“甲公司”：默认模式弹出确认，并给出泛化改写“某有限责任公司股东未实缴出资补足责任”
```

### 11.4 律师出差，用手机遥控办公室电脑

```text
移动 App（G1 第一版只含遥控与通知）与本人电脑已扫码配对 → 经中软遥控中继（端到端加密，中继只见密文）
→ 在“默认”模式下发起“把收件区里客户发来的合同按受让方立场审一遍”→ 律师在手机上把文件归入事项
→ 任务在电脑沙箱里执行；跨边界确认同时推送到手机与电脑
→ 手机上预览修订稿（由电脑渲染，经加密通道传输）；所有请求经桌面主进程遥控网关的白名单；签发、对外发送须在已登记设备上以签发流程完成
```

### 11.5 合伙人在机场签发（G2 移动 App）

```text
律师申请签发 → 控制面推送通知（只含交付件类型与时间）→ 合伙人打开移动 App（本人设备，账户密钥在 Secure Enclave）
→ 从中继取交付件密文，本地解密并完整预览确切文件 → 生物识别确认 → 账户签名密钥签名
→ 桌面端同步通知；律所策略可对“法院版、对方版”要求桌面签发
```

### 11.6 关机续跑与批量尽调

有律所执行器：事项负责人授权后，任务以信封排队，执行器只出站领取、在 Linux 沙箱中执行、结果加密写回；没有执行器：客户端防休眠并如实提示；G3 起律所可显式开启“律所专属云执行器”。

### 11.7 离职、换电脑、丢电脑

| 时刻 | 产品怎么做 |
|---|---|
| 离职 | 控制台一键回收：吊销设备与席位 → 事项负责人移交 → 后台轮换相关事项密钥 → 档案成员确认归档 |
| 换电脑 | 新电脑扫码由旧电脑批准；旧电脑已坏则输入个人恢复码；都没有时由事项内同事设备重新包裹或律所恢复 |
| 丢电脑 | 吊销 → 轮换 → 静态数据加密；如实告知已解密到本机的明文无法远程收回 |

## 12. 对外如实口径（v7）

| 不说 | 说 |
|---|---|
| “本地化部署”（标准端点时）、“数据不出律所”“零外传” | “**案卷在律师电脑上处理和保存；团队协作数据在中软云端只以端到端加密的形式存在；模型推理只收到化名后的必要片段，联网检索只发出去除直接标识符与已知当事人名称、但仍可能含案情要素的查询；网关不落盘，上游留存以签署的企业协议为准**” |
| “中软看不到任何东西” | 按渠道分情形说明（见下表），客户端“中软看得到什么”页按律所实际启用的渠道动态展示 |
| “和 Kimi Work 一样随便用”“具备 Kimi Work 全部能力” | “具备 Kimi Work 的本地 Agent 工具能力（文件、代码、子 Agent、目标、计划、技能、MCP、联网检索、定时），在律所策略与事项沙箱之内运行；不含随 Kimi 会员云提供的闭源云技能（PPT/建站、深度研究、桌面操控等，见第 3 篇 §1.5）” |
| “绝对安全”“技术上不可能泄露”“每一次联网都有记录” | “AI 写的代码在无网络的沙箱中运行；经出站闸门的每一次联网都有记录，A 级设备由系统防火墙保证客户端只经闸门出网；剩余风险与控制措施见安全白皮书” |
| “中软不是处理者” | “中软对推理与检索过境、协作与遥控密文按受托人义务管理” |

**“中软看得到什么”分情形**：

| 情形 | 中软看得到（过境或保存） | 中软看不到 |
|---|---|---|
| 默认（本机 + 网关 + 密文中继） | 账号、设备与隔离等级、席位、用量、匿名事项活动时间与期限提醒；推理时的化名片段（过境不落盘）；协作与遥控的密文 | 案卷、成果、会话转录、化名映射、事项名称、遥控内容 |
| 启用联网检索 | 去除直接标识符与已知当事人名称后的查询（过境不落盘），可能含案情要素（交易类型、金额区间、地域等） | 查询与事项的对应关系（只在本机） |
| 启用法源与主体信息查询 | 案例核验与工商查询所需的查询项（可能含当事人或关联方名称，经律师确认或按策略放行）；转给数据商 | 事项其他内容 |
| 启用 IM（M1 服务商应用） | 律师发给机器人的文字指令与文件名（过境不落盘）；文件的短时下载句柄 | 文件内容（由律师电脑直取） |
| 选择中软托管恢复 | 加密保存的恢复材料（HSM）；在两名管理员签名请求 + 72 小时冷静期后，中软可协助恢复——**此时“中软无密钥”对该律所不成立**，须在开通时明示 | 平时仍看不到事项内容 |
| 律所专属云执行（G3，默认关） | 被授权事项在任务期间的明文（内存） | 未授权事项 |

禁用词：“技术上不可能”“从来没有”“绝对”“零风险”“数据不出所”（私有化全链路组合除外）。“本地化部署 / 全链路本地化”只用于“私有模型 + 律所执行器 + 律所自有存储 + 私有控制面”的组合。

## 13. 本篇的验收（进入第 4 篇探针）

1. **能力完整**：在只配置开放平台 API token、不登录任何 Kimi 账号的前提下，Kimi Code 的 WebSearch、FetchURL、子 Agent、集群、目标、计划、技能、MCP、定时、文件历史、快照、遥控全部可用（经中软补位；终端路由在发行版关闭）。
2. **沙箱有效**：A/A′/B 三级各自通过注入红队（C 级单独标注为弱隔离）：Agent 读不到其他事项、用户目录与 homeDir；写不进原件区与交付区；沙箱内代码无法直接联网（DNS、TCP、UDP 均失败）且**访问 127.0.0.1/::1 全端口失败**；环境变量中无任何凭据；读不到任何令牌。
3. **闸门是唯一出口**：A 级设备上，除闸门进程外客户端全部进程零外部连接；B/C 级上 kap-server 出网面扫描无绕过路径（FetchURL 无本机回落）；含当事人实体的检索查询与 URL 在“默认”模式下 100% 触发确认或泛化；图像直送在 L3 事项被拦截；L3b 事项零出站；经闸门的每一次出网都有去向记录。
4. **宿主策略全覆盖**：对每一个内置工具与 MCP 工具，验证“未经宿主策略裁决不会执行”（含 Read、Agent、AgentSwarm、Skill、CreateGoal 等上游默认放行的工具）；界面或遥控送来的 `permission_mode`/yolo 不生效；子会话审批进入同一队列。
5. **云端零明文**：控制面、网关、检索服务、法源服务、中继的数据库、对象存储、日志与错误报告中抽查不到客户内容、事项名称、文件名与检索查询原文。
6. **远程降权**：手机遥控、IM、定时、执行器四个渠道都无法触发签发、对外发送、导出与改权限；遥控网关对终端、配置、工作区、插件、文件系统打开与定位等路由一律拒绝；遥控中继抓包只见密文。
7. **管理员无内容**：管理员账号在控制台与客户端都无法获得事项正文；加人进事项必须由事项成员设备完成。
8. **控制面被攻破演练**：伪造的放宽策略（只有控制面签名、无管理员设备签名）、回放的旧策略、替换的成员公钥、未经管理员签名登记的连接器，客户端全部拒绝或告警。
9. **恢复**：丢失全部设备后用个人恢复码恢复本人事项；律所恢复按版本门限恢复全部事项且留痕；中软托管恢复须管理员设备签名请求、冷静期与通知。
10. **断云**：控制面停机 72 小时内本机全部能力与推理可用、联网后同步无丢失；许可过期进入退出模式。
