### 1.1 四条不可退让的工程约束

1. **云端零明文持久化**：控制面、网关、检索服务、法源服务、中继的数据库、对象存储、日志、缓存与错误报告中不得出现客户内容、事项名称、文件名与检索查询原文。CI 扫描 + 每版红队。
2. **沙箱不可关闭，Agent 出网只经闸门**：沙箱进程无直接网络；Kimi Code 的模型、检索、抓取、MCP 全部配置为本机闸门端点；闸门是律师电脑上唯一的对外出口。
3. **一个内核、一套语义**：桌面、律所执行器、G3 云执行器运行同一份 kap-server + 法律内核制品；差别只在 DI 种子与沙箱后端。
4. **上游可追**：Kimi Code 锁版 + 补丁台账 + 双周评估；能回馈上游的（Windows 沙箱后端、hook 失败即拒绝）主动回馈，降低长期 fork 成本。

### 3.2 法律推理网关（沿用 v6，删一项）

保留：OpenAI/Anthropic 兼容接口；事项策略二次检查（如实限定能力边界）；方法资产占位符组装（含展开后 token 数回传、输出重合检测、占位符 HMAC 前缀）；无状态标识符复核（不上传当事人名单）；路由与档位（只在经评测等价的模型间切换，不自动切到其他厂商）；按律所盐值的缓存布局；权威计量与预写日志；以中软组织身份调用上游；正文与错误体不落盘；内容安全（法律专业场景策略）；模型真实性校验（能离线验签时本机校验）。

取消：**思考内容密封**。理由：K3 要求原样回传 `reasoning_content`，Kimi Code 的上下文压缩会改写历史（U6a），密封在 Agent 模式下脆弱；方法资产经思考内容回流终端的风险，以“方法正文不进系统提示全文、只在网关展开”“输出重合检测”“合同 + 水印 + 持续更新”兜底，风险等级维持“中”。

## 4. Kimi Code 全量嵌入

### 4.1 为什么用 kap-server 而不只是 SDK

v5/v6 用 node-sdk 在每个任务里起一个“只能调法律 MCP 的循环”，任务结束即删 homeDir。这样做丢掉了 Kimi Work 的大部分后端能力：会话续接、子会话树、目标模式、文件历史与快照、终端、技能与插件管理、遥控端点。kap-server 是 Kimi Code 官方的本机后端（`kimi web` 即启动它），已经提供这些路由与 OpenAPI/AsyncAPI 文档（`调研-S0` §4），并接受与 SDK 相同的 DI 种子。**v7 把 kap-server 作为桌面端的 Agent 后端**，法律内核与它并列。

### 4.2 嵌入方式

| 项 | 设计 |
|---|---|
| 进程 | kap-server 以 Electron utilityProcess 运行（Node 24），只绑定回环地址并使用 kap-server 自带的 Bearer 令牌与 Host/Origin 校验；**令牌只在主进程**，渲染进程经主进程代理访问 kap-server——主进程过滤审批响应（上层已拒绝的审批，界面送来的“批准”一律丢弃），防止被攻破的渲染进程自行批准 |
| 工作区 | kap-server 的 workspace = 事项工作区；会话与事项一一绑定（一个事项可有多个会话） |
| homeDir | 每位律师一个 Kimi Code home，存储服务替换为按事项密钥加密的实现（转录、索引密文落盘） |
| DI 种子 | `IHostProcessService` → 沙箱启动器（§5）；`IHostFileSystem` → 事项三区文件系统（v5 ZP-6 扩展）；`IFileSystemStorageService` → 加密存储；检索与抓取 provider 由配置指向闸门 |
| 配置（每次启动由内核生成） | provider `base_url` → 本机模型代理；`[services.moonshot_search]` → 闸门 `/search`；`[services.moonshot_fetch]` 不设（本机回落）或 → 闸门 `/fetch`；`mcp.json` 只含法律 MCP、法源 MCP（经闸门）、律所批准 MCP；`[tools] enabled` 按四层策略动态生成；`telemetry = false`；`builtin_product_skills = false`；`[identity]` 白标；`KIMI_CODE_PLUGIN_MARKETPLACE_URL` → 律所插件目录；`KIMI_SHELL_PATH` → 便携 bash；`skillDirs` → 中软签名技能 + 律所批准技能 + 个人技能 |
| 审批 | 引擎以 `manual` 模式运行，所有审批请求先到主进程的**策略引擎**：沙箱内动作按运行模式自动批准、上层禁止的自动拒绝、跨边界动作转给界面（桌面与已配对手机同时推送）；配置层 deny 规则不执行（#2337），用 `engineAccessor` 接线 `addRules` 作兜底（补丁 ZP-4） |
| 子 Agent | 子 Agent 审批按会话桥接到同一队列（不依赖 #4070 受影响的 hook）；集群并发与预算由策略设上限 |
| 定时 | Kimi Code Cron 保留（应用开着才触发）；内核记录错过的触发，下次启动提示补跑 |
| 遥控 | kap-server 遥控路由保留；隧道客户端经 ZP-8 改为端到端加密并指向 rc-relay |

## 5. 本机沙箱

### 5.1 统一结构

```text
kap-server（沙箱外）──IHostProcessService.spawn()──▶ 沙箱启动器（沙箱外，签名二进制）
                                                     │ 建立隔离 → 启动 → stdio 管道
                                                     ▼
                                       沙箱内命令执行器（便携 bash/Python/Node）
                                         可读：便携运行时（只读）、原件区只读副本
                                         可写：本事项工作区、私有临时目录
                                         不可见：其他事项、用户目录、系统敏感目录
                                         网络：无
                                         资源：作业对象（CPU、内存、时长、进程数）
```

文件工具（Read/Write/Edit/Glob/Grep）不进沙箱，而由“事项三区文件系统”在应用层限定；Shell 与代码执行进沙箱，由 OS 限定。两层叠加：即使应用层判断有误，OS 也不让沙箱进程越界。

### 5.2 Windows：四级实现

| 等级 | 实现 | 前提 | 参照 |
|---|---|---|---|
| **A** | 安装时（或律所 IT 一次性）以管理员权限创建专用低权限沙箱用户与出站防火墙规则，给事项工作区与运行时目录配 ACL；命令以沙箱用户身份运行并置入作业对象 | 一次管理员授权 | Codex `elevated`（`codex-rs/windows-sandbox-rs`，Apache-2.0，可复用并保留 NOTICE） |
| **A′** | Microsoft Execution Containers：按读/写/拒绝路径与原生网络策略隔离 | Windows 11 且通过能力自检；无需管理员 | Codex `mxc`（10-08 起推荐）；微软一手文档未查到，G1 探针确认后启用 |
| **B** | AppContainer/LPAC：不授予网络能力；客户端为运行时与工作区授予 ACL；作业对象 | 无需管理员；便携 bash 与 Python 须通过 LPAC 兼容性探针 | Chromium 沙箱（用户态、无需管理员） |
| **C** | 受限令牌 + ACL 写边界 + 作业对象 | 无需管理员 | Codex `unelevated`（读不受限、网络较弱）→ 只允许逐次确认的代码执行、L0–L2 |
| D | 无 | — | 代码执行不可用 |

## 6. 出站闸门与本机端点

| 端点（回环） | 来源 | 闸门做什么 | 上游 |
|---|---|---|---|
| `/v1`（OpenAI/Anthropic 兼容） | Kimi Code provider、确定性工作流 | 事项同意状态 → 化名与标识符遮蔽（请求）→ 去向记录 → 转发；响应流中**还原化名**（含 tool_call 参数），再交给引擎 | 法律推理网关 |
| `/search` | Kimi Code WebSearch | 剔除直接标识符；当事人词典 + 实体识别；按 §2 篇 §8.6 放行、确认或改写；查询原文写入本机事项账本 | 检索服务 |
| `/fetch`（可选） | Kimi Code FetchURL | 域名白名单、URL 实体与长编码串检查；结果标记“不可信外部内容” | 本机直连或中软抓取代理 |

**化名双向替换**（v7 新增的工程重点）：模型只看到化名，引擎与文件只看到真名。请求方向：引擎发出的消息（含 Read 工具返回的文件内容）在闸门里按事项映射表替换为化名；响应方向：模型的文本与工具调用参数（Edit 的 `old_string/new_string`、Write 内容、Bash 命令）在交给引擎前还原为真名，保证 Edit 精确匹配与文件写回正确。映射表在事项账本内加密保存、随事项同步；化名采用不易与正文混淆的稳定标记；还原失败（例如模型改写了化名标记）时，该次工具调用转为确认并提示。探针 6 专测。

## 7. 密钥体系（简化）

```text
账户密钥对（每位成员；P-256 签名 + P-256 加密；私钥在设备安全存储，本人设备间扫码传递）
  ├─ 个人恢复码（开通时客户端随机生成 ≥ 128 位，打印保存；包裹账户私钥备份）
  └─ 事项密钥（每事项 AES-256；HPKE 包裹给成员账户公钥 / 律所恢复公钥 / 授权的执行器）
       └─ 事件体、材料块、映射表、Kimi Code 会话存储、成果
事项目录密钥（律所一把；加密事项名称、成员、AI 使用摘要；授予主任、风控、利冲）
律所恢复密钥对（开通向导生成；私钥默认打印为 1 张律所恢复码；律所版可选 2-of-3；可选中软 HSM 托管：
  释放须两名管理员各自设备请求 + 72 小时冷静期 + 全体管理员与受影响事项负责人通知）
设备密钥（每台设备；TPM/DPAPI、钥匙串、Secure Enclave/StrongBox；用于设备身份与本地解锁）
```

- 算法套件 v1：ECDSA/ECDH P-256 + HKDF-SHA256 + AES-256-GCM + HPKE（RFC 9180）；套件 v2：SM2/SM3/SM4（按客户与密评要求切换）。选 P-256 是因为 TPM、Secure Enclave、Android StrongBox 都以它为公约数。
- 公钥分发：控制面目录 + 客户端缓存；成员公钥变化即告警；高敏事项可开启“安全码核对”。新设备加入经已有设备扫码，二维码中的一次性配对秘密不经服务器（WhatsApp 多设备 Linking Secret、1Password CPace 设备配对同类做法）。
- `platform/packages/keys`（v5 已实现 Ed25519/X25519、Shamir、ECIES）迁移到 P-256 + HPKE；Shamir 只用于律所版 2-of-3 选项。
