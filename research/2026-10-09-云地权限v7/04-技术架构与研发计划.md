### 1.1 五条不可退让的工程约束

1. **云端零明文持久化**：控制面、网关、检索服务、法源服务、中继的数据库、对象存储、日志、缓存与错误报告中不得出现客户内容、事项名称、文件名与检索查询原文。CI 扫描 + 每版红队。
2. **沙箱不可关闭，闸门是唯一出口**：沙箱进程无直接网络、对回环不可达；Kimi Code 的模型、检索、抓取、MCP 全部配置为闸门端点，并以 `HTTP(S)_PROXY` 兜底；上游“托管抓取失败即本机直连”的回落删除（ZP-11）。出站闸门是**独立签名的进程**，控制面、更新与推理流量也经它出网——A 级设备由出站防火墙按程序只放行闸门进程，使“唯一出口”由操作系统强制；A′/B/C 级为应用层约束 + 代理兜底 + CI 出网面扫描，如实标注。
5. **每一次工具调用都经宿主策略**：引擎自带的默认放行与 git 目录内自动放行不再生效（ZP-4、ZP-14）；运行模式由宿主策略决定，界面与遥控送来的 `permission_mode`/yolo 在主进程代理处剥离。
3. **一个内核、一套语义**：桌面、律所执行器、G3 云执行器运行同一份 kap-server + 法律内核制品；差别只在 DI 种子与沙箱后端。
4. **上游可追**：Kimi Code 锁版 + 补丁台账 + 双周评估；能回馈上游的（Windows 沙箱后端、hook 失败即拒绝）主动回馈，降低长期 fork 成本。

### 3.2 法律推理网关（沿用 v6，删一项）

保留：OpenAI/Anthropic 兼容接口；事项策略二次检查（如实限定能力边界）；方法资产占位符组装（含展开后 token 数回传、输出重合检测、占位符 HMAC 前缀）；无状态标识符复核（不上传当事人名单）；路由与档位（只在经评测等价的模型间切换，不自动切到其他厂商）；按律所盐值的缓存布局；权威计量与预写日志；以中软组织身份调用上游；正文与错误体不落盘；内容安全（法律专业场景策略）；模型真实性校验（能离线验签时本机校验）。

## 4. Kimi Code 全量嵌入

### 4.1 为什么用 kap-server 而不只是 SDK

v5/v6 用 node-sdk 在每个任务里起一个“只能调法律 MCP 的循环”，任务结束即删 homeDir。这样做丢掉了 Kimi Work 的大部分后端能力：会话续接、子会话树、目标模式、文件历史与快照、终端、技能与插件管理、遥控端点。kap-server 是 Kimi Code 官方的本机后端（`kimi web` 即启动它），已经提供这些路由与 OpenAPI/AsyncAPI 文档（`调研-S0` §4），并接受与 SDK 相同的 DI 种子。**v7 把 kap-server 作为桌面端的 Agent 后端**，法律内核与它并列。

### 4.2 嵌入方式

| 项 | 设计 |
|---|---|
| 进程与令牌 | kap-server 以 Electron utilityProcess 运行（Node 24），只绑定回环地址并使用 Host/Origin 校验；**令牌只在内存**——经 `startServer({ authTokenService })` 注入主进程生成的令牌，不写 homeDir 下的明文令牌文件；渲染进程与遥控网关都经主进程代理访问 kap-server，代理按各自白名单放行路由、剥离 `permission_mode`/yolo，并丢弃上层已拒绝事项的“批准”响应 |
| 工作区 | kap-server 的 workspace = 事项工作区；会话与事项一一绑定（一个事项可有多个会话） |
| homeDir 与落盘 | 每位律师一个 Kimi Code home；**加密落盘清单**：`IFileSystemStorageService`（转录、会话索引等）、文件历史与快照的 `IBlobStore`/`IAtomicDocumentStore`、会话导出 ZIP、插件存储、工作区别名——经事项密钥加密或置于已加密的事项目录；其余直连 `node:fs` 的路径列入审计清单逐一处理（探针 17） |
| DI 种子（经 kap-server `startServer({ seeds })`，与 SDK 的 `extraSeeds` 是两个入口） | `IHostProcessService` → 沙箱启动器（§5；Glob/Grep 经 ripgrep 子进程，同样进沙箱）；`IHostFileSystem` → 事项三区文件系统；存储类服务 → 加密实现；`IHostTerminalService` → 关闭（终端不是律师产品功能，且上游以 node-pty 在沙箱外起 shell）；**宿主策略服务** → 主进程策略引擎（ZP-4） |
| 配置（每次启动由内核生成） | provider `base_url` → 闸门 `/v1`；`[services.moonshot_search]` → 闸门 `/search`；`[services.moonshot_fetch]` → 闸门 `/fetch`（必须）；进程环境 `HTTP(S)_PROXY` → 闸门；`mcp.json` 只含法律 MCP、法源 MCP（经闸门）、律所批准 MCP；`[tools] enabled` 按四层策略动态生成；`telemetry = false`；`builtin_product_skills = false`；`[identity]` 白标；`KIMI_CODE_PLUGIN_MARKETPLACE_URL` → 律所插件目录；`KIMI_SHELL_PATH` → 便携 bash；`skillDirs` → 中软签名技能 + 律所批准技能 + 个人技能 |
| 审批（宿主策略） | 上游 `AgentPermissionPolicyService` 的策略链在 Agent 作用域内写死，且“默认放行”清单（Read、Glob、Grep、ReadMediaFile、TaskOutput、WebSearch、FetchURL、Agent、AgentSwarm、Skill、CreateGoal、SetGoalBudget、UpdateGoal、EnterPlanMode 等）与 git 目录内写入自动放行会在宿主看到之前就放行。**补丁 ZP-4 在策略链首位插入“宿主策略”**：经 bootstrap 种子注入的宿主策略服务对**每一次**工具调用返回允许 / 拒绝 / 询问（询问转界面，桌面与已配对手机同时推送）；ZP-14 清空上游默认放行清单与 git 自动写入放行。运行模式与预算、子 Agent 并发、目标预算都在宿主策略中判定，不依赖引擎的 `permission_mode`；`engineAccessor` 只存在于 node-sdk，kap-server 形态不使用 |

## 5. 本机沙箱

### 5.1 统一结构

```text
kap-server（沙箱外）──IHostProcessService.spawn()──▶ 沙箱启动器（沙箱外，签名二进制）
                                                     │ 建立隔离 → 启动 → stdio 管道
                                                     ▼
                                       沙箱内命令执行器（便携 bash/Python/Node）
                                         可读：便携运行时（只读）、原件区只读副本
                                         可写：本事项工作区、私有临时目录
                                         不可见：其他事项、用户目录、系统敏感目录
                                         网络：无；127.0.0.1/::1 不可达
                                         环境变量：白名单（PATH、指向事项临时目录的 HOME、LANG、PYTHON*）
                                         资源：作业对象（CPU、内存、时长、进程数）
```

文件工具 Read/Write/Edit 不进沙箱，由“事项三区文件系统”在应用层限定；Glob/Grep 经 ripgrep 子进程、Shell 与代码执行都经进程服务进沙箱，由 OS 限定。两层叠加：即使应用层判断有误，OS 也不让沙箱进程越界。

三处必须替换的上游默认：①上游 `hostProcessService` 的 `buildEnv()` 把整个 `process.env` 透传给子进程——沙箱启动器改用环境变量白名单；②kap-server 令牌默认写入 homeDir 明文文件——改为内存令牌（§4.2）；③闸门与内核的回环端点要求每进程凭据（kap-server 持有、沙箱进程不持有），并在 A/B 级由 OS 阻断沙箱访问回环，A′ 级探针专测（Codex 文档称 MXC 托管网络须放行主机回环，发行版沙箱不启用网络）。

### 5.2 Windows：五档（四种沙箱实现 + D 无沙箱）

| 等级 | 实现 | 前提 | 参照 |
|---|---|---|---|
| **A** | 安装时（或律所 IT 一次性）以管理员权限创建专用低权限沙箱用户与出站防火墙规则，给事项工作区与运行时目录配 ACL；命令以沙箱用户身份运行并置入作业对象 | 一次管理员授权 | Codex `elevated`（`codex-rs/windows-sandbox-rs`，Apache-2.0，可复用并保留 NOTICE） |
| **A′**（候选） | Microsoft Execution Containers：按读/写/拒绝路径与原生网络策略隔离 | Windows 11 且逐机通过能力自检；显式选择失败不回退；无需管理员 | Codex `mxc`（10-08 起推荐）；微软一手文档未查到——G1 探针确认前不等同 A |
| **B**（候选） | AppContainer/LPAC：不授予网络能力（含回环）；客户端为运行时与工作区授予 ACL；作业对象 | 无需管理员；便携 bash 与 Python 须通过 LPAC 兼容性探针（公开资料未见 LPAC 承载通用 Shell 的 Agent 实现） | Chromium 沙箱（用户态、无需管理员）；探针未过则 B 级只开放 Python、Bash 只在 A 级可用，或降 C |
| **C** | 受限令牌 + ACL 写边界 + 作业对象 | 无需管理员 | Codex `unelevated`（读不受限、网络较弱）→ 只允许逐次确认的代码执行、**L0/L1**；L2 须律所策略显式接受并在事项头标注 |
| D | 无 | — | 代码执行不可用 |

选择逻辑：启动自检按 A → A′ → B → C → D 依次尝试；控制台显示每台设备的等级；律所策略可要求“L3 事项只在 A 级（探针通过后含 A′/B）设备处理”。团队版开通向导提示 IT 或律师本人做一次管理员授权以获得 A 级（约 1 分钟）。**产品决策阈值**：设计合作律所盘点中，若达不到 A/B 的设备超过 20%，开通流程改为默认引导管理员授权（A 级），否则该设备只用“手动”模式。

## 6. 出站闸门与本机端点

| 端点（回环） | 来源 | 闸门做什么 | 上游 |
|---|---|---|---|
| `/v1`（OpenAI/Anthropic 兼容） | Kimi Code provider、确定性工作流 | 事项同意状态 → 化名与标识符遮蔽（请求）→ 去向记录 → 转发；响应流中**还原化名**（含 tool_call 参数），再交给引擎 | 法律推理网关 |
| `/search` | Kimi Code WebSearch | 剔除直接标识符；当事人词典 + 实体识别；按 §2 篇 §8.6 放行、确认或改写；查询原文写入本机事项账本 | 检索服务 |
| `/fetch`（必须） | Kimi Code FetchURL | 域名白名单；搜索引擎与可回显查询参数的站点不允许；URL 实体与长编码串检查；结果标记“不可信外部内容” | 闸门进程本机直连，或中软抓取代理 |
| `/mcp/sources` | 法源 MCP | 去标识；Source Registry | 法源服务 |
| `/mcp/legal` | 法律 MCP | 事项令牌校验（v5 已实现） | 本机内核 |
| `/mcp/firm/*` | 律所批准连接器（登记须管理员设备签名） | 数据级别上限 | 律所服务 |
| 控制面、更新、中继 | 客户端主进程、同步客户端 | 目的地固定、只出元数据或密文 | 中软云端 |

**闸门是独立签名的进程**：A 级设备上，出站防火墙规则只放行闸门进程（控制面、更新、中继流量也经它出网），客户端其他进程（Electron 主进程与渲染进程、kap-server、内核、沙箱）一律不能直接连外网；A′/B/C 级设备上做不到按程序阻断，改为 `HTTP(S)_PROXY` 兜底 + 删除已知直连路径（ZP-11、ZP-12）+ CI 对 kap-server 出网面的扫描，并在设备页如实显示“唯一出口：系统强制 / 应用层约束”。

**图像载荷**：推理请求中的 `image_url`/data URI（Kimi Code 的 ReadMediaFile 会把图片以 base64 送模型）单独识别：L2 须确认、L3 拦截，并计入去向卡；默认引导改走本机 OCR 后送化名文本。

**本机渲染与文档外链**：桌面渲染进程与移动端视图对 Agent 产出的 Markdown/HTML 实行严格内容安全策略（`default-src 'none'` 起步，不加载外部图片、样式与脚本），HTML 预览放在无网络的隔离框架；Agent 生成的 DOCX/XLSX/PPTX 交给 Word/WPS 打开前由文书引擎剥离外部关系（远程模板、外链图片）。

**化名双向替换**（v7 新增的工程重点）：模型只看到化名，引擎与文件只看到真名。

| 环节 | 规则 |
|---|---|
| 请求方向 | 引擎发出的消息（含 Read 工具返回的文件内容、Bash 输出）在闸门里按事项映射表替换为化名；直接标识符（证件号、手机号、银行卡、统一社会信用代码等）一律遮蔽 |
| 响应方向（流式） | 文本流可边替换边显示（以映射表最长标记长度做滑动缓冲）；**工具调用参数先完整缓冲**，参数闭合后整体还原为真名再交给引擎执行——Kimi Code 本就在参数完整后才执行工具，不增加交互延迟 |
| 思考内容 | `reasoning_content` 以**化名形态**存入会话转录并原样回传上游（满足 K3 原样回传要求，压缩时也保持化名），只在界面展示时临时还原，避免“还原—再化名”不一致 |
| 漏化名 | 词典外的新主体由实体识别兜底；识别到疑似未化名主体时，**默认暂停该次请求**并提示律师加入词典或确认放行，不静默放行 |
| 还原失败 | 模型改写了化名标记、或一个标记对应多个真名而上下文不足以判定时，该次工具调用转为确认 |
| 映射表 | 在事项账本内加密保存、随事项同步；化名采用不易与正文混淆的稳定标记 |

探针 6 测三项：Edit 匹配成功率（≥ 99%）、漏化名率（注入未入词典的新主体，看是否被拦截）、误还原率。

## 7. 密钥体系（简化）

```text
账户密钥对（每位成员；P-256 签名 + P-256 加密；私钥在设备安全存储，本人设备间扫码传递）
  ├─ 个人恢复码（开通时客户端随机生成 ≥ 128 位，打印保存；包裹账户私钥备份）
  └─ 事项密钥（每事项 AES-256；HPKE 包裹给成员账户公钥 / 律所恢复公钥 / 授权的执行器）
       └─ 事件体、材料块、映射表、Kimi Code 会话存储、成果
事项目录密钥（律所一把；加密事项名称、成员、AI 使用摘要；授予主任、风控、利冲；持有人变更时按纪元轮换并重新包裹）
管理员签名（管理员账户签名密钥；成员客户端入组时固定管理员公钥；放宽类策略与连接器登记须其签名）
律所恢复密钥对（开通向导生成；律所版默认 2-of-3 分片；团队版默认“律所恢复码 + 一名在线管理员设备确认”；
  可选中软 HSM 托管：释放须两名管理员以各自管理员设备签名请求 + 72 小时冷静期 + 全体管理员与受影响事项负责人通知）
设备密钥（每台设备；TPM/DPAPI、钥匙串、Secure Enclave/StrongBox；用于设备身份与本地解锁）
```

- 算法套件 v1：ECDSA/ECDH P-256 + HKDF-SHA256 + AES-256-GCM + HPKE（RFC 9180）；套件 v2：SM2/SM3/SM4（按客户与密评要求切换）。选 P-256 是因为 TPM、Secure Enclave、Android StrongBox 都以它为公约数。
- 公钥分发与律所侧校验锚：控制面目录（单调版本号）+ 客户端缓存；**管理员公钥入组时固定**（律所版默认当面或电话核对安全码，团队版首次信任 + 可选核对）；成员账户公钥只在账户恢复时变化（新设备经扫码继承同一账户密钥），**变化后须事项负责人或管理员核对安全码才重新包裹事项密钥**；新设备加入经已有设备扫码，二维码中的一次性配对秘密不经服务器（WhatsApp 多设备 Linking Secret、1Password CPace 设备配对同类做法）。
- 策略：收紧类由控制面签名即可；放宽类（允许云端执行、放开 L3a、开放新运行模式、新增出站地址或连接器）须律所管理员设备签名（团队版 1 名、律所版 2 名）；策略带单调版本号与 30 天有效期，客户端拒收低于已见版本者，过期回退“中软基线 + 最严模板”。
- 事项目录密钥轮换：持有人变更或离职时，由在线持有人设备生成新纪元密钥，新内容用新纪元加密；旧纪元密钥包裹给新持有人以便查阅历史；轮换写入运营审计。
- `platform/packages/keys`（v5 已实现 Ed25519/X25519、Shamir、ECIES）迁移到 P-256 + HPKE；Shamir 只用于律所版 2-of-3 选项。

## 11. 安全

### 11.1 v7 新增威胁与控制

| 威胁 | 控制 |
|---|---|
| 放开 Shell/代码执行后的外泄与破坏 | 沙箱无网络；原件只读；工作区可回滚；闸门是唯一出口；注入红队 ≥ 300 例 |
| 沙箱逃逸 | 四种沙箱实现各自的红队；沙箱对回环不可达、环境变量白名单、无令牌文件；及时跟进 Windows 与上游补丁；C 级只允许逐次确认且限 L0/L1 |
| 绕过闸门出网 | 闸门为独立进程，A 级由防火墙强制唯一出口；删除抓取回落（ZP-11）、关闭终端（ZP-12）、`HTTP(S)_PROXY` 兜底；渲染 CSP 与 Office 外链剥离 |
| 绕过审批 | 宿主策略位于引擎策略链首位、清空默认放行（ZP-4、ZP-14）；主进程代理剥离 `permission_mode`/yolo |
| 图像直送模型 | 图像载荷识别：L2 确认、L3 拦截；默认本机 OCR |
| 检索查询泄露当事人 | 本机去标识与实体匹配；命中即确认；L3b 禁止；查询原文不出律所侧日志 |
| 抓取 URL 隐写外泄 | URL 实体与长编码串检查；新域名确认；“自动”模式只放行白名单 |
| 恶意插件或技能 | 三类来源准入；案卷目录内配置一律不加载；律所批准插件哈希锁定 |
| 遥控通道被劫持或越权 | 端到端加密 + 配对密钥 + 设备凭据；隧道终止于主进程遥控网关、只开白名单接口；组织策略可整体关闭遥控 |
| 控制面被攻破 | 拿不到明文与密钥；放宽类策略与连接器登记须律所管理员设备签名、版本单调防回放、管理员公钥固定、成员公钥变更须核对——攻击者只能扣留通知或拒绝服务；残余为成员首次入组时对管理员公钥的首次信任 |
| 中软推送恶意客户端（被迫或恶意） | 代码签名与版本哈希公开、第三方审计、律所版“延迟更新 + 哈希核对”；如实写入白皮书 |
| 化名还原错误导致文件写错 | 还原失败转确认；文件历史可回滚 |
