## 2. 诊断

### 2.1 v5：一个维度决定全部位置（v6 的诊断成立）

v5 用“谁持有案卷明文”这一个问题决定所有能力的位置，推出“云端只供 token”。v6 第 1 篇 §2.2 列出的十七个问题（所内节点成为隐性必需品、身份与控制台在局域网、IM 与提醒依赖常开机器、共享文件夹同步、方法资产下发终端、计量可篡改等）全部成立，v7 接受。

但 v5 还有两个 v6 没有指出、也没有修正的问题——它们正是 v7 的出发点：

| # | 问题 | 证据 |
|---|---|---|
| P18 | **“云端只供 token”在 Kimi Code 上并不成立**：Kimi Code 的联网检索、数据源插件、手机遥控、账号、插件市场都依赖月之暗面的会员云服务，只买 token 时这些能力直接消失。v5 没有清点，而是悄悄放弃了这些能力 | `调研-S0` §2；WebSearch 工具在无托管登录且无配置时不注册（`webSearchTool.ts:117`）；“Kimi Code API 与开放平台 API 相互独立，不通用”（`调研-S1` Q3.9） |
| P19 | **把 Kimi Code 当成危险品而不是内核**：内置工具全禁、注入拒绝式进程服务、只开放法律 MCP 与四个交互工具；生产档全部走确定性工作流 | `platform/third_party/PATCHES.md`（“内置工具全禁”“拒绝式 IHostProcessService”）；v5 第 0 篇决策 2 |

### 2.2 v6：控制面修好了，留下四个结构性错误

| # | 错误 | 具体表现 | 后果 |
|---|---|---|---|
| **E1** | 漏了“能力来源”维度 | 继承 v5 的 P18：没有给检索、数据源、遥控中继找上游；用“律师逐条确认派生查询 → 云端公开沙箱”替代联网研究，用“IM 内 H5 解密签发”替代遥控 | 研究流程每次都要逐条确认，律师用起来比 Kimi Work 慢；IM 内 WebView 的不可导出密钥与生物识别可用性（U4、U18）没有把握；云端还多了一套每任务一容器的公开沙箱 |
| **E2** | 用“删能力”代替“定边界” | 继承 v5 的 P19；T0–T7 中没有 Shell，代码执行只给无网络的 WebAssembly Python，浏览器默认关，“Agent 集群改为内核控制的有界并行” | 发行版比律师花几百元就能买到的 Kimi Work 标准版**更弱**（Kimi 企业版 ¥4,200/座/年已含 Kimi Work 与 Kimi Code）；与用户“完整接入 Kimi Code”的要求相反 |
| **E3** | 用密码学对抗一个密码学挡不住的对手 | 律所根密钥治理仪式、根签名策略与设备证书、6 位确认码、24 小时观察期、2-of-3 恢复卡 + 中软第 4 片 + 72 小时冷静期、Merkle 透明日志 + 树头比对 + 第三方见证、盲化订阅、H5 解密签名、思考内容密封 | 中软同时发布客户端与 H5 并运营看得到化名片段的网关，这些机制挡不住“恶意更新”；它们真正防住的威胁用简单的端到端加密即可防住。代价约 40–60 人周、多个未决项、首日仪式、密钥丢失即案卷丢失的风险；对抗式审阅 36 条中有 11 条是在给这些机制打补丁（v6 第 6 篇 §D：B1–B3、B5、I9–I13、I21、I22）。**v7 的修正**：取消重仪式，但保留轻量律所侧校验锚（管理员公钥固定、放宽类策略与连接器登记须管理员设备签名、版本单调、公钥变更核对）——对抗式审阅 B5 指出“全部取消”会让控制面被攻破时只剩内控 |
| **E4** | 没有“云 → 本机”的渠道权限 | IM、手机、定时、执行器、云端服务都能触发律师电脑上的任务，却只按本机任务档位管理 | Kimi Code 的远程控制在源码里是把本机后端整个经中继暴露给远端（`remote-control.ts:591-690`）；WorkBuddy 把远程任务限定在“助理专属文件夹、单会话”（`调研-S2` Q1.4）——律所需要一张远程渠道权限表 |

**一句话归纳**：v5 只看“数据在哪”，v6 加上了“控制在哪”，两者都没有看“**能力从哪来**”与“**边界靠什么守**”。v7 补上这两个维度：能力来源决定云端必须补什么（第 2 篇 §4），沙箱决定本机可以放开什么（第 2 篇 §8.5）。

## 3. 主流产品给出的新证据

v6 的五条结论（控制面一律在厂商云；执行面可插拔且在往云上移；受监管客户默认更保守；法律 AI 头部全是云 SaaS 靠信任包；桌面定时关机不跑）继续成立。本轮补充六条：

1. **本机权限的通用结构是“工作区边界 + 跨边界确认”两层，而不是删工具。** Claude Code、Codex、CodeBuddy Code 都给 Agent 完整的文件与 Shell 能力，靠沙箱定边界、靠审批管跨边界；Codex 默认“工作区内读、改、执行自动，越出工作区或要联网时才问”（`调研-S2` Q4.5）。
2. **Windows 本机沙箱可以做，但只有一家做到原生。** Claude Code 在原生 Windows 上不沙箱（须 WSL2）；WorkBuddy/CodeBuddy 与 Kimi Code 上游尚无 Windows 实现；千问办公与 Cowork 用本机虚拟机（须管理员开启）；**OpenAI Codex 有三种原生实现**，其中 `mxc` 无需管理员、`elevated` 需 IT 一次性预配、`unelevated` 为受限令牌回退，代码以 Apache-2.0 开源（`codex-rs/windows-sandbox-rs`）。
3. **远程触发一律被收窄。** WorkBuddy 远程任务固定在“助理专属文件夹”；Claude Cowork 云会话只能回取已连接文件夹，Dispatch 停用；Codex“在设备间切换不授予对另一台电脑的访问”。
4. **企业锁定与“失败即拒绝”是新标配。** Claude Code 的 managed settings 可禁用 auto 与 bypass 模式，v2.1.295（10-08）新增 hook `onFailure: "block"`；而千问办公企业 Hooks 超时或不可达即放行——律所场景必须选前者。
5. **月之暗面自己在补“token 之外”的能力。** 9 月开放平台上线 `/v1/tools/search`（¥0.01/次）、`search_pro`（¥0.015/次，可限定站点）、`/v1/tools/fetch`（¥0.01/次），`$web_search` 预计 10-20 下线；同月上线托管智能体 Beta（会话与产出存服务端，**明确不符合零数据留存**）。这让“检索补位”可以留在同一供应商与同一 DPA 内，也说明托管智能体不能用于客户事项。
6. **Kimi 企业版治理仍为空白。** 截至 10-09，Kimi Work 最新仍为 3.2.15，企业版只有席位与成员管理，无 SSO、审计与管理员策略；Kimi Work 远程控制的链路与加密方式官方未说明，其同内核的 Kimi Code 远程控制明写“统一走 Kimi 中转服务”、源码无端到端加密。

## 5. 功能效果：律师看得到的差别

| 关键时刻 | v5 | v6 | **v7** |
|---|---|---|---|

## 7. 全局视角：容易被忽略的十六件事

1. **“只买 token”是采购事实，不是架构原则。** 架构原则是“案卷在所”；为了让 Kimi Code 能力不缺，中软云端必须补位检索、数据源、遥控、账号、分发（第 2 篇 §4）。
2. **律师可以自己买 Kimi 企业版。** ¥4,200/座/年已含 Kimi Work 与 Kimi Code。发行版定价 9,800 元，必须同时做到“本地 Agent 能力不少于它”和“治理、法律能力、可信交付多于它”——任何一项弱于标准版都是销售中的致命问题。
3. **检索补位优先用月之暗面自己的工具 REST 接口**：同一供应商、同一 DPA、按次计费；但须在 ZDR 申请中写明覆盖 `/v1/tools/*`（S1：文档未写明查询词留存口径）。
4. **托管智能体（Kimi Hosted Agents）不用于客户事项**：官方明写不符合零数据留存；只可用于中软内部的非敏感任务。
5. **`$web_search` 10-20 下线**：任何沿用旧内建工具的 demo 代码须在 G0 前切换。
6. **Kimi Code 2.1.1 回滚了 2.1.0 的工作区加固**：v5/v6 因“内置工具全禁”而不回移；v7 打开工具，回移加固是 P0。
7. **把 Windows 沙箱后端回馈 Kimi Code 上游**：上游 PR #4115 只做了 macOS/Linux；中软贡献 Windows 后端，是“登月计划”伙伴关系里最实在的技术投入，也降低长期 fork 成本。
8. **行业在往“自动模式 + 后台安全检查”走**：Claude Code 自 09-25 起终端默认 `auto`；Codex 默认“工作区内自动、跨边界才问”。v7 的“默认档沙箱内自动”顺应这一趋势，同时保留律所的锁定权。
9. **Hook 必须能“失败即拒绝”**：千问办公 Hooks 是 fail-open；Kimi Code 自带 hooks 也是失败放行。律所 Hooks 由我们的策略引擎实现。
10. **律师电脑多是个人 Windows 笔记本**：家庭版没有 Windows Sandbox，WSL2/Hyper-V 需管理员。凡依赖虚拟机的方案（千问办公、Cowork 路线）都不适合作为默认。
11. **Agent 集群是成本问题**：Kimi Work 宣传“最多 300 个子 Agent”；在席位制下必须由律所策略设并发与预算上限。
12. **检索查询本身是个人信息处理**：含当事人名称的查询发往中软与月之暗面，同样属于委托处理与转委托，须进 DPA 与告知同意。
13. **会话转录是案卷的一部分**：Kimi Code 默认把转录以明文 JSONL 落盘；v7 注入加密存储，并纳入事项保留与删除。
14. **期限提醒与 Agent 定时必须分开**：前者云端调度（关机不漏），后者在本机或执行器（错过提示补跑）。
15. **私有化仍是同一软件**：kap-server、沙箱、闸门、网关组件都可在律所内运行；“本地化部署”口径只用于私有模型 + 执行器 + 自有存储 + 私有控制面。
16. **不要再在执行位置上摆动**：v7 之后的调整应当只在单项能力的放置上微调（第 2 篇 §9 表内），不再改变“案卷在所、控制在云、能力补位、沙箱放权”四条主干。

## 9. v7 整合原则

1. **先问能力从哪来，再问数据在哪、控制在哪、边界靠什么守。**
2. **能在本机原样运行的 Kimi Code 能力一律保留；只买 token 拿不到的，由中软按原协议补位。**
3. **边界由沙箱守，确认只用于跨边界；没有完全访问。**
4. **远程永远比本机低一档；签发与对外发送永远是人。**
5. **端到端加密防云端被动窃取与内部越权；轻量律所侧校验锚防控制面被主动篡改；对发布客户端的一方，靠签名、审计与合同，如实说明。**
6. **放权必须有落点：宿主策略、闸门唯一出口、遥控网关三道边界是 G0 的退出条件。**
7. **v6 的控制面、网关、IM、提醒、数据分级、人的权限，v5 的本机内核与已实现代码，astra 的工程纪律，全部保留。**
