## 一、阻断

### B1　遥控通道实质暴露整个 kap-server，远程降权缺少落点

**问题**。`04` §3.5、§4.2 要求遥控“kap-server 路由不改”，ZP-8 只在隧道客户端加一层帧加解密。端到端加密解决“中继看不到内容”，不解决“远端能调用哪些接口”。`02` §8.7 承诺手机遥控“运行模式上限：默认（不可切到自动）”，且不能签发/导出/改权限/T6 写入/T7/T8。这些约束没有强制点。

**证据**（源码）：
- `remote-control/src/remote-control.ts:602-624`（`forwardHttpRequest`）、`:690`：把远端请求解析后带本机服务令牌（`localServerToken()`）转发给本地 kap-server，无路径/方法过滤。
- 远端由此可达 kap-server 全部路由：`routes/terminals.ts:116` 创建终端 → `hostTerminalService.ts:15-22` 用 `node-pty` 直接起 shell（该 `IHostTerminalService` 不在 `04` §4.2 的 DI 替换清单内，即终端不在沙箱里）；`routes/config.ts:65`、`routes/prompts.ts:282`、`routes/sessionAgentConfig.ts:37` 可把会话切 `yolo`/改 `permission_mode`；`routes/fs.ts` 的 `open/open-in/reveal`（:828、:839 经 `lib/fileLaunch.ts:195` 启动本机程序）与 `/fs::suggest`（:502，任意绝对路径）。
- `04` §4.2 新增的“主进程代理过滤审批响应”只覆盖渲染进程，遥控隧道在 kap-server 侧直连，不经主进程代理。

**为什么重要**。§8.7 全表、R5、验收 5、探针 16 都假设“远端只能做被允许的事”；实际远端具备本机最高权限（含未沙箱 shell），绕过事项沙箱与闸门。这正是 v7 在 E4 里批评上游的点，v7 只给它加密没有降权。配对手机或 WebView 页面一旦被注入（见 I3），等于设备被接管。

**建议**。遥控隧道终止于主进程“遥控网关”，以白名单只暴露：列会话、发起模板任务、查看进度与产物预览、对 T4/T5 确认作答、回答提问、上传收件区；丢弃请求里的 `permission_mode/yolo/runtime_id`；禁止远端触达 `terminals/config/sessionAgentConfig/workspaces(add-dir,trust)/plugins/fs(open,reveal,suggest)/shutdown/remote-control/oauth`。ZP-8 改为“上游遥控转发改为宿主回调”，删去 §3.5/§4.2 的“路由不改”。终端 `IHostTerminalService` 也需注入沙箱实现或在发行版关闭。探针 16 增加对上述路由的拒绝验证。

### B2　出站闸门不是唯一出口

**问题**。核心不变量是“Agent 出网只经闸门、一切出站有去向记录”（`02` §6.5、`04` §1.1 约束 2、验收 3）。多条路径不经闸门：
1. **FetchURL 回落直连**：`agent-core-v2/src/app/web/providers/moonshot-fetch-url.ts:42-62`，托管抓取失败（含非 200）后 `return this.localFallback.fetch(url,…)`，闸门拒绝一次即被同一 URL 的本机直连绕开。
2. **默认不配抓取端点即直连**：`04` §3.3、§4.2 说“默认不配置 `[services.moonshot_fetch]`，Kimi Code 回落本机直连抓取（经闸门）”，但 `app/web/webService.ts:36-37` 未配置时直接用 `LocalFetchURLProvider`，在 kap-server 进程内发请求，不经闸门；与 `02` §4 #3、`04` §6“/fetch（可选）”互相矛盾。
3. **kap-server 进程自身有完整网络**：进沙箱的只是 `IHostProcessService` 起的子进程；FetchURL、MCP 客户端、插件下载（`app/plugin/*` 直连 `node:fs`）、`features/tower/protocol/git.ts` 的 `execFile('git')`、`hostTerminalService` 均在 kap-server 进程内。“经闸门”只是 `base_url` 指向回环的配置约定。
4. **渲染/文档外链**：桌面渲染与移动 WebView 渲染 Agent 产出的 Markdown/HTML 中的外部图片/样式会直接请求外部；python-docx 产出的 DOCX 可含外部关系（远程模板/图片），律师在 Word/WPS 打开时由 Office 出网。均在闸门外。
5. **隔离浏览器输入未检查内容**：`02` §8.6 只管“白名单站点、表单提交确认”，去向卡只记域名；按当事人名在公开站点检索即把实体交给第三方。

**为什么重要**。直接决定对外第二句口号“每一次联网都有记录”（`05` §4）与 TC260“内置隔离”证据是否成立；第 1 条是可复现的闸门绕过。

**建议**。新增 P0 补丁：删除 `MoonshotFetchURLProvider` 本机回落，`[services.moonshot_fetch]` 必须指向闸门 `/fetch`；并给 kap-server 进程设 `HTTPS_PROXY/HTTP_PROXY` 指向闸门作兜底（`local-fetch-url.ts` 读代理）。把“kap-server 不得直接出网”写成可验证约束（A 级按进程路径的出站防火墙只放行闸门进程；其余等级如实降级为应用层约束 + 审计），CI 扫描 kap-server 出网面。渲染与移动 WebView 设严格 CSP，Agent 产出 HTML 预览放无网络来源；DOCX/XLSX/PPTX 交 Office 前剥离外部关系。浏览器输入也走实体匹配。验收 3 改为“除闸门进程外全部进程零外部连接”。

### B3　沙箱隔离的两处设计缺口与 C 级处理 L2

**问题**。`02` §8.5 称“沙箱内没有任何令牌”“没有直接网络”，验收 2 只测 DNS/TCP/UDP 失败与读不到令牌。实际：
- 上游 `hostProcessService.ts:40` 的 `buildEnv()` 把整个 `process.env` 透传子进程（Bash 工具仅在其上加少量变量，`bashTool.ts:166-172`）；沙箱启动器若沿用，宿主注入 kap-server 的环境变量会进沙箱。
- kap-server Bearer 令牌默认以明文文件存于 homeDir（`kap-server/src/services/auth/tokenStore.ts:13-37`，经 `node:fs` 直写，不走加密存储）。
- 回环上有 kap-server（含未沙箱终端路由，见 B1）与闸门 `/v1 /search /fetch /mcp`（`04` §6），文档未说明它们如何区分请求来源于 kap-server 还是沙箱进程；A′（MXC）据 `调研-S2` §4.4 托管网络须 `allow_local_binding=true`（放行主机回环）。
- 综合效果：C 级“读取不受限、网络弱”（§8.5 自承）时，“沙箱内无令牌、无网络”这一前提并不稳固。

同时 C 级被允许“逐次确认运行代码、只限 L0–L2”。L2 即客户材料，而 C 级读取不受限；“逐次确认”依赖律师读懂 Agent 写的脚本，律所场景不成立。

**为什么重要**。沙箱是放开 Bash/Python 的唯一前提（R4）；上述缺口把“逃逸靠补丁与红队”从残余风险变为设计缺口。

**建议**。用 `start.ts:116` 的 `authTokenService` 注入仅内存令牌（不落盘）；沙箱启动器采用环境变量白名单（PATH、HOME 指向事项临时目录、LANG、PYTHON*），在 §8.5“凭据”行写明。回环对沙箱一律不可达（A 级防火墙含回环、B 级 LPAC 不授回环、A′ 探针专测），闸门/内核回环端点要求每进程凭据。验收 2/探针 2 增加“沙箱访问 127.0.0.1/::1 全端口失败、读不到 homeDir 与令牌、env 无凭据”。C 级降为只限 L0/L1，L2 起按弱隔离要求律所显式接受并在事项头标注。

### B4　审批强制点在 kap-server 形态下没有落点

**问题**。`02` §8.2 强制点②与 `04` §4.2 把“所有审批先到主进程策略引擎、ZP-4 用 `engineAccessor` 接线兜底、子 Agent 审批经 SDK 会话桥接不受 #4070 影响”作为前提。逐条核对不成立：
- `engineAccessor` 只存在于 `node-sdk/src/sdk-rpc-client-v2.ts`，kap-server 无此接口，ZP-4 按现写法无法实施。“SDK 审批不受 #4070 影响”是 v5/v6 用 SDK 时的结论（`PATCHES.md` 免 patch 表），v7 改用 kap-server 后须重新验证子会话审批是否进入 kap-server 审批路由。
- `manual` 模式并不等于“所有工具先问策略引擎”：`agent/permissionPolicy/policies/default-tool-approve.ts:8-30` 在兜底询问前自动放行 Read/Grep/Glob/ReadMediaFile/TaskOutput/CronList/WebSearch/FetchURL/**Agent/AgentSwarm/Skill/CreateGoal/SetGoalBudget/UpdateGoal**/EnterPlanMode 等；`git-cwd-write-approve.ts:27` 在 git 工作目录内自动放行 Write/Edit。这些调用不产生审批请求，策略引擎看不到。ZP-10 只覆盖了其中 WebSearch/FetchURL。于是 §8.8 的“集群并发 ≤ 8、目标须设预算、子 Agent 不升级模式”“T3 预算内自动”“T7/T8 确认”都缺执行点。
- 运行模式可被 REST 改写（`routes/prompts.ts:282`、`routes/config.ts:65`），若不在主进程代理前拦截，策略引擎设定的档位会被绕过。

**为什么重要**。审批是四层策略落到工具层的唯一机制，也是“Agent ≤ 委托人”“子 Agent 不越权”的实现点。当前它只拦住了会主动发审批请求的少数工具，而放开的恰是编排类（Agent/AgentSwarm/Goal/Skill）与读类工具。

**建议**。不要依赖引擎的 `permissionPolicy`：在 kap-server 审批路由（`routes/approvals.ts`）与工具执行前，统一经主进程策略引擎裁决**全部**工具（含 Agent/AgentSwarm/CreateGoal/Skill/Read 等），把“中软基线 ∩ 律所策略 ∩ 事项策略 ∩ 运行模式”在此套用；或打补丁清空 `default-tool-approve` 的自动放行清单改为“全部转宿主”。明确 ZP-4 在 kap-server 下的等价实现（或删除对 `engineAccessor` 的引用）。主进程代理必须在转发前剥离/校验 `permission_mode`、`yolo`。G0 增加一条探针：对每个工具验证“未经策略引擎不会执行”。

### B5　取消律所侧信任锚后，威胁模型自相矛盾

**问题**。`02` §3.2 威胁表把“外部攻破中软云端”“中软运维越权”的防线列为“密码学”，`02` §6.5 控制面不变量称“不持有任何事项密钥、签名私钥或恢复私钥”。但 v7 为简化（E3）取消了律所根密钥签名、确认码、观察期、透明日志后，控制面同时承担：公钥目录分发（§8.11“公钥分发：控制面分发”）、策略签名与下发（§8.2“控制面签名”）、设备公钥目录与吊销、连接器登记。这些都没有律所侧独立验证锚。后果：
- **首次公钥分发可被替换**：§8.11 自己承认“恶意服务器理论上可在首次分发时提供不实公钥”，仅以“1Password 白皮书附录 C 同样承认”作类比。但 1Password 的新设备加入还有账户密码/Secret Key 或 SSO 另一因子（`调研-S3` §4.1、结论表），v7 的新设备只靠“已登记设备扫码或个人恢复码”，公钥真实性完全依赖控制面目录——攻破控制面即可对新加入成员/新事项成员做中间人。
- **策略放宽可被下发或回放**：只靠“控制面签名 + 通知全体管理员 + 放宽横幅”；攻破控制面者能用控制面签名密钥签发放宽策略，或扣留新策略、回放旧的宽松策略（v6 I22 原样未解决，`01` E3 也只说“取消”未说如何防回放）。通知走的也是被攻破的控制面。
- **连接器登记**：§8.6 根集⑦“律所批准的连接器与律所自有服务”、§8.9 律所 MCP 由控制台登记，攻破控制面可登记一个外泄用的“连接器”作为合法出站目的地。

即“密码学防住云端被攻破”这一行与“简化掉所有律所侧校验锚”直接冲突。v7 把 E3 从“过度”摆到了另一端：v6 的根签名/透明日志确实繁重，但完全取消后，表格里归为“密码学”的两类威胁实际退化为“内控 + 合同”。

**为什么重要**。这关系到对外口径“中软看不到案卷……攻破云端也拿不到”（`02` §12、`05`）能否成立，是合规承诺的底座。

**建议**。保留端到端加密（防被动窥探）的同时，为“主动攻破控制面”补回**轻量**信任锚，不必回到 v6 的全套仪式：(1) 策略与公钥目录加**单调版本号 + 律所侧 TOFU 固定**，新策略版本不得低于端侧已见版本（防回放），放宽类变更要求律所侧第二管理员设备签名（不是控制面签名）；(2) 成员公钥变更“安全码核对”从“高敏可选”改为默认，新设备/新成员首次信任给出带外校验；(3) 连接器登记须律所管理员设备签名。并在 §3.2 把两类威胁的防线如实改为“端到端加密 + 律所侧校验锚”，去掉“纯密码学即可”的表述。

### B6　“中软看得到/看不到”与真实数据流不符（v6 B4 回潮）

**问题**。`02` §12、`03` §4.6、`05` §1.1 的口径是“中软看得到账号、设备、席位、用量与匿名事项活动时间；推理片段与检索查询过境不落盘；看不到案卷、成果、化名映射与事项名称”。与方案自身其他处对照，至少以下内容会以明文到达中软而未被口径覆盖：
- **IM M1 的文字指令与文件名过境中软**（`02` §8.7 IM 行“M1：文字指令与文件名过境中软”、`05` §1.2 ⑧“M1 下文字指令与文件名经中软过境”）。文字指令与文件名常含当事人与案情，这与“看不到事项名称/客户名”直接冲突（正是 v6 B4）。
- **检索查询按 §8.6 只剔除“直接标识符 + 当事人词典实体”**；词典之外的主体名、地名、项目代号、金额等要素会随查询到达中软检索服务与上游（`05` §1.2 ② 也承认“仍可能含案情要素”）。口径“去标识检索查询”对非技术读者会被理解为“无法识别”。
- **法源/主体信息查询**（T6、能力 #18/#36）：案例存在性核验、工商信息查询往往要带当事人或关联方名称，经中软法源服务到数据商；口径未覆盖。
- **中软托管恢复**：选择该项时托管材料在中软 HSM，释放仅受“两名管理员 + 72 小时 + 通知”约束（§8.11）——此时“中软无密钥、看不到正文”对该律所不再为真，口径未分情形说明。
- **移动产物预览由电脑渲染经加密通道传输**（§11.4）属实；但遥控发起任务的**文字指令**经 rc-relay，若按 B1 修复前，指令内容是否过境中软取决于加密边界，需在清单中写明。

**为什么重要**。这是对律所与监管的核心承诺，失实表述在 PIPL 告知同意与律协“如实说明”下是合规风险；v6 已把同类问题判为阻断，v7 不应回潮。

**建议**。`02` §12 与 `05` §1.1 的“看不到”一栏按渠道分情形重写：默认（纯本机 + 网关 + 密文中继）下中软看不到什么；启用 IM M1 时文字指令与文件名过境；检索/法源查询含“去标识后仍可能保留的案情要素”；选择中软托管恢复时的例外。把“去标识”改为“去除直接标识符与已知当事人实体后仍可能含案情要素的查询”。`03` §4.6“中软看得到什么”页同步，并按律所实际启用的渠道动态展示。

### B7　ReadMediaFile 把图像原样送模型，图像无法化名且不在 ZDR 例外内

**问题**。T0 读类工具含 ReadMediaFile（`02` §8.4 T0，默认模式自动放行，见 B4）。上游 `agent-core-v2/src/agent/tools/read-media-file/readMediaFileTool.ts:417-420,443` 把图像读为 base64 以 `image_url`（data URI）放入消息送模型。化名双向替换（`02` §8.6、`04` §6）只能处理**文本**，无法对图片里的身份证、合同盖章页、病历、人像做去标识。而 `调研-S1`（`05` §1.1 ①、`03` §1.5）明确：ZDR 例外点名的恰是“图像或视频的直接上传”，`file-extract` 文本是否在 ZDR 覆盖内都未确认。于是扫描件/照片类证据经多模态推理上云时，既绕过化名，又落在 ZDR 保护之外。

**为什么重要**。律所材料大量是扫描件与照片（身份证、营业执照、合同签字盖章页、医疗票据），属 L3a 法定敏感的高发区。T0 默认自动 + 图像不可化名 + ZDR 不覆盖，三者叠加是实质外泄面，且与“L3a 强制化名”“推理只收化名内容”的承诺冲突。

**建议**。把 ReadMediaFile 从“T0 默认自动”降为跨边界动作：图像送多模态前须确认，L3a/L3b 默认禁止直接送模型；优先走本机 OCR（能力 #14 已有）得到文本后再化名送模型。闸门对 `image_url`/data URI 载荷单独计入去向卡并按事项级别拦截。谈判清单（`05` §5.4）把“多模态图像输入的 ZDR 覆盖”列入 P0，未确认前对 L3 禁用图像直送。

## 二、重要

### I1　隔离等级 A′/B 的描述与证据不符；bash 前提未证即放行；无回退路线

**问题**。`02` §8.5 等级表把 A′（MXC）、B（AppContainer/LPAC）都标“文件隔离强、网络隔离强、允许同 A（全部事项级别、全部模式）”。与 `调研-S2` 不符：
- B（LPAC）：`调研-S2` §5.1、汇总表②明说“通用 Python/Shell 在 LPAC 下兼容性差（大量路径需 ACL），未查到 Agent 场景开源实现”；把便携 bash（MSYS2 子集，大量路径访问）跑进 LPAC 是 v7 自己列为探针前提的事（`04` §5.2“便携 bash 与 Python 须通过 LPAC 兼容性探针”）。在探针通过前把 B 标为“同 A、全部模式”过于乐观。
- A′（MXC）：`调研-S2` §4.4、§5.3 说微软一手文档未查到、须逐机在 Win11 验证、显式选失败不回退、托管网络须放行主机回环（与 B3 相关）；`04` §5.2 也写“微软一手文档未查到，G1 探针确认后启用”。等级表却已给“同 A”。
- A（Codex `elevated` 参照）需一次管理员预配；`调研-S2` 与 `04` §5.2 均如此。`00` 决策 4 与 `05` §6.3 风险登记承认家庭版/杀软/LPAC 兼容性为“中”风险，但正文等级表未体现不确定性。

**为什么重要**。Windows 本机沙箱是 v7 全部放权的地基；等级表是律所策略“L3 事项要求最低等级”的依据，过度承诺会让合规基线落空。

**建议**。等级表的“允许”列在探针通过前标注“候选，待 G0/G1 探针”；B 明确“依赖便携运行时 LPAC 兼容性，未通过则降 C”；A′ 标“Win11 逐机验证、不回退”。补一条“若 A–B 均不可用的设备占比超过阈值时的产品决策”（例如强制 A 级预配或限制为手动模式）。`调研-S2` 的“未查到 MXC 一手文档/无 LPAC 通用 Shell 开源实现”直接写入风险登记。

### I2　化名双向替换的工程边界未写清

**问题**。`02` §8.6“推理”与 `04` §6 把“模型只看到化名、工具调用参数回流时还原为真名”作为关键机制，探针 6 测 Edit 匹配率 ≥ 99%。几处硬骨头未展开：
- **流式还原**：K3 以 SSE 流式返回，`old_string/new_string`、Bash 命令跨多个 chunk，闸门需缓冲到参数完整才能按映射表还原，和“边流边显示/边执行”存在张力；`04` 只说“响应流中还原”。
- **`reasoning_content` 原样回传**：`04` §3.2 自己指出 K3 要求原样回传思考内容、上下文压缩会改写历史（U6a）。思考内容里出现的化名若需参与后续推理，还原/再化名的一致性没有定义。
- **派生标识符**：真名在文中以简称、别称、“甲方/乙方”、带掩码的证件号、金额等变体出现，规则+词典+实体识别的召回不可能 100%；“还原失败转确认”只处理“模型改写了化名标记”，不处理“本应化名却漏标”。

**为什么重要**。这是 v7 新增的关键路径，直接影响“推理只收化名内容”的真实性与可用性；探针 6 若只测 Edit 匹配率会漏掉外泄面。

**建议**。`04` §6 补充：流式缓冲策略与对工具参数“先完整后执行”的约定；思考内容的化名一致性处理；探针 6 除匹配率外增加“漏化名率”（注入未入词典的新主体，测是否被实体识别拦截）与“误还原率”。明确漏化名时的失败模式（默认暂停而非放行）。

### I3　移动 App“WebView 页面从桌面 kap-server 取得”不自洽

**问题**。`04` §8 G1 称“WebView 的页面与脚本经端到端加密通道从本人电脑的 kap-server 取得，不由中软服务器下发——避开 v6 H5 方案脚本每次由中软下发的弱点”。问题：
- 这些页面原样来自 kap-server 的 web 资产（`routes/webAssets.ts`），即 Kimi Code 的 Web UI，并非为“化名/降权/收件区”定制；要实现 §8.7 的手机端降权视图需要另写前端，不是“取桌面页面”。
- “脚本来源可信”取决于桌面客户端完整性；而桌面客户端由中软签名下发，B5 已说明中软是能发布客户端的一方——把信任从“中软下发 H5”挪到“中软下发桌面端再转发”并未消除 E3 所指的根本点，只是换了位置，叙述上却当作已解决。
- 若按 B1 把遥控改为主进程网关，则页面也应由主进程网关提供而非 kap-server。

**为什么重要**。这是 v7 相对 v6 的卖点之一（移动 App 取代 IM 内 H5），论证不自洽会削弱拍板依据。

**建议**。改述为“移动端 UI 是发行版自带的前端资产，随 App 分发/或由桌面主进程网关按降权视图提供”，并如实说明“脚本可信度等同桌面客户端可信度，与 H5 相比优势在于不在每次会话从服务器拉脚本、且运行在本人设备密钥边界内”，不宣称消除了“发布方可信”这一前提。

### I4　加密存储只换一个服务，其他落盘面仍可能明文

**问题**。`02` §8.13、`04` §4.2/ZP-9 的加密落盘只注入 `IFileSystemStorageService`（`调研-S0` §8，覆盖 wire.jsonl/会话索引等 27 处）。但 kap-server 形态下还有多条独立落盘路径不经该服务：
- **文件历史/快照**走 `IBlobStore` + `IAtomicDocumentStore`（`features/fileHistory/fileHistoryService.ts:15,18`），不是 `IFileSystemStorageService`；回滚内容含客户材料。
- kap-server 服务令牌明文文件（B3；`services/auth/tokenStore.ts`）。
- 会话导出/ZIP（`app/sessionExport/*` 直连 `node:fs`）、插件存储（`app/plugin/store.ts`）、`guiStore`、workspace 别名等。
- 全仓 38 个文件直连 `node:fs`（排除 node-local/execEnv 后仍有大量），`PATCHES.md` 已记“少量路径直连 node:fs、须逐一核对”。

**为什么重要**。本机静态加密是“设备丢失/被盗”防线（§3.2）与律协“本地化保存”证据；只加密转录会给出“已加密”的错觉。

**建议**。把需加密的落盘面做成清单：至少 `IBlobStore`（文件历史/快照）、导出 ZIP、服务令牌、工作区别名一并经事项密钥加密或放入已加密的事项目录；ZP-9 扩为覆盖 `IBlobStore` 与 `IAtomicDocumentStore`。探针 17 增加“文件历史/快照与导出包以密文落盘”。

### I5　律所恢复码默认单张即全所钥匙；中软托管恢复的释放约束偏弱（v6 B1 残留）

**问题**。`02` §8.11、`04` §7：律所恢复密钥对“默认打印 1 张律所恢复码（保险柜）”，可恢复全部事项；伦理墙对持有人“是内控而非密码学”（§8.10）。这把 v6 被判阻断的“全权钥匙”换了形式保留：单张恢复码 = 全所解密权，放在保险柜，丢失即全所不可恢复（§8.11 末、`05` §6.3 风险）。中软托管恢复的释放仅凭“两名管理员各自设备请求 + 72 小时 + 通知”，而“管理员”身份由被托管方（控制面）判定——与 B5 同源。

**为什么重要**。恢复路径是端到端加密体系里权力最集中的一环，也是 v6 审阅的头号阻断；默认单张是单点既丢失风险又滥用风险。

**建议**。律所版默认 2-of-3 分片（§8.11 已有可选，改默认），团队版至少“恢复码 + 一名在线管理员确认”双因素；中软托管恢复的“管理员”须以律所侧管理员设备签名证明（非控制面断言），并对恢复动作做律所侧不可抵赖留痕。

### I6　检索的语义外泄面

**问题**。`02` §8.6 检索规则“剔除直接标识符 + 当事人词典 + 实体识别；未命中自动放行”。残余面：
- 保密要素未必是“当事人实体”：交易对价、特殊条款、未公开的并购标的、代号项目、行业+地域+金额的组合，足以反推当事人，却不命中词典/实体，于是自动放行到上游（`05` §1.2 ② 已承认“仍可能含案情要素”）。
- 检索查询由 Agent 起草（§11.3），提示注入可诱导 Agent 把材料内容编码进“检索式”自动外发（T4 默认自动，见 B4）。
- 去向卡只记“查询条数 + hash”（§8.6、`04` §3.3）；hash 对低熵查询可被字典还原，不能作为“不可见”的证据。

**为什么重要**。检索补位是 v7 相对 v6 的主要能力增量，也是新增的主要外泄面；闸门强制点③自承“隐写式外泄靠确认与审计”，而 T4 默认不确认。

**建议**。L2 及以上事项检索默认需确认或一键泛化（不只命中实体时）；检索式长度/熵阈值触发复核；去向卡保存查询原文于本机（已有）并对“自动放行”的查询也留原文以备审计；对“自动”模式的检索按律所策略默认改“泛化后放行”而非直接放行。

### I7　方法资产“正文不下发终端”在全工具形态下实际失效，风险仍标“中”（v6 I5 加重）

**问题**。`02` §8.9、`04` §3.2、`03` §1.2 延续 v6“方法正文不下发终端、由网关占位符组装”，并取消了 v6 的“思考内容密封”（`04` §3.2），风险维持“中”。但 v7 放开了 Read/Grep/Bash/子 Agent 与技能框架：技能（Skill）本身就是 `skillDirs` 下的文件，Agent 可用 Read/Grep 读到本机技能目录内容；网关占位符只对“随请求过境的方法正文”有意义，对“已经在本机技能/覆盖层文件里的方法资产”不构成保护。v6 审阅 I5 已指出占位符与 Kimi Code 上下文计数/压缩/Skill 读取不兼容，v7 放开工具后这一风险上升而非持平。

**为什么重要**。方法资产是商业壁垒（第 5 篇资产保护）；若本机就能被 Agent 读出，网关占位符的工程代价换不到对应保护。

**建议**。区分两类方法资产：纯服务端组装的（系统提示注入片段，不落本机）与必须在本机的（技能/覆盖层）。后者如实承认“对持有设备的本所成员不构成保密边界，仅靠合同与水印”，把风险等级与缓解在 `04` §3.2 写清；不要以“正文不下发终端”一句覆盖全部。

### I8　工作量漏项与“第 4 周中期评审”排期矛盾（v6 I16 回潮）

**问题**。W1–W20 合计 869（加总正确）。但按 B1–B4 的修复，以下工作量未计入或偏低：遥控改主进程网关（W16 中继仅 18、W1 遥控配对在内，网关降权是新增）、闸门补回落/代理兜底与 CSP/DOCX 外链剥离（W5/W9 未列）、加密落盘扩面到 BlobStore（W2）、审批统一到全工具（W5）。`04` §10.2 把“kap-server 嵌入、Windows 沙箱、检索对接”三项先行探针放在第 1–2 周，`00`/`05` §6.4 又要求“第 4 周中期评审先过探针 2/3/5（沙箱、注入红队前 100 例、检索）”——注入红队要在“放开工具 + 沙箱 + 闸门”全部就绪后才有意义，6 周的 G0 里第 4 周完成 100 例红队且前置探针全过，与 §10.2 的节奏（5–6 周才做注入红队）冲突（v6 I16 同类问题）。

**建议**。把 B1–B4 的修复列为 G0 显式工作包并计量；统一“中期评审”口径：要么红队前 100 例顺延至第 5–6 周，要么把沙箱与闸门探针提前到第 2–3 周完成。重新核对 W5（Kimi Code 嵌入）44 人周是否含遥控网关与审批统一。

### I9　“能力不少于 Kimi Work”与 `03` §1.5 自相矛盾

**问题**。`02` §12、`05` §4/§5.1/§5.5 反复用“具备 Kimi Work 的全部本地 Agent 能力”“本地 Agent 能力不少于/不打折”“任何一项能力弱于标准版差价就讲不通”，并以此支撑经济模型里“能力完整使席位 +10%/−15%”的敏感性。而 `03` §1.5 明列发行版**没有**：Kimi 在线 PPT/建站等专业 Skills、深度研究、Computer Use 桌面操控、WebBridge 借用本人 Chrome 登录态、图片/视频生成、Notion/飞书人机双写。其中深度研究、真实浏览器、PPT 技能、看板（`02` 能力 #31“看板与小组件”列为沿用，但 `03` 未展开实现）都是 Kimi Work 对律师可感知的能力。“全部本地 Agent 能力”因此不准确——准确的是“全部可本机原样运行、且适合律所的 Kimi Code 工具”。

**为什么重要**。这是对外口径与经济假设的共同支点；“全部/不少于”是绝对化表述，和 §12 自设的“禁用绝对化用语”相抵，销售易被客户用 §1.5 的清单当场反驳。

**建议**。统一改为“具备 Kimi Work 的本地 Agent 工具能力（文件/代码/子 Agent/目标/计划/技能/MCP/检索/定时），不含随 Kimi 会员云提供的闭源云技能（PPT/建站/深度研究/桌面操控等，见 `03` §1.5）”。经济敏感性标签“能力完整”改为“本地工具能力完整”，并在正文交叉引用 §1.5，避免矛盾。

### I10　经济模型几处假设需复核

**问题**（对照 v6 inputs 的 diff）：
- **用量上调正好抵消研发增量**：`05` §5.3 自述“+76 人周基本被更高 Agent 使用量带来的加量收入抵消”。而 Agent 开放任务月度次数 light/medium/heavy 由 v6 的 1/2/12 上调到 2/4/18（inputs `monthly_task_counts.open_task`），是收入侧的直接上调；把“放权带来更多使用”作为既定收入、把研发成本作为既定支出，二者对冲后得出“同席位几乎持平”，属于用乐观的需求假设平掉确定的成本增加，宜单列“用量不涨”的情形。
- **Agent 全工具任务 token 只 +20%**：open_task 的 `hit_k/output_k/write_5m_k` 从 400/30/80 升到 480/36/90（+20%），但该任务从 v6 的“十轮以内 WebAssembly Python”变成“全量工具 + 沙箱代码执行 + 子 Agent + 联网检索”，子 Agent 会显著放大 token（§8.8 默认并发 ≤ 8）。+20% 可能低估。
- **上行敏感性归因**：“Agent 开放任务用量再翻倍 → +889”被列为利好；用量翻倍同时抬高 token 成本，净利好依赖加量包定价覆盖成本，应说明。
- 缺“B1–B4 修复不被用量抵消”“沙箱使部分设备不可用导致可用席位缩水”两个下行情景；已有“能力弱于企业版 −15%”但无“Windows 沙箱覆盖不足导致交付受限”的情景。

**为什么重要**。经济结论（同席位谷底仅比 v6 深约 250 万、2030 +564）用于拍板；对冲式假设会让“几乎持平”显得比实际稳健。

**建议**。增加敏感性行：open_task 用量维持 v6 水平（1/2/12）；open_task token +50%；Windows 沙箱可用设备比例 85%/70% 对可计费席位的影响。`05` §5.3 解读里明确“持平”依赖用量上调假设。

## 三、一般

### G1　“四级/五级”说法不一
`00` 决策 4、§87、`02` §8.5 用 **A/A′/B/C/D 五级**；`04` §1、§5.2“Windows：四级实现”“四级实现各自的红队”、`01` 工程可行性表“四级降级”把 A′ 并入或漏算，说成“四级”。统一为“Windows 五档（A/A′/B/C/D），其中 D 为不可用降级档”，或明确“四级沙箱实现 + D 无沙箱”，并在各处一致。

### G2　“EDR 看得到其文件与网络行为”作为控制有误导
`02` §8.13 末行把“沙箱进程是带签名的普通进程，EDR 看得到”当作终端可见性保障。但 v7 自己要求沙箱进程无网络、经闸门出站，EDR 看到的网络行为仅是回环；且 EDR 可见性是律所自有能力、不是发行版提供的控制。建议改为“沙箱进程非虚拟机、不妨碍律所 EDR 监控，提供进程/域名/签名清单供加白”，不表述为一项安全控制。

### G3　“中软从不连入律所网络”触及禁用语且与遥控实质不符
`02` §6.1 图注“中软从不连入律所网络”。遥控是“律所侧出站注册、中软经中继把远端指令转发到本机 kap-server”，数据流向上确实是律所出站，但“从不连入”这类绝对化表述与 §12 禁用“从来没有/绝对”的纪律不一致，且下行指令在效果上由中软中继送达本机。建议改为“所有连接均由律所侧发起为出站 TLS；中软不主动建立到律所网络的入站连接”。

### G4　断云口径未完全衔接（v6 I3 残留）
`02` §3.4 N“离线 30 天许可”、§10“控制面停机 24 小时推理仍可用（网关离线验席位令牌）”、`04` §3.1 iam“席位令牌 JWT ≥ 72 小时”“org 许可离线 30 天”三个时效（24h / 72h / 30d）分别出现，未说明三者关系（令牌 72h 过期后、30 天许可内，推理是否仍可用）。建议在 §10 用一张小表统一“哪种凭据、多长、过期后什么降级”。

### G5　基线“不得自动放行”与 T4/T5“自动”字面冲突
`02` §8.2 中软基线写“内置工具 WebSearch/FetchURL 不得‘自动放行’出网”，而 §8.3“自动”档与 §8.4 T4“去标识通过自动”、T5“白名单域名自动”字面相反。实质可调和（基线禁止的是“不经闸门检查直接放行”，闸门检查通过后的自动是允许的），但字面矛盾。建议把基线那条改为“WebSearch/FetchURL 不得绕过出站闸门直接出网”。

### G6　收件区“问答与分类”早于归入事项，没有同意状态
`02` §8.7 收件区“文件只允许问答与分类，不跑开放 Agent”。但问答也要送模型（过境中软网关），而此时文件尚未归入事项、没有同意状态与密级判定。建议收件区的问答/分类限定为本机能力（本机解析、规则分类），送模型的问答须先归入事项并取得同意状态。

### G7　TC260 对照漏新指引且“正是…所指”无出处
`05` §2 把本地智能体“内置隔离”对照 TC260-PG-20266A《智能体部署使用安全指引》，并称“这正是该指引对本地智能体内置隔离的要求所指”。`调研-S3` §4.3 显示 09-18 新出《智能体系统开发安全指南（征求意见稿）》、09 月《人工智能应用安全指引》系列，且“该指引对‘内置隔离’的具体条款”本轮未逐条引。建议改为“对照 TC260 智能体相关指引（PG-20266A 及 2026-09 系列征求意见稿）的隔离与最小权限要求”，去掉“正是…所指”的断言或补条款出处。

### G8　补丁台账与实现细节不准
`04` §4.3 ZP-5/6 写“`extraSeeds` 透传（进程、文件系统）”“进程服务由拒绝式改为沙箱化”，但 `PATCHES.md` 里 ZP-5/6 是 node-sdk 的 `extraSeeds`；kap-server 用的是 `start.ts:120` 的 `seeds` 选项，二者不是同一入口，台账应写明 kap-server 路径（§8 已核 `seeds` 透传给 `bootstrap`）。另：`04` §5.1 说“文件工具 Read/Write/Edit/Glob/Grep 不进沙箱、由三区文件系统在应用层限定；Shell 与代码执行进沙箱”——但 Grep/Glob 上游经 `IHostProcessService` 起 ripgrep 子进程（`agent/tools/os/grep/grepTool.ts:303` `processService.spawn`），实为“进程”，会落入沙箱进程服务，需在 §5.1 澄清其归属。Tower（AgentSwarm 底层）受实验开关 `KIMI_CODE_EXPERIMENTAL_TOWER` 控制（`features/tower/flag.ts`），发行版若依赖集群需锁定该 flag 状态，台账未记。

### G9　事项目录密钥的轮换与持有人变更未设计（v6 I11 残留）
`02` §8.10/§8.11、`04` §7 新增“事项目录密钥（律所一把，授予主任/风控/利冲）”替代 v6 审计密钥与纪元，但未写：风控/利冲离职或角色变更时目录密钥如何轮换、历史加密的事项名称/摘要如何重新包裹、谁执行。v6 I11 指审计密钥生命周期未设计，此处同类。建议补目录密钥的轮换、成员增减时的重新包裹流程与执行方。

## 五、总体判断

v7 的方向（能力来源维度、沙箱放权取代删工具、远程渠道单独定权）是对 v5/v6 的实质改进，源码层面的可嵌入性判断（kap-server + DI 种子）基本准确。但本轮七条阻断集中在**同一个结构性后果**：把完整 kap-server 放到律师电脑并开放全部内置工具后，v7 据以“定边界”的三道机制——事项沙箱、出站闸门、审批/策略引擎——在当前设计里都**存在可绕过或无落点的缺口**（B2/B3/B4），遥控又把整台后端暴露给远端（B1）；与此同时为“简化 E3”取消律所侧信任锚，使密码学防线的承诺与威胁模型不一致（B5）；对外口径与图像外泄面回到了 v6 已判阻断的位置（B6/B7）。这些都应在 G0 的三项先行探针阶段作为“退出条件”解决，否则“沙箱定边界”这一 v7 的立论尚不成立。I 级问题多为“证据与正文口径、工程边界、经济假设”的收口。建议据此回填统计并在 `01-评审与裁决` 的裁决项中纳入 B1–B7。
