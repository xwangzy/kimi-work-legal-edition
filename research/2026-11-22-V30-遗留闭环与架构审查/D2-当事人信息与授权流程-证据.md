## 问题 B：客户授权逐案确认

### 7. 现行实现的完整事实

**数据模型（三层叠加）**

- `matters.consent_status`（0001_init.sql:52）取值 `agreed / pending / refused / not_required`，默认 `pending`。
- `matters.basis`（0013_v9_w1_approvals_qa_basis.sql:67，注释 :5-6）四项依据 JSON：`engagement / personal_info / sensitive / subprocessor`，每项 `confirmed / pending / not_applicable`（`packages/kernel/src/egress/gate-host.ts:48-55`）。consent_status 由四项派生（`api/index.ts:844-846`）。
- 第 48 批 D-202（0070_v22_ai_authorization.sql）：`matters.basis_source` + 表 `user_ai_authorization(engagement_terms)`——当时语义是“律师设置里声明一次，新建事项默认已授权”。
- 第 51 批 D-216（0072_v51_authorization_evidence.sql）：`basis_source` 扩为 `engagement_terms / separate_consent / confirmed(旧值兼容) / NULL`；新增 `basis_ref`（出处 ≤200 字）、`basis_notice_version`（告知时的次处理者清单版本）、`user_ai_authorization.default_ref`（常用出处，只用于预填）、表 `user_ai_notice`（律师本人看过“数据去向告知”的版本）。
- 常量：`AI_SUBPROCESSORS.version = "sp-2026-11"`（中软国际“云端转发，不保存内容”、月之暗面“Kimi 模型推理”），`AI_NOTICE_VERSION = "notice-2026-11"`（`packages/kernel/src/services/ai-authorization.ts:13-23`）。`basisNoticeStale`：版本非空且≠当前即须重新确认，空版本的旧事项不拦（:39-42）。
- 内核校验 `basisRecordFrom`（`api/index.ts:563-592`）：`engagement_terms` 无出处时若律师开了开关且有常用出处则自动用常用出处，否则拒收；`separate_consent` 必须有出处；`confirmed` 出处可空；只有 `engagement` 项为 confirmed 时才记来源，否则三列都记 NULL。

**授权依据可选项（现在只有两种 + 两个出口）**：`apps/desktop/src/lib/authorization.ts:46-50` `BASIS_KIND_LABELS` 只有“委托合同中的 AI 条款”“客户单独书面同意”两张卡；另有出口“先只用本机功能”“记为客户要求不上云”（`components/RunSheet.tsx:293-298`）；以及“改为逐项记录四项依据”（`components/Consent.tsx:123-125`，四项编辑器，可把某项标“不适用”）。**没有“口头同意+事后补”“不涉及客户信息”选项**（“不涉及”只能经逐项编辑把各项标 not_applicable 间接实现，但 subprocessor 在标准端点下不能不适用，`NewMatter.tsx:72-73`）。

**触发入口**

1. 新建事项：第 51 批起**不再记录授权**。`NewMatter.tsx:60-61` 一律写四项“待确认”；对话框只问“怎么处理”三选一（一般 / 敏感 / 客户要求不上云，`NewMatter.tsx:27-31,136-148`），一般项提示文字“第一次用 AI 时记录客户授权依据”。
2. 首次发起需要模型的任务：预估接口返回 `data_where.block_kind = "consent"`（内核 `modelBlockKind`，`api/index.ts:539-543`）→ 开始前确认卡 `RunSheet` 原地出现 `AuthorizationRecord`（`RunSheet.tsx:97,272-298`）。
3. 事项页头“记录授权 / 调整”按钮（`components/MatterHeader.tsx:64-67,114-122`）→ `pages/Matter.tsx:587-642` `BasisDialog`（同一个 `AuthorizationRecord` 组件，保存走 `patch`，:574）。
4. 法律问答（Chat）：**不触发授权**（见第 8 题）。
5. 每次发起 AI 前另有律师本人的“数据去向告知”`ensureAiNotice`（`RunSheet.tsx:51,160`；`lib/ai-notice.ts`），按版本看过一次即不再出现，读取失败不拦——它不是客户授权、也不是闸门（ai-notice.ts 注释 :2-4）。

**首次用 AI 时律师的操作步数（开始前确认卡）**

- 设置里开了“用常用条款一键预填”且存了出处：卡片已预选“委托合同中的 AI 条款”并预填出处（`RunSheet.tsx:124-135`，`authorization.ts:63-67 initialRecord`）→ 点“记录并开始”1 下（首次全局另有告知弹窗 1 下）。敏感事项须再勾“敏感个人信息已取得单独同意”（`Consent.tsx:112-120`，`recordReady` :70-73）。
- 未开预填：点选依据类型 1 下 → 手填出处（必填，合同编号+条款号 / 日期+方式）→ 点开始 1 下。
- 卡片文案：“这是本事项第一次用 AI。请记下客户授权的依据——它是你核实过的事实记录，不代替客户本人的授权”（`Consent.tsx:61-65`），只读三行“本案 / 授权要覆盖（含次处理者清单）/ 系统另外做到：发出前把姓名、证件号、电话等换成代号”（:95-111）。
- 记录后 `api.updateMatter({basis, basis_source, basis_ref})` → 重新预估 → 仍被拦则说明原因，否则直接发起（`RunSheet.tsx:154-174`）。

**设置 → 数据去向页的授权相关内容**（`apps/desktop/src/pages/Connections.tsx:503-580` `AuthorizationSettings`，位于页底、`no-print`）

- 标题“客户授权怎么记录”；正文说明每个事项第一次用 AI 时在开始前确认里记录（:549-551）。
- 唯一开关“用常用条款一键预填”`engagement_terms`（:555-558），**默认关**（`user_ai_authorization.engagement_terms DEFAULT 0`，0070；无行时 `aiAuthorizationOf` 返回 false，`api/index.ts:549-555`）。打开后出现“常用的条款出处”输入框（:560-570）。作用：只预填，“不会替任何事项自动记录”（:556）。但注意内核侧：开关开且有常用出处时，前端即使不传出处，内核也会自动套用常用出处（`api/index.ts:585-588`）。
- 显示次处理者清单与“清单有变化时，已记录的事项会在下次用 AI 前请你重新确认”（:571-575）；修改记审计 `ai_authorization.set`（`api/index.ts:3413-3429`）。
- 结论：所谓“逐案确认”开关现已不是“是否逐案确认”的开关——逐案记录是强制的，开关只控制预填。“关键操作藏在设置里”的说法对第 48 批成立，对第 51 批（当前代码）已不成立。

### 8. 强制点与绕过路径

**强制点（四处同一口径 `basisCompleteOf && !basisNoticeStale && endpoint≠none`）**

- 出站闸门授权回调：`packages/kernel/src/egress/gate-host.ts:153-159`（取事项行、算 basisComplete 下发闸门）。
- 闸门模型推理：`packages/egress-gate/src/server.ts:466` 拒绝 `basis_pending_no_egress`；网页抓取 :759；联网检索 `packages/egress-gate/src/search-guard.ts:56`。条件均带 `dataLevel !== "L0" && !== "L1"`，事项数据级别最低为 L2（`gate-host.ts:40-43`），所以事项内一律生效。
- kap-host 事项运行策略：`packages/kernel/src/index.ts:1308-1318`。
- 网关二次检查摘要：`packages/kernel/src/control-plane/governance.ts:1139-1150`。
- 内核前置：`modelBlockReason`（`api/index.ts:511-534`）用于估价（:1547）与 A1 开放任务发起时复核（:1811-1815）。s1.contract_review 发起时未见同样复核，但其模型调用仍经闸门被拦（未逐行跟踪 s1 执行路径，标“部分核实”）。

**没有授权时的行为**：任务只运行本机能力（模型、联网都不发生），估价返回 `start_blocked + block_kind=consent`，界面给记录卡；A1 发起直接 validation 拒绝。

**绕过 / 薄弱点**

1. **“逐项记录四项依据”绕过 D-216 留痕**：`RunSheet.tsx:157,161` 与 `Consent.tsx:123-125`——选逐项编辑时只提交 `basis`，不带 `basis_source/basis_ref`；内核 `basisRecordFrom` 收到 undefined 返回 null（`api/index.ts:578`），三列记 NULL。而 `basisCompleteOf`（`gate-host.ts:71-82`）只看四项是否都非 pending，`basisNoticeStale` 对空版本不拦（`ai-authorization.ts:39-42`）。结果：律师点“改为逐项记录”把四项全改“已确认”即可放行，**无出处、无次处理者版本、以后清单变更也不会要求重新确认**。这是 UI 上可见的正常路径，不是黑客路径。
2. **法律问答（Chat，不绑定事项）**：`gate-host.ts:194-212` `authorizeQa` 固定 `basisComplete: true`、L1；唯一保护是发送前的“本人可见事项当事人词典检查”，命中即拦截并引导到事项内（`packages/kernel/src/services/qa-chat.ts:376-397`），以及会话级令牌化（证件号、人名换会话代号，0013 注释 :4）。律师把案情原文贴进问答、而当事人名称未进任何事项词典（或写法未被识别）时，内容在**无授权记录**下发给模型。
3. 旧事项兼容：未记录四项 JSON 的旧事项按 `consent_status` 判定（`agreed/not_required` 即齐备，`gate-host.ts:81`）；`basis_notice_version` 为空的事项永不要求重新确认。
4. 全局搜索 `search.titles`（`api/index.ts:2741`）是本机标题检索，未见出站（未逐行核实）。OCR 走本机隔离进程（`api/index.ts:595-600 parseAny`），不出站。
5. 内核开关开 + 常用出处存在时，任一调用方传 `basis_source=engagement_terms` 不带出处即自动套用常用出处（`api/index.ts:585-588`）——即“一次声明代替逐案”的残留语义仍在内核层存在，只是界面要求律师在卡上看到并点击。

## 问题 A：事项级当事人信息

### 1. 事项数据模型现状

### 2. 令牌化：词典、识别范围、出站形态与还原

- 规则总述 `packages/tokenizer/src/index.ts:1-21`：“令牌只在两个地方还原——界面渲染层与可信文书引擎的导出；Agent、工作区、代码与模型上下文一律只见令牌。”

### 5. 三种方案的成本事实

**(i) 保留文字、存一次、各卡自动带入**
- 现有可借用存储：无现成“事项备注”列。`key_dates` 是 JSON 文本列（0001:48），语义是关键日期，塞进去属误用；`matter_parties.role` 是自由文本但每行是一个名称。

- 前端：`PARTY_INFO` 预填事项值（scenarios.ts / ScenarioStart.tsx），并把字段加到另外 7 张卡。
- 令牌化：仍走 goal → 闸门令牌化，与现状同（证件号/住址/电话/自然人名为代号，机构名原文）。明文存在本机事项库（库本身加密，未逐项核实）。

**(ii) 事项级当事人结构化表**
- 可在 `matter_parties` 上加列（住所、证件号、法定代表人、联系方式、诉讼地位），或新表。**需迁移**。

### 6. 交付环节：身份信息能否“只在本机合并、永不出站”

- docx-engine（`packages/docx-engine/src/`：compare/create/house-style/revise/…）**没有模板变量或合并域机制**（搜 placeholder/merge/MERGEFIELD/{{ 无命中；`house-style.ts:426-532` 的 template 指本所样式模板）。
- 但**代号还原本身就是本机合并**：文书在库里是代号形态，导出时 `restoreArtifactBytes` 换回真值（export-restore.ts:32-57）。所以只要律师填的证件号、住址、电话、自然人姓名在出站前被令牌化并登记进 `matter_tokens`，模型只见 `〔证件号·…〕`，交付的 docx 里就是真值——**真值本来就不出站**（机构名在一般事项除外，按设计原文发出）。
- 缺口：①现无“预先登记”入口——值只有在某次出站文本里出现时才被识别登记；②模式没识别出来的（如不规范地址、无门牌地址的部分写法）会原文出站；③模型若改写代号（拆开、加字）导出还原不了，系统会如实报 unresolved（export-restore.ts:53-55），但不会自动补。
- 另一可行路径（未实现）：模型只写【待填·原告住所】之类的命名占位，导出时由本机按事项当事人表替换——需要在 export-restore 或 docx-engine 加占位替换逻辑，属新功能。

- **B（授权）**：第 51 批起逐案确认已是强制流程——首次在事项里用 AI 时，“开始前确认”卡原地要求选依据类型并填出处；设置里那个开关只管预填，默认关。“授权藏在设置菜单里”是第 48 批的状态，现在已不存在。强制点有四处，口径一致（闸门模型/检索/抓取、kap-host、网关摘要、内核估价），事项内没有绕过。

- **A 方案成本**：(iii) 存成材料零迁移，同步、归档、令牌化自动覆盖；(i) 加一列要迁移 0073，同步自动带上，归档要手动加；(ii) 结构化表要迁移，matter_parties 目前不在同步段里，涉及 15 个以上测试文件。
