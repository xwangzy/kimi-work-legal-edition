## P0

### P0-1 平台停用可被团队管理员绕过：先“移出”再“启用”（A3 R2 / 契约 §3.4、§6.6 不成立）

- **问题**：`removeMember` 无条件把 `disabled_by` 改写成 `"team"`，覆盖了平台写下的 `"platform"`；随后团队侧 `enable` 只认 `disabled_by === "platform"` 才拒绝，于是放行。`disable` 分支有 `if (x.disabled_by !== "platform")` 保护，`remove` 分支没有。
- **证据**：
  - `platform/services/control-plane/src/server.ts:5660-5662`（`removeMember`：`x.status = "disabled"; x.disabled_by = "team";`）
  - `server.ts:5918-5923`（`act === "remove"`：只查“不是自己”“不是最后一名有效管理员”；平台停用的账号 `status !== "active"`，`lastAdmin` 恒为假，直接进 `removeMember`）
  - `server.ts:5942`（`disable` 有保护）、`server.ts:5951`（`enable` 只看 `disabled_by === "platform"`）
  - `server.ts:3294`（运营停用写 `disabled_by = "platform"`）
- **复现**（真实控制面）：
  1. 运营 `POST /v1/ops/accounts/<成员aid>/disable {reason:"风控"}` → 200；
  2. 团队管理员会话 `POST /v1/firm/members/<成员aid>/enable` → **403 platform_disabled**（符合预期）；
  3. 团队管理员会话 `POST /v1/firm/members/<成员aid>/remove` → 200，`disabled_by = "team"`；
  4. 团队管理员会话 `POST /v1/firm/members/<成员aid>/enable` → **200，status = active，disabled_by = null**。
  复现输出：`team enable (expect 403 platform_disabled) 403 platform_disabled` / `team remove 200 team` / `team enable after remove 200 active disabled_by= null`。
- **影响**：平台因欠费、风控、投诉停用的成员，团队管理员两步即可恢复登录与 AI 使用（有空席时 `enable` 还会自动补回席位，`server.ts:5953-5960`），平台停用形同虚设，并可能产生平台不认可的计费用量。
- **修复建议**：`removeMember` 改为 `if (x.disabled_by !== "platform") x.disabled_by = "team"`（与 `disable` 同口径）；`remove` 对已被平台停用的账号直接 403 `platform_disabled` 更干净；`teams/leave` 走同一函数一并受益。补用例：平台停用 → remove → enable 仍 403。另见 P2-1（存量平台停用账号没有 `disabled_by`）。

### P0-2 被移出 / 降级的管理员，其设备仍能做全部设备签名的团队管理动作（契约 §6.4“旧设备失效”不成立；新的 `remove` / `role` 语义未落到设备侧）

- **问题**：设备签名路由的授权只看**证书里的角色**与设备是否吊销：`requireAdmin` 看 `dev.cert.role === "admin"` 且签发者不是 `account_ca`，`requireRevoker` 看 `dev.cert.role ∈ {admin, partner}`；`authDevice` 不看账号状态，不看账号当前角色。本批新增的 `/v1/firm/members/:aid/remove`（移出）与 `/v1/firm/members/:aid/role`（改角色，含降级）只改账号记录、吊销会话、释放席位，**设备记录保留且不吊销、证书角色不变**，所以被移出或被降级的管理员仍持有一台“管理员设备”。
- **证据**：
  - `server.ts:1491-1499`（`requireRevoker` / `requireAdmin` 只看 `dev.cert.role` 与签发者）
  - `server.ts:1445` 起（`authDevice` 不查账号 `status` / `role`）
  - `server.ts:5660-5669`（`removeMember` 不吊销设备，注释“设备记录保留”）
  - `server.ts:5925-5932`（`role`：只改 `x.role`，`feedVersion += 1`，不吊销、不重签设备）
  - 受影响的设备签名管理路由（节选）：`/v1/invitations`（`server.ts:5406`，requireAdmin）、`GET /v1/join-requests`（`:5443`）、草稿签名 / 发布、`/v1/quota/cap`、`/v1/devices/:id/revoke`（`:5498`）、`/v1/seats/:uid/revoke`（`:5509`）、`GET /v1/audit`（`:5288`，requireRevoker）
- **复现**（真实控制面）：甲（创始管理员，律所根签发设备）升级团队；乙以合伙人身份加入；甲把乙升为管理员；乙把甲降为 lawyer，再把甲移出：
  - 降级后甲的设备 `POST /v1/invitations {role:"admin"}` → **200**；
  - 移出后（账号 disabled、会话已吊销）甲的设备**不带会话**再调 `POST /v1/invitations` → **200**；`GET /v1/join-requests` → **200**。
  复现输出：`demoted A device -> /v1/invitations (requireAdmin) 200 ok` / `B removes A 200 disabled` / `removed A device (no session) -> /v1/invitations 200 ok` / `removed A device -> GET /v1/join-requests 200 ok`。
- **影响**：离所 / 被降级的管理员继续以本所名义发成员邀请、读取待批准的新电脑（含成员编号与设备公钥）、读本所审计流水、吊销其他成员的电脑与席位（对全所拒绝服务）、设律所额度上限。设备目录里该设备仍为有效，其他成员内核也仍把它当本所有效设备（团队共享事项密钥继续包给它；中继令牌因席位已释放而拿不到，这一层挡住了密文同步，但不是有意设计的防线）。该缺口在“停用”上早已存在，本批新增的“移出”“降级”把它变成了正式流程里的常见路径。
- **修复建议**（任选其一，建议 1+2）：
  1. 设备签名的管理路由统一加“账号闸”：按 `dev.cert.memberId` 找到账号，要求 `status === "active"` 且**账号当前角色**满足要求（`requireAdmin` 看 `account.role === "admin"`，`requireRevoker` 看 `admin|partner`），不只看证书；
  2. `remove` 与“降级管理员 / 合伙人”时，吊销该成员的设备或至少把它们放进目录的暂停名单（与网关暂停名单同源），并在应答里如实说明；
  3. 补契约 §6.4 用例：移出 / 降级后，旧设备调 `/v1/invitations`、`/v1/devices/:id/revoke`、`/v1/audit` 一律 403。
  注意：创始电脑持有律所根私钥，本机签证书的能力云端收不回——离所的若是创始管理员，需在文档里写明要走“轮换律所根”流程。

## P1

### P1-1 D-304 后，账号签发钥（account_ca）签的团队合伙人 / 管理员电脑不经任何批准即获得“吊销类”与“读审计”权限；存量团队升级后被静默切到 auto

- **问题**：
  1. `requireRevoker` 不看签发者（对照 `requireAdmin` 有 `account_ca` 检查）。第 66 批时 account_ca 证书只出现在单人个人空间，问题不显；本批把 auto 登记扩到团队后，团队里角色为 partner / admin 的成员只凭账号凭证在新电脑登录、自动登记（证书 `role: a.role`），即可吊销其他成员的电脑与席位、取本所审计流水。契约 §3.5 写的是“账号签发钥签的电脑不能做律所根动作”，吊销与读审计此前只给律所根签发（经管理员核对码批准）的电脑。
  2. `policyOf(t)` 对缺字段的团队返回 `"auto"`，启动迁移不写 `member_device_policy`；存量团队（第 72 批前一律“新电脑要管理员批准”）在下一次任一设备 `/v1/devices/register` 或 `/v1/enroll` 时自动登记 `account_device_ca`，之后成员新电脑直接登记——没有任何管理员同意，也没有通知。
- **证据**：
  - `server.ts:1491-1493`（`requireRevoker` 无签发者检查）；`server.ts:4699`（account_ca 证书 `role: a.role`）
  - `server.ts:710-712`（`policyOf` 缺省 `"auto"`）、`server.ts:1778`（`autoEnrollReady` 扩到团队）
  - `server.ts:4824`（`/v1/enroll`）与 `server.ts:4846`（`/v1/devices/register`）：`if (… autoPolicyOf(t)) t.account_device_ca = …`
  - `server.ts:696-700`（启动迁移只定型 `kind`，不定型 `member_device_policy`）
- **复现**（真实控制面）：甲团队（auto）发合伙人邀请 → 乙接受 → 乙的新电脑走 `/v1/auth/devices/enroll` 拿到 `issuer: account_ca, role: partner` 证书；乙用这台电脑：`GET /v1/audit?after=0&limit=10` → **200**；`POST /v1/devices/<律师丁的设备>/revoke` → **200**（丁的设备 `revoked_at` 已写）。对管理员的设备 / 席位，合伙人检查生效（403 `partner_cannot_revoke_admin`）；角色为 admin 的 account_ca 电脑则可吊销包括创始电脑在内的任何设备（代码推理，同一函数）。
  复现输出：`partner account_ca GET /v1/audit 200 ok` / `partner account_ca revoke lawyer device 200 ok revoked_at= …`。
- **影响**：凭据被盗（或共享电脑上记住密码）的合伙人 / 管理员账号，攻击者无需管理员核对码，即可永久吊销同事电脑（吊销编号不复用）、收回席位、读审计；存量团队客户的安全基线在无告知的情况下降级。
- **修复建议**：`requireRevoker` 同 `requireAdmin` 一样拒 `account_ca`（或至少拒 `account_ca` 吊销他人设备与席位，只许吊销本人设备）；`GET /v1/audit` 同理。迁移时对“已存在的团队”写定 `member_device_policy: "approve"`，只对新开通 / 就地升级的团队缺省 auto，并在团队控制台给出一次性提示。

## P2

### P2-1 存量“平台停用”的账号没有 `disabled_by`，团队管理员照样能启用（R2 修复不覆盖 1.7.0 之前的数据）

- **证据**：`disabled_by` 只在 `server.ts:3294`（运营停用）写 `"platform"`；启动迁移（`server.ts:693-705`）不回填；`enable` 只认 `disabled_by === "platform"`（`server.ts:5951`）。
- **推理**：1.7.0 之前被运营停用的账号 `disabled_by` 为空 → 团队 `POST /v1/firm/members/:aid/enable` 直接 200。
- **修复建议**：迁移时对 `status === "disabled"` 且审计链里最后一次停用由 `ops` 发起（或 `disabled_reason` 非空且非团队写入）的账号回填 `"platform"`；拿不准的按 `"platform"` 处理，宁严勿宽。

### P2-2 平台停用“主账号”拦不住这个人：凭证仍能登录他的其他工作空间、收登录码、找回密码、再加入新团队（需拍板口径）

- **证据**：`pickWorkspace` 只过滤“可用的工作空间”（`server.ts:2098-2108`）；发登录码 / 找回密码按 `personActive`（`server.ts:1730`，有任一可用工作空间即放行）；`/v1/teams/join` 只要当前会话有效（`server.ts:5768`）。运营侧只有逐个账号停用，没有“停用此人”。
- **复现**：运营 `POST /v1/ops/accounts/<乙主账号>/disable` → 200；乙用邮箱 + 密码登录 → **200，进入乙在甲团队的关联账号**；`POST /v1/auth/password-reset/request` → 202。复现输出：`B login after primary disabled 200 team aid= linked(team)`。
- **影响**：风控 / 欠费 / 投诉场景下平台要封的是人，现实现只封了一个工作空间；被封者可继续在团队里用 AI，还能凭新邀请码挂新的关联账号。
- **修复建议**：拍板二选一：(a) 主账号停用 = 停用这个人（登录、发码、找回、加入一律 403，切换列表全灰）；(b) 保持按工作空间停用，但人员页另给“停用此人”（对 `workspacesOf` 全部置 `platform` 停用并吊销会话）。

### P2-3 管理员被移出 / 降级后，他发出的未接受团队邀请（含 admin 角色）继续有效，可用新身份重回团队

- **证据**：`removeMember`（`server.ts:5660-5669`）与 `role`（`server.ts:5925-5932`）都不处理 `t.team_invites`；邀请是持码即用（`findTeamInvite`，`server.ts:5556-5581`），`phone_hint` 只是展示，不在接受时核对。
- **复现**：已是管理员的乙 `POST /v1/team/invites {role:"admin"}` → 200，团队里留下一张 open 的 admin 邀请（复现输出：`open invites ["admin"]`）；按代码，乙被移出后该码仍可被任何新手机号注册（`/v1/auth/register` 带 `team_invite_code`）直接成为团队管理员（`already_member` 只挡同一个人）。
- **修复建议**：移出或把管理员降级时，撤销 `created_by === "account:<他的aid>"` 的 open 邀请并在应答里列出；admin 角色的邀请接受时要求手机号与 `phone_hint` 打码一致，或改为接受后待现任管理员确认。

### P2-4 团队管理员与合伙人能看到成员“这个人”的主账号邮箱，成员编号也由主账号邮箱派生（契约 §3.4 只写了打码手机号）

- **证据**：`/v1/firm/members` 行 `email: emailOf(x)`（`server.ts:5830`）、`/v1/firm/usage` 按成员行同样 `emailOf`；`/v1/teams/join` 建关联账号时 `member_slug: newMemberSlug(tt, person.email)`（`server.ts:5776`），而成员编号进设备证书与全所设备目录。
- **影响**：律师用私人邮箱注册个人工作室，再加入一家团队，团队全体管理员 / 合伙人（及全所设备目录）即可看到该邮箱或其本地部分。不是事项数据，但属于个人空间的身份信息越界。
- **修复建议**：团队视图只给打码邮箱（复用 `maskEmail`）或不给；关联账号的 `member_slug` 用随机串，不从邮箱派生；在加入团队的确认页写明团队能看到什么。

### P2-5 运营给关联账号发重置码，实际重置的是这个人的全局凭证，但审计只记在团队租户、不记在主账号所在租户

- **证据**：`server.ts:3312-3318`：`const a = primaryOf(a0)` 生成主账号的重置 / 设置码，`accountAudit(a0, …)`；`accountAudit` 按 `a.tid` 写（`server.ts:2640`）。
- **影响**：凭证变更（可接管这个人的个人空间与全部团队）在他个人空间的审计链里没有记录；反而团队审计（团队管理员 / 合伙人设备可经 `/v1/audit` 读）看到“平台给该成员发了重置码”。
- **修复建议**：审计主条目记在主账号（`tid = a.tid, target = a.aid`），团队租户只记一条不含凭证细节的附带条目；或干脆要求运营对主账号操作。

### P2-6 “闸门 Node 每次启动只算一次哈希”的安全前提在 Windows 不成立：安装目录对本人可写，元数据可伪造，窗口从“每次拉起”扩到“整个应用会话”

- **证据**：`platform/packages/kernel/src/egress/runtime-stamp.ts:11-14`（注释前提“安装目录对普通用户只读”）；`platform/apps/desktop/electron-builder.yml:70-71`（`oneClick: false`、`perMachine: false`，即装在本人的 `%LOCALAPPDATA%\Programs`，本人可写）；`platform/apps/desktop/electron/main.cjs:224-240`（启动时记元数据）、`platform/packages/kernel/src/egress/kernel-gate.ts` `startInner`（元数据一致即跳过重算）。Windows 上 `mtime` 与 `ChangeTime`（Node 的 `ctimeNs`）都可经 `SetFileInformationByHandle(FileBasicInfo)` 由对文件有写权限的进程改回，就地覆盖不变 `ino`（文件编号）与 `dev`。
- **推理**：原来启动后替换 `node.exe` 会在下一次拉起闸门时因摘要不符被拒；现在本人权限的恶意程序在启动核对之后替换并改回元数据，下一次内核重启 / 闸门崩溃重拉即运行被篡改的“唯一出口”。前提是本机已有本人权限的恶意代码（同一攻击者也可能改别的随包文件），所以不升 P1，但注释里的安全论证需要更正。
- **修复建议**：Windows 上保留跳过重算的条件改为“拉起闸门的那个文件句柄在核对后一直以拒绝写共享方式打开”（核对与执行之间不可写），或仅在 `perMachine` 安装 / macOS 已签名应用包内启用跳过；至少在 `kwl:restart-kernel` 与闸门崩溃重拉时强制整份重算一次（这两处不在启动关键路径上）。

### P2-7 团队管理员“启用”一个本就有效的成员即可清零其登录失败计数；成员主账号在团队里时，这个计数保护的是这个人的全部工作空间

- **证据**：`enable` 分支不要求原状态为停用，无条件 `x.failed = { count: 0, … }`（`server.ts:5950-5960`）；密码失败计数与锁定记在主账号（登录路径 `locked(ea)`、`noteFailure(ea)`），凭团队邀请码注册的人，主账号就建在团队里。
- **影响**：团队管理员可反复清零某成员的锁定以继续猜他的密码（来源限流 20 次 / 分钟仍在），猜中即拿到这个人的个人空间与其他团队。
- **修复建议**：`enable` 只对 `status === "disabled"` 生效；团队侧不清零主账号的 `failed`（锁定解除交给“忘记密码”或平台客服）。

## 观察项（已核实成立的性质，或低风险提示）

- **O-1 跨租户 / 跨工作空间越权（重点 1）成立隔离**：`/v1/auth/workspaces/switch` 要求 `samePerson` 且目标有效，否则统一 404（`server.ts:4556-4568`）；`/v1/firm/*` 与 `/v1/team/*` 的租户只取自会话账号（`server.ts:5725` 起），成员 / 设备一律经 `requireMemberOf` / `requireDeviceOf`（`server.ts:5524-5533`）；邀请撤销只在本租户 `t.team_invites` 里找；`/v1/me/onboarding` 只写自己主账号的两个时间戳；运营 `/v1/ops/people*` 按 `account.read`，平台角色无租户范围，口径与现有账号页一致。团队管理员对成员个人空间的 aid 一律 404。合伙人对 `/v1/firm/*` 与 `/v1/team/invites` 的写均 403（`server.ts:5820-5822`、`:5750`）。
- **O-2 登录主路径（重点 2）成立**：凭证只能找到主账号（邮箱 / 手机号索引只收主账号，`server.ts:539-545`）；`pickWorkspace` 只在这个人自己的工作空间里挑，设备命中要求 `devices.get(id) === dev && memberId` 相符，签别人电脑的签名不会把会话绑到别人账号（`enterWorkspace` 与登录的 `own` 判定同口径）；找回密码、验证码重新登录（`phoneOfDevice` → `primaryOf`）、改绑手机、重新验证密码、登记风控短信都走主账号，关联账号没有可被定位的凭证。残留：第 56 批的“改绑”分支现在作用于 `pickWorkspace` 的结果，只对不带 `account_switch` 的旧客户端生效（`server.ts:4392-4403`），属原有行为。主账号停用的口径见 P2-2。
- **O-3 团队邀请码（重点 3）成立**：16 位、31 字符表（约 79 位熵；`randomBytes % 31` 有轻微取模偏差，不影响结论）；只存 `HMAC-SHA256(pepper)`，pepper 由信封私钥 HKDF 派生（`server.ts:943-946`）；比较用 `timingSafeEqual`（`accounts.ts:227-231`）；7 天过期、一次性、可撤销、租户须为团队且许可有效；同一来源 10 分钟 10 次失败即 429、成功不计（`server.ts:5552-5581`，内存计数、单进程，重启清零）；同一人同一团队第二个身份 409 `already_member`（含已停用的身份，因此被移出的人不能凭新邀请重回，是功能取舍）。注册路径在核验短信验证码之前先核邀请码，形成“码对不对”的判别，但受同一失败限流约束，可忽略。邀请码是持码即用，`phone_hint` 不核对（见 P2-3）。
- **O-4 账号签发电脑不进团队共享（重点 4 后半）成立**：内核目录同步跳过 `issuer === "account_ca"` 的证书（`platform/packages/kernel/src/control-plane/governance.ts:723-725`），成员日志作者证书只认律所根签名（`platform/packages/kernel/src/member-log.ts:233`），事项密钥只包给 `devices` 表里的有效设备（`member-log.ts:862`）。云端 `requireAdmin` 拒 `account_ca`（`server.ts:1495-1499`），`member_device_policy` 只有团队管理员会话可改（`PUT` 属写，合伙人 403、个人空间 403 `team_only`）。缺口在 `requireRevoker`（P1-1）与存量团队缺省（P1-1）；另外改策略不要求重新验证密码，属可接受的取舍。被移出成员的中继访问由席位收回 + 中继按订阅核 `revokedSeat` 截断（`platform/services/relay-api/src/index.ts:434`）。
- **O-5 出站闸门白名单（重点 5）成立**：新增 10 条全部 `^…$` 锚定，编号限 `acc_` / `tiv_` + 16 位 `[A-Za-z0-9_-]`，不含查询串，另有全局 `..` 拒绝与 300 字符上限（`platform/packages/egress-gate/src/cp-relay.ts:72-81`、`:93`）；只有内核持有 IPC。白名单比云端窄（未放行 `reset-code`、`sessions/revoke`、`devices/:id/signout`），与内核实际调用一致。请求体含被邀请人姓名与打码手机号、团队名称，属账号元数据，已登记在 `docs/privacy/egress-paths.json`。
- **O-6 审计（重点 6）**：新动作均进审计（`workspace.upgrade_team`、`team.invite_create/revoke/accept`、`team.leave`、`team.member_remove`、`account.role`、`seat.assign/revoke`、`team.member_device_policy`、`account.reset_sms`、`account.workspace_switch`），`detail` 只有数字；新增日志事件字段只有毫秒、布尔与枚举（`platform/packages/safe-log/src/events.ts`）。小缺口：`teams/leave` 切到下一个工作空间时没有 `account.workspace_switch` 条目；切换 / 加入的 actor 是主账号 aid，团队审计因而能看到“这个成员对应哪个人”的编号（低）。`disabled_by` 可被团队侧绕过见 P0-1、P2-1。
- **O-7 `kwl:restart-kernel`（重点 7）成立**：只认应用主窗口主框架且 URL 在允许列表（`platform/apps/desktop/electron/main.cjs:795-799`），两次至少隔 15 秒；不带换账号交接，排队补跑也拿不到交接（交接在首次 `startKernel` 读取即清空，发起方 `.finally` 再清一次），渲染进程不能借它切换身份。残留：被攻破的渲染进程可每 15 秒重拉一次内核（拒绝服务，低）。运行时哈希的 TOCTOU 见 P2-6。
- **O-8 模型目录纪元**：纪元不同只在 `issued_at` 更晚时接受（`platform/packages/kernel/src/services/model-catalog.ts` `catalogNewer`），重放旧信封不能回滚；签名照验。
- **O-9 运营新接口**：`/v1/ops/tenants/:tid/invites`（`account.manage`）可给任一客户团队代发 admin 角色邀请且不要求复核（`server.ts:3745`），`seats/:aid/assign` 复用 `device.revoke` 权限（`server.ts:3717`）；现有角色表里两项权限只同时给“运营专员”（`rbac.ts`），实际无越权，建议代发 admin 邀请标 `danger`、席位分配改用专门权限名。
- **O-10 就地升级**：不可逆、只要当前会话（不要求重新验证密码）；试用期席位提到 3，额度若按席位计会随之放大（设计口径，留意试用滥用）。个人套餐在升级后不做 `audience` 校验（只有改套餐时才校验），付费个人套餐席位不变，暂无计费错误。
