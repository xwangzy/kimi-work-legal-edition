# A3 个人 / 团队体系与控制台审计（只读，2026-11-27）

> 范围：`platform/` 下控制面、内核、桌面端、控制台源码，分支 `claude/kimi-legal-b72-unify-teams`（头 55d75f32）。只读，没有改源码。
> 行号均相对 `platform/`。下文“控制面”指 `services/control-plane/src/server.ts`（5,616 行），简写 `server.ts`。

## 结论先行

1. **账号 = 某一家律所里的一名成员**（`accounts.ts:4`、`28-30`）；邮箱、手机号全局唯一。所以一个人不能同时属于两个组织，个人律师加入律所只能换号另注册。
2. **个人律师 = 自助注册开出的单人租户（角色 admin）**；“个人”靠形状推断，发出第一张成员邀请就会永久、悄悄地变成团队（`server.ts:664-676`）。套餐、席位、订阅都不分个人和团队。
3. 成员接口与设备接口都从会话或签名里取 tid，**没有发现凭网址里的 tid 越租户**；但隔离全靠代码里的 `x.tid === t.tid`，状态是一整份 JSON（`pg-state-store.ts:12-13`）。
4. 发现 5 处同租户内的越权或绕过（R1～R5）。最实的一处：个人用户可以通过 `/v1/firm/members/<自己>/limits` 把试用套餐的 1 台电脑自改为 9 台；此外，律所管理员能重新启用平台停用的账号。
5. 内核侧，**每个账号档案的目录、账本密钥、内核进程都已分开**，切换账号串数据的风险低；而档案本来就是按“工作空间 + 成员”分的，可以直接当工作空间用。
6. 云端确实没有案卷明文，也没有密钥。不过有三处例外要如实写：团队事项开启共享后，密文会到共享文件夹或中继；恢复托管凑齐 3/5 份额就能解；所内节点能读被授权的事项。个人事项永不外发。
7. 个人用户的客户端里混进了“管理”和“团队与离所”（`Connections.tsx:82`、`705`）；控制台里，同一个人在“客户”和“账号”两处各有一个落点。
8. 建议只加一个“人”实体（外加 `kind`、`audience`、`pid`、`disabled_by` 四个字段），其余全部复用；控制台拆成“个人用户 / 组织客户 / 人员 / 电脑”。约 33～35 人日。

### 1.2 个人律师账号在数据上是什么

- **就是单人租户**：自助注册不带码时，`ops.createTenant({ edition: "team", seats: trial_seats(=1), plan: trial_plan, createdVia: "self", accountsRequired: true })`，账号 `role = "admin"`（`server.ts:4011-4026`），机构名缺省“`<姓名>的工作室`”（`server.ts:4011`）。
- 标记：`TenantRecord.personal`，建租户时 `personal: createdVia === "self"`（`server.ts:1064-1065`）。但这个标记是**“形状推断 + 单向降级”**：`personalShape()`＝只有 1 个账号且是 admin、没有别的成员设备、没有未撤成员邀请（`server.ts:664-670`）；`personalOf()` 发现形状不成立就**永久**把 `personal` 写成 false 并推进 feed 版本（`server.ts:1670-1676`）。存量迁移也按形状判一次（`server.ts:655-660`）。即：**“个人”不是一种账号类型，而是“自助注册的单人租户在没长大之前”的状态**。
- 个人与律所的差异点分散在：
  - 新电脑免批准（控制面用账号设备签发钥直接签证书）：`autoEnrollReady`（`server.ts:1678`），onboarding 状态 `needs_device_auto`（`server.ts:1953`）；团队功能只认律所根签发的电脑（`requireAdmin`，`server.ts:1432-1436`）。
  - 电脑数上限封顶：个人 20、团队 9（`deviceLimitOf`，`server.ts:1658-1662`；常量 `accounts.ts:132-139`）。实际上限 = `account.device_limit ?? plan.device_limit`，试用套餐 1 台（`billing.ts:116`）。
  - 额度分母：单席位取全所总额度（`server.ts:1651-1654`）。
  - 席位：个人租户不显示席位占用（`seat_used: null`，`server.ts:2343`）；运营“客户”行的 `personal` 只读判断（`server.ts:2225-2226`）。
  - **套餐、席位数、订阅本身没有个人/团队之分**：两者用同一套 `plan` / `seats` / `subscription_until`。

### 1.4 一个手机号 / 账号能否属于多个组织

**不能。** 证据链：
1. 账号只有一个 `tid`（`accounts.ts:28`），成员标识、设备编号、证书 `memberId` 都由 tid 拼出（`accounts.ts:268-270`、`server.ts:1647`）。
2. 邮箱全局唯一（`emailTaken`，`server.ts:495`、注册 `server.ts:3942`），手机号全局唯一（`accountByPhone`，`server.ts:3992`）。
3. 凭成员邀请码注册要求**新建**账号（新邮箱 + 新手机号）；已登录账号没有“加入另一家”的接口（`/v1/auth/onboarding` 只处理本账号本租户的电脑，`server.ts:4334-4348`）。

推论：**个人律师想加入律所，只能换一个邮箱/手机号另注册一个成员账号**，个人工作室里的用量、套餐、电脑编号都不能带走；**个人升级为团队**目前只有“在个人租户里发成员邀请”这一条路，且一旦发出邀请即永久失去“个人”待遇（新电脑要另一台电脑批准、团队动作要在创始电脑上做）。

### 1.5 RBAC 与鉴权分层

三层身份、三套鉴权入口（`server.ts:4479-4494` 分流）：

| 调用方 | 路由前缀 | 鉴权 | tenant 怎么确定 |
|---|---|---|---|
| 平台人员（运营方） | `/v1/ops/*` | 人员会话 + `ROLE_TABLE` 权限（`rbac.ts:27-38`），危险权限要 10 分钟内复核（`rbac.ts:44`、`staff.ts:30`） | URL `/v1/ops/tenants/:tid`（`server.ts:3385`）——**平台人员本就是跨租户的**，`tid` 只用于审计与目标定位，按设计不做归属校验 |
| 成员网页 / 客户端会话 | `/v1/me/*`、`/v1/firm/*`、`/v1/auth/*` | 会话 → 账号 → **从账号取 tid**（`server.ts:5224-5232`）；`/v1/firm/*` 要 admin（写）或 partner（只读）（`server.ts:5256-5257`）；对他人账号逐一校验 `x.tid !== t.tid → 404`（`server.ts:5310-5314`、`5323-5326`） | 不读 URL 里的 tid，**没有发现可凭 URL 越租户的接口** |

平台角色：sysadmin / operator / issuer / finance / support / viewer（`rbac.ts:24-38`），operator ⟂ issuer 互斥（`rbac.ts:41`）。律所侧角色只有账号上的 `role` 一个字段，四值，`/v1/firm/*` 只区分 admin / partner / 其余（`server.ts:5257`）。

| # | 问题 | 位置 | 影响 | 建议 |

## 题 2：客户端里的个人 / 团队差异与本地数据隔离

### 2.1 内核怎么区分个人与律所成员

- **内核不区分。** 内核的身份只有“租户（律所工作区）+ 成员（设备）”（`packages/kernel/src/identity.ts` 头注），`member_role` 来自设备证书。所谓“个人”只体现在：①控制面 onboarding 状态 `needs_device_auto`（新电脑直接签发）；②额度视图 `ratio_basis: "personal"`（`packages/kernel/src/control-plane/client.ts:136-148`）。个人律师在内核里就是“一个只有自己、角色为 admin 的律所”。
- 律所根与恢复托管：每个工作区首跑生成律所根与**恢复托管私钥的 Shamir 3-of-5 份额**，开发形态份额以 0600 文件落在 `<workspace>/keys/recovery-shares/`（`packages/kernel/src/devices.ts:7`、`150-200`；注释自承“生产由合伙人各自离线保管，不应同机落盘”）。

### 2.2 同一台电脑多账号档案（第 68 批 D-294）

| 层 | 是否隔离 | 证据 |
|---|---|---|
| 工作区目录 | 是。一个账号一个目录：第一个沿用 `<律所标识>`，同所另一成员 `<律所标识>.<成员标识>`；`profile.json` 校验目录名与记录一致，挪过/拷贝过不认 | `packages/kernel/src/profiles.ts:1-55` |
| 账本数据库密钥 | 是。每档案一把：`ledger-key`（第一个）/`ledger-key.pending`/`ledger-key.p.<目录名>`；内核每次只拿当前档案那一把 | `apps/desktop/electron/key-slots.cjs:1-40`；`main.cjs:580` |
| 内核进程 | 是。换账号 = 内核写指针 → 主进程清文件句柄 → 换密钥重启内核；交接只在内存、只给这一次重启 | `apps/desktop/electron/main.cjs:617-630`；`packages/kernel/src/index.ts:472-482` |
| 中继收发目录 | 是。`<workspace>/relay` | `packages/kernel/src/index.ts:896` |
| 界面本机偏好 | 基本是。事项、模型、额度提示等按 `profileScopeId`（tid+成员的摘要）分键 | `apps/desktop/src/lib/profile-scope.ts`；`pages/Home.tsx:44-508`、`pages/Chat.tsx:54-111` |
| 未分键的界面偏好 | 侧栏折叠、缩放、主题（无身份信息，可接受） | `components/Sidebar.tsx:42-95`、`lib/ui-prefs.ts` |
| 数据根级共享文件 | `cloud-endpoints.json`（端点，非身份数据） | `main.cjs:338` |

结论：**档案级隔离（目录、密钥、进程）已经成立，切换账号的串数据风险低**。残余：①渲染进程同一 origin，任何新加的 `localStorage` 键若忘了 `scopedKey` 就会跨档案（建议加 lint/测试）；②恢复托管份额开发形态与创始档案同机。

### 2.5 个人用户界面里混入的组织管理

## 题 4：建议的目标架构（最简、可靠、可扩展）

### 4.0 一句话

**把“人”从“成员”里拆出来，其余全部复用。** 现在的 `AccountRecord` 本质是“某工作空间里的成员身份”（tid + member_slug + role），`TenantRecord` 本质就是“工作空间”；缺的只是一个“人”（登录身份：手机号、邮箱、密码、登录记录）把多个成员身份串起来。客户端的“账号档案”本来就按 (tid, member_slug) 分目录、分密钥、分进程（`profiles.ts:27-30`），**正好就是“工作空间”**，不需要改内核的数据模型。

### 4.1 数据模型

```
人 PersonRecord（新增）            pid、手机号（HMAC/打码/密文，唯一）、邮箱（唯一）、密码、失败计数、登录记录、状态
 └─ 成员身份 AccountRecord（复用）   aid、pid（新增）、tid、member_slug、role、status、disabled_by（新增）、device_limit、quota_limit
     └─ 设备 / 席位 / 会话（复用）   证书仍由该工作空间的律所根或账号签发钥签；uid = usr_<律所>_<成员> 不变；会话仍绑 aid
工作空间 TenantRecord（复用）       kind: "personal" | "team"（新增，显式；替代推断出来的 personal）
套餐 PlanSpec（复用）               audience: "personal" | "team" | "any"（新增，只用于筛选与校验）
```

| 项 | 处理 | 说明 |
|---|---|---|
| `AccountRecord` | **复用**，加 `pid`、`disabled_by: "platform" \| "firm" \| null`；`email/phone/pw/failed/logins` 迁到人，过渡期保留只读副本 | 成员 ID、设备编号、证书 `memberId`、用量账本、席位全按 aid / uid，**一行不改** |
| `PersonRecord` | **新增**（唯一新实体） | 唯一性从账号挪到人：`accountByEmail/Phone`（`server.ts:513-516`）→ `personByEmail/Phone` + `membershipsOf(pid)` |
| `TenantRecord.kind` | **新增**，建租户时定；迁移时按现 `personal`（`server.ts:655-660`）写一次 | `personalShape` 只留作不变式检查（个人空间 ≤1 名成员），**不再自动翻转**（`server.ts:1670-1676` 改为拒绝） |
| `PlanSpec.audience` | **新增** | 个人空间只能选个人套餐，反之亦然 |
| 会话 | 复用；登录答复带 `memberships[]`；新增 `POST /v1/auth/switch-membership {aid}`（同一人、本会话 10 分钟内或复核过）签发另一成员身份的会话 | 团队管理员撤会话只撤本团队那条 |
| 席位 | 复用；停用/移除成员时一并释放；新增管理员“分配席位” | |

约束（写死，防过度设计）：一个人**至多 1 个个人空间**；团队成员身份数设上限（建议 5）；同一工作空间里一人只有一个成员身份。

### 4.2 四种场景

| 场景 | 做法 | 数据影响 |
|---|---|---|
| 个人加入团队 | 团队管理员照旧发成员邀请码（`/v1/invitations`）；已登录的人在客户端“加入团队”输入码 → 控制面为**同一 pid** 新建团队成员身份（不再要求新邮箱/手机号）→ 客户端新建一个工作空间档案、生成新设备密钥、走现有入组申请与管理员批准（`server.ts:4637`、`5160-5189`） | 个人空间原封不动；个人事项留在个人空间、仍只包裹给个人空间的恢复托管；团队管理员看不到 |
| 退出 / 被移出团队 | 本人先做离所交接（`Offboarding.tsx`），管理员“移除成员”= 停用成员身份 + 撤会话 + 释放席位 + 吊销该成员在本团队的设备（都是“收紧”，控制面可单签，运营侧已这么做：`server.ts:3606`） | 人与其他成员身份不受影响；本机团队档案进入退出模式 |
| 个人升级为团队 | **就地升级**（同一 tid）：在开通电脑上点“升级为团队”→ `kind: personal → team`，记审计、换团队套餐；之后才能发邀请。不再“发一张邀请就悄悄变团队” | 老的个人事项仍是 `personal` 范围，新成员看不到；恢复托管份额仍在原创始人手里 |
| 同时属于多个组织 | 允许。客户端一次只开一个工作空间（一个内核进程），切换 = 现有档案切换（`main.cjs:617-630`）；云端控制台在页头选“当前工作空间” | 每个工作空间各自计费、各自额度、各自电脑数 |

客户端呈现：**就是现有“账号档案”的推广**。把 `otherProfiles`（`packages/kernel/src/index.ts:502`）与云端 `memberships[]` 合并成侧栏底部的“工作空间”菜单（名称 + 个人/团队标识 + 是否待批准），点选即走 `account-switch.ts` 现有流程（`apps/desktop/src/lib/account-switch.ts:1-4`）；同一人切换不必再收验证码（用 `switch-membership`）。

### 4.3 权限与数据隔离的落点

**云端**
1. 一个取上下文的入口：`memberCtx(req) → { person, account, tenant }`，`/v1/me/*`、`/v1/firm/*` 只从**会话的成员身份**取 tid（现状已如此，`server.ts:5224-5232`），永远不从 pid 推“他是哪家的管理员”。
2. 一个归属断言：`requireMemberOf(t, aid)` / `requireDeviceOf(t, deviceId)` 替换现在散落的 `x.tid !== t.tid`（`server.ts:5310-5314`、`5323-5326`），新接口必须用它。
3. 修 R1–R5（见 1.6）：律所侧上限 ≤ 套餐；平台停用的律所不能启用；停用即释放席位；合伙人不能吊销管理员；个人空间不开放 `/v1/firm/*` 写。
4. 平台人员保持跨租户（按权限），不变。

**内核**
1. 不改：每工作空间独立目录、独立账本密钥、独立进程、独立中继目录（2.2 已核实）。
2. 补：内核状态带 `workspace_kind`（来自 onboarding），界面据此而不是据 `member_role` 显示团队功能。
3. 本期**不做**跨工作空间移动事项（会牵涉事项密钥改包裹给另一家恢复托管）；需要时只走“导出归档 → 在另一空间作为新事项导入”，导入时明示“会归入这个团队的恢复托管”。

**“团队管理员默认不能读成员案卷”是否成立**
- 云端：**成立**。控制面只存元数据（`state-store.ts:4-5`），中继只存密文且没有事项密钥（`services/relay-api/src/index.ts` 头注）。
- 管理员电脑：**默认成立**。事项密钥只包裹给事项成员设备 + 恢复托管（`api/index.ts:1000`、`member-log.ts:889`）。
- 要如实写进产品说明的三个例外：①**团队事项**（`collab_scope='team'`，缺省不是）开启共享后，密文会到律所共享文件夹或云端中继——“案卷只在本机”应表述为“明文与密钥只在成员电脑，云端只有可选的端到端密文”；②**恢复托管**：凑齐 3/5 份额 + 拿到密文即可解开团队事项（设计用途：离职、丢电脑）；开发形态份额与创始档案同机（`devices.ts:170-200`），生产须分持；③所内节点只拿被显式授权的事项（`api/index.ts:5080-5105`）。
- 所以“团队共享”**不破坏**“云端无明文”，但**确实**让团队事项的密文离开本机；个人空间里根本没有团队事项，个人用户不受影响。

### 4.4 控制台重构

| 分区 | 现在 | 建议 |
|---|---|---|
| 平台 · 客户 | 律所与个人混在一张表，靠类型筛选（`tenants.js:27-32`） | 拆成**“个人用户”**与**“组织客户”**两个列表（同一菜单下两个页签即可）。个人用户一行 = 一个人（手机号打码、套餐、本期用量、电脑数、到期），点开直达**人员详情**；组织客户一行 = 一个团队空间，详情页签：概览 / 成员与席位 / 套餐与额度 / 用量 / 电脑 / 订阅与开通 / 操作记录 |
| 平台 · 账号 | 一行 = 某所某成员（`accounts.js:63-71`） | 改名**“人员”**：一行 = 一个人；人员详情 = 身份与登录诊断 + **成员身份列表**（个人空间、各团队及角色/状态/席位）+ 电脑（按工作空间分组）+ 会话 + 告警。个人客户的“客户详情”与它合一，消除 IA-1 |
| 平台 · 电脑 | 机队 + 查找 | 保留，不做详情页；行内链接到人员与组织；页头写明范围“所有工作空间的电脑” |
| 平台 · 代建账号 | 两个入口（IA-6） | 只留在组织详情 · 成员（代建 = 在这个组织里加一名成员身份；人存在就挂上） |
| 本所（团队管理员） | 概览/成员/电脑/用量/账单 | 页头选当前团队空间；成员页加“移除成员”（一步完成停用+席位+电脑）与“分配席位”；批准入组仍在开通电脑上（安全属性，D-298） |
| 个人用户 | “我的” + “我的工作室（用量、账单）” | **去掉“我的工作室”分区**，用量、账单、电脑、安全都在“我的”；加“我加入的团队”一栏（只读：团队名、角色、状态） |

平台管理员看到：全部工作空间与人员（按 `ROLE_TABLE` 权限裁剪字段，现状做法保留）。律所管理员看到：本团队空间的成员身份、席位、用量、电脑、账单；**看不到成员的个人空间、其他团队的成员身份**（人员详情里的“成员身份列表”只对平台人员开放）。

### 4.5 现阶段没必要做（及理由）

| 不做 | 理由 |
|---|---|
| 组织层级（部门、分所、子团队） | 客户以几人到几十人的律所为主，四个角色 + 事项成员已够；层级会牵动席位、额度、恢复托管的归属 |
| 自定义角色 / 细粒度权限 | 律所侧只有 admin/partner/lawyer/assistant 四值且接口只分 admin/partner/其余（`server.ts:5257`）；先把现有四值用对 |
| 跨工作空间移动或共享事项 | 要重新包裹事项密钥、换恢复托管归属，风险高、需求弱；用“导出归档 / 导入”兜底 |
| 同一台电脑同时打开多个工作空间 | 一内核一进程是隔离的根基（`main.cjs:617-630`）；切换已足够 |
| 个人与团队额度合并、跨空间共享额度池 | 每个工作空间独立计费最清楚，账单与对账都不用改 |
| SSO / SCIM / 域名自动入组 | 律所规模小，手机号 + 邀请码 + 管理员批准已覆盖；且与“新电脑须律所根批准”的安全属性冲突 |
| 组织转让、合并、拆分 | 低频，运营代办即可 |
| 控制面按租户拆关系表 + 行级安全 | 已登记为 G2（`pg-state-store.ts:12-13`）；本期用统一归属断言 + 越权用例兜住，规模上来再拆 |
| 管理员查看成员案卷 | 与“明文只在成员电脑”冲突；离职场景已由交接 + 恢复托管覆盖 |
