# 02 接口契约（第 72 批，云端 1.7.0 / 客户端 0.11.0）

> 本文是云端、内核、客户端、控制台四路实施的共同约定。改契约先改本文。字段名一律 snake_case；错误一律 `{ error: { code, message } }`（沿用 `CpError`）。
> 兼容原则：**新客户端连旧云端**按 `/v1/meta.features` 降级（没有 `workspaces` 就没有切换入口、团队入口）；**旧客户端连新云端**只看到原有字段，行为不变。

## 0. `/v1/meta.features` 新增

| feature | 含义 |
|---|---|
| `workspaces` | 支持 §1～§3（一个人多个工作空间、切换、创建团队、接受邀请） |
| `team_invites` | 支持 §3 网页 / 会话发团队邀请（不再要求律所根电脑） |
| `team_member_auto_enroll` | 团队成员新电脑由账号签发钥直接登记（D-304） |
| `onboarding_state` | 支持 §4 账号级上手状态 |
| `catalog_epoch` | 模型目录信封带 `epoch`（D-299 第 6 条） |

## 1. 数据模型（控制面状态，JSON 整份；新字段都有缺省，**无数据迁移脚本**，启动时就地定型）

- `TenantRecord.kind: "personal" | "team"`：启动时对缺字段的存量按现有 `personal` 布尔（`personalOf`）定型一次，之后**只由显式动作改变**（不再按形状推断、不再悄悄转换）。`personal` 布尔保留为只读兼容字段（= `kind === "personal"`）。
- `TenantRecord.member_device_policy: "auto" | "approve"`：团队成员新电脑是否直接登记；缺省 `"auto"`（D-304）。个人空间恒为 `"auto"`。
- `AccountRecord.person?: string`：**关联账号**（某人在另一工作空间的成员身份）指向其**主账号**的 `aid`；主账号无此字段。关联账号 `email = null`、`pw = null`、`phone = null`（手机号、邮箱、密码只在主账号上；任何需要手机号的地方用 `phoneOfPerson(a)` 取主账号的）。邮箱、手机号全局唯一索引保持只索引主账号。
- `AccountRecord.disabled_by?: "platform" | "team"`：谁停用的；平台停用的团队侧不能启用（A3 R2）。
- `AccountRecord.onboarding?: { completed_at?: string; dismissed_at?: string }`（只存时间；挂在主账号上，代表这个人）。
- `AccountRecord.last_workspace?: string`：主账号上记最近使用的工作空间 `aid`（登录缺省进这个）。
- `PlanSpec.audience?: "personal" | "team" | "any"`：缺省 `"any"`；控制台按它过滤可选套餐。
- 团队邀请 `TeamInviteRecord`（挂在租户 `t.team_invites: Map`）：`{ id, code_hash, name, role, phone_hint?, created_by, created_at, expires_at, status: "open"|"accepted"|"revoked"|"expired", accepted_by?, accepted_at? }`；码 16 位（人读格式 `XXXX-XXXX-XXXX-XXXX`），只返回一次明文，存 HMAC。有效期缺省 7 天。

人与工作空间：`workspacesOf(primary) = [primary, ...accounts where person === primary.aid]`，按 `kind`（个人在前）、名称排序。一个人至多 1 个个人空间。

## 2. 登录与切换

### 2.1 登录应答新增（`/v1/auth/login`、`/v1/auth/register`、`/v1/auth/me`）

```jsonc
"person": { "aid": "<主账号>", "name": "王律师", "phone_masked": "139****7201" },
"workspace": { "aid": "<当前账号>", "tid": "ten_x", "kind": "personal|team", "name": "王律师的工作室", "role": "admin|partner|lawyer|assistant" },
"workspaces": [ { "aid", "tid", "kind", "name", "role", "status": "active|disabled", "current": true } ]
```
- 登录凭证（手机号验证码 / 邮箱或手机号 + 密码）认证的是**人**（主账号）；应答的会话属于 `last_workspace`（存在且可用时）否则主账号。只有一个工作空间时与现在完全相同。
- `authResult` 其余字段（会话、onboarding 状态、设备上限票据等）按**当前工作空间账号**计算，与现在同一段代码。

### 2.2 `POST /v1/auth/workspaces/switch`（会话：desktop 或 web）

请求 `{ "aid": "<目标工作空间账号>", "client": {...}, "account_switch": true }`，可带设备签名头（与登录相同：签名的是目标账号在这台电脑上的设备时视为已登记）。
- 鉴权：当前会话账号与目标账号**属于同一个人**（同一主账号），且目标 `status === "active"`、目标租户存在且未暂停到不可登录；否则 `404 workspace_not_found`（不区分“不存在”与“不是你的”）。
- 效果：等同于“以目标账号登录”——新建目标账号的会话（`kind` 同当前会话），按目标账号算 `onboardingOf`（新电脑：个人空间与 `member_device_policy=auto` 的团队直接 `needs_device_auto`；满额 `device_limit` + 一次性票据），应答形状 = 登录应答。主账号 `last_workspace` 更新。**当前会话不注销**（这台电脑上原工作空间的档案仍在，切回来时用原档案自己的会话）。
- 审计：`account.workspace_switch`（actor = 主账号，target = 目标 aid）。限流与登录同桶。

### 2.3 `GET /v1/auth/workspaces`（会话）→ `{ workspaces: [...] }`（同 2.1 形状）。

## 3. 团队

### 3.1 个人工作室升级为团队 `POST /v1/workspace/upgrade`（会话；当前工作空间 `kind:"personal"`、本人为其唯一成员）
请求 `{ "name": "某某律师事务所" }`（名称 2～40 字，校验同机构名；可与原工作室名相同）。
- **就地升级**（同一 `tid`，A3 §4.2）：`kind: personal → team`、`member_device_policy:"auto"`、改名；席位 = `max(现席位, 注册策略 team_trial_seats ?? 3)`（试用期内；付费客户的席位仍由运营 / 销售改）；套餐不变（运营可再改）。不可逆，客户端须二次确认。
- 原有事项、成果、电脑都不动；个人事项仍只属于本人（团队共享事项要逐个显式开启）。
- 应答 `{ ok: true, workspace: {...} }`；审计 `workspace.upgrade_team`（记原名、新名、席位变化）。
- 取消原“发第一张成员邀请就悄悄转团队”：个人空间调旧接口 `/v1/invitations` → `409 upgrade_required`（`personalOf` 不再按形状翻转）。
- 不提供“另建一个新团队”（加入别人的团队走 §3.3；需要时由运营开通）。

### 3.2 团队邀请（会话：当前工作空间是团队且角色 `admin`；设备签名不再必需）
- `POST /v1/team/invites` `{ name, role: "lawyer"|"partner"|"assistant"|"admin", phone_hint? }` → `{ invite: {id, name, role, expires_at, ...}, code: "XXXX-XXXX-XXXX-XXXX" }`（明文只此一次）。
- `GET /v1/team/invites` → 列表（不含码）。`POST /v1/team/invites/:id/revoke`。
- 席位不在发邀请时占用；接受时若无空席位照样入团队，AI 用不了并如实提示（席位由管理员加）。

### 3.3 接受邀请
- 已注册的人：`POST /v1/teams/join`（会话）`{ code, client }` → 校验码（HMAC、未过期、未用、租户 `kind:"team"`）；同一个人在该团队已有成员身份则 `409 already_member`；创建关联账号（`person` = 主账号，`name` 取邀请上的姓名，`role` 取邀请）；应答 = §2.2 切换应答。审计 `team.invite_accept`。
- 未注册的人：`POST /v1/auth/register` 带 `team_invite_code`（与手机号验证码一起）→ 主账号直接建在该团队（不建个人空间）；`next` 同自助注册（直接进入）。
- 码错、过期、已用：统一 `400 invite_invalid`（不区分，防枚举）；来源限流 10 次 / 10 分钟。

### 3.4 团队成员管理（会话，团队 `admin`；`partner` 只读）——沿用 `/v1/firm/*` 前缀，补齐：
- `GET /v1/firm/members` 每行带 `person_phone_masked`、`seat`、`devices: {signed_in, limit}`、`status`、`disabled_by`。
- `POST /v1/firm/members/:aid/remove`：移出团队 = 停用该成员身份（`disabled_by:"team"`）+ 释放席位 + 吊销会话；设备记录保留（便于离所交接后再移除）；不能移出自己、不能移出最后一名管理员。
- `POST /v1/firm/members/:aid/role` `{ role }`：改角色（最后一名管理员不能降级）。
- `POST /v1/firm/seats/:aid/assign`、`/release`：手动分配 / 释放席位（不超过席位数）。
- `POST /v1/firm/members/:aid/limits`：电脑上限**不得超过套餐 `device_limit`**（A3 R1）；个人空间对 `/v1/firm/*` 写一律 `403 team_only`。
- 启用：`disabled_by === "platform"` 时 `403 platform_disabled`（A3 R2）。
- 重置码：不再把明文返回给管理员；改为“给成员手机号发重置短信”（A3 R3）。
- `PUT /v1/firm/policy/member-device` `{ policy: "auto"|"approve" }`。
- 成员自己退出团队：`POST /v1/teams/leave`（会话，当前工作空间为团队、非唯一管理员）→ 同 remove 的效果，`disabled_by:"team"`、审计 `team.leave`；应答带切回的工作空间（主账号或另一工作空间的切换应答）。

### 3.5 团队成员新电脑（D-304）
- `autoEnrollReady(t)` 扩为：有账号签发钥 && 律所根与公钥包已登记 && (`kind==="personal"` || `member_device_policy==="auto"`)。团队租户首次满足时登记 `t.account_device_ca`（同个人）。
- 账号签发钥签的电脑（`issuer: account_ca`）：能登录、用 AI、处理自己的事项；**不能**做律所根动作（`requireAdmin` 原样），**不进**团队共享（内核原样）。团队共享页提示“这台电脑还不能接收团队共享事项”，由管理员在“团队 · 电脑”里确认（复用入组批准：律所根签发新证书给同一台电脑）——本批若做不完，提示与入口先上，确认动作沿用现有入组批准。

## 4. 账号级上手状态

- `/v1/auth/me` 与登录应答带 `onboarding: { completed_at, dismissed_at }`（主账号的）。
- `POST /v1/me/onboarding` `{ completed?: true, dismissed?: true }` → 置时间（只置不清；“重看指南”只在本机）。

## 5. 模型目录（D-299）

- 内置别名：`legal/k3 → kimi-k3.1-pro`（`scopes: qa, task`）、`legal/k2.6 → kimi-k2.6`（`capabilities: tool_use, thinking`，**`scopes: qa, task`**）。缺省路由、部署模板、网关本机兜底三处同口径；说明文案写实。
- 目录项计算：若某非缺省别名解析出的主上游型号与缺省别名的相同 → `available: false`、`reason: "same_upstream"`、`reason_text: "运营尚未给它配置独立的模型"`；控制台告警 `routing.same_upstream`。
- 信封 `kwl-model-catalog` 增 `epoch`（路由状态首次建立 / 重建时随机 16 字节 base64url，存于路由状态；运营修改不换）。客户端：`epoch` 不同即接受（签名照验），同一 `epoch` 内才比 `version`。
- 用量“按模型”显示名统一用 `modelMetaOf(m).label`；任务子 Agent 调用在本人 / 团队用量明细里标“任务辅助步骤”（依据：计量记录的调用用途字段，没有就按 `alias === legal/k2.6 且 kind === task` 近似并在文档里写明）。

## 6. 越权与隔离用例（云端必须新增，全部真实控制面端到端）

1. A 的会话切换到 B 的工作空间 aid → 404。
2. 关联账号用自己的会话调 `/v1/firm/*` 读别的团队 → 404 / 403。
3. 团队管理员读成员个人空间的用量 / 电脑 → 404。
4. 被移出团队后，旧会话与旧设备在 2 分钟核对内失效；切换到该团队 → 404。
5. 个人空间调 `/v1/firm/*` 写 → 403 `team_only`；自改电脑上限超过套餐 → 400。
6. 平台停用 → 团队管理员启用 → 403 `platform_disabled`。
7. 邀请码重放、过期、跨团队使用 → `invite_invalid`；已是成员再接受 → 409。
8. 升级：非个人空间 / 非唯一成员调升级 → 409；个人空间调 `/v1/invitations` → 409 `upgrade_required`；升级后审计在。
11. 另按 A3 §4.7 的 X1～X10 补齐（尤其 X1：A 团队管理员对 B 团队**真实存在**的成员 aid 调 disable / enable / limits / sessions / remove / seat → 一律 404 且 B 状态不变）。
9. 切换应答的会话只属于目标账号：用它调原工作空间的 `/v1/me/*` 只返回目标账号数据。
10. 用量账本：两个工作空间各发一次 AI 调用，各自只计入各自租户、各自账号。

## 8. 平台运营接口补充（`/v1/ops/*`，控制台平台分区用；权限沿用 `rbac.ts` 现有权限名，不新增角色）

- `GET /v1/ops/tenants` 每行加 `kind`（显式字段）、`member_count`、`seat_used`、`seats`；支持 `?kind=personal|team` 过滤。
- `GET /v1/ops/people?q=&page=`（新增，`account.read`）：一行 = 一个人（主账号）：`{ aid, name, phone_masked, email_masked, status, created_at, last_login_at, workspaces: [{aid, tid, kind, name, role, status, seat}] }`；`q` 按姓名 / 打码前缀 / 邮箱 / 工作空间名搜。
- `GET /v1/ops/people/:aid`：人员详情 = 主账号身份与登录诊断（复用现有账号详情的诊断字段）+ 工作空间列表 + 各工作空间电脑（按工作空间分组）+ 会话。`:aid` 传关联账号时 302 语义改为返回其主账号（应答带 `primary_aid`）。
- 现有 `GET /v1/ops/accounts*` 保留（旧控制台、深链），行上加 `person`（主账号 aid，主账号自身为自己）。
- `POST /v1/ops/tenants/:tid/seats/:aid/assign`（`seat.manage` 或现有收回席位所用权限）：运营手动分配席位（不超过席位数）。
- `POST /v1/ops/tenants/:tid/kind` 不提供（类型只由“就地升级”与开通时决定，运营代办升级走同一逻辑：`POST /v1/ops/tenants/:tid/upgrade-team`，危险操作要复核，审计 `workspace.upgrade_team` actor=staff）。
- 代建成员只留组织详情一个入口：`POST /v1/ops/tenants/:tid/invites`（运营代发团队邀请，返回一次性码），旧 `POST /v1/ops/accounts` 保留兼容。
