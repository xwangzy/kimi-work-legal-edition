### 1.2 运行形态

### 1.3 计时口径

- **路径 A**：全新数据目录 → 打开应用 → 注册（手机号、取验证码、姓名 / 邮箱 / 密码）→ **点“注册并继续”起** → **到工作区首屏止**（可见“新建任务”，页面前 400 字不含“正在打开 / 这台电脑已登记为你的电脑 / 注册并继续 / 正在注册 / 正在登录 / 你已退出登录 / 正在切换 / 正在核对”）。
- **路径 B**：同一会话、同一数据目录、账号甲（刚注册）已登录 → 账号页“退出登录” → “换个账号” → “密码登录”用已存在的账号乙（上一个会话注册、已在它自己的数据目录里退出登录，不占“同时登录”名额）→ **点“登录”起** → **到乙的工作区首屏止**（同上，且页面出现乙的姓名）。
- 账号链：会话 s 的乙 = 会话 s−1 的甲。开头一个种子会话 `seed`（改前，只注册并退出登录）为第一轮供乙，不计入统计。手机号按 `1390007` + 三位序号（230 起）+ `0` 取 11 位（给定的 1390007230～1390007299 作前缀）。
- 轮次：版本 × 延迟 × 3 轮，交错执行（0 ms：改前 r1、改后 r1、改前 r2……；再 300 ms 同样顺序），取中位数。
- 改后版本另用 `scripts/measure-enroll.mjs --data <ud>/KimiWorkLegal --watch --out …` 在点击前启动、首屏后 9 s 停止，收内核 / 主进程埋点。改前版本没有这些埋点（只有 `MAIN_KERNEL_IDENTITY_RESTART`、`KERNEL_CLOSED`、`MAIN_KERNEL_READY`、`KERNEL_GATE_STARTED` 等锚点），同样收集。

### 1.4 网络延迟

- **0 ms**：客户端直连回环 18741 / 18742 / 18744。
- **300 ms 往返**：`evidence/enroll-timing/delay-proxy.mjs`（node `net`）在 28741 / 28742 / 28744 转发到原端口，每个方向每块数据延迟 150 ms（同方向按到达顺序）；新连接的第一块上行数据另加 1 个往返（模拟 TCP 握手），所以新连接上的第一个请求约 600 ms、复用连接上的请求约 300 ms。控制面、网关、检索三个地址都改指代理（`ZR_CONTROL_PLANE_BASE`、`ZR_GATEWAY_BASE`、`ZR_SEARCH_BASE`）。明文 HTTP，**没有模拟 TLS 握手**（线上 HTTPS 新连接还要再加 1 个往返）。代理逐连接日志在 `raw/proxy-connections.jsonl`。

## 7 限制与偏差

1. **平台与形态**：macOS 27.0.1、Apple M5 Pro、Electron 44.5.1 开发形态（`app.isPackaged=false`）。Windows、Defender 扫描、安装包 asar 加载、DPAPI 都不在内（A1 认为 A10、A11、S3 在 Windows 上影响最大）。S3 的 `attested` 路径只在安装包形态生效，这里两版都是每次重启整份算闸门 Node 摘要（约 52 ms / 次）。
2. **钥匙串**：`--use-mock-keychain`，取库密钥一段 0 ms，比真实 macOS 钥匙串快几十毫秒（两版相同）。
3. **延迟模型**：明文 HTTP，每方向每块 150 ms，新连接加 1 个往返模拟 TCP 握手；**没有 TLS 握手**（线上 HTTPS 新连接还要再 +1 往返，首次同步与闸门新连接会更慢），没有抖动和丢包。代理日志 756 条连接（`raw/proxy-connections.jsonl`），控制面 / 网关 / 检索流量都经过代理。
4. **同一个云端**：两版都连 b72 的 `cloud-serve.mjs`（云端 1.7.0）。改前客户端的真实搭档是云端 1.6.0；H3 的云端部分本批没做。
5. **改后版本的漂移**：内核制品在 11:39 按当时的 b72（内核 = c64c68f0/7facbf4f）构建，全程没重建；b72 在 12:00～12:08 又提交了 b53dd475（安全审查 P2-6：`kernel-gate.ts`、`runtime-stamp.ts` → `runtime-digest.ts`、`main.cjs` −28 行）、c9b1adb0、102dd0c6。所以开发 0 ms 组（11:50～11:54）用的是 7facbf4f 的 `main.cjs` + 未提交的 `src/`（diff sha `03c7cda5fa63`），300 ms 组与生产组（12:00 以后）用的是 b53dd475 起的 `main.cjs` + 11:39 的内核制品；生产渲染取 102dd0c6 的 `src/`。这些后续改动只影响安装包形态的 S3 和界面文案，对本测路径的耗时影响预计可忽略，但严格说改后的“内核 + 主进程”不是同一个提交。
6. **路径定义**：路径 A 是“自助注册即开通个人工作室”（过渡页文案“已为「…的工作室」开通”，一次重启）；“已有账号在一台全新电脑上首次登录”没有单独测。路径 B 的乙在自己的数据目录里已退出登录，所以不占“同时登录”名额（试用套餐 `device_limit: 1`）；乙仍在别处登录时会先进电脑数上限页，那条没测。
7. **计时精度**：界面每 100 ms 采样一次（±0.1 s）；日志 `t` 只到秒，阶段毫秒数取各事件自带的 `ms` 字段。
8. **试跑数据作废**：最早两批因 `pkill` 模式没匹配上相对路径启动的 `batch.mjs`，两个批次曾并发、账号登录状态不可知，全部移到 `raw/pilot/` 不计；正式轮另起账号链（手机号序号 20 起）。

## 9 结论

1. **0 ms 下改前改后没有差别**：路径 A 约 1.3 s（生产渲染 1.15 s）、路径 B 约 2.2 s（生产 约 2.0 s），差值 ≤0.06 s。每次内核重启真正的活只有约 0.3 s（关旧内核约 0.02 s + fork→就绪约 0.24 s），其余是固定的 restartSoon 300 ms、界面 1 s / 800 ms / 500 ms 轮询的量化等待和整页重载。
2. **300 ms 往返下路径 A 也没有差别（约 1.5～1.6 s）**；**路径 B（生产渲染）从 3.63 s 降到 3.31 s（−0.31 s，−9%）**，省下的是“点登录 → 出现‘正在为乙登记’”之间的一个往返，这一段埋点没覆盖，没能归因到具体改动。
3. **S3 / S6 / S7 / H4 在本测形态里看不到首屏收益**：S6 生效（席位令牌一段 0～3 ms，与文档并行），但首次同步本来就和界面并行，套餐“试用”出现时刻两版相同；S3 只在安装包形态生效；S7、H4 没被触发（关旧内核全是 `exit`、15～22 ms）。
4. **开发形态 + 300 ms 时路径 B 两版 3/3 都无声卡死**（>180 s、无错误文案、无自动重试），内核约 3 s 时已就绪；原因是 StrictMode 双调用让 `Activate.tsx` 交接等待循环被清理、`handled` ref 又挡住重跑。生产渲染 6/6 正常，所以不是线上必现，但这个写法一旦 effect 重跑就没有任何出口，H5 的兜底也够不到它，建议修。
5. **42 次计时没有出现任何“还没有登记完成 / 请关闭并重新打开应用”类文案**。剩下的耗时大头是固定等待和轮询（路径 A 1.3～1.5 s 里约 1 s、路径 B 里约 2 s）。下一步要提速，应把“轮询 kernel.status 再 reload”改成主进程推送就绪事件，并在 Windows 安装包形态 + TLS 下再测一轮。
