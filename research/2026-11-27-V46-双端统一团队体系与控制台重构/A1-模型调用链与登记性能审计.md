## 题 1：模型选择是不是真的控制了底层调用

### 1.1 任务（task）入口为什么只有一个模型

**结论：不是 bug，是配置口径。** 任务入口只列 `scopes` 含 `task` 的模型，而云端缺省路由里只有两个内置别名，其中 K2.6 的入口只有问答。两个都满足才会出下拉；现在任务入口只剩 K3 一项，选择器就按设计只显示名字。

判断条件原文：

1. 客户端：只有一项时不做下拉——`apps/desktop/src/components/ModelPicker.tsx:43`
   `if (choices.length === 1) return <span className="model-label" ...>{cur.label}</span>;`
   `choices` 来自 `modelChoices(taskModels)`（`apps/desktop/src/lib/model-choices.ts:8-10`），它把内核返回的所有模型（含不可用的）都映射进来，所以“只有一项”就是内核目录里只有一项。
2. 内核：按入口过滤——`packages/kernel/src/services/model-catalog.ts:242-249`
   `return this.models().filter((m) => m.scopes.includes(scope)).map(...)`
   能不能选另看 `check()`（同文件 :223-231）：`if (!m.scopes.includes(scope)) return fail(...)`；`if (scope === "task" && !m.capabilities.includes("tool_use")) return fail("no_tool_use")`。
   `models.list` 直接调用 `catalog.list(scope)`（`packages/kernel/src/api/index.ts:1783-1802`）。
3. 内核内置兜底（登录前 / 开发 / 试用）——`packages/kernel/src/services/model-catalog.ts:49-50`：
   `legal/k3` → `scopes: ["qa", "task"]`；`legal/k2.6` → `scopes: ["qa"]`。
4. 云端：内置别名的缺省能力与入口——`services/control-plane/src/routing.ts:96-103`，原注释：“K2.6 只在问答可选……（任务里它是子 Agent 的模型，主任务不选它——任务入口只列 scopes 含 task 的）”。
   `legal/k3`：`capabilities: ["tool_use","thinking","long_context"]`，`scopes: ["qa","task"]`，`thinking: "effort"`；
   `legal/k2.6`：`capabilities: ["tool_use","thinking"]`，`scopes: ["qa"]`，`thinking: "toggle"`。
   路由记录里没有 `scopes` 字段时，`modelMetaOf` 回落到上面这份内置口径（`routing.ts:108-122`，`scopes: m.scopes ?? b?.scopes ?? ["qa"]`）。**运营新增的别名如果没勾“任务”，缺省也是只进问答**（同一行的 `["qa"]`）。
5. 云端缺省路由状态（首次启动、状态里还没有 routing 时）——`services/control-plane/src/routing.ts:272-287` `bootstrapRouting`：
   - 只推两个内置别名（`BUILTIN_ALIASES = ["legal/k3","legal/k2.6"]`，`routing.ts:240`），记录里**不写** `scopes/capabilities`，因此按第 4 点的内置口径取；
   - 缺省上游型号：`const defaults = { "legal/k3": "kimi-k3.1-pro", "legal/k2.6": "kimi-k3.1-pro" }`（`routing.ts:279`）；
   - 部署模板同样两项都指 `kimi-k3.1-pro`：`cloud-repo/template/deploy/config/control-plane.example.json:25`、`scripts/cloud-serve.mjs:77`；开发控制台把 K2.6 指 `kimi-k3.1-pro-highspeed`（`scripts/dev-console.mjs:67`）；
   - `migrateRouting` 只在状态缺字段时整份重建为 bootstrap，否则原样保留（`routing.ts:946-950`）。
6. 云端写入约束（运营在控制台改的时候）：缺省模型必须能在任务入口选（`routing.ts:763`）；入口勾“任务”必须同时勾 `tool_use`（`routing.ts:808`）。
7. 网关本机兜底（取不到路由订阅时）：`legal/k3 → kimi-k3`，`legal/k2.6 → kimi-k2.6`（`services/legal-gateway/src/routing.ts:160-163`），和云端 bootstrap 口径**不一致**。

→ 想让任务入口出现第二个可选项，有两条路：(a) 运营在控制台给某个别名（如 K2.6，或新增 `legal/k3-fast` 指 `kimi-k3.1-pro-highspeed`）勾选入口“任务”加能力 `tool_use`；(b) 改内置口径，让 K2.6 也进任务入口。按现在的设计，K2.6 是任务里的子 Agent 模型（见 1.2），把它放进主任务入口之前要产品先拍板。

### 1.3 用量账本记的是什么模型：显示、实际调用、计费三者是否一致

- 网关计量记录同时有别名和实际上游型号：`services/legal-gateway/src/gateway.ts:740-742`（`alias`、`provider`、`upstream_model: served?.model`），本机预写日志也写 `model: alias` 与 `upstreamModel`（:785、:793）。
- 计费按实际服务的上游型号算：网关 `saleRatesFor(snap.prices, alias, served?.model)`（`gateway.ts:729`）；控制面 `resolvePrice(currentPrices(routing), routing, r.alias, r.upstream_model)`（`services/control-plane/src/server.ts:2414`）；账本 `price_basis = model` 时 `price_key` 是上游型号（`services/control-plane/src/usage-ledger.ts:80-84`）。
- 律师和管理员看到的“按模型”都按**别名**分组：`usage-ledger.ts:295-296`（`byModelDay` 键是 alias）；本所 / 本人明细 `server.ts:5217` `modelLabel = (alias) => routing.models.find(...)?.label ?? alias`，用处 :5223、:5252、:5412；`server.ts:2602` 同样。另有按上游型号的分组 `byUpstreamDay`（`usage-ledger.ts:297`），只在运营视图里用（`server.ts:3245` `group === "upstream"`）。

三者的关系：

1. **显示 = 别名，计费 = 上游型号。** 别名换了目标（例如 K2.6 指向 `kimi-k3.1-pro`），律师看到“K2.6”，实际按 K3.1 Pro 的价扣额度。
2. **任务里的子 Agent 记成 K2.6。** 律师选的是 K3，本人用量里也会出现一部分“K2.6”（来自 1.2 Work ⑦）。律师看不懂这部分从哪来。
3. **显示名有两套口径。** 目录走 `modelMetaOf`，会把占位名“主任务模型 / 子任务模型”换成 K3 / K2.6（`routing.ts:105,110`）；用量页 `modelLabel` 直接取 `m.label`（`server.ts:5217`，另见 :2602），没换。运营在控制台把 label 写成占位名时（开发控制台就是这么写的，`scripts/dev-console.mjs:170`），客户端选择器显示 K3，用量页显示“主任务模型”。

### 1.4 所选模型的持久化与云端变更后的同步

持久化：
- 任务：`models.select` → `saveModelPref(db, tid, uid, "task", id)`（`api/index.ts:1804-1811`；表 `model_prefs`，`packages/kernel/src/migrations/0073_v40_run_model_prefs.sql:8`，本机、按本人、不上云）。读回在 `models.list`（`api/index.ts:1789-1791`）：记住的不可用时回落缺省，并带 `selected_unavailable`，首页据此提示（`Home.tsx:182-184`）。
- 问答：**另一套**。`Chat.tsx:89-115` 用 `localStorage`（`scopedKey(MODEL_KEY)`），不调 `models.select`；内核 `pickRoute` 读的 `model_prefs(qa)`（`index.ts:801`）客户端从来不写（全仓 `modelsSelect(` 只有 task 的调用：`Home.tsx:190`、`ScenarioStart.tsx:850`）。两套各管各的，实际以 localStorage 为准。

同步时机（内核 `ModelCatalogService`）：
- 构造时读工作区缓存 `model-catalog.json`，重新验签（`model-catalog.ts:175-189`；文件位置 `index.ts:648`）；
- 登录成功后 `setTimeout(() => refresh("login"), 0)`（`index.ts:404`）；
- 定时：启动先取一次，之后每 10 分钟（`model-catalog.ts:296-302`；`index.ts:1479`，`ZR_MODEL_CATALOG_MS` 缺省 600000）；
- 网关按模型拒绝（`model_not_allowed|model_disabled|model_not_routed|price_unconfigured|upstream_unavailable`）时刷新，至多 30 秒一次（`model-catalog.ts:311-313`，`index.ts:565-568`）；runs.start 核不过时也刷一次（`api/index.ts:2132`）；
- 界面：`useModelCatalog` 首次读取，结果 `source !== "cloud"` 时才带 `refresh: true`；**窗口获得焦点时只读内核内存，不带 refresh**（`ModelPicker.tsx:94-105`）。

问题：
1. **聚焦刷新名不副实。** 注释写“窗口重新获得焦点时再读（云端增改启停模型后……即可看到）”（`ModelPicker.tsx:86-88`），可 `onFocus = () => void load(false)`（:104）读的是内核内存里那一份。内核拿到云端目录以后，云端再改的内容最多要等 10 分钟定时刷新才进来。
2. **问答页只在挂载时读一次** `chat.models`（`Chat.tsx:96-107`），没有聚焦刷新也不订阅。云端停用了某个模型，问答页的下拉要等切换页面才变；发送被拒以后内核会刷新目录，界面列表却不跟着更新。
3. **“只进不退”可能把旧目录钉住。** `catalogNewer` 先比 `version`，版本低的一律当 stale 不采用（`model-catalog.ts:104-109,275-283`）。`version` 是控制面路由状态的版本号：初值 1（`routing.ts:265`），每次修改加 1（`routing.ts:647-648` 等）。只要控制面路由状态被重建或回退（新部署走 `bootstrapRouting`、状态文件从旧备份恢复、迁移到新仓库或新服务器），云端版本就会低于客户端缓存里的版本，客户端会一直用缓存的旧目录（日志只有 `KERNEL_MODEL_CATALOG_STALE`），直到云端版本号重新超过它。界面上表现为“云端改了模型，客户端怎么也不变”。缓存文件在工作区，重启应用也清不掉。现在没有任何纪元 / 部署编号能让客户端认出“这是重建过的新状态”。
4. 登录刷新是 `setTimeout(0)` 异步发起，不等结果。首次登录后立刻进首页，首页可能先拿到内置两项或缓存（`source: "builtin"/"cache"`），再由 `useModelCatalog` 补一次 `refresh: true`；这条路径能自愈，只是多一次往返。

### 1.5 题 1 结论

**根因（一句话）：** 任务入口只列 `scopes` 含 `task` 的模型，云端缺省路由只有 K3 / K2.6 两个内置别名，K2.6 按内置口径只进问答（`routing.ts:102`、`model-catalog.ts:50,245`）。所以任务入口只剩 K3，选择器按设计不出下拉。这不是界面 bug。

**链路判断：** Work 和 Chat 的主调用确实用所选别名一路传到网关，网关按别名换上游型号。偏离所选模型的只有三处：子 Agent 强制 K2.6（`engine-config.ts:149`）；内核自发调用在别名失效时静默回落 K3（`executor.ts:67-75`）；BYOK / 私有端点只认内置两项（这一处会明确拒绝，不算问题）。

**“界面假切换”风险：**
- R-M1（高，需要核实线上）：按 bootstrap 和部署模板，`legal/k2.6` 与 `legal/k3` 指向**同一上游 `kimi-k3.1-pro`**（`routing.ts:279`；`control-plane.example.json:25`）。线上没被运营改过的话，问答里切到“K2.6（更快、更省额度）”其实还是 K3.1 Pro，计费也按 K3.1 Pro（`gateway.ts:729`）。说明文字和实际不符。另外 K2.6 的内置路由按 toggle 发 `thinking: {type}`（`model-broker/src/providers/gate.ts:66-71`、`config.ts:87-91`），内核注释写明“K3 不支持 thinking 参数”（`index.ts:804-806`）。上游是 K3.1 Pro 时，这个参数会不会被忽略、思考强度落到什么缺省值，要拿真实请求测。
- R-M2（中）：静默回落 K3（`executor.ts:67-75`）。律师选的是 X，复核却用了 K3，交付件上的模型信息和运行记录都看不出来。
- R-M3（中）：子 Agent 强制 K2.6，用量页里会出现律师没选过的“K2.6”；而 K2.6 实际又可能是 K3.1 Pro。
- R-M4（低）：用量页显示名和选择器显示名口径不同（`server.ts:5217` 对 `routing.ts:105-122`）。
- R-M5（中）：目录版本回退后客户端一直钉在旧目录（`model-catalog.ts:275-283`）。

1. **R2-1 残留失败记录造成误报（中，代码可证）。** `onboarding-failed.json` 只在兑换（`onboarding.ts:408`）、注册（`:831`）、重新输入（`:968`）时删除；**`accountLogin`（:842-873）和 `resumeHandoff`（:243-258）都不删**。交接等待循环先判断 `h.next !== "working"`，再判断 `o?.last_failure && !o.restarting`（`Activate.tsx:216-223`）。所以只要磁盘上有上一次留下的失败记录，交接还在 `working` 时第一次轮询就会报 E2，后台却还在继续登记，登记成功后照样重启，界面停在一条过时的错误上。登录表单初始也会把它显示成 `failed`（`Activate.tsx` `ActivatePage` 的 `failed` 属性）。

3. **R2-3 半登记的云端设备（中，需要实测）。** 云端在签名回来后写 `t.devices`（`server.ts:4410`），这时本机还没写暂存和激活（`onboarding.ts:748-753`）。中间如果内核崩溃、应用被关、证书核对没过（E8），云端就多了一台本机不认的电脑。再登录时，`full()` 用 `deviceRoomOf(a, null)`（`server.ts:4386-4391`），不排除同一台，**试用账号（上限 1 台）会直接被报“电脑数已满”**。同时 `enrollRisk` 按“24 小时内自动登记 3 台”计数（`server.ts:4372-4380`），反复重试会进短信确认。本机每次 `autoPending` 都重新生成密钥（`onboarding.ts:692`，只在同一个 autoPending 内复用），崩溃后没法幂等重放。

### 2.3 缩短耗时和自动恢复的改法（每条附文件:行与风险）

**缩短耗时（按收益排序）：**

- **S1 路径 B 去掉一次重启（收益最大，约省 4～8 s）。** 正常模式内核收到“新账号、需要登记”（`index.ts:474-483`）时不先切到待激活内核，而是**就在当前内核里**做 `withClaim` 加 `autoEnroll`（闸门和中继都现成），写好新档案的暂存与激活，再只做一次 `switch_profile`（`kind:"session"`）。难点在库密钥：新档案的待激活密钥格现在由主进程在待激活启动时生成（`main.cjs:98-118`、`key-slots.cjs`）。要改成内核先请主进程“为档案 X 预生成密钥格”（新增一条 IPC），内核拿不到别的档案的密钥，这一点不变。风险：中高，涉及档案隔离（安全复核 P-1～P-4、K-1）和失败回滚，要专门做安全评审。
- **S2 登记应答直接带首包治理文档（约省 2～4 次往返，AI 进门即用）。** `/v1/auth/devices/enroll`（`server.ts:4350` 起）签完证书时云端已经写入设备，可以顺手签发席位令牌，并附上 license / salt / directory / policy / connectors 五份签名信封。内核把它们存进暂存，新内核启动时先应用（复用 `gov.apply*`），首次同步就只剩“对一次账”。风险：中，云端接口加字段要兼容旧客户端，席位令牌在暂存里要按密钥封装，验签逻辑不变。
- **S3 闸门运行时哈希只算一次（Windows 上每次重启约省 0.3～1.5 s，路径 B 省两次）。** `kernel-gate.ts:398-401` 每次拉起闸门都对约 100 MB 的 Node 整份算 sha256。主进程已经做过随包运行时全量核验（`main.cjs:597` `sendRuntimeVerified`）。可以改成主进程把“已核验（路径、大小、mtime、inode/fileId）”交给内核，内核核对元数据一致就跳过重算；或者在主进程里按应用会话缓存。风险：中，存在核验后被替换的 TOCTOU 窗口，用元数据比对加只读安装目录缓解，要过一次安全复核。
- **S4 去掉轮询量化等待，改为事件驱动（约省 0.5～1.5 s）。** 主进程在 `identity-restart.cjs:27` 已经广播 `{status:"running"}`。界面订阅这个状态，收到后立即查一次 `kernel.status`；轮询保留作兜底，间隔从 1000 / 800 ms 降到 250 ms（`Activate.tsx:72`、`lib/account-switch.ts:28`）。风险：低。
- **S5 预热下一个内核进程（Windows 约省 0.5～2 s）。** 关旧内核的同时先 `fork` 新内核，让它解析好 bundle，停在 `waitForInit`，等旧内核退出后再发 `kernel.init`（`main.cjs:542-579`、`electron-entry.ts:151`）。风险：中，两个进程短暂共存，新进程在 init 之前不能碰数据根，`waitForInit` 现在已经满足这一点，但要核实日志 sink 等的初始化时机。
- **S6 首次同步内部再并行（省 1 次往返）。** 席位令牌只依赖 `exitMode()`（许可），可以等 license 应用后立即发，和其余四份文档的验签、应用并行（`client.ts:370-388`）。风险：低。
- **S7 关内核别卡 8 s。** `server.close()` 之前先 `closeAllConnections()` / `closeIdleConnections()`；`shareRelay` 没有在途收发时直接关（`index.ts:1530`、`:1546-1548`）。风险：低。
- **S8 新工作区用 schema 快照代替 70 个迁移（省 0.2～1 s，先测量再决定）。** 新建库时一次执行“当前版本的建表脚本”，再写入迁移版本号（`db.migrate()`，`index.ts:126`）。风险：中，快照和迁移漂移，要加一致性用例（逐个迁移后的 schema 等于快照）。
- **S9 （可选）不整页重载。** 进入工作区时只重跑 `App.loadBoot`，不调 `location.reload()`（`Activate.tsx:77`、`:204-206`）。风险：中，上一个身份的内存状态可能残留；路径 B 涉及换账号，安全上倾向保留整页重载，只在路径 A 的同账号场景考虑。

**自动恢复（让律师不用关应用）：**

- **H1 清掉残留失败记录。** `accountLogin` 开头、`resumeHandoff` 开头删 `onboarding-failed.json`（照 `onboarding.ts:408` 的做法）。交接等待循环里，只有 `last_failure.at` 晚于本次轮询开始、或者 `h` 不存在时才认失败（`Activate.tsx:221`）。风险：低。
- **H2 首次同步退避重试。** `client.ts:477-485`：首次同步的 `register` 没成功、或者没拿到席位令牌时，按 2/4/8/16/30 s 重试，直到成功或到达常规间隔；`afterFirstRegister` 改为等“首次成功或首轮重试用尽”。风险：低，重试只在首次登记阶段，不放大常态流量。
- **H3 登记幂等。** 本机在发 `enroll` **之前**把 `autoPending.gen` 加封装写进暂存，崩溃后用同一副密钥、同一 `device_id` 重放（`onboarding.ts:692-702`）。云端 `full()` 改成 `deviceRoomOf(a, deviceId)`，排除同一台；同一 `device_id`、同一公钥、还没 `register` 的条目按幂等返回原证书（`server.ts:4386-4410`）。`enroll_in_progress` 在内核里自动等 1～2 s 重试一次（`onboarding.ts:737-739`）。风险：中，云端覆盖设备证书的条件必须收紧（同公钥才幂等），要安全评审。
- **H4 主进程不吞重启。** `main.cjs:1333` 改成置 `restartAgain = true`，当前那次结束后再跑一次；`identity-restart.cjs:12` 同步改。风险：低。
- **H5 “关闭并重新打开应用”改为应用内重试。** 新增 IPC `kwl:restart-kernel`（调 `restartKernelForIdentity`），E1、E5、E6 的出口自动先重试一次，仍失败再给“重试”按钮，不再让律师关应用（`Activate.tsx:88`、`lib/account-switch.ts:42`、`identity-restart.cjs:23`）。风险：低到中，要防重试风暴，最多自动一次。
- **H6 过渡页给阶段与已用时间。** 照 `App.tsx:153-167` 的 `BootWait`：主进程和内核把“正在关闭 → 正在准备本机数据 → 正在连接云端 → 就绪”几个阶段广播出来，替换 `Activate.tsx:257` 那句写死的“第一次打开需要十几秒”。风险：低。
