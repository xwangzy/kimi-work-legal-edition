## 0. 结论先行

1. **10-13 的 P0 大多已经落地**，包括：依据一问、场景卡与开始面板、意图建议条、DOCX/XLSX 预览、合同审查工作台、时间线分层、检索卡安全默认、错误边界、侧栏状态。主路径“首页 → 场景卡 → 开始面板 → 运行 → 工作台”已经能走通。**P1 的 12 条基本都没动**（U8 及事项头、输入框底栏、复核页、材料表、首页“等你处理”、设置拆分、窄屏、全局提醒、对比度、键盘、数据去向文案），这些是今天界面“工程味”的主要来源。
2. **这轮新发现 6 个 P0，其中 3 个会直接损害“隐私可信”**：
   - **P0-A 时间线泄露原文检索式。** 律师点了“用改写后的查询检索”，时间线却显示 `Searching: 检索上海恒信置业有限公司 股东未实缴出资 补足责任`（截图 06c/06f）。这一行取自 Agent 自述的 `description`（`RunView.tsx` `buildSteps` 的 `agent.tool_started` 分支），不是实际发出的内容，还夹着英文。律师会以为当事人名称已经发出去了。
   - **P0-B 确认卡主行展示原文。** 卡片“会做什么”一栏是带当事人名称的原文（`card.title`），改写后的查询反而放在下面的小框里，也没有差异高亮。主按钮发的是改写稿，眼睛先看到的却是原文，二者矛盾。
   - **P0-C 同一事项的第二个任务先排队、后失败**，界面显示“本事项已有运行中的任务（G0：同一事项同时只运行一个任务）”。文案来自 `packages/kap-host/src/main.ts:160`，原样透传到 `run.failed`。
   - **P0-D 模型服务持续出错时只显示“正在处理…”**。原因是 `agent.error` 被归入“处理细节”（默认收起），另外没有重试状态，也没有静默看门狗。
   - **P0-E 场景开始面板右侧被裁切，主按钮“开始整理”只露出一半**（截图 02）。原因是 `styles.css:452` 的 `.ss { min-width: min(560px, 80vw) }` 放进了 560px 宽的 `.modal`，加上内边距后溢出 36px 以上。
   - **P0-F 确认卡或提问卡可能落在视线外，离开页面后也没有任何提醒。** 过程事件通道（todo、子任务、笔记）接入后，卡片会被继续往下推，超时后“Agent 跳过了这一步”。10-13 P1-9 因此升为 P0。
3. **执行态信息架构需要随“过程事件通道”一起重排。** 定位不变：中栏是“对话 + 律师层时间线 + 底部固定的待办坞（确认卡、提问卡、追问）”；右栏是“进度 → 交付件”自动切换。新增阶段行、工作清单、子任务、后台任务、重试与压缩提示，按“待你处理 > 出错/重试 > 当前阶段 > 流式草稿 > 子任务 > 压缩 > 细节”的顺序排优先级。完整规格见第 4 节。
4. **隐私体验从“确认”转向“可见”。** 建议用三件事替代更多确认卡：
   - 事项头上一个“保护状态”胶囊；
   - 发起前一行“会发给 AI：约 3,200 字 · 6 处个人信息换成代号”，可展开成**发送视图**：代号用胶囊显示，悬停还原，并支持“选中漏掉的名字 → 加入当事人名单”；
   - 事后的数据去向卡。
   典型 L2 任务的确认卡目标 ≤ 1 张。第 3 节给出线框与接口。
5. **自动更新横幅方向对（不强制、让律师选时机），但有 6 处要改。** 绿色表示“成功”，不适合用来提示待办操作；“发布签名核验”是术语；在执行态顶部会挤压三栏、和确认卡抢注意力；有任务在运行时“现在重启”会打断任务；每次收到状态事件都会重新弹出；签名被拒时用红色 `role=alert` 显示原始消息，会吓到律师。改法见 §2.12。
6. **历史 Astra Demo 还有 8 项值得吸收，目前未吸收**：
   - “继续工作”列表与状态胶囊；
   - 工作台顶部的“协议条”和“预览交付包”；
   - 成果页右侧的**质量检查清单**（勾选只记录人工核对，不代表系统验证）；
   - 材料的“我方 / 对方 / 参考”用途与页码；
   - “材料不齐也可先建立底稿”；
   - 一键虚构示例与示例事项；
   - 任务快照显示方法版本；
   - 文书“纸面”排版。
   **明确不吸收**：四步抽屉与提示词全文编辑、律师端 MCP 配置、客户端 Skill JSON 导入导出、36 个 `scene-*` 派生技能、英文大写眉题、智合式 36 场景分类。理由见第 5 节。
7. **对比度**：实算有 4 类文字色不达 AA，包括次级文字 #888（3.40–3.54:1）、Kimi 蓝链接（3.69–3.84:1）、“试用”标签（3.34:1）、禁用主按钮（3.36:1）；另有 2 类非文本控件不达 3:1，即输入框边框 1.27:1 和焦点边框 1.73:1。修正值见第 6 节，改动集中在令牌文件，约半天。
8. **实施**：第 7 节共 34 条。前 15 条（7 条 P0 加 8 条首日关键 P1）合计约 **128 小时**，前端为主，其中约 28 小时需要内核或宿主配合（同事项忙预检、重试事件、发送稿回写、`runs.list_recent`、`materials.send_preview`）；建议分两周完成，第 1 周先清 P0。

## 3. 隐私与安全：可感知、不打扰

### 3.1 设计立场

**海外同行的常见做法**（以下据各家公开资料与公开演示整理，具体界面以实测为准）：
- Harvey 和 Legora 主要靠合同（不训练、零保留）、工作区隔离、管理员策略。律师日常界面上**几乎没有逐次确认**，安全感来自“品牌承诺 + 管理控制台”。
- M365 Copilot 的做法是把**敏感度标签**带进对话：引用的文件显示标签，回答继承最高标签，用户全程看得到但不用操作。

**本产品的差异化**：发送前确定性令牌化、改写后检索，比靠合同更硬，但这只是机制，律师感知不到。所以设计目标不是增加确认，而是**让已经发生的保护被看见**。原则如下：

| 原则 | 落地 |
|---|---|
| 默认安全 | 主按钮永远是最安全、又能让任务继续的选项；律所策略允许时，“本任务内同类检索改写后自动发出”默认勾上 |
| 看得见，不打断 | 保护动作在三处“被看见”：事项头的**保护状态胶囊**（常显）、发起前的**一行去向说明 + 发送视图**（可展开）、事后的**数据去向卡** |
| 只为真正的决策打断 | 确认卡只用于：会把当事人信息发到新去向、发原图、访问白名单外的网站、跨事项读取、超预算。10-13 §3.2 的分级表继续有效 |
| 识别漏了，律师一步就能补 | 发送视图里“选中文字 → 加入当事人名单”，下一次发送前生效（应对 S8 召回不足的现实） |
| 可度量 | 埋点只记次数，不记内容：每任务确认卡数（目标中位数 ≤ 1）、改写后检索采用率、发送视图展开率、“加入当事人名单”次数 |

## 4. 执行态（RunView）过程信息规格

过程事件通道链路：宿主 → 内核 → `runs.interactions.progress`。本节给出它在界面上的布局、组件、空态、文案与优先级，并把新问题 1（同事项第二个任务失败）、新问题 2（模型持续出错）纳入同一套呈现。

### 4.1 前端期望的数据形状（供内核与宿主对齐）

```ts
// runs.interactions 返回值新增 progress（内存态，不落账本；与 live_text 同一轮询）
progress?: {
  phase: "reading" | "planning" | "working" | "waiting" | "writing" | "retrying" | "finishing";
  phase_text?: string;              // 宿主给出的律师层短句（≤ 20 字），例如“对照审查要点 3/5”；缺省时前端按 phase 映射
  heartbeat_at: string;             // 宿主最近一次心跳（模型流式字节、工具进展都算），用于静默看门狗
  todo: { id: string; text: string; status: "pending" | "in_progress" | "done" | "skipped" }[];   // TodoList / SetTodoList
  subagents: { id: string; label: string; status: "running" | "done" | "failed"; started_at: string; ended_at?: string }[];
  tasks: { id: string; label: string; kind: "compute" | "background"; status: "queued" | "running" | "done" | "failed"; position?: number }[];
  notes: { id: string; level: "info" | "warn" | "error"; code: NoteCode; at: string;
           retry?: { attempt: number; max: number; next_at?: string } }[];          // 只给 code 与数字，文案由前端映射
  compaction?: { count: number; last_at: string } | null;
}
type NoteCode = "model_unavailable" | "model_rate_limited" | "model_timeout" | "seat_or_license" | "quota_exhausted"
              | "tls_check_failed" | "search_unavailable" | "matter_busy" | "kernel_restarting" | "budget_near";
```

约束：
- `todo.text`、`subagents.label` 来自模型，可能含代号，前端统一走 `restoreTokens`。
- `notes` **不带自由文本**，避免把上游错误原文（可能含请求片段）带到界面。

**宿主与内核侧配合（新问题 2）**
- 宿主在模型请求失败时按指数退避重试（建议 5 次，2–30 秒），每次都写一条 `notes{code, retry}` 并刷新 `heartbeat_at`。
- 超过上限，或累计 3 分钟不可用时，以 `partial`（有产出）或 `paused`（无产出）结束，`reason` 用同一个 code。
- `agent.error` 中属于模型或服务类的，提升为律师层步骤，文案同上表。
- 前端看门狗只是兜底：宿主不报心跳也能提示，但不替代宿主上报。

### 4.5 同事项并发（新问题 1）的处理

现状：`kap-host/src/main.ts:160` 在受理之后才发现冲突，抛出 `RuntimeError("conflict", "本事项已有运行中的任务（G0：……）")`，界面显示为一次失败的任务，文案带 G0。

| 层 | 改法 |
|---|---|
| 内核受理前预检 | `runs.estimate` 与 `runs.start` 先查本事项有没有活动任务（排队、运行、等待中）。有则返回 `matter_busy: { run_id, title, status }`，**不受理** |
| 宿主兜底 | 保留宿主侧强制。冲突码统一为 `matter_busy`，内核映射为任务状态 `blocked`（不是 `failed`），文案走 `RUN_NOTICE` |
| 推荐（G0 末可做）：事项内排队 | 内核按事项维护 FIFO：第二个任务状态为 `queued_matter`，前一个结束后自动开始；可取消。状态胶囊“排队中：等本事项上一个任务结束”。这样律师可以连续发起“整理案卷 → 金额测算” |
| 界面（预检命中时） | 开始面板、发起确认、首页输入框（选中该事项时）、执行态追问，都在按钮上方显示一行信息条：“本事项有一个任务正在进行：『股权转让协议审查』（等你确认）。” 按钮改为 **[排在它后面，自动开始]**（主；未实现排队时改为置灰，并写“它结束后才能开始”）· [去看那个任务] |
| 追问 | 上一轮结束前，追问框显示“上一轮还在进行，结束后可以追问”，或者直接作为“补充要求”发给正在运行的会话（见 4.7） |
| 失败兜底文案 | 万一仍以失败结束：“没有开始：同一事项一次只能运行一个任务。[等它结束后重新发起] [去看进行中的任务]”。`labels.ts` 新增 `FAILURE_LABELS`，覆盖 `matter_busy`、`model_unavailable` 等，`retry-card` 不再原样显示 `terminal_reason` |
