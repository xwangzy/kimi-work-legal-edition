## 1. Electron 官方安全清单、Fuses（熔断）与 ASAR Integrity

### 1.0 结论先行

1. 官方安全清单共 20 条。其中第 2（远程内容不开 Node 集成，5.0.0 起默认）、3（上下文隔离，12.0.0 起默认）、4（进程沙箱，20.0.0 起默认）、6/8/9/10/11 是 Electron 默认值——发行前要做的是“确认没被改坏”；第 5、7、13、14、15、17、18、19、20 条默认不生效，必须自己写代码或配置。
2. Fuses 是 Electron 二进制里的“开关位”，在打包时、签名之前翻转，之后由操作系统的代码签名校验保证不被改回去。**所以熔断必须配合代码签名才有意义。**
3. 44-x-y 分支的熔断默认值（`build/fuses/fuses.json5`）：RunAsNode=开、EnableCookieEncryption=关、EnableNodeOptionsEnvironmentVariable=开、EnableNodeCliInspectArguments=开、EnableEmbeddedAsarIntegrityValidation=关、OnlyLoadAppFromAsar=关、LoadBrowserProcessSpecificV8Snapshot=关、GrantFileProtocolExtraPrivileges=开、WasmTrapHandlers=开。44 分支与 main 分支 fuses 文档逐字一致。
4. 官方文档对各熔断给出的倾向（按原文措辞）：RunAsNode——不用 `ELECTRON_RUN_AS_NODE` 的应用“would want to disable”；NodeOptions、NodeCliInspect——“Most apps can safely disable”；EmbeddedAsarIntegrityValidation、CookieEncryption——“Most apps can safely enable”；OnlyLoadAppFromAsar——与 ASAR 完整性一起开才能保证“不可能加载未校验的代码”；GrantFileProtocolExtraPrivileges——不用 `file://` 提供页面就“should disable”；WasmTrapHandlers——文档只说明关掉的代价，没有建议关闭。
5. ASAR 完整性：macOS 自 `electron>=16.0.0`、Windows 自 `electron>=30.0.0` 支持。头部哈希在 macOS 存于 `Info.plist` 的 `ElectronAsarIntegrity` 字典，在 Windows 存于 exe 的资源节（类型 `Integrity`、名称 `ElectronAsar`）。哈希不匹配或缺失时应用会被强制终止。

### 1.1 官方安全清单 20 条（electronjs.org/docs/latest/tutorial/security）

总原则（原文要点）：Electron 不是浏览器，展示不可信来源的任意内容是 Electron “不打算处理”的严重风险；绝不能在开启 Node 集成的情况下加载并执行远程代码；展示远程内容应使用 `<webview>` 或 `WebContentsView`，并关闭 `nodeIntegration`、开启 `contextIsolation`。安全警告只在二进制名为 Electron（即开发时）才打印，可用 `ELECTRON_ENABLE_SECURITY_WARNINGS` / `ELECTRON_DISABLE_SECURITY_WARNINGS` 强制开关。

| # | 建议 | 默认是否已满足 | 怎么做（官方示例的做法） | 对用户体验的影响 |
|---|---|---|---|---|
| 1 | 只加载安全内容：外部资源用 HTTPS / WSS / FTPS | 否 | `loadURL('https://…')`；`<script>`、`<link>` 用 https | 无感；云端必须有有效 TLS 证书 |
| 2 | 加载远程内容的渲染器不开 Node 集成 | 是（5.0.0 起） | 不设 `nodeIntegration: true`；需要能力时由 preload 通过 `contextBridge` 暴露受限 API | 无感 |
| 3 | 所有渲染器开启上下文隔离 | 是（12.0.0 起） | 不设 `contextIsolation: false`；注意“关闭上下文隔离（如 `nodeIntegration: true`）也会关闭进程沙箱” | 无感 |
| 4 | 开启进程沙箱 | 是（20.0.0 起） | 可用 `app.enableSandbox()` 全局强制；不要在任何非沙箱进程（包括主进程）里加载、读取、处理不可信内容 | preload 在沙箱下只能用受限的 Node 能力，需按此设计 |

| 6 | 不要关闭 `webSecurity` | 是 | 不设 `webSecurity: false`；它会关掉同源策略并把 `allowRunningInsecureContent` 置真 | 无感 |
| 7 | 定义内容安全策略（CSP），用严格规则如 `script-src 'self'` | 否 | 用 `session.defaultSession.webRequest.onHeadersReceived` 注入 `Content-Security-Policy` 响应头，或页面里写 `<meta http-equiv="Content-Security-Policy">`（`file://` 页面只能用 meta） | 规则写严后内联脚本、第三方脚本会被拦，需开发期调通 |

| 10 | 不要用 `enableBlinkFeatures` | 是 | 不设该项 | 无感 |
| 11 | `<webview>` 不要用 `allowpopups` | 是 | 不加该属性 | 无感 |
| 12 | 创建 `<webview>` 前校验其选项与参数 | 否 | 在 `will-attach-webview` 里删掉 `preload`、强制 `nodeIntegration=false`、校验 `src` | 无感 |
| 13 | 禁止或限制导航 | 否 | `app.on('web-contents-created')` → `contents.on('will-navigate')` 中用 `new URL()` 解析、按 `origin` 比对，不符则 `event.preventDefault()`。官方特别提醒：`startsWith('https://example.com')` 会放过 `https://example.com.attacker.com` | 无感；拦错会导致站内链接点不动 |
| 14 | 禁止或限制新建窗口 | 否 | `contents.setWindowOpenHandler()` 一律 `{ action: 'deny' }`，确有需要的外链交给系统浏览器 | 外链改在系统浏览器打开 |
| 15 | 不要对不可信内容调用 `shell.openExternal` | 否 | 只对经过校验（协议白名单如 https、主机白名单）的 URL 调用；“用于不可信内容时可被利用来执行任意命令” | 无感 |

### 1.2 Electron Fuses（electronjs.org/docs/latest/tutorial/fuses）

**机制**：熔断是 Electron 二进制里一段“保险丝线”（以固定哨兵串 `dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX` 定位，之后是版本字节、长度字节、每个熔断一个字节：`0x30` 关、`0x31` 开、`r` 已移除）。官方原文：因为在**签名之前**的打包阶段翻转，所以由操作系统层面的代码签名校验（macOS Gatekeeper、Windows AppLocker）负责保证这些位不被改回。可用 `npx @electron/fuses read --app <应用路径>` 读取已打包应用的熔断状态。

| 熔断（@electron/fuses 名） | 44 默认 | 含义 | 官方倾向 | 对本产品的影响与前提 |
|---|---|---|---|---|
| `RunAsNode` | 开 | 是否响应 `ELECTRON_RUN_AS_NODE` 环境变量。关闭后 `child_process.fork` 会抛错（它依赖这个变量） | 不使用该变量的应用“会想要关闭它”，以防一类“就地取材（living off the land）”攻击；需要独立 Node 进程的改用 `utilityProcess` | **前提**：代码里不能再依赖 `fork`，也不能用 `spawn(process.execPath)` 加 `ELECTRON_RUN_AS_NODE=1` 起 Node 子进程（关掉后这条路同样失效，属于按文档的推论）；需改用 `utilityProcess`。用户无感 |
| `EnableCookieEncryption` | 关 | 是否用操作系统密钥加密磁盘上的 Cookie 库（Chromium 默认把 Cookie 值明文存在 SQLite）。单向：开启后旧 Cookie 写入时加密，之后再关会让 Cookie 库损坏不可用 | “大多数应用可以安全开启” | **前提**：macOS 上它与 `safeStorage` 用同样的钥匙串访问，必须正确代码签名，否则表现不一致。一旦上线开启就不能回退 |
| `EnableNodeOptionsEnvironmentVariable` | 开 | 是否响应 `NODE_OPTIONS` 与 `NODE_EXTRA_CA_CERTS` 环境变量 | “大多数应用可以安全关闭” | 关闭后，用户/企业不能再靠 `NODE_EXTRA_CA_CERTS` 给主进程追加根证书（律所内网有 TLS 中间人代理时需另想办法），属于按文档的推论 |
| `EnableNodeCliInspectArguments` | 开 | 是否响应 `--inspect`、`--inspect-brk` 等参数；关闭后 `SIGUSR1` 信号也不会开启主进程调试器 | “大多数应用可以安全关闭” | 发行包无法再附加调试器排障；开发构建不翻转即可 |
| `EnableEmbeddedAsarIntegrityValidation` | 关 | 在 macOS 与 Windows 上加载 `app.asar` 时校验其内容；“对性能影响很小，但可能略微减慢从 asar 读文件” | “大多数应用可以安全开启” | **前提**：打包工具要写入头部哈希（见 1.3）；asar 被改动则应用直接终止 |
| `OnlyLoadAppFromAsar` | 关 | 默认按 `app.asar` → `app` → `default_app.asar` 顺序找应用代码；开启后只找 `app.asar` | 与上一项**同时开启**，才能“使加载未经校验的代码成为不可能” | 需确认产品代码全部在 `app.asar`（`asarUnpack` 出来的原生模块等仍可正常加载，属另一机制，未查到官方对 unpacked 文件是否校验的说明） |
| `LoadBrowserProcessSpecificV8Snapshot` | 关 | 开启后主进程使用 `browser_v8_context_snapshot.bin`，其余进程用原快照；可避免渲染器使用带 `nodeIntegration` 的快照 | 未给出一般性建议（仅在使用自定义 V8 快照时有意义） | 未使用自定义快照可不动 |
| `GrantFileProtocolExtraPrivileges` | 开 | `file://` 页面是否获得超出浏览器的特权：可 `fetch` 其他 `file://` 资源、可用 Service Worker、对同为 `file://` 的子框架拥有通用访问权（不论沙箱设置）——官方注明此列表“不完整” | “如果你不从 `file://` 提供页面，就应该关闭它” | **前提**：先按清单第 18 条把页面改成自定义协议；否则关闭后 `file://` 页面里的 `fetch` 等会失败 |
| `WasmTrapHandlers` | 开 | V8 用信号处理器捕获 WebAssembly 越界访问（在 WASM 堆两侧各放 8GB 保护区）。仅 64 位 x86_64（Linux/macOS/Windows）与 aarch64（Linux/macOS）支持 | 文档只列出关闭的代价：编译更慢、模块更大、每次内存访问前多一次比较跳转，运行时开销“显著”；**未建议关闭** | 保持默认（开）。若产品用到 WASM（如本地 OCR、PDF 处理），关掉会明显变慢 |

### 1.3 ASAR Integrity（electronjs.org/docs/latest/tutorial/asar-integrity）

- **版本支持**：macOS 自 `electron>=16.0.0`；Windows 自 `electron>=30.0.0`。生成 `app.asar` 的工具须支持完整性：`asar@3.1.0` 起支持，迁移后的 `@electron/asar` 所有版本都支持。
- **原理**：每个 ASAR 的 JSON 头里有 `integrity` 对象（`algorithm: SHA256`、整档哈希 `hash`、`blockSize`（示例 1024）、每块哈希数组 `blocks`）。另外，打包时要把**整个 ASAR 头的哈希**写到应用外层；运行时 Electron 校验头部哈希，**缺失或不匹配就强制终止应用**。
- **开启方式**：打开熔断 `EnableEmbeddedAsarIntegrityValidation`，并“通常也要”打开 `OnlyLoadAppFromAsar`，否则可借应用代码搜索路径绕过校验。
- **哈希存放位置**：
  - macOS：`Info.plist` 中的 `ElectronAsarIntegrity` 字典，键为 `Resources/app.asar`，含 `algorithm`（目前仅 `SHA256`）与 `hash`（对 ASAR 头的哈希，可用 `@electron/asar` 的 `getRawHeader` 结果计算）。
  - Windows：exe 的 Win32 资源，类型 `Integrity`、名称 `ElectronAsar`，值为 JSON 数组：`[{"file":"resources\\app.asar","alg":"sha256","value":"…"}]`。实现示例见 `electron/packager` 的 `src/resedit.ts`。
- **工具链**：Electron Forge（≥7.4.0）与 `@electron/packager`（≥18.3.1）在启用 asar 时自动完成；其他构建系统须自行写入（electron-builder 的做法见第 2 节）。
- **Mac App Store**：完全支持并建议作为最佳实践。
- **对用户体验的影响**：正常无感；若 asar 被篡改（含杀毒软件、用户误改），应用启动即退出，无提示界面（文档只说“forcefully terminate”）。
- **与签名的关系**：头部哈希写在 `Info.plist`/exe 资源里，受代码签名保护——不签名则攻击者可同时改 asar 和哈希，完整性校验形同虚设（按 Fuses 文档“由 OS 代码签名校验保证”的推论）。

来源：
- https://www.electronjs.org/docs/latest/tutorial/asar-integrity
- https://github.com/electron/electron/blob/44-x-y/docs/tutorial/asar-integrity.md（44 分支与 main 分支逐字一致）

### 1.4 Electron 官方“代码签名”页中与发行直接相关的要点

- 官方结论：打算打包分发的 Electron 应用“应当签名”；Windows 和 macOS 都会阻止或警告未签名应用。
- macOS 发行两步：签名 + 上传 Apple 公证。前提：加入 Apple Developer Program（年费）、安装 Xcode（需要 Mac）、生成并安装签名证书。
- **依赖签名才能正常工作的 macOS API**（官方列举）：`safeStorage`（未签名或 ad-hoc 签名时，macOS 可能认不出两次构建是“同一个应用”，每次更新后钥匙串都会再次弹窗要授权）、`app.setLoginItemSettings()`（未打包、未签名、未公证时可能静默注册失败）、`cookieEncryption` 熔断（同 safeStorage）、`autoUpdater`（Squirrel.Mac 要求应用已签名，否则自动更新完全不可用）。
- Windows：官方把 **Azure Artifact Signing（原 Azure Trusted Signing）** 列为首选，称其为“Windows 上最便宜的签名方式，并能消除 SmartScreen 警告”，但“目前只对部分国家的开发者开放”，以 Microsoft 快速入门的前提条件为准。非 Windows 机器可用 `jsign --storetype TRUSTEDSIGNING` 调用。
- 传统证书：文档称“自 2023 年 6 月起，微软要求用 EV 代码签名证书签名……更便宜的普通（OV）证书不再带来好处，Windows 会把应用当作完全未签名”，且 EV 证书须存放于符合 FIPS 140 Level 2、Common Criteria EAL 4+ 或同等的硬件模块，不能直接下载到 CI；许多 CA 提供云签名（Electron 自家应用用 DigiCert KeyLocker）。
  - **注意**：这段关于“OV 证书等同未签名”的说法是 Electron 文档的表述，与微软自己的 SmartScreen 文档口径不完全一致（微软文档见第 3 节）；以微软文档为准。

来源：
- https://www.electronjs.org/docs/latest/tutorial/code-signing
- https://github.com/electron/electron/blob/main/docs/tutorial/code-signing.md

## 2. electron-builder：熔断、Windows 签名、macOS 签名与公证、electron-updater 校验

> 版本口径：本产品 `platform/apps/desktop/package.json` 锁定 `electron-builder 26.15.3`、`electron-updater 6.8.9`。npm 上 electron-builder 当前 `latest` 为 26.18.0，`next` 为 27.0.0-alpha.15；GitHub master 分支文档已按 v27 写。**下文以 `electron-builder@26.15.3` 标签下的文档和源码为准**，v27 才有的内容单独标注。

### 2.0 结论先行

1. `electronFuses` 配置项（26.15.3）直接映射 `@electron/fuses`，**只支持 8 个熔断 + `resetAdHocDarwinSignature`，没有 `wasmTrapHandlers`**（源码 `generateFuseConfig` 中无此项）；要动 WasmTrapHandlers 只能在 `afterPack` 钩子里调 `context.packager.addElectronFuses()`。源码注释写明“熔断必须在签名之前翻转”，electron-builder 在翻转后立即签名。
2. electron-builder 默认就会计算 ASAR 完整性哈希并写入：Windows 写进 exe 资源（`addWinAsarIntegrity`），macOS 写进 `Info.plist`（`createMacApp`）；只有设 `disableAsarIntegrity: true` 才跳过。但**运行时是否校验取决于熔断 `enableEmbeddedAsarIntegrityValidation`**，默认关。
3. Windows：`win.signtoolOptions`（传统 signtool / pfx / EV）与 `win.azureSignOptions`（Azure Trusted Signing，现名 Artifact Signing）二选一；两者同时给时以 Azure 为准。Azure 路径通过 PowerShell 安装并调用 `TrustedSigning` 模块的 `Invoke-TrustedSigning`，**构建机需要 PowerShell**（源码事实；官方未写是否支持 macOS 上的 pwsh，未查到官方来源）。
4. macOS：`hardenedRuntime` 默认 `true`；找不到证书时**跳过签名、不会自动 ad-hoc**；没有自备 entitlements 文件时，使用内置模板（`allow-jit`、`allow-unsigned-executable-memory`、`disable-library-validation` 三项都为 true）。只要设置了公证环境变量（三种之一）就自动用 `notarytool` 公证 `.app` 并装订（staple），`notarize: false` 才跳过。DMG 默认不签名（`dmg.sign` 默认 false，官方注释称签 DMG“不是必需的，并会与公证要求一起导致不必要的错误”）。
5. electron-updater：所有平台都对下载的安装包做 `latest*.yml` 中的 **sha512 校验**；Windows 另用 PowerShell `Get-AuthenticodeSignature` 校验新安装包的 Authenticode 签名并比对 `publisherName`——**但如果打包时没签名（`app-update.yml` 里没有 `publisherName`），这一步直接跳过**；macOS 靠 Squirrel.Mac，应用必须已签名才能自动更新。`latest.yml` 本身在 v26 不签名，v27 才引入 Ed25519 签名的更新清单。

### 2.1 `electronFuses`（Adding Electron Fuses）

- **做什么**：打包时按配置翻转 Electron 熔断（底层就是官方 `@electron/fuses`）。
- **怎么配**（官方示例，原文注明“true/false 只是示例，按自己需要定”）：

```jsonc
// electron-builder 配置
"electronFuses": {
  "runAsNode": false,
  "enableCookieEncryption": true,
  "enableNodeOptionsEnvironmentVariable": false,
  "enableNodeCliInspectArguments": false,
  "enableEmbeddedAsarIntegrityValidation": true,
  "onlyLoadAppFromAsar": true,
  "loadBrowserProcessSpecificV8Snapshot": false,
  "grantFileProtocolExtraPrivileges": false
}
```

- **可选写法**：仍可在 `afterPack` 钩子里调用 `context.packager.addElectronFuses(context, fuseConfig)`，可传完整 `FuseConfig`（例如 `strictlyRequireAllFuses: true`，要求列全所有熔断，新熔断出现时构建报错提醒）。
- **`resetAdHocDarwinSignature`**：源码注释称“由于 electron-builder 在翻转熔断后直接签名，这一项应当不需要”。
- **只写了的项才会翻转**：源码逐项判断 `!= null` 才写入，注释说明这是为了避免旧版 Electron 报“fuse wire 不够长”。
- **验证**：`npx @electron/fuses read --app <打包产物>`。
- **前提**：Mac 通用包（universal）构建时，x64/arm64 中间产物会以 `disableAsarIntegrity`、`disableFuses`、不签名方式先打，最后合并时再处理（源码 `macPackager.ts`）；本产品只出 arm64，不涉及。
- **用户体验**：同第 1.2 节各熔断。
- **来源**：
  - https://www.electron.build/tutorials/adding-electron-fuses （仓库文件 `website/docs/tutorials/adding-electron-fuses.md`，标签 `electron-builder@26.15.3`）
  - 源码：https://github.com/electron-userland/electron-builder/blob/electron-builder@26.15.3/packages/app-builder-lib/src/platformPackager.ts （`doAddElectronFuses`、`generateFuseConfig`）与 `src/configuration.ts`（`FuseOptionsV1`、`disableAsarIntegrity`）

### 2.2 Windows 签名：`win.signtoolOptions` 与 `win.azureSignOptions`

**官方文档要点（code-signing-win）**
- 证书两类：EV 代码签名证书、普通代码签名证书，“都能用于自动更新”。普通证书安装时会有警告，“在足够多用户安装、建立信任后消失”；EV 证书信任更高、立即无警告，但绑定实体 USB 硬件、不能导出。用 EV 时需在 win 配置里给 `certificateSubjectName`。在 Linux/Mac 上用 EV 签 Windows 包，见“Unix 上签 Windows 应用”教程。
- Windows 默认**双签**（SHA1 + SHA256，`signingHashAlgorithms` 默认 `['sha1','sha256']`；AppX 恒用 sha256）。
- 环境变量：`WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD`（缺省回落到 `CSC_LINK` / `CSC_KEY_PASSWORD`）；Windows 环境变量值上限 8192 字符，base64 证书超长时导出时不要带证书链。

**`win.signtoolOptions` 主要字段（源码 `options/winOptions.ts` 注释）**

| 字段 | 含义 / 默认 |
|---|---|
| `certificateFile` / `certificatePassword` | pfx 路径与密码；官方建议优先用 `CSC_LINK`/`WIN_CSC_LINK` 环境变量 |
| `certificateSubjectName` | 证书“颁发给”主题名；**仅 EV 需要**，只在 Windows（或 Mac 上的 Parallels Win10 虚机）可用 |
| `certificateSha1` | 证书 SHA1 指纹，多张证书都符合时用来指定；同样只在 Windows 可用 |
| `additionalCertificateFile` | 加入签名块的附加证书 |
| `rfc3161TimeStampServer` / `timeStampServer` | 时间戳服务器，默认均为 `http://timestamp.digicert.com` |
| `signingHashAlgorithms` | 默认 `['sha1','sha256']` |
| `publisherName` | 证书里的发布者名，可给多个；**缺省取签名证书的 CN**；electron-updater 用它校验更新包 |
| `sign` | 自定义签名函数或模块路径（接云签名、HSM 厂商工具时用） |

**`win.azureSignOptions`（Azure Trusted Signing / Artifact Signing）**

| 字段 | 含义 / 默认 |
|---|---|
| `publisherName` | **必须与所用证书的 CN 完全一致** |
| `endpoint` | 创建证书时选的区域端点（须与签名账户、证书配置文件所在区域一致） |
| `certificateProfileName` | 签名账户下的证书配置文件名 |
| `codeSigningAccountName` | Trusted Signing 账户名（不是应用注册的名称） |
| `fileDigest` | 默认 `SHA256` |
| `timestampRfc3161` | 默认 `http://timestamp.acs.microsoft.com` |
| `timestampDigest` | 默认 `SHA256` |
| 其他字段 | 原样传给 `Invoke-TrustedSigning` PowerShell 模块 |

- 认证用环境变量（由 `Invoke-TrustedSigning` 直接读取，electron-builder 不解析）：最简“服务主体 + 密钥”方式只需 `AZURE_TENANT_ID`、`AZURE_CLIENT_ID`、`AZURE_CLIENT_SECRET`；其余方式见 Azure.Identity `EnvironmentCredential`。
- 前提：先按微软快速入门建 Trusted Signing（Artifact Signing）账户与证书配置文件，再在 Entra ID 建“应用注册”并创建密钥、授予签名角色（微软侧条件见第 3 节）。
- 源码事实：`windowsSignAzureManager.ts` 先 `Install-PackageProvider NuGet`，再 `Install-Module -Name TrustedSigning -MinimumVersion 0.5.0`，最后执行 `Invoke-TrustedSigning`——构建机需能访问 PowerShell Gallery。
- `signtoolOptions` 与 `azureSignOptions` 不能同时用；同时给时“签名将默认走 Azure Trusted Signing”。
- 其他相关开关：`signExecutable`（只关签名、保留改资源）、`signAndEditExecutable`（连资源编辑一起关）、`signExts`（额外要签的文件扩展名，如 `.dll`）。
- **用户体验**：签名后安装/运行时 UAC 与 SmartScreen 显示发布者名；未签名时显示“未知发布者”（SmartScreen 行为见第 3 节）。
- **来源**：
  - https://www.electron.build/code-signing-win （文件 `website/docs/features/code-signing/code-signing-win.md`，标签 `electron-builder@26.15.3`）
  - https://www.electron.build/code-signing （`features/code-signing/code-signing.md`）
  - 源码：https://github.com/electron-userland/electron-builder/blob/electron-builder@26.15.3/packages/app-builder-lib/src/options/winOptions.ts 、`src/codeSign/windowsSignAzureManager.ts`

### 2.3 macOS 签名、Hardened Runtime、entitlements 与公证

**签名身份（`mac.identity`）**

| 取值 | 行为 |
|---|---|
| 不设（默认） | 在钥匙串里找有效证书；找不到则**所有架构都跳过签名**，不会自动 ad-hoc |
| `null` | 完全跳过签名 |
| `"-"` | ad-hoc 签名（无 Team ID）；在默认 `hardenedRuntime: true` 下须加 `disable-library-validation`，否则因 Electron 预编译框架带 Apple 的 Team ID 而启动失败 |
| 证书名 | 用指定证书 |

- 直接分发（DMG/ZIP）用 **Developer ID Application** 证书；PKG 另需 Developer ID Installer。Gatekeeper 只认 Apple 签发的证书。
- CI 用 `CSC_LINK`（base64 的 .p12）+ `CSC_KEY_PASSWORD` 导入临时钥匙串。

**Hardened Runtime 与 entitlements（`mac.hardenedRuntime`、`mac.entitlements`、`mac.entitlementsInherit`）**
- `hardenedRuntime` 默认 `true`；公证要求必须开启。
- `entitlements`：存在 `build/entitlements.mac.plist` 就用它（官方推荐做法）；**都没有时，源码回落到内置模板 `templates/entitlements.mac.plist`**，其内容为：

```xml
<key>com.apple.security.cs.allow-jit</key><true/>
<key>com.apple.security.cs.allow-unsigned-executable-memory</key><true/>
<key>com.apple.security.cs.disable-library-validation</key><true/>
```

- `entitlementsInherit`：子进程（Helper、渲染器等）使用，存在 `build/entitlements.mac.inherit.plist` 就用它，否则同样回落内置模板。
- 官方提醒：“Electron 20+ 的 arm64 构建若没设 `com.apple.security.cs.allow-jit` 等正确 entitlements，应用可能崩溃。”
- 官方公证页“Electron 至少需要”的 entitlements：`allow-jit` 与 `allow-unsigned-executable-memory`；常见 entitlements 表中 `allow-unsigned-executable-memory` 标为“某些 Electron 版本需要”，`disable-library-validation` 标为“加载第三方框架或插件时需要”。（与 Apple 对这三项含义的说明见第 4 节。）
- 其他：`gatekeeperAssess` 默认 false、`strictVerify` 默认 true、`preAutoEntitlements` 默认 true、`timestamp`（时间戳服务器）、`signIgnore`、`binaries`（额外要签的二进制）、`additionalArguments`（给个别文件加 `--deep` 之类，官方说不宜整包用）。

**公证（`mac.notarize`）**
- 26.15.3 中 `notarize` 是布尔值：**设置了以下任一组环境变量就自动公证**，`notarize: false` 显式跳过：
  1. `APPLE_API_KEY`、`APPLE_API_KEY_ID`、`APPLE_API_ISSUER`（App Store Connect API 密钥；官方称“出于安全原因推荐”，适合 CI，不过期、不需要双重认证）
  2. `APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID`（App 专用密码，不要用 Apple ID 本身的密码）
  3. `APPLE_KEYCHAIN`、`APPLE_KEYCHAIN_PROFILE`（钥匙串里预存的凭据，多用于本地）
- 工具：源码固定用 `notarytool`（经 `@electron/notarize` 2.5.0）；公证对象是 `.app`，成功后自动装订票据（官方原文：装订后“即使没有网络连接，公证检查也能通过”）。
- 前提：Apple Developer Program 会员（文档写年费 99 美元）、Developer ID Application 证书、Hardened Runtime、正确的 entitlements、上述凭据之一。
- DMG：`dmg.sign` 默认 `false`。
- **用户体验**：签名 + 公证 + 装订后，首次打开只出现常规的“从互联网下载，确定打开吗”确认；缺任何一步则被 Gatekeeper 拦截（见第 4 节）。
- **来源**：
  - https://www.electron.build/code-signing-mac （`features/code-signing/code-signing-mac.md`）
  - https://www.electron.build/notarization （`features/code-signing/notarization.md`、`notarization.md`）
  - https://www.electron.build/mac
  - 源码：https://github.com/electron-userland/electron-builder/blob/electron-builder@26.15.3/packages/app-builder-lib/src/options/macOptions.ts 、`src/mac/MacTargetHelper.ts`（entitlements 回落与 `notarizeIfProvided`）、`templates/entitlements.mac.plist`、`packages/dmg-builder/src/dmg.ts`

### 2.4 electron-updater 的更新校验

| 平台 | 校验什么 | 怎么校验 | 失效条件 / 注意 |
|---|---|---|---|
| 全平台 | 下载的安装包完整性 | 与 `latest.yml` / `latest-mac.yml` 中的 `sha512` 比对 | v26 中清单本身不签名，只靠 HTTPS 与存储安全；v27（目前 alpha）新增“签名的更新清单”（Ed25519，发布时强制要求签名，清单被改或未签名则“fail closed”，但只保护**采用之后**发出的安装） |
| Windows（NSIS） | 新安装包的 Authenticode 签名与发布者 | `win.verifyUpdateCodeSignature` 默认 `true`；`NsisUpdater` 下载后用 PowerShell `Get-AuthenticodeSignature -LiteralPath` 取签名，要求 `Status` 为 Valid（0），再把签名证书 Subject 与 `app-update.yml` 中的 `publisherName` 比对：给的是完整 DN 就逐项比对，只给 CN 则只比 CN 并告警建议改成完整 DN；不匹配抛 `ERR_UPDATER_INVALID_SIGNATURE` | ① `app-update.yml` 里**没有 `publisherName`（即打包时未签名）或没有该文件时，直接跳过签名校验**；② PowerShell 版本过低（<3）或无法执行时只告警并跳过；③ `publisherName` 缺省取签名证书 CN，换证书（如 OV 换 Azure）时发布者名变化会导致老版本拒收新包，需在 `publisherName` 里同时列出新旧名称 |
| macOS | 新版本的代码签名 | 由 Electron 内置 `autoUpdater`（Squirrel.Mac）完成；electron-builder 文档：“macOS 应用必须签名，自动更新才能工作”；Electron 文档：“Squirrel.Mac 要求应用已签名，否则自动更新完全不可用” | 必须产出 `zip` 目标（默认 `dmg`+`zip`），否则生成不了 `latest-mac.yml` |

- 第 ③ 条中“换证书需列出新旧名称”是根据源码比对逻辑与 `publisherName` 可给多个名称的说明作出的推论。

## 3. 微软：Authenticode、SmartScreen 信誉、CA/B 论坛硬件密钥要求、Azure Artifact Signing

### 3.0 结论先行

1. **SmartScreen 现行口径（微软 2026 文档）：EV 证书不再绕过 SmartScreen。** 有效 OV/EV 签名的新程序首次下载仍会被标为“无法识别”，但会显示经验证的发布者名；随下载量积累信誉后提示消失，“没有确切阈值，可能需要数周、来自广泛用户的数百次干净安装”。未签名或自签名：显示“Windows 已保护你的电脑”，用户须点“仍要运行”，企业策略可完全禁止继续。**为了躲 SmartScreen 而多花钱买 EV“已不再合理”**（微软原文）。这与 electron-builder 文档“EV 立即信任”、Electron 文档“OV 等同未签名”的说法都不一致，以微软文档为准。
2. 信誉可以随**同一签名身份**延续到新版本；未签名文件每个新版本都从零开始。所以：每个版本都签、始终用同一签名身份、签名后不再改文件。
3. Windows 11 的“智能应用控制（Smart App Control）”可能取代 SmartScreen 应用信誉：**会阻止未签名且无正面信誉的文件执行**，且对所有可执行文件生效，不限于从网上下载的。
4. CA/B 论坛代码签名基线要求（CSBR，当前 3.11.0 版）：**自 2023-06-01 起，代码签名证书（不分 EV/OV）的订户私钥必须在符合至少 FIPS 140-2 Level 2 或 Common Criteria EAL 4+ 的硬件加密模块中生成、存储、使用**；可用方式包括硬件令牌、满足条件的云端 HSM（须开启全量访问日志）、或符合要求的签名服务。另：**2026-03-01 起签发的代码签名证书有效期不得超过 460 天**（此前为 39 个月）。
5. Azure Artifact Signing（原 Trusted Signing）：**公共信任（Public Trust）证书只对美国、加拿大、欧盟、英国、澳大利亚、新西兰、日本、韩国、新加坡、瑞士、挪威、以色列的组织开放；个人开发者必须在美国或加拿大**。中国内地、香港不在列表中（私有信任 Private Trust 证书不受地域限制，但私有信任不被公众 Windows 设备默认信任——此点为常识推断，未在本次抓取页面中找到原文）。不签发 EV 证书，且官方称“未来也不计划”。合规等级 FIPS 140-3 Level 3。身份验证 1～30 个工作日。

### 3.1 Authenticode

- **做什么**：微软的代码签名技术，标识软件发布者，并验证软件自签名发布后未被修改；通过把签名里的证书链到受信任根证书来验证发布者身份。签名嵌在文件的非执行部分，不改动可执行内容。
- **怎么配**：用 SignTool（或 electron-builder 的 `signtoolOptions` / `azureSignOptions`）对 exe、dll、安装包签名；应同时加时间戳（electron-builder 默认 DigiCert 时间戳，Azure 路径默认 `http://timestamp.acs.microsoft.com`）。
- **前提**：有 CA 签发的代码签名证书（私钥须在硬件模块中，见 3.3），或使用 Artifact Signing。
- **用户体验**：UAC 弹窗、文件属性“数字签名”页、SmartScreen 提示中都显示发布者名；未签名则显示“未知发布者”。
- **来源**：https://learn.microsoft.com/en-us/windows-hardware/drivers/install/authenticode （ms.date 2025-07-11；该页以驱动为例，但对 Authenticode 的定义通用）

### 3.2 SmartScreen 信誉（SmartScreen reputation for Windows app developers）

- **两类信号**：发布者信誉（是否签名、签名证书是否来自已知可信发布者）与文件哈希信誉（这个具体文件是否被用户下载且无恶意迹象）。任一为负面或未知都可能出警告；即使签名，新二进制在哈希或证书积累足够正面证据之前仍可能出警告。
- **各证书类型首次下载表现（官方表格）**：

| 方式 | 首次下载的 SmartScreen 表现 |
|---|---|
| Microsoft Store 分发 | 无警告（由微软证书覆盖，Store 应用会被微软重新签名） |
| 有效证书（OV/EV） | 警告：在信誉积累前标为“无法识别”，显示经验证的发布者名 |
| 未签名 | 警告“Windows 已保护你的电脑”，须点“仍要运行”；企业策略可完全禁止继续 |
| 自签名证书 | 与未签名相同 |

- **Artifact Signing 在该页的描述**：微软推荐的非 Store 分发签名服务；起价每月 9.99 美元；无需硬件令牌、可直接接 GitHub Actions / Azure DevOps；签发前要做身份验证；SmartScreen 信誉同样随下载量和行为逐步积累（**不是立即无警告**）。
- **官方的减少警告做法**：能上 Store 就上 Store；每个版本都签名；签名后不要改文件（视客户端配置可能破坏签名）；不要给潜在有害程序签名（证书会积累负面信誉）；保持签名身份一致（换证书影响发布者信任信号）；提前告知早期用户首次下载可能看到提示。
- **企业环境**：可能禁止绕过 SmartScreen；企业可从受信任内网位置分发而不受 SmartScreen 审查；企业 IT 管理员可通过 Microsoft Security Intelligence 门户提交文件复核以加速受管部署的信任。面向普通用户“不需要也没有机制”手工提交信誉复核。
- **Smart App Control**：见 3.0 第 3 条。
- **对本产品的含义**：律所客户多为受管 Windows 环境，首发阶段即便签名也可能出现“无法识别”提示；需要在安装指引中说明，并优先争取客户 IT 把安装包放到受信任内网位置或提交复核。
- **来源**：https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation （ms.date 2026-05-04，更新于 2026-08-17）

### 3.3 CA/Browser Forum：代码签名私钥须存于硬件模块（CSBR 6.2.7.4）

- **生效日与范围**：CSBR 生效日表：“自 2023 年 6 月 1 日起，对代码签名证书，CA 必须确保订户私钥在合适的硬件加密模块中生成、存储和使用”（6.2.7.4.2）。此前 EV 已有同类要求；2021-06-01 起签名服务（Signing Service）对非 EV 证书也须用 FIPS 140-2 Level 2 模块。
- **订户可选的方式（6.2.7.4.1，2023-06-01 起）**：CA 须取得订户的合同承诺，在单元形态认证达到**至少 FIPS 140-2 Level 2 或 Common Criteria EAL 4+** 的硬件加密模块中生成并保护私钥，方式三选一：① 自用合规硬件模块；② 云端密钥生成与保护方案（私钥的创建、存储、使用不出云端 HSM 的安全边界；管理私钥的订阅须记录所有访问、操作和配置变更日志）；③ 使用符合 6.2.7.3 的签名服务（签名服务须用至少 FIPS 140-2 Level 3 或 CC EAL 4+ 的模块）。
- **CA 的核验方式（6.2.7.4.2）**：CA 寄出预生成密钥的硬件模块；密钥证明（key attestation）；CA 指定的加密库 + 硬件组合；内外部 IT 审计；云端方案的配置报告；CA 认可的审计师见证生成；订户签署使用合规签名服务的协议。
- **有效期**：2026-03-01 起签发的代码签名证书有效期不得超过 460 天；之前签发的不得超过 39 个月（CSBR 6.3.2，3.10 版“Maximum Validity Reduction”，2025-11-07）。
- **对本产品的含义**：买传统证书（OV 或 EV）都拿不到可导出的 .pfx，只能用 USB 令牌或 CA 的云签名（如 DigiCert KeyLocker、SSL.com eSigner 等，以各 CA 官方说明为准），CI 签名要走云签名或自定义 `win.sign` 函数；证书每年多一点就要续，需排进运维日历。
- **来源**：
  - CSBR 当前版本（3.11.0）原文：https://github.com/cabforum/code-signing/blob/main/docs/CSBR.md （生效日表、6.2.7.3、6.2.7.4.1、6.2.7.4.2、6.3.2）
  - 论坛页面：https://cabforum.org/working-groups/code-signing/requirements/

## 4. Apple：Developer ID、Hardened Runtime、notarytool 公证与 stapler、entitlements、未公证 App 的打开流程

### 4.0 结论先行

1. 在 Mac App Store 之外分发，必须 **Developer ID Application 证书签名 + 开启 Hardened Runtime + 安全时间戳 + Apple 公证**，并把公证票据**装订（staple）**到产物上。Developer ID 证书**只能由开发团队的“账户持有人（Account Holder）”生成**。
2. 公证只能用 `notarytool`（或 Notary API）：**自 2023-11-01 起，公证服务不再接受 `altool` 与 Xcode 13 及更早版本的上传**。公证通常一小时内完成。
3. 三个 entitlement 都是 Hardened Runtime 的“运行时例外”，默认 false，能不加就不加：`allow-jit`（JIT，Electron/V8 需要）；`allow-unsigned-executable-memory`（Apple 称“罕见情况”才需要，并警告会暴露于内存不安全语言的常见漏洞）；`disable-library-validation`（允许加载非 Apple、非同一 Team ID 签名的库/插件；**Gatekeeper 会对关闭库校验的程序做额外安全检查**，被拦时先查是否不必要地关了）。
4. 用户侧：**macOS 15（Sequoia）起不能再用“按住 Control 点按 → 打开”绕过 Gatekeeper**（Apple 2024-08-06 开发者新闻）。macOS 15 与 26 上，未签名/未公证 App 首次打开的流程相同：先尝试打开被拦 → 系统设置 → 隐私与安全性 → 安全性 → 点“仍要打开”（尝试打开后约一小时内有效）→ 输入登录密码 → 好。之后该 App 被记为例外，可正常双击打开。

### 4.1 Developer ID 签名

- **做什么**：Gatekeeper 通过 Developer ID 证书确认软件来自已识别的开发者、且未被修改；适用于 App、插件、安装包。
- **怎么配**：在 Xcode 或开发者账户的 Certificates, Identifiers & Profiles 中生成 Developer ID 证书（App 用 Developer ID Application；pkg 安装包用 Developer ID Installer）；electron-builder 通过 `CSC_LINK` 导入（见 2.3）。
- **前提**：Apple Developer Program 会员；**必须是团队的 Account Holder 才能生成 Developer ID 证书**。公证不接受 Mac Distribution、ad hoc、Apple Development 或本地开发证书。
- **用户体验**：签名且公证的 App 首次打开只出现常规确认（“这是从互联网下载的 App，确定要打开吗？”）。
- **来源**：
  - https://developer.apple.com/developer-id/
  - https://support.apple.com/en-us/102445 （Safely open apps on your Mac）

### 4.2 Hardened Runtime

- **做什么**：与系统完整性保护（SIP）一起保护软件运行时完整性，防止代码注入、动态库劫持、进程内存篡改等。
- **怎么配**：Xcode 中加 Hardened Runtime 能力；手工或 electron-builder 签名时用 `codesign --options runtime`（electron-builder `hardenedRuntime: true`，默认即开）。确需某项被限制的能力时，加对应 entitlement 关掉单项保护，“只用功能绝对必需的 entitlement”。
- **规则**：entitlement 只加在可执行文件上；共享库、框架、进程内插件继承宿主可执行文件的 entitlement。布尔 entitlement 默认 false，值为 false 时不要写入。
- **前提**：**上传公证必须开启 Hardened Runtime**（Apple 原文“must”）。
- **用户体验**：对大多数应用无影响；缺少必要例外时可能崩溃或功能异常。
- **来源**：https://developer.apple.com/documentation/security/hardened-runtime

### 4.3 三个运行时例外 entitlement

| entitlement | Apple 官方含义 | 何时需要（官方表述） | 风险提示（官方） |
|---|---|---|---|
| `com.apple.security.cs.allow-jit` | 允许用 `MAP_JIT` 标志创建可写且可执行的内存 | 依赖 JIT 的场景，如 JavaScriptCore 快路径、某些 Python 框架、PCRE、自研动态编译宏语言；没有它，依赖 JIT 的框架可能退回解释器，其他 JIT 代码可能崩溃或行为异常 | Hardened Runtime 默认禁止，因为有安全风险 |
| `com.apple.security.cs.allow-unsigned-executable-memory` | 允许**不受 `MAP_JIT` 限制**地创建可写可执行内存 | “罕见情况”：需要覆盖或修补 C 代码、使用早已废弃且本质不安全的 `NSCreateObjectFileImageFromMemory`、使用 DVDPlayback 框架 | **加了它会让应用暴露于内存不安全语言的常见漏洞，应仔细考虑是否需要**；使用未签名可执行内存的 DRM 方案应改用 `MAP_JIT` + allow-jit |
| `com.apple.security.cs.disable-library-validation` | 允许加载任意插件或框架而不要求代码签名一致 | Hardened Runtime 默认开启库校验：只允许加载 Apple 签名或与主程序同 Team ID 签名的框架/插件/库；程序需加载其他第三方开发者签名的插件时才加 | **库校验是重要的加固特性；关闭它的程序会被 Gatekeeper 做额外安全检查**，被 Gatekeeper 拦时应检查是否不必要地关闭了库校验 |

**与 Electron 的关系（官方材料对照）**
- `@electron/osx-sign` 默认 darwin entitlements（`entitlements/default.darwin.plist`）中运行时例外只有 `allow-jit`（其余为摄像头、麦克风等设备/隐私权限键），**不含** `allow-unsigned-executable-memory` 与 `disable-library-validation`。
- electron-builder 内置模板三项都开（见 2.3）；其公证文档称 Electron“至少需要” `allow-jit` 和 `allow-unsigned-executable-memory`，但其常见 entitlements 表又把后者标为“某些 Electron 版本需要”。各方说法不一，**以 Apple 的含义说明为准，按“最小必要”原则实测**：先只留 `allow-jit`，用正式 Developer ID 签名包在目标系统上回归；只有实测崩溃时再逐项加。`disable-library-validation` 在正式 Developer ID 签名（Electron 框架被重签为同一 Team ID）下通常不需要；electron-builder 文档只把它列为 ad-hoc 签名时的必需项。
- 上述“先只留 allow-jit”是基于官方材料的工作建议，不是任何一方的原文结论。
- **来源**：
  - https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit
  - https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-unsigned-executable-memory
  - https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation
  - https://github.com/electron/osx-sign/blob/main/entitlements/default.darwin.plist

### 4.4 notarytool 公证与 stapler 装订

- **公证是什么**：不是 App 审核，而是 Apple 公证服务对 Developer ID 签名软件的自动扫描（恶意内容、代码签名问题），无问题则生成票据（ticket），并在线发布供 Gatekeeper 查询。签名密钥泄露时，公证还提供审计线索，发现未授权版本可请 Apple 吊销对应票据。
- **强制时间线**：macOS 10.14.5 起，新 Developer ID 证书签名的软件须公证才能运行；macOS 10.15 起，2019-06-01 后构建、用 Developer ID 分发的软件都须公证。
- **公证前必须满足**：所有可执行文件都有有效签名；用 Developer ID 证书；开启 Hardened Runtime；签名带**安全时间戳**；**不得含 `com.apple.security.get-task-allow`=true**；链接 macOS 10.9 及以上 SDK；entitlements 为格式正确的 XML、ASCII 编码。
- **怎么做**：
  - 提交：`xcrun notarytool submit <zip|dmg|pkg> --keychain-profile "<名>" --wait`（`--wait` 等结果；可加 `--webhook`）。凭据可用 `xcrun notarytool store-credentials` 存入钥匙串（Apple ID + App 专用密码 + Team ID；App Store Connect 强制双重认证，所以要用 App 专用密码），也可用 App Store Connect API 密钥，或直接调 Notary API（不依赖 Xcode）。
  - 可接受格式：UDIF 磁盘映像（DMG）、签名的扁平安装包、ZIP；嵌套容器也会处理，**提交 DMG 会为 DMG 本身及其中每个嵌套项（如 .app）都生成票据**。
  - 日志：`xcrun notarytool log <id> --keychain-profile "<名>" developer_log.json`；Apple 要求“即使成功也要看日志”，里面可能有警告。
  - 装订：`xcrun stapler staple "<App>.app"`（也可装订 bundle、DMG、扁平安装包）。**ZIP 不能直接装订**，要先装订里面的 .app 再重新打 ZIP；独立二进制目前无法装订。stapler 通过 CloudKit 下载票据，需能访问 Apple 指定 IP 段的 443 端口。
  - 磁盘映像注意：不要提交损坏的 DMG（可用 `hdiutil` 校验），避免高度压缩的 DMG。
- **装订的意义（Apple 原文要点）**：公证完成后，macOS 10.14 及以上用户再运行时 Gatekeeper 会**在线**找到票据（包括公证前就下载的用户）；装订后即使**无网络**也能找到。
- **与 electron-builder 的对应**：electron-builder 26.15.3 用 `@electron/notarize`（notarytool）公证并装订 `.app`；DMG 本身默认既不签名也不公证。按 Apple 的说明，若希望 DMG 本身也带票据，可在构建后对 DMG 另行 `notarytool submit` + `stapler staple`（属于基于官方材料的可选做法）。
- **用户体验**：装订后离线首次打开也不会被拦；未装订但已公证时需联网校验。
- **来源**：
  - https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution
  - https://developer.apple.com/documentation/security/customizing-the-notarization-workflow
  - https://developer.apple.com/documentation/security/resolving-common-notarization-issues

### 4.5 Gatekeeper 与未公证 App 在 macOS 15 / 26 上的首次打开流程

- **Gatekeeper 默认行为**：从 App Store 以外下载并打开 App、插件、安装包时，验证其来自已识别开发者、经 Apple 公证无已知恶意内容、且未被修改；首次打开前请求用户批准。必要时 Gatekeeper 会从随机的只读位置打开 App（防止随 App 分发的插件被自动加载）。用户可覆盖 Gatekeeper 策略，**除非受设备管理（MDM）限制**。
- **macOS 15 的变化**：Apple 2024-08-06《Updates to runtime protection in macOS Sequoia》：在 macOS Sequoia 中，用户**不能再用 Control 点按来覆盖 Gatekeeper** 打开未正确签名或未公证的软件，必须去“系统设置 > 隐私与安全性”查看安全信息后再允许运行。
- **macOS 15 / 26 上的完整用户流程（Apple 使用手册 15.0 与 26 版本页面内容一致）**：
  1. 尝试打开 App，弹出警告对话框（官方说明：该 App 未经审核，macOS 无法检查它自发布以来是否被修改或损坏）；
  2. 打开“苹果菜单 > 系统设置”，点边栏的“隐私与安全性”（可能需要向下滚动）；
  3. 在“安全性”下点“打开”，再点“仍要打开”——**此按钮只在尝试打开 App 后约一小时内可用**；
  4. 输入登录密码，点“好”；
  5. 该 App 被存为安全设置例外，以后可直接双击打开。
  - Apple 同页明确劝阻：覆盖安全设置打开 App“是 Mac 感染恶意软件最常见的途径”。
- **常见警告类型（Safely open apps on your Mac）**：已识别开发者的 App 首次打开会询问“确定要打开吗”；“Apple 无法检查 App 是否包含恶意软件”；“无法验证开发者”（Catalina 起且未公证）；“只允许 App Store”设置下打不开；“App 会损坏你的电脑 / 已损坏”（检测到恶意内容、授权被吊销或被修改，已知恶意软件会被移到废纸篓）。
- **对本产品的含义**：律所用户多数没有管理员思维，未公证包在 macOS 15/26 上需要走“系统设置 → 仍要打开 → 输密码”四步，且有一小时窗口限制；受 MDM 管理的律所电脑可能根本无法放行。正式发行必须签名 + 公证 + 装订。
- **来源**：

## 5. electron-vite 官方文档“源代码保护（Source Code Protection）”

> 说明：本节只整理官方文档写了什么。抓取日 npm 上 electron-vite `latest` 为 6.0.0。本产品各 `package.json` 中未见 electron-vite 依赖（本次只读核对），若要采用需先引入构建链。

### 5.0 结论先行

1. 官方方案是 **V8 字节码 + ASAR 完整性**两件套，并明说“没有绝对的客户端保护”，只能显著抬高门槛，须配合架构层安全与服务端校验。
2. 字节码选项：electron-vite 5 起用 `build.bytecode: true`（或 `BytecodeOptions` 对象）开启，此前须用 `bytecodePlugin`。**只在生产构建生效，只支持主进程与 preload，不支持渲染器。**
3. **关键冲突**：preload 用字节码依赖 Node 的 `vm` 模块，**必须把 preload 所在渲染器设为 `sandbox: false`**——这与 Electron 安全清单第 4 条（开启进程沙箱）直接冲突。只对主进程用字节码则不受影响。
4. **构建限制**：字节码缓存绑定 **V8（Node.js）版本**与 **CPU 架构**，不能跨架构复用；同架构跨操作系统（如 Windows x64 与 macOS x64）“实践中不可靠、不推荐”；官方原话“不要指望在一个平台上为所有平台构建”。因此 Windows 包的字节码应在 Windows 上编译，macOS arm64 包在 arm64 Mac 上编译；每次升级 Electron（即 V8 版本变化）都必须重新编译（后半句为按“绑定 V8 版本”的推论）。

### 5.1 官方写明的内容

- **ASAR 完整性部分**：引用 Electron ASAR integrity；注明需要 macOS 上 Electron 16+、Windows 上 30+；给出 electron-builder 配置示例：`electronFuses.enableEmbeddedAsarIntegrityValidation: true`，并“可选但推荐” `onlyLoadAppFromAsar: true`。保护特性：发现并阻止文件篡改、阻止未授权重新打包。
- **V8 字节码原理**：用 Node 标准库 `vm` 模块从 JS 源码生成 V8 字节码缓存，原为性能优化设计，缓存可分发并在运行时解释执行，从而隐藏原始源码。官方列出的特性：逆向难度高、保持原生性能、无外部依赖、兼容 Electron 运行时。
- **原生限制（官方列出）**：① 异步箭头函数可能导致运行时崩溃；② 字符串字面量（加密密钥、令牌、凭据）在字节码里仍可读。electron-vite 称已内置解决：把箭头函数转成普通函数、对指定字符串做混淆。
- **实现**：受 bytenode 启发；包含字节码编译插件（解析产物、决定哪些 chunk 编成字节码）、**用 Electron 进程编译**生成 `.jsc`（保证与 Electron 的 Node 环境兼容）、运行时加载器。
- **不支持 `Function.prototype.toString`**：源码不随字节码分发，拿不到函数源码。
- **选项 `BytecodeOptions`**：

| 选项 | 类型 / 默认 | 官方说明 |
|---|---|---|
| `chunkAlias` | `string \| string[]` | 只编译指定别名的 chunk，通常配合 `build.rollupOptions.output.manualChunks` 只保护部分模块 |
| `transformArrowFunctions` | `boolean`，默认 `true` | 用 Babel 把箭头函数转为普通函数；关掉“可能导致运行时崩溃” |
| `removeBundleJS` | `boolean`，默认 `true` | 设 `false` 则保留已编译成字节码的原 JS 文件 |
| `protectedStrings` | `string[]` | 指定要保护的敏感字符串，转换为 `String.fromCharCode` 形式的 IIFE，编译后不可读；支持普通字符串与“纯静态”模板字面量（不含 `${}`）；官方提醒不要把所有字符串都列进去，只列敏感的 |

- **跨架构构建**：若目标架构的 Electron 能在当前系统运行（如 arm64 Mac 能跑 x64 Electron），可通过另一份配置把环境变量 `ELECTRON_EXEC_PATH` 指向目标架构的 Electron 可执行文件来编译；一次构建多架构时，可在 electron-builder 的 `beforeBuild` 钩子里按目标架构切换 `ELECTRON_EXEC_PATH` 并逐个调用 `electron-vite build`。
- **对本产品的含义（按官方限制推出）**：
  - 若 preload 坚持开沙箱（安全清单第 4 条），则只能对主进程用字节码；
  - “字符串混淆”只是抬高门槛，**不能用来保护真正的密钥**（官方自己也说客户端保护不是绝对的）；密钥仍应放在 safeStorage/钥匙串或服务端；
  - 现行在 Mac 上出 Windows 包的做法与字节码不兼容，需改为 Windows 构建机（或 CI）上编译 Windows 包。
- **来源**：
  - https://electron-vite.org/guide/source-code-protection
  - 文档源文件：https://github.com/alex8088/electron-vite-docs/blob/master/packages/en-US/docs/guide/source-code-protection.md （中文版同目录 `packages/zh-CN/...`）
  - 实现源码：https://github.com/alex8088/electron-vite/blob/master/src/plugins/bytecode.ts

## 6. Electron safeStorage：macOS（钥匙串）与 Windows（DPAPI）

### 6.0 结论先行

1. **安全边界不同**：macOS 上密钥存在钥匙串，未经用户放行其他应用无法读取——**可防同机其他用户、也防同一用户下的其他应用**；Windows 上密钥由 DPAPI 保护，“通常只有与加密者相同登录凭据的用户才能解密”——**只防同机其他用户，不防同一用户下运行的其他应用**。
2. **macOS 必须正确签名**：没有有效且一致的签名时，macOS 可能认不出两次构建是同一应用，**每次更新后钥匙串都会再次弹窗要授权**；访问钥匙串可能提示用户（同步 API 会阻塞当前线程等待用户输入）。
3. **API 版本差异（重要）**：Electron 44 同时有同步 API（`isEncryptionAvailable` / `encryptString` / `decryptString`）与异步 API（`isAsyncEncryptionAvailable` / `encryptStringAsync` / `decryptStringAsync`），44 文档“推荐异步 API，同步 API 将来可能废弃”；**main 分支文档已写明同步 API 在 Electron 46 中移除**，同步 API 加密的数据可用 `decryptStringAsync` 解密。现在写新代码应直接用异步 API，避免升级到 46 时返工。

### 6.1 各平台实现与安全含义（44-x-y 文档）

| 平台 | 同步 API 的密钥来源 | 异步 API 的密钥来源 | 防护范围 |
|---|---|---|---|
| macOS | 为应用存储在“钥匙串访问”中，其他应用未经用户放行不能加载 | 从钥匙串存取（与同步 API 安全模型相同） | 防其他用户 + 防同一用户空间的其他应用 |
| Windows | 通过 DPAPI（`CryptProtectData`）生成 | 通过 DPAPI 保护（与同步 API 安全模型相同） | 防同机其他用户；**不防**同一用户空间的其他应用 |
| Linux（参考） | kwallet / kwallet5 / kwallet6 / gnome-libsecret 等，因桌面环境而异；无密钥库时用硬编码明文密码加密（`getSelectedStorageBackend()` 返回 `basic_text`），等同未保护 | Portal Secret（Flatpak 首选）、Secret Service；无密钥服务时用回退提供者 | 因环境而异 |

**方法要点（44 文档）**
- `isEncryptionAvailable()`：macOS 上钥匙串可用即 true；Windows 上应用发出 `ready` 事件后即 true。
- `isAsyncEncryptionAvailable()`：返回 Promise；异步加密器在 app ready 后首次调用该方法或 `encryptStringAsync` / `decryptStringAsync` 时**惰性初始化**。
- `encryptString(plainText)` → `Buffer`，失败抛错；`decryptString(encrypted)` → `string`。
- `encryptStringAsync(plainText)` → `Promise<Buffer>`；`decryptStringAsync(encrypted)` → `Promise<{ shouldReEncrypt, result }>`：`shouldReEncrypt` 为 true 表示密钥已轮换或有了安全级别不同的新密钥，应重新加密后保存。
- 异步 API 非阻塞，支持密钥轮换（`shouldReEncrypt`）与临时不可用处理（`isTemporarilyUnavailable`）。
- `setUsePlainTextEncryption()` 仅 Linux 有效，Windows、macOS 上无操作。
- 只能在主进程使用。

**相关联动**
- `cookieEncryption` 熔断在 macOS 上与 safeStorage 使用同样的钥匙串访问，同样要求代码签名（见 1.2）。
- 签名身份变化（例如从 ad-hoc/未签名切到 Developer ID，或换 Team ID）后，旧钥匙串条目对新签名的应用可能需要用户重新授权（依据：官方“没有一致签名时 macOS 认不出是同一应用”的说明推出）——正式发行前应确定最终签名身份，避免老用户升级后反复弹窗。
- Windows 上 DPAPI 不防同用户的其他进程：本机恶意软件以当前用户身份运行即可解密，故 safeStorage 不能替代“敏感数据少落盘”与服务端控制。
