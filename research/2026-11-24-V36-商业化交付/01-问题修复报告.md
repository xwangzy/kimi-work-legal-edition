# 第 62 批问题修复报告：模型计费与 Word 预览空白

## 1. Word 预览空白（封装后客户端）

**现象**：任务已生成《民事起诉状》，成果区认得文档与版本，右侧预览框空白（用户截图，安装包 0.2.0）。

**取证（用户本机已安装的正式包，经同意以调试端口重开同一工作区）**
- 隔离框架 `iframe.sp-frame` 的 srcdoc 3,321 字符，含完整起诉状；CDP 直连框架目标（about:srcdoc，独立渲染进程）：已载入、正文 1,868 字符、文字色 rgb(31,29,26)、纸面底色——**文档完整，父页面合成不出图**。
- 同一 srcdoc 放进新插入的框架立即显示；对原框架再改 srcdoc 仍空白；把原框架换成属性相同的新元素立即显示。
- 帧事件：框架插入并开始初始导航 → 2 ms 内换到独立进程（swap）→ 4 ms、6 ms 两次脚本发起的 about:srcdoc 再导航（React 随代号表、引用角标到达更新 srcDoc）。
- Electron 44.5.1 最小复现（`evidence/preview-blank/probe-electron-srcdoc.cjs`）：插入后 0～50 ms 内原地改 srcdoc → 0 像素，稳定复现；≥200 ms 正常；每次换新元素 → 每次正常；与窗口隐藏/最小化无关。

**根因**：sandbox 隔离框架（不透明来源）由独立渲染进程承载；首次导航提交前对同一框架再次导航，该框架此后永久不出图。安装包里内核走 IPC，代号表与引用角标在 HTML 到达后几毫秒内就到，srcDoc 连变两三次，落进窗口；开发形态经 HTTP 开发桥更慢，所以只在安装包稳定出现。与 CSP、自定义协议、沙箱、文件内容、内核渲染都无关。

**修复**（ffeaf96c、945fdddd）：
- `SafePreview`：隔离框架以内容摘要（`previewFrameKey`，FNV-1a + 长度）作 React key——内容不变不重挂（不闪烁），内容一变就换新元素，绝不原地改 srcdoc；隔离强度不变（仍是 `sandbox=""` + 注入 CSP + 网络层拦截）。
- 加“重新载入预览”（换新元素的人工恢复）；任务页与复核页的 Office 预览按成果版本记账，切换时显示“正在生成预览”，生成失败显示原因与“重新生成预览”（原先误报“这种文件不能在应用内预览”）。
- 用例 `apps/desktop/test/b62-preview-frame.test.ts`；安装包验收驱动加 `preview` 阶段：按框架区域截图数深色像素（“载入了但没画出来”也判失败）。

**生产安装包验证**：macOS 0.3.0 正式包（生产内容签名，`5276f7ca…`）连线上云端真实起草起诉状（32 分钟、16 份成果）：复核页全部 Word/Excel 各版本 + 任务页右栏下拉逐项切换，**24/24 出图**（Word 每份约 6.4 万个文字像素），含用户截图同一场景“民事起诉状 · 第 2 版”。Windows 见 04 文。

## 2. 模型定价与计费

**线上现状（只读核实）**：价目 v2 按别名（legal/k3 13/1.3/68、legal/k2.6 6.5/1.1/27），成本全空；607 行账本 580 行未定价；额度按原始 token 扣。

**根因清单**（后端子代理核查 + 主 Agent 复核，证据见 `platform/docs/contract-b62-pricing.md` §9 与用例）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 额度 `charge = input + output`，缓存命中按全量扣 | 一单约 190 万 token 里 88% 是命中（单价只有 1/10），额度消耗被高估约 5 倍 |
| 2 | 价目按别名定、成本全空 | 别名切到 highspeed 后售价仍按 13/68（应 26/136），成本与毛利不可信 |
| 3 | 缓存写入未识别（上游给 `prompt_tokens_details.cache_write_tokens`，1 小时 TTL 另有响应头） | 5 分钟写入价恰等于输入价没算错；1 小时写入按 13 计（应 26）少一半 |
| 4 | usage 采集会漏：非流式 >64 KiB 只留尾部、流中途出错丢掉已收 usage、只看尾部 64 KiB | 回退估算并按估算扣费（与 MaaS 11 月核查到的多扣/少扣同类） |
| 5 | 估算直接进扣费与成本 | 估算值当作实测 |
| 6 | 预占与定价检查只看别名 | 切到更贵的备用目标时预占偏低；备用目标未定价按 0 元放行 |
| 7 | 桌面端自己把 `charge/1e6` 显示成元 | 违反“客户端不得自行计算可信账单” |

已核实无误：账期两端都是北京时间；`prompt_tokens` 含命中与写入（官方文档与实测一致）；网关内换目标只记一条；回报重发与并发回报按 request_id 去重。

**修复**（5e18e4b9、bdeacad6）：价目按上游型号（成本缺省官方价，来源与日期入库；售价 = 成本 × 倍率或显式覆盖）；五档计费（未命中/命中/写入 5min/写入 1h/输出）；每行记价目版本、实际型号、倍率与计费明细；额度按售价口径金额扣；网关全程采集 usage（含 `choices[].usage`、断流后继续读完上游）；估算只记待对账、不扣额度不计金额并告警；预占按候选中最贵档；结算按实际型号；桌面端只显示云端给的比例。
迁移：读回时一次性把价目转为按型号、token 套餐按 4.2 元/百万 token 换成金额、价目生效前的用量折成“迁移前已用”保持百分比连续，原值入迁移记录可还原；旧接口 `PUT /v1/ops/routing/prices` 返回 409，防止悄悄改回按别名。

**真实调用对账**（本机控制面 + 网关，上游中软 MaaS）：18 次调用、计费 16 行，客户端看到的 usage 与账本逐项一致，金额与官方价手算一致 16/16；
首次写入 8,960 → 127,034 微元，之后命中 8,960 → 19,890 微元；ttl=1h 写入按 26 元计；别名切 highspeed 不改价目即按 26/136 计；加价 1.2 后新行记第 2 版价目、旧行不变；上游 400 与真实 429 有记录不计费；客户端首块即断开的两次，网关读完真实 usage 照常计费。
用例：控制面 142/142、网关 56/56（合并后），桌面 537/537。

**偏离与取舍（待登记 D-278）**：上游不给 usage 时估算不扣额度（沿用 D-194 对断流的口径），靠 `usage_missing` 告警兜底，待对账行的自动回填（按 upstream_request_id 用 MaaS 日志补录）未做。
