## 2. 凭据存储：safeStorage、钥匙串、DPAPI

### 2.1 官方说明（electron/electron `44-x-y` 分支 `docs/api/safe-storage.md` 原文要点；10 文 §6 已汇编，此处只列与核对相关的）

- macOS：密钥存在钥匙串，“其他应用未经用户放行不能读取”——防其他用户，也防同一用户下的其他应用。
- Windows：密钥由 DPAPI 生成，引微软原话“通常只有与加密者登录凭据相同的用户才能解密”——**防同机其他用户，不防同一用户下的其他应用**（DPAPI：https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata）。
- 异步 API “非阻塞、支持密钥轮换（`shouldReEncrypt`）、能妥善处理暂时不可用（`isTemporarilyUnavailable`）”；44 文档推荐异步，同步 API 在 46 移除（10 文 §6.0）。44 文档没有写 `isTemporarilyUnavailable` 出现在哪个返回值上（API 列表里没有这个字段）。
- 重要提示：macOS 上应用应**代码签名**，否则 macOS 可能认不出不同构建是同一个应用，“每次更新都可能让钥匙串重新请求授权”（https://www.electronjs.org/docs/latest/api/safe-storage）。

### 2.3 结论

- **符合官方建议**：用异步 API、只在主进程、安装包形态失败即关闭、`shouldReEncrypt` 已处理、Windows 不放漫游目录。
- **与官方限制一致的残余**（不是缺陷，需写进对客户的安全说明）：Windows 上同一账户下的恶意程序可以调 DPAPI 解出主密钥，进而解开全部封装文件（源码已登记：`devices.ts:73-75`）；macOS 在 ad-hoc 签名下每次升级都会弹钥匙串授权（官方原文即此现象），等于训练用户点“始终允许”——**需证书后**由 Developer ID 根治。
- **缺口 A（本批做，落地清单第 1 项）**：内核侧没有兜底。`packages/kernel/src/electron-entry.ts:146-156` 等 `kernel.init` 10 秒，收不到主密钥就“以明文开发库启动”。正常路径下主进程先解封后 fork，不会触发；但这是“主进程任何一处改坏就静默落明文库”的单点。做法：安装包形态（主进程给内核环境加 `ZR_AT_REST=required`，或直接以 `ZR_RELEASE_BUILD=1` 为据，`release-config.cjs:115`）收不到 `dbKey` 即抛错退出、不建库。验证：用例模拟不发 `kernel.init` → 内核退出且数据目录无 `ledger.db`；开发形态行为不变。
- **缺口 B（可选，小）**：macOS 上用户在钥匙串弹窗点了“拒绝”，现走“无法打开本机加密数据”对话框（只有“退出 / 用恢复包恢复”）。可在 darwin 分支的文案里加一句“如果刚才在钥匙串提示里点了拒绝，请退出后重新打开并选择允许”，避免用户误走“移到一边并恢复”。验证：手工在钥匙串弹窗点拒绝看文案。
- **不在本批**：律所根私钥与 5 份恢复份额同机（审计 11 第 3 项，`keys/recovery-shares/` 本机仍在）——产品设计决定，已在第 60 批待拍板。

### 4.1 熔断与 asar 完整性的生效条件（官方原文要点）

### 4.4 npm 依赖审计

- 现状：`platform/package-lock.json`（lockfileVersion 3，561 项），CI 一律 `npm ci`（如 `.github/workflows/windows-desktop.yml:41`）；全部工作流（`.github/workflows/engine-drift.yml`、`windows-desktop.yml`，`platform/desktop-repo/template/.github/workflows/desktop-ci.yml`、`windows-e2e.yml`）**没有** `npm audit`，也没有 `npm audit signatures`；随包 Windows Node 与原生包另有锁文件与摘要核对（11 文 §4.2）。
