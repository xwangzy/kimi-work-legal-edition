# 第 62 批安全加固报告

依据：`12-发布配置与安全核对.md`（子代理按 Electron / Apple / Microsoft 官方文档逐项核对源码与已安装正式包，附出处与行号）、第 60 批 `02-安全加固报告.md`（H1～H9 已做项）。
原则：只用平台官方机制与成熟做法，不堆叠收益不明的技术，不干扰操作系统防护，不做规避检测的实现。

## 1. 现状结论（核对后）

| 方面 | 结论 |
|---|---|
| 构建卫生 | JS 全部压缩，0 个 `.map`、无 `sourceMappingURL`；asar 内无测试与 TS 源码。缺口：渲染进程留有开发桥回落地址、随包运行时带约 1,100 个类型声明与说明文件、**安装包没有第三方许可声明**（商用合规缺口） |
| 凭据存储 | 符合 Electron safeStorage 官方建议（macOS 钥匙串 / Windows DPAPI，异步 API，失败即关闭，Windows 不放漫游目录）。缺口：内核 10 秒收不到主密钥会“以明文开发库启动” |
| 本地数据 | 实测：账本数据库（SQLCipher）、材料、Agent 会话记录均为密文；日志只有事件码（令牌与案卷内容命中 0）；崩溃转储不上传；配置文件无服务端秘密 |
| 完整性 | 8 项 Electron 熔断与 asar 完整性校验已开；官方原文：其防篡改效力依赖操作系统代码签名——**本机没有 Developer ID / Windows 代码签名证书**，这一层目前不成立 |
| 客户端 / 云端边界 | 席位令牌与吊销、模型路由、额度预占与结算、上游密钥、设备入组、账号角色均在服务端强制；改本地配置只影响本机，动不了云端额度与授权。本批计费改造后，客户端只显示云端给的比例，不再自行折算金额 |
| 依赖审计 | 所有 CI 原先都没有 npm audit |

## 3. 评估后不做（理由）

| 候选 | 判断 |
|---|---|
| 进一步的代码变形 / 字节码化 | 收益有限（逻辑仍在本机可执行）、与随包 Node 版本及 asar 完整性、跨平台构建的兼容与排错成本高；核心价值（方法包、法规库）已由内容签名与服务端控制保护。本批只做常规生产构建卫生（压缩、无 sourcemap、无开发残留） |
| 敏感模块原生化 | 维护与双平台构建成本高、收益同上；关键授权与额度已在服务端 |
| 拦截远程调试端口 | 正式安装包的端到端验收依赖它；能以本人身份启动程序的本机进程本就能读本人文件。保留为待拍板项（第 60 批同） |

## 4. 需要证书后做

Windows Authenticode（含第三方原生模块，须在计算运行时清单摘要前签）、Apple Developer ID 签名与公证、填 `update_publishers` 并开启自动更新通道。届时熔断与 asar 完整性的防篡改效力才完整成立。

## 5. 剩余风险

- 未经操作系统代码签名：安装时有 SmartScreen / Gatekeeper 提示，安装包被替换的风险靠 SHA256SUMS 签名清单与线下核对公钥指纹缓解。
- 上游不给 usage 时，估算只记待对账、不扣额度（沿用 D-194 口径），靠“上游未给用量”告警兜底（拟登记 D-278）。
- 发布规格里席位公钥只有 1 把、密钥编号带 `stg`（部署名 stg-116）：轮换前需在云端预置第二把并按正式口径命名（运维事项）。
- 生产部署名 `stg-116` 不以 prod 开头，`sms.allow_dry_run` 的启动拒绝靠部署名判断：手册已写明线上不得配置该项。
