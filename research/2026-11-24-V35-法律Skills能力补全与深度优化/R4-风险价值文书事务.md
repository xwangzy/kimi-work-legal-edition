### dispute-and-performance-risk（识别争议与履约风险）

1. **基本信息**：原子技能；正文约 1.9 万字（全组最长），含两套报告模板、七类场景、两个完整示例；不依赖北大法宝 MCP，法源靠模型记忆列举。
2. **业务价值**：解决“这份合同 / 这笔交易会不会出纠纷、会不会违约”，面向企业法务、非诉律师、谈判人员。与律师业务匹配度**中**：拟签合同审查部分与产品 contract-review 高度重合且更粗；真正有增量的是“已签署、正在履行或已出现履约偏差”这一段（违约是否成立、解除还是继续履行、哪些期间在跑），产品目前没有专门处理。
3. **专业逻辑**：三层风险（条款层 / 交易层 / 环境层）× 两维（争议 / 履约）；每项风险须过“事实基础、法律依据、因果链、现实可能性”四要素验证；概率 × 影响 3×3 矩阵定级；预防 / 控制 / 补救三段应对；“对手方模拟”作为防错步骤。法源核查：
   - 民法典章节区间（143–157 效力、509–534 履行、535–542 保全、577–594 违约责任、595–647 买卖、703–734 租赁、788–808 建设工程）均与现行法一致；“担保合同 681–702”实为保证合同一章，表述不准确（担保物权在物权编）。
   - 示例援引民法典第 715 条主张“经同意的改善可请求适当补偿”——**法规库已核：第 715 条无补偿内容**，只规定经同意可改善、未经同意可请求恢复原状或赔偿；装修残值的分情形处理在《城镇房屋租赁合同解释》第 9、10 条（法规库已核：出租人违约解除可赔剩余租期残值；期满请求补偿附合装修费用不予支持，另有约定除外）。示例结论方向对，依据引错。
   - 第 734 条第二款优先承租权、第 585 条第二款违约金调整（法规库已核）正确。
   - 防错表仍以“管理性 / 效力性强制性规定”二分为判断框架；**合同编通则解释第 16 条（法规库已核）**已改为按规范目的、能否以行政或刑事责任实现立法目的等因素判断，二分法表述已过时。
   - “重大经济损失 = 超过合同金额 30%”是自设阈值，与合同编通则解释第 65 条“违约金超过损失 30% 一般认定过高”（法规库已核）是两回事，容易被模型混用。
4. **工程设计**：步骤齐全、清单式，可直接读懂；但大量“是否明确、是否合理”式勾选项不可检验；对手方财务、涉诉、失信等交易层核查要求外部数据，技能未给取数方式，模型只能空转或臆测；输出为 Markdown 报告带表情符号等级，无结构化落点。冗长度高，示例占一半篇幅。
5. **问题与缺陷**：依据引错（715 条）；强制性规定二分法过时；“发生概率”无证据支撑时仍要求给高 / 中 / 低，易成主观打分；“整体风险占比”统计鼓励凑数；交易层、环境层（市场、汇率、行业周期）超出律师职责，容易写成商业咨询。
6. **与产品对照**：`contract-review/SKILL.md` 已覆盖条款层几乎全部内容且更好——severity 有四种后果的硬定义并限制重大卡比例（第 3 节第 5 步）、按我方最大敞口校准（5a）、客户节点倒排并用 `calc.deadline`（5b）、格式条款应对（5c）、文件家族跨文件审查、已签合同只能写补充协议（第 2 节）、风险卡逐字锚点 + `citations.verify`。`due-diligence` 覆盖对手方 / 目标公司核查（外部查询结果由律师导入，不臆造）。**缺口**：已签合同“履约体检”——把合同义务、付款与交付节点、通知 / 异议 / 验收期限抽成台账，对照已发生的履约事实判断谁违约、违约形态、可用救济与正在流逝的期间（检验异议期、解除权行使期限、诉讼时效）。
7. **建议决策**：**融合**。把“已签署·履约体检”作为 `contract-review` 的一个模式（`stage=performing`），产出“合同义务与期限台账.xlsx”+ 履约偏差卡；期限届满日一律走 `calc.deadline`，违约金是否过高一律给出 `calc.ledger` 算出的损失基数后再判断。依据：产品条款层已更强，增量只在履约阶段。收益：覆盖企业法务“合同履约风险排查”高频需求，并与 procedure-check 的时效核查衔接。优先级 **P1**。
8. **可吸收的设计精髓**：
   - 合同已签署且材料或律师说明存在履约偏差时，先建“义务台账”（义务方、义务内容、履行期限或条件、对应条款、已发生的履行事实及出处），再逐项判定“已履行 / 迟延 / 不完全 / 拒绝 / 预期违约 / 尚未到期”；每个判定必须挂一条事实时间线记录，没有事实的写“待确认”。【可确定性检查：台账每行须有条款锚点；判定非“尚未到期”的行须有 facts 编号】
   - 判定违约后必须并列三种救济路径（继续履行、解除、违约金或损失赔偿）各自的条件与对我方的利弊，不替客户选择；涉及解除的必须写解除权行使期限（约定期限，或民法典第 564 条的一年 / 合理期限）及起算事实。
   - 合同中出现通知期、异议期、验收期、宽限期的条款，一律抽取为期限行并用 `calc.deadline` 算届满日；起算事实不明的给分支，不下“已过 / 未过”结论。【可确定性检查：期限行的届满日字段须来自 calc.deadline 调用结果】
   - 每项风险须能回答“哪一条原文 → 在什么情形下 → 我方受到什么后果”；缺任何一环不出卡（即四要素中前三项）。“发生概率”只在有材料事实支撑时填写，无事实支撑一律写“无法评估”，不得估概率。
   - 涉及合同或条款效力的，按合同编通则解释第 16 条的因素分析（规范目的、能否以行政或刑事责任实现立法目的、对方能否审查），不再使用“管理性 / 效力性”二分作为结论理由。【可确定性检查：出现“管理性强制性规定”“效力性强制性规定”字样且未引合同编通则解释第 16 条的，交付前检查提示】
   - 违约金是否“过分高于损失”先算损失基数，再对照 30% 一般标准；不得把“合同金额的 30%”当作判断标准。
   - 写完每张卡，以对方律师身份列出其最可能的一条抗辩或反主张（如“轻微违约不构成解除事由”），并说明我方应对；对方抗辩成立可能性高的，卡的严重度不得高于对我方的实际后果。

### internal-compliance-risk-identification（内部合规风险识别）

1. **基本信息**：原子技能；正文约 7 千字；三维度（制度体系 / 业务流程 / 个人信息保护）+ 两个示例；不依赖外部检索服务。
2. **业务价值**：企业合规体检、上市或并购前合规自查、合规事件后的体系排查。面向企业合规、常年法律顾问律师。匹配度**中高**：个人信息保护审查（隐私政策、第三方共享、SDK、跨境）和反商业贿赂制度是律师合规业务的真实高频需求；但“内部控制、不相容岗位分离、审批权限分级”更偏内审与咨询，律师很少以此单独出具意见。
3. **专业逻辑**：先按行业梳理合规义务清单 → 建“制度—法规对照矩阵”（应建 / 现有 / 覆盖状态）→ 逐条审制度内容 → 还原业务流程找应设未设的控制节点 → 隐私政策按法定告知与同意事项逐项对照。问题卡按 G（制度）/ P（流程）/ D（数据）编号。法源核查：
   - 反商业贿赂援引反不正当竞争法第 7 条、第 19 条——**法规库已核**：该法 2025 年修订（2025-10-15 施行）后，商业贿赂规定在第 8 条，罚则在第 24 条（罚款幅度提高到十万至一百万、情节严重一百万至五百万，并增加对单位负责人个人责任与收受方责任）。外部技能条号**已过时**。
   - 个人信息保护法第 6、13–17、23、29、31、38–43、44–47 条的指向（法规库已核第 17、23、29、31 条原文）正确；但遗漏了处理敏感个人信息、自动化决策、委托处理与对外提供、向境外提供等情形下的个人信息保护影响评估义务（第 55、56 条，法规库已核），而该义务是合规体检最常见的硬缺口。
   - 把行政法规写成“网络数据安全条例”，正式名称为《网络数据安全管理条例》（法规库收录，2025-01-01 施行）；“银保监会规章”机构名已不存在（2023 年机构改革后为国家金融监督管理总局）；《企业内部控制基本规范》第 29 条：**未核**（法规库未收录）。
4. **工程设计**：结构清楚、问题卡格式统一、示例贴近实务，可执行性在三者中最好的是隐私审查（有逐项审查表）。制度—法规对照矩阵的“应建制度”清单依赖模型对行业监管的记忆，缺数据来源；流程还原要求访谈与流程图，桌面端只能基于律师上传材料；风险等级三级定义用“可能导致处罚”这类不可检验的描述；无工具调用、无锚点要求，问题描述不回链原文。
5. **问题与缺陷**：条号过时（反不正当竞争法）；漏影响评估义务；机构名过时；把“制度缺失”一律定重大，缺乏按企业实际业务是否触发义务的前置判断（例如非金融企业不需要反洗钱制度）；“实际处理与政策声明不符”的核查要求在纯文本审查中做不到却未声明边界；整改建议中出现具体审批金额分级（5 万 / 20 万）属于管理建议，不是法律要求，容易被当作法定标准。
6. **与产品对照**：`policy-review/SKILL.md` 只审劳动用工规章制度（内容合法性、与劳动合同冲突、劳动合同法第四条民主程序与公示），**不覆盖**隐私政策、个人信息处理规则、反商业贿赂、数据出境；`due-diligence` 有合规模块但定位为交易尽调发现；`client-advice` 只答具体问题。法规库已收录 PIPL、数据安全法、网络数据安全管理条例、数据出境三件套、2025 反不正当竞争法，**基础数据已齐，缺的是方法**。
7. **建议决策**：**新增**（合规体检方法，首期限定“个人信息保护合规审查”模式；第二期“反商业贿赂与第三方合作”模式），劳动用工部分**融合**进现有 `policy-review`（不另起）。落地位置：新方法 `platform/content/skills/privacy-compliance-check/`（名称待定）+ 复用 `riskcards.submit`（锚点逐字取自隐私政策）、`tabular-review` 的逐格带出处表；法定告知事项清单写成内核可读的结构化清单。预期收益：补上企业法务线最常见的合规审查场景，且能落成确定性检查。优先级 **P1**（个人信息保护）/ **P2**（反商业贿赂）。
8. **可吸收的设计精髓**：
   - 审查隐私政策或个人信息处理规则时，按个人信息保护法第 17 条第一款列举的告知事项（处理者名称与联系方式、目的与方式、种类、保存期限、个人行使权利的方式和程序等）逐项判“有 / 无 / 不完整”，每项须附逐字摘录或写明“全文未见”及检索过的说法。【可确定性检查：清单每项状态非“有”的须有 searched_terms；状态为“有”的须有可在材料中定位的 quote】
   - 发现向第三方提供、处理敏感个人信息、处理不满十四周岁未成年人信息、向境外提供的任一情形，必须分别核对单独同意（第 23、29 条）、监护人同意与专门规则（第 31 条）、出境路径（第 38 条）以及影响评估（第 55 条）；触发情形与核对项一一对应。【可确定性检查：触发标签与必查条款的映射由内核比对，缺项即提示】
   - 合规义务先判“是否触发”再判“是否缺失”：每项义务写明触发条件（行业、主体规模、数据量、业务形态）及企业是否满足的事实依据；不触发的不出问题卡。
   - 引用反不正当竞争法、个人信息保护法等近年修订的法律，一律以 `law.get_article` 按分析截止日取现行条文再写条号；援引旧条号（如商业贿赂第 7 条）由 `citations.verify` 拦截。【可确定性检查】
   - 整改建议区分“法定义务（必须）”与“管理建议（可选）”两类并标注；管理建议不得写成法律要求，具体金额阈值、审批层级只作为示例并注明由企业自定。
   - 只审文本时在结论中写明“未核查实际数据处理活动与政策声明是否一致”；需要技术核查（SDK 实际调用、日志）的列为“需客户提供或技术检测”的待办，不作推断。
   - 制度—法规对照矩阵作为体检的主交付物：每行“合规义务（法源条号）| 触发事实 | 现有制度及条款 | 覆盖状态 | 缺口”，覆盖状态只取“覆盖 / 部分覆盖 / 未覆盖 / 不触发”四值。【可确定性检查：状态枚举与法源条号核验】

### legal-risk-assessment（识别外部监管风险）

1. **基本信息**：原子技能；正文约 3 千字（全组最短之一）；三块：许可资质、监管法规遵循、历史处罚与信用；需要国家企业信用信息公示系统等外部查询，正文自己承认模型无法自动登录查询，未接北大法宝 MCP。
2. **业务价值**：评估企业面临的行政处罚与信用惩戒风险，面向企业合规、常年顾问、投融资尽调律师。匹配度**中**：资质缺口与处罚记录核查是尽调和合规体检的必查模块，但独立成方法的场景不多；“信用修复”是真实但窄的需求。
3. **专业逻辑**：经营范围与实际业务 → 应持资质清单 → 实际持有与有效期比对；业务领域 → 强制性要求 → 差距 → 可能处罚类型与幅度；外部查询 → 处罚 / 经营异常 / 严重违法失信 / 失信被执行人 → 对经营的影响 → 可否修复。法源核查：
   - description 写“四个维度”，正文只有三块，自相矛盾。
   - 摘录了市场监管信用修复规章的条件（经营异常名录、行政处罚公示期满、严重违法失信名单满一年）：**未核**（法规库未收录该规章，需核对是否有新版）。
   - 示例把列入经营异常名录写在处罚机关、处罚日期栏里；经营异常名录属信用管理措施，不是行政处罚法规定的处罚种类，概念混用。失信被执行人名单由法院依执行程序管理，修复路径与市场监管信用修复完全不同，技能未区分。
   - 大气污染防治法第 46、99、123 条，海关法第 11 条，互联网信息服务管理办法第 3、7 条：**未核**（法规库均未收录）。示例中同一条环保输出重复粘贴两遍。
   - 遗漏行政处罚法自身的关键规则：违法行为两年（涉及公民生命健康安全、金融安全且有危害后果的五年）内未被发现不再给予处罚、首违且危害轻微及时改正可不罚、从轻减轻情形——这些直接决定“历史违规”是否仍有处罚风险。**未核**（法规库未收录行政处罚法）。
4. **工程设计**：模板化“应持资质 / 实际状态 / 问题 / 依据 / 整改”五栏，简洁可执行；但应持资质清单与处罚幅度全靠模型记忆，没有检索或核验步骤；外部查询步骤空转（写明了做不到却仍列为步骤）；输出无出处字段。成熟度低。
5. **问题与缺陷**：维度数自相矛盾；处罚与信用措施概念混用；未区分市场监管信用修复与法院失信名单；缺追责时效判断；示例重复；依赖不可访问的外部系统而无降级方案。
6. **与产品对照**：`due-diligence/references/dd-modules.md` 第 9 模块（诉讼仲裁与行政处罚）、第 10 模块（资质与合规）已覆盖资质、处罚核查，且明确外部信息只用律师导入的查询结果（`due-diligence/SKILL.md` 第 36 行），行业监管列为“待确认”而不臆造（第 47 行），比外部技能更稳。缺口：①非交易场景（常年顾问做年度监管体检）没有入口；②处罚追责时效、信用修复条件这类可确定计算的规则没有工具；③法规库未收录行政处罚法。

   - 对外部查询记录先分类再评估：行政处罚 / 经营异常名录 / 严重违法失信名单 / 失信被执行人 / 限制高消费，各自的主管机关、影响范围与移出或修复途径不同，不得混写在“处罚”一栏。【可确定性检查：记录类型取值限定枚举】

### strategic-risk-prioritization（战略层面风险优先级排序）

1. **基本信息**：原子技能（论证组织与评估类）；正文约 1.4 万字；概率—影响矩阵 + 三个调整因子 + 两个示例；不依赖外部检索。

8. **可吸收的设计精髓**：
   - 多个风险排序时依次用三个可核验的键：①最近的相关期限届满日（来自期间工具，越近越前）；②我方金额敞口（来自计算工具或已确认数字，越大越前）；③后果是否可逆（权利消灭、证据灭失、财产转移等不可逆的在前）。不用主观概率作为排序键。【可确定性检查：排序与前两个键的数值一致性可由代码校验】
   - 对排在前三的风险各写一条“翻转条件”：哪一个事实或证据如果被证实 / 推翻，该风险会明显升级或降级；这条就是下一步补证或核实的对象。

   - 同一根因引起的多个风险合并后再排序，排序表注明合并关系，避免同一问题因拆分而占据前几名。

   - 风险描述中区分“法律规则不确定”（法律适用有争议）、“事实不确定”（证据不足或待确认）、“对方行为不确定”三种来源，分别对应研究、补证、谈判三类下一步动作。

### judicial-value-judgment（司法价值判断）

1. **基本信息**：原子技能；正文约 6.5 千字；11 步流程 + 11 段固定输出 + 一个行政管理措施的示例；不依赖外部检索。
2. **业务价值**：辅助**法官**在权利冲突、开放性概念、比例原则审查等疑难案件中形成可审查的价值判断与说理。面向法官。与律师业务匹配度**低（直接使用）/ 中（借结构）**：律师不做裁判，但在违约金调减、人格权侵权责任认定、损失酌定、过错比例、公序良俗等“法官有裁量空间”的争点上，代理词需要写成法官可以直接采纳的说理，这正是该技能的结构价值。
3. **专业逻辑**：先判“是否真的需要价值判断”（排除纯事实、纯规则适用问题）→ 区分事实 / 规范 / 价值 / 裁量四类问题，只处理后两类 → 识别冲突主体与冲突价值 → 价值位阶 → 个案平衡 → 比例原则四阶（目的正当、适当、必要、狭义均衡）→ 至少两个方案比较 → 说理框架与反驳点。质量控制靠“不得泛泛罗列价值”“被限制利益须获最低保护”等原则性要求。法源核查：全文不引具体条号，只泛称宪法、法律、司法解释、指导性案例；未涉及过时法。**它遗漏了中国民法的一个关键事实**：大量价值衡量已被立法写成法定考量因素清单，例如民法典第 998 条（人格权侵权责任考量职业、影响范围、过错程度、目的方式后果）、第 1026 条（合理核实义务六项因素）、合同编通则解释第 65 条（违约金调整以损失为基础兼顾多因素、30% 一般标准、恶意违约一般不予减少）——法规库已核这三条。法官在这些争点上首先按法定因素说理，而不是从“秩序、自由、平等”等抽象价值出发。
4. **工程设计**：步骤清楚、边界声明好（“不应强行调用”）；但输出固定 11 段，对简单争点严重过度；“人民根本利益原则”段落在民商事案件中几乎总是空转；示例是行政管理措施，与民商事律师场景距离远。可检验性弱，全部是论证质量要求。
5. **问题与缺陷**：抽象价值清单优先于法定考量因素，次序颠倒；对民商事纠纷适用比例原则需要谨慎（比例原则主要用于公权力限制私权），技能未提示适用范围；面向法官的“裁判说理参考”若被律师直接搬进文书，语气与立场不符。
6. **与产品对照**：`agency-statement/SKILL.md` 第 41 行已要求每个焦点“我方观点 → 事实（证据编号、笔录出处）→ 已核验依据 → 对对方观点的回应”，附《争点与依据对照表》；`legal-research-memo` 处理法律适用争议。产品缺的是：针对**裁量型争点**的写法——先列法定考量因素、逐项对应事实、给出法官可采纳的具体裁量结果（数额或比例）及理由。
7. **建议决策**：**吸收**（作为 `agency-statement` 与 `legal-research-memo` 的“裁量型争点”写法），不作为独立方法。落地：`agency-statement/SKILL.md` 第 3 节逐个焦点论证增加一个分支；`platform/content/skills/AGENTS.md` 不动。优先级 **P2**。
8. **可吸收的设计精髓**：
   - 起草代理词或研究备忘录时，先判断每个争点属于事实争议、法律适用争议还是裁量争议；只有裁量争议（违约金增减、损失酌定、过错比例、精神损害金额、人格权责任认定等）才使用下列衡量结构，其余争点按要件论证，不做价值铺陈。
   - 裁量型争点先用 `law.search` 找有无法定考量因素清单（如民法典第 998、1026 条，合同编通则解释第 65 条），有则逐项列“因素 → 本案事实（证据编号）→ 对我方有利 / 不利”，无一遗漏；找不到法定清单时才援引一般原则（诚信、公平）。【可确定性检查：引用了含“应当考虑……因素”的条文时，对照表须为该条每一项因素各有一行】
   - 给法官一个可以直接采纳的具体结果（如“违约金调整为以实际损失 ×× 元为基础上浮不超过 30%”），并说明对方主张的结果为何不可采；不止于“请求法院酌情”。
   - 对对方最有力的一条论点作出正面回应，并说明即便该论点部分成立，我方主张的最低可接受结果是什么（退一步的替代请求）。
   - 比例原则（目的、适当、必要、均衡）只在涉及公权力措施或法律明确要求比例衡量的争点上使用；民商事合同争点不套用。
   - 交付给法庭的文书不得出现“价值位阶”“人民根本利益”等学理或政策宣示用语，说理落在法条、事实与证据上。【可确定性检查：受限文书中的禁用词表】

1. **基本信息**：复合技能（编排层），调度 8 个原子技能（要素提取、概念理解、争点识别、法条检索、案例检索、演绎推理、格式、术语）；正文约 1.2 万字；**仅面向刑事案件**（预测罪名、法条、刑期、罚金）；法条与案例检索依赖北大法宝 MCP 或等价检索；示例取自公开判决预测评测数据（2016–2017 年盗窃、诈骗案）。
2. **业务价值**：本质是 LJP 学术评测任务的编排说明，面向学术评测与刑事辩护参考。与产品业务匹配度**低**：产品无刑事辩护线；输出“罪名置信度 X%、刑期点估计”在律师执业中不可直接使用。
3. **专业逻辑**：要素 → 候选罪名与构成要件 → 争点（罪名竞合、形态、共犯地位、数额档次、情节）→ 法条与司法解释 → 类案量刑分布 → 五层演绎（定罪、形态、档次、情节叠加、附加刑）→ 置信度。三个质量检查点 + 回溯上限 2 次 + 未遂、共犯、多罪名、信息不足、法条冲突五类分支，编排设计是全组最完整的。法源核查：刑法第 23、25–29、52、53、64、67 条第三款、264、266 条的指向在常识上正确，**未核**（法规库未收录刑法及刑事司法解释）；“情节叠加按先减轻后从轻的顺序”与量刑指导意见确立的“特定情节对基准刑连乘调节、其余情节同向相加逆向相减”的方法不一致，表述不准确（**未核**原文）；未提示刑法修正案（十一）等修订后行为时法与裁判时法的从旧兼从轻选择，只在质检点泛称“司法解释时效性”。
4. **工程设计**：步骤、质检点、回溯规则清晰，可执行；但“类案量刑分布”“置信度百分比”在没有可靠案例库与统计的前提下只能由模型臆造，是空转且有害的步骤；报告格式要求列“参考案例 1、2”的量刑结果，在无检索工具时极易编造案号。
5. **问题与缺陷**：①置信度以百分比输出（总体、罪名、形态、量刑分项），与律协 AI 指引精神及产品工作准则第 7 条（不预测裁判结果、不给百分比）直接冲突；对当事人展示此类数字，可能被视为对结果的承诺或误导，构成执业风险；②量刑方法表述不准；③类案数据来源不可验证；④刑事业务超出产品业务线。
6. **与产品对照**：产品无刑事方法；`platform/content/skills/AGENTS.md` 第 18 行、`case-analysis/SKILL.md` 第 72、80 行、`appeal-draft`（“不预测二审结果”）均明确不预测；内核 `deliverable-check.ts` 目前**没有**对百分比概率、胜诉率措辞的确定性拦截（只在提示词层约束）。
7. **建议决策**：**舍弃**（方法本体）。只把两样工程做法反向吸收：①把“不给概率 / 胜诉率”从提示词约束升级为交付前确定性检查（见 strategic-risk-prioritization 第 8 条第 3 点，同一条规则）；②复合方法的“质检点 + 回溯上限 + 超限后标不确定继续”机制可作为长链方法（如审合同两段、起诉状）的编排参考。优先级：确定性检查 **P1**，其余 **P3**。
8. **可吸收的设计精髓**：
   - 任何交付物出现对裁判结果的数值化预测（“胜诉率”“支持概率”“置信度 xx%”“刑期预计 x 个月”），交付前检查标为必须修改，提示改为“支持与不利的依据各列”。【可确定性检查：正则 + 语境词（胜诉、支持、败诉、判处、预测）】
   - 长链任务设置固定质检点：每个质检点列明“检查项 → 不通过回到哪一步”；同一检查点最多回溯两次，仍不通过的在交付物“待律师判断事项”中写明哪一项未通过，而不是无限重试或静默放过。【可确定性检查：质检记录写入任务日志，回溯次数计数】
   - 涉及行为时法与裁判时法不同的（法律修订跨越行为日），先用 `law.get_version` 分别取两个时点的版本，列出差异后再适用；不得只用现行版本。【可确定性检查：as_of 与行为日不一致时 citations.verify 双时点核验】
   - 争点识别后，逐个争点标注“它影响哪一项结论”（定性、数额、责任比例），未影响任何结论的争点不进入正文。
   - 引用类案必须来自律师提供或检索工具返回的可核验来源（案号 + 法院 + 裁判日期），没有来源的类案一律不写；不得以“司法实践中一般”替代来源。【可确定性检查：案号格式 + 来源字段非空】

### judgment-document-generation（裁判文书生成，复合）

1. **基本信息**：复合技能；调度与上一项相同的 8 个原子技能；正文约 9 千字；**仅面向刑事一审判决书**；检索依赖外部服务。
2. **业务价值**：替法官生成完整刑事判决书（首部、事实、本院认为、主文、尾部）。面向法院 / 学术评测。与产品匹配度**低**：律师不制作裁判文书；产品无刑事线。
3. **专业逻辑**：同上一项的编排链，增加文书组装与术语润色；四个质检点，其中 QC4 的“主文与理由一致性”“附录法条完整性”“刑期起止日期计算（含羁押折抵）”是有价值的确定性检查思路；“辩护意见逐一回应（采纳 / 不采纳并说理）”分支专业。法源核查：援引刑法第 23、24、25–29、52、53、64、67 条与最高人民法院刑事判决书样式，**未核**（法规库未收录）。示例同样来自评测数据。
4. **工程设计**：步骤与质检点完整；文书格式依赖模型对法院样式的记忆，未给样式来源；刑期折抵计算交给模型完成，没有计算工具，容易算错。
5. **问题与缺陷**：主体错位（法官视角）；以模型生成“判决书”易被误用为对结果的预测；刑期计算无工具；类案量刑同样存在编造风险。
6. **与产品对照**：产品文书方法全部是当事人一方文书（`pleading-draft`、`defense-draft`、`appeal-draft`、`agency-statement` 等），已有：先 `outline.submit` 论点与依据由律师确认后再起草（`outline.get` 只按确认版写）、`deliverable-check.ts` 的大小写金额一致、表格合计、算式复算、标题编号与交叉引用检查、条号核验。**缺口**：“请求与理由一致性”——起诉状 / 上诉状的每项请求在事实与理由部分是否都有论证、请求金额是否与计算明细和理由中的数一致，目前没有确定性检查。
7. **建议决策**：**舍弃**（方法本体）；**重构**其“主文与理由一致性”思想为当事人文书的确定性检查：请求项 ↔ 理由段 ↔ 计算明细三方核对。落地：`platform/packages/kernel/src/services/deliverable-check.ts` 新增规则（适用 pleading-draft、appeal-draft、arbitration-application、labor-arbitration-draft、enforcement-application）。优先级 **P1**（诉请金额前后不一是起诉状最常见的硬伤之一）。
8. **可吸收的设计精髓**：
   - 起诉状、仲裁申请书、上诉状、执行申请书中，“请求事项”每一项都必须在“事实与理由”部分有对应论证段落（按请求编号或关键词对应）；无对应的请求报“请求缺少理由”。【可确定性检查：请求项抽取 + 理由段关键词 / 编号匹配】
   - 请求事项中的金额、利率、起止日，与事实与理由中的同名数字以及本任务《计算明细》表中的结果逐一比对，不一致的报“金额前后不一”。【可确定性检查：数字抽取与比对，复用 amount_words、tableSumIssues 的解析】
   - 对方（被告、被上诉人）已提出的每一条主要抗辩，在答辩、代理或上诉文书中都有“采纳 / 反驳 + 理由”的回应；未回应的列入律师待判断事项。
   - 文书末尾的依据列表与正文援引的条号一一对应：正文引而列表未列、列表列而正文未引的都报出。【可确定性检查】
   - 涉及日期推算的（刑期、期间、利息起止），一律由计算工具给出结果并在文书或附表中保留算式来源，不得由模型心算后直接写入。

### legal-document-formatting（法律文书格式适用）

1. **基本信息**：原子技能（名义上），实际按段落强制调用要素提取、争点识别、证据评价、法条检索、冲突判定、演绎推理、价值判断等多个技能，近似复合；正文约 1.3 万字；只做**法院裁判文书**（民事判决书、刑事一审判决书），不含当事人文书；不直接依赖外部检索。
2. **业务价值**：按法院裁判文书制作规范起草判决书。面向法官、书记员、学术评测。匹配度**低（直接使用）/ 中（格式规则可迁移）**：律师不写判决书，但律师文书与裁判文书共用一套引用与书写规范（法律全称 + 书名号 + 条款项、项号写法、当事人简称首次定义后通篇一致、裁判主文式的给付写法），而且律师写诉讼请求时，越接近判决主文的写法越容易被直接采纳。
3. **专业逻辑**：民事七段（标题、首部、事实、理由、依据、主文、尾部）与刑事六段，逐段写明格式要点、需暂停的情形（事实陈述矛盾且均有证据、关键证据三性存疑、法律关系定性争议）、依据引用顺序（法律→行政法规→地方性法规→司法解释；实体在前程序在后；宪法、会议纪要、答复不作裁判依据）、金钱给付写明本金利率起止、诉讼费用不入主文、迟延履行告知等，最后有一张 11 项格式校验表。法源核查（**法规库已核**）：民诉法（2023 修正）第 40 条合议庭、第 147 条缺席判决、第 264 条迟延履行加倍支付债务利息、第 171 条十五日上诉期（技能告知语中的 15 日）**均与现行条号一致**；买卖合同解释第 18 条指向逾期付款违约金规则，正确。刑事部分（刑诉法上诉期十日、刑法第 63 条第二款报核）**未核**（法规库未收录）。
4. **工程设计**：段落级规则具体、可检验（标点、序号、日期写法都能程序判定），是本组最接近“确定性检查规格书”的一项；但把多个推理技能硬编进格式技能，职责混乱；示例占篇幅过半，并附真实风格的案号与金额（示例案号以真实格式出现，存在被模型模仿编造案号的风险）。
5. **问题与缺陷**：主体错位（法官文书）；格式与推理耦合；“本件与原本核对无异”等法院专属要素若被迁移到律师文书会出错；示例中的价值判断段落把“合同严守”“公平原则”写成标签式口号，与其价值判断技能自己的要求相矛盾。
6. **与产品对照**：产品律师文书格式由各方法（如 `pleading-draft/references/civil-complaint-fields.md`）规定，内核 `deliverable-check.ts` 已有：标题编号、条文交叉引用、大小写金额、表格合计、算式复算、对外文书不留内部用语等。`tools/tools/citations.ts` 已能识别“第X项 / 第（X）项”等写法用于核验。**缺口**：①当事人名称与简称一致性（首次“以下简称”定义后全文统一、首部与正文与落款一致）没有确定性检查；②引用格式规范化（项号写法、法名全称首次出现）未做；③诉讼请求按“裁判主文可执行”标准的写法要求（本金、利率、起止日、履行期限、连带责任主体）未写成检查。
7. **建议决策**：**重构**（把格式规则落成内核确定性检查，不做方法）。落地：`deliverable-check.ts` 增“当事人称谓一致性”“简称先定义后使用”“诉讼请求可执行要素”三条规则，适用起诉状、答辩状、上诉状、仲裁申请书、执行与保全申请书。优先级 **P2**。
8. **可吸收的设计精髓**：
   - 对外文书中每个当事人第一次出现时写全称；需要简称的，用“（以下简称××）”定义，此后全文只用该简称；首部、正文、落款三处主体名称逐字一致。【可确定性检查：抽取“以下简称”定义表，检查定义前使用、定义后混用全称与其他简称、与首部名称不一致】
   - 金钱给付类请求必须同时写明：计算基数（本金）、利率或标准、起算日、截止日（或“至实际清偿之日止”）、给付主体（多主体时写明连带或按份）；缺任何一项的请求报“请求不具可执行性”。【可确定性检查：请求项要素抽取】
   - 引用法条使用“《法律全称》第×条第×款第×项”，项号用汉字且不加括号；同一法名第一次出现用全称，此后可用规范简称。【可确定性检查：正则】
   - 依据列表排序：法律（基本法律在前）→ 行政法规 → 地方性法规 → 司法解释；实体法在前、程序法在后；会议纪要、答复、指导意见只在说理中援引其精神，不列为依据。【可确定性检查：依据列表按法规库 level 字段排序校验；九民纪要等标为“说理参考”】
   - 起草中遇到“同一事实双方陈述相反且各有证据”“关键证据仅有复印件”“法律关系定性有争议”三种情形之一时，暂停并把该情形列入律师待判断事项，再继续其余部分；不得替律师选定一种说法写成确定陈述。
   - 日期、编号写法统一：法律文书落款日期按本所或法院要求统一一种写法（汉字或阿拉伯数字，不混用）；全文序号层级（一、（一）、1.、（1））不跳级不混用。【可确定性检查：复用 headingNumberIssues】

### case-lifecycle-planning（案件全周期规划）

1. **基本信息**：原子技能；正文约 1 千字（全组最短）；无法律内容、无工具依赖说明；本质是案件日历 / 路线图的交互规格。
2. **业务价值**：把各案件的立案、庭前会议、开庭、执行等关键时间汇总成“本案路线图”“本月路线图”“关键时间一览表”（按城市、按月）。面向律师团队与律所运营。匹配度**中**：律师确实需要跨案件的开庭日历与出差安排，但这是案件管理系统功能，不是推理技能。
3. **专业逻辑**：识别案件名 → 识别时间类别（开庭、庭前会议、执行）→ 写入案件表与月度表 → 追问缺失地点 → 输出四张表。没有诉讼阶段模型（起诉—保全—举证—庭审—判决—上诉—执行）、没有阶段对应的文书与期限，也不处理提醒（限制条件中明说）。法源核查：无法律依据可核。排除情形中出现“与案件管理无关的一般性编程任务”，属模板残留。
4. **工程设计**：只有交互描述，无数据结构、无持久化说明，依赖宿主自带的存储；模型按对话记忆维护跨案件状态不可靠。成熟度低。
5. **问题与缺陷**：内容过薄；需要持久状态却未定义；“上传传票识别”没有识别字段规范（法院、审判庭、案号、开庭时间地点、传唤对象）。
6. **与产品对照**：产品内核已有事项（matter）与期限提醒：`kernel/src/services/reminders.ts`（提醒类型 hearing / evidence / appeal / limitation / contract / filing / other；本机巡检 + 云端加密调度）、`kernel/src/api/index.ts` 的 `reminders.list` 已能跨事项按期限日排序列出本人全部提醒；`case-report` 出进展汇报，`casefile-organize` 出事实时间线。**缺口**：①传票、开庭通知、判决书等程序文书中的时间要素没有被结构化抽取并转成提醒候选；②没有“诉讼阶段路线图”视图（当前阶段、下一阶段的法定动作与期限）。
7. **建议决策**：**重构**（以内核能力实现，不做方法）：在 `casefile-organize` 识别出程序文书时，抽取“法院、案号、事件类型、日期时间、地点、对我方的要求（如举证期限、答辩期）”，作为提醒候选交律师确认后写入 `reminders`。阶段路线图作为 `case-report` 附表的一个工作表。优先级 **P2**。
8. **可吸收的设计精髓**：
   - 识别到传票、开庭通知、举证通知、判决书、裁定书、保全裁定、受理通知等程序文书时，抽取固定字段：文书类型、法院或仲裁机构、案号、落款日期、送达日期（以送达回证或签收记录为准）、指定的时间地点、要求我方完成的动作与期限；送达日期无凭证的标“待确认”。【可确定性检查：字段齐全性与日期格式】
   - 每个抽取出的时间点生成“提醒候选”（类型、期限日、依据文书与页码），律师逐条确认后才写入提醒；不自动创建，也不自动修改已确认的提醒。
   - 同一案号的多份程序文书时间冲突（如两份开庭通知时间不同）时，以落款日期较晚者为准并提示律师核对，不静默覆盖。【可确定性检查】
   - 路线图按“已完成 / 当前阶段 / 下一阶段”三段展示，下一阶段写明法定动作、届满日（来自期间工具）与负责人；不写对阶段结果的预测。
   - 案件名称统一用事项名，不由模型根据对话猜测案件；用户提到的案件对不上事项时列出候选让律师选择。

### trial-scheduling-and-deadline-monitoring（庭审排期与程序时限监控）

1. **基本信息**：原子技能；正文约 2 千字；含输入输出表格模板与一个上诉期示例；“Scripts”一节只有 `script1.py: Description` 占位符，属未完成模板；不依赖外部检索（只说“根据民事诉讼法及相关司法解释计算”）。
2. **业务价值**：跟踪开庭、举证、上诉、送达、保全续行等期限，按期限类型或近 30 日出一览表，到期前 5 天、3 天提醒。面向律师、法官、仲裁员。匹配度**高**：漏期限是律师执业责任事故的第一大来源，期限全周期管理是刚需。
3. **专业逻辑**：录入起算事实 → 按法律计算届满日 → 用户确认 → 入表 → 按类型、按近期筛选 → 到期前提醒；非法定期限（法院指定期限）要求二次确认再写入。法源核查（**法规库已核**，民诉法 2023 修正、民诉法解释 2022、财产保全规定 2020）：
   - 示例“3 月 2 日收到一审判决书、上诉期 3 月 17 日届满，依据民诉法第 171 条”：条号与期间正确（判决十五日、裁定十日）；但未提示第 85 条“届满日为法定休假日顺延”，也未区分境内无住所当事人上诉期三十日（第 286 条）。
   - 技能把“送达期限”列为监控对象，送达是法院的职责，不是当事人期限，对律师而言意义有限；真正需要监控却未列出的有：答辩期（第 128 条十五日、第 285 条境外被告三十日）、诉前保全后三十日内起诉或申请仲裁（第 104 条第三款，否则解除保全；财产保全规定第 17 条自动转换且期限连续计算）、申请执行期间二年（第 250 条，自履行期间最后一日起算）、再审申请六个月（第 216 条）。
   - “保全续保”只写了名称，未写规则：法规库已核——冻结存款不超过一年、查封扣押动产不超过二年、查封不动产及冻结其他财产权不超过三年（民诉法解释第 485 条）；申请续行须在保全期限**届满七日前**提出，逾期自负后果（财产保全规定第 18 条）。技能“前 5 天、前 3 天”的固定提醒点**晚于**续行申请的最后时点（届满前 7 日），按其设计会直接导致漏续。这是本组发现的最实质性的专业缺陷。
   - 举证期限：法规库已核——一审普通程序不少于十五日、二审新证据不少于十日（民诉法解释第 99 条），简易程序不超过十五日（第 266 条），小额诉讼一般不超过七日（第 275 条）；技能未区分程序类型下的取值范围，只在最佳实践里提到“询问是普通、简易还是小额”。
4. **工程设计**：输入（案件名、期限类型、起算日）与输出（按案件、按类型、按近期三种一览表）设计合理，“非法定期限二次确认”是好做法；但计算完全交给模型、无期间计算工具、无节假日数据，“提醒”需要宿主有定时能力而技能未定义；Scripts 占位未完成。
5. **问题与缺陷**：保全续行提醒时点设计错误（见上）；遗漏答辩期、诉前保全起诉期、申请执行期间、再审期间、涉外三十日；未处理法定休假日顺延；“5 天、3 天”固定提前量对不同期限一刀切。
6. **与产品对照**：
   - 产品**更好**的部分：`kernel/src/tools/tools/deadline.ts`（`calc.deadline`）确定性计算届满日，开始日不计入、按月对应日与月末规则、末日遇法定休假日顺延（民法典第 200–204 条、民诉法第 85 条），附逐步过程与节假日数据来源，并对节假日未收录年份给警告；另有 workday 规则（行政处罚法工作日期间）。`intake-notes`、`procedure-check`、`case-analysis`、`appeal-draft` 均要求届满日由工具算、取最保守口径、不下“已过 / 未过”结论。`reminders.ts` 有本机 + 云端加密提醒、跨事项列表（`api/index.ts` 的 `reminders.list`）。
   - 产品**缺**的部分：①`calc.deadline` 只是通用期间计算器，期间长度与起算事实由模型自行选择，没有“程序期间目录”（期限类型 → 法定期间、起算事实、依据条号、变体）；②`intake-notes/references/collection-lists.md` 第 106、108 行把答辩期、上诉期写成“条号待核”，诉前保全起诉期也“条号待核”，且**没有保全续行、再审申请、涉外三十日**三行；③`reminders.ts` 文件头写明“期限日由律师填写”，一条提醒只有一个提前天数（默认 3 天），提醒类型没有“保全续行”“申请执行”“答辩”；方法算出的届满日不能一键转为提醒。
7. **建议决策**：**重构**（内核）+ **吸收**（参考表）。三件事：①给 `calc.deadline` 增加 `type` 参数与程序期间目录（每类写法定期间、起算事实、依据条号、变体条件，如境内无住所、裁定 / 判决、程序类型），目录随法规库版本核验；②新增“期限候选”工具（模型提交、律师确认后写入 `reminders`），并允许一条期限多级提醒，保全续行默认在“届满前 7 日”之前再提前（如届满前 15 日、10 日）提醒；③补齐 `intake-notes/references/collection-lists.md` 的条号与缺失三行。优先级 **P0**（保全续行与上诉期漏算属执业事故级风险，现有参考表有“条号待核”且无续行行）。
8. **可吸收的设计精髓**：
   - 程序期间一律按“期间类型”调用计算工具，期间长度由目录给出而非模型填写；目录至少包含：上诉（判决 15 日 / 裁定 10 日 / 境内无住所 30 日，民诉法第 171、286 条）、答辩（15 日 / 境外被告 30 日，第 128、285 条）、诉前保全后起诉或申请仲裁（30 日，第 104 条）、申请执行（2 年，自履行期间最后一日或分期最后一期届满日起算，第 250 条）、再审申请（6 个月，第 216 条）、保全期限（存款 1 年 / 动产 2 年 / 不动产与其他财产权 3 年，民诉法解释第 485 条）与续行申请截止（届满前 7 日，财产保全规定第 18 条）、举证期限范围（第 99、266、275 条）。【可确定性检查：目录与法规库条文逐条核验，条文变化时目录失效告警】
   - 保全续行的提醒以“续行申请截止日 = 保全届满日前 7 日”为基准再向前设提醒，而不是以保全届满日为基准；提醒文案写明保全标的、裁定文号与届满日。【可确定性检查：保全类提醒的 remind_at 必须早于届满日前 7 日】
   - 同一期限设多级提醒（如 15 日、7 日、3 日、当日），提醒级数与提前量按期限类型取默认值，律师可改；单一“提前 3 天”不适用于需要准备材料的期限。
   - 法院指定的期限（举证期限、补正期限）以通知书载明日期为准，录入时要求附通知书出处；与法定最低期限不符的（如普通程序举证期限少于 15 日）提示律师核对是否为简易或小额程序。【可确定性检查】
   - 方法交付物中出现的每一个届满日（上诉期、答辩期、时效等），都生成提醒候选，律师在交付页一键确认；未确认的候选在事项页持续显示为“待确认期限”，不得因任务结束而消失。
   - 期限一览表按“剩余天数”升序，剩余不足 7 日的置顶并在事项列表上标记；已届满的显示为“已届满（请核实是否已办理）”，不自动判定权利已丧失。

### billing-and-litigation-budget（工时计费与诉讼预算控制）

1. **基本信息**：原子技能；正文约 6 千字；含工时单、费用单、预算执行报告三套模板与三个示例；不依赖外部检索，但需要持久的工时、费用、预算数据。
2. **业务价值**：两块内容。①律所运营：工时记录、账单、费用归集、预算预警（70% / 90% 两档）、结案成本分析——面向律所管理与客户账单。②诉讼经济性：已发生与预计成本对比争议金额，判断“值不值得继续打”——面向律师与客户决策。匹配度：①**中低**（属于律所管理系统，产品不是计费系统）；②**高**（客户最常问的问题之一，也是是否起诉、是否保全、是否上诉的决策依据）。
3. **专业逻辑**：计费模式（计时、固定、风险代理、混合）→ 成本构成树（人力、专家与鉴定、调查取证、法院与仲裁费用、其他）→ 预算编制 / 执行 / 决算三阶段 → 使用率预警。经济性示例用“胜诉概率 70% × 争议金额 − 成本 = 期望净收益”得出“建议继续诉讼”。法源核查：
   - 只泛称“律师服务收费管理办法及当地律协收费标准”，未提及 2021 年底司法部等三部门关于进一步规范律师服务收费的意见对风险代理的限制（禁止风险代理的案件范围、按标的额分段的收费比例上限）：**未核**（法规库未收录律师收费规范），但技能把风险代理直接列为“争议解决、执行案件”的适用模式而不提示限制，存在合规缺口。
   - 法院费用只列项目，未与《诉讼费用交纳办法》挂钩；法规库已核：该办法第 29 条“诉讼费用由败诉方负担”，第 14 条执行申请费分段标准——这些决定了哪些费用可以从对方收回，经济性测算却没有区分“可转嫁给对方的费用”和“只能自担的费用”（律师费一般只有合同约定或特别法规定时才能主张由对方承担）。
4. **工程设计**：运营部分模板清楚但依赖不存在的数据存储与票据 OCR；经济性部分输入主观胜率，输出点值期望收益，属虚假精确；预算“基于进度外推”无方法。
5. **问题与缺陷**：①以胜诉概率做期望值并直接给出“建议继续诉讼”，违反产品工作准则第 7 条与律协 AI 指引精神，也替客户作出了商业决定；②经济性只看判决金额，忽略执行回收（对方偿付能力、财产线索、保全是否到位）这一往往比胜诉更关键的变量；③风险代理限制缺失；④成本未区分可收回与不可收回。
6. **与产品对照**：`calc.court_fee`（`kernel/src/tools/tools/court-fee.ts`）已确定性计算案件受理费、执行申请费、保全申请费、支付令、劳动案件，含减半规则与叠加警告；`amount-calc/SKILL.md` 第 40 行可在律师要求时预估诉讼费；`enforcement-application` 用 `calc.ledger` 算加倍部分债务利息；`case-report/SKILL.md` 第 38 行“预计费用由律师提供、不自行估算”。**缺口**：没有一张把“诉请金额、法院费用（工具算）、律师给定的律师费与鉴定费、保全担保费、可收回部分、执行回收情景”放在一起的《诉讼成本测算表》；运营计费（工时、账单）产品不做。
7. **建议决策**：经济性部分**融合**进 `amount-calc`，作为“诉讼成本测算”模式（全部数字来自计算工具或律师给定参数，回收按情景并列、不给概率）；运营计费部分**舍弃**（产品定位非律所管理系统，若未来对接律所计费系统再议，P4）。落地：`platform/content/skills/amount-calc/SKILL.md` 新模式 + `xlsx.render_table` 出表；`calc.court_fee` 可增加“仲裁费按机构费用表（律师上传）计算”的扩展位。优先级 **P1**。
8. **可吸收的设计精髓**：
   - 诉讼成本测算表固定分四段：①诉请金额（来自计算明细）；②法院或仲裁费用（`calc.court_fee` 算出，含受理费、保全费、执行申请费，标明减半等口径）；③律师给定的费用（律师费、鉴定评估费、公证费、保全担保或保险费、差旅），无参数的写“待律师提供”，不估算；④可从对方收回的部分（受理费等由败诉方负担的费用；律师费仅在合同约定或法律特别规定时列入，并注明依据）。【可确定性检查：②段数字须来自工具调用结果；④段律师费行须有依据字段】
   - 回收情景并列而不给概率：“全额执行到位 / 部分执行到位（按律师给定比例或已知财产线索金额）/ 无可执行财产”，各情景下的净回收 = 回收额 − 自担成本；结论由律师判断，测算表不写“建议继续 / 放弃”。【可确定性检查：禁用“胜诉概率”“期望收益”字样；各情景算式复算】
   - 测算到二审、执行阶段的追加成本分阶段列示（一审、二审、执行），每阶段注明触发条件（对方上诉、需申请执行），便于客户逐阶段决策。
   - 风险代理或含结果收费的委托，在测算或委托建议中提示收费合规审查：是否属于禁止风险代理的案件类型、收费比例是否超出规定上限；未核实规范原文前只作提示，不写具体比例。
   - 预计费用的每个参数写来源（工具算出 / 律师给定 / 机构费用表），与进展汇报中的“金额敞口”同源，一个数只有一个出处。【可确定性检查：与 case-report 附表“金额口径”工作表比对】

### 最值得做的三件事

1. **程序期间目录 + 期限候选转提醒（P0）**：`calc.deadline` 增加 `type` 参数，内置上诉、答辩（含境外三十日）、诉前保全后起诉、申请执行、再审、保全期限与续行截止（届满前七日）、举证期限范围等目录，条号逐条对法规库核验；新增“期限候选”工具，方法算出的每个届满日交律师一键确认写入 `reminders`，支持多级提醒，保全类提醒强制早于续行截止日。同时补齐 `intake-notes/references/collection-lists.md` 的“条号待核”与缺失三行。
2. **交付前检查新增三条确定性规则（P1）**：①裁判结果数值化预测拦截（胜诉率、置信度、概率百分比）；②起诉 / 仲裁 / 上诉 / 执行文书“请求事项 ↔ 事实与理由 ↔ 计算明细”金额与要素一致性；③当事人全称、简称先定义后使用、首部与落款一致。均落在 `kernel/src/services/deliverable-check.ts`。
3. **两个新模式（P1）**：`contract-review` 的“已签署·履约体检”（义务与期限台账、违约形态判定、三种救济并列、期限走工具），`amount-calc` 的“诉讼成本测算”（法院费用由 `calc.court_fee` 算、律师参数标来源、可收回与自担分列、执行回收按情景并列不给概率）；个人信息保护合规审查作为新方法紧随其后，法定告知事项清单做成可逐项判定的结构化检查。
