### Q6-01 重要：范本放入时的客户信息检查漏掉常见写法，界面说法过头

**位置**：`platform/packages/kernel/src/services/firm-templates.ts:49-54`、`:115-116`；`platform/apps/desktop/src/components/FirmTemplates.tsx:226`

**问题**：除当事人词典之外，客户信息只靠下面 5 条正则：

```ts
const PATTERNS: [TemplateHit["kind"], RegExp][] = [
  ["case_no", /[（(\[〔【]\s*\d{4}\s*[)）\]〕】][^\s，。；、]{1,20}号/g],
  ["id_no", /(?<!\d)\d{17}[\dXx](?!\d)/g],
  ["phone", /(?<!\d)1[3-9]\d{9}(?!\d)/g],
  ["account", /(?<!\d)\d{16,19}(?!\d)/g],
  ["email", /[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}/g],
];
```

`\d` 只认半角数字，正则也不容许分隔符。复核人用 `findHits(splitClauses(s), () => [])` 逐条试过，下面这些写法都返回空：

| 写法 | 结果 |
|---|---|
| `联系电话：１３８００１３８０００`（全角数字） | 未命中 |
| `联系电话：138-0013-8000`、`138 0013 8000` | 未命中 |
| `开户账号：6222 0212 3456 7890 123`（银行账号按 4 位分组，合同里最常见的写法） | 未命中 |
| `身份证号：110105 19491231 002X` | 未命中 |
| `案号：（２０２４）京0105民初12345号` | 未命中 |
| `固定电话：010-62345678` | 未命中 |
| `邮箱：zhang＠example.com` | 未命中 |
| `住所：北京市海淀区中关村大街1号` | 未命中 |
| 统一社会信用代码（如 `91110108MA01G2X93K`，含字母） | 任何一条正则都匹配不上 |

当事人只按“本人仍是成员、未删除的事项”的令牌词典查（`api/index.ts:3054-3057`）。客户不在系统里时查不出来，例如别的律师的事项，或者从前所带来的范本；不在词典里的自然人（法定代表人、联系人）也查不出来。界面却写的是：

> `FirmTemplates.tsx:226`：“放入前会逐条检查像客户名称、案号、证件号、电话、账号、邮箱的写法；查到的会先列给你看。”

**为什么是问题**：范本库按律所存放，这台电脑上的成员共用（`firm-templates.ts:7` 注释，驻留面第 19 类）。律师 A 放入一份从真实交易改来的范本，首部写着“统一社会信用代码 9111…”“住所：…”“开户账号 6222 0212 …”“联系电话 138-0013-8000”。检查放行后，同一台电脑上的律师 B 能在“方法与模板”页的查看框里看到全文（`ViewTemplate` 首部 seq 0 也显示），审合同时卡片也会列出这些条款。B 不是那个事项的成员，等于从侧面越过了伦理墙。

仓库里已有更全的识别器 `packages/tokenizer/src/patterns.ts:210 findIdentifiers`：
- 先做 `foldWidth`，全角半角都认；
- 手机号容许 `-` 和空格分组，认座机；
- 认 `uscc`（统一社会信用代码）和住址；
- 案号有选项开关。

范本库没有用它，自己另写了一套较弱的正则。

**建议修法**：
1. 识别器改用 `findIdentifiers(text, [], { caseNumbers: true })`，所有类别都算命中，替换用它给出的位置。当事人以外，再加上 tokenizer 已有的自然人识别（`knownPersons`，或与材料令牌化同一口径的姓名识别），至少覆盖首部常见的“法定代表人：”“联系人：”。
2. 界面改成如实的说法，例如：“放入前会查你事项里的当事人名称（含简称）和案号、证件号、电话、账号、邮箱、地址；不在你事项里的客户名称和人名可能查不出来，请自己再核一遍。”
3. 用例补全角、分隔符、座机、统一社会信用代码、住所的反例。

### Q6-03 重要：拆条把“第 X 条”下面的“1、”“1.”拆成单独条款，主条只剩标题

**位置**：`platform/packages/kernel/src/services/firm-templates.ts:72`、`:88-97`

**问题**：

```ts
const HEADING = /^(第\s*[一二三四五六七八九十百零〇\d]+\s*条|[一二三四五六七八九十]+、|\d{1,3}\s*[、.．](?!\d))/;
...
for (const p of paras) {
  if (HEADING.test(p)) {
    flush();
```

三种层级的标题一视同仁，哪一种出现都另起一条，不分主从。复核人实测的结果：

```
splitClauses("第五条 付款\n1、买方应于验收合格后六十日内付款。\n2、卖方应先开具发票。\n第六条 交付\n卖方按期交货。")
→ [1,"第五条 付款","第五条 付款"], [2,"1、买方应于…","1、买方应于…"], [3,"2、卖方应先开具发票",…], [4,"第六条 交付",…]
splitClauses("一、付款\n1. 买方应于…\n2. 卖方应先…\n二、交付\n…") → 同样拆成 4 条
```

**为什么是问题**：“第 X 条”下面分“1、2、”，或者“一、”下面分“1. 2.”，是中文合同最常见的排版。现在的结果是：
- “第五条 付款”成了只有一行标题的条款，`clauseBody` 在只有一行时原样返回（`:236-240`），正文就是“第五条 付款”；
- 子项各成一条，标题是正文的前 30 字。

审合同时，付款卡的匹配会落到两种结果上：
- 落到“第五条 付款”：标题关键词“付款”有 0.25 分加分，见 Q6-07。律师点“照这条改”，修改框里只有“第五条 付款”几个字。
- 落到某个子项：只拿到半条，看不到同条的其他款。

用例只测了“1.1”这种下一级（`v94-b24.test.ts:136-143`），恰好绕开了这个问题。

**建议修法**：按出现过的最高一级来拆。
- 有“第 X 条”时，只认“第 X 条”起条，“一、”“1、”“1.”都并进当前条；
- 没有“第 X 条”而有“一、”时，只认“一、”；
- 两种都没有时，才用“1、”“1.”。

另外补用例：“第五条”下面带“1、2、”，断言拆成 1 条、正文含两款。

### Q6-04 一般：换占位符后，标题里留下截断的名称片段，换完也不复查

**位置**：`platform/packages/kernel/src/services/firm-templates.ts:77`、`:92-93`、`:123-133`；`platform/packages/kernel/src/api/index.ts:3061-3065`

**问题**：标题是截取正文前 30 字得来的：

```ts
const label = (p: string) => [...p.replace(/\s+/g, " ")].slice(0, 30).join("")...
const m = /^[^：:，,。；;]{1,30}/.exec(p.replace(/\s+/g, " "));
```

替换时，标题和正文都按命中的整串去换：

```ts
heading = heading.split(h.text).join(`【${HIT_LABEL[h.kind]}】`);
```

内核换完直接保存，不再查一遍：

```ts
const saved = saveTemplate(db, ..., hits.length > 0 ? { ...t, clauses: replaceHits(t.clauses, hits) } : t, sourceName);
```

实测：正文是“第一条 本合同由甲方与乙方在平等自愿基础上签订买卖双方为丁贸易有限公司 / 具体内容”（当事人词典里有“丁贸易”）。替换后，正文正确换成了“【当事人】”，标题却是“第一条 本合同由甲方与乙方在平等自愿基础上签订买卖双方为丁贸”，名称的前两个字留在了标题里。没有条款标题、按段落拆条的范本，每段的标题都是这样截取的（`:79-81`）。截断点落在手机号、账号中间时，同样会留下一截数字。

**为什么是问题**：标题会显示在两处：
- 审查工作台卡片上的“《范本名》第一条 …”（`ReviewWorkbench.tsx:786`）；
- 查看框的条款标题（`FirmTemplates.tsx:292`）。

留下的名称片段会给同一台电脑上的其他成员看到。

**建议修法**：
- 替换只做在正文上，替换完再从正文重新生成标题（重跑 `splitClauses`，或者对每条重新取 `label`）；
- 保存前对替换结果再跑一次 `findHits`（标题也要查），仍有命中就拒绝保存。

### Q6-06 一般：“选用后才随任务发给 AI”不准确，Agent 能读到事项里全部材料

**位置**：`platform/apps/desktop/src/components/FirmTemplates.tsx:264`；`platform/packages/kernel/src/tools/tools/review.ts:42-46`、`:74`、`:86`；`platform/packages/kernel/src/tools/tools/materials.ts:25-37`

**问题**：放进事项后的提示是：

> “在这个事项里起草合同、从范本整理审查要点时可以选用它；选用后会随任务发给 AI。”

Agent 工具 `materials.list` 列出的是整个事项的未隔离材料，不限于本次选的（`review.ts:42-46`）。返回结果里明确告诉模型：

> `review.ts:86`：“…其他材料可用 materials.read_excerpt 按 parse_version_id 读取。”

`materialsReadExcerpt` 也只核对材料属于本事项（`materials.ts:36`），不核对本次有没有选它。

**为什么是问题**：律师按“选用后才发”来理解，会以为不选就不会发。实际上这个事项里的任何一次开放任务，Agent 都可能读取这份范本。这和 Q6-02 是同一类问题（说法比实际窄），只是程度轻一些：读取的内容仍然先令牌化，而且这本来就是事项材料的一般规则。

**建议修法**：提示改成，例如：“已放进事项的材料（用途为‘参考’）。这个事项里的 AI 任务可能读取它，和其他事项材料一样处理。”不想让它被读到时，律师可以在材料页删除。

### Q6-07 一般：标题关键词加分一项就能过门槛，会列出不相关的条款

**位置**：`platform/packages/kernel/src/services/firm-templates.ts:218`、`:274-275`、`:283`

**问题**：

```ts
const hw = headingWord(r.heading);
if ([...hw].length >= 2 && plainQuery.includes(hw)) score += 0.25;
...
.filter((s) => s.score >= 0.18)
```

只要卡片文字（含模型写的 issue 和 suggestion）里出现条款标题的关键词，就加 0.25 分。这一项已经超过 0.18 的门槛，不用正文有任何相似。实测：范本里有“第十五条 其他（本合同未尽事宜，由双方另行协商…）”，卡片内容是“【违约责任】卖方逾期交货的违约金过低…并约定其他损失的赔偿”，返回的第一条就是“第十五条 其他”（score 0.332）。“其他”“定义”“通知”“费用”“期限”这类短标题词很常见，卡片文字里随处会出现。

- 标题词要求至少 3 个字，或者不认“其他”“附则”“定义”“通知”这类泛词；
- 补一条反例用例。

### Q6-08 一般：用例多为源码正则断言，几处门禁没有行为覆盖

### Q6-09 建议：理由字数的算法，界面和内核不一样

**位置**：`platform/apps/desktop/src/pages/Review.tsx:472`；`platform/packages/kernel/src/services/argument-outlines.ts:307-312`

**问题**：界面只去首尾空白就计字数：`(outlineOpen && [...outlineReason.trim()].length < 4)`。内核在计字数前，先去控制字符、再把连续空白压成一个：`raw.replace(/[\u0000-\u001f\u007f]/g, " ").replace(/\s+/g, " ").trim()`。

**为什么是问题**：律师输入“好    的”时，界面按 6 个字算，按钮可点；内核压成“好 的”只算 3 个字，返回 409。错误提示能看到，但前后不一致。

**建议修法**：界面用同一套清洗规则（压空白）再计字数，或者干脆不在界面判断，只看内核的结果。

### Q6-10 建议：末位是 X 的身份证号，会多报一条 17 位的“像银行账号”

**位置**：`platform/packages/kernel/src/services/firm-templates.ts:51`、`:53`、`:119`

**问题**：`11010519491231002X` 同时命中 `id_no`（18 位）和 `account`（`\d{16,19}(?!\d)` 匹配到前 17 位，因为 X 不是数字）。去重只去掉文字完全相同的那条：

```ts
return hits.filter((h) => !(h.kind === "account" && hits.some((x) => x.seq === h.seq && x.kind === "id_no" && x.text === h.text)));
```

实测返回两条：`id_no:11010519491231002X`、`account:11010519491231002`。替换时先换长的，结果正确，但命中清单里多出一条“像银行账号”。

**建议修法**：去重改成按位置判断，账号与证件号的区间有重叠就去掉账号；或者在账号正则后面加 `(?![\dXx])`。改用 `findIdentifiers` 后（见 Q6-01），这个问题自然消失。

### Q6-11 建议：放入和比对的资源上限

**位置**：`platform/packages/kernel/src/api/index.ts:3048`、`:3057`；`platform/packages/kernel/src/services/firm-templates.ts:252-260`

**问题**：
- `data_base64` 分支没有大小上限，只有 `p.file` 分支有 5 MB 上限（`:3046`）。
- 放入时 `spans` 对每一条款、每一个事项都调一次 `tokens.partySpansIn`。每次都新建一个 `MatterTokenizer`，并查库取事项、词典、密钥。一份 300 条的范本、50 个事项，就是 15,000 次构造。另外，`keyFor` 遇到还没有令牌密钥的事项，会顺带写一把新密钥。
- `for_card` 每点开一张卡，都把全库条款取出来重算字符二元组和逆文档频率。库的上限是 200 份 × 20 万字，最坏要处理约 4,000 万字，都是在内核的同步处理里。

**为什么是问题**：常见规模下没事，但没有兜底。这些都是同步计算，算的时候内核其他请求都在排队。

**建议修法**：
- `data_base64` 解码前按长度拒绝超过 5 MB 的内容；
- `spans` 改为每个事项只构造一次令牌化器，复用到所有条款（或者把全部条款拼起来一次查完，再按位置分回各条）；
- 二元组和逆文档频率在放入或删除时算好缓存（按律所一份），`for_card` 只算卡片这一侧。

### Q6-12 建议：“照这条改”会把【当事人】等占位符带进修改框，保存时不提醒

**位置**：`platform/apps/desktop/src/components/ReviewWorkbench.tsx:802`

**问题**：`onClick={() => setEditing({ id: c.card_id, text: m.body })}` 把范本正文原样放进修改框，正文里可能有放入时换上的“【当事人】”“【电话】”。按钮的 title 写着“删改成适合本合同的写法后保存并接受”，但保存时（`:208` `api.decideRiskCard(...)`）不检查占位符还在不在。

**为什么是问题**：律师漏改一处，“【当事人】”就会原样进入修订稿，包括对外版。

**建议修法**：保存前检查文本里是否还有 `【当事人】【案号】【证件号】【电话】【账号】【邮箱】`，有就提醒一句，律师确认后才能保存。也可以把占位符高亮显示。

### Q6-13 建议：任何成员都能删别人放入的范本，删除审计不记是哪一份

**位置**：`platform/packages/kernel/src/api/index.ts:3069-3073`；`platform/packages/kernel/src/services/firm-templates.ts:198-204`

**问题**：`firm_templates.remove` 只按租户核对，不看 `created_by`，也不看角色。审计记的是 `audit(db, id, "firm_template.removed", "firm_template", tid, undefined, keyctx)`，摘要为空。

**为什么是问题**：共用电脑上，一位律师可以删掉别人（例如合伙人）放入的定稿范本。事后从审计只能看到一个编号，看不出删的是哪一份；行已经硬删，无法恢复。

**建议修法**：

- 审计 detail 记上这份范本的 `sha256`（正文摘要，不含正文），和放入时的记录能对上。
