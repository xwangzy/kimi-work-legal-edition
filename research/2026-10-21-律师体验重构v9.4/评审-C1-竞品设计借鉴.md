# 评审 C1：竞品设计借鉴（Harvey / LegalOn / Legora / Spellbook / CoCounsel / 国内）

调研日期：2026-10-21。对象：Kimi Work 法律行业发行版 V9.3（代码基线 `.claude/worktrees/v93-b16/platform/apps/desktop/src`）。
证据口径：竞品资料均为公开页面，“官方说明”只证明厂商这么写，不证明在任何账号里可用、好用；“实测”一词只用于本轮亲自操作过的东西（本轮没有登录任何竞品，因此没有实测）。

> 结构：§0 一页结论 → §1 模式目录（29 条）→ §2 合同审查呈现 → §3 事项与表格式审阅 → §4 引用呈现 → §5 不照搬 → §6 未能访问。附 A 已知结论、附 B V9.3 现状、附 C 本轮逐产品调研记录（证据 URL 都在附 C）。

## §0 一页结论

**(1) 领先产品最值得借鉴的是什么？**
不是某个功能，而是四个交互模式：
- **先结构化、再综合**。Harvey Review Table、Legora Tabular Review、CoCounsel Tabular Analysis 都是“行 = 文件，列 = 问题，格 = 带原文出处的答案”，表做完再据表写报告。它解决的是律师最怕的“漏看一份”。
- **AI 先做、人逐格把关，把关结果不被冲掉**。Harvey 单元格可锁定（2026-08-12，官方），重跑保留已核实的格子（待核）；Legora 有“标记已复核 / 锁定单元格 / 复核模式”。它解决“AI 重跑一次，我刚核过的又变了”。
- **规则驱动的合同审查**。LegalOn 每条告警旁并排显示触发它的 Playbook 规则；“缺失条款”是一类正式告警并能一键补条款（2026-09-04）；对方回稿只审改动（Harvey 2026-08-12）。它解决“AI 的意见到底按谁的标准、能不能对客户说得出口”。
- **起草前先让律师选论点和依据**。CoCounsel Brief Builder 起草前停四次，每条依据附“引注 + 要旨 + 怎么支持这个论点”；Harvey 驳回动议工作流要律师批准研究计划后才写。它解决“文书写完了才发现依据撑不住论点”。

**(2) V9.3 的关键差距**（按影响排序）
1. 没有多文档表格式审阅。证据清单、尽调、合同台账都只能逐份跑任务。
2. 合同审查没有“缺失”和“偏离规则”两类结果。`RiskCard` 只有 anchor（原文锚点），缺失条款找不到锚点，会落到 `not_found`，修订稿只能跳过；卡片也不说按哪条规则判的。
3. 引用核验是“引用清单”，不是“论断—依据对照”。“支持待判”这个状态已经有了，但律师看不到被支持的那句话。成果预览里也没有行内角标。
4. 谈判梯度只能看、不能选。接受时只写“首选”，想用“可退让”得手工复制。
5. 事项页的“任务”是 AI 运行流水，不是“这件事要做什么、谁复核”。

V9.3 已经领先或持平的地方：单份合同逐条复核到 Word 原生修订稿、事实先确认再进文书、引用分级状态、签发前检查“系统已核 / 你来核”分开、保护状态可见。这些不要因为借鉴而推倒。

**(3) 哪些直接继承、哪些要重新设计**
- 直接继承：单元格状态与锁定、重跑不覆盖已核、缺失条款告警、规则并排、备选改法并排可选、修订作者名、行内引用悬停卡、起草前确认论点与依据、事项模板、命中已有方法时提示。
- 重新设计：Word 插件（中国律师大量用 WPS，且我们是本地客户端，先做“打开并定位”）；市场基准（中国没有可授权的市场条款库，改为“本所定稿库”）；客户门户（违反案卷不上云，改为导出脱敏包）；AI 自动整理文件（只建议标签，绝不移动或改名原件）；万份级大表（本机算力和 token 成本，先分批加估价）；案例引用状态（没有 Shepard's / KeyCite，改为“审级 + 案例类别 + 时点版本”）。

**(4) 应优先实现的专业能力**（P0，都有明确律师价值且落在已有页面上）
- 合同审查补齐“缺失条款”和“偏离本所规则”两类卡，修订稿分“对外版”和“内部版”。
- 引用改成“论断—依据”对照，成果预览加行内角标和悬停卡。
- 事项材料页加“表格审阅”最小版：三个固定模板（诉讼证据清单、尽调合同摘要、合同台账），格子回原文，格子有复核状态，重跑不覆盖已核。
- 文书类场景（起诉状、答辩状、代理词、研究备忘录）在起草前加一站“论点与依据确认”。

**(5) 如何平衡丰富、专业、简洁**
- **不加导航，只加视图**。侧栏保持 5 项。表格审阅是“材料”标签里的一个视图；规则、缺失、偏离都是工作台里的卡片类型；论断对照是右栏“引用”标签的新版式。
- **默认只显示要律师决定的东西**。卡片默认收起，只露等级、性质、条款号、一句话问题；规则原文、依据、前提点开才看。表格默认只露值和状态色，出处悬停才出。
- **专业深度放在数据结构，不放在按钮数量**。缺失卡、规则号、审级、时点版本是字段，不是新功能入口。字段对了，界面自然简洁。
- **能批量的只给低风险项**。批量接受只开放给“提示”级和格式/一致性类；重大风险必须一张一张过。
- **每加一项都问一句**：它是否减少律师复核时间？如果只是展示 AI 做了更多事，不加。

| 结果类型 | 偏离、缺失（2026-09 可一键补） | 只审改动（2026-08） | 风险与非市场条款 | 只有“风险”一类 |
| 规则可见 | 每条告警并排触发规则 + 解释 | 未公开 | 未公开 | 不显示 |
| 修改建议 | 预批准退让文本；一键修 | 备选改法并排，按立场选 | 直接写修订 | 首选 / 可退让 / 底线三行，只能用首选 |
| 写回方式 | Word 预览后一键插入为修订 | Word 修订，可回旧对话再应用 | Word 内 | 生成原生修订稿文件 |
| 表格条款 | 审，定位到单元格 | 未公开 | 未公开 | 不审 |
| 批量 | 未公开 | 表格侧有批量编辑 | 未公开 | 无 |

结论：V9.3 在“谈判梯度”“性质（必须 / 建议 / 可谈）”“需客户决定”“修订定位失败时说清原因”上比公开资料更细。差在**判断标准不可见**和**结果类型单一**。

### 2.2 我们的复核工作台应该长这样

```
← 返回任务   审查工作台 · 采购合同（对方第二稿）.docx
我方：买方 · 规则：客户甲采购标准 v3（2026-08 审定） · 法域：中国大陆 · 文件：主合同 + 补充协议一 + 附件一
[审全文 | 只看对方改动]                           重大待处理 2 · 缺失 1 · 偏离规则 4 · 可谈判 3
[生成修订稿 ▾ 对外版 / 内部版]   [导出审查意见表]   [待客户决定 3]

左：合同原文（高亮锚点；缺失卡在建议插入处显示虚线插入标）   右：卡片
                                                        分组：[按等级] 按条款顺序  按类型
┌───────────────────────────────────────────────┐
│ 重大 · 必须修改 · 偏离 R-12 付款期限   第 8.2 条              │
│ 付款期限 90 天，超出本所采购标准上限 60 天                     │
│ ▸ 规则 R-12（客户甲采购标准 v3）：付款期限不超过 60 日…        │
│ ▸ 合同原文：买方应于验收合格后九十日内…                        │
│ ▸ 依据：商业条件，无法律强制要求（来源：规则 R-12）           │
│ 首选   验收合格后三十日内        [用这一级]                    │
│ 可退让 验收合格后六十日内        [用这一级]                    │
│ 底线（待客户定）六十日，逾期按 LPR 计息                         │
│ [接受首选] [修改后接受] [不采纳]   需客户决定 □                 │
└───────────────────────────────────────────────┘
┌───────────────────────────────────────────────┐
│ 一般 · 建议修改 · 缺失            建议插入：第 12 条之后（可改） │
│ 未找到“知识产权归属”条款                                        │
│ ▸ 查过的说法：知识产权、著作权、专利、成果归属、工作成果         │
│ ▸ 补充协议一、附件一中也未找到                                  │
│ 建议新增 第 12A 条 ……                     [插入] [不需要]      │
└───────────────────────────────────────────────┘
```

设计要点：
1. **四类卡**：风险（条款写了但不利）、缺失（该有没有）、偏离（违反本所或客户规则）、一致性（定义、金额、日期、交叉引用前后不一）。类型是字段，胶囊显示，不加新页面。
2. **缺失卡必须说清“为什么认为缺失”**：列出查过的说法和查过的文件。这是防误报的关键。律师看到“补充协议里其实有”就能一键驳回，并把这个说法补进规则的同义词。
3. **规则来源三分**：偏离本所/客户规则（商业立场，可谈）、法律强制（无效或违法风险，不可谈）、通用建议（没有规则时的模型意见，要律师判断）。三者混在一起，律师会把商业偏好当成法律要求去和对方硬谈。
4. **谈判梯度可选用**：每一级一个“用这一级”。写入修订稿的是律师选的那一级。“底线”只展示不写入，提醒“待客户定”（沿用 `risk-ladder.ts` 的口径）。
5. **批量接受有边界**：勾选模式只对“提示”级和一致性类开放。重大、必须修改、缺失、需客户决定的卡不可勾选。批量后顶部出“已接受 12 项 [撤回本批]”。
6. **两版修订稿**：对外版只有修订，不带理由、规则号、底线；内部版带批注（理由 + 规则号 + 依据），供合伙人复核或发客户。默认对外版。生成时提示“对外版不含内部批注”。
7. **对方改动模式**：只列对方改动，每张卡左边是我方原稿、右边是对方改动、下面是规则判断；动作是“接受对方 / 恢复我方 / 改用退让文本”。
8. **导出审查意见表**：Word 或 Excel，列为 条款、问题、类型、等级、规则、依据、建议、律师决定。很多律师交付给客户的是这张表，不是修订稿。
9. **不做**：不做“一键全部接受”；不显示“风险分数 87 分”这类伪精确数字。

建议改动落点：`api.ts` `RiskCard` 增加 `kind`、`rule_ref`、`insert_after`、`searched_terms`、`related_docs`；`ReviewWorkbench.tsx` 增加分组切换、勾选模式、梯度选用；内核修订稿生成增加插入型修订与对外/内部两档；合同审查 Skill 的输出模式同步加上这些字段。

## §3 事项工作空间与多文档表格式审阅专项

### 3.1 竞品怎么组织事项

- Harvey 2026-10 把 Spaces 改成“律师在一件事项或项目上的大本营”，可打上客户事项号，可绑定 Playbook，有 Space 模板预置阶段、任务、复核人。任务可分给 Agent、同事或客户；产出好了通知复核人。
- CoCounsel 每个事项一个 Workspace，表格分析和其他任务共用同一上下文。
- LegalOn 的事项管理偏企业法务：收需求、分诊、看板看瓶颈和负载、在历史事项里搜条款。
- 共同点：事项是容器，表格和任务都挂在事项下，成果和复核状态在事项里汇总。

### 3.2 V9.3 事项页的调整

现在的标签：材料 / 事实 / 任务 / 交付件 / 当事人 / 数据去向 / 结案与删除。建议：

1. **加“概览”作为默认标签**（新事项无材料时仍停在“材料”，沿用 `lib/matter-tab.ts` 的规则）。内容只有四块：
   - 阶段条：诉讼“立案前 → 一审 → 二审 → 执行”，非诉“尽调 → 谈判 → 签约 → 交割”。当前阶段由律师点选，不由 AI 推断。
   - 待办：每条写做什么、谁做（律师 / 助理 / AI）、谁复核、期限。AI 完成的任务自动变成“待你复核”。
   - 关键期限：从期限提醒取。
   - 最近成果和待签发数。
2. **“任务”改名“AI 记录”**：它是运行流水，不是待办。避免和概览的待办混淆。
3. **事项头加“审查规则”**：一件事项绑定一套规则版本。
4. **新建事项选模板**：预置阶段、待办、推荐场景、期限提醒。模板来自方法与模板页，律所可发布自己的版本。

团队协作（任务分配给同事、通知复核人）受“案卷在本机”约束，首期只在已开通团队共享的律所内做（`TeamShare.tsx`），不做客户门户。

### 3.3 材料页的表格审阅

**入口**：材料标签顶部“列表 | 表格审阅”切换。表格审阅里可以有多张表，每张表有名字（“证据清单”“合同尽调”）。

**首期三个模板**（固定列，律师可增删）：

| 模板 | 业务线 | 列 |
|---|---|---|
| 证据清单 | 诉讼 | 证据名称、形成时间、提供方、原件/复印件、页码、拟证明事实、与哪个争点相关、真实性/合法性/关联性风险 |
| 合同尽调摘要 | 非诉 | 合同名称、相对方、金额、期限与续约、控制权变更条款、排他/竞业、转让限制、违约责任上限、争议解决 |
| 合同台账 | 企业法务 | 合同名称、相对方、签署日、到期日、自动续约、付款节点、通知期限、负责人 |

**每个格子**：
- 值（按列格式：日期、金额、是否、分类、原文摘录）。
- 角标：点开在右侧预览原文并高亮那一段（复用工作台的高亮）。
- 五态：AI 提取（默认）、未找到（区分“文件里没有”和“这页读不出来”）、有冲突（同一份材料里两处说法不一）、律师已核（绿勾）、律师已改（蓝点，保留原 AI 值可查）。
- 锁定：律师已核和已改自动锁定，重跑只覆盖前三态。

**表级操作**：
- 按状态筛选（“只看未核的”）、按列排序。
- “复核模式”：键盘 J/K 逐格走，A 确认，E 修改（沿用工作台快捷键）。
- “推为事实”：已核的格子可一键送进“事实”标签，与现有 `FactsPanel` 的确认流合并，避免两套事实。
- “据此起草”：证据清单 → 证据目录（Word）；合同尽调 → 尽调报告草稿；合同台账 → 期限提醒批量创建（逐条确认后创建）。只用已核的格子，未核的在成果里标“待核”。
- 导出 Excel。

**本地与隐私的改法**：
- 每个格子的提问都走现有的令牌化发送；格子值在本机还原显示（同工作台）。
- 开始前估算：多少份 × 多少列 = 约多少次调用、预计点数、多长时间（沿用 `RunSheet.tsx` 的先预估后确认）。首期上限 200 份 × 15 列，超出分批。
- 读不出来的扫描件在行首标“读取差”，不让 AI 猜。

**为什么是 P0 最小版**：三个模板覆盖三条业务线最高频的“多文件 × 同一组问题”工作；格子状态与锁定直接复用事实确认的心智；不需要新导航。自由建列、条件列、跨表对话放 P1/P2。

## §4 引用与来源呈现专项

### 4.1 律师要一眼看出的三件事

1. **这条依据是真的吗**（来源）：法条存在、条号对、原文一致；案号存在、法院对。
2. **用的是对的版本吗**（时点）：事件发生时适用哪一版；有没有修改、废止；案例有没有被上级法院改判。
3. **它撑得住这句话吗**（支持）：法条或判决的内容是否真的推出这个论断。

V9.3 的状态词表（来源已核 / 版本已核 / 支持待判 / 律师已确认 / 已拦截 / 未核实离线）已经覆盖这三层，问题在呈现：律师只看到一个胶囊，看不出三层各自过没过，也看不到被支持的那句话。

### 4.2 三处呈现

**① 成果预览里的行内角标**（`components/Markdown.tsx` 加引用标记渲染）
- 每处引用后一个小角标 ①②③。
- 颜色取三层中最弱的一层：灰 = 未核实（离线）；红 = 已拦截；橙 = 支持待判；无色细边 = 系统已核三层；实心绿 = 律师已确认。
- 系统核过和律师确认过要分开。不要让系统核验显示成律师认可的绿色。

**② 悬停卡**（参考 LegalOn 内联引用悬停卡、MetaLaw 悬停看“本院认为”）
```
《民法典》第 584 条                         现行有效 · 2021-01-01 施行
来源 ✓  版本 ✓（事件时点 2023-05 适用此版）  支持 ?（待判）
原文：当事人一方不履行合同义务或者履行合同义务不符合约定，造成对方损失的…
[看对照]  [我确认支持]  [标为不支持]
```
案例卡：
```
（2024）沪 02 民终 1234 号（示例，虚构）  上海二中院 · 二审 · 2024-08-12 · 普通案例
后续审级：未查到再审（核至 2026-10-21）
本院认为（摘录）：……
与本案：相同点 2 · 不同点 1   [看对照]
```

**③ 右栏“引用”标签改为“论断—依据”对照**（替换 `RunView.tsx` 的 `Citations` 列表）
- 每行：左边是成果中的论断原句（点击回到正文位置），右边是依据原文摘录，下面是三层状态与理由。
- 一句论断可以挂多条依据；一条依据也可能只撑住论断的一半，此时写“部分支持：只支持违约责任成立，不支持损失数额”。
- 排序：已拦截 → 支持待判 → 系统已核 → 律师已确认。
- 顶部汇总：“14 处引用：律师已确认 3 · 系统已核 8 · 待判 2 · 已拦截 1”。

### 4.3 事实引用也要同样可回溯

文书里的事实（“2023 年 5 月 6 日买方签收”）应同样带角标，指向材料名、页码、原文片段，点击在右栏打开材料并高亮。来源是事实标签里律师已确认的事实时，角标显示“已确认事实”。来源是 AI 直接从材料读的时，显示“未经确认”。这一条把现有“只有确认过的事实进文书”的规则显示出来。

### 4.4 与签发的衔接

签发前检查（`pages/Review.tsx`）已经区分“系统已核对 / 你来核对”。建议把“已拦截”和“支持待判”的引用数作为“你来核对”的必过项：已拦截的必须处理（删除或替换）才能签发；支持待判的要逐条点“确认支持”或“我已知悉”。

## §5 不建议照搬的设计及理由

| 设计 | 出处 | 不照搬的理由 | 替代做法 |
|---|---|---|---|
| 市场基准（与市场条款比） | Spellbook Benchmarks | 中国没有可公开授权的市场条款数据；“市场惯例”容易被律师误当成依据写进意见 | 本所定稿库（模式 23），明确标“本所过往处理”，不叫“市场” |
| AI 自动整理、移动、重命名案卷文件 | Harvey Agentic Vault Organization（有人工确认） | 案卷原件的文件名和目录本身是证据管理的一部分；本地原件被改动后难以追溯 | 只建议分类标签，标签存在本产品数据里，原文件不动（现有“只引用不复制”也不能改原件） |
| 客户门户实时协作 | Legora Portal；Harvey 任务可分给客户 | 与“案卷不上云”冲突；客户看到未复核的 AI 中间结果有执业风险 | 导出给客户的脱敏包（已有“客户版与对外脱敏”场景）；只给签发后的成果 |
| 万份级表格 | CoCounsel 单表 1 万份、100 问 | 本机解析和 token 成本；律师也无法复核 1 万格 | 首期 200 份 × 15 列，超出分批，开始前给估价 |
| 让律师选模型 | Harvey 模型选择器（2026-10 列多款模型） | 律师不该为模型负责，也无法判断模型差异；增加界面复杂度 | 按场景内部选择，记录在任务的“处理细节”里 |
| 自建 Agent 保存即用 | Harvey 2026-10-14 简化治理 | 我们的场景都要过法律质量门槛；个人随手写的方法直接用于正式成果有风险 | 个人方法可用于个人草稿；用于签发成果需合伙人发布版本 |
| 胜诉率、裁判趋势预测 | 国内“类案大数据预测”类产品 | 样本口径、地域、时间偏差不透明；客户会把数字当承诺 | 只展示检索范围和类案分布，不出概率 |
| 一键全部接受 | 多家一键修 | 重大风险被顺手接受是不可逆的执业事故 | 有边界的批量接受（模式 9） |
| 移动端运行 Agent、云端定时 | Harvey 2026-10 移动端 Agents | 违反本地执行；手机上无法复核 | 不做；期限提醒已在本机 |
| 从 AI 直接生成并放进邮箱草稿 | Harvey 2026-10-14 Outlook 草稿 | 发送类动作风险高，且要读写邮箱 | 生成后复制到剪贴板或另存为 Word |
| 日常界面零确认的“安全感” | Harvey、Legora 靠合同与管理台 | 我们的差异正是发送前令牌化与可见保护；但也不要为了显得安全加确认 | 保持 Y4 §3：保护被看见、只为真决策打断 |

要点（来自观韬测评，属第三方使用评价）：
1. **审级陷阱是中国律师的真实痛点**：MetaLaw 会出现“断章取义”——二审已改判，结论仍引用一审说理。律所建议逐一核对案例的审级变化。对我们：案例引用卡必须显示审级、是否有后续审级结论，不能只给案号。
2. **案例层级**：MetaLaw 的结论引用案例有随机性，不会优先纳入最高法案例、公报案例、指导性案例。对我们：类案结果要按“指导性 / 入库参考 / 公报 / 最高法 / 高院 / 其他”分层显示，层级比相似度更先映入眼帘。
3. **回看原文的两种做法**：MetaLaw 悬停可看案件概述和“本院认为”；通义法睿点击跳到裁判文书原文，案例固定展示“本院认为、裁判结果、相关法条”三段。律师要的是不离开当前页面就能看到判决的关键段落。
4. **类案表格**：MetaLaw 的类案结果可做成可自定义列的表格、高亮争议焦点、导出 Word/PDF 报告。这是“表格式审阅”在诉讼研究里的中国版本。
5. **检索词可见可改**：通义法睿自动生成检索关键词，律师可改。对我们：研究任务应把实际用过的检索式摆出来，律师可改了重查。
6. 律所给律师的使用建议：输入写清事实和争点、换词多查对比、按时间/法院层级/地域筛选、不完全依赖 AI 结论。

### C.7 本轮未调研

Luminance：受调用预算限制，本轮没有查。它以“大批量合同 + 异常检测”著称，与 Harvey Vault / Legora 表格式审阅的价值重叠，结论不影响本报告的优先级判断。
