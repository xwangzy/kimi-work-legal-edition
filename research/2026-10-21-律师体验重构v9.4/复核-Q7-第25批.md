## Q7-01 阻断：音译名排除字挡掉“阿不都”“理查德”“查尔斯”，令牌表里的同类真名一并退役

**位置**
- `packages/tokenizer/src/names.ts:118`：新增 `NOT_TRANSLIT = "不及涉料载推论待果区间补充反证查调取庭结具材否是确认请求事实理由"`。
- `names.ts:145`：`finishDotted` 的结果只要含其中任一字就返回 null。
- `names.ts:411`：`stillLooksLikeName` 对带间隔号的值做同样判断。
- `packages/tokenizer/src/index.ts:236-243`：`retired(e)` 为真的条目（来源为 recognizer）不进词典匹配，也不提供姓氏。

**复现**：同一组句子分别跑现行规则和 `b5df5bb` 的旧规则。

| 输入 | 旧规则 | 现行规则 |
|---|---|---|
| 被告：阿不都热依木·买买提，男，维吾尔族 | 阿不都热依木·买买提 | （无） |
| 原告：阿不来提·吐尔逊，男 | 阿不来提·吐尔逊 | （无） |
| 原告：艾力·阿不力孜 | 艾力·阿不力孜 | 艾力（后半漏出） |
| 原告：理查德·史密斯，男 | 理查德·史密斯 | （无） |
| 证人约翰·理查兹出庭作证 | 约翰·理查兹 | （无） |
| 代理人：查尔斯·王 | 查尔斯·王 | 查尔斯（“王”漏出） |

`stillLooksLikeName("阿不都热依木·买买提")`、`stillLooksLikeName("理查德·史密斯")`、`stillLooksLikeName("查尔斯·王")` 都返回 false。因此：
- 某事项里规则早先认出、已写进令牌表的这些姓名，现在退役，不再匹配新文字；
- 同一个人此后在律师说明、材料快照、追问里都以明文发给模型；
- 已有代号的旧成果照常还原，所以律师从界面上看不出变化。

“阿不”是维吾尔族名最常见的开头之一（阿不都、阿不来提、阿不力孜、阿不都热合曼），“理查德”“查尔斯”“查理”“理查森”是最常见的西文音译。涉疆案件、涉外案件里都很常见。这违背“自然人姓名默认令牌化”的口径，召回比上一批明确下降，所以定为阻断。

律师在当事人词典里登记的姓名（来源 dictionary）不受影响。漏出的是证人、经办人、对方员工这类只靠规则认出的人。

**建议修法**
1. 音译名排除不按单字判断，改为按“整段在材料用语表里”判断：
   - 只在间隔号两侧都是已知清单词时不认，清单词如“涉及、不涉及、待确认、原件、申请鉴定、补充反证、调查取证、材料载明、推论”；
   - 或者要求每一段都不是常见音译用字组合。
   至少把“不、理、查、及、是、实、由、结、具、果、区、间”等音译常用字移出 `NOT_TRANSLIT`。
2. `stillLooksLikeName` 不对间隔号姓名做单字排除。退役条件收窄到本批明确列出的误认值（“任务”“权利”“时告知”“由律师”“向股东”“解除权”“涉及·不涉及·待”）这一类；也可以改成“现行规则在该值自身的上下文里不再认出”才退役。宁可多替换几个普通词，也不放出真名。
3. 在 `name-recall.test.ts` 加召回用例：上表 6 句；令牌表里来源为 recognizer 的“阿不都热依木·买买提”在新文字里仍被替换。

## Q7-02 重要：待签发、待核、未决项提示仍按种类判断“最新版”

**位置**
- `packages/kernel/src/services/pending-checks.ts:37`：`unsignedLatestArtifacts`，被 `api/index.ts:2960` 用来给未签发成果做引用待核提示。
- `pending-checks.ts:79`：成果未决项（表格没核、论点未经确认、引用没通过、来源已隔离）。
- `packages/kernel/src/services/matter-todos.ts:170`：`derivedTodos` 的“草稿待看”（drafts_to_review）和“待签发”（to_sign）。

这三处还是 `a.version = (SELECT MAX(b.version) … b.kind = a.kind AND b.audience = a.audience)`，或 `NOT EXISTS (… b.kind = a.kind AND b.audience = a.audience AND b.version > a.version)`。

**失败场景**：同一事项里：
1. 任务一出“民事起诉状”Word，种类 agent_report，按种类编号 v1，带“论点未经确认”，已提交复核；
2. 任务二出“证据目录”Word，同样是 agent_report，按种类编号 v2。

结果两边口径不一致：
- 复核页 `review.completeness` 按 lineage 判断，起诉状是最新版、可以签发；
- 事项首页的“待签发”、任务二之前的“草稿待看”、“论点未经确认”“引用待核”这几条提示里，起诉状都没有了，因为按种类它是旧版。

律师按待办清单做事，会漏签这份起诉状，也看不到它的未决项。

**建议修法**：三处子查询都加 `AND b.lineage IS a.lineage`。SQLite 的 `IS` 能正确比较 NULL。可以在 `artifact-lineage.ts` 导出一段 SQL 片段，统一“最新版”条件，避免以后再漏。再补一条用例：两次任务各出一份 agent_report，`pendingChecks` 和 `derivedTodos` 都列出第一份。

## Q7-03 重要：“同名即同一份文件”会把不同文件并成一份

**位置**
- `packages/kernel/src/services/artifact-lineage.ts:15-17`：`docNameKey` 用 `/[-_ ]?\d{4}-\d{2}-\d{2}/g` 去掉文件名里所有日期，不只是 fileDay 后缀。
- `artifact-lineage.ts:40-42`：`runLineage` 规定，非回复草稿一律按 `name:<去日期文件名>` 认同一份文件。

**会撞名的来源**
- 场景固定名，每次任务都一样：
  - S1 审查意见书：`executor/deliverables.ts:206`，“审查意见书（内部稿）-日期.docx”；
  - 条款问题表：`deliverables.ts:230`；
  - 回稿比对报告、回稿差异表：`executor.ts:661,674`；
  - 脱敏报告：`executor.ts:730`。
  这些文件的 manifest 里也没有所审合同的编号，无法按合同区分。
- 模型起的标题：`tools/tools/review.ts:265` 的 `safeTitle(p.title)`，常见如“法律意见书”“律师函”“合同审查意见”。
- 工作区路径：`executor.ts:1111` 的 `workspaceArtifactName`，常见如“outputs-report.md”。

**失败场景**
1. 同一事项先后审甲合同、乙合同，各跑一次 S1。乙的“审查意见书（内部稿）”成了甲的新版：
   - 甲的意见书在复核页显示“已有更新版本”，`review.approve` 报 409 `approval_invalidated`；
   - 预览交付包把它归为“已有更新版本”；
   - 如果甲已签发，`approvals.verify` 的 `bindingStillCurrent` 变为 false，验签不再有效。
2. 同一事项先后起草给两个债务人的“律师函”（同一次任务里调用两次 `docx.render_report` 也一样），后一封取代前一封。
3. “2026-10-01会议纪要.docx”和“2026-10-15会议纪要.docx”，日期本身就是文件身份的一部分，`docNameKey` 去掉日期后都成了“会议纪要.docx”。

修复前这些情形也是这样，因为原来按种类判断，所以不是新回退。但提交说明和代码注释写的是“两次任务各出一份 Word，前一份不再被当成旧版”，而这里列的恰恰是律师最常遇到的几种情形，没有修到。用例（`v94-b25.test.ts:123-182`）只用了起诉状和证据目录这对不同名的文件。

**建议修法**
1. 场景成果的 lineage 带上所审对象：
   - S1、S1b 用所审合同的 `document_version_id`（`doc:`）；如果不同合同版本要视为同一份，可以用合同的版本链根；
   - 脱敏报告按任务。
2. Agent 工具成果和工作区文件，同名只在同一追问链内算新版（`run:<链根>:name:<名>`）。跨任务同名不当成新版，把“这是不是同一份”的判断交给律师，或在界面提示“与《…》同名，是否作为新版”。原则是只放宽、不收紧，和迁移注释的说法一致。
3. `docNameKey` 只去掉 fileDay 写的末尾日期，即 `-YYYY-MM-DD` 后接“-部分完成”或扩展名，不去掉文件名中间的日期。

## Q7-04 一般：新的“不作名字用字”和常用词让少数真名漏认或截短

**位置**
- `names.ts:46,51`：`NOT_GIVEN` 在 `givenOk` 里不分边界一律排除。
- `names.ts:353-355`：`readName` 末段遇到 `NOT_GIVEN` 首字整名返回 null，遇到次字截成单名。
- `names.ts:85-86`：新增的常用词。
- `names.ts:448`：称谓分支对 `slice(j+1, j+3)`，即名字前两字，也查常用词表。

**复现**（旧规则都认）：

| 输入 | 现行规则 |
|---|---|
| 原告：王项明，男 | （无），整名漏 |
| 被告：张小项， | 张小，漏出“项” |
| 王监军律师 | （无） |
| 李劳动律师 | （无），“劳动”进了常用词，称谓分支按名字前两字挡掉 |

`NOT_GIVEN` 里大多数字（且须只取写待按问询告哪些赔偿）确实很少用在名字里，“项”“问”“监”偶见。常用词新增的 28 个里，“劳动”“修正”“关键”“任意”在老一代人名里偶有出现。另外“应付、应收、高管、原样”按前两字判断，只挡“应付×”“高管×”这类极少见的名字，影响很小。

单看这一项风险不大。但它和 Q7-01 是同一个方向：为了消除方法正文里的误认，牺牲了召回。

**建议修法**
- `NOT_GIVEN` 只在没有明确右边界时排除（`loose === false` 或 `readName` 末段）。有标点、称谓、身份信息作右边界时照常认整名。
- 截短改为不认，免得漏出末字；或者截短时把整段交给二次检测提示。
- 称谓分支对名字前两字的常用词检查，不包括本批新增的这组词，它们是为“××的任务说明”这类前两字设的。

## Q7-05 一般：迁移回填与 `docNameKey` 算法不一致

**位置**：`migrations/0066_v94_artifact_lineage.sql:14-17` 与 `services/artifact-lineage.ts:15-17`。

**复现**（`node:sqlite` 跑回填表达式）：

| 文件名 | 回填 lineage | `docNameKey` |
|---|---|---|
| 合同-2023-12版.docx | `name:合同ocx`（把“-2023-12版.d”当成 11 字符的日期删掉） | `合同-2023-12版.docx` |

**后果**：升级前的旧版与升级后新出的同名新版不在同一 lineage。旧版在复核页、交付包里仍是“最新版”，可以签发，也能随包交出。迁移注释说“只放宽、不收紧”，但这里放宽的结果是旧稿可以当最新稿交出去。这几类文件名都来自模型标题或工作区路径；fileDay 写的“-YYYY-MM-DD”后缀不受影响，所以定为一般。

**建议修法**：回填不用 SQL 字符串运算。迁移后在启动时由 TS 跑一次：对 `lineage IS NULL AND run_id IS NOT NULL` 的行逐行用 `runLineage` 算，迁移系统支持 TS 步骤的话就放在迁移里。或者收窄 `docNameKey`（Q7-03 第 3 条），让 SQL 能写出同一算法。

## Q7-06 一般：同步来的成果不补 lineage

**位置**：`packages/kernel/src/sync-engine.ts:678-698`（`applyArtifact`）。

1. 还没升级的设备同步来的成果行没有 lineage 列，插入后为 NULL。回填只在迁移时跑过一次，这些行永远按种类单独成组：
   - 与本机同名的 `name:` 行互不取代，两份都显示“最新”；
   - 几份 NULL 行之间仍按种类互相取代，还是本批要修的老问题。
2. 反方向：新版设备的行带 `lineage` 键，`Object.keys(row)` 原样拼 INSERT，旧版内核会报 no such column。

## Q7-07 建议：任务页“最新修订稿”按文件内版本号排序

**位置**：`apps/desktop/src/pages/RunView.tsx:103`。

`runs.get` 现在经 `withFileVersions` 返回文件内第几版（`api/index.ts:1620`）。一次任务改了两份合同时，两份修订稿（`doc:A`、`doc:B`）都是 version 1。按 version 倒序稳定排序后取到的是 created_at 较早的那份，首屏“下载修订稿（Word）”“提交复核”针对的就不是最新的。以前 version 按种类递增，不会这样。

**建议修法**：改用 `is_latest` 加 `created_at` 排序，或者按 `kind_version` 排序（接口已返回）。

## Q7-08 建议：迁移里的 `json_extract` 没有 `json_valid` 兜底

**位置**：`migrations/0066_v94_artifact_lineage.sql:8-11`。

`json_extract('not json', '$.a')` 在 SQLite 里直接报错 malformed JSON。限定的几个 kind 目前写入处都是 `JSON.stringify`，`matter-lifecycle.ts:268` 清除时写的是 `'{}'`，都合法；同步来的行理论上可以是任意内容。迁移失败会让内核起不来，代价大。

**建议修法**：条件改为 `json_valid(manifest) AND json_extract(...) IS NOT NULL`。`api/index.ts:1875` 已经这样写了。
