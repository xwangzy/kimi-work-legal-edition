## 一句话结论

**修掉 H1、H2 两条以后可以合并（M1 建议同批修）。** 令牌与 scope 的设计没有发现伪造路径，“担保文字”也没有发现能夹带姓名的办法。问题出在提交依赖的前提：“送进 knownOnly 的原件文字，在此之前一定都完整识别过”。这个前提在两条常见路径上不成立。第一条是 docx.revise 的工具返回，第二条是非“修改文书”类复核里的清洁稿页眉页脚。这两条路径在本提交之前都会完整识别，本提交之后会把原件里的真实姓名以明文发往云端，事后只在去向记录里计数提示。

## 发现（按严重程度）

### H1（高）：docx.revise 返回的改前整段、编号顺延与互引文字按“模型写的”处理，可以带出从没识别过的原件文字

- **现象**：`egress-gate/src/readback-fields.ts:17,45` 把 docx.revise 结果里的 `changes`、`numbering_changes`、`conflicts`、`note` 等字段列为模型写的文字。这张规则表**同时被内核第一层用到**：`kernel/src/local-server.ts:411-413` 里 `tokenizeToolResult(raw, …, READBACK_MODEL_FIELDS[name])`。所以内核层和闸门层两层都只替换已知名单。
  - `changes[].before/after` 是原件**整段**的真实文字（`kernel/src/tools/tools/revise.ts:63-87` previewChanges 取 `paragraphs[para]`；`services/structured-patch.ts:294` 从原件直接取段落，不经令牌化）。助手只需要锚点命中段落里的一小段，整段其余文字助手未必读过。
  - `numbering_changes.renumbered[].text`（每个被顺延条款的开头 20 字）和 `references[].at`（任何写着旧条号的段落开头 24 字）来自原件里**助手没有改、也可能从没读过**的段落（`structured-patch.ts:226-235`）。
- **可达条件**：docx.revise 接受本事项的**任意**文档版本，不限于本任务快照（`structured-patch.ts:262-266` 只核对 matter_id）。`materials.list` 也会列出本事项全部文档和它们的编号（`tools/tools/review.ts:48-53`）。导入时不做令牌化：`api/index.ts` 的导入路径没有 tokenize 或 learnAliases，只有进过某次任务快照的材料，里面的姓名才进过代号表（`executor/executor.ts:1017-1020`）。所以，只要助手对一份没进本任务快照、也没进过以前任务快照的材料调 docx.revise，就会触发。比如律师另传了补充协议但没勾选，或者是早先导入、从没用过的文件。锚点只需要出现在令牌化视图里，写“甲方”“第一条”这类常见词就能命中。另外，即使在快照里，超过 200 万字被截断的部分也同样可达（`executor.ts:939-944`）。
- **影响**：原件里的自然人姓名以明文进入助手会话，并经闸门发往云端模型。识别不再学进代号表，以后每一轮都会重复发送。本提交之前，这些字段在两层都照常识别。
- **证据**：上文行号；用例 `egress-gate/test/b41-known-only.test.ts:280-322` 只覆盖“DOC 本身是助手写的”这一种情形。
- **建议改法**（任选其一，第一种最稳）：
  1. docx.revise 不进 READBACK 规则表，恢复照常识别。误认普通词的问题改在源头解决：内核在返回前，把 `before` 按原件已令牌化视图（`viewText`）取对应段落，这样不必让闸门放松；或者只对 `after` 里由助手 `proposed_text` 构成的片段按 knownOnly 处理。
  2. 退一步：docx.revise 在进入 `reviseOnce` 前，对目标原件全文（正文加页眉页脚）调用一次 `tokens.tokenizeAll(mid, …)` 并持久化，相当于复核阶段 `sources` 的做法提前到工具调用时。同时把 `numbering_changes` 从规则表里去掉。

### H2（高）：非“修改文书”类的复核里，清洁稿与修订稿的原件文字（含页眉页脚）只换已知名单，页眉页脚里的姓名从没识别过

- **现象**：`kernel/src/executor/executor.ts:1293-1328` 只在 `kind === "revise"` 时把原件文字放进 `sources` 先做完整识别。其他 kind 也会挑出本任务的 `revision_draft`、`revision_clean`（SQL 在 1295 行）。清洁稿的文字是 `headerFooterText(buf) + labeledTextWithRows(buf)`（1334 行），也就是包含原件页眉页脚。随后在 1464 行用 knownOnly 处理，并在 1488 行带 `model:known_only` 发出。页眉页脚不在材料快照里（parse 只解析 `word/document.xml`；提交说明自己也承认这一点），所以里面的姓名一定不在代号表里。
- **可达条件**：`contract-review` 映射为 `review` kind（`services/independent-review.ts:35`）。合同审查任务里助手按提示在原件上用 docx.revise 出修订稿和清洁稿（`executor.ts:981` 的工作方式说明），这是主场景之一。即使是 `revise` kind，也有三种情况可达：一次任务修订了两份以上原件，因为 `sources` 只取最后一份清洁稿的原件（1305 行 `.at(-1)`），而 docs 最多取 4 份；清洁稿 manifest 缺 `source_document_version_id`；读原件失败，因为 1322-1325 行 `catch {}` 静默吞掉。另外，H1 里没进快照的原件，正文同样走这条路。
- **影响**：页眉页脚里常见“承办人 / 联系人 / 签字人”的姓名会以明文发往云端复核模型。复核意见里如果引用了这些姓名，还会经“担保文字”再发一次（见 C-2）。
- **建议改法**：`sources` 不再按 kind 区分，凡是 picked 里的 `revision_clean` 和 `revision_draft`，都按各自 manifest 的原件完整识别。读不到原件或 manifest 缺字段时，**这份文书不走 knownOnly**：要么整个复核请求不带 `knownOnly`，要么这份文书在内核里先做完整识别。不要用 `catch {}` 静默降级成少遮。

### M1（中）：“出文书 / 改文书只能作用于助手自己生成的成果”这一前提不成立：修改对照表是 agent_report，里面是原件原文

- **现象**：docx.revise 会登记《修改对照表》，kind 为 `agent_report`，run_id 为本任务（`tools/tools/revise.ts:366`，registerComparison 在 449 行前后）。表里是原件整段的“修改前”，文件名由律师上传的原件文件名派生。`r.changes` 还包含页眉页脚行（`structured-patch.ts:493` 的 `[...hfRows, ...]`）。docx.edit_draft 只核对 `run_id` 和 `kind === "agent_report"`（`tools/tools/edit-draft.ts:134-137`），所以可以作用在这份对照表上。它返回的 `repeated_sentences` 是对照表里的原句，`note` 里有 `《${name}》`（原件派生的文件名，222、235 行）。按本提交，这些整体按 knownOnly 处理（`readback-fields.ts:40`）。复核阶段也会把这份对照表当成 docs 和 inventory 发出。
- **可达条件**：助手在修订之后想“修一下对照表”；或者律师上传的原件文件名里含姓名、而这份原件不在快照里，因为快照只对进了快照的文件名做识别（`executor.ts:1019`）。
- **影响**：原件页眉页脚和正文的原句、原件文件名里的姓名，可能明文外发。现实里的可达性比 H1、H2 低。
- **建议改法**：edit_draft 和 READBACK 规则只对 `manifest.tool === "docx.render_report"` 或 edit_draft 自己派生的版本生效；对照表（`manifest.tool === "docx.revise"`）拒绝用 edit_draft 修改，或者把它的结果按照常识别处理。

### M2（中）：二次检测只计数、不拦截；knownOnly 路径会让“疑似姓名”提示变成常态噪音

- **现象**：knownOnly 路径上 suspects 仍会计算（用例 `b41-known-only.test.ts:259-260` 验证过）。闸门把它写进去向记录（`egress-gate/src/server.ts:485`）。界面在“数据去向”里显示“另有 N 处像姓名的原文没有替换为代号，已随这次请求发出”（`apps/desktop/src/components/DataFlow.tsx:76-78`）。**发送照常进行，不拦截**。
- **影响**：H1、H2 漏出的真名**会**被计数并在界面提示，D 项的要求算基本满足，但这是事后提示。另外，本提交要解决的正是“曾根据”“应发工资”这类误认词。现在这些词不再替换，就会转而触发 suspects。几乎每次复核和每次修订读回都会出现“有 N 处像姓名的原文已发出”，律师很快会习惯性忽略，真漏的那一次也就看不出来。
- **建议改法**：knownOnly 请求里 `suspects.high > 0` 时，至少按任务汇总进时间线，必要时把这一条请求降级为完整识别后重发。界面把“复核请求里的疑似项”单独列出，不要和日常读回混在一起计数。

### L1（低）：读回结果 JSON 解析失败时整段按 knownOnly 处理，失败方向偏少遮

- **现象**：`egress-gate/src/chat-payload.ts:136` 在 `!parsed` 时走 `tok(raw, true)`。这是 D-157 第二步的既有策略，本提交把它扩大到五个新工具。docx.revise 里本来特意排除了 `header_footer*` 字段，引擎截断超长结果时这些字段会一起变成 knownOnly。
- **影响**：只影响闸门这一层。内核第一层是对对象逐字段处理，不受解析影响，所以页眉页脚字段在内核层已照常识别。单独看风险低，但与 H1 叠加时没有第二道兜底。
- **建议改法**：解析失败时，对“规则不是 `() => true`”的工具（目前就是 docx.revise）按照常识别处理。

### L2（低）：担保文字本身只做过 knownOnly 处理，会把复核模型看到的东西原样再发一次

- **现象**：`executor.ts:1564-1566` 里的 goal = `fixPrompt(findings, review.text, fixTargets…)`，经 knownOnly 处理后登记为担保文字。只要复核请求里漏过真名（H1、H2），复核意见引用了它，修改轮就会再发一次，而且闸门对这一段只替换已知名单。
- **影响**：放大 H1、H2，本身不新增来源。
- **建议改法**：H1、H2 修好后，这条自然收敛。也可以在登记前对 goal 跑一次 suspects，有 high 级别时不登记。

### L3（低，功能面）：担保文字只在内存、按 runId 保存，追问任务（新 runId、同一会话）里旧提示回到完整识别

- `kernel/src/egress/kernel-gate.ts:415-420`。失败方向是多遮，不是安全问题。但律师追问时，误认问题会在会话历史里重新出现，可能又触发“无出处代号”的连锁反应。建议在偏离记录里注明。

## 逐题回答

### A. 有没有真实姓名以明文发往云端的路径

| 复核请求的组成部分 | 进入请求前是否完整识别 | 依据 |
|---|---|---|
| 委托原话 goalSent（含追问） | 是，开工前 `tz.tokenize` | `executor.ts:1025-1029` |
| 材料快照 | 是，`tokenizeAll`，不超过 200 万字；文件名同样识别 | `executor.ts:1015-1020` |
| 律师对提问的“其他”回答 | 是，收到时识别 | `api/w1.ts:155-158` |
| 退回计划的意见 | 是 | `api/w1.ts:130`、`kap-agent-client.ts:636-639` |
| 立场、法域 | 是，本提交新增 | `executor.ts:1457` |
| 文书全文（render_report 出的） | 文书里的真名由已有代号还原，成立 | — |
| **清洁稿、修订稿的原件文字（含页眉页脚）** | **只有 revise kind、且只有最后一份原件** | H2 |
| 差异 diff | revise kind 下与 sources 同源 | 同 H2 |
| 文件清单、标题 | 原件派生的文件名只有进过快照才识别过 | M1 |
| 最终答复 | 模型写的；会受 H1 污染 | — |

其余几类：律师在审查工作台“修改后接受”的 `lawyer_text`、成果页改写的事实陈述、论点提纲、事项标题，都**不在复核请求里**（`reviewMessages` 的入参见 1472 行）。riskcards、facts、outline 读回时律师字段照常识别，是既有逻辑。工作区命令行读到的材料是快照文件，已令牌化。OCR 文本经 parse_texts 进快照，与正文同口径。

五个工具：render_report、xlsx.render_table 的入参是助手写的。xlsx.edit_cells 限定 `agent_table` 加本任务（`tools/tools/review.ts:445-447`），**不能**作用于律师上传的 Excel，这一点可靠。edit_draft 的限定不足以排除原件文字（M1）。docx.revise 的改前整段、编号顺延和互引是主要漏口（H1）。冲突详情 `detail` 是引擎报错的前 200 字，我没有核实引擎报错里会不会带出段落原文（见“未核实”）。

### B. `model:known_only` 能否被拿到或伪造

没有发现路径。
- 密钥：`kernel/src/identity.ts:35`，进程启动时 `randomBytes(32)`，只在内存，不进环境变量、不下发子进程。重启后全部失效。
- 签发：带这个 scope 的令牌只出现在 `kernel/src/index.ts:356-359` 的 gateTokenFor 里，由 `ModelBroker` 的 `args.knownOnly` 触发（`model-broker/src/broker.ts`）。唯一传 `knownOnly: true` 的调用方是 `executor.ts:1488`。
- 宿主：运行令牌 scope 固定为 `model:chat` 加可选的 search、fetch（`kap-agent-client.ts:507`）和 `tool:legal`（511 行）。宿主经本机端点转发时，`local-server.ts` 的 handleChat 以 `bearer` 原样转交，没有任何请求字段能映射到 `knownOnly`。
- 校验：`gate-host.ts:175` 只在 purpose 为 model、且令牌 scope 含这一项时生效；不看请求头和请求体。
- 有效期与绑定：600 秒，绑定 tid、uid、mid、rid、aid、fen，尝试结束即失效（活性检查）。令牌**不是一次性**的：没有 jti，在有效期内可以重复用于本尝试的任意模型请求。但令牌只在内核与闸门子进程之间传递，宿主拿不到，可以接受。建议加 jti，并在 note 里写明用途，便于审计。

### C. 担保文字

- 登记：只有 `KernelGate.vouchKnownOnly` 能登记，调用方只有 `executor.ts:1566`。宿主和模型没有登记通道。
- 匹配：用 `indexOf` 做**子串逐字**匹配（`chat-payload.ts:92-99`）。担保段内部按 knownOnly 处理，前后各自照常识别（递归）。担保文字是内核生成的定长文本，不可能往里面“夹带”姓名，任何改动都会对不上，回到完整识别。跨边界的情形是：宿主在担保段前后紧贴一个姓名的半边，而担保段首尾恰好也是姓名的另半边。担保段的首尾是内核模板文字，实际不可达。20 字下限的作用是防止短串到处命中，与防夹带无关；对于防夹带，下限高低都无所谓。
- 失效：内核重启后清空；每个任务保留最近 4 条、最多 200 个任务；按 runId 隔离。runId 全局唯一，所以不会在事项之间或并发任务之间串用。失败方向都是多遮。
- 真正的问题是担保**内容**的来源：见 L2。

### D. 二次检测

knownOnly 路径上仍然生效、仍然计数，并在“数据去向”界面提示（M2），但不拦截，只是事后提示，而且会被误认词的噪音淹没。内核侧 `tokenizeAll(..., {knownOnly})` 不单独报 suspects，要靠闸门这一层的计数。

### E. 失败时的默认方向

| 环节 | 方向 |
|---|---|
| 令牌缺 scope 或不是内核签发 | 完整识别（多遮） |
| 担保文字对不上、太短、内核重启 | 完整识别（多遮） |
| 规则表里没有的工具 | 完整识别（多遮） |
| 读回结果 JSON 解析失败 | **只换已知名单（少遮）**（L1，既有策略被扩大） |
| 复核时读原件失败、清洁稿缺 manifest、非 revise kind | **静默不学、照样 knownOnly（少遮）**（H2） |
| 没有令牌存储（tz 为空） | 只替换直接标识符（既有） |

### F. 用例覆盖与缺口

已覆盖：knownOnly 整段不学新姓名、标识符照换、suspects 照常计数；担保文字的命中、改动、过短；五个工具进规则表、改前整段原样、页眉页脚照常识别；端到端：委托原话里的新姓名、材料里的真名在复核请求里仍是代号；修改轮引用的原句原样。

缺：
1. docx.revise 作用于**不在本任务快照里**的原件时，`changes.before` 和 `numbering_changes` 里原件段落的姓名不外发（H1）。
2. contract-review（review kind）任务出了清洁稿，原件页眉写“承办人：某某”，复核请求里该姓名不是明文（H2）；同一任务修订两份原件（H2）；读原件失败时不降级为少遮（H2）。
3. docx.edit_draft 作用于修改对照表时被拒绝，或者结果照常识别（M1）。
4. 令牌层：宿主运行令牌和本机端点转发的请求不能触发 knownOnly；gate-host 授权器单元测试只看 scope；带这个 scope 的令牌在尝试结束后被拒绝。
5. 读回结果解析失败时 docx.revise 的处理方向（L1）。
6. 担保文字在追问任务（新 runId）里的行为（L3）。

## 没能核实的部分

- docx-engine `applyRevisionsToDocx` 的报错文案会不会带出段落原文。如果会，`conflicts[].detail` 也属于 H1 一类。
- render_report 的交付前检查（`deliverableQualityFor`）会不会扫到本所函头或页眉里的律师姓名并摘句返回。函头来自所里设置，不在代号表里。
- parse_texts 与 `extractParagraphs` 对域代码、内容控件、文本框的覆盖是否完全一致。如果不一致，即使原件在快照里，H1 也成立。
- 闸门子进程与内核之间传递令牌的通道是否只有本进程可达（没读 `createGateProvider` 的传输细节）。
- 没有运行任何用例。
