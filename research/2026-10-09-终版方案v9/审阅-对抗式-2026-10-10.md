## 一、WASM 执行域（第 02 篇 §9.10、第 04 篇 §4.1，v9 最大新设计）

### A1【阻断】把 Python 换成 Pyodide，等于拆掉 just-bash 的 Python 安全模型；“Python 只能经桥接访问虚拟文件系统、没有系统调用通道”对 Pyodide 不成立

**问题**：v9 把 just-bash 的 `python3` 替换为“自定义可信命令：Pyodide（WASM CPython 3.13）+ 离线包”（04 §4.1 进程图），并据此宣称“Python 在 WASM 线性内存里运行，没有系统调用通道，只能经桥接访问虚拟文件系统；没有网络实现即无法联网”（02 §9.10“为什么可以作为默认”第 2 条；04 §4.1“隔离来源（如实）”）。这对 just-bash 自带的 Python 成立，对 Pyodide 不成立：

- just-bash 自带的 `python3` 是 **CPython-Emscripten**（`vendor/cpython-emscripten/python.wasm` + `python313.zip`，只有标准库，跑在 worker 线程里），其 worker 源码开头明确写着安全模型是“**CPython Emscripten has zero JS bridge code**”（`src/commands/python3/worker.ts:5`），文件访问经 `SyncBackend` + `SharedArrayBuffer` 桥回 just-bash 的虚拟文件系统（同文件 :25、:178-187 “HOSTFS backend that bridges to just-bash's filesystem”）。这是 just-bash 作者为“不可信 Python”刻意做的选择。
- **Pyodide 的设计目标正相反**：它内置完整的 Python⇄JS 互操作（`import js` 即宿主 JS 全局对象；`pyodide.code.run_js()` 执行任意 JS；`pyodide.ffi`），在 Node 里意味着 guest Python 可以拿到宿主 realm 的 `process`、动态 `import("node:fs")` 等。04 §4.1 写的“`pyodide.http`/`js.fetch` 等桥接在进程启动时移除”只删了网络入口，`js`/`run_js`/`pyodide_js`/`_pyodide` 内部模块仍在，且从 `sys.modules` 删除可被重新导入或经内部对象取回。Pyodide 官方 FAQ 也没有任何“可运行不可信代码”的承诺。
- 一旦 guest 能执行宿主 JS，W 域对 Python 的实际边界就退化为 **Node 权限模型**；而 Node 官方文档原文：该特性“does not protect against malicious code……implements a ‘seat belt’ approach……does not provide security guarantees in the presence of malicious code”，并在“Limitations and Known Issues”中写明“**Symbolic links will be followed even to locations outside of the set of paths that access has been granted to**”（nodejs.org/api/permissions.html，v26.11.1）。v9 自己也承认它只是“安全带”（02 §9.10 第 2 条）——但随即又把它当作 Python 的实际边界。

**证据**：04 `04-技术架构与KimiCode集成.md` 第 157、176–177 行；02 第 445 行；just-bash `packages/just-bash/src/commands/python3/worker.ts:5,25,178-187`、`python3.ts:300`（`new Worker(workerPath…)`）；just-bash README“Python Support”（“CPython compiled to WASM”）与“Security Model”；Node Permissions 文档。

**为什么重要**：W 域是 v9 对外“AI 写的代码默认在无网络的 WASM 执行域里运行”（02 §12、05 第 70 行）与“默认档自动执行、不弹窗”（02 §9.3）的唯一依据。注入后的模型写一段 Python 就能在 W 进程内执行任意 JS：读 `--allow-fs-read` 授权范围内的一切（含运行时目录与其他已挂载内容）、借助符号链接跟随越界、在工作区内创建符号链接/硬链接投毒后续宿主读取。对外承诺与默认放权都建立在一个不成立的前提上。

**建议修改**：
1. **02 §9.10、04 §4.1 改口径**为：“bash 命令由 TypeScript 解释器在宿主 JS realm 内执行（无 VM 隔离，依赖实现健壮性）；Python 若用 Pyodide，guest 可调用宿主 JS，边界等于 W 进程本身（Node 权限模型 + 作业对象 + 独立进程），**不是 WASM 级隔离**。”“天然无网”改为“W 进程未授予 `--allow-net`（运行时强制，非 OS 强制）”。
2. **技术路线三选一并在 G0 P2 明确判定**：(a) 沿用 just-bash 自带的“零 JS 桥”CPython，自建 numpy/pandas/openpyxl 等对该 CPython 的 Emscripten 轮子（工作量大，但边界真实）；(b) 用 Pyodide，但自编译剥离 `js`/`pyodide.ffi`/`run_js`/`pyodide_js` 并维护分支（W4 工作量须从 22 人周上调）；(c) 接受 Pyodide 原样，把 W 定位为“进程级隔离”，再叠加 OS 层：W 进程以**独立低权限身份**运行（Node 文档自己给出的建议：“run sandboxed and target processes under different OS users, or use OS-level isolation”），这又回到需要一次管理员授权的问题，须在 06 的 U2 写清退路。
3. Python 的文件访问**不得用 NODEFS 直挂真实目录**，应仿照 just-bash 的 SyncBackend 桥，所有路径经 just-bash 虚拟文件系统（`allowSymlinks:false`）。
4. 06 T03 与 04 §11 P2 的逃逸用例补充：`import js`、`from pyodide.code import run_js`、`import pyodide_js`、重新导入被删模块、在 `/work` 创建指向外部的符号链接/硬链接/junction 后由宿主 Read 读取。

### A2【阻断】对外“隔离强度”表述夸大，应给出分层的准确说法

**问题**：02 §9.10 第 3 条“一致、无管理员、无杀软冲突”、第 4 条“W 覆盖 100%”、01 §8 第 1 条“同时解决了隔离、Windows Git Bash 依赖与杀软兼容三个问题”、01 §4 表 T3/T7“通过”、03 第 109 行设备自检显示“可安全运行代码（WASM 执行域）”，都把 W 当作与 MXC/原生沙箱同级、甚至更普适的“强隔离”。但按 A1 与 just-bash 自述（README Security Model：“All execution happens without VM isolation……designed to be robust against prototype-pollution attacks”；“Node worker `resourceLimits` do not reliably cap the WebAssembly linear memory……strong memory containment……requires process/container isolation”），W 的真实强度是“**语言运行时隔离 + Node 运行时权限（安全带）+ 进程资源限制**”，弱于 OS 强制的 MXC/AppContainer/独立用户。

**证据**：just-bash README“Security Model”整段；Node Permissions 文档；02 第 446–449、511 行；03 第 109 行；01 第 75、79、185 行。

**为什么重要**：律所 IT 与客户会把“可安全运行代码”理解为 OS 级沙箱；一旦出现 just-bash 原型污染或 Pyodide 桥接逃逸事件，v9 的对外口径（05 第 70 行写进销售话术）就构成失实陈述。

**建议修改**：
- 设备页与 03 自检文案改为三档如实显示：“**代码运行：运行时隔离（W）**——无网络由运行时强制、文件范围由运行时强制，非操作系统沙箱”/“**原生增强：系统强制（MXC）**”/“**未隔离：不运行代码**”。
- 01 §4 表 T7 对 v9 的评价从“通过”改为“部分（W 为运行时强制；系统强制依赖 MXC 覆盖率）”；01 §8 第 1 条删去“同时解决了隔离”的绝对化表述。
- 律所策略增加选项：“L3a/L3b 事项仅在系统强制执行域（N）运行代码，否则只运行可信工具”——W 适合 L0–L2 的默认放权，不宜覆盖“全部事项级别”（02 §9.10 表“适用：全部事项级别、全部 Work 模式”）。

### A3【重要】宿主路径与执行域路径是两套命名空间，Bash 与 Read/Write/Grep 会互相找不到文件

**问题**：Kimi Code 的 Bash 工具把**宿主路径**经 `shellPathBridge` 转换后拼进命令：`cd '<shellCwd>' && <command>`（`bashTool.ts:163-164`），`effectiveCwd = view.resolve(args.cwd ?? view.workDir)` 也是宿主路径（:191）；Read/Write/Edit 经 `IHostFileSystem` 用宿主绝对路径；系统提示告诉模型的工作目录也是宿主路径。v9 却让 W 只挂载 `/materials`、`/work`、`/out`、`/tmp`（04 §4.1），并写“kap-server workspace = 事项工作区（执行域的 `/work`）”（04 §3.2“工作区”行）。结果：模型在 Bash 里写出 `/work/out.xlsx` 后用 Read 读 `/work/out.xlsx` 会落到宿主 `C:\work\…`；反之模型把 Read 看到的 `C:\Users\…\work\a.csv` 写进 Python 脚本，W 内不存在。Windows 上 `shellPathBridge` 在 `osKind==='Windows' && shellName==='bash'` 时启用（`shellPathBridge.ts:56`），而 Windows 探测把 `shellName` 硬编码为 `'bash'`（`environmentProbe.ts` 第 77–86 行），并会尝试在占位 shell 同目录找 `cygpath.exe` 再用 `execFileSync` 直接起进程（`shellPathBridge.ts` 第 60–80 行区段）。

**证据**：上列源码行；04 第 102–103、146–158 行。

**为什么重要**：这是 P2“20 类律师数据任务”最先会撞上的问题；不解决，Agent 会在两套路径间反复试错、消耗 token，或把文件写到错误位置。

**建议修改**：04 §3.2/§4.1 明确**单一路径命名空间**：要么 W 的挂载点与宿主路径的 shell 形式一致（如把工作区挂在 `/c/Users/<u>/…/matters/<id>/work`），要么把种子化的 `IHostFileSystem` 也虚拟化为同一 `/materials`、`/work`、`/out` 命名空间并令 `pathClass=posix`；执行域路由负责解析并剥离 `cd '<…>' &&` 前缀；`cygpath` 查找改为不可达（或种子化环境服务返回固定 `shellName`）。补一条 P2 通过标准：“Bash 生成的文件可被 Read/Edit/Grep 以同一路径访问，反之亦然”。

### A4【重要】just-bash 的 `rg` 与 Kimi Code 的 Grep/Glob 参数不兼容；“G0 以性能决定”判据错误

**问题**：04 §4.1 路由表写 Grep/Glob 的 `spawn(rg, args)` 走“W 内的 `rg` 实现；或随包签名的原生 ripgrep……G0 以性能决定”。核对实际参数：

| Kimi Code 实际传参 | 位置 | just-bash rg 支持情况 |
|---|---|---|
| `--sortr=modified` | `globTool.ts:360`（Glob 每次都传） | `parseSort` 只接受 `--sort`/`--sort=` 且值仅 `path`/`none`（`rg-parser.ts:621-643`），`--sortr` 落入未知参数报错（:795-800） |
| `--field-context-separator :` | `grepTool.ts:451`（content 模式带行号时） | `rg-parser.ts`/`rg-options.ts` 无此参数 |
| `--max-columns N` | `grepTool.ts:433` | 无此参数 |
| `rg --version`（定位探测） | `rgLocator.ts:56` | 无此参数 |
| `--no-require-git`、`--json` | `fsService.ts:663-667,879-888`（界面文件搜索） | 前者无 |

即 Glob 每次都会失败、Grep 的常用模式会失败、rg 探测会判定“rg 不可用”。另外 Grep 输出依赖 `--null` 分隔的宿主路径记录（`grepTool.ts:435,485-526`），W 返回的虚拟路径还要逆映射（见 A3）。

**证据**：上表源码位置；just-bash `src/commands/rg/rg-parser.ts`（main，3.6.0）。

**为什么重要**：Grep/Glob 是 T0 默认自动的高频工具（02 §9.4），一旦走 W 即整体失效；判据写成“性能”会让 G0 误判。

**建议修改**：04 §4.1 路由表改为：“Grep/Glob **默认用随包签名的原生 ripgrep 作为可信工具**（cwd 固定为事项工作区、拒绝绝对路径与 `..`、拒绝 `-L/--follow/--pre/--search-zip`、路径参数经文件 broker 规范化），W 内 `rg` 只服务模型在 Bash 里自己写的命令”；或写明需自建参数翻译层并列入 W4 工作量。02 §9.4 表 T0 的“Glob/Grep 在执行域”同步改为“可信 rg（受限参数）”。

### A5【重要】`IHostProcess` 可以由非 OS 进程实现，但 v9“同一事项最多 1 个 W 进程”与 Kimi Code 的后台任务、超时转后台、两阶段终止语义冲突

**问题**：接口本身只要求 `pid/exitCode/stdin/stdout/stderr/wait()/kill(signal)/dispose()`（`hostProcess.ts:17-28`），用 PassThrough 流 + 合成 pid 可以满足。但语义上：
- **超时转后台**：前台命令默认 60 秒、最长 5 分钟；超时后默认**不杀而转后台**（`bashTool.ts:118-120,239`；`bash.ts:6-9`），后台默认 10 分钟、最长 24 小时，`disable_timeout` 可不设超时（`bashTool.ts:193-197`）。just-bash `hardened` 档默认 `maxExecutionTimeMs: 30_000`（README“Execution Protection”）。v9 写“单次命令默认 60 秒（后台 10 分钟）”，没有处理 5 分钟前台上限、24 小时后台上限与 `disable_timeout`。
- **终止**：`ProcessTask` 在取消时发 `SIGTERM`（`process-task.ts:58-60`），`forceStop` 发 `SIGKILL`（:89-97）；ripgrep 路径是 SIGTERM → 5 秒宽限 → SIGKILL（`runRg.ts:50-76`）。just-bash 的 `signal` 是协作式取消，“stops at next statement boundary”（README 选项表）；Pyodide 的死循环只能靠中断缓冲区或终止 worker/进程。若同一事项只有一个 W 进程，SIGKILL 只能杀整个进程，会连带杀掉该事项其他后台任务与子 Agent 的命令。
- **流式输出**：`ProcessTask` 按 `data` 事件逐块写任务输出（`process-task.ts:143-156`），前台超 `DEFAULT_TOOL_RESULT_MAX_CHARS` 时落盘（`bashTool.ts:221-228`）；just-bash README 的 `exec()` 只给聚合结果，未见流式接口——后台任务的 TaskOutput 在完成前将一直为空。
- **并发**：AgentSwarm 并发 3 + 主 Agent + 后台任务，都可能在同一事项同时跑 Bash（02 §9.7），与“同一事项同时最多 1 个 W 进程”（04 §4.1 资源行）冲突，要么排队（体验与超时连锁），要么一个进程内多实例（一个 Pyodide 同步循环会阻塞同进程所有 bash 实例的事件循环，除非每条 Python 都在独立 worker）。

**证据**：上列源码；04 第 175 行。

**建议修改**：04 §4.1 增加“W 进程模型”小节：每事项一个 W 监督进程，**每次 Bash 调用一个 worker（Python 再各占一个可终止 worker）**；`kill('SIGTERM')`→AbortSignal + 宽限，`SIGKILL`→`worker.terminate()`；pid 用合成 ID；stdout/stderr 需要 just-bash 侧的流式回调（列为对上游的需求或自维护补丁）；超时策略与 Kimi Code 的 60 s/5 min/10 min/24 h 档位逐一对齐（或经 `bashTaskTimeoutS`、`bashAutoBackgroundOnTimeout` 配置收紧并写入能力账本）。资源行“同一事项同时最多 1 个 W 进程”改为“同一事项最多 N 个并发 W worker（N=活动执行单元数）”。

### A6【重要】just-bash 明文警告“不要通过宿主文件系统 API 并发修改 ReadWriteFs 根目录”，而 v9 的 `/work` 正是多方并发写入

**问题**：README 写明：“Do not mutate a `ReadWriteFs` root concurrently through direct host filesystem APIs. Node.js does not expose the descriptor-relative operations needed to make pathname validation atomic against an external actor”，且元数据操作“not atomic against a trusted host actor concurrently replacing that pathname with a symlink”。v9 中同一事项工作区同时被 kap-server 的 Write/Edit（宿主 `IHostFileSystem`）、文件历史与快照回滚、Office 桥写回、**端到端加密同步客户端写入同事的修改**、后台 Bash 并发写入（04 §3.2“工作区”、§4.4、§7）。

**证据**：just-bash README“ReadWriteFs”节第 267–281 行（本地抓取副本）；04 第 103、154、198–201 行。

**为什么重要**：这正是 just-bash 自认的 TOCTOU 窗口；叠加 Node 权限模型“符号链接会被跟随到授权范围之外”，构成可组合的越界路径。

**建议修改**：04 §4.1/§4.4 规定：W 每次执行使用**工作区快照 + 写回**（OverlayFs 读 + 执行结束由文件 broker 校验后原子提交），或在 W 执行期间对该事项工作区加写锁（同步客户端、Office 桥、Write/Edit 排队）；文件 broker 拒绝任何一方在 `/work` 内创建符号链接、硬链接、junction。

### A7【重要】并非所有子进程都经过 `IHostProcessService`，“seeds 替换进程服务即可路由全部子进程”不成立

**问题**：04 §4.1 的路由规则以“锁版源码中调用进程服务的位置”为全集，“其他—默认拒绝并记审计”。但锁版中仍有直接调用 `node:child_process` 的位置，seeds 拦不到：`agent-core-v2/src/features/tower/protocol/git.ts:1,27`（`execFile` 调 git，实验特性）、`kap-server/src/lib/fileLaunch.ts:2,198`（`spawn` 打开本机程序）、`_base/execEnv/environmentProbe.ts:1`（`execFile`）、`_base/execEnv/shellPathBridge.ts`（`execFileSync` 调 cygpath）。

**建议修改**：04 §3.4 补丁台账增加一条 P0：“删除或封闭 `fileLaunch.ts` 的直接 spawn（不只依赖路由不可达）；`tower` 以 ZP-13 锁死为关闭；CI 增加‘`node:child_process` 只允许出现在白名单文件’的静态检查，上游升级时自动报警。”

### A8【一般】“Node ≥ v25”应改为 Node 26 LTS，并写明随包分发第二个 Node 运行时

**问题**：04 §4.1 与进程图写“独立 Node（≥ v25）运行时”。Node 25 是奇数版（Current），按 Node 发布节奏已于 2026-06 结束支持；当前文档版本为 v26.11.1。另需随包分发独立 `node.exe`（Electron 内嵌 Node 无法这样用 `--permission`），其签名、更新节奏、杀软信誉要单列；Kimi Code 自身要求 Node ≥ 24.15（仓库 `CLAUDE.md` 环境要求），Agent 宿主所在 Electron 的内嵌 Node 版本也要核对。

**建议修改**：04 §4.1、§10 供应链表改为“Node 26 LTS（锁定小版本与 digest），`--permission` 不授予 `--allow-net/--allow-child-process/--allow-addons/--allow-wasi/--allow-ffi`”；把“验证 `--allow-net` 是否覆盖 DNS 解析（`dns.lookup`）”列入 P2 用例（02 §13 第 2 条已要求 DNS 失败，但正文未说明强制点）。

### A9【重要】后台任务输出文件在会话目录、明文、且模型被指示去 Read 它——与“事项三区文件系统”冲突

**问题**：任务完成通知会对模型说“Read the output file to retrieve the result: <outputPath>”（`taskService.ts:1457-1460`），输出文件是任务持久化根目录下的 `output.log`（`persist.ts:14,140`），不在事项工作区。v9 把 Read 限制为事项三区（04 §2 能力账本“文件读取与搜索”），模型按指示读取会被拒；同时该日志含事项内容却不在 ZP-9“加密落盘扩面”清单（会话存储、文件历史与快照、导出包、插件存储）内。

**建议修改**：04 §3.4 ZP-9 增列“后台任务输出日志（`task/persist.ts`）”；文件 broker 为“本会话任务输出目录”开只读例外，或把任务输出根目录种子化到事项工作区的隐藏子目录。

## 二、kap-server 私有嵌入（第 04 篇 §3）

### B1【重要】“只由 Agent 宿主访问”在回环 TCP 上并不天然成立；更好的做法是不监听端口

**问题**：04 §3.2 设计为 kap-server 在 Agent 宿主进程内 `startServer` 并“只绑定回环”，宿主再经 HTTP/WS 调它。但：
- 回环端口对本机**所有进程、所有用户**可连；能否调用只取决于 bearer 令牌。回环模式下鉴权失败限速被关闭（`start.ts:179-180`：`exposureClass === 'loopback' ? undefined : createAuthFailureLimiter(...)`）。令牌足够长时不可暴力破解，但令牌在宿主进程内存中，同用户恶意进程可读；N 域（MXC）若未屏蔽回环，guest 也能尝试连接。
- “不写令牌文件”可行，但前提是**显式注入** `authTokenService`（`start.ts:116,186-187`）；否则默认 `createTokenStore(homeDir)` 会持久化令牌（:189）。远程控制管理器无论如何都会创建，并持有 `localServerToken: () => authTokenService.getToken()`（:219-222），只靠路由不可达 + ZP-8 保证它不被启用。
- 更根本的是：v9 选 kap-server 的理由（文件历史、快照、子会话、持久审批与提问）其能力本体在 agent-core-v2：`routes/fileHistory.ts:1-5` 直接从 `@moonshot-ai/agent-core-v2` 引入 `IAgentFileHistoryService`；kap-server 自己就是在进程内 `bootstrap(..., seeds)` 后经 DI 取服务（`start.ts:198-211`）。仓库还提供 `@moonshot-ai/klient` 的 `memory`/`ipc` 传输（仓库 `CLAUDE.md` 项目地图）。

**为什么重要**：v9 把“界面不见管理面”写成不可退让约束（04 §1.2 第 4 条），但实现上保留了一个本机任何进程都可连接的 HTTP 管理面，只靠令牌保护；P1 的“从宿主外不可达”在端口存在时只能证明“无令牌不可用”。

**建议修改**：04 §3.2“进程与令牌”改为优先级：①**不监听**：Agent 宿主直接调用 `bootstrap` 并经 DI 访问所需服务，或用 klient `memory` 传输，或 Fastify `inject()`（无端口）；②若必须监听，绑定命名管道/Unix 套接字并设置仅当前用户与宿主进程可访问的 ACL；③注入内存令牌服务（明确写“禁止使用默认 tokenStore”）。P1 通过标准补“端口扫描：Agent 宿主不监听任何 TCP 端口（或仅命名管道且 ACL 正确）”。

### B2【一般】ZP-4 不是“种子注入”，而是对策略链构造函数的源码补丁；宿主策略必须“永不弃权”

**问题**：04 §3.2 seeds 行把“宿主策略服务 → 策略链首位（ZP-4）”列为 seed，§3.4 又写 ZP-4 是补丁“待实现”。实际结构：策略链是 `AgentPermissionPolicyService` 构造函数里**硬编码的数组**（`permissionPolicyService.ts:39-55`），注册在 Agent 作用域（:69-75）；`evaluate` 取第一个非 `undefined` 结果（:61-64）；闸门订阅 `toolExecutor.onBeforeExecuteTool`（`permissionGateService.ts:30`）。因此需要源码补丁（或在 Agent 作用域替换整个服务，需确认 kap `seeds` 能否覆盖 Agent 作用域注册）。宿主策略若对某工具返回 `undefined`，链会继续走到 `AutoModeApprove`、`YoloModeApprove`、`DefaultToolApprove`、`GitCwdWriteApprove` 等自动放行策略；另外 `bootstrap.args.nonInteractive` 为真时 `DangerousCommandAsk` 会被移除（:42-44），无界面的律所执行器/云端执行器形态要注意。

**建议修改**：04 §3.2 seeds 行删去“宿主策略服务”，改写为“ZP-4 源码补丁：构造函数首位插入由 seed 提供的 `IHostPolicy`；宿主策略对所有工具必须返回 approve/ask/deny 之一（不得弃权），单测断言链中其后策略对任何工具都不会被触达”。P1 通过标准补“遍历全部内置工具与 MCP 工具，断言裁决来源均为宿主策略”。

## 四、云地划分的逻辑与用户场景（第 02 篇为主）

### D1【阻断】“直接标识符”漏掉了自然人姓名，对外说“已遮蔽直接身份信息”与事实不符

**问题**：
- 02 §8.3 默认遮蔽的范围是身份证/护照号、手机号、银行卡与账号、统一社会信用代码、详细住址、车牌；当事人名称默认不遮蔽（化名只在 L3a 强制，L2 可选）。
- GB/T 37964-2019《信息安全技术 个人信息去标识化指南》把“直接标识符”界定为“在特定环境下可以单独识别个人信息主体”的属性，举例就是姓名、身份证号（以标准原文为准）。自然人姓名是最典型的直接标识符。
- 但 02 §12 的对外口径写“模型推理只收到完成任务所需、**已遮蔽直接身份信息**的内容”，05 ① 写“直接标识符已遮蔽”。劳动、婚姻家事、人身损害、刑事等以自然人为当事人的事项在 L2 里大量存在，这些事项的姓名和案情会以明文送到月之暗面，“已遮蔽直接身份信息”不成立。“完成任务所需”也无法验证，因为 Agent 读进上下文的是整份材料。

**为什么重要**：这是 T9（说得清）判据下最核心的一句对外承诺，会写进销售材料和 DPA。按国家标准术语，它构成失实陈述；按 PIPL 第六条的最小必要，也难以说明为什么自然人姓名必须明文出境到第三方模型。

**建议修改**：
1. 02 §8.3 的术语改为“**证件、账户与联系方式类标识符**遮蔽”。
2. 默认策略按主体类型区分：**自然人姓名默认替换为事项内稳定的代号**（如〔自然人甲〕）；**法人和机构名称默认保留**。商事事项的主体多是公司，主体关系推理不受影响，同时落实对自然人的最小必要。L3a 仍然全量化名。
3. 02 §12 和 05 §5 的口径改为：“模型推理会收到任务涉及的文档内容；证件号、账号、手机号、住址和自然人姓名在发送前替换为代号；机构名称保留，可按事项开启全部化名。”
4. 01 V7-7 的依据同步改写（见 C3）。

### D2【重要】可逆令牌“在响应中还原”，与“不在代码和命令里替换”自相矛盾

**问题**：04 §5.1 `/v1` 的规则是：遮蔽为可逆令牌，“响应中按令牌还原到界面（化名事项不还原到 Agent 工作区）”。也就是说，非化名事项的令牌会在模型响应流里先还原，再交给 kap-server。而模型响应里包含工具调用参数（Bash 命令、Write 内容、Edit 的 `old_string`），这正是 01 V7-4 和 02 §8.4 否定掉的“工具参数双向还原”。如果不还原，Agent 写进工作区草稿的、Python 用来计算的又都是令牌，例如按账号核对流水就会失败。

另外，K3 要求 `reasoning_content` 原样回传。闸门每一轮重新遮蔽时，如果同一个值的令牌编号不稳定，既破坏了原样回传，也破坏了前缀缓存，而前缀缓存是经济模型的主要假设之一（无持久缓存时 2030 年从 +696 降到 +157）。

**建议修改**：02 §8.3/§8.4 与 04 §5.1 统一成一条规则：“令牌只在界面渲染层还原；Agent、工作区、代码一律只看到令牌；需要真实值的交付件，由可信文书引擎在导出时还原（与化名工作区同一机制）；令牌按事项确定性分配（如 HMAC(事项密钥, 规范化值)）。”P6 增加“跨轮令牌稳定性与缓存命中率”用例。

### D3【阻断】“中软看得到什么”有三处与真实数据流不符（v7 审阅 B6 的同类问题部分残留）

**问题**：
1. **检索**：02 §12 写中软看不到“查询与事项的对应关系（只在本机）”。但 02 §9.12 的运营审计在控制面保存“模型/检索/法源调用元数据（席位、匿名事项 ID、模板、token、耗时）”至少 6 个月，§9.2⑤ 网关也要用事项匿名摘要做二次检查。所以检索请求过境时，中软同时看到查询原文、发起席位和匿名事项 ID，并长期保存后两者，能把同一事项的全部查询串起来、归到具体律师名下，事项可被再识别。
2. **IM**：02 §12 写中软看不到“文件内容（由律师电脑直取）”。但下载句柄由中软 IM 后端签发，说明 IM 平台的应用凭据在中软云端，中软在技术上可以下载文件。“看不到”是策略承诺，不是技术事实。
3. **期限提醒**：默认情形把期限提醒当作普通元数据。但“期限类型 + 时间 + 接收人”（02 §7.5 #51、05 ⑩）对非诉交易来说就是交割、付款、披露的时间表，在上市公司并购中可能构成内幕信息。03 的“一周”叙事里，云端提醒的正是“补充协议约定的付款节点”。

**为什么重要**：02 §12 是 v9 的对外口径表，T9 又是 v9 自己的验收判据；这三处都会被客户或监管逐条追问。

**建议修改**：
- 检索行改为“中软过境看到查询原文、发起人和匿名事项编号；不保存查询原文；不知道编号对应的事项名称”。或者检索调用不带事项 ID，只按席位计量。
- IM 行改为“中软 IM 后端持有平台下载凭据，按设计不下载、不留存文件，访问有审计”。
- 期限提醒的内容（类型、事项代号、文案）用接收人各设备的公钥加密；云端只知道触发时间和推送目标；推送只含唤醒，App 在本地解密显示。

### D4【重要】跨设备续接、离职交接、手机预览这三个高频场景没有落到可实现的设计

**问题**：
- **会话续接**：本地事项的 Agent 会话（kap-server 会话存储、文件历史、快照）只在一台设备上；端到端加密共享同步的是事项账本和成果（02 §6.1、04 §7），**没有定义 Agent 会话能否在另一台设备上续接**，例如办公室台式机发起、家里笔记本继续，或助理发起、律师接手。X1 显示 WorkBuddy 至少会跨设备同步会话元数据（02 §4 表）。
- **离职**：02 §11.5 依赖“事项负责人移交 → 档案成员确认”，但“律所档案成员”是可选项（02 §9.9 末行）。没开启时，离职律师独自负责的事项只能走律所恢复（2-of-3，或恢复码加管理员）。律所保有业务档案是执业管理上的硬要求，现在却建立在一个可选项上。
- **手机只读预览**：02 §11.3 写“App 本地解密只读预览”修订稿。在手机上本地渲染 DOCX 原生修订是工程难题，而端到端加密下又不能在服务端转换格式；W15 的 30 人周没有覆盖这一项。

**建议修改**：
- 02 §6.1 加一行“会话移交”：任务暂停或结束时，把会话快照（转录、待办、计划、文件历史指针）写入事项账本；另一台设备导入后可续接；进行中的工具调用和执行域状态不迁移。工作量计入 W3/W9。
- 团队版和律所版默认开启档案成员。伦理墙事项不加档案成员，改为封存一份事项密钥，由律所恢复主体持有，并留痕。
- 申请签发时，由桌面生成“预览件”（PDF/HTML，带修订标注，与交付件 hash 绑定），随密文一起同步；App 只渲染预览件。

### D5【重要】“无事项问答”成了绕过事项数据策略的旁路

**问题**：按 02 §7.4 #43 和 §9.6，移动 App 和桌面都可以发起“无事项问答”：不读任何事项，经网关、检索、法源过境。但律师在手机上提问时天然会带上案情和当事人，例如“我的客户张三被……”。这个通道没有 L3b 当事人限制检查，没有四项依据，也没有当事人词典（词典只在事项内、只在本机）。结果是，书面拒绝上云或拒绝使用 AI 的当事人（L3b）的信息，可以经无事项问答出站。

**建议修改**：无事项问答也要经过闸门的当事人词典匹配：把本人可见事项的词典加密同步到本人设备（含手机）；命中 L3b 当事人时拦截，命中其他当事人时提示“请在事项内处理”。02 §7.4、§12 的口径从“不涉及案卷”改为“不读取事项材料，用户输入同样经过闸门检查”。

### D6【重要】IM 收件区“文件由电脑直取”，电脑离线时会丢文件

**问题**：律师出差几天不开电脑，IM 平台的临时文件可能已经过期。例如企业微信的临时素材 `media_id`，官方文档写明 3 天内有效（收文件场景是否同样适用，须逐家核实）。而 v9 又规定“中软不下载文件”（02 §12、05 ⑨）。另外，03 §IM 写“企业微信场景默认个人机器人模式”，但没有写这种模式下由谁收文件、下载凭据由谁持有，以及“零服务器开通”是否仍然成立。

**建议修改**：02 §9.6 增加“电脑离线超过平台有效期”的处置。可以由中软 IM 后端用接收人设备公钥加密暂存（只见密文，同时把 D3 第 2 点技术化）；或者在回执里明确提示“请在 N 天内打开电脑”。05 §8 第 12 条加上“各平台媒体文件有效期与机器人收文件能力”。

## 五、合规与商业（第 05 篇）

### C1【重要】登记时点与首次付费时点冲突

**问题**：05 §3 把生成式 AI 应用登记设为“**首家付费前门禁**”。但模型 `launch.paid_start_month_2027 = 4`，01 和 05 也都写“2027-04 设计合作律所转付费”；而 06 §1 把“登记与公示”列为 G2（03-01～06-11）的必须交付，05 §7.5 的 G2 预算也写着“含登记”。如果登记到 6 月才完成，4 月转付费就违反了方案自设的门禁。App 备案、等保定级备案到 G2 才启动，同样偏晚。

**建议修改**：06 §1 把“登记材料递交、App 备案、等保定级”提前到 G1；05 §7.5 的 G2 证据写明“登记完成后才转付费”；模型的付费起点改为“登记完成月”。敏感性表已有“推迟一季度：现金谷底 −5,232”，可以直接作为主要下行情景引用。

### C2【重要】开源许可表漏了 token 路径上的 new-api（AGPLv3 + 附加署名条款）

**问题**：05 §3 的开源许可行只列了 Kimi Code、just-bash、Pyodide、mxc 和 Codex 参考代码。而 v9 的推理路径是“网关 → 中软 MaaS → 月之暗面”（04 §5.2），中软 MaaS 基于 new-api 的 gitee 分支，许可是 AGPLv3，另有第 7 条附加署名条款（见项目记忆《中软 MaaS token 服务》）。如果中软改过 new-api，AGPL 第 13 条要求向“经网络远程交互的用户”提供对应源码。律所用户经网关调用算不算“远程交互”需要法务判断，附加署名条款还可能要求在界面上展示署名。

**建议修改**：05 §3 增列 new-api；05 §10 增加一项决策：MaaS 法律通道要么用不含 AGPL 代码的独立网关实现，要么完成 AGPL 合规评估。06 U17 同步补充。

### C3【一般】律协指引的证据纪律前后不一

**问题**：
- 05 §4 和 06 U19 都规定：深圳律协 2026 指引还没取得官方原文，引用条号前必须先取得。但 02 §9.12 已经写了“满足……深圳律协 2026 指引‘保留使用记录’的要求”。
- 01 V7-7 用“上海律协居村指引第二十九条”作为“不默认化名当事人”的依据；可 05 §4 自己标注这份指引“2025 试行一年、未见续期”，而且适用对象是居村法律顾问，不宜拿来定商事执业的默认策略。

**建议修改**：02 §9.12 改为“按已公开报道的深圳指引要点设计，取得官方原文后核对条号”；01 V7-7 的依据改为 PIPL 第六条（最小必要）加 D1 的主体区分。

### C4【一般】定价叙事只对比了通用办公 Agent，没有法律垂直产品的价格锚

**问题**：05 §6.1 以 Kimi 企业版 ¥4,200/座/年和 WorkBuddy 旗舰版 ¥2,376/人/年为锚（出处在 X1 第 76、146 行，已核对一致）。但律所采购时真正比较的是法律垂直产品，如 iCourt Alpha、北大法宝、威科先行、元典的席位价或年费。03 §1.3 列了这些竞品，却没有任何价格和出处。9,800 元是 Kimi 企业版的 2.3 倍、WorkBuddy 旗舰版的 4.1 倍；如果法律产品的价格锚更低，或者捆绑了法律数据库，这套叙事就站不住。

**建议修改**：X1 和 05 §6.1 补 3–5 家法律产品的公开报价或访谈价，注明出处和日期；G1 访谈加入价格敏感度问题。

### C5【重要】谈判清单漏项（05 §8）

月之暗面一侧：
- **模型版本冻结与下线通知期**：K3 或 K2.6 下线、行为变更，会让已通过盲测的方法包和 06 §3 的质量结论失效。需要至少 6 个月的通知期，并保留旧版本。
- **上游 SLA 与故障责任**：06 §4 已把“外部依赖……故障责任齐全”设为门禁，但清单里没有这一项。
- **安全事件通知时限**：对律所的 DPA 里有，对上游没有。
- **内容安全误拦截的申诉通道**：刑事、人身伤害、性侵类案卷文本容易触发上游审核，与 06 U14 的网关策略相对应。
- **登记所需的上游模型备案号与授权证明**：与 C1 对应，登记时要公示模型备案号。
- **`search_pro` 检索结果的展示与转载许可**：检索结果正文进入律师交付件时的版权边界。

中软内部：
- MaaS 法律通道的 AGPL 处置（见 C2）。

推送通道：
- 国内安卓没有 FCM，要接入各手机厂商的推送 SDK，应列入次处理者清单和 App 隐私合规。05 ⑫ 只写“苹果/安卓推送通道”，过于笼统。

月之暗面服务协议第 3.1 款（“不可再许可”“仅供内部使用或向最终用户提供服务”）和第 6.3 款（“模型服务优化”使用权）：X2 第 166–167 行引用了原文，05 的解读与原文一致，本审阅不另提问题。

## 六、与用户要求的符合度

### U1【重要】“完整接入 Kimi Code”：能力账本和补丁台账漏了“工作区指令文件”，会形成持久化注入（G0 不补即升级为阻断）

**问题**：Kimi Code 的 `workspaceInstructionsService` 按工作区和 homeDir 两处加载 AGENTS.md，并在文件变化时重载（`workspace/workspaceInstructions/workspaceInstructionsService.ts:71-72,118-120,133`）。v9 的 kap-server 工作区就是事项的 `/work`（04 §3.2），而“默认”档下 Agent 写工作区是自动放行的（02 §9.4 T1）。被注入的 Agent 可以在 `/work/AGENTS.md` 写入指令，下一次会话会把它当作可信指令加载，形成**持久化注入**。

02 §9.8 规定案卷目录里的 `AGENTS.md`、`.kimi-code/skills` “一律不加载”，04 §2 也写了“任务可写目录不能新增有效指令”；但 ZP 补丁台账只有 ZP-1（项目级 agent profiles）和 ZP-2（项目级 MCP），没有对应 AGENTS.md 和项目级技能目录的补丁。另外，用户直接执行 shell（`agent/shellCommand`）、`undo` 等引擎能力也没有出现在能力账本中。

**建议修改**：04 §3.4 新增 P0 补丁：工作区指令只从签名方法包和只读的可信配置区加载，`/work` 下的 AGENTS.md 和技能目录不加载。P12 红队加“写入 `/work/AGENTS.md` 后新开会话”的用例。能力账本补登“用户 shell → 走 W 或关闭”和“undo → 映射业务版本”两行。

### U2【重要】过度保守：移动端在 G3 前完全不能发起事项任务

**问题**：02 §9.6 规定，G3 之前移动 App“不发起事项任务”，合伙人在路上只能看、不能让 Agent 做事。而 X1 显示，Kimi Work、WorkBuddy、ChatGPT Work 的手机端都能遥控在线的电脑执行任务（02 §4 表）。v9 已经设计好了端到端加密的设备中继和业务网关白名单（02 §9.6 强制点）。在 G2 加一项“从手机向本人在线电脑发起预设模板任务（运行模式上限为‘默认’，产物只是草稿）”，增量很小，却是律师在移动端最常见的需求。

**建议修改**：把这一项列为 G2 的争取交付；开放遥控（自由文本任务）和移动签发仍放在 G3。

### U3【重要】过度乐观：安全、体验、商业、日期四项结论都押在一个未经实测的组件上

**问题**：WASM 执行域同时支撑着四类结论：安全（02 §12、05 §5 的对外口径）、体验（默认档不弹窗）、商业（支持成本下调；05 §7.4 把可签约席位的下行从 v7 的 −15% 降为 −5%）和日期（W4 只有 22 人周）。可这个组件还没在任何一台真实的 Windows 设备上运行过（06 §9“未做”）。A1–A6 也显示，安全边界被高估、集成工作量被低估。

**建议修改**：
- 01 §4 表中 T3、T7 对 v9 的评价改为“设计通过，实现待 P2”。
- 05 §7.4 的执行域敏感性扩成 −5% 和 −15% 两档。
- W4 从 22 人周上调，至少覆盖四项：路径命名空间（A3）、rg 兼容（A4）、流式输出与终止（A5）、Pyodide 安全加固（A1），粗估 +20–30 人周。
- 06 U2 的退路写具体：P2 不过时，默认档的代码执行改为“逐次确认 + 只在 N 域或可信工具中运行”；同时如实降级对外口径，而不是只写“自研最小模拟 shell”。
