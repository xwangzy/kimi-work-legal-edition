## 1. 产品定义

### 1.1 一句话

**「Kimi Work 法律行业发行版」是律师桌面上的事项工作台：以 Kimi Work 的设计与交互、Kimi Code 的本地 Agent 能力和 Kimi 模型，在律所策略与执行域之内完成从材料到可交付文件的工作；案卷默认在律师电脑上处理与保存，团队以端到端加密方式共享；律师得到有出处、有版本、经律师签发的 Word/Excel 交付件。按账号席位订阅，个人可买，团队可协作，律所零服务器即可开通。**

### 1.2 律师为什么买：三件可验证的结果

1. **少花复核时间**：从收到材料到完成可交付文件的总工时下降（计入改错、核出处、排版、恢复时间），而不是“生成更快”。试点价值门槛：同任务中位数节省 ≥ 30%。
2. **少漏、少错**：关键风险漏检、引用不支持结论、金额与期限算错、版本混乱这四类事故显著减少；每个关键结论都能点回原文与法源。
3. **能向客户说清楚**：每一次外发去了哪里、为什么、经谁批准，都有记录；案卷默认不托管在供应商云端。

| **增强** | 「项目」→「事项」（端到端加密团队共享、伦理墙）；「技能」→ 签名法律方法包 + 本所覆盖层；「看板」→ 事项与团队看板（期限、待签发、用量）；「定时任务」→ 云端期限提醒 + 本机内容任务（错过提示补跑）；运行权限三档 → 手动/默认/自动 + 先出计划 + 管理员锁定；手机 → 通知、确认、只读预览、无事项问答（G2），遥控与移动签发（G3） |

| **新增** | 执行域（W 运行时隔离默认、MXC 系统强制增强）与出站闸门；令牌化工作区；数据去向卡与“中软看得到什么”；收件区；审批与签发；引用四态；会话移交；律所执行器与云端事项（G3） |

### 1.5 不提供或替代的 Kimi Work 能力（如实）

| Kimi Work 能力 | 为什么拿不到或不提供 | 发行版怎么做 |
|---|---|---|
| 在线版 Kimi Agent 的建站、PPT 等专业技能；深度研究 | 闭源，随 Kimi 会员云提供，只买 API token 拿不到 | 法律文书与表格由文书引擎与法律方法包承担；汇报材料由 Agent 在执行域内用 python-pptx 生成草稿（G2 评估“法律汇报”方法包）；研究由“Agent + 检索服务 + 法源服务”组合实现，结果带引用四态 |
| Kimi Computer Use（桌面操控）、WebBridge（借用本人 Chrome 登录态） | 法院系统、客户邮箱、律所内网的登录态被提示注入利用代价极高；商业数据库个人账号不得被 Agent 复用（服务条款禁止） | 不提供；隔离内置浏览器访问公开站点；需要登录的网站只提供“打开页面由律师手工操作” |
| Kimi Claw 云主机、Kimi 云端定时、托管智能体 | 会员云产品；托管智能体不符合零数据留存 | 期限提醒与公开监测在中软云；客户内容的云端执行 = 云端事项（G3，按事项授权） |
| 图片与视频生成 | 与法律交付无关；直传图像/视频不在 ZDR 覆盖内 | 不提供 |
| Notion/飞书文档“人机双写”等第三方 SaaS 插件 | 需律所评估数据去向 | 律所批准后作为连接器接入，标注可接收数据级别 |

### 1.6 它不是什么

不是法律数据库；不是案件管理系统（可对接）；不是自动出具法律意见的机器（律师签发）；不是默认托管案卷的云服务；不向律师个人开放任意插件市场；不做判决预测、法官画像与胜诉率；不提供“完全访问”档。

| 对话 | **问答（Chat）** | 无事项法律问答；事项内问答（只读） |

### 4.2 首页

不塞 36 个功能入口。按律师业务线（诉讼仲裁 / 非诉 / 企业法务）展示**已验收**的场景卡（首发：审合同、整理材料、法律研究），其余在方法库中按状态（生产 / Beta / 模板）筛选；未验收场景不出现在首页。

### 4.3 任务执行态（三栏）

左：材料与覆盖情况（已读、失败、未提供）；中：计划、进度、澄清、确认卡、子任务树（可展开，不展示冗长思考作为“法律推理证据”）；右：成果预览（Word/Excel/HTML 安全预览）与文件历史。审批卡独立于聊天文本，模型生成“已批准”字样不触发任何权限。

### 4.4 事项头（常显）

客户 / 相对方 / 立场 / 法域 / 关键日期 / 数据模式（本地事项·云端事项）/ 密级（L2·L3a·L3b）/ 依据状态（委托授权、个人信息依据、敏感条件、转委托）/ 允许的模型端点 / 执行位置 / 当事人化名开关 / 保留与保全。

## 5. 首日体验：零服务器，第一个交付件 ≤ 30 分钟（试点目标）

| 步骤 | 律师看到什么 | 设计要点 |
|---|---|---|
| 0 开通（律所一次，约 5 分钟） | 主任扫码开通 → 选择策略模板（推荐模板默认最严）→ 生成律所恢复材料（律所版 3 张恢复卡；团队版 1 张恢复码） | 不再有“治理仪式”；恢复材料只打印一次 |
| 1 安装与登录 | 一键安装（签名包）；扫码或手机号登录；打印个人恢复码 | 设备生成独立密钥 |
| 2 设备自检 | “代码运行：运行时隔离（无网络、只见本事项；非操作系统沙箱）”；满足条件的 Win11 另显示“系统强制（MXC）：可用，数据分析增强可用” | 如实标注强度，不写“可安全运行代码” |
| 3 示例事项 | 虚构“股权转让（受让方）”事项与已完成交付件，标“示例” | 合成数据，不发真实请求 |
| 4 恢复演练 | 创建第一个真实事项前，用恢复码演练一次，看到“备份可恢复” | 降低密钥丢失风险 |
| 5 第一份真实合同 | 拖入 DOCX 或挂载文件夹；填写或确认四项依据；看到预计点数与数据去向预览 | 依据“待确认”时只运行本机能力 |
| 6 执行与追问 | 合同审查工作流 → 风险卡；追问进入 Agent：“按 LPR 四倍算逾期违约金”“查这类条款的最新监管口径” | 默认档下执行域内动作不打断；检索查询自动去标识 |
| 7 Word 中打开 | 一键打开带原生修订的文件 | 结构化补丁写回 |
| 8 客户版与签发 | 受众检查 → 预览确切文件 → 申请签发 → 合伙人桌面签发 | 审批绑定确切版本 |

“30 分钟”按文件长度、扫描质量、机器条件、人工复核时间分层报告达成率，不作为所有案件承诺。

## 6. 三条首发业务闭环

首发以“完整业务链”定义，不以功能数定义。每条链给出输入、流程、交付件、错误处理与验收（逐项规格沿用 v5 第 3 篇，以下为 v9 的口径）。

### 6.1 合同审查 → 修订 → 回稿 → 交付

- **输入**：DOCX 优先（PDF 可审阅但不承诺重建原生修订）；合同类型、律师立场、商业目标、附件、适用法、截止日、本所规则版本。
- **流程**：解析结构与覆盖清单 → 定义/金额/日期/附件交叉检查（确定性）→ 法定强制规则 + 立场 Playbook + 本所覆盖层 → 风险卡与替代条款 → 律师接受/修改/拒绝 → 文书引擎写原生修订 → 对方回稿三方比较（原始稿/我方发出稿/对方回稿）→ 只重审变更与受影响定义 → 受众检查 → 复核签发 → 归档。
- **风险卡字段**：原文锚点、风险事实、法律/商业属性、严重度、适用前提、依据与核验状态、首选修改、可谈判备选、需客户决定事项。不以“高风险”代替解释，不把偏好包装为法律禁止。
- **交付件**：审查报告.docx、带修订合同.docx、问题清单.xlsx、关键商业决定清单、引用与覆盖清单、签发证明（独立 manifest）。对方版剥离内部谈判底线、内部批注、隐藏属性与未授权材料。
- **首发内容范围**：先验证 4 类 × 双立场（采购/买卖、服务、保密、软件许可与实施），通过后扩至 9 类 × 双立场（增股权转让、技术开发、商业租赁、借款担保、劳动及配套）。未验收类型显示“通用辅助阅读/草稿”，不套用已售准确率。

### 6.2 材料整理 → 事实与证据 → 受限文书 → 金额表

- **输入**：有序文件包、证据来源、争议类型、当事人与主张、分析截止日。首发为内地民商事；刑事、涉密、复杂监管业务不因通用 Agent 能回答就上架。
- **流程**：安全扫描/解压 → 本机 OCR → 原件页码/图像/文本锚点 → 去重保留来源链 → 分别抽取“材料声称的事实”“律师确认事实”“推论”“待确认” → 时间线与证据矩阵 → 缺失证据与相反材料 → 文书字段确认 → **确定性金额计算** → 原生文书与附件目录 → 人工复核。
- **计算**：精确十进制；本金分段、币种、利率来源与版本、起止日规则、节假日规则、还款冲抵与上限由确定性组件计算；模型只提议参数；不把 LPR 四倍当作所有违约金与利息的一般公式；律师确认法律适用与事实输入后才形成正式表。Agent 在执行域内用 Python 做的情景测算是草稿，进入正式文书前须经确定性组件复算。
- **期限**：模型抽取候选起算事实，律师确认送达方式、日期、期间性质、中止中断；日历引擎计算并记录规则版本；“提醒已送达”只表示通知渠道回执。首发不自动向法院提交。
- **交付件**：证据目录.xlsx、时间线.xlsx、争点—证据矩阵.xlsx、文书草稿.docx、计算明细.xlsx、缺口清单；每个关键事实链接确切文件版本与页段；“未检出”不写成“不存在”。

### 6.3 法律研究 → 引用核验 → 顾问答复

- **输入**：研究问题、法域与地域、事件时点、分析截止日、事实假设、可用数据源与许可。
- **流程**：研究计划 → 生成获准检索式（经闸门去标识）→ 官方法源与授权案例库并行 → 取得原文、版本与权利 → 检索相反依据与区别事实 → 命题逐一对照出处 → 区分现行法、行为时法与过渡规则 → 草拟答复 → 律师核查 → 交付与跟踪。
- **引用四态**：已核验且支持命题 / 出处已核验但支持或适用待确认 / 来源未核验 / 来源不可得、冲突或失效。真实性、支持度、适用性是三个字段；红色状态不得出现在正式稿的确定性依据中。
- **交付件**：法律研究备忘录.docx、类案对照.xlsx、来源目录与受许可摘录、顾问答复.docx、假设/限制与相反依据。案例列表不是研究结论；不宣称胜诉率。
- **没有完整数据许可时**，产品准确称“限定资料研究”，显示覆盖范围与缺失库。

## 9. Office 与 WPS

- **基线**：所有环境都能导出标准 DOCX/XLSX；首家深度集成为 Word（COM 加载项，Windows）；WPS 按试点占比在 G2 接入（WPS 个人版 12.1.0.16910 起禁用 oem.ini/jsplugins.xml，须用 publish 方式注册）。批量许可 Office 2016/2019 的 Office.js 只到 WordApi 1.3（无修订 API），所以 Windows 以 COM 为主。
- **权限**：加载项只绑定用户当前打开的文档、当前版本与事项；读取选区与全文分别授权；不从一个窗口扫描本机其他文件。
- **写回**：`base_version + anchor + expected_text_hash + replacement` 结构化补丁；冲突返回预览，不做模糊替换；保存、关闭、另存与人工同时编辑都有冲突策略；带有效电子签章的原件不编辑，生成新版本并说明签章不再适用。
- **保真**：原生修订保留段落、表格、脚注、目录、页眉页脚、编号与批注关系；含域代码、保护、宏、外部关系的文档先检查；Agent 生成的 DOCX/XLSX/PPTX 交 Office 打开前剥离外部关系（远程模板、外链图片）。

## 10. IM 与移动 App

### 10.1 IM（首发一家，试点决定）

- 机器人只做四件事：把文件放进本人**收件区**、发起**预设模板任务**、**查进度**、**收提醒与签发通知**；不接受用任意文字驱动开放任务；需要开放任务时卡片按钮跳转 App 或电脑。
- 卡片不含文件名、事项名、客户名与案情；只响应已绑定的律所成员（配对模式，禁用“所有人可对话”），群聊不收文件。
- 电脑在线时文件由律师电脑凭短时句柄直取；电脑离线超过平台有效期（如企业微信临时素材 3 天，逐平台核实）时，中软 IM 后端在内存取得文件后立即用接收人设备公钥加密暂存（默认 7 天，律所可关）。中软 IM 后端持有平台下载凭据，按设计不留存明文、访问有审计；平台重投去重、链接过期、真正落地回执全部验收；不宣称“机器人转发文件完全不经云”（IM 平台本身保存消息与附件）。
- 企业微信服务商应用收不到文件（v6 R3 一手核验），企业微信场景默认个人机器人模式；钉钉、飞书可用服务商应用。

## 12. 审批、签发与法律责任

- 成果状态：`草稿 → 待复核 → 待签发 → 已签发 → 被新版本替代/撤销使用`；Agent 只能推进到“待复核”。
- 审批对象绑定：具体渲染版本、附件、受众、去向与金额；**不允许审批一个版本却交付另一个版本**。
- 输出顺序：确定内容 → 受众处理 → 依法配置 AI 标识与元数据（隐式标识写入 custom.xml 等）→ 生成文件 → 计算 hash → 生成独立 manifest → 设备签名。签名只证明所声明的签发流程与文件完整性；可靠电子签名、时间戳、存证与证据效力另按适用服务与法律要求实现。
- 无显式 AI 标识版本：按《标识办法》第九条由用户申请、记录并保留日志 ≥ 6 个月；隐式标识始终保留。
- 任务成功与法律复核通过分别统计；部分完成如实列出剩余；律师可限定范围签发，产品不把未读材料计入覆盖率。

## 13. 知识、规则与内容工程

- 租户、事项与个人记忆分区；跨事项复用默认只允许经知识负责人批准的模板与匿名方法；不把客户事实、谈判底线写入全所记忆。
- 规则项：适用条件、立场、效力时点、法源、法律要求/商业偏好类别、建议与备选、例外、内容负责人、测试样本、版本。
- 法源：Source Registry 记录每个来源的检索、全文、缓存、向量化、送模型、展示、摘录导出、团队共享、终止留存、评测/训练许可；许可到期自动停止相应处理；已签发成果是否保留依合同。
- 内容流程：法律工程师起草 → 资深律师审校 → 独立盲测 → 签名发布 → 灰度 → 观察误报漏报 → 回滚；模型、规则、模板、法源或 OCR 升级按影响图回归。
- 方法包对持证律所可见（可解释性优先），保护靠许可绑定、水印、持续更新与合同。

## 14. 一个事项的一周（v9）

周一上午，客户在微信上把对方发来的股权转让协议发给经办律师。律师在企业微信里转给自己的个人机器人，文件落进她电脑上的收件区；她在电脑上把它归入事项“甲公司受让乙公司股权”（本地事项，L2），确认委托授权与个人信息依据后，按受让方立场与本所覆盖层首轮审查——合同在本机解析，条款经中软网关发给 Kimi，证件号、银行账号与自然人姓名在发送前替换为代号（公司名称保留）。审查完成后她追问：“对方要求的业绩补偿公式，按三种情景算一下我方最大赔付额”，Agent 在本机执行域里用 Python 跑完三种情景，表格进了工作区，没有一次弹窗；接着问“最近一年有没有关于对赌回购条款效力的新判例”，Agent 把检索式里的“甲公司”泛化为“目标公司”，在法律官方站点集里检索、抓取全文、经法源服务核验，结论带着引用四态写进备忘录。同组助理在家打开客户端，经密文中继同步到最新结果，不需要 VPN。周二合伙人出差，在高铁上用 App 收到签发请求，只读预览桌面生成的预览件（带修订标注）后退回一处措辞意见；周三回到办公室在电脑上签发。周三下午，云端提醒“补充协议约定的付款节点还有 7 天”。周四对方回稿，律师在高铁上断网，本机比对只重审被改动的 6 个条款，法条核验离线完成；需要模型的 2 处排队，联网后续跑。客户问“你们用 AI 会不会泄露交易信息”，合伙人打开数据去向卡与“中软看得到什么”页逐条说明。

## 17. 产品效果验收方法

- 同一任务集比较三组：现有人工流程、Kimi Work 标准版、法律发行版；由不知产品来源的律师评估严重遗漏、来源支持、修改可接受性、格式与总交付时间；通用竞品不得使用本产品没有合法取得的额外数据制造不公平比较。
- 数值门槛与样本分层见第 06 篇；数据未取得前不宣称“减少 80% 工时”或“能力全面超过标准版”。
