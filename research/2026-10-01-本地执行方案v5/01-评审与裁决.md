# 第 1 篇　评审与裁决：从“云端执行”回到“律所侧执行”

版本 5.0 · 2026-10-01 · 适用：立项评审、产品与研发负责人、与月之暗面及中软 MaaS 的联合评审

本篇回答四个问题：v4.0 及此前 astra、opus 各稿的执行架构错在哪里；各稿哪些内容在“律所侧执行、云端只供 token”的前提下仍然成立；功能效果与工程可行性如何比较；v5.0 怎么取舍。第 2–8 篇是据此重写的完整方案，凡与本篇裁决冲突，以本篇为准。

---

## 1. 本轮要解决的问题

用户在评审 v4.0 时指出：v4.0 把分析、规则应用、模型调用、法源核验与审批等绝大多数功能放在云端执行，而**云端实际提供的只是 Kimi 的 token API 服务**，其余都应在本地执行。

这一判断有三项事实支撑：

| 事实 | 证据 | 含义 |
|---|---|---|
| 中软的云端能力就是 token 服务 | 中软 MaaS 平台基于 new-api，内部方案写明“中国软件国际面向客户销售 Kimi 官方原厂 API token”（本机 `MaaS 生产/new-api/docs/kimi-auto-design-2026-09-24.md`）；令牌支持额度、模型白名单、IP 白名单、到期，消费日志只记模型、token 数、IP 与请求 ID（`model/token.go`、`model/log.go`） | 法律发行版不需要、也不应该再建一套多租户云端执行系统；云端只需要“法律专用分组”的 token 通道 |
| Kimi Work 本身就是“本地 Agent + 云端模型” | Kimi Work 是桌面端本地 Agent 客户端，官方称内核即 Kimi Code；挂载本地文件夹、本地执行、直出 Office 文件 | v4.0 的“单一云端内核 + 本机能力层”偏离了被授权沿用的产品形态；发行版应当是“Kimi Work 的形态 + 法律能力 + 律所治理” |
| Kimi Code 的引擎可以进程内嵌入、宿主执行环境可替换 | `node-sdk` 在调用方进程内 bootstrap 引擎（`sdk-rpc-client-v2.ts:450-469`）；宿主文件系统 `IHostFileSystem` 与进程服务 `IHostProcessService` 是 App 作用域 DI 服务，`bootstrap(input, extraSeeds)` 可注入替换实现（注意：会话级 `kaos` 参数在 v2 引擎中被忽略，见源码 `sdk-rpc-client-v2.ts:941-948`） | 本机运行 Kimi Code 时，可以只改 SDK 透传一处、不改引擎核心，就把它关进“只看事项派生文本、不能执行进程、不能联网”的笼子 |

因此本轮不是“把 v4.0 的几个模块挪到本机”，而是改变架构的基本假设：**律所的事实、规则、执行、审批与审计都在律所侧；中软云端只提供无状态的模型推理通道。**

## 3. 诊断：v4.0 为什么把执行放到云端，代价是什么

### 3.1 v4.0 的五条理由逐条复核

v4.0 第 4 篇 §1 给出“为什么不在本机跑 Agent”的五条理由。逐条看：

| # | v4.0 理由 | 复核 | v5.0 的回答 |
|---|---|---|---|
| 1 | 治理：审批、签发、审计、预算必须在服务端可信执行 | **部分成立。** 预算确实需要一个律师无法篡改的点；但签发与审计的可信性不来自“放在中软服务器上”，而来自“不可伪造、不可抵赖、可独立验证”。服务端数据库记录反而可被平台运维修改，律所无法自证 | 预算的强制点放在唯一花钱的地方——中软 MaaS 的 token 额度；签发用合伙人设备密钥签名并绑定文件 hash，审计用签名 hash 链（可选把每日链头 hash 送可信时间戳）。律所内任何人离线可验证，中软也改不了（第 4 篇 §6） |
| 2 | 方法资产保护：Playbook 只在服务端组装 | **理由偏弱。** 规则的实质会通过修订卡、意见书和“触发了哪条规则、为什么”的解释暴露给律师；服务端组装挡住的是“整包复制”，挡不住“看懂后照着写”。方法资产真正的价值在持续维护、法变联动与评测 | 规则包签名加密分发、内存解密、按律所水印、随许可到期失效；合同禁止提取。把壁垒放在维护节奏、评测资产与上线服务（第 5 篇 §3.3） |
| 3 | 多入口一致：IM、Office、批量与定时需要云端执行 | **前提不成立。** 一致性需要的是“一个事实库、一个内核”，不需要“这个内核在中软云”。IM 平台已提供长连接接入，律所内网一台常开设备即可承接；Office 加载项本来就在律师电脑上 | 同一个“本机法律内核”以两种形态运行：每台电脑内嵌、所内节点无界面运行；所有入口都连律所侧内核，事项账本在律所内同步（第 4 篇 §2、§7） |
| 4 | 端侧安全：Kimi Code 上游有加固回滚、权限规则不执行等问题，每台电脑都是攻击面 | **问题真实，结论过度。** 这些缺陷针对的是内置文件与 Shell 工具；源码核验显示，配置层 `[tools] enabled=["mcp__legal__*"]` 可让内置工具在模型可见层与执行层同时消失，`skillDirs` 可替代项目级发现，bootstrap 时注入的宿主文件与进程服务可把文件访问与进程执行替换为受控实现。端侧攻击面可以收敛到“只能调用法律工具、只能连本机模型代理” | 引擎在每任务独立的低权限子进程中运行；执行环境经 DI 注入受限文件系统与拒绝式进程服务（只读派生文本、不能启动进程）；模型请求只能发往本机模型代理，由出站闸门检查化名与数据去向；TC260 本地智能体条款逐条落实（第 4 篇 §4、§11） |
| 5 | 测试面减半：一个内核、一套恢复与计量语义 | **成立，但 v4.0 并没有做到。** v4.0 实际上是“云端多租户平台 + 本机 sidecar + 反向工具通道 + Office 桥”，两侧都有状态与故障语义 | v5.0 只有一个内核（律所侧），云端没有业务状态；多租户隔离、行级安全、云端编排高可用、专属云模板这些测试面整体消失 |

### 3.2 v4.0 架构的代价（v4.0 自己没有计入的部分）

1. **中软成为案卷托管方。** 原件、解析文本、成果、审计都存在中软云，中软对律所是个人信息受托人与商业秘密的保管人：DPA 的核心条款、等保三级、多租户隔离与伦理墙、备份与删除证明、事故通知都由中软承担。律协指引（深圳 2026 第 25 条：审慎评估公共云共享实例风险，优先本地化或专有云）恰好把共享实例列为需要额外论证的选项，v4.0 只能用“共享实例风险评估材料”去解释。（公平起见：v5.0 标准端点的**模型推理**仍属共享实例，同样须提供推理共享实例风险评估——差别在于案卷、成果与审计不再托管在共享实例中，见第 6 篇 §5。）
2. **固定成本与人力。** v4.0 经济模型中云平台固定费 2027–2030 年为 120/200/280/330 万元，合规认证 80–120 万元/年，SRE 与平台运维常设；专属云（2027-Q3）与私有化（2027-Q4）是另外两条交付线。
3. **桌面价值被打折。** “本机原件模式”排到 G2，案卷整理默认要先上传到云端；离线只能阅读；大文件上传、排队与时延直接体现在首日体验上。v4.0 用“本机能力层”补救，但律师看到的仍是“套壳网页 + 上传”。
4. **私有化成为另一个产品。** 高敏律所要的“全链路不出所”在 v4.0 里需要整体搬迁云端平台；而在律所侧架构里，它只是“把模型端点换成律所私有模型”。
5. **与 Kimi Work 形态和中软 MaaS 定位都不一致。** 被授权沿用的是 Kimi Work 的设计与能力；中软已有的云端业务是 token 服务。v4.0 在两者之间又造了一个中软法律云。

### 3.3 结论

v4.0 的状态语义、验收纪律、场景规格、内容资产、合规动作、商业纪律都应保留；**需要推翻的是执行位置**，以及由执行位置派生出来的处理模式、数据合同链、经济模型的云平台成本、专属云/私有化路线和组织中的云平台运维。

## 10. 全局视角：容易被忽略的二十件事

“云端只供 token”是正确的方向，但它会把一些原来由云端顺手承担的责任转移到律所侧或产品内。完整的产品必须正面处理这些：

1. **“除模型推理外都在本地”不等于“本地化部署”，更不等于“数据不出律所”。** 上海律协居村指引 4.7 把“本地化部署”定义为“系统运行、数据的存储和处理完全在本地环境内完成”（V2 一手），本机客户端 + 云端模型不满足。对外统一说“**本地执行，云端推理（大所可选律所内私有模型）**”：案卷本地存储、本地分析，审批与审计在律所完成，仅把任务所需的文本片段（化名后）发给已备案的 Kimi 模型推理，中软不存储案卷内容；“本地化部署 / 私有化部署”只用于私有模型端点。
2. **团队协作需要一个律所侧的共享点。** 没有所内节点时用律所共享文件夹（NAS/企业网盘）同步签名事件；两者都没有就只能个人使用。
3. **手机审批、IM 接收材料、定时提醒需要常在线的接入点。** 所内节点承担；没有节点时，产品必须如实显示“律师电脑离线，任务将在上线后处理”。
4. **计费与防滥用的唯一可信点是 token 通道。** 点数结算方式要随之改变（服务端只知道 token，不知道“这是一份合同审查”）。
5. **方法资产下发到端侧后不可能绝对保密。** 用加密、水印、合同、到期失效与持续更新管理风险，不承诺“不可提取”。
6. **法源数据要谈“终端本地分发”。** 否则只能在线核验；官方公报文本是不依赖授权的底座。
7. **端侧 Agent 落入 TC260 本地智能体条款。** 必须逐条落实并出具对照表与测试证据，律所 IT 会按它验收。
8. **备份、设备丢失与密钥恢复由产品负责设计、律所负责执行。** 否则“本地化”会变成“丢失风险”。
9. **运维从 SRE 变成桌面支持。** 需要诊断包（不含正文）、远程协助（律所批准）、版本通道与回滚。
10. **私有化不再是另一条产品线，但“全链路本地化”有硬件门槛。** 同一软件 + 私有模型端点；K3（2.8T 总参、权重约 1.56 TB）至少要 8×GB300 或 16×H200 / 32×H100 / 32 张昇腾 A3（V4 一手），单家律所不可行——K3 只能放在中软或认证推理伙伴机房做单租户“专有云”（2028 年评估）；律所内可行的上限是 K2.6（8×H200 级单机），质量差距要用盲测量化后再决定哪些场景可在私有端点上架。
11. **法律发行版是中软 MaaS 的行业应用层。** 法律 token 走 MaaS，集团层面可叠加 07-20 协议的 token 分成；法律产品自身仍按“席位收入 − token 成本”算账。
12. **MaaS 底座的许可证。** 中软 MaaS 是修改版 new-api（AGPLv3 + 附加条款）对外提供网络服务，集团法务应确认 AGPL 第 13 条的合规安排；法律客户端只通过 API 调用，不受其传染。
13. **上游 Kimi Code 的每次升级都要发到每台电脑。** 补丁台账、回归门禁与 LTS 通道成为客户端发布流程的一部分。
14. **Windows 生态是新的主要风险源。** 杀软误报、组策略、代理、Windows 10 存量、ARM 笔记本，兼容矩阵与报备要前置。
15. **没有中心数据后，质量改进要靠“可选的规则级统计回传”。** 只传规则 ID、采纳/拒绝计数与原因类别，不传内容；由律所选择是否开启。
16. **律所 IT 能力差异巨大。** 小团队要“一键共享文件夹 + 自动备份”；规模所要 MSI、组策略、所内节点高可用与审计导出。产品按两类分别设计默认值。
17. **中软中转本身需要授权背书。** TC260 PG-20266A 7 c)3) 要求调用大模型使用官方接口，“不应通过来源不明的中转站、未授权代理”，附录 B 还要求律所 IT 识别与大模型 API 通信的主机（V2 一手）。中软 MaaS 必须取得月之暗面的书面授权（作为授权接入渠道）并向律所公开，否则律所 IT 可以直接否决；Kimi 官方的请求签名校验可作为补充证据。
18. **终端数据外传要同意和影响评估。** TC260 PG-20268A 7.4 c)4)：部署于终端的应用，用户数据原则上不宜传出终端，确需传输的宜提前征得同意并做个人信息保护影响评估（V2 一手）。产品内的当事人告知同意与律所影响评估支持包因此是上线前提，而不是附件。
19. **“本地执行”本身不是差异。** 腾讯 WorkBuddy 官方文档已写明本地执行、本地与云端端到端加密、模型可选（含 Kimi）并支持本地模型（V4 一手）。发行版的差异只能落在法律专属治理（签名签发、密码学伦理墙、出站闸门与数据去向证据、所内节点、律协与 TC260 对照）与法律内容资产上。
20. **化名模型的训练数据要自建。** 公开中文 NER 数据集（CLUENER2020、MSRA、Resume、Weibo）都没有明确的商用许可，部分含真实个人信息；HanLP 中文模型限研究教学、LTP 商用须付费（V3 一手）。NER 训练语料必须由法律工程团队自建，成为评测资产的一部分。

## 11. v5.0 整合原则

1. **律所的事实留在律所。** 事项、材料、规则、成果、审批、审计都在律所侧；中软云端不持有任何业务数据。
2. **一个内核、两种形态。** 本机法律内核在电脑内嵌运行，或在所内节点无界面运行；所有入口连它，事项账本在律所内同步。
3. **云端只有 token。** 中软 MaaS 的法律专用分组：令牌、额度、计量；ZDR 渠道与不落盘正文是 P0 目标，签署与审计前只处理合成或公开材料；模型端点可替换为律所自带密钥或私有模型。
4. **离开电脑之前检查。** 出站闸门在本机执行化名校验与数据去向记录，每个任务可展开查看。
5. **可信来自密码学，而不是来自服务器。** 签发与审计用设备密钥签名，律所内离线可验证；伦理墙用密钥分发实现。
6. **E 的纪律 + D 的完整度 + v4 的整合成果全部保留**，只改执行位置及其派生内容。
7. **如实说明边界。** 不把“本地执行”说成“本地化部署”或“数据不出律所”，不把加密规则包说成“不可提取”，不把所内节点说成“零运维”。
