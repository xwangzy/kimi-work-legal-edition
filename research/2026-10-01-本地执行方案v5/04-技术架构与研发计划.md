# 第 4 篇　技术架构与研发计划

版本 5.0 · 2026-10-01 · 技术证据截点 2026-10-01（Kimi Code 锁版 `f67e6398f` 源码复核、中软 MaaS 本机代码复核、本轮 V1–V4 联网核验）

## 1. 架构结论

**律所侧单一内核 + 云端只供 token。** 事项、材料、规则、执行、核验、审批、审计都在律所侧完成：律师电脑上运行“本机法律内核”，律所可选部署“所内节点”（同一内核的无界面形态）承担团队同步、IM、定时与批量。**中软云端不持有任何业务数据**：模型推理只经中软 MaaS 的“法律专用分组”（鉴权、额度、计量、转发到月之暗面企业接口）；此外只有不接触案卷的支撑服务——许可签发、内容分发（安装包、规则包、法规库增量）、工单与诊断包接收、可选的产品遥测与规则级统计回传（默认关闭）。数据条款的**目标**是企业协议 + ZDR + 排除“服务优化”使用权、MaaS 不落盘正文；这些在 P0 谈判与配置审计中，**完成前标准端点只处理合成或公开材料**（第 6 篇 §4）。

为什么这样做，见第 1 篇 §3。一句话：**中软云端提供的本来就只是 token；Kimi Work 本来就是“本地 Agent + 云端模型”；律所的保密义务、律协指引与 IT 审批都偏向“数据留在律所”。**

### 1.1 三条不可退让的工程约束

1. **中软云端无业务状态。** 中软 MaaS 只保存令牌、额度与计量元数据，支撑服务只处理许可、版本与工单；任何“为了方便”在中软云端缓存材料、成果、规则或审计的设计都不进入基线。
2. **离开律所侧之前检查并记录。** 所有出站请求（模型、法源、时间戳、更新、模型真实性校验）都经本机出站闸门：目的地白名单、事项策略、化名校验、数据去向记录；IM 收发与云盘同步虽不经闸门，也由节点连接器与同步模块写入数据去向记录。引擎与工作流都不能绕过。
3. **一个内核、一套语义。** 桌面与所内节点运行同一份内核代码与同一套持久任务、审批、审计语义；入口（桌面、Office、IM）只是内核的客户端。

## 2. 部署拓扑：同一软件，四种组合

| 拓扑 | 适用 | 律所侧组件 | 团队协作 | IM / 定时 / 批量 | 模型端点 |
|---|---|---|---|---|---|
| **单机** | 个人律师、专业版 | 桌面客户端 | 无（加密备份到自选位置，设备私钥用律师自设口令另行包裹以便恢复） | IM 不提供（需律所 IM 组织与常驻连接点）；定时与批量在本机运行 | 中软 MaaS（默认）或自带密钥 |
| **共享文件夹团队** | 3–10 人、无服务器的小团队 | 桌面客户端 × N + 律所自有 NAS / SMB 共享（公有云盘同步目录须律所评估后自担，见 §7.2） | 签名事件经共享文件夹同步；团队事项的原件须放在共享位置或导入为加密副本 | IM 须指定一台工作时间常开的电脑作“IM 主机”（连接器必须是律所侧唯一的消息消费者），否则不开通 IM；定时与批量在发起人电脑上运行，关机不执行；可加购“节点部署服务包”升级为节点模式 | 同上 |
| **所内节点团队 / 律所**（推荐） | 5 人以上团队、律所版 | 桌面客户端 × N + 所内节点（虚拟机、NAS 容器、服务器；律所版建议主备两台，见 §7.4） | 节点为同步中心，局域网或律所 VPN | 节点常在线承接；定时与批量在节点执行（仅限授权节点的事项，§5.3） | 同上 |
| **私有化** | 大所、律所联盟、高敏律所、刑事等受限业务 | 同上 + 私有模型端点 | 同上 | 同上 | 2027-Q4 私有化 v1：律所内推理服务（K2.6 级，可称“本地化部署”）与节点小模型预处理；中软专属推理（K3，单租户“专有云”）为 2028 年评估项；分档见 §10.2 |

四种组合是**同一个安装包 + 不同配置**，不是四条产品线。所内节点的资源预算（不含模型）：4 核、16 GB 内存、按事项量配置磁盘（50 人律所起步 1 TB），可在 Windows Server、Linux（容器）或主流 NAS 的容器环境运行；律所 IT 负责其备份与高可用，产品提供一键备份、恢复演练与健康检查。所内节点属于 TC260 PG-20268A 7.4 c)3) 所称“本地服务器”，部署前提写进交付验收：防火墙、入侵检测与防御、恶意代码防护、严格访问控制与权限管理（V2 一手）；局域网访问一律双向证书认证。

## 3. 桌面进程模型

| 进程 | 职责 | 权限与隔离 |
|---|---|---|
| Electron 主进程 | 窗口、托盘、通知、文件关联、电源保持（任务运行时防休眠）、更新、拉起内核 | 用户权限；不处理案卷内容 |
| 渲染进程（React 界面） | Kimi Work 设计语言的全部页面 | 沙箱、上下文隔离、无 Node；只通过 preload 暴露的最小 IPC 通道与内核通信 |
| **本机法律内核**（常驻；登录时随托盘自启） | 事项账本、工作流与任务队列、法律工具、规则引擎、法规库、策略与签发、审计、出站闸门、模型代理、Office/IM 桥、同步、定时 | 用户权限；唯一持有数据库密钥与 MaaS 席位令牌的进程；界面与 Word COM 走 IPC/命名管道；WPS 与 Office.js 走**按用户分配的固定本机端口**（安装时从保留段分配，远程桌面/RDS 下按会话偏移）+ 一次性令牌握手；数据库主密钥由主进程经 `safeStorage` 解封后一次性 IPC 交付内核，主进程随即清除 |
| **Agent 宿主进程**（每任务一个，短生命周期） | 运行 Kimi Code 引擎 | **独立签名的可执行文件**（随包附带并改名签名的 Node 24 运行时，不复用 Electron 二进制，Electron 的 RunAsNode 熔丝保持关闭）；受限令牌 + 作业对象降权；不持有长期凭据；与内核只经**命名管道**通信（宿主内全局 HTTP 调度器把模型代理与法律工具的请求路由到管道，不走回环网络）；任务结束或急停即杀进程树 |
| **解析进程**（每批次一个） | 解析不可信文件：DOCX/PDF/XLSX/压缩包、OCR | 同样为独立可执行文件；AppContainer（无网络能力）+ 作业对象；先做压缩炸弹、路径穿越、符号链接与类型校验；命名管道 ACL 只授予该容器 |
| Word COM 加载项（在 Word 进程内） | 任务窗格、读取选区、写入原生修订 | 经命名管道连内核，会话令牌校验 |
| WPS JS 加载项（在 WPS 进程内） | 同上 | 页面由内核在本机提供（publish 在线模式），同源请求内核，令牌 + 来源校验 |

**运行时选型**（V1 一手核验）：Kimi Code 引擎要求 Node.js ≥ 24.15；Electron 43/44/45 内置 Node 24.21.0，均满足；42 线 2026-10-20 停止支持。G0/G1 用 **Electron 44**；它在 2027-03-02 停止支持、早于公开销售，所以 **G2 内完成迁移到 Electron 45 或 46 的回归**，此后外壳随上游三条受支持主线滚动（§14）。

- 内核以 Electron `utilityProcess` 运行，共用 Electron 内置 Node，不另外分发运行时；所内节点用同版本的独立 Node 24 运行同一份内核制品。
- `utilityProcess` 在源码中固定不开沙箱、也没有降权选项，所以**需要隔离的两类进程（Agent 宿主、解析/OCR）不放在 `utilityProcess` 里**，而是由内核经一个小型原生启动器拉起**独立签名的可执行文件**，施加受限令牌、作业对象与目录访问控制（V3 一手：没有成熟的 npm 包可直接用；以 openai/codex 的 `windows-sandbox-rs`（Apache-2.0，生产在用）为参考裁剪；受限令牌 + 作业对象 + AppContainer **不需要管理员**，而 WFP 断网与独立沙箱用户需要一次性管理员安装——律所 IT 以 MSI/SYSTEM 部署时一并完成，个人自装时退化为“受限令牌 + 作业对象 + 出站闸门”）。AppContainer 默认禁止回环访问，所以 Agent 宿主不依赖回环网络，统一走命名管道（探针 2 验证）。
- 现有 `platform/` 代码按 Node 26 编写（README 要求 ≥ 26，依赖原生 TS 类型剥离运行），迁移时统一用打包器产出面向 Node 24 的制品，并清理 Node 26 专有 API。

## 4. Kimi Code：在律师电脑上怎么跑

### 4.1 用哪些能力

| 能力 | 本机用法 | 不用 / 替代 |
|---|---|---|
| Agent 循环、上下文压缩、Skills、计划模式 | **自建锁版 `kimi-code-sdk` 进程内嵌**，每个 Agent 任务一个宿主进程 | 结构化场景（S1/S1b/S2/S3/S6）不经过 Agent |
| MCP 客户端 | 只连内核的本机法律工具端点（HTTP，127.0.0.1，每任务能力令牌）；写在每任务 `homeDir` 的 `mcp.json` 中（`bearerTokenEnvVar` 指向任务令牌、`enabledTools` 收敛工具面） | 不启用 stdio MCP；项目级 `mcp.json` 已由 ZP-2 写死不加载 |
| 内置工具（Bash、Read/Write/Edit、Glob/Grep、FetchURL、WebSearch、Agent/AgentSwarm、Cron 等） | **全部不可见**：`[tools] enabled` 只列法律工具与下一行的少数交互工具（模型可见层与执行层同时生效，已实测） | 计算、文书、检索都由法律工具提供 |
| 计划模式、待办列表、向律师提问（`EnterPlanMode`/`ExitPlanMode`、`TodoList`、`AskUserQuestion`） | **开放**：不触及事项文件、进程与网络，直接支撑 A1 的“计划先行、中途提问”；提问经 SDK 交互通道进入“待我处理”（宿主须声明交互能力）；计划文件写在每任务临时目录 | 背景提问依赖 TaskList 等任务工具，保持关闭 |
| 子代理 | 默认关闭（随 `Agent` 工具关闭）；需要并行时由内核任务队列有界并行多个 Agent 任务 | 不继承内置 `coder`/`explore`/`plan` |
| 审批 | `session.setApprovalHandler` 转内核策略引擎（三分级）；子代理审批同样经此回调（按 sessionId 桥接，不受 #4070 影响） | 不依赖 Hook 与配置权限规则（#2337 未合入） |
| 会话持久化 | 每任务临时 `homeDir`，任务结束销毁；权威状态在事项账本 | 不保留引擎会话作为业务记录 |
| 品牌 | `KimiHostIdentity` + `[identity]` 白标；`builtin_product_skills = false` | — |
| 遥测、自动更新、问卷、远程控制 | SDK 嵌入路径默认不启用（源码核验）；配置 `telemetry = false` 双保险 | 插件市场 URL 指向黑洞（已有补丁 ZP-3） |

### 4.2 执行环境：怎么把引擎关进笼子

源码复核纠正了一个容易误用的接口：`createSession` 的 `kaos`/`persistenceKaos` 参数在 v2 引擎中**被忽略**（`node-sdk/src/sdk-rpc-client-v2.ts:941-948` 注释：v2 引擎没有 kaos 注入点，文件与进程抽象在 bootstrap 时解析）。正确的注入点是 bootstrap 的 DI 种子：宿主文件系统 `IHostFileSystem` 与宿主进程 `IHostProcessService` 是 App 作用域服务（`os/interface/hostFileSystem.ts`、`os/backends/node-local/hostProcessService.ts:208`），`bootstrap(input, extraSeeds)` 允许替换。

五道约束由外到内：

1. **进程层**：Agent 宿主是独立签名的可执行文件，降权运行（Windows 受限令牌 + 作业对象，限制子进程与内存；G2 评估在命名管道传输下叠加 AppContainer），工作目录是每任务快照目录，只含本次任务允许读取的**派生文本**（不放原件、不挂律师文件夹）。
2. **网络层**：宿主进程不使用网络栈访问内核——进程内全局 HTTP 调度器把模型代理与法律工具端点的请求路由到内核的命名管道（每任务令牌）；内核侧出站闸门才是唯一出口。因为宿主是独立可执行文件，律所 IT 部署时可用 Windows 防火墙按程序路径禁止其一切出站（WFP 规则需管理员一次性安装），个人自装时以命名管道 + 出站闸门为界（探针 2 分别验收）。
3. **工具层**：`[tools] enabled` 只放行法律工具（`mcp__legal__*`）与计划、待办、提问四个交互工具；签名的法律 Agent 文件声明 `subagents: []`；法律工具在内核侧再次校验事项范围与权限；外发、签发、删除类动作根本不做成工具。
4. **执行环境层（新增补丁 ZP-5、ZP-6）**：在 fork 的 SDK 中增加 `extraSeeds` 透传，注入“拒绝式”进程服务（任何进程启动请求都失败）与“受限”文件系统服务（快照目录与签发技能目录只读、每任务临时目录可读写，其余路径拒绝）。引擎内部为系统提示调用 `git` 取上下文（`session/agentLifecycle/profile/gitContext.ts`），拒绝后应降级为“不可用”——列入探针 P1 验证稳定性。
5. **内容层**：案卷内容一律作为数据；快照目录中的 `AGENTS.md`、`.kimi-code`、`.agents`、skills、伪工具指令都不被加载（ZP-1、ZP-2 已写死；`skillDirs` 替代项目级发现）。

```ts
  identity: { productName: 'KimiWorkLegal', version: APP_VERSION, platform: 'kwl_desktop' },

  extraSeeds: legalSandboxSeeds(task),         // ZP-5/6（fork 新增透传）：拒绝式进程服务 + 受限文件系统
});
const session = await harness.createSession({
  workDir: task.snapshotDir,                   // 只含派生文本
  permission: 'manual',
  agentFiles: [task.legalAgentFile],           // 签名校验后的法律 Agent：工具白名单、subagents: []
});
session.setApprovalHandler(req => kernel.policy.decide(task, req));   // 三分级；外发/签发类动作根本不做成工具
session.onEvent(ev => kernel.ledger.append(task.runId, toLedgerEvent(ev)));  // 先落账本再推界面
await session.prompt(task.goal);
// 急停：内核撤销任务令牌 → 工具端点与模型代理拒绝 → 杀宿主进程树（不依赖引擎配合）
```

接口名取自锁版源码（`createKimiHarness`、`createSession`、`setApprovalHandler`、`onEvent`、`prompt`）；`extraSeeds` 为 ZP-5 新增，实现前以锁定提交逐项核对。

## 5. 事项账本、存储与密钥

### 5.1 工作区与存储

每台电脑上，每个律所工作区一个目录（Windows：`%LOCALAPPDATA%\KimiWorkLegal\<律所 ID>\`）：

| 内容 | 实现 | 说明 |
|---|---|---|
| 事项账本 | SQLite + 页级加密：`better-sqlite3-multiple-ciphers` 13.x（MIT，N-API，npm 包内置 win32-x64 预编译约 2.4 MB，可按 SQLCipher v4 格式读写；V3 一手；Electron 44 下免重编译须 G0 确认） | 事件表 + 投影视图；数据库主密钥由 Electron `safeStorage` **异步 API**（Windows 为 DPAPI）包裹——DPAPI 只防其他 Windows 用户、不防同一用户下的恶意进程，所以同用户隔离依赖 §3 的子进程降权与系统安全基线（如实写进安全白皮书）；同步 API 已在 Electron 46 移除，新代码直接用异步 API |
| 材料块 | 内容寻址目录（SHA-256），AES-256-GCM 按事项密钥加密 | 导入的副本、解析版本、OCR 结果、成果文件都按 hash 存放，不可变 |
| 原件引用 | **个人事项**：挂载目录中的文件只记录路径、大小、修改时间与 hash，**不复制、不修改**。**团队事项**：原件必须来自律所共享位置（NAS/SMB），或以“导入”生成按事项密钥加密的副本进入内容寻址块——否则同事与节点无法生成修订稿、做回稿比对与受众检查；挂载本机私有路径时提示并提供一键导入 | 读取时复算 hash，变化即生成新的文档版本 |
| 本地法规库 | 只读 SQLite 包（签名） | 见 §9 |
| 规则包与方法包 | 签名加密包 | 内存解密；任务需要时解密到每任务临时目录，结束清除 |
| 日志 | 结构化运行日志（不含正文） | 诊断包只导出这些 |

### 5.2 事项账本：事件溯源

所有业务事实以**签名事件**追加写入，投影视图由事件重建。事件头最小化（事项 ID、事件类型、作者设备与成员、Lamport 时钟、**密钥纪元**、作者所见最近一次吊销检查点的 hash、前一事件 hash、本事件 hash、签名），事件体按事项密钥加密。**撤权校验不依赖时钟**：事件所引用的密钥纪元早于其作者被吊销后的纪元即拒收，被吊销设备离线“回填”的事件无论时钟值多小都无效；共享文件夹模式撤权时同时撤销该成员对共享目录的写权限（列入撤权演练清单）。

| 事件族 | 例子 | 关键约束 |
|---|---|---|
| 事项与成员 | 创建事项、加入/移出成员、调整保密等级、记录当事人告知同意、变更模型端点策略 | 策略类事件需要相应角色签名；移出成员触发事项密钥轮换 |
| 材料 | 文档版本登记（来源、hash、位置：挂载/导入）、解析版本、OCR 纠正、质量标记 | 原件只读；纠正生成新版本 |
| 执行 | 任务创建、尝试、步骤检查点、工具调用记录（参数摘要与结果 hash）、模型调用记录（模型、token、出站字节、目的地）、取消、预算暂停 | 先落账本再推界面 |
| 结论与修订 | 风险项、引用及其四态、修订建议、律师处置（接受/修改/拒绝 + 原因） | 生成方无权写“律师已确认” |
| 成果与签发 | 成果版本（文件 hash）、受众版本、完整性单、复核、签发、交付、导出 | 签发绑定最终字节 hash；改动即失效 |
| 规则 | 本所覆盖层草案、回测报告、合伙人批准、发布、撤回 | 未批准规则不生效 |
| 审计与运维 | 登录、设备登记与吊销、导出、删除、保全、备份、恢复 | 只记元数据 |

现有 `platform/packages/domain` 的领域对象（Matter、DocumentVersion、ParseVersion、EvidenceAnchor、Run/Attempt、ArtifactVersion、Approval 等）直接成为投影视图的结构；v4.0 第 4 篇 §4.3 的对象约束全部保留。

### 5.3 密钥体系与“密码学伦理墙”

```text
律所根密钥（律所开通时在管理员设备或所内节点生成；离线恢复码 + 可选多名合伙人分持）
  └─ 签发：成员设备证书（成员 ID、角色、设备 ID、有效期；Ed25519 签名密钥 + X25519 加密密钥）
       └─ 包裹：事项密钥（每事项一把 AES-256 数据密钥，只包裹给该事项成员的设备公钥）
            └─ 加密：事件体与材料块
```

- **伦理墙由密钥分发实现**：不是事项成员的设备拿不到事项密钥，无法解密、检索或知道其内容；管理员角色不自动获得事项密钥——“**管理员单人**拿不到案卷正文”由密码学保证，而不是靠服务端权限表。
- **恢复托管密钥（M-of-N）**：密钥只包裹给成员设备会导致“唯一成员的电脑损坏即永久丢失”；反之让根密钥能解所有事项又会让管理员能读全部案卷。v5 的取舍是：每把事项密钥在创建时**另包裹给律所的恢复托管公钥**；托管私钥离线生成，按 Shamir 分持给多名合伙人（建议 3-of-5），任何一人单独不可用。动用托管私钥是“破窗事件”：须 M 名持有人签名，写入审计链并通知事项成员。开通流程强制完成一次“唯一成员设备丢失后从备份恢复事项”的演练。
- **单机与专业版**：没有合伙人分持，设备私钥另用律师自设的恢复口令（scrypt 或 Argon2id 派生）包裹，随加密备份导出；口令遗失则数据不可恢复，开通时明确告知。
- **所内节点是显式的“服务成员”**：节点要接收 IM 文件、执行转交的任务、跑定时与批量，就必须能解密相应事项。因此节点只对**事项负责人逐事项勾选“允许节点执行”**的事项持有事项密钥；伦理墙事项与高敏事项默认不授权节点（这些事项不使用 IM 入口与节点执行，只在成员电脑上运行）。节点私钥封存在 TPM 或硬件模块中，导出受控并写入审计。由此，“**未授权节点的事项，节点与管理员都拿不到事项密钥**”。
- **节点的密钥保护**：Windows Server 用 TPM 封存或 DPAPI-NG；Linux 用 systemd-creds + TPM2；没有 TPM 的 NAS 容器在启动时要求 M-of-N 口令解锁（会影响无人值守重启，开通时说明）。桌面侧：主进程经 `safeStorage` 解封数据库主密钥后一次性 IPC 交付内核，主进程立即清除。
- **离职与撤权**：吊销设备证书；所内节点与其他成员拒绝其同步；轮换相关事项密钥（新纪元），新内容对其不可读；同时吊销其 MaaS 席位令牌与共享目录写权限。**已解密、已导出的明文无法远程收回**，如实告知。
- **设备丢失**：吊销证书与令牌；本机数据库与材料块在静态时加密，密钥受操作系统登录保护（Windows 数据保护 API；推荐律所启用 BitLocker）；可选“密钥租约”——内核每 N 天须向所内节点续租解锁，超期不可读。
- **恢复**：律所根密钥（签发设备证书）与恢复托管私钥都由律所按上述方式保管；**中软不托管任何密钥**，因而也无法替律所恢复。
- **实现**：Node.js 内置 `crypto` 已支持 Ed25519/X25519/AES-GCM 与 scrypt，不引入额外密码库；设备私钥经 `safeStorage` 异步 API（Windows DPAPI / macOS 钥匙串）包裹保存；需要与系统凭据管理器交互时用 `@napi-rs/keyring`（MIT；keytar 已归档，不再选用）。用 Windows Hello/TPM 做签发签名的可行性本轮未核实，列为 G2 增强项。

## 6. 本机执行：工作流、任务、签发与审计

### 6.1 确定性工作流与持久任务队列

生产档场景（S1 合同审查、S1b 回稿比对、S2 案卷整理、S3 要素式文书、S6 脱敏）由代码编排的工作流执行，直接调用本机工具与模型代理，不经过 Agent。工作流从现有 `platform/services/bff/src/orchestrator/` 平移（S1/S1b/S6/A1 已有实现）。

v4.0 用 DBOS（依赖 PostgreSQL）做持久编排；本机与所内节点都是单进程内核，改用**基于 SQLite 的本地持久任务队列**（约 1–2 千行自研），保留 astra 定义的语义：

| 语义 | 本机实现 |
|---|---|
| 任务 / 尝试 / 步骤检查点 | 每步完成即落库；客户端重启、断电、崩溃后从最后检查点继续 |
| 幂等 | 工具操作以“任务 ID + 步骤 + 输入 hash”为键；成果写入以内容 hash 去重 |
| 外部结果不明 | 代理为每个请求生成**客户端幂等 ID** 并随请求头发送；MaaS 侧记录该 ID 并提供按令牌查询（MaaS 侧开发项，§10.3）；查不到时按“可能已扣费”登记、不盲目重发，进入月度对账 |
| 取消与急停 | 撤销任务令牌 → 工具端点与模型代理立即拒绝 → 杀 Agent/解析进程树；界面显示已经发生的动作 |
| 预算 | 任务开始前预估；执行中按实耗累计；超限保存部分结果并暂停 |
| 归属 | 任务由发起它的主机（某台电脑或所内节点）执行，事件同步后其他成员可见；同一事项在两台主机上并发写同一成果时产生两个版本，由律师选择，不“最后写入者获胜” |

### 6.2 策略引擎与三分级决策

| 档位 | 动作 | 本机规则 |
|---|---|---|
| 仅律师本人决策 | 签发、对外发送、提交、删除原件、导出无显式标识版本、修改事项模型端点策略 | 不暴露给 Agent；须本人设备签名；绑定对象版本、受众与有效期 |
| 律师授权后执行 | 覆盖写入正式成果、批量改写、调用付费法源、扩大材料范围、写入长期记忆、实名企业查询 | 一次授权只对本次对象有效；签名记录 |
| 智能体自主执行 | 读取本事项派生文本、检索本地法规库、起草草稿、确定性校验、计算 | 在事项与工具白名单内；全程记录；一键急停 |

### 6.3 签发：可离线验证的签名

签发事件 = {成果版本 ID、最终文件 SHA-256、受众、完整性单 hash、签发人成员证书、时间、保证等级、签名}。

- **保证等级**：`设备签名`（签发人在自己电脑上确认，用本人设备私钥签名）——**对外交付件的“签发”只认这一种**；`IM 确认（节点见证）`（签发人在手机上经律所自有 IM 的卡片确认，由所内节点以**节点服务密钥**签名记录“谁在何时确认了哪个文件 hash”），保证等级低于设备签名，只能用于律所策略允许的受众（例如“内部稿、客户版允许，法院版与对方版必须设备签名”），且只适用于已授权节点的事项。
- **验证**：律所内任何设备离线可验证；导出 DOCX/PDF 在自定义属性中写入签发记录 ID 与文件 hash 摘要（不含签名私密信息），与 AIGC 隐式标识并存。
- **失效**：签发后任何字节变化生成新版本，原签发不带到新版本。

### 6.4 审计链与时间锚定

- 每台主机的事件流是一条 hash 链，内核每日对链头签名形成检查点；所内节点汇总各设备检查点。
- **可选时间锚定**：把检查点的 Merkle 根（加随机盐，避免对案号、姓名等短字段做字典反推）以 RFC 3161 协议提交可信时间戳服务（如联合信任时间戳服务中心，接口遵循 RFC 3161 与 GB/T 20520-2006，只提交 hash；价格不公开、需询价，是否支持 SM3 待确认），取得时间戳令牌与记录一起保存在律所侧，并提供离线验证工具（V2 一手）。**签发即锚定**，其余审计每日锚定。
- **证据效力的如实表述**：最高法《关于互联网法院审理案件若干问题的规定》第十一条把“可信时间戳、哈希值校验”等列为可证明电子数据真实性的技术手段；《人民法院在线诉讼规则》第十八条提示，锚定只能证明锚定之后未被篡改，锚定之前的真实性要靠数据的生成机制与保存过程证明（V2 一手）。因此审计链必须记录生成机制（谁、何时、哪个模型版本、哪条规则），并尽量缩短“生成到锚定”的间隔；对外只说“采用司法解释列举的可信时间戳与哈希校验技术”，不说“司法存证即具法律效力”或“法院认可”。
- 审计只记元数据与 hash，不存正文；默认保存期不少于 6 个月（律所可设更长），可按事项、人员、动作导出报表。
- 篡改检测：链断裂、签名不符、检查点与时间戳不一致都会在所内节点与管理员界面告警。

## 7. 同步：所内节点与共享文件夹

### 7.1 设计

借鉴“本地优先软件”与成熟的端到端加密笔记同步做法（V4 一手）：Joplin 用“类文件系统驱动 + 每条目一个文件 + 用口令包裹的主密钥随数据同步 + 共享单元独立数据密钥与公私钥分发”，设计可借鉴，但它是 **AGPL** 许可（不能复用代码），冲突处理是“远端覆盖本地、本地副本进冲突本”，不满足审计要求；Automerge 与 Yjs 均为 MIT、活跃，但**不内置签名与身份**——所以审计与审批事件用自研的签名事件段，Automerge 只留给将来“多人同时编辑同一份草稿”的场景。设计要点：

- **每台设备只追加写自己的事件段文件**，从不改写他人的文件——共享文件夹上不会出现写冲突；
- **材料与成果是内容寻址的密文块**，不可变，天然无冲突；
- 各设备按（Lamport 时钟，设备 ID）合并出确定的全序，重建投影；
- 业务冲突显式处理：同一成果的并发修改保留两个版本；策略类事件按角色与签名校验，冲突时冻结相关动作并提示管理员；
- 只同步“团队事项”；个人事项默认只在本机（可单独加密备份）。

### 7.2 两种同步介质

| 介质 | 怎么同步 | 优点 | 限制 |
|---|---|---|---|
| **所内节点**（推荐） | 客户端经局域网或律所 VPN 与节点双向同步（双向证书认证）；节点是常在线的副本与备份点 | 实时、可靠；承接 IM、定时、批量、管理控制台；可作更新与法源查询的局域网代理（律师电脑出站只剩节点与 MaaS） | 律所需要一台常开设备与基本运维 |
| **律所共享文件夹** | 事件段与密文块写入律所 NAS、SMB 共享或企业网盘同步目录 | 零服务器；利用律所现有存储与备份 | 依赖同步客户端的及时性；不承接 IM 与定时。V4 一手：网络文件系统的写入可能乱序或丢失、锁不可靠（SQLite 官方），同步器会产生临时文件与冲突副本（如 `.sync-conflict-*`、“conflicted copy”），按需同步会留下占位文件。因此**共享目录里绝不放 SQLite 或任何需要锁的文件**，只放不可变的段文件与密文块；写入采用“临时名 → 刷盘 → 原子改名”，读取端只认已封口（尾部带 hash 与签名）的段，忽略临时文件与各种冲突副本命名，出现冲突副本即告警；本机索引库放 `%LOCALAPPDATA%`，由同步目录重放生成。首批只认证**律所自有**的 SMB/NAS 与群晖 Drive（自建 NAS）；坚果云等公有云盘（官方说明有桌面同步目录）属第三方云，律所评估后自担并记入数据去向；企业微信微盘、钉盘、飞书云盘实测后再列入 |

远程办公：经律所 VPN 连节点；或离线工作、回所后同步。中软不提供数据同步中继——这是“云端只供 token”的直接推论；如未来律所普遍需要外网同步，可评估“端到端加密中继”（中软只见密文），但须单独拍板，不进入基线。

### 7.3 备份与导出

- 所内节点：每日快照 + 律所自有备份系统；产品提供恢复演练脚本。
- 共享文件夹模式：共享目录本身就是一份副本；另提供定期加密导出。
- 单机：加密备份到律师选择的位置（移动硬盘或其自有网盘）。
- 导出格式开放（事件 JSON Lines + 原始文件 + 签名与证书），律所随时迁出，不靠数据锁定续费。

### 7.4 所内节点高可用

节点同时是同步中心、IM 消息消费者、定时与批量执行点和（已授权事项的）密钥持有者，律所版建议**主备两节点**：

- 两节点共享同一份签名事件存储（各自写自己的段，与客户端相同的同步语义），任一节点可从另一节点恢复。
- IM 连接器：飞书（每应用最多 50 条连接）与钉钉（多连接随机投递）可双活；企业微信（每机器人单连接）用账本租约选主、单活，主节点失效后备节点接管。
- 定时与批量任务以账本租约防止两节点重复执行。
- 恢复目标（待测）：节点故障后 15 分钟内备节点接管 IM 与定时；单节点律所以“当日备份 + 4 小时内重建”为目标，并如实说明期间钉钉消息可能丢失、飞书卡片点击报错。
- 一台常开的 Windows 电脑也可作节点，但系统更新重启会中断 IM，只建议小团队使用。

## 8. 解析、OCR、化名与出站闸门

### 8.1 解析与 OCR

- DOCX/XLSX：自研 OOXML 解析（现有 `docx-engine` 的文本映射与锚点）；PDF 文本层：`pdfjs-dist` legacy build（Apache-2.0）在 Node 中用 `getTextContent` 抽取，无需 canvas；扫描件渲染成位图用 `@napi-rs/canvas`（MIT，win32-x64 约 38 MB）或 PDFium 的 WebAssembly 包（约 11 MB），G0 同台比较速度与对畸形 PDF 的稳定性（V3 一手）；压缩包在解析进程中解包并做安全检查。
- **本机 OCR**（V3 一手；安装包含 win32-x64 与 win32-arm64 两种架构的运行时，ARM 笔记本列入兼容矩阵）：RapidOCR 转换的 PaddleOCR ONNX 模型，全链 Apache-2.0；默认档 PP-OCRv5 mobile（检测 + 识别 + 方向分类约 22.5 MB），精度档 PP-OCRv6 small（约 31 MB，2026-06 发布，社区验证尚少），所内节点可用 server 档（约 173 MB）；运行时 `onnxruntime-node` 1.30（MIT，有 Windows x64 预编译；npm 全平台包 301 MB，打包按 win32-x64 / win32-arm64 分别裁剪并跳过 CUDA 下载）；Node 封装以 `ppu-paddle-ocr`（MIT）或参考 RapidOCR 前后处理自研薄封装为起点；**单个 OCR 进程串行处理、页级流水**（第三方实测批处理峰值内存约 1 GB）。官方 CPU 耗时只有服务器 Xeon 8 线程数据（mobile 检测约 58 ms/图、识别约 21 ms/行），**i5 笔记本上没有一手数据，以探针 8 实测为准**。低质量页可见、可重扫、可人工纠正（生成新解析版本）。扫描件与图片默认**不发给模型厂商**（ZDR 不覆盖经文件上传接口提交的图像）；确需发送时以内联方式发送。
- **不选用**：Marker/Surya（代码已改 Apache-2.0，但模型权重仍限制商用）；MinerU（改为“Apache-2.0 + 附加条款”，集团合并口径门槛与在线服务标注义务需法务评估，且是 Python 重栈，只可能作为所内节点的可选组件）。
- 印章、手写、复杂表格：首发只做质量标记与人工核对，不承诺识别率。

### 8.2 化名

- 第一遍规则：身份证号、手机号、银行卡号、统一社会信用代码、车牌、邮箱、详细地址、案号、金额（按任务决定保留或泛化）。
- 第二遍词典：事项当事人、代理人、证人与关联方名单（建事项与材料入库时抽取，律师确认）。
- 第三遍 NER（V3 一手）：基座用 `hfl/rbt3`（Apache-2.0，3 层，FP32 约 156 MB，量化为 INT8 ONNX 常驻）；**CLUENER2020、MSRA、Resume、Weibo 等公开中文 NER 数据集都没有明确的商用许可，Resume 与 Weibo 还含真实个人信息——不得用于商用权重训练**，只可内部评测；训练语料由法律工程团队自建（合成文书 + 官方公开文本 + 律所书面授权的脱敏样本），列为评测资产的一部分（第 5 篇 §1）。HanLP 中文预训练模型限研究与教学、LTP 企业商用须付费，均不选用。可选小模型复核在所内节点或私有端点运行。
- **映射表**：进入事项账本、按事项密钥加密，律所内同步，**永不离开律所**；同一事项内代号一致，跨事项不复用。模型返回后在本机还原显示。

### 8.3 出站闸门

内核里唯一可以发起外部网络请求的模块；工作流、Agent 工具、法源连接器、时间戳、更新都只能调用它。

| 检查 | 规则 |
|---|---|
| 目的地 | 白名单，按主机分列：**律师电脑**——MaaS 推理端点（或律所自带密钥 / 私有端点）、Kimi 模型真实性校验接口、已登记的数据商（无节点时）、时间戳服务、中软许可与内容分发（或改由节点镜像）、工单与诊断包上传（律师预览后手动）；**所内节点**——同上，另加 IM 平台长连接与文件下载域名、MaaS 律所级管理接口。清单与第 6 篇 §14 的“出站域名、IP 与进程清单”是同一张表；其他一律拒绝 |
| 事项策略 | 当事人告知同意状态（PG-20268A 7.4 c)4)：终端数据确需外传的，宜事先征得同意并做影响评估）；“拒绝云端”的事项只允许私有模型端点；保密等级对应的允许端点；上海律协居村指引第十五条所列敏感信息（生物识别、医疗健康、金融账户、行踪轨迹、未满十四周岁未成年人信息）默认只允许私有模型端点 |
| 化名校验 | 对模型请求逐段扫描直接标识符与当事人词典；发现未替换即补替换或拦截（按策略），并记录 |
| 范围 | 每个请求只能携带本任务快照中的片段；单请求与单任务字节上限 |
| 记录 | 写入“数据去向”事件：目的地、所含文档与锚点、字符数、化名统计、请求 ID——界面“数据去向卡”与审计报表都由此生成 |
| IM 与同步介质 | 不经出站闸门，但同样记录：节点 IM 连接器写入“IM 入站 / 出站”记录（文件名、hash、发送对象、所在平台）；同步模块写入“同步介质”记录（介质类型、写入的密文块与事件段数量）。高敏事项默认开启“IM 只发通知、不发文件，签发在桌面或内网完成” |

## 9. 法源与核验（本机）

| 能力 | 本机实现 | 网络依赖 |
|---|---|---|
| 法规版本库 | 随客户端分发的签名只读 SQLite 包：法规、条文、公布/施行/修改/失效日期、效力状态、修订沿革、官方链接；每日签名增量包；界面显示“法规库最后更新日” | 只下行更新（经 CDN 或所内节点镜像） |

| 案例存在性与摘录核验 | 调用授权数据商接口，只发案号或抽象争点等去标识查询；结果按许可缓存。**数据商凭据**：优先要求数据商按律所签发可吊销、带额度的子凭据（第 7 篇 §4.2）；拿不到子凭据时，中软的数据商凭据只放在所内节点，无节点团队的案例在线核验不开通（只做法条离线核验与人工核验链接）；法源按量费由节点或客户端本机计量，计入任务点数并月度对账 | 数据商 |
| 检索（事项材料、本所知识） | 本机全文索引为主召回：SQLite FTS5 + `wangfenjin/simple` 中文分词（MIT/GPL 双许可，选 MIT；有 Windows 预编译，须验证与加密 SQLite 的扩展加载兼容）；向量检索作补充：笔记本用 `bge-small-zh-v1.5` INT8 ONNX（MIT，约 24 MB），所内节点可用 `bge-m3` 或 `Qwen3-Embedding-0.6B`（约 0.6 GB，不在 8 GB 笔记本常驻），向量存储用 `sqlite-vec`（Apache-2.0，pre-v1，锁版本）；权限过滤在召回前（事项密钥天然隔离）（V3 一手） | 无 |
| Source Registry | 每个来源的许可动作集合在本机强制：检索、展示、摘引、缓存、送入模型、导出、训练 | 无 |
| 离线时 | 案例核验显示“未核实（离线）”，该引用不得进入签发版，直到联网核验 | — |

法规库的数据来源与授权条件见第 5 篇 §2（V2 一手核验）：**主体由法律工程团队从全国人大常委会公报、国务院公报、部门与地方公报的标准文本人工采集并自建结构化**（著作权法第五条：法律法规等立法、司法性质文件不适用著作权法；立法法第六十二、七十八条：公报文本为标准文本），每条记录保存公报期号、页码与采集日期；不自动化抓取国家法律法规数据库。法律之星“法规订阅数据服务”面向订阅方“全量同步到本地系统”，其 MCP 协议禁止向第三方分发原始数据集合——**未取得“终端离线再分发”书面授权前，不把其数据写入随客户端分发的包**，只在中软内部用作“哪部法规有变更”的提示；联网时用法律之星 MCP 做现行有效核验，结果不入库。指导性案例从最高法官网原文自建内置；其他案例在线调用数据商。

## 10. 模型代理与 token 通道

### 10.1 本机模型代理

内核内的本机服务，工作流与 Agent 都只连它：

| 能力 | 设计 |
|---|---|
| 接口 | 127.0.0.1 随机端口，OpenAI 兼容与 Anthropic 兼容；每任务令牌 |
| 路由 | 按步骤类型选择模型：法律判断用 K3；抽取、分类、摘要用 K2.6 / K2.7-code；核验、计算、格式、比对用代码。只在经评测等价的模型之间切换，不为可用率静默降级 |
| 推理档位 | 厂商默认 `max`；本产品默认 `high`，代理按步骤下调到 `low`，`max` 只在律师显式选择时使用 |
| 缓存友好 | 提示按“系统提示 → 基础方法包 → **按律所（或按事项）派生的盐值块** → 本所覆盖层 → 材料片段 → 任务”组装。Kimi 自动前缀缓存**按组织隔离**（V1 一手），经 MaaS 中转时同一上游组织内各律所共享缓存；V1 同时提示“同一前缀跨律所命中”是保密评估点（例如谈判双方的律所审的是同一份合同，命中时延可能泄露“对方正在审”）。所以**跨律所共享只到“系统提示 + 基础方法包”为止**，其后插入盐值块，材料片段不可能跨律所命中。走 Anthropic 兼容接口时 `cache_control` 只在请求顶层生效、不传则只读不写，代理负责设置。**ZDR 下前缀缓存是否保留、保留多久、是否计入留存，列入 P0 条款确认**；经济模型基准以“缓存可用”为显式前提，并给出无缓存敏感性（第 7 篇 §3.4） |
| 模型真实性校验 | 代理在请求头附 `X-Msh-Request-Nonce`，用 Kimi 官方校验接口（全量或抽样）校验响应签名，**可证明请求到达了 Kimi 官方接口、使用的是声明的模型、未被替换**；**不能证明中转层没有留存或复制明文**——后者靠 DPA、MaaS 不落盘配置审计与等保测评。须在 G0 探针 10 确认 MaaS 透传请求头与签名后才启用 |
| 预算 | 任务前预估；查询 MaaS 剩余额度；超限暂停 |
| 计量与容量 | 记录每次请求的模型、token 分类、耗时、客户端幂等 ID、任务归属，写入账本；每日与 MaaS 消费记录对账。代理对每个请求设置合理的 `max_completion_tokens` 上限（Kimi 按该值预估占用 TPM），避免按模型上限预占配额 |
| 出站 | 一律经出站闸门 |
| 凭据 | 席位令牌只在内核进程内存与操作系统凭据库中；Agent、界面、加载项都拿不到 |
| 故障 | 429 / 超时有界退避；交互任务优先、批量让路；长时间不可用如实提示，**不自动切换到其他厂商模型** |

| P2 律所内大模型（K2.6） | Kimi-K2.6：1T / 32B，原生 INT4 约 595 GB，256K 上下文，Modified MIT | 单节点 8×H200 级（或国产同级）；CPU+GPU 异构方案可降本但吞吐低 | 大所、律所联盟或律协集中托管 | 部署在律所自有或控制的服务器上，可称“本地化部署”；**与 K3 的质量差距须用 360 任务盲测量化后才上架对应场景** |
| P3 节点预处理（小模型） | Kimi-Linear-48B-A3B（MIT，约 98 GB，2–4 卡）；Kimi-VL-A3B（MIT，约 33 GB，单卡） | 工作站级（与约 20–30 万元的“一体机”同档，价格为二手参考） | 化名复核、摘要、OCR 辅助、长文预处理；主推理仍走 K3 | 不替代主模型 |

私有端点要求与标准端点一致的消息格式：K3 等始终思考的模型必须原样回传 `reasoning_content` 与工具调用，审计与重放才能复现。

### 10.3 中软 MaaS 法律专用分组（需要 MaaS 侧配置的事项）

中软 MaaS 基于 new-api，已具备按令牌的额度、模型白名单、IP 白名单、到期与消费日志（本机代码复核：`model/token.go`、`model/log.go`）。法律发行版需要“**配置 + 少量 MaaS 侧开发**”：

| 能力 | 状态 | 说明 |
|---|---|---|
| 令牌（席位）、模型白名单、到期、IP 白名单、元数据日志 | 已有 | 配置即可 |
| 律所级额度池与令牌剩余额度 | 已有（硬上限） | 席位“软上限”由本机与节点执行，MaaS 只做硬上限 |
| 每月发放额度、年度合同期内结转、到期失效 | 需开发或外部作业 | 由 MaaS 定时作业按许可写入额度 |
| 律所级受限管理接口（按许可席位数校验后创建/吊销/轮换令牌） | 需开发 | 管理凭据只放在所内节点或中软侧，**不落律师电脑** |
| 按律所分组限流、交互优先与批量让路 | 需开发 | new-api 现有渠道与分组限流需扩展优先级 |
| 客户端幂等 ID 记录与按令牌查询 | 需开发 | 支撑“结果不明先对账” |
| 平台原因失败的额度返还 | 外部作业 | 月度对账后由 MaaS 返还 |
| 请求签名头透传、顶层 `cache_control` 透传 | 待确认 | 探针 10 |
| 正文不落盘的配置与审计报告 | 需审计 | 写入 DPA |

上述开发由 MaaS 团队估算并计入第 8 篇的分摊；法律客户端侧对应工作在 W4。配置与门禁事项：

0. **授权接入渠道背书（上线门禁）**：TC260 PG-20266A 7 c)3) 要求调用大模型使用官方接口、不经“来源不明的中转站、未授权代理”（V2 一手）。中软须取得月之暗面书面确认“中软 MaaS 为授权接入渠道”，并在律所材料与产品“连接”页公开；结合 §10.1 的请求签名校验，律所 IT 可自行验证请求确实到达 Kimi。
1. **专用分组与渠道**：法律流量走单独分组，上游是月之暗面企业组织的密钥；**目标**是开通 ZDR、排除“服务优化”使用权（第 6 篇 §4），签署前该分组只处理合成或公开材料。
2. **令牌即席位**：律所 = MaaS 企业用户；每个生产席位一个令牌（模型白名单、月度额度、到期；律所有固定出口 IP 时可启用 IP 白名单）；团队额度池用律所账户额度实现。**令牌由所内节点调用 MaaS 的律所级受限接口创建、吊销与轮换**（MaaS 按许可席位数校验）；无节点团队由中软侧代为执行管理员的指令，MaaS 管理凭据不出现在律师电脑上。
3. **正文不落盘（待审计）**：确认请求与响应正文不落盘（消费日志只含模型、token 数、IP、请求 ID）；错误日志不记录请求体；由中软安全团队出具配置与审计记录，写入 DPA。
4. **日志留存**：元数据日志不少于 6 个月。
5. **独立上游组织、并发与容量**：Kimi 的限速、缓存、IP 白名单与余额都在**组织**一级，项目级只有预算与 TPM 上限，Key 级没有任何控制；公开最高档 Tier5 只有并发 100、RPM 300、TPM 500 万，且所有模型共享同一份限速（V1 一手）。法律分组使用**独立的月之暗面企业组织**（不与 MaaS 其他客户共享限速与缓存），并在采购合同中约定专属额度。容量按“**峰值并发 ≈ 生产席位 × 峰时活跃率 × 每任务并发路数 × 推理时间占任务时长的比例**”测算：例如 1,000 席 × 10% × 2 路 × 0.8 ≈ 160 并发，所以 **2027 年要价并发 ≥ 300、TPM ≥ 2,000 万，2029 年起按席位线性扩容**（探针 9、10 实测“每任务并发·秒”后校准）。MaaS 侧按律所分组限流，交互优先、批量让路。对缓存隔离有更高要求的大所，可配置“一所一上游组织”的渠道，或采用自带密钥。
6. **月之暗面密钥只在服务端**：服务协议的许可“不可再许可”，账号与 Key 不得提供给他人使用（V1 一手），所以月之暗面密钥只存在于 MaaS 渠道配置中；律师电脑持有的是 MaaS 签发的席位令牌，不是月之暗面密钥。
7. **只发文本，图片内联**：扫描件在本机 OCR 后只发文本；确需发图像时以内联方式发送，不使用文件上传接口（ZDR 不覆盖经文件上传提交的图像与视频）；不使用 Batch 与文件接口处理案卷，直到月之暗面书面确认其留存期与 ZDR 覆盖。
8. **许可证**：MaaS 为修改版 new-api（AGPLv3 + 附加条款）对外提供网络服务，集团法务确认 AGPL 第 13 条的合规安排；法律客户端只作为 API 调用方，不受影响。
9. **不使用 MaaS 的自动选模**（kimi-auto）承载生产档场景：生产路由必须固定、可回归。
10. **不使用平台联网搜索**：`$web_search` 预计 2026-10-20 下线，新的 `/v1/tools/search` 与 `fetch` 由云端执行、查询词出域；法律研究只走授权数据商与本地法规库。

## 11. Office 与 IM 接入

### 11.1 Word / WPS

宿主路径沿用 v4.0（本方案第 2 篇 §7.3）：Windows Word 默认随安装包按用户注册的 COM 加载项；WPS 用金山官方 publish 方法注册、用户在 WPS 内确认启用；M365 租户与 Mac 走 Office.js（G3）；所有环境保留“本机直出修订稿并调用 Word/WPS 打开”的兜底。

变化在于**加载项连本机内核**：

| 宿主 | 连接方式 | 约束 |
|---|---|---|
| Word COM 加载项 | 命名管道（当前用户、会话令牌） | **用 .NET Framework 4.8 编写**：微软明确 VSTO/COM 加载项不能用 .NET Core/.NET 5+ 构建、也不会更新该平台，4.8 是最后一个主版本但继续受支持（V4 一手）；加载项只做薄外壳，业务逻辑在内核 |
| WPS JS 加载项 | publish 在线模式的地址填本机内核的**按用户分配的固定端口**（`http://127.0.0.1:<用户端口>`，安装时从保留段分配并写入注册信息；远程桌面/RDS 下按会话偏移），由内核提供 ribbon.xml 与页面；或离线 7z 包（页面随包，只调用内核接口）；页面与接口同源，避免跨域；令牌 + 来源校验；内核随登录自启，未运行时功能区显示“请启动客户端” | V4 一手：官方示例即用 localhost 地址；新个人版只能走 publish；加载项内请求本机是否另受跨域或安全设置限制未核实（社区经验可能要用户信任加载项）——列入探针 6；不接受其他来源的请求 |
| Office.js（G3） | **任务窗格页面直接由本机内核以 `https://localhost:<用户端口>` 同源提供**；证书为安装时生成、**只对 localhost 签发的叶子自签证书**（或带名称约束的本机 CA），登记在当前用户证书存储，私钥由 `safeStorage` 保护——不安装可为任意网站签发证书的根 CA；不做“云端页面访问本机服务” | V4 一手：Windows 加载项运行在 WebView2，受 Chromium 本地网络访问限制，2025-12 曾因此大面积失效、2026-02 修复；Mac 上访问 http 本机被微软判为 By Design 不支持；manifest 指向 localhost 的生产部署微软文档未明确，须 PoC，只在探针通过的宿主上售卖 |

写回安全不变：每次写回绑定文档基线 hash、段落/表格锚点与预期原文，不匹配就停止，转人工或改批注。

### 11.2 企业微信 / 钉钉 / 飞书

原则：**律所在自己的 IM 组织里创建自建应用 / 机器人，所内节点用平台提供的长连接方式接入**；中软不运营 IM 中转服务，消息与文件只在律所 IM 组织与律所侧内核之间流动。

V1 一手核验：三家都提供**不需要公网 IP 与回调域名**的接入方式，律所内网一台能出公网的设备即可承接“转文件 → 本机处理 → 回卡片 → 合伙人点卡片审批”的闭环。

| 平台 | 接入方式 | 收文件 | 卡片回调 | 离线行为 | 关键约束 |
|---|---|---|---|---|---|
| 钉钉 | Stream 模式（出站 443，无需公网 IP、域名、白名单） | 机器人单聊收文件；群聊须 @；以下载码换取文件 | 互动卡片回调走 Stream | **机器人消息不重投，离线即丢**；事件订阅超时会重投 | 多连接时随机推给其中一条；连接数上限与费用未核实 |
| 飞书 | 长连接（WebSocket），**仅企业自建应用** | `messages/:id/resources/:file_key` 下载；< 100 MB 直接下载，更大用分片 | `card.action.trigger` 可走长连接，**须 3 秒内响应** | 消息事件约 7 小时内重推 4 次；**卡片点击在离线时立即报错** | 每应用最多 50 条连接、随机投递；**外部群不能下载资源** |
| 企业微信 | **智能机器人长连接 API 模式**（`wss://openws.work.weixin.qq.com`，无需固定公网 IP） | 文件、图片、视频**仅支持单聊**；下载地址 5 分钟有效并带解密密钥 | 模板卡片按钮事件走长连接，更新卡片须 5 秒内完成 | 文档未说明（按单连接设计推断离线消息难以补收） | **每个机器人同时只能一条连接**，新连接踢掉旧连接；自建应用回调需要公网 URL，不采用 |

由此得到三条设计约束：

1. **IM 连接器必须是律所侧唯一的消息消费者**：飞书（每应用最多 50 条连接）、钉钉会把消息随机派给某一条连接，企业微信每个机器人只允许一条连接——绝不能让每台律师电脑各连同一个机器人。连接器运行在所内节点上（主备节点时，飞书与钉钉可双活，企业微信租约选主，§7.4）；没有所内节点的团队，可指定一台工作时间常开的电脑作为“IM 主机”，并在开通时如实说明离线时的行为（钉钉丢消息、飞书卡片报错）。
2. **连接器只做接收、派发与回执**：收到文件后按发送人与绑定关系写入事项账本（只限已授权节点的事项），派发给对应主机执行（节点自身或律师电脑）；卡片回调在 **2 秒内**同步应答“已收到”（飞书 3 秒、企业微信 5 秒为硬限），审批结果异步落账本后更新卡片（飞书回调令牌 30 分钟内最多更新 2 次）。
3. **“把文件转给机器人”一律在单聊完成**：企业微信只能单聊收文件、飞书外部群拿不到文件，引导文案与首日激活路径都按单聊设计。

机器人能力边界沿用 v4.0：只供律所内部人员使用（深圳律协 2026 指引第 9 条）；只做材料投递、触发任务、状态查询、通知与审批卡片；通知默认不含客户名称与案情；签发必须先看到完整待交付文件（经律所自有 IM 向签发人单独发送确切文件），群转发不扩权。

## 12. 安全

### 12.1 威胁模型（律所侧）

| 资产 | 威胁 | 控制 |
|---|---|---|
| 案卷与成果 | 设备丢失、被盗 | 静态加密、设备吊销、可选密钥租约、推荐 BitLocker |
| | 案卷内的间接提示注入诱导外泄 | 工具面只有法律工具；出站闸门白名单；外发类动作不暴露给 Agent；注入红队每版必测 |
| | 恶意文件（压缩炸弹、路径穿越、畸形 PDF/DOCX） | 解析进程降权无网；解析前校验；超时与资源上限 |
| | 本机其他程序或网页调用本机服务 | 界面、Word COM、Agent 宿主走 IPC/命名管道（按用户、按会话隔离）；WPS 与 Office.js 的固定用户端口只监听 127.0.0.1，一次性令牌握手、来源校验、拒绝跨源请求 |

| 签发与审计 | 伪造、篡改 | 设备密钥签名；hash 链；每日检查点；可选可信时间戳 |
| 软件供应链 | 更新被劫持、依赖投毒 | 安装包与更新包代码签名 + 清单签名；锁版本与 SBOM；Kimi Code fork 补丁台账 |

### 12.2 端侧硬化清单

- 按用户安装、非管理员运行；渲染进程沙箱与上下文隔离；关闭页面 Node；严格内容安全策略。
- 本机接口以命名管道为主；必须用 HTTP 的（WPS、Office.js）只监听 127.0.0.1 的按用户固定端口；所有本机接口要求令牌；拒绝跨源请求。
- Agent 与解析进程降权运行，资源上限，任务结束销毁；急停即杀进程树。
- 出站只经出站闸门；遥测**默认关闭**，律所管理员同意后开启，只采集不含内容的产品事件（网络安全法 2025 修正第二十四条第三款）。
- 卸载时清除本机缓存与密钥（可选先导出）；吊销设备证书与令牌。
- 对照 TC260《智能体部署使用安全指引》的本地智能体条款逐条落实（第 6 篇 §8）。

## 14. 发布、更新与内容分发

- **外壳滚动、内核与内容锁定**：Electron 只支持最新三条主线（约 6 个月一换），所以“LTS”不锁外壳——外壳随上游安全更新滚动；LTS（季度）锁定的是内核接口、事件格式、Kimi Code fork、方法包、模型路由与法规库主版本。律所可在所内节点锁定 LTS 通道。
- **兼容与回滚规则**：事件格式版本 N 必须能读 N-1；回滚只回到同一事件格式版本；同步协议要求**节点版本 ≥ 律所内客户端的最高版本**，低版本客户端遇到新格式事件时只读并提示升级。**紧急撤回**（有问题的规则包、模板或模型路由）不受通道锁定限制，并写入审计。
- **签名与增量**：安装包代码签名（国内 CA 的 OV 证书，私钥在硬件模块或云签名）；更新清单 Ed25519 签名；增量更新、分批灰度、可回滚。
- **内容包**：规则包、方法包、法规库增量与客户端分开发布，均签名；法规库每日增量。所内节点可作局域网镜像，律师电脑只需从节点取更新。
- **变更即回归**：引擎、模型路由、方法包、解析器、模板、修订引擎、法规库结构的变更触发相关回归；灰度失败自动停止并回退；已签发成果与审计可读不受影响。
- **分发与信任**：Windows SmartScreen 信誉、主流杀毒软件（Defender、360、火绒、腾讯电脑管家）报备与误报申诉流程前置到 G0；2026 年的证书与信誉规则本轮未核验，G0 与证书商和安全厂商书面确认。

### 16.3 十四项探针（G0 退出条件）

1. **本机引擎**：宿主进程内的 Kimi Code 新建、提示、取消、急停、崩溃后从账本检查点恢复正常；ZP-5/6 注入后引擎稳定（`git` 上下文等降级不报错）；缺签名 profile 时失败关闭。
2. **工具与隔离**：内置工具在模型可见层与执行层都不存在；经原生启动器（参考 codex `windows-sandbox-rs` 裁剪）降权后，宿主进程无法读取快照外文件、无法发起进程、无法直连外网（抓包验收，分别测“免管理员”与“IT 部署含 WFP”两种模式）；遥测、更新、远程控制零外连。
3. **注入**：案卷中放 `AGENTS.md`、伪工具指令、隐藏 skills、项目级 `mcp.json`、符号链接、路径穿越压缩包，无法改变策略、越权读取或绕过出站闸门。
4. **出站闸门**：未化名的直接标识符零外发；“拒绝云端”事项零外发到 MaaS；数据去向卡与抓包结果一致。
5. **文书保真**：50 份真实结构中文合同在 Word 2016/2019/2021/2024/M365 与 WPS 中打开、逐条接受/拒绝、保存再打开零损坏（自研引擎与 Docxodus 同台）。
6. **Office 宿主**：.NET Framework 4.8 COM 加载项经命名管道写修订；WPS 以 publish 在线模式（地址为本机内核）注册并连内核，验证加载项内请求本机是否受跨域或安全设置限制；记录每个宿主 build 与授权类型。
7. **化名**：直接标识符漏替换为 0、姓名召回 ≥ 99%；化名前后高风险召回下降 ≤ 2 个百分点。
8. **本机 OCR 与资源**：8 GB 内存 i5 笔记本上 100 页扫描件在 PP-OCRv5 mobile 与 PP-OCRv6 small 两档的耗时、内存峰值与识别质量；加密 SQLite、FTS5 中文分词扩展与 `onnxruntime-node` 在 Electron 44 下的加载；安装包与内存预算达标。
9. **成本与时延**：S1/S2 的 token、费用、耗时；经 MaaS 中转的缓存命中率；推理档位影响；校准经济模型。
10. **MaaS 法律分组**：令牌即席位的创建/吊销/轮换；额度耗尽与恢复；不存正文的配置核查（含错误日志）；独立上游组织下 100 名律师并发的限流与排队；`X-Msh-Request-Nonce` 透传与响应签名校验可用；顶层 `cache_control` 透传与缓存命中率。
11. **同步与恢复**：所内节点（含主备切换）与共享文件夹两种介质下，断网、断电、同步客户端冲突副本、并发修改的正确性；成员移出后的密钥轮换；**被吊销设备离线回填事件被拒收**；**唯一成员设备丢失后经恢复托管密钥（M-of-N）从备份恢复事项**；单机口令恢复。
12. **签发与审计**：签发签名离线可验证；改一个字节即失效；链篡改可检出；时间戳锚定（若采用）可验证。
13. **分发与环境**：签名安装包在 Windows 10/11（x64 与 ARM64）、Defender 与主流国产安全软件下安装运行不被拦截；**远程桌面/RDS 与云桌面多用户同机**下端口与命名管道不冲突；更新与回滚（含事件格式兼容）。
14. **IM**：从选定平台把 100 MB PDF 转给机器人，所内节点经长连接收取、进入事项、本机处理、卡片回传；审批卡片回调经长连接到达；节点离线时的行为符合说明。
