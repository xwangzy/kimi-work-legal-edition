### 1.2 模型体积与 CPU 耗时（一手）

**PaddleOCR 官方表**（文本检测/识别模块文档；CPU = Intel Xeon Gold 6271C @2.60GHz，FP32、8 线程，“常规模式 / 高性能模式”；体积为 Paddle 推理模型存储大小）：

| 模型 | 精度指标 | CPU 耗时 ms（常规/高性能） | 体积 MB |
|---|---|---|---|
| PP-OCRv5_server_det | Hmean 83.8 | 383.15 / 383.15 | 84.3 |
| PP-OCRv5_mobile_det | Hmean 79.0 | 57.77 / 28.15 | 4.7 |
| PP-OCRv5_server_rec | Avg Acc 86.38 | 31.21 / 31.21（单行） | 81 |
| PP-OCRv5_mobile_rec | Avg Acc 81.29 | 21.20 / 5.32（单行） | 16 |
| PP-OCRv6_medium_det / rec | Hmean 86.2* / Acc 83.2* | 表中未给 CPU 数据 | 59.4 / 73.3 |
| PP-OCRv6_small_det / rec | 84.1* / 81.3* | 未给 | 9.6 / 20.4 |
| PP-OCRv6_tiny_det / rec | 80.6* / 73.5* | 未给 | 1.9 / 4.4 |

来源：https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/module_usage/text_detection.md ；…/text_recognition.md（*号为 v6 新评测集口径，与 v5 数字不可直接横比）。

**新情况（一手）**：PaddleOCR 3.7.0（2026-06-11）发布 **PP-OCRv6**，三档 tiny(1.5M 参数)/small(7.7M)/medium(34.5M)，官方称 medium 相对 PP-OCRv5_server 检测 +4.6%、识别 +5.1%，CPU 端到端 5.2× 提速（OpenVINO）。来源：https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/README.md 。

**官方 ONNX Runtime 引擎对比**（同一文档“5.1 速度数据”，单张示例图、Xeon Gold 6248 @2.50GHz，onnxruntime-gpu 1.23.2 环境；端到端 ms，含前后处理）：PP-OCRv5_mobile_det 17.90；PP-OCRv5_server_det 25.86；PP-OCRv6_medium_det 26.18；PP-OCRv6_small_det 21.49；PP-OCRv6_tiny_det 20.49。**注意**：该表测试环境含 A100 GPU、文档未明确 onnxruntime 行是否走 CPU，只能作为“ONNX 引擎不慢于 Paddle 静态图”的相对参考，**不能当作 i5 笔记本 CPU 数字**。

**RapidOCR 托管的 ONNX 文件实际大小**（ModelScope API，RapidAI/RapidOCR v3.9.2，一手）：

| 文件 | 大小 |
|---|---|
| ch_PP-OCRv5_det_mobile.onnx | 4.82 MB |
| ch_PP-OCRv5_rec_mobile.onnx | 16.63 MB |
| ch_PP-OCRv5_det_server.onnx | 88.12 MB |
| ch_PP-OCRv5_rec_server.onnx | 84.58 MB |
| 方向分类 ch_PP-LCNet_x0_25_textline_ori_cls_mobile.onnx | 1.02 MB |
| PP-OCRv6_det_tiny / small / medium.onnx | 1.83 / 9.93 / 62.12 MB |
| PP-OCRv6_rec_tiny / small / medium.onnx | 4.49 / 21.23 / 76.63 MB |

**推算（非实测）**：mobile 组合 det+rec+cls ≈ 22.5 MB；server 组合 det+rec ≈ 173 MB（不含方向分类）；v6 small 组合 ≈ 31 MB。i5 笔记本单页（A4 扫描 300dpi，约 30–60 行）端到端耗时**本次无一手实测数据**，官方数字来自 Xeon 8 线程，笔记本 4 核/8 线程低压 i5 预计显著更慢；建议 POC 阶段在基线机上实测 mobile 与 v6-small 两档，**未核实**。

**第三方自测（二手）**：ppu-paddle-ocr（MIT）README 在 Apple M1 + Bun 上，PP-OCRv6 tiny 单张小票中位 ≈ 140–160 ms；批量识别峰值 RSS 约 1.0–1.1 GB（不限并发的 Promise.all 达 1.4 GB）。**8 GB 笔记本需限制并发与常驻**。来源：https://raw.githubusercontent.com/PT-Perkasa-Pilar-Utama/ppu-paddle-ocr/main/README.md 。

**Electron safeStorage（官方文档原文要点，一手，electron/electron main 分支 docs/api/safe-storage.md）**：

**判断**：
1. **无需管理员即可落地的组合**：Job Object（资源/生命周期/禁止子进程逃逸）+ 受限令牌或 AppContainer（文件系统 ACL 限制）。AppContainer 对 Node 子进程兼容性差（需为可读写目录单独授 ACL、默认无网络能力，需声明 internetClient capability），适合 OCR/解析等纯计算 worker；Agent 执行 shell 命令更适合“受限令牌 + Job Object + ACL”。

3. 推荐路线：以 **Codex windows-sandbox-rs（Apache-2.0，生产级）为参考裁剪出一个 helper exe**，或直接集成 srt（Apache-2.0，Node 原生 API，但 Windows 仍为 alpha）；不建议依赖个人小项目。

## 7. 8 GB 笔记本内存预算提示（推算，须 POC 实测）

- OCR：二手数据显示 PP-OCR ONNX 批处理峰值 RSS 约 1.0–1.1 GB（M1/Bun），无界并发 1.4 GB → 需单 worker 串行 + 页级流水。
- 嵌入：bge-small-zh int8 约 24 MB 权重，可常驻；bge-m3 / Qwen3-Embedding-0.6B int8 约 0.57–0.61 GB 权重，**不建议在 8 GB 笔记本常驻**，放律所服务器。
- NER：rbt3 FP32 156 MB，量化后更小，可常驻。
- Electron 主进程 + 渲染进程 + Kimi Code Agent（Node）本身占用未在本次核实范围内。
