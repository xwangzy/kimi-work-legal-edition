# Kimi CLI 法律工作台：产品、法源与合规独立研究

调研日期：2026-09-22。适用设计前提：**中国大陆律所、境内托管试点，用户已确认有正式授权或内部平台接入**。本笔记不重复要求取得已有授权；需要的是核对现有合同和部署方案的具体覆盖范围。公开服务条款是核对基线，双方有效的专项协议优先按其约定分析。本文是产品与工程决策材料，不对尚未审阅的合同和具体业务给出已经合规的结论。

## 一、独立判断

可以将当前演示发展为可售产品，但“CLI 接到聊天框”只解决执行能力。律所购买的实际单位是**一个能恢复、能核对、能交付、权限清晰的事项工作空间**。最有价值的闭环是：选定事项和委托立场 → 收集并阅读材料 → 找到事实和法律依据 → 生成可编辑成果 → 律师实质复核 → 交付与归档。

法律质量并非模型单独能保证。至少需要四个相互独立的约束：材料定位可靠；法源版本和适用时间可靠；推论与依据的关系可审查；成果由具有权限的律师定稿。多个 agent 互相评价可以提高发现问题的机会，但不能替代真实法源、确定性字段校验、盲测及律师审阅。

建议首批以**商业合同审查 + 材料整理/事实时间线 + 有来源的法律研究底稿**作为三个实运行场景。合同成果支持 DOCX 修订、评论和干净稿；研究和事实整理支持 Word/Excel/PDF 交付。其他现有场景保持“可配置方法/待开通”，不要把 36 个展示入口同时承诺为已验证生产能力。

## 三、事项工作链路与完整产品的最低组成

### 3.1 建立事项

事项不只是文件夹。需要客户与相对方名称、关联公司/别名、委托立场、争点、适用法域、业务类型、责任律师、成员、保密级别、材料截止时间、法律检索截止时间。允许客户暂未签约时使用受限的预委托事项。

利益冲突检查首期可以衔接律所现有台账，由责任人确认。查询时只返回“可能命中，请联系指定合规人员”，不能通过对手客户的搜索结果泄露被隔离事项名称。系统自动匹配只是线索，不能宣称完成利益冲突审查。《律师法》第38、39条分别涉及保密与利益冲突；本产品采取上述控制是实施建议，而非法律规定的唯一技术方式。[国家法律法规数据库：现行律师法](https://flk.npc.gov.cn/detail?fileId=&id=2c909fdd678bf17901678bf867e80a55&title=%E4%B8%AD%E5%8D%8E%E4%BA%BA%E6%B0%91%E5%85%B1%E5%92%8C%E5%9B%BD%E5%BE%8B%E5%B8%88%E6%B3%95&type=)

### 3.2 收集和阅读材料

保存原始字节与不可变版本；衍生 OCR、结构化文本、缩略图和脱敏件另存。每份材料有“来源、提供人、取得日期、原件/复印件/截图、我方/对方/参考、完整性、解析结果”。扫描缺页、表格错位、批注/修订、附件遗漏必须可见；不支持的文件直接报告，不以空文本继续分析。

文档全量阅读与局部检索应区分：任务报告明确哪些文件和页数已解析、哪些参与当前分析、哪些因错误排除。长文不能因上下文不足悄悄截断。邮件线程保留发件人、收件人、时间、附件关系；首期可只支持用户导出后的文件，不急于接邮箱。

### 3.3 从材料形成可核对的事实

事实表建议含 statement、角色、类型（明确记载/当事人陈述/推断/有争议）、来源定位、相反材料、置信提示、律师确认状态。金额/日期/主体名称用结构化抽取和确定性比较检查；不能把模型“置信度 95%”展示成客观正确率。

哈希和上传记录只能证明系统接收后某版本的一致性，不证明上传前事实真实。证据真实性、合法性、关联性仍涉及举证质证和司法认定；产品界面宜用“材料一致性已核对”“来源可定位”，避免“证据已认证”。[最高法院《人民法院在线诉讼规则》](https://www.court.gov.cn/zixun/xiangqing/309551.html)

### 3.4 分析、复核与交付

合同审查每条建议关联原条款、委托立场/本所规则、问题、影响、建议修订、依据、可退让条件。DOCX 生成器按选中的修订生成结果；禁止让 agent 任意改写文件后把原文悄悄丢弃。保留原版、建议版、律师编辑版和定稿版。

研究报告区分法条原文、案例要旨、事实对照和作者推论；将不利案例与未解决争点一并展示。证据时间线按发生日期排序，同时保存文档形成日期，避免把开票日误认成履行日。

复核不是单个勾选框：对象应是某版本的某条结论。律师改材料、法源、条款或分析后，受影响的复核状态自动转为“需重新核对”。导出包含引用清单和需要保留的生成标识；对外发送是独立动作，要求用户看到确切收件人、文件版本和内容。

### 3.5 归档、退出和运维

首期就需要合同期满的数据导出、删除流程、保留期限、诉讼/监管保全例外、备份处置、人员离职撤权。知识沉淀须由律师选择并脱敏审批，不将所有事项全文自动并入所级知识库。提供服务支持渠道、故障升级、配额、余额/额度预警、费用账单、失败任务恢复和供应商故障说明；这些与“模型好用”同等重要。

## 四、法源策略：采购访问能力，自己掌握引用质量

### 4.1 已核实的一手数据入口

| 来源 | 能确认的事实 | 本产品的适用角色 | 不能据此推断 |
|---|---|---|---|
| [国家法律法规数据库](https://flk.npc.gov.cn/search) | 全国人大提供法源入口，现行法详情可显示公布/施行和效力状态 | 法律与相关规范核验、官方原文链接 | 已有可商用批量 API、全量覆盖所有地方规范 |
| [人民法院案例库](https://www.court.gov.cn/fabu/xiangqing/431662.html) | 2024-05-07 工作规程说明指导性案例和入库参考案例、体例及运行 | 高优先级案例核验与裁判参考 | 全部裁判文书全集、所有案例同等约束力、任意抓取授权 |
| [北大法宝 MCP](https://mcp.pkulaw.com/apis) / [接入指南](https://mcp.pkulaw.com/docs) | 官方公开法规/案例检索、法条识别、引用溯源服务及鉴权配置 | 优先验证企业授权范围内的机器检索连接 | 宣传规模/“修正幻觉”意味着完整覆盖或结果保证 |
| [北大法宝服务条款](https://login.pkulaw.com/Register/ShowClause) | 普通用户使用范围受书面约定及合理自用目的约束 | 核对现有机构/平台许可、补齐确实未覆盖事项 | 律所个人会员自动允许向第三方 SaaS 全租户转供 |

不建议把大规模爬取裁判文书/验证码页面设为核心依赖。公开可阅读与可自动批量采集、长期缓存、向量化、商用再分发是不同问题。若现有平台已有数据接入，先复用并测试其字段、历史版本、许可和限流；不要无理由重买。

### 4.2 法源数据模型建议

法规记录至少包括规范名称、机关、法域、文号、效力层级、公布/施行/失效日期、修改沿革、条号、正文、官方链接、供应商记录 ID、获取时间、内容哈希、许可策略。**查询当前有效法与判断某历史事件应适用的法是两个问题**。除“截至检索日”外必须保存事实发生时间和适用法判断；新旧法衔接、溯及力、地方特别规则需显式分析。

案例记录至少包括案号、法院、裁判日期、程序、文书类型、生效信息、入库/指导案例编号（如有）、争点、案件事实差异、原文定位、官方或获授权链接、抓取日期。不能将普通案例直接描述成普遍适用法律规则；参考价值和适用差异要分开。

### 4.3 引用验证应拆成四层

1. **存在性**：真实来源是否返回该法规、案号或材料；无真实返回记录的引用不能标记已验证。
2. **一致性**：名称、条号、版本、案号、引用原文与返回记录是否匹配；引用由来源记录拼装，避免模型自由生成 URL。
3. **支持性**：该段引文是否支持本条主张，是否断章取义、有相反段落；可用第二次模型审查辅助，仍保留人工核验。
4. **适用性**：法域、时间、案件事实、效力层级与程序是否匹配；这里不能仅以文本匹配代替律师判断。

引用状态建议为“定位已校验／版本已核验／支持性待律师核对／律师已复核”，避免一个绿色盾牌把四者混为一谈。引文点开直达原页或条文，展示周边上下文；来源被删或许可到期时保留允许存储的最小审计信息，按合同处理全文，不静默替换成新版本。

### 4.4 RAG 与检索的分工

事项材料索引遵守 Matter ACL，律所方法/范本索引遵守机构发布权限，外部法源受各自授权。三者分层检索，不混成无来源的向量库。向量检索适合召回，法规定位、案号、合同编号、日期金额宜配合关键词和结构过滤；最终引用必须回到原文。先检索后授权过滤容易泄露摘要/命中数量，应在可访问集合内检索，并在读取原文、导出和引用回放时再次鉴权。

## 五、境内托管试点的合规判断与工程动作

### 5.1 不把“B2B”“境内”“私有部署”当自动结论

《生成式人工智能服务管理暂行办法》第二条区分向境内公众提供服务与未向境内公众提供服务的研发/应用；第十七条针对具有舆论属性或社会动员能力服务规定评估/备案。封闭的特定律所内部试点、向多家律所开放注册销售、律师将能力进一步面向客户开放，事实不同，应逐一评估，不能只凭 B2B 标签排除。[正式办法](https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm)

2026-09-14 最新官方公告仍明确，通过 API 等调用已备案模型的应用/功能由地方网信办开展登记，并规定适用的服务情况公示要求。因此不能把“底层模型已备案”当作下游产品全部手续完成。建议先形成封闭试点事实说明，核实现有内部平台的备案/登记边界，新增产品是否被覆盖由专项合规审阅及属地适用要求决定。[2026年7—8月公告](https://www.cac.gov.cn/2026-09/14/c_1791136833136332.htm)

### 5.2 个人信息与律师保密

律所、产品运营方、云/OCR/模型/MCP 供应商要按照谁决定处理目的和方式区分委托、共同或独立处理关系；不能用统一“用户已同意”代替实际关系。应依据《个人信息保护法》处理合法基础、受托处理约定、敏感信息与影响评估等问题；客户同意不当然覆盖相对人、证人和其他第三方的所有信息。[个人信息保护法](https://www.npc.gov.cn/WZWSREL25wYy9jMi9jMzA4MzQvMjAyMTA4L3QyMDIxMDgyMF8zMTMwODguaHRtbD9yZWY9aW1i)

工程上采用材料分级、按需发送片段、日志默认不存正文、审计访问控制、支持人员临时授权、字段脱敏及密钥隔离；有身份映射表的去标识化信息仍应按受保护数据管理。高敏感/涉密材料在首期明确不接收；无法自动判断全部秘密性质，上传人和责任律师仍承担分类确认。

《网络数据安全管理条例》2025-01-01 生效，涉及分类分级、访问控制等措施、受托处理安排及自动化采集边界。建议由安全负责人完成系统定级/等保等适用判断、风险处置和供应商管理，不以“使用国内云”替代系统级评估。[正式条例](https://www.cac.gov.cn/2024-09/30/c_1729384452307680.htm)

### 5.3 境内部署仍须画清实际数据流

不仅检查数据库和对象存储地点，还要检查模型端点、OCR、检索、遥测、报错跟踪、客服工单、远程运维、CDN 与备份。境外主体远程访问、境外 API 等是否构成出境及需要何种路径，取决于真实处理活动和数据类别；2024 年跨境规定提供分情形安排，不能只据服务器地理位置作结论。[促进和规范数据跨境流动规定](https://www.cac.gov.cn/2024-03/22/c_1712776611775634.htm)

首批试点建议限定已确认的境内处理链路，出网域名按任务工具允许列表，默认关闭任意联网、任意远端 MCP 和 agent 自装依赖。这是为了让已签合同覆盖的范围与真实执行一致。

### 5.4 生成标识和律师定稿

2025-09-01 生效的标识办法第二条有适用主体边界；符合规定情形的服务还涉及显式/隐式标识、下载导出、用户协议等要求。不要对所有内部文书一律作法定义务判断，也不要默认律师点击定稿即可删除全部标识。产品应预留可配置的输出标识和元数据，对应实际适用判断。[标识办法全文](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)

在用户体验上把“AI 草稿”“律师编辑”“责任律师定稿”作为内容流转状态，并在内部审计保留完整来源。客户交付稿的样式、标识、内部批注和源文件暴露范围由机构政策和适用规则共同决定。

## 六、现有正式授权/平台合同应核对什么

Kimi CLI 当前根许可证为 Apache-2.0，允许依条件使用、修改和分发，要求保留相关许可/通知；它本身不提供一般商标授权。开放源代码授权与 Kimi Work 的产品代码、界面素材、品牌、云 API、模型和企业 SLA 是不同权利层。已有正式合作应按实际授权矩阵落地，无需假定这些缺失。[仓库 LICENSE](https://raw.githubusercontent.com/MoonshotAI/kimi-cli/main/LICENSE)

作为公开核对基线，Kimi 国内 API 协议现行页面标明 2026-08-31 生效：第三部分允许接口用于内部或最终用户服务；第四部分要求不要把模型输出直接作为法律专业建议；第五部分描述客户数据按指示处理；第六部分另有输入输出用于服务优化和品牌使用限制。**不能只摘“按指示处理”推断绝不训练/优化，也不能忽略已有专项协议的排除约定。**[官方 API 协议](https://platform.kimi.com/docs/agreement/modeluse)

建议整理一页合同核对矩阵，逐项填“已覆盖的文件/条款/负责人”，只为真正缺口补签：

| 核对事项 | 需要具体到的范围 |
|---|---|
| 发行与品牌 | 使用 Kimi Work 名称、图标、界面、对外称官方/合作产品、渠道和期限 |
| 最终用户服务 | 律所多租户、用户数/机构数、托管运行、API 转售与应用服务区别 |
| 数据用途 | 输入、输出、缓存、工具返回、反馈是否用于训练/评测/人工审查/服务优化；可否排除及执行凭据 |
| 数据链路 | 境内端点、实际运营主体、OCR/模型/搜索子处理商、日志和缓存保留期限、删除流程 |
| 运营保障 | 峰值并发/限流、模型变更通知、停服通知、故障升级、SLA、责任和赔偿界限 |
| 法源许可 | 机器检索、多机构终端展示、引文、全文导出、缓存、向量化、模型输入、统计、授权到期处理 |
| 内部平台接口 | SSO、Matter ACL、文件与消息 API、审计、成果写回、工作流 hooks、正式扩展/分发机制 |
| 用户合同 | 律所与终端用户责任、律师复核、支持和续费、保密与委托处理条款、退出迁移 |

不建议为了赶工把个人 Kimi 订阅账号或个人法律数据库账号集中共享给所有租户。应使用现有企业平台或获授权的机构身份，与各租户可用能力和用量绑定。

## 七、可售 MVP 的实际验收门槛（建议值，非已实现或行业法定标准）

先选 3—5 家设计伙伴律所，每所 5—15 名律师，采用已授权或合成/适当处理样本。建立至少 100 个覆盖三类主场景的任务，按合同类型、文档质量和复杂度分层；至少两名有经验律师对争议样本仲裁。任何统计必须报告样本量、分母、场景、错误类型，不能宣传为总体法律准确率。

| 验收维度 | 建议上线门槛 |
|---|---|
| 跨所/事项隔离 | 所有安全负向测试无越权；检索、下载、引用回放、缓存、后台支持均覆盖；上线前所有 P0/P1 漏洞关闭 |
| 解析完整性 | 每页可追踪成功/失败；错误和跳页 100% 可见；低质扫描自动转待核验；超限拒绝或分批处理 |
| 引用真实性 | 测试集不存在伪造法条/案号/来源；所有对外定稿的可验证法律引用均有关联记录和来源定位 |
| 引用质量 | 律师标注支持性正确率目标 ≥98%；历史适用法单独测；未通过项不允许标为已验证 |
| 合同质量 | 预定义高风险问题召回目标 ≥95%，同时报告误报率；不以多写问题提高表面召回；遗漏直接影响权利责任的项单列 |
| 原文一致性 | 重要金额、日期、主体名称与来源核对；无法确认为明确待确认；DOCX 修订不得损坏原条款/表格/编号 |
| 人工复核 | 所有定稿含责任律师与版本；上游变化自动使相关复核失效；未经定稿不自动对外发出 |
| 恢复和审计 | 断网/worker 重启可恢复已提交输入与成果；重试不重复外部副作用/扣费；每个产物可追到输入、方法、法源和执行版本 |
| 删除与退出 | 单事项/机构导出及删除演练成功；备份残留策略与合同一致；日志不泄露正文和密钥 |
| 有效效率 | 律师盲测“从开始到可交付的总时间”中位数目标降低 ≥30%，包括检查修错时间；记录未达到场景 |
| 成本 | 每场景 P50/P95 成本可见，计入 OCR、搜索、模型、重试、存储与支持；任务预算到限能暂停并保留结果 |

“零伪造引用”是封闭测试和发布门槛，不是对未来所有输入的保证。售卖表达宜为可追溯、可编辑、可复核的辅助工作，不承诺自动消除法律错误。

MVP 暂缓自动法院提交、自动向客户/对方发送文件、自动签署、独立生成并发布正式法律意见、胜诉率承诺、刑事/涉密高风险场景、无限制通用电脑操作。上述动作可在后续明确业务责任、接口可用性和审批机制后逐项开放。

## 八、接下来的最小决策集合

1. 选定三类首发任务各一个明确范围和真实文书样本，确认责任律师与可衡量收益。
2. 复用现有平台的机构、身份、事项权限和文件能力；确认哪些由本产品补建，避免重复做平台。
3. 拿现有正式协议填完授权/数据用途矩阵，建立端点和子处理商清单。
4. 先用一个获授权法源连接做“检索—原文—历史版本—引用验证”的端到端验证。
5. 将实际解析/OCR、DOCX 修订、人工定稿、恢复删除纳入首个付费试点验收，不延后到全面销售以后。

整体判断：最先形成竞争力的不是更大的场景数，而是**律师能快速看懂为什么这样建议、能找到原文、能改成可交付文书，而且能放心在本所权限体系中长期使用**。Kimi CLI 负责执行与推理迭代，以上事项、法源、审阅和运营机制构成产品的长期资产。
