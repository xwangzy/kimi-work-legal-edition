## 2. 账号登记慢与“还没有登记完成”的根因（02）

线上 `/v1/meta`（1.5.0）没有 `device_auto_enroll`；本机用 `stack-local.mjs --no-account-ca` 复现了线上形态。根因与修法：

| # | 根因 | 修法 | 验证 |
|---|---|---|---|
| R1 | 换账号交接结果为“等批准”时，内核 `onboarding.status()` 待批准分支不带交接结果 → 激活页空等 120 秒报“还没有登记完成” | 带上交接结果；激活页认出“等批准”立即转页 | 内核用例 `b71-device-choice`（真实控制面） |
| R2 | 等待循环不看入组失败、交接丢失，只能空等并要求“重启应用” | 立即说明，改为“再登录一次（不用重启应用）” | 代码走查 |
| R3 | 线上签名服务缺账号设备签发钥（`upgrade.sh` 补钥失败只打印一句）→ 个人账号也走“等批准”；试用 1 台时移除唯一旧电脑后**无人可批**（死路，已在本机栈截图复现） | 云端不再进死路（`device_enroll_unavailable`）+ 启动缺钥严重告警；升级脚本失败不静默、末尾 `verify-capabilities.sh` 核对；运维手册 §5.2 | 云端用例；本机复现截图 |
| R4 | 等批准时同一账号再登录：云端已撤回原申请，本机仍报“正在等待批准”（作废核对码） | 先撤回再按新登录重新申请；别的账号可一步“放弃那个申请” | 内核用例 |
| R5 | 首次打开竞态：重启后首次同步登记电脑前，界面查用量 / 取模型目录得 `device_unknown_or_revoked` | 设备签名的用量、模型目录、账号接口先等首次登记（至多 8 秒） | 计时脚本：报错消失 |

## 3. 设备管理策略（04，D-298）

三种策略独立论证：自动替换（安全差、会在不知情时挤掉正在用的电脑）、人工审批（个人账号的批准人就是本人另一台电脑，会出死路）、用户自主选择。**决定：以用户自主选择为主，人工审批只留给多人律所成员的新电脑，不自动替换；云端是唯一判定方。** 并补了用户倾向里没说到、但决定体验好坏的两点：

1. 上限的口径改为**同时登录的电脑**（未移除且有有效会话），已退出登录的电脑不占名额；
2. 满额时的默认动作是**可逆的“让它退出登录”**（那台电脑上的事项与成果保留，回去重新登录即可），“移除”是次要动作（丢失、转手），带琥珀风险提示。

落实：新电脑、已登记电脑重新登录、换账号三条路径共用同一张选择卡与同一个云端判定；凭刚完成的这次登录（一次性票据）继续，不必再输密码或再收验证码；自动登记签名期间按账号加锁（修两台新电脑同时登记超额、撞编号）；被让出的电脑如实告知是谁让它退出的（本人另一台电脑 / 律所管理员 / 客服）；网关随订阅暂停其 AI；重新登录只填验证码（发到账号绑定手机）。两台“电脑”（两个独立内核）端到端：B 满额让 A 退出 → B 2.3 秒进入；A 得知原因；A 重新登录让 B 退出 → 0.8 秒回到工作区、不重启内核。

## 4. 云端控制台重构（03、07、10、11、13、14）

信息架构采用方案 B：**以客户为主轴**——客户详情是中心（个人客户单人版式），账号详情升为独立页面（顶部“登录诊断”：电脑已满、锁定、客户暂停、待批准一处看全，并给出补救操作），“账号”“电脑”两页降为查找入口；席位、待批准、登录中 / 已退出登录 / 待批准 / 已移除四态、“退出登录 vs 移除”在平台、本所、我的三个分区同一口径；操作记录中文化、可筛选与导出；顺带修复 8 个既有缺陷（操作记录永远为空、个人上限预填错值、没有解锁按钮、收回席位必 404 等）。五轮独立评分：**3.5 → 4.0 → 4.1 → 4.14 → 4.16**（第五轮 13 个主页面无一低于 4.0）。
