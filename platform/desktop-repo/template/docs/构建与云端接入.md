# 构建与云端接入（Windows EXE / macOS DMG）

本页回答三件事：怎样让安装包连上一套云端（含**只有公网 IP、没有域名**的情况）、怎样打 EXE 与 DMG、以后换地址或迁到正式域名怎么办。

## 1. 客户端怎样信任云端

客户端所有出站都经本机**出站闸门**进程。闸门对中软云端（控制面、网关、检索等）的每个连接都做：

1. 只用 `https://`、TLS ≥ 1.2、证书链完整校验（`rejectUnauthorized`，不读 `NODE_TLS_REJECT_UNAUTHORIZED`、`NODE_EXTRA_CA_CERTS` 等环境变量）；
2. 主机身份核对：地址是域名就核对 DNS SAN，**地址是 IP 就核对 IP SAN**（只写了域名的证书按 IP 访问会失败）；
3. 公钥钉住：证书链上任一证书的 SPKI 摘要必须在 `release.json` 的钉住集里，否则在发出任何请求字节前断开（`tls_pin_mismatch`）；
4. 不跟随重定向。

所以“没有域名”本身不是障碍，障碍是**证书**：公网 IP 需要一张带该 IP SAN、且客户端信任的证书。

## 2. 两种证书方案

| | 公共 CA 的 IP 证书（推荐） | 演示 CA（后备） |
|---|---|---|
| 来源 | Let's Encrypt 为公网 IP 签发（短期证书，约 6 天，云端定时续期） | 云端安装时自建 CA，签一张带 IP SAN 的服务器证书 |
| 客户端信任 | Node 内置公共根，无需额外配置 | CA 证书写进 `release.json` 的 `cloud_ca_pem`，**只对中软上游生效、替换公共根** |
| 构建要求 | 正式或测试构建都可以 | 只许测试/演示构建（`test_build: true`），正式发布拒收 |
| 前提 | 服务器 80 端口对公网开放（http-01 验证） | 无 |
| 浏览器打开控制台 | 正常 | 需把演示 CA 导入浏览器/系统，否则提示不安全 |
| 钉住 | 续期复用私钥，SPKI 不变；另备一把离线备份密钥 | 同左 |

两种方案都**不关闭、不放宽证书校验**。云端怎样签发与续期见云端仓库 `docs/部署手册.md`。

## 3. 生成 release.json

云端部署完成后，`tls-ip.sh pins`（`install.sh` 结束时会自动执行）打印两把钉住值（当前 + 备份；控制面、网关、检索共用一张证书），并把客户端需要的公开材料放在服务器的 `/etc/kwl/public/client-inputs/`：`client-release-spec.json`（已填好地址与钉住）、控制面与席位公钥表、备用公钥、演示 CA 证书（演示 CA 方案）。整个目录拷到构建机（只有公钥与证书，没有私钥）。说明文件形如（`release-spec.json` 不入库）：

```json
{
  "control_plane_base": "https://203.0.113.10:8443",
  "gateway_base": "https://203.0.113.10:8444/v1",
  "search_base": "https://203.0.113.10:8445/v1/search",
  "backup_pins": ["tls-backup.pub.pem"],
  "cp_public_keys_file": "cp-public-keys.json",
  "seat_public_keys_file": "seat-public-keys.json",
  "endpoint_profile_key_file": "/secure/endpoint-keys/ep-1.pub.pem",
  "endpoint_deployment": "demo-ip",
  "test_build": true
}
```

- 演示 CA 方案多一行 `"cloud_ca_file": "demo-ca.crt"`（`client-release-spec.json` 已写好）；
- 地址里的 IP 不要写 `:443` 这样的缺省端口；
- `endpoint_profile_key_file` 可选（见 §5）；私钥 `ep-1.key.pem` 离线保管，不入库、不上服务器。

然后在材料目录里（相对路径按当前目录解析）：

```bash
cd client-inputs
node <桌面仓库>/scripts/make-release-config.mjs --spec client-release-spec.json --out <桌面仓库>/apps/desktop/electron/release.json
```

脚本会逐个连上服务（按给定 CA 或公共根完整校验证书、IP 地址不发 SNI），取叶子证书的 SPKI 作“当前”钉住，加上备份钉住，再用客户端同一份代码核对，任何一项不合格都不写文件。服务还没上线时加 `--offline` 并在 `pins.<上游>` 里给出证书或公钥文件。

## 4. 打包

```bash
npm ci
npm run fetch:ocr-models          # OCR 模型（约 21 MB，按摘要核验）；缺了打包会失败
# Windows（推荐在 Windows 上原生构建，或用 .github/workflows/windows-e2e.yml 在运行器上构建并真实联调；
#          Apple 芯片 Mac 上可借 Homebrew makensis 交叉构建，见 scripts/mac-nsis-shim.mjs）
node scripts/package-desktop.mjs --target win32-x64 --sign none
# macOS（Apple 芯片）
node scripts/package-desktop.mjs --target darwin-arm64 --sign none
```

- `--sign none` 只用于测试/演示构建（`release.json` 带 `test_build: true`）。正式发布须 `--sign env`（Windows 代码签名证书 `CSC_LINK` / `CSC_KEY_PASSWORD`；macOS 需 Developer ID 证书与公证）。
- 安装包里的 JS 制品（内核、主进程、Agent 宿主、出站闸门、解析进程）打包时一律压缩（第 60 批；`--no-minify` 只用于排错包，不得对外分发）。

### 4.1 正式发布（域名 + 公共证书，`release.json` 不标 `test_build`；第 60 批）

正式发布只认**生产内容签名公钥**：随包的法规库、方法模板、工具清单、Agent 配置必须用生产内容签名私钥签名，开发公钥在正式包里一律拒载。私钥离线保管，不入库、不进安装包、不上传 CI。

```bash
# 在持有生产内容签名私钥的机器上（Mac）：签好内容并打包（只含签好的产物与公钥，不含秘密）
KWL_CONTENT_SIGNING_KEY_FILE=<私钥 JSON> node scripts/pack-signed-content.mjs --out kwl-signed-content.tar.gz
# 任一构建机：解到仓库根后用现成内容包构建（--prebuilt-content），内核按公钥核对签名者
tar -xzf kwl-signed-content.tar.gz -C .
KWL_CONTENT_SIGNING_PUB_FILE=$PWD/content-signing.pub.json node scripts/package-desktop.mjs --target darwin-arm64 --sign none --prebuilt-content --unsigned-release
```

- `--unsigned-release` 是**还没有代码签名证书时的过渡开关**：其余正式门禁照旧（不得带开发内容公钥），只放行 `--sign none`。证书到位后去掉它、改 `--sign env`。
- Windows 安装包在 `windows-e2e` 工作流里原生构建：把 `release.json` 与 `kwl-signed-content.tar.gz` 放进同一预发布，运行时填两者的 sha256（`release_json_sha256`、`content_bundle_sha256`）。
- 对外分发附摘要清单与发布签名（没有操作系统代码签名时，客户 IT 据此核对来源与完整性）：

```bash
KWL_RELEASE_SIGNING_KEY=<发布签名私钥 PEM> node scripts/sign-release-checksums.mjs --out <分发目录> KimiWorkLegal-Setup-0.2.0.exe KimiWorkLegal-0.2.0-arm64.dmg
node scripts/sign-release-checksums.mjs --verify <分发目录>          # 或用 OpenSSL 3：见脚本头注释
```
- 打包时会扫描安装包内容，出现构建机用户目录路径即失败（第 54 批：W 运行时里在构建机上从源码编译的可选原生插件曾把 `/Users/<构建者>/…` 带进安装包，现已不随包）。
- 未签名的 EXE：Windows SmartScreen 会提示“Windows 已保护你的电脑”，点“更多信息 → 仍要运行”；开启了“智能应用控制”的 Windows 11 不允许运行未签名程序，需关闭该项或改用签名构建。
- ad-hoc 签名的 DMG：把 `KimiWorkLegal.app` 拖进“应用程序”（Finder 里显示为 KimiWorkLegal，启动后菜单栏与程序坞显示“Kimi Work 法律版”）。从网上、聊天工具或 U 盘拷来的 DMG 带隔离标记，首次打开会被拦：macOS 15 起右键“打开”已不能放行，请到“系统设置 → 隐私与安全性”底部点“仍要打开”并输入登录密码；或在终端执行 `xattr -dr com.apple.quarantine /Applications/KimiWorkLegal.app`。

## 5. 换地址、迁到正式域名（不重装）

`release.json` 带了 `endpoint_profile` 的安装包会读本机的签名地址配置：

```bash
# 一次性：生成签名密钥（私钥离线保管）
node scripts/endpoint-profile.mjs gen-key --dir /secure/endpoint-keys --kid ep-1
# 每次换地址：写新的地址说明（格式同 release-spec.json 的地址与钉住部分），签发，序号递增
node scripts/endpoint-profile.mjs sign --spec new-endpoints.json --key /secure/endpoint-keys/ep-1.key.pem \
  --kid ep-1 --deployment demo-ip --seq 2 --out cloud-endpoints.json
node scripts/endpoint-profile.mjs verify --release apps/desktop/electron/release.json --profile cloud-endpoints.json
```

把 `cloud-endpoints.json` 放到律师电脑：

- macOS：`~/Library/Application Support/KimiWorkLegal/cloud-endpoints.json`
- Windows：`%LOCALAPPDATA%\KimiWorkLegal\cloud-endpoints.json`

重启应用生效。从演示 CA 迁到公共 CA 证书的域名时，在地址说明里写 `"cloud_ca": null`，签出的配置会让客户端改回只认公共根。

规则与边界：只能改地址、钉住与（测试构建的）私有 CA；控制面/席位公钥只随安装包；签名不对、部署标识不符、三项不齐、钉住不足两把——整份不生效。

防回滚（第 52 批，D-217）：客户端把生效过的配置原样存为同目录下的 `cloud-endpoints.applied.json`。之后放进来的配置 seq **更小**、seq 相同而内容不同、或签名验不过，都不生效，继续用已生效的那份（重新验签），日志 `MAIN_ENDPOINT_PROFILE_APPLIED` 的 `source` 为 `applied`、并另记 `MAIN_ENDPOINT_PROFILE_PROBLEM`。所以：
- 每次签发 `--seq` 必须递增；要回到旧地址，也签一份 seq 更大的；
- 删掉 `cloud-endpoints.json` = 回到随包地址（换了新安装包、地址也随包变了时这么做）；已生效记录保留，之后再放进更早的配置照样拒绝；
- 同一账户下能改数据目录的恶意程序可以连记录一起删掉，不在防护范围内。

不带 `endpoint_profile` 的安装包要换地址，就重新生成 `release.json` 并重新打包——同样只改配置、不改代码。

## 6. 排查

- **设置 → 备份与安全 → 检测连接**（第 52 批）：逐项连一次云端各服务的 `/healthz`（经出站闸门，与真实流量同一钉住集与演示 CA，不带凭据、不发事项内容），给出每项“正常 / 连不上 / 超时 / 证书公钥与安装包内置的不符 / 证书不受信任 / 证书地址不符 / 安装包连接配置不完整 / HTTP 状态”，可“复制给 IT 的说明”（钉住值只给短前缀）。律师端在问答、任务、登录里遇到证书类失败时也会单独说明“证书校验未通过，已中断、未发出任何内容”，不再笼统说“AI 服务暂时不可用”。
- 登录报“连不上云端”：先在构建机上 `node scripts/make-release-config.mjs --spec release-spec.json --out /tmp/check.json`，看能否连上、证书 SAN 是否含该 IP、钉住是否一致。
- `tls_pin_mismatch`：服务器换了证书私钥。用备份密钥续期，或签发新的 `cloud-endpoints.json`。
- `tls_verify_failed`：证书不受信任或 SAN 不含该 IP（公共 CA 方案下检查证书是否续期成功；演示 CA 方案下检查安装包是否测试构建、CA 是否对应）。

## 7. 已知限制（演示构建）

- **未做代码签名与公证**：EXE 未签名（SmartScreen 提示“未知发布者”）；DMG 为 ad-hoc 签名（首次打开见 §4 的“仍要打开”）。正式发布需要中软的 Windows 代码签名证书与 Apple Developer ID（公证），接入点见 `scripts/package-desktop.mjs` 与 `apps/desktop/electron-builder.yml`。过渡期（第 60 批）以 `--unsigned-release` 出正式内容信任的包，并随附 `SHA256SUMS.txt` 及其 Ed25519 签名（§4.1）。注意：Azure Artifact Signing 的公共信任证书目前不对中国内地与香港主体开放；EV 证书也已不能直接免除 SmartScreen 提示（信誉随下载量积累）。
- **正式包没有开发者工具**（第 60 批）：菜单里没有“切换开发者工具 / 强制重新载入”，快捷键也打不开；测试包保留。远程调试开关 `--remote-debugging-port` 仍可用（端到端验收靠它驱动真实界面）。
- **macOS 钥匙串提示**：数据库主密钥存在钥匙串“Kimi Work 法律版 Safe Storage”里。ad-hoc 签名每次重新打包都会变，升级到新包后第一次打开会弹钥匙串授权框，点“始终允许”即可；换成 Developer ID 签名后不再出现。
- **只有 Apple 芯片 Mac 的 DMG**（darwin-arm64）；Intel Mac 需另锁 x64 原生包，未做。
- **试用构建（`--trial`）不在本仓库**：它把云端网关与可还原的模型密钥打进安装包，与“客户端不持有上游密钥”的边界相反，只在 monorepo 里做。
- **随包子进程用 spawn + IPC 拉起**（不用 `child_process.fork`）：安装包关闭了 Electron 的 runAsNode 熔断，Electron 44 会拒绝应用内的 fork。新增随包子进程时用 `spawnNodeChild`（`packages/kernel/src/executor/child-env.ts`），用例 `packages/kernel/test/b50-no-fork-in-app.test.ts` 会拦住 fork。

## 8. 持续集成（`.github/workflows/desktop-ci.yml`）

本仓库是私有仓库：Windows 分钟按 2 倍、macOS 分钟按 10 倍计费，所以工作流只有两个 job，同一分支有新提交即取消旧运行。

| job | 何时运行 | 做什么 |
|---|---|---|
| `windows`（windows-latest，≤120 分钟） | 推送到 main、推送 `v*` 标签、手动触发（选 windows 或 both） | 导出来源核对 → `npm ci` → 下载并核验 OCR 模型与 Windows 随包运行时（有缓存）→ 构建产物 → Windows 关键用例（`scripts/run-tests-watchdog.mjs` 逐文件、每个文件 10 分钟硬时限，临时目录改到 `C:\kwl-tmp` 避开 runner 的 8.3 短名）→ 用每次运行新建的**仅供测试**自签名证书打 NSIS 安装包 → 静默安装 → `--kwl-smoke` → 无残留进程 → 结果文件已存在时以 3 退出 |
| `macos`（macos-14，Apple 芯片，≤60 分钟） | **只在手动触发**并选 macos 或 both | 打 DMG（ad-hoc 签名）→ `hdiutil attach` → 直接运行 `.app/Contents/MacOS/KimiWorkLegal --kwl-smoke` → 同样的判定 |

冒烟判定（`scripts/ci/check-smoke.mjs`）：`ok` 为 true，且 `checks.children` 的四项全为 `ok`——`gate` 出站闸门、`kap` Agent 宿主、`w` W 执行域（含一次真实的 echo + python3 往返）、`parse` 隔离解析进程（解析一份内存里生成的文本 PDF）。这四项由内核经产品同一代码路径真拉起（`packages/kernel/src/services/child-selftest.ts`），不发网络请求、不调用模型，结果只有结果码。以前的冒烟只看闸门对象存在（闸门按需拉起，进程从未拉起也报 true），抓不到“安装包里 fork 被拒、子进程全部拉不起来”（D-215）。某项失败时结果里是原因码，例如 `runtime_missing`（随包 Node 找不到）、`spawn_denied`（被拦截）、`node_digest`（摘要不符）、`gate_unavailable`（宿主因闸门起不来而未启动），冒烟的 `error` 为 `child_<项>_failed`。

安装包与 `smoke.json` 作为构件保留 7 天。要让 CI 安装包连某套云端（试点 / 预发），把 `make-release-config.mjs` 生成的 `release.json`（须标 `"test_build": true`）整份放进仓库变量 `KWL_RELEASE_JSON`；没设即不带云端上游。CI 不做试用构建（不用 `--trial`），也不做正式签名与公证。

### 8.1 Windows 安装包真实联调（`.github/workflows/windows-e2e.yml`，第 54 批）

只能手动触发（`workflow_dispatch`），因为它要连真实云端、用律所管理员发的一次性邀请码、并跑几十分钟真实模型。输入：预发布标签（里面放 `release.json`，构建出的 EXE 也回传到这里）、`release.json` 的 sha256、邀请码、管理员电脑上的“本所识别码”；正式发布（`release.json` 不标 `test_build`）另填 `content_bundle_sha256`（同一预发布里的 `kwl-signed-content.tar.gz`）。

工作流加固（第 60 批）：第三方 Action 固定到提交 SHA；`checkout` 不留存凭据；邀请码、本所识别码从事件文件读取后屏蔽，其余输入经 `env:` 传入、不内插进脚本；断网演练按云端域名解析出的 IP 封锁（防火墙规则不认域名）。

流程：Windows 原生构建 EXE（不签名）→ 静默安装（按用户）并核对卸载登记、桌面与开始菜单快捷方式 → 以 `--remote-debugging-port` 启动已安装的程序，`scripts/e2e/ui.mjs` 用 playwright-core 经调试端口操作真实界面 → 凭邀请码注册（运行器就是律师的新电脑），打印入组核对码 → 等管理员在自己电脑上核对并批准 → 与输入的本所识别码逐位比对，一致才进入 → 检测连接 → 问答 → 合同审查 + 建议修订稿（`scripts/e2e/cards/contract-review-D2.json`，虚构材料在 `scripts/e2e/fixtures/D2/`）→ 每份 Word/Excel 成果点“下载”，系统“另存为”对话框由 `scripts/e2e/win-save-dialog.ps1`（Windows UI 自动化）填路径并保存，核对 zip 完整、修订（插入/删除/批注）数量与作者 → 套餐与用量 → 用 Windows 防火墙封住云端地址演练断网（检测连接与问答都应如实报错）→ 解封恢复 → 关闭并核对无残留进程 → 静默卸载并核对程序、快捷方式与卸载登记都已清理（本机案件数据按设计保留）。

证据（截图、各阶段日志、导出的成果、`exports.json`、`quota-status.json`）作为构件 `windows-e2e-evidence` 保留 14 天。律师账号的邮箱按运行编号生成、密码在运行器上随机生成，只进屏蔽过的环境变量；工作流不注入任何模拟数据，所有 AI 结果来自真实模型。

本机（macOS）同样可以用 `scripts/e2e/ui.mjs` 驱动已安装的 DMG：启动时加 `--remote-debugging-port=<端口>`，设 `KWL_CDP_PORT`、`KWL_E2E_OUT`、`PW_CORE`（playwright-core 所在目录）；macOS 上的保存对话框没有辅助功能权限时由人点“存储”，脚本等文件出现。
