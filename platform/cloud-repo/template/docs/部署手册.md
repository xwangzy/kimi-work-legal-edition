# 部署手册：从一台空的 Ubuntu 24.04 到上线

本手册在 2026-11-19 从零执行过一遍：环境是本机虚机，Ubuntu 24.04.5、arm64、2 vCPU、4 GB、无预装软件。执行记录见第 12 节。
命令都是演练里实际执行过的。只有两处是演练做不了的，都标了“演练未执行”：公网证书（certbot），以及签名服务账本外送对象存储。

**没有域名、只有一个公网 IPv4 的服务器**，按第 4.5 节“纯公网 IP”部署（2026-11-20 在同一虚机演练，记录见第 12.2 节）：`install.sh --public-ip` 一条命令填好地址、签证书、装续期。其余步骤（密钥、签名服务、启动、控制台）与有域名时相同。

读完第 0 节再动手。服务器上的命令都以 root（`sudo`）执行。

## 0. 全貌

```text
 律师电脑（Windows exe）                         服务器（单机试点；多机见 1.2）                       运营人员（任意网络）
┌─────────────────────┐ HTTPS + 证书钉住  ┌─────────────────────────────────────────────────┐     ┌────────────────────┐
│ 内核 · 出站闸门      │ ─────────────────▶│ 控制面 control-plane   :8443  账号/设备/额度/计费/路由│◀─── │ 浏览器 · 统一控制台   │
│ release.json（地址、 │ ─────────────────▶│ 法律模型网关 gateway    :8444  验席位令牌、调上游、逐请求记账│ ┌─▶ │ https://console…    │
│ 钉住值、公钥）        │ ─────────────────▶│ 检索 search            :8445                         │ │   └────────────────────┘
└─────────────────────┘                   │ 签名服务 cp-signer  127.0.0.1:9443（mTLS，只许控制面）  │ │
                                          │ nginx :443  只托管控制台静态页 ──────────────────────────┘ │
                                          └────────────────────────┬────────────────────────┘
                                                                   │ 上游（只出不进）
                                                          中软 MaaS https://maas.jointpilot.com/v1
```

- **一个进程一个角色**：`node scripts/cloud-serve.mjs --config /etc/kwl/<角色>.json`，由 systemd 单元 `kwl@<角色>` 管。
- **TLS 终止在服务进程本身**：控制面、网关、检索前面**不要**放 nginx、WAF、CDN 或七层负载均衡。客户端钉住服务证书的公钥，被代理换证书就连不上；控制面的登录限流也按来源地址。需要负载均衡时只用四层直通，并保留来源地址。nginx 只托管控制台静态页。
- **运行时零第三方依赖**：只需要 Node.js（≥ 24.15，建议 26.8.1）。
- **上游密钥只在服务端**：可以在控制台录入（浏览器里用网关公钥加密，控制面只存密文），也可以放网关本机文件。前端、exe、仓库、日志里都没有明文。
- **控制台与登录对任意公网 IP 开放**（D-218 取消了运维网段与平台人员两步验证）：不按来源 IP 准入。安全靠 TLS（证书完整校验、客户端钉住）+ 账号密码 + 角色权限 + 登录限流与锁定 + 危险操作密码复核 + 访问审计，全部在服务端。

### 0.1 目录约定

| 路径 | 内容 | 属主 / 权限 |
|---|---|---|
| `/opt/kwl/app` | 本仓库（按发布标签检出） | root，只读 |
| `/etc/kwl/<角色>.json` | 各角色配置 | root:kwl 0640 |
| `/etc/kwl/secrets/` | 私密：服务间凭据、状态密钥、签名私钥、路由私钥、上游密钥 | 目录 root:kwl 0750，文件 0440 |
| `/etc/kwl/public/` | 公开：控制面与席位公钥表、路由公钥 | 0644 |
| `/etc/kwl/tls/` | 证书与私钥、内部 CA 证书 | 目录 root:kwl 0750；私钥 0440 root:kwl（nginx 用的 console.key 0400 root） |
| `/var/lib/kwl` | 数据：控制面状态（密文）、用量账本、审计、网关预写日志、签名服务账本、访问日志 | kwl 0700 |
| `/var/www/kwl-console` | 控制台静态页 + `config.json` | root，0644 |
| `/var/backups/kwl` | 备份 | root 0700 |

## 1. 服务器与网络

### 1.1 单机试点（≤ 20 家律所、≤ 200 名律师）

4 vCPU / 8 GB / 80 GB SSD，Ubuntu 24.04 LTS（x86_64 或 arm64 都行）。

| 端口 | 服务 | 谁访问 |
|---|---|---|
| 443 | nginx · 控制台静态页（80 只做跳转与证书验证） | 律师、律所管理员、运营（浏览器） |
| 8443 | 控制面 | 律师客户端、浏览器里的控制台、网关与检索（订阅） |
| 8444 | 法律模型网关 | 律师客户端 |
| 8445 | 检索 | 律师客户端 |
| 9443 | 签名服务（只听 127.0.0.1） | 只有控制面 |

域名（示例）：`console.kwl.example.com`、`cp.kwl.example.com`、`gw.kwl.example.com`、`search.kwl.example.com`，都解析到这台服务器的公网地址。签名服务用内网名 `cp-signer.internal`，写进本机 `/etc/hosts`。

没有域名时四个端口都用公网 IP：控制台 `https://<IP>`、控制面 `https://<IP>:8443`、网关 `https://<IP>:8444`、检索 `https://<IP>:8445`，见 4.5。

### 1.2 多机

签名服务单独一台，只许控制面所在地址访问 9443。控制面、网关、检索可以各自一台，这时都可以用 443。改动只在配置里：各配置的 `listen.port`，以及网关、检索里 `control_plane.url` 的地址。用量账本是控制面本机文件，所以控制面只跑**单实例**。一主多备时账本目录（`usage_dir`）必须放共享存储，见运维手册。

### 1.3 防火墙（ufw）

> **先放行你正在用的 SSH 来源，再 `ufw enable`**，否则当前会话一断就再也登不上（公网服务器尤其如此）。
> SSH 来源取你管理服务器所用的出口地址；直接从自己电脑登录公网服务器时，取当前会话的来源地址（下面第一行自动取）。这只管服务器的 SSH，与控制台无关。来源地址会变（家庭宽带、手机热点）时，改用云平台安全组限制 22 端口，这里写 `sudo ufw limit 22/tcp`。

```bash
SSH_SRC=${SSH_CLIENT%% *}; echo "当前 SSH 来源：$SSH_SRC"     # 空的话手工填，如 SSH_SRC=198.51.100.7
sudo ufw allow from "$SSH_SRC" to any port 22 proto tcp     # 必须在 enable 之前
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 8443/tcp
sudo ufw allow 8444/tcp
sudo ufw allow 8445/tcp
sudo ufw enable
sudo ufw status verbose
```

`ufw enable` 之后另开一个终端确认还能 SSH 登录，再关掉原会话。云主机另有安全组的，安全组里同样放行 80/443/8443/8444/8445（纯公网 IP 的证书签发与续期要从公网访问 80）。

对外只需开放 80/443/8443/8444/8445 这五个端口（对所有来源放行），外加只对你自己放行的 SSH 22；不需要别的端口。9443 不放行（签名服务只听回环）。

**控制台、登录入口与平台运营功能（`/v1/ops/*`）对任意公网 IP 开放**，不按来源地址准入（D-218）：平台人员在家、出差、手机热点都能直接登录。服务端的防护是：TLS；账号密码（平台人员不再有两步验证，`console.staff_mfa` 已废弃）；按角色授权（没有权限的操作 403、没有会话 401）；登录按来源地址限流（每分钟 20 次）、同一账号 15 分钟内错 10 次锁 15 分钟（423）；危险操作 10 分钟内要输密码复核；每个运营请求与人员登录都写访问审计。老配置里的 `ops.allow_cidrs`、`console.staff_mfa` 不会让服务起不来，启动日志提示“已废弃、已忽略”。

### 1.4 时间与代理

- 时间同步必须开（运营会话、设备签名与证书校验都依赖时钟）：`timedatectl` 应显示 `System clock synchronized: yes`；Ubuntu 缺省有 systemd-timesyncd 或 chrony。
- 服务器若在 `/etc/environment` 里配了 HTTP 代理：Node 服务不读代理变量，直连上游（演练实测：直连 MaaS 正常）；但用 curl 自检本机域名时要加 `--noproxy '*'`，或把内部域名加进 `no_proxy`。

## 4. TLS 证书

### 4.1 签名服务的 mTLS：内部 CA（必做）

在离线的安全电脑上执行（演练在服务器 `/root/kwl-offline` 上执行）：

```bash
OFF=/secure/kwl-offline && mkdir -p $OFF/backup && cd $OFF && umask 077
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout internal-ca.key -out internal-ca.crt -days 3650 -subj "/CN=kwl internal CA"
mk() { # 名称  SAN  用途
  openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout $1.key -out $1.csr -subj "/CN=$1"
  printf "subjectAltName=%s\nextendedKeyUsage=%s\n" "$2" "$3" > $1.ext
  openssl x509 -req -in $1.csr -CA internal-ca.crt -CAkey internal-ca.key -CAcreateserial -days 825 -out $1.crt -extfile $1.ext
}
mk signer        "DNS:cp-signer.internal"          serverAuth
mk cp-api-client "URI:spiffe://kwl/prod/cp-api"   clientAuth      # 签名服务配置 allowed_callers 要与此一致
```

### 4.2 对外三个服务与控制台：公共 CA（生产，必须）

> **硬性要求（演练实测）**：Windows 客户端的出站闸门只信任 Node 内置的公共根证书，再核对钉住值。它**不读**系统证书库，也不读任何“额外 CA”的环境变量；闸门子进程只拿到 `PATH`，这是有意的安全设计，目的是防止被中间人替换证书。
> 所以控制面、网关、检索**必须用公共 CA 签发的证书**。用内部 CA 签的话，服务端自检全部正常，律师端却会提示“连不上中软服务”。内部 CA 只用于签名服务的 mTLS（4.1）。
> 唯一例外：内部测试包可以在打包时内置一个演示 CA（说明文件 `cloud_ca_file`，只许 `test_build`，偏离 D-212），配合 4.5 的 `--tls demo-ca`。正式包不认。

客户端钉住的是**证书公钥**。续期时必须**复用同一把私钥**（`--reuse-key`），或者换成预先登记过的备用密钥（4.3）。否则已经装好的 exe 会连不上。

```bash
# 证书验证走 nginx 的 80 端口（第 3 步装的站点此时只开 80，已放行 /.well-known/acme-challenge/）；四个域名都先解析到本机
sudo apt-get install -y certbot
for d in console cp gw search; do
  sudo certbot certonly --webroot -w /var/www/letsencrypt -d $d.kwl.example.com --key-type ecdsa --reuse-key --non-interactive --agree-tos -m ops@example.com
done
# 拷到 /etc/kwl/tls（服务进程以 kwl 读；控制台证书给 nginx）
for d in cp gw search; do
  sudo install -m 0644 /etc/letsencrypt/live/$d.kwl.example.com/fullchain.pem /etc/kwl/tls/$d.crt
  sudo install -o root -g kwl -m 0440 /etc/letsencrypt/live/$d.kwl.example.com/privkey.pem /etc/kwl/tls/$d.key
done
sudo install -m 0644 /etc/letsencrypt/live/console.kwl.example.com/fullchain.pem /etc/kwl/tls/console.crt
sudo install -m 0400 /etc/letsencrypt/live/console.kwl.example.com/privkey.pem /etc/kwl/tls/console.key
```

证书都到位后重跑 `sudo bash deploy/scripts/install.sh --cp-origin https://cp.kwl.example.com:8443 --console-domain console.kwl.example.com`，nginx 换成完整站点（443）。

续期后要重新拷贝并热换：把上面的拷贝命令写进 `/etc/letsencrypt/renewal-hooks/deploy/kwl.sh`，末尾加 `systemctl reload kwl@control-plane kwl@gateway kwl@search && systemctl reload nginx`（`reload` 让服务重读证书，不断开正在进行的流式回复；旧版单元没有 `ExecReload` 时用 `restart`）。

> **演练未执行**：演练环境没有公网域名，对外证书也只能用 4.1 的内部 CA 签（`mk cp "DNS:cp.kwl.test" serverAuth` 等）。服务端各项（网关和检索订阅控制面、控制台、平台运营）都按生产形态验证通过，因为 systemd 单元里的 `NODE_EXTRA_CA_CERTS=/etc/kwl/tls/internal-ca.crt` 让服务之间认这个 CA。按上面的硬性要求，律师端连不上这种证书：律师端的真实联调改在“本机全链路栈”上做，与生产同一个入口、同一份代码，见验收报告。

### 4.3 备份钉住（必做，离线保管私钥）

```bash
for n in cp gw search; do
  openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out $OFF/backup/$n.backup.key
  openssl pkey -in $OFF/backup/$n.backup.key -pubout -out $OFF/backup/$n.backup.pub.pem
done
```

只把 `*.backup.pub.pem` 交给客户端团队，打进 exe 的钉住集。当前密钥泄露或要更换时，用备用私钥签新证书，`certbot certonly --csr <用备用私钥生成的 CSR>`。

### 4.4 放到服务器

```bash
sudo install -m 0644 $OFF/internal-ca.crt /etc/kwl/tls/internal-ca.crt
for n in signer cp-api-client; do
  sudo install -m 0644 $OFF/$n.crt /etc/kwl/tls/$n.crt
  sudo install -o root -g kwl -m 0440 $OFF/$n.key /etc/kwl/tls/$n.key
done
echo '127.0.0.1 cp-signer.internal' | sudo tee -a /etc/hosts
```

### 4.5 纯公网 IP（没有域名）

适用：服务器只有一个公网 IPv4（云主机的 1:1 NAT 也行），没有域名。**TLS 不降级**：仍是公共 CA 证书 + 客户端钉住，只是证书里写的是 IP（IP SAN）。

**两种证书，二选一**

| `--tls` | 证书 | 客户端 | 用途 |
|---|---|---|---|
| `acme`（缺省） | Let's Encrypt 短期 IP 证书：`shortlived` 配置，有效期 160 小时（约 6.7 天），只能用 HTTP-01（80 端口）或 TLS-ALPN-01 验证 | 正式包、测试包都能连（公共根） | 对外试点 |
| `demo-ca` | 本机演示 CA 签的一年期证书；CA 带名称约束，只能签这一个 IP | 只有内置了这个 CA 的**内部测试包**能连（说明文件 `cloud_ca_file` + `test_build: true`，偏离 D-212） | 内网演示、公网 80 端口进不来时 |

Let's Encrypt 自 2026-01-15 起正式签 IP 证书（必须选 `shortlived`）。限额：同一个 IPv4 每 7 天最多 50 张；完全相同的标识集合每 7 天 5 张（每 34 小时回 1 张）；按 ARI（续期时间建议）续的不占限额。本脚本约 3.3 天续一次，每周 2 张左右。

**前提**：先做完 4.1（签名服务内部 CA）、第 2 节（Node、nginx）；80/443/8443/8444/8445 已在 ufw 和云安全组放行（1.3）。控制台与平台运营不限来源，不用准备运维出口地址。

```bash
cd /opt/kwl/app
sudo bash deploy/scripts/install.sh --public-ip 203.0.113.10 \
     --admin-email admin@csi.example.com --admin-name 系统管理员            # 证书缺省 --tls acme
# 内网演示用演示 CA：把 --tls demo-ca 加在后面；以后换回公共 CA：重跑同一条命令带 --tls acme
```

旧版命令里的 `--ops-cidr` 已废弃：仍给出时脚本只提示“已废弃、已忽略”，照常往下做。脚本在 `install.sh` 原有步骤之外依次做：

1. **地址写进配置**（`deploy/scripts/ip-config.mjs`；配置已存在时只改这几项，可重复执行）：
   - `control-plane.json`：`console.origins` = `https://<IP>`；`console.bootstrap_admin`；删掉已废弃的 `ops.allow_cidrs`、`console.staff_mfa`（老部署重跑时顺手清掉）；
   - `gateway.json`、`search.json`：`control_plane.url` = `https://<IP>:8443`，`control_plane.connect_address` = `127.0.0.1`；
   - 控制台 `config.json`：`control_plane_base`；页面 CSP 与 nginx 响应头的 `connect-src`：`https://<IP>:8443`；nginx `server_name`：IP。
2. **证书**（`deploy/scripts/tls-ip.sh`）：
   - 生成**一把** P-256 私钥 `/etc/kwl/tls/ip/server.key`（已有就绝不覆盖），四个端口共用；证书装成 `cp/gw/search/console.crt|key` 四个名字，配置与有域名时一样；
   - 生成**备用密钥**：私钥 `/root/kwl-offline/tls-backup/server.backup.key`，公钥 `/etc/kwl/public/tls-backup.pub.pem`。**私钥拷到离线介质后从服务器删除**（`shred -u`）；
   - `acme`：下载 lego v5.6.0（脚本里固定了官方 sha256），`lego run --profile shortlived --private-key server.key --reuse-key`，HTTP-01 文件写进 nginx 的 `/var/www/letsencrypt`；
   - `demo-ca`：在 `/etc/kwl/demo-ca/` 建演示 CA（目录 0700、私钥 0600，名称“KWL 演示用（非生产）”），签一年期 IP 证书；网关、检索经 systemd 附加配置 `/etc/systemd/system/kwl@.service.d/kwl-extra-ca.conf` 认“内部 CA + 演示 CA”（不往 `internal-ca.crt` 里追加：签名服务拿它验客户端证书）；
   - 装续期定时器 `kwl-cert-renew.timer`（每天 03:17、15:17 前后各一次）。
3. **钉住值**：打印两把（三个服务相同：当前私钥的公钥 + 备用公钥），并把交给客户端团队的材料放到 `/etc/kwl/public/client-inputs/`：`client-release-spec.json`（地址、`backup_pins`、`pins`，演示 CA 模式另有 `cloud_ca_file` 与 `test_build: true`）、`tls-backup.pub.pem`、`cp-public-keys.json`、`seat-public-keys.json`（第 5 节之后才有，届时执行 `sudo bash deploy/scripts/tls-ip.sh pins` 重新生成）、`pins.txt`，`demo-ca.crt`（演示 CA 模式）。不含任何私钥。

之后照常做第 5 节（密钥）。第 6 节只需复制签名服务的配置：控制面、网关、检索的配置已由脚本生成，**不要**再从样例覆盖，只按表补其余必改项。检索的 `upstream` 与有域名时相同。

**续期与钉住不变**：定时器调 `tls-ip.sh renew`，到期过半才真续（lego 按证书寿命与 ARI 判断）。续了之后钩子 `tls-ip.sh deploy` 先核对“新证书公钥 = 当前私钥公钥”，不等就拒绝安装（否则已装好的 exe 全部连不上），再把证书装到四个名字，`systemctl reload` 控制面、网关、检索（进程收到 SIGHUP 重读证书，已有连接与流式回复不断）并 reload nginx。

```bash
systemctl list-timers kwl-cert-renew.timer          # 下次检查时间
journalctl -u kwl-cert-renew -n 50 --no-pager       # 续期记录；装着的证书 24 小时内到期时本单元记为 failed
sudo bash deploy/scripts/tls-ip.sh renew --force    # 立刻续一张（占限额，别频繁用）
sudo bash deploy/scripts/tls-ip.sh pins             # 再打印钉住值、重新生成 client-inputs
```

**网关、检索连控制面（`connect_address`）**：很多云主机的公网 IP 不在网卡上，本机连自己的公网 IP 要绕出去再回来，有的平台不通。`control_plane.connect_address: "127.0.0.1"` 让 TCP 连回环，证书仍按 `control_plane.url` 里的公网 IP 完整校验（证书链 + IP SAN，不关任何校验）。网关、检索与控制面不在同一台时（1.2 多机），删掉这一项或给 `install.sh` 加 `--no-connect-address`。

**常见问题**

| 现象 | 原因与处理 |
|---|---|
| lego 报 `Non-200 status code … returned 403` | nginx 读不到验证文件：`/var/www/letsencrypt` 及子目录要 0755（脚本已处理；手工建过目录的检查权限） |
| lego 报连接超时 / `Connection refused` | 80 端口没对公网放行（ufw 或云安全组），或 `--public-ip` 不是这台机器的公网地址 |
| `rateLimited` | 同一 IP 一周 5 张已用完：等 34 小时，或先用 `--tls demo-ca` 演示 |
| 浏览器打开控制台提示跨源错误 | `console.origins` 必须是 `https://<IP>`（不带 `:443`、不带末尾斜杠）；脚本已写好，手改过的核对一下 |
| 平台人员登录得 423“密码错误次数过多” | 同一账号 15 分钟内错 10 次，锁 15 分钟：等锁定到期；或请另一位系统管理员在“人员与权限”点“启用”（清锁）或“重置”（发新设置码）。所有系统管理员都被锁时按运维手册 1.2 找回。不是来源 IP 的问题：控制台不限来源 |
| 平台人员登录得 429“尝试过于频繁” | 同一来源地址每分钟登录超过 20 次（多人共用一个出口时容易碰到）：等一分钟再试 |

> **演练范围**：虚机里用 Pebble（Let's Encrypt 的测试 ACME 服务端，支持 IP 标识与 `shortlived` 配置）把首次签发、按时不续、强制续期、钉住不变、热换都走通了（12.2）。**向 Let's Encrypt 正式环境签 IP 证书没有执行过**：演练环境没有公网 IP。第一次在真实公网服务器上执行时，留意上表前三行。

### 4.6 以后从公网 IP 换成域名

只改配置和证书，不改代码。客户端两种接法：安装包的 `release.json` 带了 `endpoint_profile`（签名地址配置的验签公钥）时，**不用重装**——发布方签一份新的 `cloud-endpoints.json` 发给律师电脑即可（见 4.7 第 4 步，域名证书来自公共 CA 时地址说明里写 `"cloud_ca": null`）；没带的安装包要按新地址重新出包。

1. 域名解析到这台服务器，按 4.2 签域名证书。可以继续复用 `/etc/kwl/tls/ip/server.key`（`certbot certonly --csr`，用这把私钥生成的 CSR），钉住值就不变；
2. 重跑 `install.sh --cp-origin https://cp.<域名>:8443 --console-domain console.<域名>`（换控制台页面、CSP 与 nginx 站点）；
3. 改配置：`control-plane.json` 的 `console.origins`；`gateway.json`、`search.json` 的 `control_plane.url`（`connect_address` 可保留，证书按新域名核对）；控制台 `config.json` 的 `control_plane_base`；
4. 停掉 IP 证书续期：`sudo systemctl disable --now kwl-cert-renew.timer`，删 `/etc/kwl/tls-ip.env`；演示 CA 模式另删 `/etc/systemd/system/kwl@.service.d/kwl-extra-ca.conf` 并 `systemctl daemon-reload`；
5. `systemctl restart kwl@control-plane kwl@gateway kwl@search`，按 4.2 的续期钩子接管续期；客户端按上面两种接法之一切到新地址。

### 4.7 换公网 IP（客户端不重装）

服务器换了公网 IP（迁移、换云主机、弹性 IP 变更）。2026-11-20 在虚机上实测：192.168.64.2 → 192.168.64.20，演示 CA 模式。

1. 改各服务里的地址与控制台页内 CSP（可重复执行，保留文件属主 `root:kwl`；输出里应有一行 `index.html：页内 CSP connect-src 'self' https://<新 IP>:8443`）：
   ```bash
   cd /opt/kwl/app
   sudo node deploy/scripts/ip-config.mjs --app /opt/kwl/app --etc /etc/kwl --public-ip <新 IP> --console-dir /var/www/kwl-console
   ```
2. 换证书（服务私钥 `/etc/kwl/tls/ip/server.key` 不变，**钉住值不变**）：
   - 公共 CA：`sudo bash deploy/scripts/tls-ip.sh acme --ip <新 IP>`（新 IP 的 80 端口要先能从公网访问）；
   - 演示 CA：`sudo bash deploy/scripts/tls-ip.sh demo-ca --ip <新 IP> --rotate-ca`（演示 CA 有名称约束、只能签原 IP，所以要换一把新 CA；旧 CA 留在 `/etc/kwl/demo-ca.old-*`）。
3. 换控制台站点（nginx 的 server_name 与证书；页内 CSP 第 1 步已改），并重启服务：
   ```bash
   sudo bash -c '. deploy/scripts/nginx-site.sh; kwl_nginx_site <新 IP> https://<新 IP>:8443 /opt/kwl/app'
   sudo systemctl restart kwl@control-plane && sleep 3 && sudo systemctl restart kwl@gateway kwl@search
   for p in 8443 8444 8445; do curl -s --cacert /etc/kwl/public/demo-ca.crt https://<新 IP>:$p/readyz; echo; done   # 公共 CA 时去掉 --cacert
   ```
   此时旧地址上的客户端连不上（证书不再含旧 IP），这是预期。
   **用浏览器打开 `https://<新 IP>/` 登录一次控制台**（2026-11-21 补核：第 1 步原先只改 `config.json`、不改页内 CSP，换 IP 后控制台页面能打开但登录被浏览器按 CSP 拦下——`curl` 查 readyz 发现不了，第 52 批已修）。
4. 让已装的客户端改连新地址（安装包带 `endpoint_profile` 时）：把新的 `/etc/kwl/public/client-inputs/` 拷到发布方电脑，写地址说明（`client-release-spec.json` 里的三项地址、`pins`、`backup_pins`，演示 CA 时加 `cloud_ca_file`），用离线签名私钥签发：
   ```bash
   node scripts/endpoint-profile.mjs sign --spec addr-v2.json --key /secure/endpoint-keys/ep-1.key.pem --kid ep-1 --deployment <部署标识> --seq <比上次大> --out cloud-endpoints.json
   node scripts/endpoint-profile.mjs verify --release <该安装包的 release.json> --profile cloud-endpoints.json
   ```
   （脚本在桌面客户端仓库。）`--seq` 必须比这台电脑上生效过的大：客户端把生效过的配置存为 `cloud-endpoints.applied.json`，seq 更小、seq 相同而内容不同、签名验不过的配置一律不生效，继续用已生效的那份（防回滚，D-217）；要回到旧地址也签一份 seq 更大的。把 `cloud-endpoints.json` 放到律师电脑 `~/Library/Application Support/KimiWorkLegal/`（macOS）或 `%LOCALAPPDATA%\KimiWorkLegal\`（Windows），重启应用。客户端日志记 `MAIN_ENDPOINT_PROFILE_APPLIED`。
   安装包不带 `endpoint_profile` 时，按新地址重新生成 `release.json` 并重新出包。


```bash

  sudo install -o root -g kwl -m 0440 $OFF/init/secrets/$f /etc/kwl/secrets/$f
```

- `secrets/cp-envelope-next.pem` 是下一把控制面签名密钥：**离线保管，不部署**，轮换时才用。
- 上游（中软 MaaS）密钥有两种放法，二选一：

- 密钥目录按公司规定备份到密钥管理系统，**不进**常规备份（`backup.sh` 已排除）。

## 9. 上线初始化（控制台）

1. **模型与路由**：先核对页头“路由公钥 … 指纹”与服务器上的一致：
   ```bash
   sudo openssl pkey -in /etc/kwl/secrets/routing-key.pem -pubout -outform DER | sha256sum
   ```
   一致后，点上游“中软 MaaS”→ 输入密钥 → 保存，需要复核。约 15 秒后网关生效，健康列显示“正常”，延迟有数。演练：录入后第一次探测 `up`、116 ms。
2. **价目表**：给 `legal/k3`、`legal/k2.6` 填售价和成本价，三档，单位是元/百万 token。不填时 tokens 套餐照常用，账单里的金额显示“未定价”。
3. **套餐与额度**：确认套餐、每席位额度、5 小时窗口、设备数。注册策略保持“凭开通码或邀请码”（`code`）。只有确实要开放自助试用时才改成 `open`，此时控制台会显示风险提示。
4. **开通律所**：客户运营在“客户 → 开通律所”填租户编号、名称、套餐、席位和订阅天数。然后开通专员在律所详情“开通与订阅 → 发创始开通码”，把码交给律所负责人。负责人在 exe 里“注册 → 我有开通码”。
5. **检索**：中软 MaaS 的 `/v1/tools/search` 至今返回失败。上线前要和 MaaS 确认联网检索的地址；不提供的话，检索上游另配。在此之前，律师端“法律检索”不可用，本机法规库不受影响。
