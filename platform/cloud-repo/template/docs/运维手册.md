# 运维手册

部署好之后的日常操作。路径与命令按《部署手册》的单机布局：代码 `/opt/kwl/app`，配置 `/etc/kwl/<角色>.json`，密钥 `/etc/kwl/secrets/`，
证书 `/etc/kwl/tls/`，数据 `/var/lib/kwl`，控制台静态页 `/var/www/kwl-console`，服务 `kwl@<角色>`。

## 1. 首个系统管理员（取代旧的“运营私钥文件”）

控制面配置里写了 `console.bootstrap_admin`（邮箱、姓名）时，控制面第一次启动发现**没有有效的系统管理员**，就建这个人员并生成 24 小时有效的设置码：

```bash
sudo cat /var/lib/kwl/control-plane/bootstrap-admin.txt     # 只有 root 与 kwl 能读（0600）；内容：邮箱、设置码、到期时刻
```

1. 用浏览器打开控制台 → 登录页“首次设置 / 用设置码设密码”→ 填邮箱、设置码、新密码（至少 10 位，字母 + 数字）。
2. 用新密码登录即进入控制台（D-218 起平台人员不再有两步验证）。
3. 设置码用过即作废，文件自动删除。之后在“平台运营 → 人员与权限”添加其他人员。

> 控制台、登录入口与平台运营接口对任意公网 IP 开放（D-218 取消运维网段与两步验证；`ops.allow_cidrs`、`console.staff_mfa` 已废弃，配置里还有时启动日志提示“已忽略”，跑一次 `ip-config.mjs` 即删掉）。
> 安全靠 TLS + 账号密码 + 角色权限 + 登录限流与锁定（同一来源每分钟 20 次；同一账号 15 分钟错 10 次锁 15 分钟）+ 危险操作密码复核 + 访问审计。密码只本人知道、不共用账号。

### 1.1 人员与角色

| 角色 | 能做什么 |
|---|---|
| 系统管理员 | 人员与角色、注册策略、模型与路由（含上游密钥）、系统设置；看全部 |
| 客户运营 | 开通与管理律所、套餐与额度、账号停用/重置、设备吊销；看用量、账单、路由 |
| 开通专员 | 只发开通码（与“客户运营”互斥：开律所的人不能自己发码） |
| 财务 | 看律所、用量、账单 |
| 客服 | 给律师发重置码、解锁、下线；看律所、账号、用量 |
| 只读 | 看全部，不能改 |

- 一人 1～3 个角色；至少保留一名有效的系统管理员；不能停用自己、不能去掉自己的系统管理员角色。
- 危险操作（改人员与角色、改注册策略、改路由或上游密钥、终止或清除律所）要求 10 分钟内**复核**过：控制台会弹窗要密码。
- 添加人员：“人员与权限 → 添加”→ 得到一次性设置码（24 小时），当面或经安全渠道交给本人；本人在登录页“用设置码设密码”。
- 离职：停用（立刻下线所有登录）。忘记密码或被锁定：“重置”→ 新设置码（同时清掉锁定、吊销此人全部登录）；只想解锁点“启用”。

### 1.2 所有系统管理员都进不来时（找回）

有服务器 shell 的人：

```bash
echo 'admin@kwl.example.com' | sudo tee /var/lib/kwl/control-plane/admin-recovery.request >/dev/null
sudo chown kwl:kwl /var/lib/kwl/control-plane/admin-recovery.request
sleep 35; sudo cat /var/lib/kwl/control-plane/bootstrap-admin.txt
```

控制面 30 秒内处理：给这位系统管理员发新设置码（同时吊销其全部登录），写进 `bootstrap-admin.txt`，删除请求文件，记审计。邮箱必须是已有的系统管理员。

### 1.3 从旧版（运营名册 + 私钥 / 凭据文件）升级

旧的 `/etc/kwl/ops-roster*.json` 与 `ops/credentials.json` 不再用于控制台登录（不删，回滚旧版时还能用）。按旧名册逐人在“人员与权限”里添加，权限对照：

| 旧名册权限 | 新角色 |
|---|---|
| tenant.manage、quota.manage、quota.cap、plan.manage、account.manage、device.revoke、tenant.terminate | 客户运营 |
| activation.issue | 开通专员 |
| route.manage、tenant.purge | 系统管理员 |
| 只有 tenant.read | 只读 或 财务 |

support / relay / notify 三个可选服务的运营接口仍用名册 + 私钥签名，只给命令行 `scripts/ops-cli.mjs call` 用（不是登录）。`ops-cli password …` 已停用。

## 2. 接入或更换上游模型（控制台 → 平台运营 → 模型与路由）

- 上游密钥**只在服务端**：要么控制台录入（浏览器里用网关路由公钥加密后提交，控制面只存密文与尾号，网关解封后只放内存），要么网关本机文件 `/etc/kwl/secrets/maas.key`（选“使用网关本机密钥”）。前端、exe、代码仓库、日志里都没有明文。
- 录入前核对页面上显示的**路由公钥指纹**与服务器上的一致：

```bash
sudo openssl pkey -in /etc/kwl/secrets/routing-key.pem -pubout -outform DER | sha256sum | cut -c1-16
```

- 型号、Base URL、备用线路、价目表都在这一页改；网关每 15 秒取一次路由，**不用重启、不用重打 exe**。新上游的主机必须先加进网关配置 `routing.allow_hosts` 并 `systemctl restart kwl@gateway`（控制面被攻破也不能把请求改投到名单外）。
- 轮换本机密钥文件：替换 `/etc/kwl/secrets/maas.key`（0400 kwl）后 `sudo systemctl restart kwl@gateway`。

## 2.1 短信验证码服务（控制台 → 客户 → 注册管理 → 短信服务）

手机号验证码注册、验证码登录、找回密码、登录后绑定 / 更换手机号共用一条赛邮云（SUBMAIL）通道，**全部在控制台配置、即时生效**，不改服务器文件、不重打 exe：

- **凭据只在服务端**：AppID、AppKey（只写不回显，控制面存 AES-256-GCM 密文、视图只给末 4 位）、签名（报备的签名文字，不带【】）。验证码的生成、发送、核对都在控制面；exe、网页、日志里没有 AppKey 与验证码，手机号在日志与审计里一律打码。
- **模板项目**：注册模板必填；找回密码、登录、绑定手机号三项不填即沿用注册模板（同一个验证码模板 `@var(code)`、`@var(time)` 通用），页面上显示每项实际生效的模板。
- **开关**：“启用短信验证码”是总开关；“手机号验证码登录”单独开关（缺省开），关掉只影响验证码登录，注册、找回、绑定照常，律师端下次打开登录页即只剩密码登录。“注册必须验证手机号”开着时不能停用短信。
- **频控与风控**（同页可调）：验证码位数、有效期、同号重发间隔、同号每日上限、来源每小时上限、全平台每日上限、单码最多校验次数；另有固定的“来源每小时查询上限 30 次”（登录发码时没注册 / 绑定发码时已被占用这类不发短信的拒绝，防批量探测手机号是否注册）。
- **自检**：先“测试连接”（查余额，不发短信）→“发送测试短信”（要复核密码）→ 启用。服务器出口 IP 若在赛邮云开了白名单要先加上（否则 `sms_ip_blocked` / 赛邮云代码 113）。
- **排查**：“发送记录”页有逐条记录（用途、打码手机号、结果、本平台失败代码与赛邮云代码）与最近 7 天统计（已发送、失败及原因、被频控拦下、核对成功 / 失败 / 输错作废）。常见：`sms_template_invalid`（模板项目不存在或未审核，赛邮云 117/118/120/305–307/406/407…）、`sms_sign_invalid`、`sms_balance_insufficient`、`sms_auth_failed`。
- **生产不要**在 `control-plane.json` 写 `"sms": { "allow_dry_run": true }`（测试部署用：验证码随应答返回、不发短信；部署名以 prod 开头时写了即拒绝启动）。

## 3. 日志与监控

| 看什么 | 命令 |
|---|---|
| 服务状态与最近日志 | `sudo bash /opt/kwl/app/deploy/scripts/healthcheck.sh`、`journalctl -u kwl@control-plane -n 100 --no-pager` |
| 访问与错误日志（白名单字段、不记内容） | `/var/lib/kwl/obs/`（保留 190 天，`log_retention_days` 可改） |
| 平台人员的操作记录 | 控制台“平台运营 → 系统 → 访问记录”；文件 `/var/lib/kwl/control-plane/ops/access.jsonl` |
| 用量账本（逐请求） | `/var/lib/kwl/control-plane/usage/YYYY-MM.jsonl`（只追加，按请求编号去重） |
| 网关预写日志 / 发件箱 | `/var/lib/kwl/gateway/meter.jsonl` + `meter.ack` |
| 指标 | 配 `"metrics": {"host":"127.0.0.1","port":9464}`，Prometheus 抓 `/metrics` |

重点指标：`kwl_gateway_upstream_responses_total{code_class="429"}`（上游限流）、`kwl_gateway_upstream_up{provider,state}`、`kwl_gateway_routing_version`（0 = 没取到路由）、`kwl_gateway_meter_pending`（持续增长 = 控制面不可达，恢复后自动重放）、`kwl_cp_quota_leases_total{result}`、`kwl_cp_state_saves_total{result="failed"}`。

控制台“平台运营 → 总览 → 需要关注”会列：额度阈值 / 上限 / 用完、异常消耗、上游不可用。

## 4. 备份与恢复

```bash
sudo bash /opt/kwl/app/deploy/scripts/backup.sh            # 每日（cron 或 systemd timer）；--stop 时短暂停控制面以严格一致
ls -l /var/backups/kwl/                                     # kwl-YYYYmmdd-HHMMSS.tar.gz + .sha256 + .commit，保留 14 份
```

- 备份含 `/var/lib/kwl`（控制面状态是 AES-GCM 密文，要配合 `cp-state.key` 才能读；账本；审计；签名服务账本；网关预写日志）与 `/etc/kwl` 的配置，**不含** `/etc/kwl/secrets/`——密钥只在密钥管理里备份。
- 建议每日把备份复制到另一台机器或对象存储（开版本控制）：`rsync -a /var/backups/kwl/ backup-host:/srv/kwl-backups/`。
- 恢复：`sudo bash /opt/kwl/app/deploy/scripts/rollback.sh <备份时的代码提交> --restore /var/backups/kwl/kwl-….tar.gz`（会停全部服务、把现有数据目录改名留底再解包）。恢复的是状态（律所、账号、设备、套餐、路由、额度）；用量账本、审计链、网关计量发件箱、签名流水、运营访问记录与运行日志保留恢复前的那一份——备份之后的计费行与审计记录不会随回滚消失。确实要连这些一起换回备份时加 `--restore-all`（会丢备份之后的计费行，律所电脑上已取回的审计记录将与云端对不上）。

定时备份（systemd timer）：

```bash
sudo tee /etc/systemd/system/kwl-backup.service >/dev/null <<'EOF2'
[Unit]
Description=Kimi Work 法律版云端备份
[Service]
Type=oneshot
ExecStart=/bin/bash /opt/kwl/app/deploy/scripts/backup.sh
EOF2
sudo tee /etc/systemd/system/kwl-backup.timer >/dev/null <<'EOF2'
[Unit]
Description=每日 03:30 备份
[Timer]
OnCalendar=*-*-* 03:30:00
Persistent=true
[Install]
WantedBy=timers.target
EOF2
sudo systemctl daemon-reload && sudo systemctl enable --now kwl-backup.timer && systemctl list-timers kwl-backup.timer
```

## 5. 升级与回滚

```bash
cd /opt/kwl/app && sudo git fetch --tags && sudo git tag --sort=-creatordate | head
# 用“目标版本”的升级脚本升级（新版本的升级步骤可能有变化）：备份 → 切代码 → 校验共享契约包 → npm ci → 换控制台、systemd 单元与 nginx 配置 → 按顺序重启并健康检查
sudo git show v1.1.0:deploy/scripts/upgrade.sh > /tmp/kwl-upgrade.sh && sudo bash /tmp/kwl-upgrade.sh v1.1.0
sudo bash deploy/scripts/rollback.sh           # 回到 upgrade.sh 记下的上一版本（代码 + 控制台；数据不动）
```

- 顺序：签名服务 → 控制面 → 网关 → 检索等（`upgrade.sh` 已按这个顺序）。网关依赖控制面的新接口，反过来会 503。
- 升级前看发布说明里有没有“破坏性变更”（`CONTRACT.md` 变更规则）：有的话先发新版 exe，再把 `clients.min_version` 抬上去。
- 回滚只回代码时，新版本写进状态的新字段会被旧版本忽略；要连数据一起回到升级前，用 `--restore`。
- **从旧仓库检出换到本仓库**（例如第 46 批的 `kimi-work-legal-cloud` 检出、上面又覆盖过导出文件）：`upgrade.sh` 用 `git checkout <标签>` 切代码，工作区有未提交改动会切不过去。先把现状记成一个本地提交当回滚目标，再换远端：
  ```bash
  cd /opt/kwl/app && sudo git add -A && sudo git -c user.name=kwl-ops -c user.email=ops@localhost commit -m "升级前现状"
  sudo git remote set-url origin <本仓库地址> && sudo git fetch --tags origin
  sudo bash deploy/scripts/upgrade.sh <标签>      # 之后 rollback.sh 回到上面那个提交
  ```
  2026-11-21 虚机实测（第 52 批）：`upgrade.sh v1.0.7-ip.2` 8.5 秒（备份 → 切代码 → 校验 → npm ci → 换控制台与 nginx → 四个服务按序重启 → 健康检查全 200）→ `rollback.sh` 8.3 秒回到升级前提交 → 再升级；每一步之后律师端问答 6～9 秒正常、控制台浏览器登录正常。

## 6. 排障

| 现象 | 先看 | 常见原因 |
|---|---|---|
| exe“连不上中软服务” | exe 诊断里的去向记录；`/var/lib/kwl/obs/` 访问日志有没有这台电脑的请求 | 防火墙；证书续期换了钉住集之外的密钥；律师电脑时钟偏差 > 5 分钟 |
| 域名部署上所有客户端突然“连不上中软服务”（诊断：证书校验失败） | `echo \| openssl s_client -connect <域名>:8443 -servername <域名> \| openssl x509 -noout -issuer -ext subjectAltName` | 第 63 批线上事故（2026-11-25）：这台机器早先做过纯公网 IP 部署，`kwl-cert-renew.timer` 与 `/etc/kwl/tls-ip.env` 还在，续期把 **IP 证书**装进 `/etc/kwl/tls/{cp,gw,search,console}`，覆盖了域名证书。处置：`systemctl disable --now kwl-cert-renew.timer`、移走 `tls-ip.env`、从 `/var/backups/kwl/` 最近一份备份取回 `etc/kwl/tls/` 的域名证书与私钥、重启 kwl@control-plane / gateway / search。v1.2.2 起 `tls-ip.sh` 遇到域名证书拒绝覆盖、`upgrade.sh` 自动停用这个定时器 |
| 纯公网 IP：证书快到期、`kwl-cert-renew` 失败 | `journalctl -u kwl-cert-renew -n 100`；`systemctl list-timers kwl-cert-renew.timer`；`openssl x509 -in /etc/kwl/tls/cp.crt -noout -enddate` | 80 端口没对公网放行；同一 IP 一周 5 张的限额；新证书公钥与当前私钥不符（脚本拒绝安装）。见部署手册 4.5 |
| 控制台打不开或白屏 | 浏览器开发者工具的控制台报错；`/var/log/nginx/kwl-console.error.log` | `config.json` 缺失或地址写错；CSP 的 connect-src 没写控制面地址 |
| 控制台“连不上控制面” | 浏览器网络面板的跨源（CORS）报错 | 控制面配置 `console.origins` 没写控制台来源（https://console…，无路径无斜杠） |
| 平台人员登录被锁定（423“密码错误次数过多”） | 控制台“平台运营 → 人员与权限”看锁定状态；`/var/lib/kwl/control-plane/ops/access.jsonl` 的 `staff.login` 记录 | 同一账号 15 分钟内错 10 次、锁 15 分钟：等到期；或请另一位系统管理员点“启用”（清锁）或“重置”（新设置码）；所有系统管理员都被锁时按 1.2 找回。不是来源 IP 的问题（控制台不限来源）；短时间大量失败来自陌生地址时按暴力尝试处理，看访问审计 |
| 平台人员登录得 429“尝试过于频繁” | 访问审计里同一来源的登录次数 | 同一来源每分钟登录超过 20 次（多人共用一个出口时容易碰到）：等一分钟 |
| “账号或密码不对”反复出现、随后“已暂时锁定” | 控制台“平台运营 → 账号”或“人员与权限”看锁定状态 | 15 分钟内错 10 次锁 15 分钟；有权限的人点“启用 / 解锁” |
| 律师 AI 报额度相关 | 控制台“客户 → 律所 → 用量”、账号的个人上限 | 本期额度、5 小时窗口、律所上限、个人上限 |
| 网关 503 `routing_unavailable` / `upstream_unavailable` | 控制台“模型与路由”健康列；`journalctl -u kwl@gateway` | 服务间凭据不一致；上游不在 `allow_hosts`；控制台录入的密钥解不开（公钥指纹与网关私钥不配） |
| 用量不更新 | 指标 `kwl_gateway_meter_pending`；`meter.ack` 是否前进 | 网关连不上控制面（恢复后自动重放，账本按请求编号去重，不会重复计费） |
| 控制面起不来 | `journalctl -u kwl@control-plane -n 80` | 配置项名写错（启动时逐项报中文原因）、密钥文件权限不是 kwl 可读、签名服务没起来 |
