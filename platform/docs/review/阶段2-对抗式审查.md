## 级别定义

- **阻断**：违反 P1 通过标准或方案硬约束，且已复现；修复之前 P1 不能判通过。

## 一、问题清单

### S2-01【阻断】目标模式在嵌入形态下不可用，而且会“伪成功”：首个主回合结束就判 succeeded 并解绑，目标仍是 active，会话持续 busy；无预算、无时限的目标也被批准

- **位置**：`runtime.ts:331-351`（主 Agent 的 `turn.ended` 直接进入 finish）、`runtime.ts:358-371`（finish 解绑策略与出口）；`policy.ts:240-250`（CreateGoal 按 T3 直接 approve `orchestration_within_budget`，不检查预算和时限参数）；`capabilities.ts:111`（“目标模式”current = policy_limited）。
- **复现 R4**（端到端，默认档、桌面渠道、假模型经宿主出口）：模型调用 `CreateGoal{objective}`，宿主策略 approve；引擎自带的目标确认卡（`tool_confirmation:orchestration_within_budget`，只能逐次）经业务审批批准；随后模型回复一段文字。观测结果：
  - 运行状态为 `succeeded`，事件序列 `run.started … run.tool_result → run.succeeded`，final_text 是“本轮完成，继续推进目标”；
  - `GET /goal` 返回 `status: "active"`、`turnsUsed: 2`，budget 中 `tokenBudget/turnBudget/wallClockBudgetMs` 全部为 null；
  - 运行判终态之后，引擎继续发起目标续跑回合：8 秒内有 4 次模型请求被宿主出口以 `session_not_bound_or_run_not_live` 拒绝；会话 `status.busy = true`；业务 API 无法再收拾这个会话（终态运行调用 `runtime.cancel` 会得到 conflict）。
- **为何违反**：§11 P1 要求“目标……在嵌入形态可用”；§8 规定“未知状态、缺成果、截断、超时都不能成功”；第 02 篇 §9.7 与能力账本要求“目标模式必须设预算与时限”；能力账本这一行的当前状态高于事实。
  同类问题（静态推断，未复现）：已批准的 CronCreate 到点触发、后台子 Agent 完成后的通知回合，都会落在已经解绑的会话上，表现相同（失败关闭，但会话挂住、结果丢失）。
- **建议**：在 G1 目标语义落地之前，宿主策略对 CreateGoal/SetGoalBudget/UpdateGoal 失败关闭；或者要求 CreateGoal 必须带 token、回合、墙钟三类预算，且不超过运行预算。运行生命周期改为“会话空闲，且没有活动的目标、定时任务和后台子 Agent”时才判终态；目标仍 active 时回合结束不得判 succeeded。终态解绑时同时 abort 引擎回合并清除目标。能力账本把“目标模式”改为 pending/disabled。

### S2-02【重要】“本任务内允许”的范围键只是工具名（FetchURL 再加域名），导致超预算询问被自动批准：任务预算和子 Agent 上限都能被无限突破

- **位置**：`policy.ts:133-139`（allowanceKey）、`policy.ts:170-176`（`ask()` 先查 taskAllowances）、`policy.ts:283-300`（超预算 → `ask("over_budget")`）；`runtime.ts:126-132`（ONCE_ONLY_REASONS 只禁止对 over_budget 这张卡本身选“本任务内允许”）、`runtime.ts:411`。
- **复现 R1**（策略单元）：
  - 默认档，`max_tool_calls = 1`：第一次 FetchURL 访问新域名 → `ask:fetch_new_domain`；律师选“本任务内允许”（与 `runtime.approve` 走同一条路径 `allowForTask`）；之后 4 次同域名抓取全部超出预算，结果都是 `approve:task_allowance:over_budget`。
  - 手动档，`max_subagents = 1`：第一次 Agent → `ask:manual_mode` → 本任务内允许；之后 3 次 Agent 都超过子 Agent 上限，结果都是 `approve:task_allowance:over_budget`。
- **为何违反**：第 02 篇 §9.5⑥ 把“超出任务预算”列为跨边界动作，须逐次确认（实现自己也把 over_budget 列进 ONCE_ONLY）；§9.7 要求并发和预算有上限；能力账本“子 Agent”“Agent 集群”两行写的是“预算不超”。
- **建议**：超预算路径一律不查 taskAllowances。范围键纳入裁决原因和跨边界类别（例如 `manual_mode:Read`、`fetch_new_domain:FetchURL:<host>`），MCP 的键再纳入副作用和资源。对 over_budget、L3a 检索、图像直送、定时、停止任务设一条“永不按任务放行”的硬规则，并补回归用例。

### S2-03【重要】宿主代批计划确认时，按模型给出的 toolCallId 查裁决，不核对会话、Agent、工具名和参数：任何同 id 调用留下的 plan_auto_approved，都能让本调用的审批被宿主自动批准

- **位置**：`runtime.ts:141`（`decisionsByCall` 是全局 Map，键为 toolCallId，跨事项、跨运行共用，从不清理）、`runtime.ts:174`（每次裁决都覆盖写入）、`runtime.ts:269-277`（只要 `decision === "approve" && reason === "plan_auto_approved"` 就调用 `resolveApproval("approved")`）。
- **复现 R3**（运行时单元）：先放入一条来自“另一运行、另一会话”的 ExitPlanMode 裁决（toolCallId = `dup`，plan_auto_approved）；随后本运行收到一条 CronCreate 的 `permission.approval.requested`，toolCallId 也是 `dup`。结果：宿主调用了 `resolveApproval("s", "ap1", "approved")`，事件为 `run.approval_auto`（tool = CronCreate）。律师从头到尾没有看到确认卡。
- **可利用性**：toolCallId 由模型或上游供应方生成。主 Agent 和集群成员在同一会话里并发执行（`toolExecutorService.ts:501` 用 `Promise.allSettled` 收拢同一步的多个调用，静态推断为并发）；不同事项的运行并发时也共用这张表；Kimi 系模型常见的 `functions.<工具名>:<序号>` 形态让跨会话同 id 并不罕见（静态推断）。端到端的碰撞时序未复现。
- **为何违反**：第 02 篇 §9.5 要求“批准绑定主体、事项、动作、参数 hash、对象版本……”；第 04 篇 §3.3 要求“批准人来自可信界面认证或已登记设备签名，不来自模型参数”。“先出计划”（planFirst）和 T8 定时确认都可能因此被绕过。
- **建议**：裁决记录按 (sessionId, agentId, toolCallId) 存取，并核对 toolName 和 argsHash；只有审批请求本身是 ExitPlanMode、同一会话、参数摘要一致时才代批；运行进入终态时清理该运行的记录。

### S2-04【重要】业务 API 信任调用方提供的策略输入，而且默认值失败开放：数据级别缺省为 L2，依据状态、预授权、抓取白名单、预算、渠道都由请求体决定

- **位置**：`runtime.ts:67-80`（StartRunRequest 含 channel、data_level、basis_complete、preauthorized、fetch_allowlist、budget）、`runtime.ts:200`（渠道上限按请求体里的 channel 计算）、`runtime.ts:222-234`（`dataLevel: req.data_level ?? "L2"`；basisComplete、preauthorized、fetchAllowlist、budget 原样进入 RunPolicyContext）。
- **证据**（代码）：
  - L3b 事项的运行，如果调用方不传 data_level，宿主策略按 L2 裁决：WebSearch 从“拒绝”变成“询问”，ReadMediaFile 从“拒绝”变成“询问”；
  - 调用方可以自报 `channel = "desktop"`，拿到桌面的档位上限和批准资格；
  - fetch_allowlist 由请求体给出，默认档下白名单域名的 FetchURL 自动批准。
- **为何违反**：第 04 篇 §1.2 第 2 条规定“运行模式由宿主决定，界面与远程送来的模式参数在业务网关丢弃”；第 02 篇 §9.6 规定“请求中的运行模式、工作区、运行时参数一律丢弃”。数据级别、四项依据、预授权应来自事项记录和律所策略（内核），不应来自请求方。
- **建议**：startRun 只接受 matter_id、method、material_versions、mode、plan_first、goal。data_level、依据状态、fetch_allowlist、预算上限由内核按事项和策略版本提供；缺失时拒绝，或按最严处理（L3b、basis = false）。channel 由业务网关依据传输层身份写入，不从请求体读取。

### S2-05【重要】审批不识别批准人：远程拒批看的是“运行由哪个渠道发起”，device_signature 从不校验；P1“远程渠道”测试名不副实

- **位置**：`runtime.ts:394-414`（approve 的入参只有 decision、object_hash、scope、device_signature、feedback；第 405 行比较的是 `run.channel`）；`p1-kap-host.test.ts:403-419`。
- **证据**（代码与测试阅读）：
  - 对桌面发起的运行，任何调用方（包括将来的手机、IM 网关）调用 approve 都会被接受，因为接口里根本没有“批准人”或“批准渠道”；
  - 反过来，对手机发起的运行，桌面律师也无法批准。第 403 行的测试只证明了这一点；
  - `device_signature` 参数从未被读取。
- **为何违反**：第 04 篇 §3.3 要求“批准人来自可信界面认证或已登记设备签名”；§8 的 Approval 必需字段包括“批准人与设备签名、nonce、有效期、消费状态”；第 02 篇 §9.6 要求远程渠道权限不高于本机。
- **建议**：approve 增加由网关注入的 approver{user, device, channel}，按批准渠道而不是运行渠道判定；记录 nonce、有效期和消费状态。补两条用例：“桌面运行 + 手机批准 → 拒绝”“手机运行 + 桌面批准 → 允许”。

### S2-06【重要】可信 rg 的路径检查只做字符串定位：工作区内的符号链接会被 rg 跟随到事项之外；合并短选项 `-e` 会让路径参数被误当成模式而漏检

- **位置**：`exec-router.ts:146-150`（toolLoc 只调用 `broker.locate`，这是字符串层定位，不做逐级 lstat）、`exec-router.ts:161`（explicitPattern 只认独立出现的 `-e/--regexp/-f/--file`）、`exec-router.ts:196-203`。
- **复现 R2**（执行域路由单元 + 真实 rg `~/.kimi-code/bin/rg`）：
  - 对照组 `[--, root, /etc/passwd]` 被拒（path_outside_matter）；
  - `[-ie, root, /etc/passwd]` 和 `[-eroot, /etc/passwd]` 都被放行，rg 输出了 /etc/passwd 的首行；
  - 在工作区放一个 `lnk -> /etc` 后，`[-m1, --, ^root:, lnk/passwd]` 被放行，并读出了 /etc/passwd。
- **可利用性**：锁版 Grep/Glob 以 `-- <模式> <路径>` 的形式构造参数，模型无法直接注入合并短选项，所以 `-e` 这一项是纵深缺陷。符号链接这一项需要工作区或材料区里出现链接：P1 没有开放 Bash，但 W-core、同步客户端、材料快照中任何一条路径引入链接就能利用。rg 以宿主用户的全部权限运行。
- **为何违反**：第 04 篇 §2“文件读取与搜索”行要求符号链接、重解析点、UNC、长路径、TOCTOU 全拒，并拒绝绝对路径与 `..`；§4.1 Grep/Glob 路由要求拒绝绝对路径（实现接受区内的绝对路径）；§4.4 路径安全。
- **建议**：rg 的每个路径参数和 cwd 都走 broker 的逐级 lstat（与文件读写共用一套实现），遇到链接即拒；按方案拒绝绝对路径；解析短选项时把合并的 `-e`/`-f` 计入 explicitPattern；补回归用例。

### S2-07【重要】能力账本有多行“当前状态”高于事实，而账本测试只证明了“不高于目标”

- **位置**：`capabilities.ts:68`（会话、续接、分叉、导出 = native）、`:72`（提问 = native，证据写“恢复后不丢问题”）、`:84-92`（文件读取与搜索 = policy_limited，证据含“符号链接全拒”）、`:109-111`（子 Agent、集群、目标 = policy_limited）、`:112`（文件历史与快照 = native，证据写“回滚……”）；`p1-kap-host.test.ts:480-494`。
- **证据**：
  - 分叉与导出不在宿主白名单（路由测试本身断言 `:fork` 不可达），也没有导出接口；
  - `runtime.ts:15-16` 自述“审批与提问队列在引擎内是进程级内存，重启即丢失”；
  - 回滚 `runtime.rollback` 恒抛 unavailable；
  - S2-01、S2-02、S2-06 已复现的缺口。
  - 测试只判定 `rank(current) ≤ rank(target)`，而多数行的 current 和 target 写的是同一个字面量，属于同义反复。
- **为何违反**：第 04 篇 §2 规定“完整度不按勾选数平均；每一行都有验收证据”。
- **建议**：只有对应的验收证据（测试名）存在并且通过时，current 才能取 native 或 policy_limited，否则为 pending。账本每行带一个 evidence_test 字段，测试按证据测试的实际结果校验。

### S2-08【一般】P1 工具遍历：覆盖了本配置下模型可见的全部 23 个工具，但没有以模型实际可见的工具集为准，也没有覆盖按配置才出现的工具和子 Agent 作用域的 MCP

- **位置**：`p1-kap-host.test.ts:166-277`。
- **证据**：R4 记录了模型可见工具（无执行域、无 rg、无检索与抓取配置）：Agent、AgentSwarm、AskUserQuestion、CreateGoal、CronCreate、CronDelete、CronList、Edit、EnterPlanMode、ExitPlanMode、GetGoal、Glob、Grep、Read、SetGoalBudget、Skill、TaskList、TaskOutput、TaskStop、TodoList、UpdateGoal、WaitFor、Write，共 23 个，与测试的 mainCalls 一致。所以在本配置下，“全部”成立。不足之处：
  - 清单是手写的，没有与请求里的 `body.tools` 比对；
  - 只跑了自动档；
  - Bash（执行域就绪时）、FetchURL/WebSearch（闸门接入时）、ReadMediaFile（有图像能力时）、NotifyUser、SetTodoList 都没有遍历；
  - 子 Agent 只调用了 Read：子 Agent 作用域里的 MCP 工具，以及 T8、T3 的拒绝路径都没有测。
- **建议**：以每次请求的 `body.tools` 为全集，断言每个工具都出现了裁决；按配置矩阵（执行域 on/off × 检索/抓取 on/off × MCP on）和四种运行模式各跑一遍；子 Agent 作用域至少覆盖 MCP、写入和编排。

### S2-09【一般】计划文件例外放得过宽（静态推断，未复现）

- **位置**：`policy.ts:214-218`、`policy.ts:303-306`。
- **问题**：`isOwnPlanFile` 只校验 `rel[1]` 是本会话，不校验 `rel[3]`（agentId），也不校验当前是否处于计划模式。结果是：子 Agent 可以读写主 Agent（或任意 agentId 目录）的计划文件；任何时刻都能在引擎内部状态区写入 `*.md`。
- **建议**：限定 `rel[3]` 等于请求方的 agentId，并且只在该 Agent 处于计划模式时放行；计划文件路径从引擎的计划服务获取，而不是按目录形状匹配。

### S2-10【一般】可信配置仍有一次磁盘直读（静态推断，未复现）

- **位置**：`engine-config.ts:4-7`、`engine-config.ts:165-167`；`matter-engine.ts:136`；上游 `app/config/configService.ts:384`、`:631-650`（seedInitialLoad 用 `node:fs` 的 readFileSync 直读 configPath）、`:386-397`（watchCandidates 监听 homeDir）。
- **问题**：宿主没有检查 `<home>/kwl-trusted-config.toml` 是否存在。如果该文件存在，它的内容会在构造期成为有效配置，直到 `load()` 用内存存储把它覆盖；构造期就读取配置的服务可能捕获到这个值。“不被磁盘内容覆盖”的说法不严谨：写入确实不可达，但读取可以被预置文件影响。
- **建议**：启动前断言该路径不存在，并以 O_EXCL 占位为只读的空文件或目录；或者打补丁去掉 seedInitialLoad 的直读。

### S2-11【一般】MCP 工具令牌按事项授权，而不是按运行授权；运行结束或取消后 tools.kwl 仍放行

- **位置**：`host-egress.ts:168-173`；`runtime.ts:155`。
- **问题**：工具令牌只看路径里的事项，没有会话或运行绑定。工具调用本身仍要经过宿主策略（未绑定的会话会被拒），但 MCP 握手、`tools/list`、通知等不属于工具调用的请求，在运行之外也会出站。进度文档已将其列为残余。
- **建议**：按“会话 → 运行”签发 MCP 令牌（与模型请求同一机制），运行终态即撤销。

### S2-12【一般】fencing 只落在宿主策略和出口两处

- **位置**：`runtime.ts:358-371`；file-broker 没有运行或纪元的概念。
- **问题**：§8 要求“网关、文件 broker 与提交点都检查纪元”。当前运行进入终态时只解绑策略与出口，已经批准、正在执行的工具（写入、rg）会照常完成。进度文档已将其列为残余。

### S2-13【一般】进程内的越权入口，以及静态面扫描的边界

- `runtime.matterEngine()`（`runtime.ts:454`）是公开方法，返回的 MatterEngine 上 policy（allowForTask、bindSession）、router（setDomain）、kap 都是公开字段。业务网关一旦误把它暴露出去，就绕过了业务 API。建议只在测试构建中可见。
- 静态面测试只扫描 kap-embed 制品，以下内容不在扫描范围内：标为 external、运行时从 node_modules 加载的 jimp（制品中 50 处导入）、node-pty、fsevents，以及 kap-host 自身的依赖。NETWORK_MODULES 不含 `inspector`，文本层也没有检查 `process.getBuiltinModule`。以上几项在当前制品中均不存在（已 grep 核实），但升级时测试发现不了。

## 二、P1 通过标准逐条判定

### 新问题

#### S2-14【一般】可信 rg 读取硬链接文件，与 broker 的硬链接拒绝不一致；检查与使用之间存在 TOCTOU

- **位置**：`exec-router.ts` 的 checkRgArgs（只用 `broker.realpath` 逐级 lstat 检查符号链接，不检查 `nlink`）；`spawnTrusted`。
- **复现**：
  - R2v2：在工作区放置指向事项外文件的硬链接 `hl.txt`。`[--, SECRET, hl.txt]` 被放行，rg 输出 `SECRET-OUTSIDE-ZONE`；同一文件经 `broker.asHostFileSystem().readText` 读取返回 `EMLINK: hard-linked file rejected`。
  - 另以同样的最小环境在工作区直接运行 rg、不给路径参数（等同 Grep 的默认遍历），输出 `inner.txt:SECRET-TRAVERSAL`。也就是说，参数检查对遍历中遇到的文件无能为力。
- **可利用性**：P1/P2 中 Agent 自己无法创建硬链接：Write 经 broker；W-core 写入留在内存，经 broker 校验后提交。需要事项外的写入者（同步客户端、其他进程）在工作区或材料区放置链接。TOCTOU 为静态推断，未复现。
- **建议**：
  - 区域完整性由写入侧保证：材料快照生成、工作区提交、外部写回检测时拒绝 `nlink > 1` 和链接，并定期扫描；
  - Grep/Glob 改为先由 broker 列出合格文件，再把文件清单交给 rg（`--files-from` 或逐个文件传参）；
  - 方案“文件读取与搜索”行如实写明 TOCTOU 残余。

#### S2-15【一般】运行总时限只在主回合结束后才检查；审批有效期只在有人调用 approve 时才生效

- **位置**：`runtime.ts` settleWhenIdle（只有这里比较 deadline）；`onApprovalRequested` 和 `approve`（只有调用 approve 时才检查 `expiresAt`）。
- **复现**：R4v2(c)。设 `maxRunMs = 5000`，手动档运行停在审批等待；8 秒后状态仍是 `waiting_approval`，事件只有 `run.started, run.turn_started, run.approval_requested`。
- **为何违反**：§8 要求运行有 deadline，超时进入 TIMED_OUT/EXPIRED 终态。`RuntimeDeps.maxRunMs` 的注释“单次运行的总时限”与行为不符。
- **建议**：运行级定时器在 deadline 到点时直接收尾，审批卡到期主动按拒绝处理，二者都不依赖主回合结束。

#### S2-16【一般】能力账本的证据核对只检查“字符串存在”，不检查证据是否覆盖该行

- **位置**：`p1-kap-host.test.ts`《能力账本如实标注（审查 S2-07）》（`sources.includes(t)`）；`capabilities.ts`“计划模式”行（evidenceTests: [TOOLS]）。
- **证据**：
  - 登记的证据名只要在任意测试源码中出现（包括注释）即算通过，例如 `"S2-04"`；
  - “计划模式 = native”的“计划审批走业务审批卡”没有任何测试覆盖：全部测试中 `planFirst` 只出现过 false。
- **建议**：evidenceTests 用完整测试名精确匹配；补 `plan_first: true` 时计划确认走审批卡的用例，或者把该行降为 policy_limited/pending。

#### S2-17【一般】业务运行时 API 的剩余口径问题（静态推断，未复现）

- `events()`、`artifacts()` 不要求来源：任何调用方都能读他人运行的事件，其中含 final_text、审批 nonce、工具名。这与伦理墙相悖，须由网关或运行时按发起人或事项成员校验。
- `verifyDeviceApproval` 的签名载荷只有 {approvalId, objectHash, nonce}，不含 decision 与 scope：中继可以把用户签名的“逐次批准”改成“本任务内允许”。第 02 篇 §9.5 要求批准绑定范围。
- `answer()` 不按渠道限制：第 02 篇 §9.6 规定 IM 渠道“能确认：无”。
- `plan_first` 由请求方决定且缺省 false：第 02 篇 §9.3 要求新用户与开放任务默认开启，应由事项策略给出缺省值和下限。
