## 1. 恢复包与恢复码

核对范围：`packages/kernel/src/services/recovery-package.ts`、`packages/keys/src/share-codec.ts`、`packages/kernel/src/index.ts:870-942`（`recovery.* / backup.*` 接线与定时器）、`packages/kernel/src/services/export-file.ts`、`apps/desktop/electron/file-dialogs.cjs`、`apps/desktop/src/components/RecoveryBackup.tsx`。

### 核对属实的部分（正面）

- **熵与派生**：恢复码秘密为 `randomBytes(32)`（256 bit，`recovery-package.ts:95`）；包裹密钥 `HKDF-SHA256(秘密, salt="kwl", info="kwl-recovery-package/3")`（`:51-53`）。秘密已满熵，不做口令拉伸是成立的；离线穷举不可行。
- **AEAD**：AES-256-GCM，每个包新秘密（新密钥）+ 随机 12 字节 IV（`:99-101`），不存在同钥同 IV 复用；附加数据为外层明文 `{kind, v, firm_name, device_id, set_id, created_at}` 的规范化 JSON（`:98`、`:102`、`:144`），外层任一字段被改即解不开；解开后再核 `c.device.device_id === outer.device_id`（`:148`）。
- **编码与校验**：`KWR1` = `ver(1) ‖ set_id(4) ‖ 秘密(32) ‖ check(4)`（`share-codec.ts:147-157`），`set_id` 独立随机（不由秘密派生），外层明文里的 `set_id` 不泄露秘密；行校验字符只是该行可见字符的加权和（`:215-219`），“第 N 行可能抄错”的提示只反映输入本身的一致性，不构成关于秘密的预言机；整体 `check` 是秘密的 32 bit 截断哈希，对 256 bit 秘密不构成可利用的缩减。AEAD 失败统一回“文件被改动过，或恢复码不对”（`recovery-package.ts:151`）。
- **输出路径**：`recovery.create_package` 只在 `SAVE_METHODS` 里经保存句柄换成 `path`（`file-dialogs.cjs:39`），渲染进程自带的 `path/file/dir` 一律剥掉（`:42`、`:130`）；无句柄时内核拒绝（`index.ts:886-887`）。`writeExportFile` 拒绝相对路径、父目录为链接、目标为链接/目录、落在数据根内（`export-file.ts:22-43`），先写同目录 `.part`（独占创建 0600、fsync）再改名——临时文件里也只有密文。
- **明文不落盘**：`collectRecoveryContent` 只读（秘密文件经主密钥解封到内存），`sealRecoveryPackage` / `openRecoveryPackage` 不写任何文件；审计只记动作与设备编号（`index.ts:884`、`:900`、`:910`、`:921`）；`slog` 无恢复码字段；内核 `invoke` 不记录返回值（`index.ts:969-974`）；本机工具端点不转发 `api[*]`（`local-server.ts` 只走工具表）。恢复码只在 `create_package` 的这一次应答里出现，界面只放在 React 状态里，“收起”后置空（`RecoveryBackup.tsx:44`、`:110`），不进 localStorage。
- **包里有什么**（`recovery-package.ts:21-34`、`:56-91`）：密文内——`activation`（含律所与本人显示名）、数据库主密钥、设备签名与加密两把私钥及证书、律所根公钥与恢复托管公钥；创始设备另有律所根私钥及其种子（`firm-root.json` 的 `recoveryCode`）与 `recovery-shares/` 下全部份额。外层明文——律所显示名、设备编号（`dev_<律所>_<成员>`）、恢复码集编号、创建时刻（用于识别，均在附加数据里，改了即解不开）。外层明文让拿到 U 盘的人知道这是哪家律所、哪位成员的恢复包，属设计取舍，建议在第 28 类写明。

### R2A-01【重要】恢复包永久有效、不能作废也不能轮换；“再生成一次”只会多一份同等能力的包

- 证据：
  - 恢复包里是数据库主密钥与设备两把私钥（`recovery-package.ts:83-84`）。仓库里没有任何主密钥轮换（无 `PRAGMA rekey`、无重新封装 `keys/*.json` 的路径——`grep rekey` 无结果），设备身份是确定性的、没有换身份流程（设计 §3.5、D-42）。
  - 每次 `recovery.create_package` 都生成新秘密与新包（`:95`），旧包与旧码不受影响；`backup.status` 只回“已生成 N 次”（`index.ts:913-918`），界面显示“已生成 N 次，试过 M 次”（`RecoveryBackup.tsx:74`），没有任何“旧包请销毁 / 旧包仍然有效”的提示。
  - 备份始终用同一把主密钥（SQLCipher 页、`kwl-sealed/1` 的 HKDF 都派生自它，`devices.ts:82-88`）。
- 推演：律师怀疑恢复码被拍照、或放恢复包的 U 盘丢了，唯一的“补救”是再生成一次——但旧包 + 旧码仍能打开此后**每一份**备份（同一主密钥、同一设备私钥），也能在任何电脑上恢复出与本机同权的设备。泄露无法止损，只能换律所/重装且放弃数据。律师按直觉多次生成，则同等能力的包散落多处。
- 建议修法：
  1. 提供“轮换”：`PRAGMA rekey` 换主密钥 → 重新封装 `keys/` → 主进程按 `adopt` 同一路径重新包裹 → 立即全量备份 → 生成新恢复包；轮换后旧包解出的主密钥打不开新备份（旧备份副本仍可被旧包打开，如实写明）。
  2. 至少先做到：生成新包时界面明说“以前生成的恢复包仍然有效，请销毁”；`backup.status` 返回最近几次的 `set_id` 与时刻，便于律师对照手里的纸。
  3. 设备身份轮换随 G1“按安装生成编号”一并做，写进偏离登记。
- 建议补的测试：轮换后旧包可解但旧主密钥打不开新备份账本；`backup.status` 能列出有效 `set_id`。

### R2A-02【一般】创始设备的恢复包 = 全所控制权，界面与驻留面只说“这台电脑的全部数据”

- 证据：`collectRecoveryContent` 对创始设备另装 `firm-root.json`（根私钥 + 派生它的种子 `recoveryCode`）与 `recovery-shares/` 下**全部** `share-N.json`（`recovery-package.ts:68-76`、`:87-88`）；`create_package` 返回 `includes_firm_root`（`index.ts:901`），界面未使用；界面文案“两样在一起，就等于这台电脑的全部数据”（`RecoveryBackup.tsx:79`）；驻留面第 28 类 `residual`“恢复包 + 恢复码 = 本机全部能力”。
- 推演：创始设备包 + 码可以签发任意管理员证书（往律所里加人）、并凑齐恢复托管私钥的全部份额（门限在包内塌缩为 1），从而解开所有包裹给恢复托管公钥的事项密钥——不止“这台电脑”。这些份额本来就都在创始设备盘上（设计 §1 第 3 点、D-41 过渡），恢复包没有扩大本机的集中度，但把它做成了一个可随身带走的文件。设计 §3.5 写了“过渡”，驻留面与界面没有把后果写全。
- 建议修法：`includes_firm_root` 为真时界面另起一段：“这台是开通律所的电脑：恢复包里有律所的管理钥匙，丢失会让别人能以管理员身份加人、解开全所的托管密钥”；第 28 类 `residual` 补同义一句；C6 落地前至少只放创始人自己那份（或门限所需份数以下）的恢复份额，其余份额走离线分持。
- 建议补的测试：`privacy-residency.test.ts` 对第 28 类断言 `residual` 含“律所根/托管份额”字样（防回退）。

### R2A-04【建议】恢复码的显示与抄写环节

- `window.print()`（`RecoveryBackup.tsx:104`）打印整页设置页；Windows 打印走后台打印池（假脱机文件在打印完成前落在系统目录），选“Microsoft Print to PDF / OneNote”时会生成可能位于同步盘的文件。建议只打印恢复码卡片（打印样式表隐藏其余内容），并提示“不要打印成 PDF 存到网盘”。

## 2. `kernel.adopt_master_key`（采用恢复的数据库主密钥）

核对范围：`packages/kernel/src/index.ts:809-847`、`packages/kernel/src/electron-entry.ts:74-157`、`apps/desktop/electron/main.cjs:298-366`、`:890-912`、`apps/desktop/electron/secret-store.cjs:99-117`、`apps/desktop/dev/bridge.ts:17-28`、`apps/desktop/electron-builder.yml:13-19`。

### 核对属实的部分（正面）

- **谁能触发**：全仓只有一处发出这条广播——待激活模式下 `onboarding.restore` 成功之后（`index.ts:843`）；`onboarding.restore` 只在 `config.onboarding` 时注册（`:802-848`），激活模式的内核没有这个方法。渲染进程只能经 `kwl:invoke` 发 `{id, method, params}`（主进程自己拼消息，`main.cjs:484`），不能往内核端口塞带 `type` 的消息，也不能伪造“内核发来的”消息（主进程只在 `kernel.on("message")` 里处理，`main.cjs:298`）。要诱发这条广播，必须拿得出有效恢复包 + 恢复码 + 签名一致的备份；其他内核方法都不会发它。
- **不转发界面、不进日志**：主进程在白名单转发之前单独截住这条消息并 `return`（`main.cjs:318-334`），白名单只有 `run.updated / run.settled / kernel.event / reminder.due`（`:357-365`）；`slog` 事件只有 `MAIN_ADOPT_KEY_REJECTED / DONE`，不带字段；内核标准输出环形缓冲不含密钥（内核不打印它）。
- **开发桥**：`bridge.ts:20` 只在 `k.config.onboarding` 为真且 `key` 是字符串时设 `process.env.ZR_DB_KEY`；`dev/` 不在 `electron-builder.yml` 的 `files` 里，不进安装包。开发桥本身就以 `ZR_DB_KEY` 作开发形态的主密钥来源（`config.ts:345-346`），没有引入新的生产面。
- **时序**：`kernelOnboarding` 在每次 `kernel.ready` 时按内核自报更新（`main.cjs:308`）；广播在应答后 300 ms 才发（`index.ts:841-845`），而内核入口在处理完排队调用后立即发 `kernel.ready`（`electron-entry.ts:154-157`），同一端口消息有序，因而不会出现“采用消息先于就绪消息”的错序。待激活内核之外的进程发不出这条消息，旧值残留不构成可利用的窗口。

### R2A-05【重要】“本机还没有任何案件数据”这个前提没有被核对：待激活模式下本机可以已有加密的旧工作区，采用新主密钥后它们被静默孤立

- 证据：
  - 主进程只凭内核自报的 `onboarding` 接受采用（`main.cjs:321`），注释写“本机还没有任何案件数据”（`:316`）。
  - 待激活模式的判定只是“没有可读的 `activation.json` 且要求控制面”（`config.ts:311`）；`activation.json` 损坏或格式不符即视为没有（`config.ts:84-104`）；入组生效失败会主动删除它（`index.ts:150-151`）。
  - 第 13 批 B13-K06 已确认：第 13 批之前的安装包以 `demo-firm` 等身份运行，升级后进入待激活，旧工作区（含 `ledger.db`）仍在数据根里——内核甚至会把它们列给激活页（`onboarding.ts:200-209`、`Activate.tsx` “这台电脑上还有以前留下的数据”）。这些旧账本与 `keys/*.json` 都由**当前** `ledger-key` 里的主密钥保护。
  - `adoptDbKey` 把现有 `ledger-key` 改名为 `ledger-key.prev-<毫秒>` 后写入新包裹（`secret-store.cjs:114-115`），之后应用只认新 `ledger-key`。
- 推演：试点律所升级后（或 `activation.json` 被误删/损坏后）在激活页点“从备份恢复”，恢复成功即用恢复包里的主密钥替换本机主密钥——旧工作区的账本与密钥文件此后在应用里打不开；唯一能救回的 `.prev-*` 文件既不在界面出现，也没有任何工具或文档说明怎么用，所内 IT 清理“无用文件”时删掉即永久丢失。`.prev-*` 每次采用都新增一个、从不清理，驻留面第 20 类只登记了 `userData/ledger-key`。
- 建议修法：
  1. `onboarding.restore` 在 `legacyWorkspaces()` 非空时拒绝（或要求律师先确认“旧数据将无法在本应用里打开”，并在采用前把旧工作区与 `.prev` 的对应关系写进 `onboarding-failed.json` 同级的说明文件）；
  2. 更稳妥：`ledger-key` 支持多把（`{current, previous[]}` 均经 DPAPI 包裹），内核按工作区试用，旧工作区仍可导出；
  3. 第 20 类补登记 `userData/ledger-key.prev-*`（DPAPI 包裹的旧主密钥，保留期与清理方式），运维手册写明用途。
- 建议补的测试：待激活数据根里放一个旧工作区 → `onboarding.restore` 拒绝或返回需确认；`adoptDbKey` 单测（现无任何测试覆盖 `adoptDbKey`，`grep adopt apps/desktop/test` 为空）：格式不符拒绝、`safeStorage` 不可用拒绝、旧文件被保留。

### R2A-06【一般】`adoptDbKey` 先改名再写入，两步之间中断会让 `ledger-key` 消失，下次启动静默生成新主密钥

- 证据：`secret-store.cjs:114-115`：`renameSync(file, file.prev-<ts>)` 之后才 `atomicWrite(file, sealed)`；`loadOrCreateDbKey` 在文件不存在（`ENOENT`）时视为首次运行并生成新密钥（`:35-40`、`:58-64`）。
- 推演：两步之间进程被结束（断电、杀进程、`atomicWrite` 写临时文件失败抛错——`adoptDbKey` 的调用方没有 `catch`，`main.cjs:325` 的 `.then` 链上异常成为未处理的拒绝），下次启动 `ledger-key` 不存在 → 生成全新主密钥 → 已恢复的账本打不开，且恢复包里的旧主密钥只存在于已退出的进程内存里；数据根里已有恢复出的工作区，再次恢复会被“已经有这个律所的数据”拒绝（见 R2A-15）。
- 建议修法：先写 `ledger-key.next`（独占创建、fsync），再 `copyFileSync(file, file.prev-<ts>)`，最后 `renameSync(next, file)`（原子替换，文件始终存在）；`adoptDbKey` 的异常统一捕获为 `{ok:false, code:"write_failed"}`。
- 建议补的测试：注入 `atomicWrite` 失败 → `ledger-key` 仍是原文件、返回 `write_failed`。

### R2A-07【建议】采用消息走通用广播通道，安全性依赖展开顺序与白名单两处细节；并发恢复无互斥

- `electron-entry.ts:149` 以 `{ type: "kernel.event", ...msg }` 包装广播——是消息自带的 `type` 覆盖了信封，主进程才认得出 `kernel.adopt_master_key` 并截住。若将来改成 `{ ...msg, type: "kernel.event" }`（与其他信封写法统一时很自然），这条带明文主密钥的消息就会以 `kernel.event` 身份进入白名单，被发给所有窗口（`main.cjs:357-360`）。建议主密钥走专用的点对点消息（不经 `listeners`），并加一条主进程侧测试：任何含 `key` 字段的内核消息都不被 `webContents.send`。
- `onboarding.restore` 没有进行中标记：两次快速调用（两份不同律所的恢复包）都能通过“目标工作区为空”的检查，`activation.json` 后写者胜，主进程两次 `adoptDbKey` 交错，最终 `ledger-key` 与 `activation.json` 可能不属于同一份恢复包。`onboarding.redeem` 与 `restore` 之间同样没有互斥。建议与 `OnboardingService.restarting` 合用一个互斥标记，进行中或已请求重启时一律 409。

## 3. 增量备份

核对范围：`packages/kernel/src/services/backup.ts`（全文 177 行）、`packages/kernel/src/index.ts:870-942`、`apps/desktop/electron/main.cjs:508-519`（选文件夹）、`apps/desktop/electron/file-dialogs.cjs:108-116`、`packages/kernel/src/devices.ts:107-145`、驻留面第 28 类。

### 核对属实的部分（正面）

- 账本：`wal_checkpoint(TRUNCATE)` 后同步 `copyFileSync`（`backup.ts:108-111`），内核是单连接同步驱动，复制期间事件循环被占住、不会有写入，快照一致；`ledger.db-wal/-shm` 不进备份（`:21`）。SQLCipher 页级密文原样复制。
- 清单 `manifest.json` 由设备签名私钥签（`:138-142`，签名字节带域分隔前缀 `kwl-backup-manifest/1\n`，`:62-64`）；恢复时**先**核签名、账本摘要与每个文件摘要，全部通过后才检查目标工作区并开始写（`:159-175`），测试确认核对不通过时不写任何数据（`backup-restore.test.ts:87-89`）。清单路径拒绝 `..` 与绝对路径（`:165`）；清单由本机遍历生成、经设备签名，攻击者不持设备私钥就伪造不了路径。
- 不跟随源侧链接：`walk` 用 `Dirent.isFile()/isDirectory()`（`:52-53`），工作区里的符号链接不进备份。
- 备份位置：主进程选文件夹带 `dontAddToRecent`、拒绝数据根与 userData、给出同步/网络风险标记（`main.cjs:508-519`），内核再拒绝数据根（`index.ts:880-883`、`backup.ts:94`）；渲染进程给不出路径（`FOLDER_METHODS` + `PATH_KEYS` 剥离）。
- `SKIP` 覆盖了运行期日志、套接字、`.log-salt`、入组与认领暂存、设备恢复暂存（`:21`）。测试用金丝雀扫描备份目录 0 命中（`backup-restore.test.ts:49-51`）。

### R2A-08【重要】增量判定只看“大小 + 修改时间”，且清单摘要取自备份位置上的副本：能写备份位置的人可以让本机设备为他的内容签名

- 证据：`backup.ts:120-131`：
  ```ts
  const same = existsSync(dst) && (() => { const ds = statSync(dst); return ds.size === ss.size && ds.mtimeMs >= ss.mtimeMs; })();
  if (!same) { …copyFileSync(src, `${dst}.tmp`)… }
  files.push({ path: rel, size: ss.size, sha256: sha256File(dst) });
  ```
  判定“不用复制”时，清单里写的是**备份位置上那份文件**的摘要，随后整份清单由设备私钥签名（`:138-140`）；恢复时只核“文件摘要 = 清单摘要”（`:166`）。
- 推演：设计与驻留面都写“备份位置本身不需要可信”（`backup.ts:4`、第 28 类）。但能写备份位置的人（共享 NAS 上的其他账户、借用过 U 盘的人、被入侵的同步盘客户端）只要把某个备份副本换成同样大小的内容、并把修改时间设到将来，下一次备份就不会覆盖它，而会把它的摘要签进清单——之后从这份备份恢复，内核认定它是本机设备亲自备份的原件。可被利用的对象是工作区里**不靠自身 AEAD 认证**的文件：
  - `backup.json`（明文，`index.ts:878`）：其中 `dir` 被恢复到新电脑后即成为新电脑的备份位置——可指向攻击者的 UNC 共享（新电脑每天向它发起 SMB 连接并写入全部密文；SMB 连接本身会带出 Windows 账户的 NTLM 质询应答）；
  - `keys/*.json`：`readSecretFile` 对**非封装**的 JSON 照收并就地封装（`devices.ts:143-144`，为旧明文迁移保留的路径），封装格式的认证在这里不起作用（推断：能否借此换入密钥材料取决于 `ensureDevice/ensureFirmIdentity` 对账本内公钥的核对，未逐一闭环，待确认）；
  - 其余明文配置（`.pipe-salt`、`kap/<事项>/home/mcp.json` 等）。
  对密文块与 KWE1 文件，替换的后果是“备份看似成功、恢复后解不开”（静默损坏），同样违背“恢复时先验清单”的意图。非恶意情形下（备份位置时钟超前、FAT 类文件系统时间粒度）也会出现“同尺寸原地修改的文件没有复制、清单却照签”的陈旧副本（推断，未实测）。
- 建议修法：清单摘要一律取自**本机源文件**（复制时边读边算；跳过复制时比对“本机源文件摘要 = 本机上次记录的摘要”，摘要索引存账本或 `backup.json` 之外的封装文件）；若本机摘要与备份副本摘要不符，即重新复制。增量判定可保留“大小 + 修改时间”作快速路径，但签名对象必须是源文件摘要。`readSecretFile` 的明文迁移路径在“从备份恢复”的首次启动中关闭（恢复出来的 `keys/` 只接受 `kwl-sealed/1`）。
- 建议补的测试：备份后把备份里的 `backup.json` 换成同尺寸、改过 `dir` 的内容并把修改时间设到将来 → 再备份一次 → 恢复必须拒绝（或新清单摘要等于本机源文件摘要）。

### R2A-09【重要】文件名与目录结构以明文进入备份位置（含清单），备份位置可以是网盘——界面与驻留面都说“对方只能看到大小与时间”

- 证据：备份目录按工作区相对路径原样建立（`backup.ts:119`），`manifest.json` 以明文列出全部相对路径（`:138-139`）；KWE1 工作区与引擎会话“文件名、目录结构……不加密”（D-48，驻留面第 4 类 `residual`）；目标目录名含律所标识与设备编号 `dev_<律所>_<成员>`（`:58-60`）。界面提示“备份内容是加密的，对方看不到案件内容，但能看到文件大小与备份时间”（`RecoveryBackup.tsx:127`）；第 28 类写“内容全是密文”，`residual` 未提文件名。
- 推演：`kap/<事项>/work/` 下的草稿与产物文件名由律师或模型给出（“某某诉某某起诉状.docx”之类，推断：以实际运行确认），材料快照可能沿用原件文件名（推断）；选同步盘作备份位置时，这些文件名连同事项编号、律所标识与成员标识一起到达网盘服务商，并留在网盘的版本历史里。设计 §2 写“云端（中软）全程看不到……备份内容”，对第三方网盘则未写文件名这一面。
- 建议修法：备份按内容寻址存放（`files/<sha256 前缀>/<sha256>`），相对路径只写进**加密**的清单（清单用由主密钥派生的备份密钥 AEAD 封装后再签名）；目标目录名改为不透明编号（如 `HMAC(主密钥, tid‖device_id)` 截断），恢复时由恢复包里的设备编号算出。至少先把界面与第 28 类改成如实口径：“网盘能看到文件名、文件数量、大小与时间”。
- 建议补的测试：运行一次带工作区文件的任务后备份，断言备份目录与清单里不出现该文件名的明文（金丝雀放在文件名里）。

### R2A-10【重要】“删除事项后备份里同样密码学擦除”不成立：上一份账本快照里仍有事项密钥

- 证据：设计 §3.3 与 `backup.ts:10`“删除事项后的密码学擦除在备份里同样成立：事项密钥已删，备份里的块与工作区解不开”；第 28 类 `residual`“之前的备份副本因事项密钥已删而不可读”。但事项密钥在**账本**里（以设备公钥包裹，第 20 类），备份位置上的 `ledger.db` 是上一次备份时的快照，要到下一次备份才被覆盖（`backup.ts:109-111`，每 24 小时一次，`index.ts:930-932`）；块副本也要到下一次备份才删（`:134-136`）。事项删除不触发备份（全仓没有从删除路径调用 `runBackup`）。
- 推演：删除事项后到下一次备份之前（至多约 25 小时），备份位置上的旧账本 + 恢复包 + 恢复码 = 被删事项完整可读；备份位置是带版本历史的网盘（OneDrive、Dropbox 等缺省保留旧版本）或带快照的 NAS 时，旧 `ledger.db` 版本长期留存，“密码学擦除”在备份侧实际不成立。删除回执写的是“系统备份（还原点、卷影、NAS 快照）”（`matter-lifecycle.ts:309-312`），没有提到本产品自己的备份位置。
- 建议修法：事项删除（以及成员移出事项后的本机清除）完成后立即触发一次备份（覆盖账本快照、删除块副本），失败则在删除回执里写明“备份位置上的副本将在下一次成功备份时失效”；删除回执与第 28 类如实写“备份位置若保留旧版本（网盘版本历史、NAS 快照），旧版本账本连同恢复包可解开已删事项，须按律所保留期清理”；验收用例补设计 §5 的“删除过的事项在恢复后仍不可读”（当前测试未覆盖）。
- 建议补的测试：备份 → 删除事项 → 立即恢复（不再备份）——当前实现下被删事项可读（应改为删除后自动备份使之不可读）；回执含备份位置条目。

### R2A-11【一般】备份位置里的链接与联接点会被跟随：备份可被重定向写到本机任意可写目录（含数据根）

- 证据：`runBackup` 对目标路径不做 `lstat`/`realpath`：`mkdirSync(target)`、`copyFileSync(d.dbFile, target/ledger.db.tmp)`、`mkdirSync(dirname(dst))`、`copyFileSync(src, dst.tmp)`（`backup.ts:106-128`）都跟随路径中的符号链接与目录联接点；临时文件名固定为 `<名>.tmp`，不用独占创建。“不在数据根内”的两道检查都是字符串比较、不解析链接（`index.ts:880-883`；`file-dialogs.cjs:109-116`）。
- 推演：能写备份位置的人把 `KimiWorkLegal-backup/<律所>/<设备>` 或其下某个子目录换成联接点（NTFS 格式的 U 盘上普通用户即可创建），本机每天的备份就会写到联接点指向的目录：写入内容是本机密文（攻击者控制不了内容），但控制得了**位置**和以本应用文件名（`ledger.db`、`manifest.json`、`manifest.sig`、块文件名）覆盖目标目录里的同名文件；指向本机数据根时还会把工作区复制进工作区自身（每次备份递归增长）。
- 建议修法：`configureBackup` 与每次 `runBackup` 先 `realpath` 备份位置，核对“不在数据根内”用解析后的路径；逐级 `lstat` 目标子路径，遇链接或联接点即中止并记错误代码；临时文件用随机名 + `wx` 独占创建；改名前再核目标不是链接。
- 建议补的测试：备份位置下预置指向另一临时目录的符号链接 → `backup.run` 失败且另一目录未被写入。

### R2A-12【一般】恢复时“先验后写”之间重新打开文件，备份位置可在两步之间换文件；恢复不拒绝旧备份

- 证据：`restoreFromBackup` 先对每个文件 `sha256File(join(src, "files", f.path))`（`backup.ts:164-167`），再整体 `copyFileSync` 同一路径（`:170-175`），复制时不再核对；清单的 `seq`、`at` 不与任何东西比较（`:157-177`），恢复包里也没有备份序号（R2A-03）。
- 推演：① 能写备份位置的人在核对与复制之间替换文件（大备份在 NAS 上核对要数分钟，窗口不小）：密文块与 KWE1 会在使用时被 AEAD 拒绝，但非封装的明文文件与 `readSecretFile` 的明文迁移路径（见 R2A-08）照收。② 把整个设备目录换回更早的一份（签名同样有效）即可让律师恢复到几周前的状态而不自知——界面只显示“备份于 日期”（`Activate.tsx` `onDone` 文案），设计 §5 的负例“备份比恢复包旧（提示丢失的天数）”未实现；回退还会让本机的控制面高水位等单调状态一起回退（推断）。
- 建议修法：边复制边算摘要（写到数据根内的暂存目录，核对通过后再改名就位），任何不符整体回滚；恢复包记录生成时的最新备份序号与时刻，恢复时备份 `seq` 低于它即要求律师确认“将丢失 N 天的数据”；界面把备份时刻与恢复包时刻并列显示。
- 建议补的测试：用较旧的一份签名备份恢复 → 返回需确认/提示天数。

### R2A-13【建议】`SKIP` 与备份内容的几处补漏

- `keys/recovery-staged.rejected-<ts>.json`（`devices.ts:342`，被拒的设备恢复暂存，按主密钥封装）不在 `SKIP` 里；`recovery/device-export.json`（`api/index.ts:3159`，`recovery.export_device` 未带保存句柄时的缺省位置，**口令 scrypt 包裹**，口令只要求 ≥ 10 字）不在 `SKIP` 里——若存在，就会把一份只靠律师口令保护的设备私钥放到“不需要可信”的备份位置，供离线碾磨。当前界面不调用 `recovery.export_device`（`grep export_device apps/desktop/src` 为空），属潜在路径。建议 `SKIP` 加 `^recovery(/|$)` 与 `^keys/recovery-staged`，并把 `recovery.export_device` 的缺省路径去掉（无句柄即拒绝，与 `create_package` 一致）。
- `SKIP` 的 `^\.kwl-tmp`、`^logs` 只匹配工作区顶层；`kap/<事项>/home/logs/`（引擎文件日志，`sealed-storage.ts:302` 在启动迁移时按“可丢弃的明文”删除）运行期间是否会重新出现明文日志：**待确认**。若会，每小时一次的备份检查可能在任务运行中把它复制出去。建议 `SKIP` 加 `(^|/)logs/`、`(^|/)\.kwl-tmp`、`(^|/)w-tmp/`，并在 `backup-restore.test.ts` 里先跑一次带工具调用的任务再做金丝雀扫描（当前测试没有创建任何 `kap/` 目录）。
- `kap-trusted/<摘要>.tmp-<pid>-<时刻>`（`skills-bundle.ts:110`）不匹配 `\.tmp-\d+$`（中间多一个 `-`），物化中途被备份会带上半成品（公开内容，影响小）。
- 备份每次对全部文件 `sha256File(dst)`（`backup.ts:131`），即每天把整份备份从 U 盘/NAS 全量读回一遍，且整个过程同步占住内核事件循环（期间所有调用排队）。属可用性问题，建议移到工作线程或按 R2A-08 改为本机摘要索引。

## 4. 恢复到新电脑

核对范围：`packages/kernel/src/index.ts:802-848`、`packages/kernel/src/services/onboarding.ts:580-626`、`packages/kernel/src/services/backup.ts:153-177`、`services/control-plane/src/server.ts:950-994`（设备登记）、`packages/kernel/src/control-plane/governance.ts:312-325`、`apps/desktop/src/pages/Activate.tsx`（`RestoreFromBackup`）、`packages/kernel/src/electron-entry.ts:137-169`、`apps/desktop/electron/main.cjs:366-380`。

### 核对属实的部分（正面）

- 门禁：`onboarding.restore` 只在待激活模式注册、在 `ONBOARDING_METHODS` 白名单内（`onboarding.ts:581`）；安装包形态的恢复包与备份位置只能来自系统对话框句柄（`file-dialogs.cjs:20-28`、`:149-155`）。内核核对：恢复包能用恢复码打开 → 证书由包内律所根签发、证书两把公钥等于包内私钥对应的公钥（`index.ts:814-818`）→ 律所标识字符集与占位名（`:819`）→ 备份清单由该证书公钥签名（`:820-826`）→ 目标工作区为空（`backup.ts:168`）。任一不符都在写入前拒绝。

### R2A-14【重要】恢复后与旧电脑同一设备身份，控制面不知情；“被偷”场景下吊销旧电脑就等于吊销恢复出的新电脑

- 证据：恢复沿用旧设备编号、旧证书、旧私钥（`index.ts:813-826`，备份里的 `keys/device.json`）；控制面登记时证书未变即不记录、不改目录（`server.ts:969-973`、`:988-993`），控制面无从知道这台设备已换了电脑；激活页恢复完成只显示“已恢复……正在打开”（`Activate.tsx` `RestoreFromBackup.onDone`），没有设计 §3.5 所说的“建议吊销旧设备”；内核只记 `slog` 事件 `KERNEL_RESTORED_FROM_BACKUP`（`index.ts:840`），恢复出的账本里没有任何“本设备于何时从哪份备份恢复”的审计记录。
- 推演：律师电脑被偷后在新电脑上恢复——被偷的那台与新电脑持有同一把设备私钥、同一张证书。管理员若吊销被偷电脑（设备编号相同），新电脑一并被吊销（退出模式，`governance.ts:320`）；不吊销，则被偷电脑（若窃贼破解了 Windows 账户口令，DPAPI 只与口令同强；未开 BitLocker 时可离线攻击）仍是律所在册设备：可继续经控制面同步，经中继收到此后包裹给“本设备”的团队事项新纪元密钥。驻留面第 28 类只写了“旧电脑若被偷，其数据仍受该 Windows 账户 DPAPI 保护”，没有写“无法单独吊销旧电脑、新内容仍会送达旧电脑”这一后果。旧电脑仍能工作的情形（换机未停用旧机），两台同身份设备并发运行，中继段序号、本机审计链与成员日志会分叉（推断，未闭环核实中继侧的处理）。
- 建议修法：
  1. 首期至少：恢复完成后的首次正常启动在显眼处提示“如果原电脑丢失或被偷，请立即联系管理员——当前版本无法单独停用原电脑，管理员会为你重新办理入组”，第 28 类与 D-42 补写上述后果；在恢复出的账本里写一条审计（恢复时刻、备份序号、恢复包 `set_id`），控制面登记时附带“已从备份恢复”标记供管理员页显示。
  2. 根本解决：恢复时生成新的设备密钥对，按同一设备编号换发证书（创始设备包内有律所根可自签；成员设备须管理员批准）——控制面登记会以新证书替换旧证书（`server.ts:969-973`），旧私钥签的请求随即失效。注意：控制面目前接受**任何**由律所根签发、未过期的同编号证书并以后到者为准（无“签发时刻不早于在册证书”的单调检查），换证之后须同时补这条检查，否则旧电脑可重新登记旧证书把身份夺回（既有问题，第 14 批之前已存在）。
- 建议补的测试：恢复后首次启动账本里有“从备份恢复”审计记录；控制面拒绝签发时刻早于在册证书的同编号证书。

### R2A-15【重要】恢复中途失败或主进程没能采用主密钥时没有回滚：应用每次启动都失败，再次恢复也被拒

- 证据：
  - `onboarding.restore` 的顺序是：复制备份（`backup.ts:169-175`，逐个 `copyFileSync`，中途失败不清理）→ 写 `activation.json`（`index.ts:839`）→ 300 ms 后广播采用（`:842-845`）。
  - 主进程采用失败（`safeStorage` 不可用、格式不符、写入失败）只记 `MAIN_ADOPT_KEY_REJECTED`，既不通知界面也不撤销 `activation.json`（`main.cjs:321-333`）；界面等 120 秒后让律师“关闭并重新打开应用”（`Activate.tsx` `waitForActivated`）。
  - 重新打开后：`activation.json` 已在 → 激活模式 → 用本机原主密钥打开恢复出的账本 → `file is not a database` → 内核致命错误退出（`electron-entry.ts:140-146`、`:166-169`），主进程 2 分钟内重启 5 次后停在“后台服务多次异常退出”（`main.cjs:374-380`）。错误文案还是开发形态的“G0 开发库可删除重建”。
  - 想再恢复一次：数据根里已有该律所工作区 → “这台电脑上已经有这个律所的数据，不能覆盖恢复”（`backup.ts:168`）；复制中途失败（备份盘拔出、空间不足）同样卡在这里。
  - 待激活内核在 300 ms 窗口内崩溃同理（`activation.json` 已写、采用消息未发）。
- 推演：律师在最需要恢复的时刻遇到一次 U 盘松动或 DPAPI 异常，就进入“应用打不开、也不能重新恢复”的状态，只能由 IT 手工删除 `activation.json` 与工作区目录——而手工删错目录（例如删了 `ledger-key.prev-*`）即造成永久丢失。
- 建议修法：恢复写入一个暂存目录（`<数据根>/.restore-<随机>/`），复制并逐个核对摘要后整体改名为 `<数据根>/<律所>`；`activation.json` 改由主进程在采用成功之后通知内核再写（或写成 `activation.pending.json`，主进程采用成功后改名），采用失败时内核删除暂存与恢复出的工作区并回到待激活、在激活页显示原因代码；内核启动时发现“有恢复暂存、无 `activation.json`”即清理。错误文案改为律师可懂的“恢复没有完成，请重新恢复一次”。
- 建议补的测试：模拟复制中途失败 → 数据根无残留，可再次恢复；模拟采用失败 → 回到待激活且 `activation.json` 不存在。

### R2A-16【一般】恢复与备份不受律所治理：退出模式与吊销后照常备份、照常生成恢复包；管理员看不到成员把备份放在哪里

- 证据：备份定时器与 `backup.run`、`recovery.create_package` 都不检查 `governance.exitMode()`（`index.ts:885-942`；对照同文件其他定时器 `:305`、`:752` 都检查）；退出模式下“阅读、本机检索、导出、验签照常”（`governance.ts:313-325`）；`firm-trust` 与控制面治理代码里没有任何与备份相关的策略项（`grep -rl backup packages/firm-trust/src packages/kernel/src/control-plane` 为空）。
- 推演：被吊销或离所的成员，其设备仍每天把律所事项的密文与账本快照写到他自己选的位置，并可随时再生成恢复包；他在另一台电脑上离线恢复即得到吊销时刻的全部本机数据。“已解密到本机的内容无法远程收回”是既定口径（D-40），但备份把它从“这台电脑”扩大成“任意多份可离线恢复的副本”，律所既不能限定备份位置（例如只许律所 NAS），也看不到有没有、放在哪。
- 建议修法：退出模式（至少 `device_revoked`）下停止定时备份与 `create_package`；律所策略加“备份位置要求”（允许的位置类别：本机外接盘 / 律所共享盘 / 同步盘）与“恢复包生成需管理员知情”（审计上送控制面只含计数与时刻，不含位置）；第 28 类写明“吊销与移出不影响已生成的恢复包与备份”。
- 建议补的测试：`device_revoked` 退出模式下 `backup.run`、`recovery.create_package` 返回 409。

### R2A-17【建议】恢复内容的几处一致性核对

- 恢复包里的 `activation`（`c.activation`）原样写成 `activation.json`（`index.ts:828-839`），不核对它与包内 `firm_slug / tid / member_slug`、证书角色是否一致；不一致时下次启动 `readActivationFile` 判为无效（`config.ts:90-99`）→ 回到待激活、恢复出的工作区成为孤儿。建议写入前逐项核对，角色以证书为准（与 A-08 处置同口径）。
- 恢复出的工作区带着旧电脑的 `backup.json`（`dir` 是旧电脑上的路径），其 `last_ok_at` 早于 24 小时，新电脑启动后一小时内定时器就会自动向这个路径备份（`index.ts:930-934`）——同一盘符在新电脑上可能是另一块盘或网络映射。即使没有 R2A-08 的篡改，也应在恢复后清空 `dir`、请律师重新选择备份位置。
- 证书按“签发后 1 秒”的时刻核验（`index.ts:815`），即不检查是否已过期；过期证书的设备恢复后登记控制面会失败（`server.ts:957-958`），界面不提示。建议恢复时按当前时刻核验，过期则明确提示“请管理员重新办理入组”。
- 自制的恢复包与自签的备份（任何人都能造：恢复包只是自选恢复码下的 AEAD）可以让一台未激活的电脑在本机进入“已激活”状态，绕过开通码/邀请码门禁；随后因控制面没有对应的根与许可而处于退出模式（`governance.ts:322`，推断），本机阅读与导出等功能仍可用。影响有限，但与“待激活不可用”的口径不一致。建议恢复后的首次启动必须先在控制面完成登记（证书由该租户已登记的根签发）才离开“恢复待核对”状态，或在待激活内核里经闸门向控制面核对包内律所根指纹。
