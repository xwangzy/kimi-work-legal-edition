## 一、恢复与备份的端到端流程（Electron）

**链路核对（成立的部分）**：渲染进程 `recovery.*`（`src/api.ts`）→ preload `pickFolder / pickFiles / pickSave`（`electron/preload.cjs:32`）→ 主进程对话框只发一次性句柄（`electron/main.cjs:508-520` 选文件夹、`:489-505` 选文件、`:521-533` 选保存位置）→ `resolveFileParams` 先剥掉渲染进程带来的一切路径键、再按方法把句柄换成内核参数（`electron/file-dialogs.cjs:128-157`：`onboarding.restore` 的 `file_handle→file`、`folder_handle→dir`；`backup.configure` 的 `folder_handle→dir`；`recovery.create_package` 的 `save_handle→path`）→ 内核。待激活模式下只有 `onboarding.restore` 进白名单（`services/onboarding.ts:581`），`backup.* / recovery.create_package` 被拒（`onboarding.test.ts` 篡改用例逐个断言 `not_activated`）；备份定时器只在已激活时挂（`index.ts:869`）。主进程只在最近一次 `kernel.ready` 报告 `onboarding:true` 时接受 `kernel.adopt_master_key`（`main.cjs:308`、`:318-334`），处理后 `return`，不进转发白名单，主密钥不到渲染进程；开发桥只把它写进本进程环境变量（`dev/bridge.ts:20`），不转发浏览器。`backup-restore.test.ts` 的正路径（备份 → 恢复包 → 新数据根 + 新主密钥 → 恢复 → 采用旧主密钥重启 → 事项与材料原文可读）跑通。

以下是不成立或有缺口的部分。

### R2B-01 采用旧主密钥失败时律师看不到任何提示，且本机落入“已写激活记录、账本打不开”的死状态　【重要】

- 证据
  - `packages/kernel/src/index.ts:839`：`onboarding.restore` 先 `writeActivationFile`，`:842-845` 才在 300 毫秒后广播 `kernel.adopt_master_key`——激活记录在主密钥确认采用**之前**就落盘。
  - `apps/desktop/electron/main.cjs:325-333`：`adoptDbKey(...).then(r => { if (!r.ok) { slog...; return; } ... })`——失败只记一条不带原因的事件，不广播、不重启、不回滚；`.then` 没有 `.catch`，`adoptDbKey` 里 `renameSync`/`encryptStringAsync` 抛错时是未处理的拒绝，连事件都不记。
  - `apps/desktop/src/pages/Activate.tsx:36-55`：`waitForActivated` 只看到内核仍是待激活、没有 `last_failure`，2 分钟后给出“请关闭并重新打开应用”。
  - 重新打开：`packages/kernel/src/config.ts:311` 有 `activation.json` 即不进待激活 → `index.ts:91` 用本机主密钥打开恢复来的账本（旧电脑主密钥加密）→ `electron-entry.ts:139-146` 报“无法用提供的密钥打开账本数据库” → `main.cjs:367-387` 连续 5 次重启后停止；启动占位页只显示“后台服务没有启动起来”（`App.tsx` boot 占位）。此时既不在待激活模式（“从备份恢复”入口不可达），工作区也已非空（`services/backup.ts:168` 拒绝覆盖恢复）——律师与 IT 都没有界面出路，只能手工删 `activation.json` 与 `<数据根>/<律所>/`。
- 说明：Windows 上 DPAPI 一般可用、主密钥格式与 `loadOrCreateDbKey` 生成的一致（44 字符 base64，`secret-store.cjs:59` 与 `:104` 的正则相符），所以这条是低概率；但一旦发生就是不可自救的，而且界面给的唯一建议（重开应用）正好把人送进死状态。
- 建议修法：两段提交——内核恢复时只写 `restore-staged.json`（不写 `activation.json`），主进程采用成功后回一条 `kernel.adopt_master_key_done`（或直接按身份重启），新内核启动时先用新主密钥试开恢复的账本，开得了才把暂存改名为 `activation.json`；采用失败时主进程广播 `{type:"kernel.status", status:"restore_failed", reason}`，内核删除恢复出的工作区并回到待激活，激活页显示“恢复没有完成：本机的数据保护服务不可用……请联系所内 IT”。`.then` 补 `.catch`，`MAIN_ADOPT_KEY_REJECTED` 带原因枚举（not_onboarding / key_invalid / unavailable / write_failed）。
- 建议补的测试：`secret-store` 单测——`safeStorage` 不可用、`renameSync` 抛错时 `adoptDbKey` 返回失败码而不抛；kernel 用例——恢复后**不**采用旧主密钥、用新主密钥重启：断言回到待激活、`onboarding.status` 报 `restore_failed`、工作区已清理、可再次恢复。

### R2B-02 恢复复制到一半失败（磁盘满、U 盘拔出、关闭应用）留下半份工作区，之后再恢复一律被拒　【重要】

- 证据：`packages/kernel/src/services/backup.ts:163-167` 先全部核对摘要（正确），`:168` 目标非空即 409“这台电脑上已经有这个律所的数据，不能覆盖恢复”，`:169-175` 直接往最终目录 `<数据根>/<律所>/` 逐个 `copyFileSync`，账本最后复制；中途任何异常都不清理。`index.ts:809-846` 没有 try/finally。`onboarding.restore` 是同步执行（见 R2B-04），大备份要几分钟到几十分钟，律师在“正在核对与恢复…”时关窗口是可预见的。
- 说明：失败后 `activation.json` 还没写，内核仍在待激活，律师会再点一次“恢复”——得到“已经有这个律所的数据”，激活页的“旧数据”提示也不会出现（`legacyWorkspaces` 只认有 `ledger.db` 的目录，`services/onboarding.ts:200-210`，而账本是最后复制的）。没有界面出路。
- 建议修法：复制到同卷的暂存目录 `<数据根>/.restore-<律所>-<随机>/`，全部复制并 fsync 后再 `rename` 成 `<数据根>/<律所>/`；失败时删暂存；启动时清理残留的 `.restore-*`。目标已存在但带“恢复未完成”标记时允许覆盖。
- 建议补的测试：注入第 N 个文件复制失败 → 数据根下没有 `<律所>/`；再次 `onboarding.restore` 成功。

### R2B-03 备份不是原子的，也只有一代：中断后整套备份“恢复不了”而界面仍报上次成功；源数据损坏次日即覆盖唯一的备份　【重要】

- 证据（`packages/kernel/src/services/backup.ts`）
  - 写入顺序：`:110-111` 先把新账本改名覆盖 `ledger.db` → `:125-129` 逐个覆盖变化的文件 → `:136` 删除本机已没有的文件 → `:139-142` 最后才改名 `manifest.json`、再改名 `manifest.sig`（两次独立改名）。恢复时 `:162-166` 要求清单签名、账本摘要、每个文件摘要全部吻合。
  - 所以：从第 1 步之后到第 4 步完成之前的任何中断（退出时被强杀，见 R2B-04；拔 U 盘；网络盘断开；同步盘锁文件，见 R2B-12），都留下“旧清单 + 新账本/部分新文件/已删的文件”，整套备份核对不通过；`manifest.json` 与 `manifest.sig` 之间中断则新清单配旧签名。`:146-149` 失败只改 `last_error`，`last_ok_at` 仍是上次——设置页显示“最近一次 X”（`RecoveryBackup.tsx:76`），律师以为上次那份还能用。
  - 只有一代：每次都在同一目录原地覆盖。账本损坏、事项被误删、勒索软件加密工作区之后，24 小时内的下一次备份就把唯一的好副本覆盖掉。
- 说明：本条回答“备份进行中退出会不会留下半份备份或坏清单”——会。中断留下的 `*.tmp` 文件下次备份会被第 3 步清掉（`.tmp` 不在跳过表里，`:21`），但“坏清单”要等下一次完整成功才恢复。
- 建议修法：按代保存——块与密钥文件按内容寻址放 `objects/<sha256>` 永不覆盖；账本写 `ledger-<seq>.db`；清单与签名合成一个文件 `manifest-<seq>.json`（签名放在文件内）最后一步改名落地；保留最近 7 代（或 7 天 + 4 周），之后再回收不被任何清单引用的对象。恢复时取最新一份完整核对通过的清单，不通过就退回上一代，并告诉律师恢复的是哪一天。
- 建议补的测试：在 `runBackup` 第 1 步之后注入异常 → 从备份恢复仍成功（取上一代）；连续两次备份之间篡改/删除源文件 → 仍能恢复到上一代。

### R2B-04 备份与恢复在内核主线程同步执行，且每次全量回读备份介质：界面与进行中的任务会卡住数分钟到数十分钟；退出、安装更新时在此期间被强杀　【重要（数据量大时实测可升为阻断）】

- 证据
  - `services/backup.ts:101-151` 全部是同步 fs；`:43` `sha256File` 用 `readFileSync` 整个读进内存；`:131` **每个文件每次都**从备份位置读回来算摘要（未变化的也算）——每日备份的读量 = 整个备份集。恢复 `:163-175` 同样同步、先读一遍算摘要再读一遍复制。
  - 调用方：内核主进程里的定时器（`index.ts:930-938`）、设置页“设置备份位置 / 立即备份”（`RecoveryBackup.tsx:61`、`:94`）。内核是单线程，承担全部界面 IPC 与 Agent 宿主的工具调用（kernel 本地服务）。
  - 主进程 `kwl:invoke` 对内核调用不设超时（`main.cjs:478-486` 只等内核出现，转发后无限等）：备份期间界面所有调用挂起。
  - 退出：`kernel.shutdown` 要等同步备份结束才轮得到处理，`stopKernel` 8 秒后强杀（`main.cjs:920-944`）→ 中断即触发 R2B-03。安装更新：`kwl:update-install` 先 `kernelCall("runs.list_recent", …, 10 秒)`（`main.cjs:604-605`），内核在备份中超时返回 `null`，**“有进行中的任务不安装”的检查被绕过**，随后 8 秒强杀——强杀内核会留下占用安装目录的随包子进程（B4-R11 的老问题），安装失败。
- 推断/待在 Windows 上实测：USB 2.0 U 盘约 20–30 MB/s，20 GB 的工作区首份备份约 11–17 分钟复制 + 同样时长回读；此后**每天**即使没有新文件也要回读约 11–17 分钟。网络盘（SMB）不可达时，同步的 `mkdirSync`/`statSync` 每小时一次阻塞到 SMB 超时（数十秒）。备份位置在 OneDrive 且开了“按需文件/存储感知”时，已被释放空间的副本每天回读都会触发全量下载。
- 建议修法：备份放 `worker_threads`（或独立子进程，只给它工作区与目标两个路径和签名回调）；复制时流式边读边算源文件摘要，本机另存“相对路径 → 大小、修改时间、摘要”的索引，未变化的文件不再回读目标；块文件是内容寻址、只增不改，存在且大小一致即可跳过；进度经广播给界面；`kernel.shutdown` 时取消进行中的备份（配合 R2B-03 的按代写入，取消不会破坏上一代）；`kwl:update-install` 拿不到任务列表时按“忙”处理，而不是放行。
- 建议补的测试：大文件集备份期间 `kernel.status` 响应 < 200 ms（worker 形态）；备份进行中发 `kernel.shutdown` → 2 秒内退出且上一代可恢复；`update-install` 在 `kernelCall` 超时时返回 `busy`。

### R2B-05 自动备份可能实际从不运行，失败或过期也没有全局提醒；“还没有恢复包”横幅不看备份　【重要】

- 证据
  - `index.ts:930-938`：`setInterval(…, 3600_000)`——第一次检查在内核启动 **1 小时后**；设计 §3.3 的“应用退出时补一次”没有实现（全仓 `shutdownHooks` 只清定时器，`:940-942`）。每次打开不足 1 小时就关的律师，除了首次“设置备份位置”时那一次，永远不会自动备份。
  - 设计 §3.3“超过 3 天在侧栏底部提示”没有实现：只有设置页一行“（已 N 天没有成功备份）”（`RecoveryBackup.tsx:76`），侧栏、首页都不提示；`last_error` 也只在设置页显示。
  - `App.tsx:108-115`、`:180-187`：横幅文案是“完成开通的最后一步：生成恢复包并设置备份”，判定却只看 `packages_created === 0`——生成恢复包后横幅即消失，哪怕从没设置备份位置（只有恢复包没有备份，电脑坏了数据照样找不回）。
- 建议修法：启动后 5–15 分钟随机一次检查（与内容更新同一做法），之后每小时；退出时若距上次成功 > 20 小时，在有序关闭前补一次（有时限、可取消，见 R2B-04）；`backup.status` 增加 `stale_days`，侧栏底部在 `!configured`、`stale_days ≥ 3` 或 `last_error` 时常驻提示；横幅判定改为 `packages_created === 0 || !configured`，文案按缺哪一样分别写。
- 建议补的测试：内核用例——启动后（定时器缩短）自动跑一次；`close()` 时距上次成功 > 20 小时则补一次；界面纯函数——三种缺失状态对应的提醒文案。

### R2B-06 恢复后沿用旧电脑的备份位置；之后每次备份都 `mkdir -p`，不核对“还是不是那块盘”　【一般】

- 证据：备份状态文件在工作区里（`index.ts:878` `stateFile: join(config.workspaceDir, "backup.json")`），而跳过表（`services/backup.ts:21`）不含 `backup.json`——它随备份走、随恢复回来，新电脑一启动就按旧电脑的 `dir`（如 `E:\`）继续自动备份。`runBackup` 每次 `mkdirSync(target, { recursive: true })`（`:106`），只要那个盘符此刻挂着**任何**介质（另一只 U 盘、读卡器、手机）就在上面新建 `KimiWorkLegal-backup\…` 写入；`configureBackup` 的存在性检查只在设置那一刻做（`:93`）。另外恢复来的 `backup.json` 是旧电脑**上一次**备份前的状态（状态在清单之后才更新，`:143-144`），`seq` 会重复。
- 说明：U 盘拔掉后盘符被别的设备占用，在 Windows 上很常见；结果是备份写到了律师不知道的盘上，设置页仍显示“最近一次成功”。
- 建议修法：`backup.json` 移出工作区（或列入跳过表），恢复后把备份状态置为“未设置”，激活后提示“请重新选一次备份位置”；设置位置时在 `<位置>/KimiWorkLegal-backup/` 写一个带随机编号的标记文件、编号存进状态，每次备份先核对标记，不符即报“备份盘不是原来那块”；`st.dir` 本身不存在时报错而不是逐级创建。
- 建议补的测试：恢复后 `backup.status.configured === false`；标记不符 → `backup.run` 409 且不写入。

### R2B-07 从备份恢复：一次性句柄在第一次失败后已被消费、10 分钟过期，再点“恢复”报“所选文件已失效”，按钮却仍显示已选　【一般】

- 证据：`electron/file-dialogs.cjs:73-80` `take` 取出即作废、`:13` 10 分钟有效；`:139-155` 转发前就把 `file_handle` 与 `folder_handle` 都取走。`pages/Activate.tsx:183-199`：失败时只 `setErr`，不清 `pkg/folder`，按钮仍是“恢复包：xxx / 备份位置：xxx”（`:207-212`）。最常见的失败恰恰是恢复码抄错一行（内核报“第 N 行可能抄错了”），律师改好再点，得到“所选文件已失效，请重新选择”——与刚才的错误毫无关系。先选文件、再对着纸慢慢抄 70 个字符，超过 10 分钟也会失效。
- 说明：设置页的“试解”“生成”“设置位置”每次都重新弹对话框（`RecoveryBackup.tsx:39-64`），没有这个问题；只有激活页的恢复是“先选、后用”。
- 建议修法：激活页在调用失败后清空 `pkg/folder` 并在错误下补一句“请重新选择恢复包和备份位置”；或把“选文件/选文件夹”放到点“恢复”之后再弹（与设置页同一做法）；句柄过期时间对恢复流程放宽到 30 分钟。
- 建议补的测试：`resolveFileParams` 单测已覆盖“取出即作废”；界面加纯函数——调用失败后表单状态复位。

### R2B-08 残留的入组失败记录会让一次成功的恢复立刻显示“入组没有完成”　【一般】

- 证据：`onboarding-failed.json` 只在重新兑换（`services/onboarding.ts:225` `redeem`）或“重新输入”时删除；`onboarding.restore`（`index.ts:809-846`）不删，也不置 `restarting`。`Activate.tsx:46-48`：`waitForActivated` 第一轮（1 秒后，内核重启前）读到 `last_failure && !restarting` 就 `onStuck(JOIN_FAILED_TEXT)`，把页面切回输入码页并显示“入组没有完成……请向管理员重新要一个邀请码”。随后内核其实已按恢复的身份重启，但页面不会再自己刷新。
- 场景：成员在新电脑上入组失败（K02 路径）后，IT 让他改用“从备份恢复”。
- 建议修法：`onboarding.restore` 成功时删除 `onboarding-failed.json` 并像 `restartSoon` 一样置 `restarting=true`；`waitForActivated` 的失败判断只认“本次操作之后写的”失败（比较 `last_failure.at` 与发起时刻）。
- 建议补的测试：先写 `onboarding-failed.json` 再恢复 → `onboarding.status.last_failure` 为空、`restarting` 为真。

### R2B-09 恢复与备份的运行记录不足以排障　【建议】

- `MAIN_ADOPT_KEY_REJECTED`、`KERNEL_BACKUP_FAILED` 都没有字段（`packages/safe-log/src/events.ts`），分不清“不是待激活”“主密钥格式不对”“DPAPI 不可用”“写不进去”，也分不清备份是空间不足还是被占用；而 `backup.json` 里其实存了错误码。建议两条事件都带登记过的原因/错误码字段（沿用 `ERR` 片段），IT 拿诊断包就能判断。

## 二、Windows 特有问题（只读推演）

**核对通过/风险低的部分**

- 跨卷改名：备份里的每次 `renameSync` 都在同一目录内（`ledger.db.tmp→ledger.db`、`<文件>.tmp→<文件>`、`manifest.*.tmp→manifest.*`、`backup.json.tmp-<pid>→backup.json`，`services/backup.ts:87-89`、`:109-111`、`:127-128`、`:139-142`），恢复只用 `copyFileSync`（`:170-175`），`adoptDbKey` 的改名也在 `userData` 同一目录（`electron/secret-store.cjs:114-115`）。不存在 `EXDEV`（跨盘改名）问题。
- 中文路径：全部经 Node fs（Windows 上走 UTF-16 宽字符 API），清单里存 POSIX 分隔的相对路径、落地时 `join` 换成反斜杠（`:44`、`:119`、`:171`）。`insideDataRoot` 比较前统一小写（`index.ts:880-883`），对中文无影响。推断无问题，CI 已有中文临时目录重跑的先例，建议把 `backup-restore.test.ts` 加进那一轮。
- 盘符拔出：备份前拔出 → `mkdirSync` 立即 `ENOENT`，记 `last_error`，设置页提示“请检查备份位置是否插好”；备份中拔出 → 见 R2B-03（整套备份失效）。libuv 在 Windows 上启动时设置了 `SEM_FAILCRITICALERRORS`，空读卡器不会弹“驱动器中没有磁盘”对话框（推断）。
- DPAPI 换账户：新 Windows 账户 = 新的 `%LOCALAPPDATA%` 与 `userData` → 内核进待激活 → “从备份恢复”可走；`adoptDbKey` 用**当前**账户的 `safeStorage` 重新包裹恢复包里的原始主密钥（`secret-store.cjs:103-116`），不依赖旧账户的 DPAPI。这个设计成立。

### R2B-10 同一账户上 DPAPI 解封失败（管理员重置了本地账户密码、系统重装后还原了用户目录等）时，“从备份恢复”根本进不去；报错框还在指向已不存在的“设备恢复包”　【重要】

- 证据：`electron/main.cjs:238-259`：`loadDbKey` 失败即弹框并 `app.quit()`，内核不启动；`:252-255` 文案“请联系所内 IT 或客服，使用“设备恢复包”或律所恢复流程找回数据”——“设备恢复包”是旧的 `recovery.export_device`（界面已无入口），新流程叫“恢复包 / 从备份恢复”。而“从备份恢复”只在待激活模式的激活页上（`Activate.tsx:161-165`），待激活要求数据根下没有 `activation.json`（`config.ts:311`）。
- 说明：设计 §1 第 1 条写的正是“DPAPI 绑定旧 Windows 账户”导致打不开账本；本批只解决了“换新电脑/新账户”，没解决“同一账户 DPAPI 坏了”这一半——而这恰恰是律所 IT 最常遇到的情形（重置本地账户密码会让 DPAPI 主密钥不可恢复）。现在律师手里有恢复包、恢复码和完好的备份，仍然必须由 IT 手工删除 `ledger-key`、`activation.json` 与 `<数据根>/<律所>/` 才能恢复，而界面没有一句话告诉他们可以这样做。另：Electron `safeStorage` 在 Windows 上用的是存在 `userData\Local State` 里、由 DPAPI 保护的一把密钥（推断，Electron 实现细节），`.electron` 目录被清理也会落到同一处境。
- 建议修法（需拍板）：解封失败的对话框给两个按钮——“退出”与“用恢复包恢复”；后者把 `activation.json`、`<数据根>/<律所>/` 与旧 `ledger-key` 改名到 `<数据根>/.unreadable-<时刻>/`（不删除）、生成新主密钥、以待激活模式启动并直接打开“从备份恢复”。文案把“设备恢复包”改成“恢复包（设置 → 本机与安全 → 恢复与备份里生成的那份）”。
- 建议补的测试：`secret-store` 单测已有解封失败；加主进程编排的纯函数——“移到一边”只改名不删除、之后 `config` 进入待激活。

### R2B-11 增量判断依赖备份介质上的修改时间：exFAT/FAT32 U 盘上可能每次都全量复制；同步盘释放空间后每天回读即全量下载　【一般（推断，待在 Windows 上实测）】

- 证据：`services/backup.ts:121-124` 以“目标大小相同且目标修改时间 ≥ 源修改时间”判“没变”。
- 推断：Windows 的 `CopyFileW`（Node `copyFileSync` 的实现）会把源文件的最后写入时间带到目标；NTFS 精度 100 ns，exFAT 10 ms、FAT32 2 秒——大容量 U 盘出厂多为 exFAT、小容量多为 FAT32。目标时间被截断后普遍略小于源时间，判定恒为“变了”，每天全量复制整个工作区（叠加 R2B-04 的同步阻塞）。FAT32 另有单文件 4 GB 上限（账本或法规库更新包超过即失败）。OneDrive/坚果云等“按需文件”把旧副本释放成占位后，`:131` 每天回读算摘要会触发全量下载；离线时读失败即整次备份失败。
- 建议修法：比较对象改为“源文件自己上次备份时的（大小, 修改时间, 摘要）”——存在本机索引里，不读目标；块文件按内容寻址，存在且大小一致即跳过；不再每天回读目标算摘要（摘要在复制时由源数据流算出）。
- 建议补的测试：用 `utimesSync` 把目标时间改成比源早 5 毫秒 → 第二次备份 `copied` 仍为 0。

### R2B-12 Agent 宿主与内核并发写工作区：临时文件只在顶层被排除，备份会因“列出后消失”整次失败；同步盘、杀毒软件锁文件时改名失败无重试　【一般】

- 证据
  - 跳过表 `/^\.kwl-tmp/`（`services/backup.ts:21`）带 `^`，只匹配工作区**顶层**；Agent 宿主的临时文件在 `<工作区>/kap/<事项>/…` 下，命名为 `<文件>.kwl-tmp-<随机>` 或 `.kwl-tmp-<随机>`（`packages/kap-host/src/sealed-storage.ts:88`、`:453`），都不被排除。
  - 内核注释“单连接同步驱动，复制期间不会有写入”（`services/backup.ts:6`、`:107`）只对账本成立：Agent 宿主是另一个进程（`index.ts:372-374`，数据根 `<工作区>/kap`），备份期间照常写会话、事件日志、草稿与材料快照。`walk`（`:46-56`）列出之后、`statSync`（`:120`）之前，临时文件被改名或删除 → `ENOENT` → `:146-149` 整次备份失败；备份到一半的追加日志副本可能停在半条记录（宿主读取时是否容忍，待核）。
  - Windows：`renameSync` 覆盖已有文件用 `MoveFileExW(…REPLACE_EXISTING)`，目标正被同步盘客户端上传、杀毒软件或 Windows 搜索索引打开时报 `EPERM/EACCES/EBUSY`（推断，待实测）；`runBackup` 第一个错误即放弃整次（叠加 R2B-03 的半份状态）。
- 建议修法：跳过表改为匹配任意层级（`/(^|\/)\.kwl-tmp-|\.kwl-tmp-[0-9a-f]+$/`、内核块的 `/\.\d+\.(reseal\.)?tmp$/`）；`walk` 与复制之间文件消失视为“跳过本文件”而不是失败；改名遇 `EPERM/EBUSY/EACCES` 退避重试 3 次；备份目标也设“不进 Windows 搜索内容索引”（与工作区同一做法，`index.ts:366`）；有运行中的 Agent 任务时，宿主管理的目录可推迟到空闲时再备份（或请宿主在备份期间暂停落盘）。
- 建议补的测试：备份过程中在 `kap/<事项>/work/` 下创建并删除 `.kwl-tmp-*` 文件 → 备份成功、清单里没有它。

### R2B-13 长路径：备份里的路径比工作区里长约 40 个字符　【建议（推断）】

- 备份路径 = `<位置>\KimiWorkLegal-backup\<律所>\dev_<律所>_<成员>\files\<相对路径>`（`services/backup.ts:58-60`、`:119`），比源路径 `%LOCALAPPDATA%\KimiWorkLegal\<律所>\<相对路径>` 多出律所标识（两遍）与成员标识；`kap/<事项>/work/` 下是 Agent 起的中文文件名，深度不受控。Node 在 Windows 上对绝对路径自动加 `\\?\`，本应用自己读写不受 260 字符限制；但律所 IT 用资源管理器把 `KimiWorkLegal-backup` 整个拷到新硬盘、或同步盘客户端/NAS 处理超长路径时可能静默漏文件，到恢复时才报“备份里的文件被改动过或不完整”。建议目标目录用短编号（如设备编号的 8 位摘要），清单里登记最长路径，超过 240 字符时在设置页提示。

### R2B-14 账本快照：检查点结果没有核对，实现也与设计的“在线备份 API”不一致　【建议】

- 证据：`packages/kernel/src/db.ts:103-105` `checkpointTruncate()` 丢弃 `wal_checkpoint(TRUNCATE)` 的返回值（`busy / log / checkpointed`）；`services/backup.ts:108-111` 接着直接复制主库文件。设计 §3.3 写的是“SQLite 在线备份 API 生成快照”。
- 说明：内核是单连接同步驱动，复制期间本连接不会写，正常情况下检查点会完整完成，快照一致——这一点成立。但若将来引入第二个连接（只读连接、所内节点、迁移工具），检查点返回 `busy=1` 时 WAL 里还有未合并的页，复制出的主库就是旧的，而现在没有任何断言能发现。Windows 上读取一个本进程以写方式打开着的 SQLite 文件，`CopyFileW` 的共享模式是否总能成功，待实测（尤其账本 > 1 GiB 时锁字节页所在的区段）。
- 建议修法：核对 `busy === 0 && log === checkpointed`，否则报错不复制；或改用 `VACUUM INTO`/`db.backup()`（需确认 SQLite3MultipleCiphers 下目标沿用同一密钥），与设计一致，也避免直接复制正在使用的文件。
- 建议补的测试：用第二个只读连接持有读事务时调用备份 → 报错而不是产出旧快照。

### R2B-15 采用旧主密钥会让本机已有的“旧工作区”失去当前主密钥　【一般】

- 证据：`main.cjs:316-317` 注释称待激活时“本机还没有任何案件数据”；但第 13 批 K06 的处置正是待激活时报告本机已有账本的旧工作区（`services/onboarding.ts:200-210`，例如以前 `demo-firm` 试用的数据，用的是本机当前主密钥）。恢复时 `adoptDbKey` 把当前 `ledger-key` 改名为 `ledger-key.prev-<时刻>`、换成旧电脑的主密钥（`secret-store.cjs:114-115`），此后应用再也打不开那些旧工作区；能救回它们的只有手工处理那份 `.prev` 文件。激活页的旧数据提示（`Activate.tsx:166-170`）没说这一点。
- 说明：`.prev` 文件留档、不删除，数据没有丢；问题是没人知道要保留它，也没有工具用它。
- 建议修法：有旧工作区时，恢复前在激活页明确提示“恢复后，本机以前留下的数据（xxx）只有 IT 才能取出；如需保留请先联系所内 IT”，并要求勾选确认；`adoptDbKey` 的留档文件名写进诊断包的“本机状态”（只写有无与时刻）。
- 建议补的测试：有旧工作区时 `onboarding.restore` 不带确认参数 → 409 并说明原因。

## 三、律师可用性（RecoveryBackup、Activate 恢复流程、提醒）

**做得好的部分**：设置页把要做的事压成三件（生成恢复包、试一次、选备份位置），“主密钥、DPAPI、证书”等词没有出现在律师层；“恢复包和恢复码要分开放（例如恢复包放 U 盘，恢复码打印后锁进柜子）”写得具体；打印样式只露出恢复码（`styles.css` 末尾 `@media print`）；“收起”要先勾“我已抄下或打印好”（`RecoveryBackup.tsx:107-112`）；同步盘/网络位置在设置备份后如实说明“对方看不到案件内容，但能看到文件大小与备份时间”（`:127`）；恢复码抄错一行能报出行号（`keys/src/share-codec.ts:269`）；激活页恢复入口“换了新电脑？从备份恢复 →”位置自然（`Activate.tsx:161-165`）。

### R2B-16 “选择备份位置”要选的是备份所在的盘本身；律师按直觉选 `KimiWorkLegal-backup` 或下层文件夹就失败，报错还说“这台电脑”　【重要】

- 证据：恢复按 `<所选文件夹>/KimiWorkLegal-backup/<律所>/<设备编号>/manifest.json` 找清单（`services/backup.ts:58-60`、`:158-159`）。律师打开 U 盘看到的是一个叫 `KimiWorkLegal-backup` 的文件夹，最自然的动作是选它（或一路点进去选到最里层）——两种都得到“这个位置没有这台电脑的备份（找不到备份清单）”。激活页只写“备份所在的位置（例如 U 盘）”（`Activate.tsx:204`），没说“选 U 盘本身，不要点进 KimiWorkLegal-backup”。报错里的“这台电脑”在新电脑上指代错了（应为“原来那台电脑”）；同样的措辞见 `:162`“不是这台电脑的备份”。
- 建议修法：内核在所选目录、其 `KimiWorkLegal-backup` 子目录、以及往上两级里按设备编号找清单，三种选法都接受；找不到时列出“这个位置里有哪些律所/设备的备份（只给显示名与日期）”；文案改为“这个位置没有原来那台电脑的备份。请选备份所在的 U 盘或文件夹本身（里面应有一个 KimiWorkLegal-backup 文件夹）”。
- 建议补的测试：`dir` 分别给 `<位置>`、`<位置>/KimiWorkLegal-backup`、`<位置>/KimiWorkLegal-backup/<律所>/<设备>` → 都能恢复。

### R2B-17 恢复包缺省存到“文档”（与数据同一块硬盘，常被 OneDrive 同步），界面不警示、也不引导复制到 U 盘；生成后不引导当场试解　【重要】

- 证据：保存对话框缺省 `app.getPath("documents")`（`electron/main.cjs:526`）；`kwl:pick-save` 回了风险标记 `risk`（`:532`），但 `RecoveryBackup.tsx:39-46` 完全不看 `target.risk`，也不判断是否在系统盘。设计 §2 写“开通时**强制**完成一次：生成 → 导出 → 当场试解（证明能用）”；实现是：生成后只显示恢复码，“试一下”收在折叠的 `<details>` 里（`:116-125`），状态行只写“已生成 N 次，试过 M 次”，`App.tsx:113` 的提醒只看 `packages_created`。
- 说明：律师最可能的操作是一路点“保存”——恢复包就和账本躺在同一块硬盘上，硬盘坏了一起没；在开了“已知文件夹移动”的 Windows（律所用 Microsoft 365 很常见）上，“文档”就是 OneDrive。恢复包本身用 256 位秘密加密，放 OneDrive 不至于泄密，但违背“与电脑分开保管”的目的。
- 建议修法：保存后若目标在系统盘/用户目录内，提示“恢复包现在存在这台电脑上：电脑坏了它也会一起丢。请把它复制到 U 盘或交给律所负责人保管”并给“我已复制到别处”勾选；同步/网络位置提示“恢复包会同步到网盘（加密，看不到内容）”。生成成功后自动展开“试一下”，状态行改为“最新一份恢复包：已试过 / 还没试过”，提醒按“最新一份是否试过”判定（`backup.status` 增加 `latest_package_verified`，按 `set_id` 对应）。
- 建议补的测试：界面纯函数——保存位置风险 → 提示文案；`backup.status` 在“生成第二份但只试过第一份”时 `latest_package_verified === false`。

### R2B-18 恢复码报错的行号不数 KWR1 那一行，界面却让律师“含第一行 KWR1”去数　【一般】

- 证据：`keys/src/share-codec.ts:250-269`：先 `rows.shift()`（`:255`）去掉前缀行，再按“行号从 1 起，不含前缀行”报错（注释 `:246`）；`backup-restore.test.ts:65-68` 改的是 `lines[2]`（含 KWR1 在内的第 3 行），断言报“第 2 行”。界面两处都写“恢复码（含第一行 KWR1）”（`RecoveryBackup.tsx:119`、`Activate.tsx:227`），显示时也没有行号（`RecoveryBackup.tsx:102` 原样 `<pre>`）。律师按看到的顺序数，会去核对错的那一行。
- 建议修法：显示与打印时每行前加行号（KWR1 行不编号，或标“0”）；报错改为“KWR1 下面的第 2 行可能抄错了”。
- 建议补的测试：`openRecoveryPackage` 报错文案含“KWR1 下面的第 N 行”。

### R2B-19 第一次备份与恢复可能要几十分钟，界面没有进度、没有时长预期、没有“请勿关闭”　【一般】

- 证据：“设置备份位置”点下后同步跑完整的第一次备份（`RecoveryBackup.tsx:56-64`），期间只有按钮变灰、`msg` 被清空；激活页恢复只有按钮文字“正在核对与恢复…”（`Activate.tsx:237`）。两处都不说可能很久，也不说别关应用——而中途关闭正好触发 R2B-02/R2B-03。
- 建议修法：与 R2B-04 的进度广播配套，显示“已复制 n / N 个文件（约 x GB）”；开始前提示“第一次备份要把全部案卷复制一遍，可能需要几十分钟，可以继续工作”（worker 化之后）/“恢复期间请不要关闭应用或拔出 U 盘”。

### R2B-20 失败提示把错误码、文件名和路径原样给律师；I2 门禁扫不到新页面与内核报错　【一般】

- 建议补的测试：S1 运行的材料含一个案号 → 勾选后可签发（或按拍板结论断言）；复核页纯函数在运行级计数 > 0 且未勾时返回“不可签发”。

### R2B-28 O02 的“自定义日期格式”判定把带 `[Red]`、`[DBNum1/2/3]` 的数字格式当成日期：金额被改写成日期　【重要】

- 证据：`packages/docx-engine/src/render-html.ts:247`：
  `if (/[yd]|m(?![^\[]*\])/i.test(formatCode去掉引号段) && !/^\[?h/i.test(formatCode)) customDate.add(id)`
  `[yd]` 不排除方括号内的字母、且大小写不敏感。逐字推演：
  - `#,##0.00_);[Red](#,##0.00)`、`"¥"#,##0.00;[Red]"¥"\-#,##0.00`（Excel“数值/货币，负数红色”的常见自定义格式）——`[Red]` 里的 `d` 命中 → 判为日期；
  - `[DBNum2][$-804]General`（中文大写金额，合同、发票、付款表里很常见）——`DBNum` 的 `D` 命中 → 判为日期。
  之后 `:301-309` 对这些单元格的数值调用 `excelDate`：1 ≤ 数值 ≤ 2,958,465 时一律改写，例如合同金额 `500000` → 公元 3268 年的某一天，`1234.56` → “1903-05-18 13:26”；超过 2,958,465 的保留数字但打上 `xlsx_dates_raw`（界面显示“部分日期显示为数字”）。
- 说明：B13-O02 要解决的是“日期变成序列号”，现在反过来把付款记录、流水、标的额表里的**金额**改成了日期，送进 Agent 的事实材料，且没有任何提示。`import-xlsx.test.ts` 的夹具只用了内置格式 4（`#,##0.00`）作“普通数字”，测不到。另：内置格式 18–21、45–47 是时间而非日期，`[h]:mm:ss` 时长大于 1 天时会被写成“1900-01-01 12:00”；`workbookPr date1904="1"`（Mac 旧工作簿）没有处理，日期整体差 4 年零 1 天。
- 建议修法：判定前先去掉所有方括号段（`\[[^\]]*\]`）、引号段与反斜杠转义字符，再要求同时出现年/月/日占位（`y` 或 `d`，且 `m` 不与 `h`/`s` 相邻），并排除含 `0`/`#`/`?` 数字占位的格式；内置 18–21、45–47 按时间输出 `HH:MM(:SS)`；读 `workbookPr date1904`。
- 建议补的测试：`[Red]` 负数格式、`[DBNum2]` 大写金额、`"¥"#,##0.00` 三种格式的数值原样保留；`yyyy"年"m"月"d"日"`、`m/d/yy`、`[$-F800]dddd, mmmm dd, yyyy` 转日期；`h:mm`、`[h]:mm:ss` 转时间；`date1904` 工作簿日期正确。

### R2B-29 C02 的漂移作业只在推送到 main 或手动触发时运行　【一般】

### R2B-30 ZIP 读取改为“解压大小必须等于声明大小”：对所有 DOCX 路径生效，比防炸弹所需更严　【建议】

- 证据：`packages/docx-engine/src/zip.ts:90-103`：deflate 条目输出上限为“声明 + 1”且要求 `out.length === e.size`，stored 条目要求 `compressed.length === e.size`。`readZipEntries` 解压全部条目，被脱敏（`mask.ts:26`）、修订（`revise.ts:28`）、清洗（`sanitize.ts:16`）、属性（`props.ts:5`）、DOCX 预览（`render-html.ts:117`）、导出还原（`kernel/services/export-restore.ts:42`）、外部引用扫描（`kernel/executor/executor.ts:1185`）共用——任何一个条目（包括图片）大小与声明不符，整份 DOCX 422。
- 说明：防炸弹只需要“不超过声明”；“比声明小”是损坏或写入器缺陷，不是炸弹。合规的 ZIP 中央目录大小总是准确的，所以对正常文件无影响；风险在于少数写入器有缺陷的存量 DOCX（以前能读、现在被拒，提示还是“疑似压缩炸弹”）。本轮没有找到存量 DOCX 回归集来实测。
- 建议修法：只在超过声明时拒收；小于声明时接受并给 `zip_size_mismatch` 解析标记（界面话术“文件可能不完整，请核对原件”）；报错文案区分“疑似压缩炸弹”与“文件损坏”。在 CI 里放一组不同来源（Word、WPS、LibreOffice、在线文档导出）的 DOCX/XLSX 夹具做回归。

### R2B-31 成果引用门禁扩到全部格式后的行为变化：PDF、图片、网页成果一律要勾“已人工核对”；表格成果里成百个案号只给一个勾　【一般】

- 证据：`services/artifact-citations.ts:43-59`：`.xlsx` 成果现在经 `xlsxToText` 全文核验，其余格式返回 `format` → `checked:false` → 须勾“这份文件的引用已人工核对”（`:100-104`）。第 13 批之前这些成果直接放行。

### R2B-32 输出上限的环境变量允许到 262,144，超过引擎的压缩预留（50,000）后可能超窗；网关预占随之放大　【建议】

- 证据：`model-broker/src/config.ts:25-28` 接受 1,000–262,144；第 13 批核对过“输入 + 输出上限不会超窗”的前提是输出上限（32,000）小于引擎自动压缩预留 `reservedContextSize: 5e4`（B13-C01）。把 `ZR_MODEL_K3_MAX_TOKENS` 调到 50,000 以上，上下文接近满时请求可能被上游以超窗拒绝；网关按“输入估算 + max_tokens”预占点数，调高后余额较少的律所会更早被拒。
- 建议修法：上限钳到 `reservedContextSize - 安全余量`（如 48,000），或在路由表里同时登记窗口大小、按“窗口 − 输入估算”取较小值；运维文档写明调高的代价。

### R2B-33 迁移 `0045_v93_member_invitations.sql` 改名为 `0050_…`：已经跑过第 13 批集成版本的账本升级后内核起不来　【一般】

## 七、结论与汇总

**总体判定：有条件通过。** 恢复与备份的**正路径**在代码上走得通：渲染进程拿不到路径、只拿一次性句柄；恢复包用 256 位随机秘密 + AES-256-GCM 包裹、恢复码抄错能定位到行；旧电脑的主密钥只在内核处于待激活时才被主进程采用、用本机 DPAPI 重新包裹、原包裹文件留档，且不转发界面；端到端用例从“另一台电脑”恢复后事项与材料原文可读。问题集中在**失败与中断的路径**和**每日自动备份的可靠性**：主密钥采用失败、恢复复制到一半都会落入界面无出路的状态；备份原地覆盖、只有一代、中断即整套不可恢复而界面仍报成功；备份在内核主线程同步执行、每天全量回读，会冻结界面与任务，退出与安装更新时被强杀；首检在启动 1 小时后、退出不补、过期无全局提醒，自动备份可能从不发生。这几条处置前，不建议对外宣称“电脑坏了能找回”。另有一条与恢复无关、但会直接污染事实材料的新缺陷：O02 的日期判定把带红色负数或中文大写格式的金额改写成日期（R2B-28），建议最先修。
