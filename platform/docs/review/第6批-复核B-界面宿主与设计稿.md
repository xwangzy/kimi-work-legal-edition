## 发现

### S6B-01 · 重要 · 执行页丢弃“只有心跳变化”的过程快照，静默看门狗仍会在长时间思考时误报

- **结论**：不成立（声明“长时间思考或执行工具不再误报‘没有新进展’”）。
- **依据**：
  - `apps/desktop/src/lib/progress.ts:79-84`：`progressActivityKey` 有意剔除 `activity.heartbeat_at`（只保留 phase/since/tool）。
  - `apps/desktop/src/pages/RunView.tsx:146`：`setProgress((prev) => (progressActivityKey(prev) === progressActivityKey(next) ? prev : next))`——键相同就**保留旧对象**，新快照里的 `heartbeat_at` 被丢弃。
  - `apps/desktop/src/pages/RunView.tsx:259`：`silentFor = now - Math.max(lastActivity, engineHeartbeatMs(progress))`，读的是 state 里的 `progress`，即旧心跳。
  - `apps/desktop/test/run-progress-view.test.ts:83` 明确断言“只有心跳不同：活动键相同”，所以两段代码各自都“对”，组合后心跳永远进不了看门狗。
- **影响**：主 Agent 连续思考（`thinking.delta` 不改阶段）超过 90 秒时，宿主每 15 秒推一次心跳，但界面状态不更新，`RunView.tsx:506` 照旧显示“已经有一阵子没有新进展了……可以取消后重新运行”。这正是 P0-D 要消除的误报，律师可能因此取消正常运行的任务。
- **建议修法**：比较键保持不变（看门狗的 `lastActivity` 仍按内容），但 `setProgress` 时若只有心跳不同，也要换成新对象或单独存一个 `heartbeatMs` state；例如 `setProgress(prev => key(prev)===key(next) && prev?.activity?.heartbeat_at === next?.activity?.heartbeat_at ? prev : next)`，`lastActivity` 的 effect 仍依赖 `progressKey`。
- **应补测试**：把“轮询合并 + 看门狗计算”抽成纯函数（输入：上一份快照、新快照、上次活动时刻、now；输出：保留的快照、silentFor），断言“只有心跳更新时 silentFor 归零而 lastActivity 不变”；以及“心跳停止 90 秒后 silentFor > 90 000”。

### S6B-02 · 重要 · “结果不明的联网记录”对账入口只剩管理员可见，普通经办律师无处对账

- **结论**：设置拆分造成功能回退。
- **依据**：
  - 对账操作只出现在 `apps/desktop/src/pages/Connections.tsx:458`（`DiagnosticsTab`，位于“管理 → 诊断”，只对 `firm_admin`/`partner` 显示，`Connections.tsx:14,43,49`）。拆分前在所有人可见的“设备”页（`git show HEAD:…/Connections.tsx` 第 86、247 行）。
  - 内核授权并不要求管理员：`egress.reconcile` 只要求事项可写（`packages/kernel/src/api/index.ts` 中 `egress.reconcile`：`requireMatterAccess` + `requireMatterWriter`）。
  - 工作台引导律师“请在对应任务的‘数据去向’里逐条确认”（`apps/desktop/src/pages/Boards.tsx:124`），但 `components/DataFlow.tsx` 只显示“结果不明（待对账）”，没有任何对账操作；事项页也只有一条横幅（`pages/Matter.tsx:367`）。
- **影响**：最清楚“那次到底发没发出去”的经办律师无法登记结论；工作台的指引指向不存在的操作；对账只能由不在场的管理员代为判断。
- **建议修法**：在执行页“数据去向”卡（或事项页“数据去向”）为结果不明的记录加“已发出 / 未发出 / 无法确定”三键（复用 `api.egressReconcile`），并把 `Boards.tsx:124` 的文字指向实际位置；“管理 → 诊断”保留全所视图。
- **应补测试**：桌面静态检查——对账按钮在非管理视图中存在；内核侧已有 `requireMatterWriter` 用例可沿用，补一条“非管理员成员可对账本人事项的记录”。

### S6B-03 · 一般 · 长时间无输出的工具执行，看门狗文案覆盖阶段行

- **结论**：部分成立。修好 S6B-01 后，思考与流式写作不会再误报；但主 Agent 执行一个长时间、无 `shell.output`/`tool.progress` 事件的工具（例如一次长 `python3`，见偏离 D-07“命令内部输出在命令结束时一次给出”）时，宿主收不到任何引擎事件，`heartbeat_at` 不再前进（`packages/kap-host/src/progress.ts:88-114` 只在事件到达时更新）。
- **依据**：`RunView.tsx:506` 中 `silentFor > 90_000` 优先于 `phaseLine(...)`，于是“正在执行：在本机计算 / 整理数据（已 2 分 10 秒）”被替换成“已经有一阵子没有新进展了……可以取消”。
- **影响**：律师在正当的长计算中看到劝取消的提示。真卡死时提示仍会出现（这一半成立）。
- **建议修法**：阶段为 `tool` 时把两句合并：保留阶段行与已用时间，另起一行弱提示（“这一步还没有返回；如果超过 N 分钟仍无变化可以取消”），并把阈值按工具类别放宽（Bash/W 执行域取 5 分钟，与上游前台 5 分钟一致）。
- **应补测试**：`phaseLine` + 看门狗组合函数在 `phase=tool` 且 silentFor>90s 时同时返回阶段行与弱提示。

### S6B-04 · 一般 · “先开始，缺的稍后补”在材料补齐后仍把“材料还不齐”写进任务说明

- **结论**：只限 Agent 场景成立（`components/ScenarioStart.tsx:66`）；估价与发起使用同一 `value`（`:68`、`:73-89`、`:91-108`）成立；但附加文字有缺陷。
- **依据**：`ScenarioStart.tsx:62` 只看 `partial`：律师点了“先开始”之后再勾选材料使 `needDocs` 归零，`canPartial` 变为 false，界面上的“材料还不齐”提示随之消失（`:156-173` 都要求 `canPartial`），但 `goal` 仍附带“（材料还不齐：……缺少的材料列为‘待补充’……）”并发给模型与估价。
- **影响**：律师看不到、模型却被告知材料不齐，交付件里会出现不必要的“待补充”；执行页目标气泡会显示这句，律师会困惑。
- **建议修法**：`goal` 用 `canPartial && partial`；或 `needDocs` 归零时 `setPartial(false)`。文字本身合适（要求“不要推测”、标注待补充），可保留。
- **应补测试**：把 goal 拼接抽为纯函数，断言 `needDocs=0` 时不附加该句。

### S6B-05 · 一般 · “接着做”按方法模板反查场景卡，企业法务与非诉线的下一步被指到诉讼线

- **结论**：部分成立。路由 `#/start/<场景>/<事项>` 成立：`App.tsx:47-48` 解析出 `matterId`，从执行页跳转时 `routeKey` 变化使 `Home` 重新挂载，`useState(presetMatterId)`（`pages/Home.tsx:45`）+ 事项载入后的 effect（`Home.tsx:76-85`）确实在该事项下打开面板一次。
- **依据**：`lib/scenarios.ts` 的 `scenarioOfRun` 对 Agent 任务按 `input_snapshot.skill` 取**第一张**同模板卡；`legal-research-memo` 同时属于 `research-lit`（诉讼）与 `research-deal`（非诉），`contract-review` 同时属于 `contract-review` 与 `contract-review-inhouse`，`demand-letter` 同时属于 `demand-lit` 与 `demand-inhouse`。因此 `NEXT_STEPS` 中 `research-deal`、`contract-review-inhouse` 两个键永远取不到；企业法务审完合同会看到“回稿比对”而不是“合规问答”，非诉研究会看到“起草起诉状 / 律师函”。`label: card.title` 只在界面（`components/RunSheet.tsx:59`），没有写进 `runs.start` 的快照。
- **影响**：与已拍板的“诉讼 / 非诉 / 企业法务三线”组织方式冲突，企业法务线律师看到诉讼链建议。
- **建议修法**：发起时把卡片编号写进 `input_snapshot`（例如 `run_options.card` 或 `scenario_card`，内核原样存、白名单校验），`scenarioOfRun` 先按卡片编号找；旧任务回退到“按事项业务线 + 模板”找。另：Y4 D-4 原文要求“打开带上本次成果的开始面板”，现在只打开空面板，宜在进度文档里如实写“未带成果”。
- **应补测试**：`batch6-lib.test.ts` 增“每个 `NEXT_STEPS` 键都能被某个运行快照反查到”的断言（当前只校验键与值是已有卡片）。

### S6B-06 · 一般 · 召回评测标注页的类别快捷键会劫持输入框

- **结论**：选区换算、重叠拒绝、编号基本成立；快捷键屏蔽不成立。
- **依据**：`pages/RecallEval.tsx:184-197` 在有待标注选区（`pending`）时向 `window` 注册 keydown，没有排除 `INPUT/TEXTAREA/SELECT/contentEditable`，也没有检查 `isComposing`；而侧栏“当事人名单”输入框（`RecallEval.tsx:330-345`）在 `pending` 存在时仍可聚焦（点输入框不会清除 `pending`）。键入 `0-9`、`e`、`c`、`b` 会被 `preventDefault` 并把选区标成对应类别。
- **其他核对**：
  - `pointOffset`（`RecallEval.tsx:137-153`）：文本节点端点与以根元素为容器的端点换算正确；当端点落在**段元素本身**（`span/mark[data-s]`，偏移指向其文本子节点）时返回 `null`，该次选区被静默忽略（不会标错，但双击/三击选词时可能“选了没反应”）。建议：`node` 自身带 `data-s` 时返回 `Number(node.dataset.s) + (off > 0 ? node.textContent.length : 0)`。
  - 重叠拒绝成立（`lib/eval-annotate.ts:104`）。
  - 编号：`addSpan` 同写法沿用编号（`eval-annotate.ts:106-110`），但 `updateSpan` 把别的类别改成自然人时直接取新编号（`:126`），不走“同写法沿用”，与规范 v1“同一写法沿用自然人编号”不一致。
  - 状态只在模块内存（`RecallEval.tsx:22-35`），未写浏览器存储，与声明一致。
- **建议修法**：keydown 处理与 `ReviewWorkbench` 一样先判目标元素与 `e.isComposing`；`updateSpan` 复用 `addSpan` 的同写法查找。
- **应补测试**：`batch6-lib` 增“改类别为自然人时同写法沿用编号”；界面快捷键屏蔽须界面测试（可先列入手工走查清单）。

### S6B-07 · 一般 · D-1 中栏“回复 · 摘要”取自右栏当前选中的成果

- **依据**：`RunView.tsx:607-620` 用 `preview.text` 生成摘要；`preview` 是右栏下拉当前选中成果的预览（`RunView.tsx:192-217`）。律师在右栏切到另一份 `.md` 工作区文件后，中栏标题仍是“回复（草稿）· 摘要”，内容却变成那份文件的前三行。另 Y4 D-1 要求“没有任何交付件的问答型任务里中栏显示全文”，实现一律只给摘要。
