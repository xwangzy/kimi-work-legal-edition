### B3-B01（重要）端点不再独立执行“问答档只读”：A1 增加 write_draft 后，端点裁决固定按“默认档”判

- 影响：违背第 04 篇 §1.2 第 6 条“每处独立校验”与 `local-server.ts` 自己的注释（“不采信宿主……按任务记录派生”）。宿主出缺陷或被绕过时，问答档运行可以在事项里写风险卡、事实行和草稿成果。手动档的“询问”本来就只能由宿主做，端点无法代替，但问答档的“拒绝”端点可以独立做到。

### B3-B03（一般）工具生成的成果按“事项内同 hash”去重，可能把本任务的成果记到别的任务名下

### B3-B04（重要）提交时“已定位”的卡，生成修订稿时仍可能定位失败：定位口径不一致，存的是 Agent 的原话而不是视图原文

- 位置：`packages/kernel/src/services/review-cards.ts:73-94`（`locateQuote` 第二步忽略空白比较）、`:161`、`:378`（修订稿用 `c.anchor_text`）、`:340-343`（`minimalEdit` 的唯一性按精确匹配计数）；`packages/kernel/src/services/structured-patch.ts:122`（`viewText.includes(anchor)` 精确匹配）；`packages/kernel/src/services/parser.ts:69-81` 与 `packages/docx-engine/src/compare.ts:32`（两种 DOCX 文本口径）
- 事实：① 提交时 `locateQuote` 先精确匹配，找不到再忽略空白匹配，后一种也判 `located`，工作台显示“已定位”；修订稿生成却要求锚点在视图里精确出现，`minimalEdit` 的唯一性也按精确匹配计数，只有当变化区段恰好不跨空白差异时才能救回。② Agent 摘录的来源是材料快照，即解析文本 `docxXmlToText`：制表符记为 `\t`，三个以上换行压成两个，首尾去空白，**已有修订的删除文字（w:delText）也保留**。而定位与补丁用的视图是 `extractParagraphs` 按 `\n` 拼接的段落文本。两种口径的空白与删除文字都不同；回稿（带修订）合同的锚点如果含被删除的文字，永远定位不到。③ 跨段落的锚点（含 `\n`）提交时可以判 `located`，但补丁引擎按段落写修订，必然失败。
- 影响：合同审查主路径（D-47：AI 提议 → 律师决定 → 原生修订）上，律师在工作台逐张接受后点“生成修订稿”，才发现若干卡“锚点不在视图中”，只能跳过。“已定位”这个状态对律师是误导；回稿场景尤其明显。
- 建议：提交时按定位结果把视图原文 `view.slice(start, end)` 存为规范锚点（另存 Agent 原话），修订稿一律用规范锚点；锚点含段落分隔时判为“跨段落、不能自动修订”，在提交结果里提示 Agent 拆卡。中期把 Agent 快照与定位视图统一到同一个 DOCX 文本口径（同一函数），并写明回稿里删除文字的处理方式。
- 建议补测：`review-tools.test.ts` 增 3 例：(a) Agent 把换行写成空格的锚点 → 判 located，修订稿能生成；(b) 跨两段的锚点 → 提交时给出明确状态，修订稿预览说明原因；(c) 原件已有 w:del 的回稿，锚点含被删文字 → 行为与提示一致。

### B3-B05（一般）修订稿成果没有绑定“律师当时的决定”，作者“律师审定”缺少可核对的依据

- 位置：`packages/kernel/src/services/structured-patch.ts:197-204`（manifest 只有 `patches` 数量与作者）；`api/index.ts:1749`（审计只记卡数、跳过数与状态）；`review-cards.ts:295-301`（决定可随时 reset 或改写）
- 事实：修订稿登记后，卡的决定还可以撤回或改写，但修订稿 manifest 里没有卡号、决定、改写文本 hash、决定人与时间。事后无法从成果追溯“这一版修订对应哪些卡的哪次决定”。
- 影响：修订作者写的是“律师审定”。以后进入签发流（W2）或发生争议时，无法证明某处修订确实经律师接受；改了决定之后，旧修订稿与新决定也会不一致。
- 建议：manifest 写入 `cards: [{card_id, status, decided_by, decided_at, final_text_sha256}]`；工作台在决定变化后，把已生成的修订稿标为“与当前决定不一致”。
- 建议补测：生成修订稿 → reset 一张卡 → 断言旧成果 manifest 仍能列出生成时的决定，界面或接口能给出“不一致”标记。

### B3-B06（一般）缩短后的锚点只在令牌视图里核唯一，还原成原文后可能有歧义，导致整份修订稿退回预览

- 位置：`packages/kernel/src/services/review-cards.ts:340-347`；`structured-patch.ts:157-160`
- 事实：`minimalEdit` 在令牌视图里判断缩短后的锚点是否唯一。还原到原件后，代号掩盖的文字可能使同一段短文字出现多次（例如锚点缩成“三公司”，原件里“张三公司”被代号掩盖，在视图里看不到）。这时补丁引擎判“歧义”，整份修订稿退回预览，律师看到的提示与他接受的卡对不上。
- 影响：概率低，但一旦发生，整份修订稿都写不出来（全有或全无），律师不知道原因。
- 建议：唯一性在还原后的原件段落里同样校验；不唯一时继续向两侧扩展，或退回整句锚点（`paragraph_hint` 已有，可一并使用）。
- 建议补测：`minimalEdit` 单测增加“视图唯一而原件不唯一”一例（可在测试里模拟令牌表）。

### B3-B07（建议）同一列混存令牌形态与原文（`risk_cards.final_text`、`matter_facts.statement`）

- 位置：`review-cards.ts:292-301`（`final_text` 为律师原文）、`:483`（律师确认时改写的 `statement` 为原文，Agent 提交的 `statement` 为令牌形态）
- 事实与核对：现有消费方都能正确处理。界面用 `matters.tokens.restore` 还原，对原文是恒等变换；交回 Agent 前端点会令牌化（`local-server.ts:63-74`，`lawyer_text` 不属于结构性字段）；修订稿先对 `final_text` 令牌化再比对（`review-cards.ts:377`）。**复核没有发现错名或残留代号的路径。** 残余风险有两处：将来新增的消费方不知道某列是哪种形态；对律师原文令牌化时会顺带往事项令牌表登记新条目（`deps.tokens.tokenize`），冲突代号会让律师自己写的文字以“unknown_token”被拒，提示难以理解。
- 建议：落盘统一为令牌形态（律师原文写入前令牌化），或加 `*_form` 列标明形态；冲突代号导致的拒绝，在界面上改写成“这段文字里的「…」与其他当事人代号冲突，请在当事人词典里处理”。

### B3-B08（建议）“不残留代号”的交付检查只覆盖正文段落

### B3-B22（一般）主路径上仍有技术术语（U6 未收敛部分）

- 位置与原文：`components/Composer.tsx:19`（“通用 Agent”“联网检索（经出站闸门）”）、`:20`（“按立场与 Playbook”）、`:127`（“代码只在执行域中运行”）、`:163`（“事项材料（只读原件；Agent 只见令牌化视图）”，UIUX 替换表第 292 行已给出“选择本事项的材料（原件不会被修改）”）；`pages/Home.tsx:63`（“请确认内核已启动：桌面客户端内嵌，或开发桥 127.0.0.1:7720”）、`:150`（“四项依据”，与 U1“一问”口径冲突）；`pages/Matter.tsx:172`（hash 列，UIUX 第 188–191 行建议移入详情）、`:234`、`:255`（“出站”）；`pages/RunView.tsx:95`（“Agent 引擎已启动（本机）”）。
- 影响：目标客户几乎没有 IT 背景；输入框菜单与首页报错都在首日主路径上。
- 建议：按 UIUX 替换表逐条落地；内核不可用时的报错改为“本机服务没有响应，正在自动恢复（如持续，请重启应用）”，技术细节放到“诊断信息”里。

### B3-B23（一般）可达性缺口（读屏与键盘）

- 位置：`components/ReviewWorkbench.tsx`（生成修订稿的结果横幅没有 `role="status"`/`role="alert"`，读屏用户听不到“已生成 / 未生成”；原文高亮 `<mark role="button">` 只响应 Enter，不响应空格；筛选用了 `role="tablist"/"tab"`，却没有 tabpanel 和方向键切换）；`pages/RunView.tsx:567-571`（流式回复整块放在 `aria-live="polite"` 里，每次轮询都会重读最多 4,000 字）；`components/ScenarioStart.tsx`（必填星号的 `aria-label` 加在无角色的 span 上不起作用，输入框没有 `aria-required`）
- 建议：结果横幅加 `role="status"`（失败时用 `alert`）；mark 补空格键处理，或改用 `<button>`；筛选改为普通按钮组加 `aria-pressed`；流式区域去掉 aria-live，另设一行“正在写（已写约 N 字）”的状态播报；必填项用 `aria-required="true"`。

### B3-B24（一般）意图建议把“答辩状 / 仲裁申请书”引到只做起诉状的模板

- 位置：`apps/desktop/src/lib/scenarios.ts:100`（起诉状卡 `intents` 含 `["仲裁申请书"]`、`["答辩状"]`）；`content/skills/pleading-draft/SKILL.md` description（“首发只做民商事起诉状，不用于仲裁申请书、答辩状……”）
- 事实：律师输入“帮我写答辩状”时，建议条显示“这看起来是「起草起诉状」”，用了之后模板会拒绝或停下。另外 `suggestScenario` 按目录顺序取第一个关键词命中（`:324-328`），“核对起诉状里的引用”会被引向起诉状而不是引用核验。
- 建议：去掉模板不支持的意图词；对“不支持”的意图给出明确说明（“答辩状暂不支持，可用通用任务起草”）；匹配时排除“核对 / 检查 / 引用”这类动词与文书名同时出现的情况，或按命中词数取最优。

### B3-B25（建议）其他细节

- 没有建议文本的卡（提示类）不能“接受”，只能“修改后接受”或“不采纳”（`ReviewWorkbench.tsx` 接受按钮在 `!c.suggestion` 时置灰），律师想表示“已知悉、不改”时只能选“不采纳”，进度与统计会失真。建议增加“知悉（不改动）”决定。
- 起诉状卡自带一个“补充要求”字段，开始面板又有通用的“补充要求（可选）”，同一页出现两次（`scenarios.ts` 起诉状卡 `fields`、`ScenarioStart.tsx`）。
- 场景卡缺省用当前选中的事项（首次进入为列表中的第一个，`Home.tsx:61`），面板副标题显示了事项名（`ScenarioStart.tsx`），但不能就地切换。建议在面板内提供事项选择，避免在错误的事项里发起。
- `kernel/test/skills-bundle.test.ts` 的用例标题仍写“五个方法模板”，现有模板已是 13 个，建议同步断言数量。
