## 二、新发现问题

### N-01【阻断（在阶段 2 开放任何新工具之前必须修复）；G0 下需要宿主进程被攻破才能利用】令牌活性只在收到请求头时检查一次，预开请求可以跨越取消、尝试被取代和终态

- **位置**：`kernel/src/local-server.ts:251-257`（`handleMcp` 在 `readBody` 之前调用 `assertLive`），`:300-301`；`:322-329`、`:351-355`（`handleChat`，流式响应开始后不再检查，也不会中止）；`model-broker/src/` 中没有任何 abort 或 signal（grep 结果为空）；本机服务器未设置超时，取 Node 默认 `requestTimeout`=300 s（`createServer` 的默认值，见附录 E）
- **复现**：附录 A K1、K2、K6。取消后的新请求为 401（对照），同一令牌的预开请求则为 200。三个后果均已复现：读到材料、调用上游并产生出网记录、写类副作用把 outbox 记为 succeeded
- **后果**：用户急停（`runs.cancel` 返回“已立即生效”）之后，仍然可以读新材料、调上游、产生副作用；结算前的 assertNoUnresolved 也能被“检查之后才送请求体”的请求绕过。这违反第 04 篇 §8“失去租约后不得读新材料、调上游、写产物”和 §9 F6“先吊销能力令牌”。G0 下令牌只在宿主进程内，引擎自己不会故意拖住请求体，所以需要宿主被攻破才能利用；阶段 2 开放 Bash 之后，Agent 写的代码只要能连到本机端点（TCP 回环或命名管道）就能直接利用
- **建议**：① 读完请求体之后、调用工具或上游之前，再做一次活性检查；② 所有提交点（outbox 完成、成果登记、结算）在同一个 DB 事务里复核尝试行与纪元（R-06/R-07）；③ 按 rid/jti 登记在途请求，撤销时中止上游流与工具执行（AbortController）；④ 本机服务器把 `headersTimeout`、`requestTimeout` 降到秒级；⑤ 用预开请求补测试，覆盖工具、模型流式与非流式、写类工具，以及取消、取代、终态三种触发

### N-02【一般】端点的跨事项拒绝引入了存在性探测

- **位置**：`local-server.ts:128-131`（`not_found: 对象不存在或不属于本事项`）对比 `kernel/src/tools/tools/materials.ts:36`（`notFound("材料")` 返回“材料不存在或无权查看”）
- **复现**：附录 A K3，两种情形的口径不同（`false`）
- **说明**：ID 是随机生成的，实际可探测性低；但这与处置声明直接矛盾，测试也没有做对照。建议两条路径用同一个错误构造，并加上“不存在 vs 他事项”的逐字对照测试

### N-03【一般（纵深）】活性检查不核对令牌中的事项、租户、副作用类别、用途是否与任务记录一致

- **位置**：`identity.ts:47-63` 只按 (rid, aid, fen) 查 attempts/runs；`local-server.ts:81-87`、`:110-134` 直接信任 `claims.mid/tid/fx/pur`
- **复现**：附录 A K4。用本事项活动尝试的 (rid, aid, fen) 加上他事项的 mid 签出令牌，可以读到他事项材料（需要持有内部签名密钥）
- **说明**：利用前提是拿到 `ZR_INTERNAL_SECRET`。该密钥没有传给宿主（`agent-host-manager.ts:345-363`），但留在内核进程的环境变量里。同用户进程能否经 `/proc/<pid>/environ`（Linux）或 KERN_PROCARGS2（macOS）读到它，属于静态推断，未复现，需要在阶段 2 威胁模型中核实。建议服务端从 runs/attempts 记录派生事项、租户、fx 和用途，不再采信令牌里的这些字段

### N-04【一般】`GET /v1/models` 不做活性检查

- **位置**：`local-server.ts:405-411`；复现见附录 A K5（终态任务的令牌返回 200）。泄露的只是路由别名，影响小，但与“每次调用都做活性检查”的口径不一致

### N-05【重要（静态推断，未在 Windows 复现）】Windows 上宿主退出后按裸 PID 执行 `taskkill /T /F`，可能误杀无关进程树

- **位置**：`agent-host-manager.ts:108-117`（`taskkill /PID <pid> /T /F`），调用点为 `:426`（close 时，宿主已退出）、`:440`（宿主已退出时的 terminate）、`:451`（取消后 5 s，宿主通常已经退出）
- **说明**：Windows 的 PID 在进程对象释放后会很快被复用。宿主退出后，再按这个 PID 带 `/T /F` 杀树，可能杀掉律师当时打开的 Word 等无关进程及其子进程。POSIX 下只要进程组里还有成员，pgid 就不会被复用，风险低得多。Windows 是主要目标平台，所以定为重要
- **建议**：只在宿主仍在运行时按 PID 动手；宿主退出之后，靠 `KILL_ON_JOB_CLOSE` 作业对象清理残留进程。作业对象落地之前，宿主退出后不再执行 taskkill

### N-06【一般（阶段 2 出现真实子进程之前须修复）】终态只在 `'close'` 时裁定，持有 stdio 的逃逸孙进程能让任务永不收尾

- **位置**：`agent-host-manager.ts:413-432`（收尾只在 close 中）、`:436-442`（宿主已退出时 terminate 直接返回，不强制收尾）、`:427`（互斥锁只在 close 时释放）；`executor.ts:820-840`（轮询没有总时限）
- **复现**：附录 C。宿主退出、管理器超时都过去之后，任务仍是 running，互斥锁一直占着（同一把锁还管着其他 Agent 任务和 OCR）；令牌直到超时才被撤销
- **建议**：同 R-15 一行

### N-07【一般（静态推断，未复现）】内核非流式模型代理把缺失的 finish_reason 默认成白名单值 `"stop"`

- **位置**：`model-broker/src/providers/upstream.ts:86`。这与 R-03“缺失不能成功”的前提冲突。引擎主回合走流式，触发面有限

### N-08【一般（静态推断，未复现）】成果跨任务去重导致恢复误判，成果也会挂在别的任务名下

- **位置**：`executor.ts:494-498` 对比 `:797`。同一事项、同一 kind 下出现同内容的成果时，会返回另一个任务的成果行。结算正常的话，本任务成功了却没有一条属于自己的成果行；在结算前崩溃的话，恢复时被误判为 reconciling

## 三、总评

1. **两项阻断的关闭情况**：R-12 在 broker API 范围内成立（本机 macOS，附录 B 共 17 项反例全部被拒），同意关闭；Windows 的复测按声明随实机探针进行。R-01 只是部分成立：新请求一律被拒，但同一类缺口——令牌在任务终止之后仍能完成一次读取、上游调用或副作用——经预开请求可以稳定复现（N-01）。因此不同意“R-01 阻断已关闭”。
2. **是否同意“可以进入阶段 2”**：**有条件同意**。可以开始阶段 2 的工程工作（kap-host、内存可信配置、端点双键等），理由是：G0 的生产工具面只有 6 个只读工具，令牌 fx 只含 read，宿主进程服务为全拒绝，N-01 在 G0 下需要宿主进程被攻破才能利用。但在下列条件满足之前，**不同意**向 Agent 开放 Write、Edit、Bash，或任何写类、网络类、执行类工具（第 06 篇 §8 第 2 条）。
3. **开放 Write/Edit/Bash 之前必须先满足的条件**（在主审已列三项之外追加）：
   1. **N-01 修复并用测试锁定**：读完请求体后、执行之前复核活性；所有提交点（outbox 完成、成果登记、结算）在同一事务内复核尝试行与纪元，outbox 写回带 `status='pending'` 守卫；撤销时中止在途上游流；本机服务器超时降到秒级；用预开请求测试覆盖取消、取代、终态三种触发，以及读工具、写工具、模型流式与非流式。
   2. **主审三项**（R-13 内存可信配置、R-09 补充的双键绑定、R-07 写类工具的副作用事务边界）：同意列为入口条件；R-07 的事务边界应同时带上尝试与纪元守卫（R-06）。
   3. **文件面**：Bash、Write、Edit 的全部文件访问必须经过 broker，否则就得先把可信配置移出可写区。补测试覆盖“非 broker 行为者改名、建硬链接”（附录 B 末三行：改名即可替换 mcp.json，硬链接导致 EMLINK 拒绝服务）。
   4. **进程面**：Bash 产生真实子进程之前，必须先落地 N-05（Windows 作业对象，不按裸 PID 杀树）和 N-06（宿主退出后有界收尾，执行器轮询设总时限）。
   5. **令牌面**：服务端从任务记录派生事项、租户、fx、用途（N-03）；核实 Agent 执行的代码读不到内核环境中的 `ZR_INTERNAL_SECRET`，或改为每个尝试一把的密钥。
   6. **口径**：修正 N-02（统一 not_found 并加对照测试）；把处置表中不准确的声明改为如实表述，涉及 R-05 的 reconciling、R-06 的 attempt_id 改记、R-09 的用途与存在性探测、R-14 的代理口径、R-16 的外键检查时机、R-20 的界面文案。不要把“部分修复”记成“已修复”。

### 4.2 新发现问题

#### M-01【重要（阶段 2 开放 Bash 或任何会产生真实子进程的能力之前必须修复）；G0 下不可达】宿主控制协议走 stdout，继承 stdout 的子孙进程可以注入完成记录与成果，并且以最后一条 done 为准

- **位置**：`agent-host-manager.ts`：`handleChildMessage` 的 `done` 分支直接覆盖 `task.doneRecord`（`task.doneRecord = msg`）；`artifact` 分支只要求文件在 outDir 内且 hash 一致；协议通道就是宿主的 stdout
- **复现**：附录 G H-inject。宿主如实上报了截断（`finish_reason: max_tokens`、`provider_finish_reason: truncated`，本应判 partial），然后退出 0。继承了 stdout 的 setsid 孙进程在 300 ms 后往 outDir 写入 `forged.md`，再注入一条 `artifact` 和一条 `done{succeeded, end_turn, completed}`。最终裁定为 **succeeded**，成果为 `final_message.md` 与 `forged.md`
- **后果**：F1（终态枚举化）与 F5（结构化成果）的证据都可以被伪造。G0 下宿主进程服务为全拒绝、宿主自己也不起子进程，所以不可达；阶段 2 中，只要 Bash 或执行域产生的进程能继承宿主的 stdio，或者能写 outDir，就可以利用
- **建议**：控制通道改为不可继承的专用管道（CLOEXEC；Windows 上句柄不可继承），或者每条消息带每任务随机数的 MAC；只接受第一条 `done`，`done` 之后的记录一律丢弃并记取证事件；执行域进程不得继承宿主 stdio，也不得有 outDir 写权限；内核按出网记录核对最后一次上游调用的结束原因（1.5 轮 R-03 已建议）

#### M-02【一般】读类调用在交付前复核失败时，不留任何审计行

- **位置**：`local-server.ts:221-226`。复核失败时抛错，而 `recordOp` 就在同一个事务里，随之回滚；读取本身已经执行过了
- **复现**：附录 F I2，`审计行: []`
- **建议**：另记一行 `blocked_after_read`（或 `aborted`），注明读取已发生、结果没有交付，供取证使用

#### M-03【一般（静态推断，未复现）】失去租约的执行者走通用失败分支，会把任务连同新尝试一起置为 failed

- **位置**：`executor.ts:162-167`（`assertAttemptHolds` 抛出的是 `conflict`）→ 工作流 catch 中的通用分支 → `markTerminal("failed")`。`executor.ts:974-987`：任务行的 CAS 只比对 status 与 version，不比对尝试；attempts 的更新为 `WHERE run_id = ? AND status = 'running'`，不带尝试过滤，会把新尝试一并置为 failed
- **可达性**：只有同一账本上同时存在两个执行者（例如内核被双开，或执行者假死后恢复）时才可达；单进程内的队列去重不会触发
- **建议**：失去租约时用专门的错误类型，安静退出，不改任务状态；markTerminal 只收尾本尝试（`AND attempt_id = ?`），并要求任务当前的活动尝试就是本尝试

#### M-04【一般（纵深，静态推断，未复现）】任务令牌密钥在内核进程内存中；在 Windows 上，同用户、同完整性级别的进程可以读到

- **说明**：N-03 把密钥移出了环境变量，确实挡住了 `KERN_PROCARGS2` 与 `/proc/<pid>/environ` 这类读取。但在 Windows 上，同用户、同完整性级别的进程默认可以 `OpenProcess(PROCESS_VM_READ)` 后 `ReadProcessMemory`，读到这把 32 字节的密钥，进而为**任意**活动尝试（包括他事项的任务）签发令牌：令牌里的 rid、aid、fen 可以指向任何正在运行的任务，claims_mismatch 只核对令牌与该任务是否自洽。宿主环境变量中的令牌也可以被同样窃取，但它受该尝试约束
- **建议**：列入阶段 2/3 的威胁模型。执行域进程不得以“同用户、同完整性级别、无隔离”的方式运行（方案中的 W 执行域：AppContainer、低完整性或独立用户）；中期可以考虑每个尝试一把密钥，并让命名管道按连接对端进程身份做绑定

### 4.3 总评（阶段 1.6）

1. 同意 **N-01 与 R-01 关闭**。1.5 轮的全部反例（预开请求的读、上游调用、写副作用）在本轮均被拒绝，执行过程中注入的终止也都在提交点或交付前被挡住。同意 R-12、N-02～N-08 关闭；N-05 待 Windows 真机复测。
2. 同意 **阶段 2 继续**。主审结论写明“Write/Edit/Bash 在 kap-host 中仍只在测试与探针里开放”，与第 06 篇 §8 第 2 条一致。
3. 在生产环境开放 Write、Edit、Bash（或任何会产生真实子进程的能力）之前，除了主审列出的条件 2～4，还应满足：
   1. **M-01**：控制通道不可被继承或伪造，只接受第一条 done；执行域进程不能写 outDir；补“子孙进程注入完成记录”的回归测试（可直接改用 `review1b/v16/fake-host-c.mjs` 的 inject 模式）。
   2. **M-04**：执行域与内核不能是“同用户、同完整性级别、无隔离”的关系，阶段 2 威胁模型要写明 Windows 上 ReadProcessMemory 这一路径。
   3. **M-03**：出现多执行者的可能之前（双开内核、执行者假死后恢复），修正失去租约时的失败处理。
   4. **N-06 残余**：收到 `exit` 时立即撤销令牌。
