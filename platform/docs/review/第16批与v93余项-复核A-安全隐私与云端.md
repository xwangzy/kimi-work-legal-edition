## 总体结论

没有阻断级问题。A-8 的核心承诺站得住：签名服务只收结构、不收字节，签名字节带域分隔前缀并按种类白名单生成；信封与席位令牌用不同的密钥；mTLS 调用方身份解析不能用 SAN 注入伪造（已实测）；控制面改成 async 之后，逐个核对了全部 `await` 点，**没有**找到“已回复成功的写被别的请求的 `rollback()` 冲掉”的时序。A-7 的 SQL 全部参数化，TLS 不降级，`seq` 围栏与“连接一断即失去主实例身份”的写侧语义成立。客户端版本上报、A-9 指标和账本加密算法钉住都没有把标识或内容带出去，也没有副作用。

真正的缺口集中在四处：

1. **签名账的“防抵赖”比文档说的弱**。末尾截掉、整本删掉都发现不了（RB16A-01）；一次记账写入失败就会让账本与内存脱节，签名服务下次启动直接拒绝启动（RB16A-02）。这是“签名账与控制面审计对账”这道兜底能不能成立的前提，列为重要。
2. **A-7 在故障态下的表现与文档不一致**。SCRAM 的服务端签名核对可以被跳过，已复现（RB16A-06）。主实例“健康”只看内存标志，连接静默断开时旧主实例会继续用旧吊销集应答（RB16A-07）。Redis 启动时连不上就拒绝启动（RB16A-09）；Redis 挂起时既不超时也不计失败（RB16A-17）。库里没有状态行时静默以空状态启动（RB16A-10）。Redis 键是可逆编码，租户与设备编号明文可读（RB16A-08）。
3. **A-11 让一项旧修复失效、清扫失败没人知道**。包本体读取又开始跟随符号链接，绕开了 S9B-09（RB16A-11）；对象存储一次删除失败就中止整轮清扫，而且完全静默（RB16A-12）。
4. **“移到一边”漏了 `onboarding.json`**。待批准的设备移完之后进不了“从备份恢复”（RB16A-14）；驻留登记与说明文字对明文激活记录的描述也不如实（RB16A-15）。

## 一、A-8 签名服务（cp-signer、control-plane signer.ts、server.ts、cloud-serve.mjs）

已核对、未发现问题的部分：
- 结构化接口：信封只收 `request_id/req_now/kind/body` 四个字段、种类白名单、签名字节由 `envelopeBytes` 带域分隔前缀与 `canonicalJson({kind,kid,body})` 生成（firm-trust/envelope.ts:24-33），调用方无法提交任意字节；席位令牌由席位密钥签、信封由信封密钥签，`kwl-signer-selftest` 不在白名单内。
- mTLS 调用方：cloud-serve 对 cp-signer 角色设 `requestCert + rejectUnauthorized + ca=client_ca_file`；`callerOf` 的 SAN 正则在 Node ≥17.3.1 上不可被 DNS SAN 里的逗号注入——实测 DNS SAN 值 `x, URI:spiffe://kwl/prod/cp-api, y` 被 Node 输出为 `DNS:"x, URI:…, y"`，正则取到的是真实的 URI SAN（草稿实验）。
- 控制面路由改 async 后与 `rollback()` 的交错：逐个核对了全部 `await` 点（server.ts:425/891/898/1234/1385/1414-1492），所有“改状态 → send（审计 → 写盘 → 回复）”都在同一个同步段内完成，`await` 之前唯一的改动是 `issueLicense` 写 `t.license`（只是缓存）。`rollback()` 只回到 `lastSaved`，而每个已回复成功的写都已先同步写进 `lastSaved`，因此**没有找到“已回复成功的写被别的请求的回滚冲掉”的时序**。残留问题见 RB16A-05。

### RB16A-01 签名账可被截尾或整本删除而不被发现
- 级别：**重要**
- 证据：
  - `services/cp-signer/src/ledger.ts:46-51`：启动时只验“文件里已有的行彼此连得上”；文件不存在就从创世哈希 `0…0`、序号 0 重新开始（`existsSync(file)` 为假即跳过核验）。
  - `ledger.ts:76-97` `verifySignerLedger`：任何前缀都是合法的链；末尾删掉 N 行后返回较小的 `seq/hash`，`ok: true`。
  - `ledger.head()` 全仓没有调用者（`grep head()` 只有接口声明）；签名服务的指标（index.ts:301）与 cloud-serve 导出的 `kwl_signer_requests_total` 都不含账本序号或末行哈希；签名回复里也不带。
  - 文件头注释（ledger.ts:3）写“删改任何一行都验不过”，与事实不符：删末尾的行验得过。
- 失败场景：攻陷签名区主机（或有数据盘权限的运维）的人在签发一批“格式合法”的恶意许可/吊销通知后，`head -n <签发前行数> ledger.jsonl > x && mv x ledger.jsonl`，或直接删掉 `ledger.jsonl`；重启签名服务 → 核验通过、从截断处（或从 seq 1）继续记账。签名账与控制面审计对账（§4.3 列为兜底手段）时找不到这批签名的任何痕迹，而 A-11 的 WORM 外送尚未实现，期间没有任何外部锚点。
- 建议：
  1. 把 `head()`（seq + 末行哈希）作为指标导出（gauge `kwl_signer_ledger_seq`），并定期写入与签名区不同信任域的地方（控制面审计流水 / WORM 桶）；对账脚本比对“外部最后见过的 seq/hash 是否仍是本账的前缀”。
  2. 账本缺失时不要静默从创世开始：要求显式初始化（例如另一个只写一次的 `ledger.genesis` 标记或启动参数 `--init-ledger`），文件丢失即拒绝启动。
  3. 改正 ledger.ts 头注释的“删改任何一行都验不过”为“改动或删除中间行验不过；截尾须靠外部锚点发现”。

### RB16A-02 记账写入失败的一半状态会让账本与内存脱节，签名服务下次启动直接拒绝启动
- 级别：**重要**
- 证据：`ledger.ts:56-65`：
  ```ts
  writeSync(fd, `${line}\n`);
  fsyncSync(fd);
  seq = rec.seq;
  prev = lineHash(line);
  ```
  - `writeSync` 成功、`fsyncSync` 抛错（EIO、ENOSPC 延迟报错、网络盘抖动）时：这一行**已经在文件里**，但内存里的 `seq/prev` 没有前进。该请求得到 503（index.ts:273-278，符合“记不进就不签”），但下一次 `append` 会以**同一个 seq、同一个 prev** 再写一行。文件里出现两个相同序号 → `verifySignerLedger` 返回“序号不连续”。
  - `writeSync` 的返回值没有检查：普通文件在磁盘满时 `write(2)` 可以只写入一部分并返回较小的字节数而不报错，Node 的 `fs.writeSync` 不会替调用方补写。此时 `append` 认为成功、签名照常交付，文件里留下半行；下一行接在半行后面 → 该行不是 JSON。
  - 拒签路径（index.ts:236-241）吞掉 `append` 的异常继续服务，同样会造成上面的错位。
- 失败场景：签名区数据盘一次瞬时 I/O 错误（或磁盘写满后清理）→ 之后签名服务看似恢复正常、继续签名记账，但账本已错位；下一次发布或重启 → `openSignerLedger` 抛“签名账核验不通过（第 N 行：序号不连续）” → 签名服务不启动 → 控制面所有信封与席位令牌 503，设备只能靠 72 小时宽限，直到有人手工修账（而手工修账本身正是 RB16A-01 担心的操作）。“半行”情况下还违反了“记不进就不签”：签名已交付，但账上那一行不完整。
- 建议：`append` 失败（任一步抛错或 `writeSync` 返回值小于行长）时，用 `ftruncateSync(fd, 上次成功末尾偏移)` 把文件截回最后一行完整记录并 fsync；截不回去就把账本置为“已损坏”状态，此后所有签名一律 503（失败关闭且不继续写错位的链）。拒签路径不要吞异常后继续写，至少同样置“已损坏”。

### RB16A-03 签名服务的计数键直接用调用方提交的 `kind` / `aud` 原文，内存与指标基数不受限
- 级别：**一般**
- 证据：`services/cp-signer/src/index.ts:232` `kind` 只限 `length <= 64`，未过白名单就进了计数键；`index.ts:235` 拒签计数 `count(\`${op}/${kind ?? (typeof b.aud === "string" ? b.aud : "general")}/rejected\`)`，席位令牌请求的 `b.aud` 是**任意长度**的任意字符串；`counts` 对象永不清理（index.ts:184-186）。obs.mjs 输出时虽按字符集过滤标签值（obs.mjs 新增段），但 `counts` 本身照样增长，每次抓指标都要遍历它。
- 失败场景：设计 §4.3 明确把“已攻陷的 cp-api”放进威胁模型。攻陷者循环提交 `{op: seat_token, aud: "<随机 1 MB 字符串>"}`（每次都在 `audience_not_allowed` 被拒、但先计数）→ 签名服务内存持续上涨直至 OOM（签名服务停摆 = 控制面全部签名 503）；或用 64 字符以内的合法字符集 kind 刷出上百万个标签，指标抓取超时、签名速率告警失明——恰好是攻陷者想要的。
- 建议：计数键只用登记过的种类/受众，其余一律记为 `invalid`；`aud` 在进计数前先按 `SEAT_AUDIENCES` 归一。

### RB16A-04 远程签名者不核验签名服务的回复，就把信封与席位令牌交给设备
- 级别：**建议**
- 证据：`services/control-plane/src/signer.ts:205-216`：只检查 `e.kind === kind`、`pub.envelope[e.kid]` 存在、`token.startsWith("zst1.")`，没有用已取得的公钥表验 `sig`，也没有解析令牌核对 `tid/uid/sid/dev/aud/exp`。注释写“回复里的文档必须与提交的逐字一致”，但代码只是把本地的 `body` 拼回去，并没有任何一致性核验。
- 失败场景：签名服务密钥轮换配错（公钥表报 `cp-prod-2`、实际用旧私钥签）或签名服务被替换/中间人（mTLS 配置错误时）→ 控制面照样回 200，设备侧全部 `envelope_signature_invalid`，故障表现为“所有律所同步失败”，而控制面自己的指标与日志一切正常，排障方向被误导。
- 建议：交付前 `openEnvelope(...)` 与 `verifySeatToken(...)` 各验一次（Ed25519 验签开销可忽略），不过即抛 `SignerUnavailableError("reply_invalid")`。

### RB16A-05 席位令牌“先查席位、再等签名”之间出现窗口，吊销确认之后仍可能交付新令牌
- 级别：**建议**
- 证据：`server.ts:1424-1431`（以及 support/notify/relay 三条同型路由）：席位与许可核对在 `await seatToken(...)` 之前；改 async 之前这两步在同一同步段内（原子），现在中间隔着一次到签名服务的网络往返（`timeoutMs` 缺省 5 秒）。`authDevice` 的设备吊销核对同理。
- 失败场景：设备 D 发起 `/v1/seat-token`，核对通过后在等签名；此时管理员吊销该席位，`revokeSeat` 回复成功并已落盘；随后 D 的请求恢复，拿到一张 96 小时的新席位令牌。网关等服务按订阅里的 `revoked_seats` 仍会拒收（所以只是建议级），但“吊销已确认后控制面不再签发”的不变量不再成立，审计流水里会出现“吊销”之后又一条 `seat_token.issue ok`，对账时会被当成异常。
- 建议：`await` 返回后、`send` 之前重新取 `t.seatsByUser.get(...)` 与设备记录再核一次（席位、设备、许可），不过即丢弃令牌回 403/402。

## 二、A-7 控制面 PostgreSQL 一主多备 + Redis 防重放（pg-wire.ts、resp.ts、pg-state-store.ts、pg-state-worker.ts、nonce-mirror.ts）

已核对、未发现问题的部分：
- 参数化：pg-wire 只用扩展查询协议，Bind 全部按文本格式单独传值（pg-wire.ts:234-237）；pg-state-worker 的所有语句都是常量 SQL + `$n` 参数，咨询锁编号也作为参数传入；没有拼 SQL。
- TLS 降级：生产入口的 URL 形态一律带 `tls`（cloud-serve 只有 `insecure && socket_dir` 才走明文 Unix 套接字）；SSLRequest 回答不是 `S` 即拒绝；`S` 之后同一数据块里多出的字节被丢弃、不会被当成 TLS 内数据处理（避开 CVE-2021-23214 类“缓冲注入”）；`servername` 缺省为 host，`rejectUnauthorized` 保持缺省 true。
- 围栏：`INSERT … ON CONFLICT DO UPDATE … WHERE s.seq = $7` 的命令标签在条件不满足时为 `INSERT 0 0`，代码据此置 `fenced` 并永久失去主实例身份；连接关闭即 `connection_lost`，不重连。
- Atomics.wait：超时即置 `lost`，之后所有同步调用直接抛错，晚到的回复只会被按 id 跳过，不会被错当成下一次调用的结果；生产入口 5 秒内据 `healthy()` 退出。

### RB16A-06 SCRAM 客户端不强制服务端最终消息，“核对服务端签名”可以被跳过
- 级别：**一般**
- 证据：`services/control-plane/src/pg-wire.ts:165-231`。认证循环里 `code === 0`（AuthenticationOk）在任何阶段都 `continue`，随后 `Z` 即 `break`；循环后只检查 `o.password !== undefined && !scram`（防 trust）。服务端签名只在收到 `code === 12`（AuthenticationSASLFinal）时才核对（:212-223）。若服务端在收到 client-final 之后**不发 12、直接发 0 + Z**，或者在 code 10 之后直接发 0，`scram` 非空、循环正常结束，连接被接受。另外：服务端 nonce 只检查 `startsWith(客户端 nonce)`，未要求比客户端 nonce 更长；迭代次数没有上限（`i=2^31-1` 会让工作线程里的 `pbkdf2Sync` 卡住很久）。
- 复现（草稿目录 fake-pg.mjs，直接 import 本仓 pg-wire.ts）：假服务端对启动消息回 `R(10, "SCRAM-SHA-256")`，收到 client-first 后直接回 `R(0)` + `Z`，对随后的 `SELECT seq FROM kwl_cp.state` 回零行 → `connectPg` 成功返回，输出 `CONNECTED without server signature; rows = 0`。
- 失败场景：在 TLS 失效的情况下（测试用 Unix 套接字形态、CA 文件配错成公共根、CA 被滥发），假冒的数据库按上面的顺序应答即可让控制面认为认证成功——文件头（:4）与 :213 注释承诺的“核对服务端签名：防止假冒的数据库骗取连接”并不成立。配合 RB16A-10（库里没有状态行即以空状态启动），假冒库只需对 `SELECT … FROM kwl_cp.state` 回零行，控制面就以空状态对外服务（吊销集清空）。
- 建议：记录 `scramVerified`，收到 AuthenticationOk 时若已发起 SCRAM 但尚未核过服务端签名即拒绝；服务端 nonce 须严格长于客户端 nonce；迭代次数设上限（如 ≤ 1,000,000）。

### RB16A-07 主实例“健康”只看内存标志，不探测数据库；连接静默断开时旧主实例继续以旧状态应答，备实例的等锁查询可能永远挂住
- 级别：**一般**
- 证据：
  - `pg-state-worker.ts:85-87` `status()` 直接返回内存里的 `{ leader, lost }`，不发任何查询；`pg-state-store.ts:144-153` `healthy()` 与 cloud-serve 的 `/readyz`、5 秒巡检都只依赖它。
  - `lost` 只在套接字 `close/error` 事件（pg-wire.ts:153-154）或写失败时置位；pg-wire 没有 `setKeepAlive`，也没有单条查询超时。
  - `acquire` 的 `pg_try_advisory_lock` 轮询（worker:51-56）没有超时，连接若静默失效，`await conn.query` 永不返回。
- 失败场景：主实例 A 到数据库的路径被静默丢包（安全组变更、宿主网络故障、旧主库宿主断电而无 RST）。数据库侧按 `tcp_keepalives_*` 终止 A 的会话、咨询锁释放，备实例 B 拿到锁成为主实例并开始处理吊销。A 这边没有收到任何包，`leader` 仍为 true，`/readyz` 照样 200，负载均衡继续把请求分给 A；A 的只读路由（尤其是 `GET /v1/feed/gateway`，`feedBody()` 不改状态、不会触发写入）持续用旧内存应答——网关从 A 拿到的吊销集缺少 B 上新吊销的设备与席位。直到 A 碰到第一个改状态的请求，阻塞 10 秒超时后才退出。安静时段这个窗口可以很长。反过来，B 若是在等锁期间遭遇同样的静默断连，会永远卡在 `acquire`，永不成为主实例。
- 建议：工作线程里定时（如每 2 秒）异步执行一次带超时的探测，并核对锁仍在本会话手里（`SELECT 1 FROM pg_locks WHERE locktype='advisory' AND pid = pg_backend_pid() AND objid = …`），失败即置 `lost`；pg-wire 打开 TCP keepalive；每条查询（含等锁轮询）设超时，超时即销毁连接。

### RB16A-08 Redis 里的防重放键是可逆编码，租户编号与设备编号明文可读，与设计“摘要后”不符
- 级别：**一般**
- 证据：`nonce-mirror.ts:66` 键名为 `prefix + base64url(key)`；`key` 来自 `request-auth.ts:80` 的 `${tid}\0${deviceId}\0${nonce}`；读回时 `:37` 直接 base64url 解码还原。设计 `docs/design/云端持久化与KMS设计-v1.md:109` 写的是 Redis 存“摘要后的 (租户, 设备, nonce)”。控制面状态在 PostgreSQL 里是 AES-256-GCM 密文（pg-state-store.ts:10 “库里只有密文”），Redis 却是明文元数据。
- 失败场景：能读 Redis 的人（缓存运维、Redis 快照与备份、云厂商侧）`SCAN kwl:cp:nonce:*` 后逐个 base64url 解码，就能得到每个律所在最近 10 分钟内哪些设备在活动、活动频度——这正是 PG 那一侧刻意加密的元数据；Redis 的 RDB/AOF 备份会把它长期留存。nonce 判重只需要等值比较，并不需要可逆。
- 建议：键名改为 `HMAC-SHA256(状态封装密钥派生的子密钥, key)` 的十六进制；读回时把 HMAC 值本身并入内存表，判重前对新请求的键做同样的 HMAC（内存表可以统一存 HMAC 值）。若暂不改，至少在部署文档与数据驻留登记里如实写明 Redis 中有租户与设备编号。

### RB16A-09 Redis 在启动时不可达即拒绝启动，与“Redis 不可用只降级”相反，换主实例时会连锁停服
- 级别：**一般**
- 证据：`scripts/cloud-serve.mjs`（control-plane 分支）先 `openPgStateStore` 拿到主实例锁，再 `openRedisNonceMirror`，后者抛错即 `fail("连不上 nonce_store（Redis）")` → `process.exit`；`nonce-mirror.ts:22-39` 打开时同步做 `connectRedis` 与整段 `SCAN`，任何失败都向上抛。部署文档 `docs/部署-云端生产入口.md:117` 与 nonce-mirror.ts:6 都写“Redis 不可用时只计数、降级为状态快照里的随机数”。
- 失败场景：Redis 维护或故障期间，主实例恰好重启或被换掉 → 新主实例拿到 PG 锁 → 连 Redis 失败 → 退出、锁释放 → 下一个实例重复同一过程 → 控制面整体不可用（设备登记、席位令牌续期、吊销全部停摆），而运行中的主实例在同样的 Redis 故障下却能正常服务。
- 建议：启动时 Redis 不可达按运行期同样降级（`initial` 为空、只计数并告警，后台重连）；或至少把“启动必须连上 Redis”写进部署文档并给出开关。

### RB16A-10 状态库里没有状态行时静默以空状态启动（错指向新库/空库即“撤销全部吊销”）
- 级别：**一般**
- 证据：`pg-state-store.ts:110-115`：`load` 查不到行即 `seq = 0; return null`，控制面按空状态启动；同文件 :125 对解密失败明确写“不静默从空状态开始（那等于撤销全部吊销）”。worker 的 `acquire` 对任何库都会 `CREATE SCHEMA/TABLE IF NOT EXISTS`（worker:58），所以指向一个新库也能顺利启动。文件存储在两代文件都不存在时也返回 null（state-store.ts:91-97），属同一残余；但 PG 形态多了“连接串里库名写错、恢复演练后切到空副本、换了实例但 schema 不同”等现实的错指向路径。
- 失败场景：运维把 `state_store.url` 的库名从 `kwl` 误写成 `kwl_cp`（或从空的新实例恢复）→ 控制面以零租户启动并对外服务 → 网关订阅拿到的吊销集为空，已吊销设备手里仍在有效期内（≤96 小时）的席位令牌重新被网关接受；第一次写入后空状态以 seq 1 落库，原库里的状态也不再被这个部署使用。
- 建议：首次初始化写入一个独立的标记（如 `kwl_cp.meta(initialized_at, deployment)`），或要求显式配置 `state_store.init: true` 才允许空库启动；库里有标记而没有状态行、或部署标识不符时拒绝启动。

## 三、A-11 对象存储接口与诊断包进对象存储（blob-store、support-api）

已核对、未发现问题的部分：
- 键名：`KEY_RE` 禁止前导 `/` 与任何 `..`，字符集不含 `%`，因此在 S3 路径里无法用 `..` 或百分号编码的点段跳出 `prefix/`；`list` 的前缀作为查询参数传给服务端，返回的键再按 `startsWith(prefix)` 过滤。
- SigV4：规范 URI 只编码一次（S3 规则）、查询键与值同一套编码且签名与实际 URL 一致、`x-amz-content-sha256` 为真实摘要、会话令牌入签；配置文件内容经 `read()` 的 `.trim()`，不会把换行带进凭据。
- SSE：每次 `put` 都带加密头，回复里没有对应的 `x-amz-server-side-encryption` 即删除该对象并报错。
- 列举解析：`<Key>` 做了实体反转义，键名字符集不含 `<`，本服务写入的键不会打乱正则切分。

### RB16A-11 诊断包本体改走 `fsBlobStore.get` 后又开始跟随符号链接（复核 S9B-09 的修复被绕开）
- 级别：**一般**
- 证据：改动前 support-api 读包本体用 `readRegular(binPath(...))`，即 `lstatSync(path).isFile()`，注释“只读普通文件（不跟随符号链接；复核 S9B-09）”（support-api/src/index.ts:114-121，仍用于元数据）。改动后运营下载走 `await blobs.get(binKey(...))`（index.ts:338），缺省 `blobs = fsBlobStore(o.dir)`，其 `get` 用的是 `statSync(p).isFile()`（blob-store/src/index.ts:64-71）——`statSync` 跟随符号链接。
- 失败场景：数据目录里的 `SUP-XXXX.bin` 被替换成指向 `/etc/kwl/meter.key`、其他工单或其他服务数据的符号链接（S9B-09 当时防的正是这种情况）→ 有下载权限的运营 `GET /v1/ops/support/SUP-XXXX` 拿到的是链接目标的内容，访问审计还记成“下载诊断包”。清扫用的 `Dirent.isFile()` 不跟随链接，所以这个链接既不会被当成孤立本体删掉，也会一直留着。
- 建议：`fsBlobStore.get` 改用 `lstatSync`（或 `openSync(p, O_RDONLY | O_NOFOLLOW)` 后 `fstat`），与 `readRegular` 同一口径；补一条“包本体是符号链接时下载得 404”的用例（S9B-09 原用例只覆盖元数据）。

### RB16A-12 清扫改成异步后，对象存储一次删除失败即中止整轮清扫，且失败完全静默
- 级别：**一般**
- 证据：`support-api/src/index.ts` 新 `sweep`：到期工单循环里 `await blobs.delete(...)` 抛错会直接让整个 `sweep()` 拒绝，后面的到期工单与孤立本体本轮都不再处理；启动与每小时的调用都是 `void sweep().catch(() => {})`，既不计数也不写错误日志，指标里也没有对应项（A-9 余项新增的 support 指标为空）。
- 失败场景：IaC 给服务的访问密钥漏了 `DeleteObject` 权限，或对象存储某个对象删除持续 5xx → 每一轮清扫都在第一个到期工单处失败退出，所有诊断包本体与元数据都超过“保存 7 天后删除”的承诺，而运营与告警看不到任何信号；唯一的兜底是桶生命周期规则，但代码与启动检查都不核它是否存在。
- 建议：逐条 try/catch，失败计数（`kwl_support_sweep_failures_total`）并 `obs.recordError("support_sweep", …)`；启动时可选地读一次桶生命周期配置（`GET ?lifecycle`），缺失即告警。

### RB16A-13 上传等待对象存储期间，运营删除会被随后写回的元数据“复活”
- 级别：**建议**
- 证据：上传路由在 `await blobs.put(...)` 之前检查 `fresh`，之后无条件 `writeAtomic(metaPath(...), { ...meta, uploaded_at })`（index.ts:292-295）；运营 `DELETE` 只看元数据是否存在，不看 `uploading` 集合（index.ts:332-336）。改动前 `put` 是同步写盘，两者不会交错；现在 S3 写 2 MB 需要数百毫秒到数秒。
- 失败场景：运营在律师上传进行中删除该工单（访问审计记“delete ok”）→ 上传随后完成，包本体写进对象存储，元数据被重新写出且带 `uploaded_at` → 工单与包在“已删除”之后仍然存在，直到 7 天到期。
- 建议：`DELETE` 遇到 `uploading.has(ticket)` 回 409；或上传在写元数据前再读一次元数据，已不存在则删掉刚写的本体并回 410。

## 四、主密钥解封失败“移到一边”（unreadable-data.cjs、main.cjs、onboarding.ts set_aside、residency.json）

已核对、未发现问题的部分：
- 移动顺序：记录文件 → 有账本的工作区 → DPAPI 包裹的主密钥文件最后移；任一步失败即停，主密钥文件仍在，下次启动仍走同一对话框，不会出现“新主密钥 + 旧激活记录”。

- 跨卷：Windows 上 userData = `<LOCALAPPDATA>\KimiWorkLegal\.electron`，与数据根同卷；其他平台二者同在 appData 下。EXDEV 只在人为挂载时出现，且按设计停下交给 IT。

### RB16A-14 “移到一边”漏掉成员待批准记录 `onboarding.json`，待批准设备移完后卡在“等待批准”，进不了“从备份恢复”

### RB16A-15 驻留登记与“说明.txt”对移走内容的描述不完整：明文激活记录被无限期保留，但第 24 行没有登记，说明里写“仍是加密的”
- 级别：**建议**

  - `activation.json` 是明文（residency.json 第 24 行：租户与成员编号、律所显示名、本人显示名、角色），被改名到 `.unreadable-<时刻>/` 后“不删除、由所内 IT 决定”；第 24 行的 `disk` 与生命周期描述没有提到这份副本（只有第 20 行“密钥材料”里顺带写了“同目录里的激活记录”）。
  - unreadable-data.cjs:33 写给 IT 的 `说明.txt`：“这里的案件数据仍是加密的，只有原来的密钥才能打开”——同目录里的 `activation.json`、`onboarding-failed.json` 是明文。

## 七、补充发现（复查第一、二节时追加）

### RB16A-16 席位密钥按受众拆分后，验签侧没有把“密钥编号 ↔ 受众”绑在一起，拆分的隔离效果取决于运维把哪些公钥放进各服务的公钥表
- 级别：**建议**
- 证据：`packages/seat-token/src/index.ts:55-80` `verifySeatToken` 只按 `kid` 在公钥表里找公钥，再按 `aud` 声明判受众，不核“这个 kid 是不是本受众的密钥”；cloud-serve 对 `seat_keys_file` 只核“是公钥”（`pubMap`），不按角色核 kid 前缀；而签名服务 `GET /v1/public-keys` 与控制面 `publicKeys.seat` 给出的恰恰是“全部席位公钥（通用 + 各受众）”（signer.ts:93-104、server.ts:272），最顺手的部署做法就是把这张全表发给每个服务。签名服务一侧已经强制 kid 形如 `seat-<受众>-<环境>-<编号>`（cloud-serve cp-signer 分支 `kidRe`），验签侧却没有用上。
- 失败场景：通知受众密钥 `seat-notify-prod-…` 泄露（拆分要防的正是这种情形），而网关的公钥表是全表 → 攻击者用通知密钥签一张**不带 aud** 的通用席位令牌，网关按 kid 找到公钥、验签通过、`aud` 为空按通用令牌接受——“一把受众密钥泄露不牵连其他服务”不成立。
- 建议：cloud-serve 按角色核 `seat_keys_file` 的 kid：gateway/search/dist 只许 `seat-<env>-*`，support/notify/relay 只许各自的 `seat-<受众>-<env>-*`（回落期可另许通用 kid）；或在 `verifySeatToken` 增加 `allowedKids` 选项由各服务传入。

### RB16A-17 Redis 命令没有超时，Redis 挂起（连接在、不回复）时待回复队列无限增长且不计失败
- 级别：**一般**
- 证据：`services/control-plane/src/resp.ts:118-125` `command()` 把每个请求压进 `pending` 数组，只有收到回复或连接 `close/error` 才出队；没有单条超时，也没有 TCP keepalive。`nonce-mirror.ts:57-72` 的 `record` 只看 `c.closed`，连接未断即继续发送；失败计数只在 Promise 被拒时加。
- 失败场景：Redis 主节点卡死或网络单向丢包（TCP 不断开）→ 控制面每个通过验签的设备请求都往 `pending` 里加一项、永不释放，内存持续增长；`kwl_cp_nonce_mirror_total{result="failed"}` 保持为 0，监控看不出镜像已失效；换主实例时读回的随机数是挂起之前的，等于重放窗口回到了没有 Redis 时的状态，而运维以为它还在工作。
- 建议：`command()` 设超时（如 2 秒），超时即销毁连接、拒绝全部待回复项并计失败；`pending` 设上限，超过即不再发送并计失败；打开 TCP keepalive。
