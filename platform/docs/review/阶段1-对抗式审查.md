## 问题清单

### R-01【阻断】F6：超时路径（以及失败、正常结束）不撤销任务令牌；注释与测试名不副实

- **位置**：`apps/agent-host/src/host.ts:234-242`；`packages/kernel/src/executor/agent-host-manager.ts:317, 325-326, 370-384, 388-392`；`packages/kernel/src/index.ts:135-139`；`packages/kernel/src/executor/executor.ts:846-870`
- **问题**：
  1. 管理器把宿主超时设为 `timeoutMs - 5_000`（manager:317），宿主自身的超时**总是先于**管理器定时器触发。宿主超时后只发 `done{status:"timed_out"}` 并 `exit(124)`；管理器在 `exit` 回调里 `clearTimeout`，于是 `terminate()` 永远不会执行，`revokeRun` 不会被调用。
  2. 执行器 `markTerminal("timed_out" | "failed")` 不撤销令牌；`index.ts` 的撤销集只在**内核重启时**按 `cancelled/timed_out/expired` 重建。运行期间只有“用户取消 API”（api/index.ts:767）与“管理器自身定时器”两条路径会撤销。
  3. 令牌 TTL 固定 1800 s（manager:325-326），远长于任务 600 s 预算；`failed / succeeded / partial` 终态之后令牌仍可用于模型代理与工具端点。
  4. `index.ts:134` 注释写“取消、超时、过期的任务令牌一律撤销”，与运行时行为不符。
- **证据**：附录 B「self-timeout」——用真实 `createLocalAgentClient` 拉起按真实宿主超时协议说话的假宿主，终态 `timed_out`，`revokeRun` 调用记录为空。
- **为什么违反方案**：第 04 篇 §9 F6 修复要求“进程树终止 + **先吊销能力令牌**”；§8 “失去租约后不得读新材料、调上游、写产物”；第 02 篇 §9.2 “失败即拒绝”。现有测试《F6 超时：管理器超时同样先撤销令牌再杀进程组》用的假宿主不会自行超时，只覆盖了生产中几乎走不到的管理器定时器分支。
- **建议**：把撤销放到 Run/Attempt 的终态迁移里（`stepSettle`、`markTerminal`、`markReconciling` 及管理器 `finalize` 都调用 `revokeRun`，按 attempt 撤销）；或者改由内核负责超时，宿主只上报；令牌 TTL 取任务 deadline；测试要覆盖“真实宿主自行超时”这条路径。

### R-02【重要】F6：宿主先退出时 `killTree` 是死代码；Windows 的 `taskkill /T` 清不掉孤儿进程；`setsid` 可以逃出进程组

- **位置**：`agent-host-manager.ts:94-113`（守卫 `if (child.exitCode !== null || child.signalCode !== null || !child.pid) return;`），`:376-384`（exit 回调里的 `killTree(child)`），`:399`（宽限 5 s 后的 `killTree`）
- **问题**：
  1. exit 回调写着“清理同组残留”，但宿主一旦退出，`exitCode` 就不为 null，`killTree` 在第一行直接返回，同组的孙进程不会被杀。真实宿主收到 cancel 后会在 5 s 内自行 `shutdown → process.exit`，所以 5 s 宽限定时器触发时同样直接返回。
  2. 测试《孙进程不残留》让假宿主忽略 SIGTERM、永不退出，正好绕开了上面这条路径。
  3. Windows：`detached:false`，没有作业对象（Job Object）。`taskkill /T` 按“活着的父进程”遍历进程树，父进程退出后留下的孤儿找不到。`spawn("taskkill")` 的失败以异步 `'error'` 事件抛出，try/catch 接不住；ChildProcess 又没有挂 `'error'` 监听器，结果是未捕获异常，内核进程退出。
  4. POSIX：孙进程只要 `setsid` 或以 `detached` 方式启动，就会离开进程组。方案说的“进程树”在这里退化成了“进程组”。
- **证据**：附录 B「exit-with-child」「cancel-fast-exit」——宿主正常结束或快速响应取消之后，孙进程仍然存活。
- **为什么违反方案**：第 04 篇 §9 F6“进程树终止”；第 02 篇 §9.10“作业对象与看门狗”。
- **建议**：POSIX 记录 pgid，宿主退出后仍按 `-pgid` 发 SIGKILL（去掉 exitCode 守卫）；Linux 加 cgroup 或 `PR_SET_CHILD_SUBREAPER`；Windows 让宿主加入 `KILL_ON_JOB_CLOSE` 作业对象，并给 taskkill 挂 `'error'` 监听；补测试“宿主快速退出、遗留孙进程”。

### R-03【重要】F1：结束原因缺失或未知时判为成功，与函数自己的注释（“任何缺失或未知都不是成功”）相反

- **位置**：`packages/domain/src/states.ts:125, 161-167`；`apps/agent-host/src/host.ts:207-208`；`agent-host-manager.ts:207`
- **问题**：截断判定用的是黑名单。`finishReason` 为 `undefined`（宿主从未收到 `turn.step.completed`，或 `finish_reason:null`）、`"other"`（Kimi Code 对未知 provider 原因的归一化值，见 vendor `index.mjs:138025-138040`）、`"interrupted"`、`"error"`、`"truncated"` 时，只要 `turnEndReason=completed` 且有成果，结果就是 `succeeded`。真实引擎的归一化链是：原始 `length` → provider 层 `truncated` → `normalizeFinishReason` → `max_tokens`（`index.mjs:208783-208788`）。`max_tokens` 恰好在黑名单里，所以长度截断能被识别；但流中断、缺 finish_reason 等“未知”情形不能。
- **证据**：附录 A [F1]：`finishReason=undefined/other/interrupted/error/truncated` 的结果都是 `{"outcome":"succeeded"}`。
- **为什么违反方案**：第 04 篇 §8“**未知状态**、缺成果、截断、超时都不能成功”；§2 能力账本“流中断、错误码、length 截断、usage 缺失均有明确终态”。
- **建议**：改成白名单，只有 `finishReason ∈ {end_turn, stop, completed}` 才可能成功，缺失或未知一律按失败（或在有成果时判 partial）；测试改用真实引擎的归一化值（`max_tokens`/`other`/缺失），不要再用宿主实际不会发送的 `length`。

### R-04【重要】F1/F5：恢复路径缺 `agent.outcome` 记录时，默认按 succeeded 结算

- **位置**：`packages/kernel/src/executor/executor.ts:739-745`
- **问题**：`const status = outcome ? ...status : "succeeded"`。缺记录时直接视为成功；查询没有按 attempt 过滤也没有排序，可能读到旧尝试的 outcome；结算前也不复核已入库成果是否存在、hash 是否一致。
- **为什么违反方案**：第 04 篇 §8“未知状态不能成功”“恢复时重新检查权限与输入版本”。现有测试《F6 检查点》只覆盖了“outcome=succeeded 已写入”这一条正路径。
- **建议**：把 outcome 与成果 hash 写进 `agent_store_draft` 检查点的 `result_json`（与成果入库同一事务），恢复时据此结算；缺记录时转 reconciling 或 failed。

### R-05【重要】终态迁移不是 CAS：`markTerminal` 能改写其他终态；`queue.recover` 绕过状态机

- **位置**：`executor.ts:846-860`（`WHERE run_id = ? AND status NOT IN ('succeeded','partial')`）；`packages/kernel/src/queue.ts:86`；`packages/domain/src/states.ts:73-106`
- **问题**：`cancelled / timed_out / expired / failed / reconciling` 都可能被 `markTerminal` 改写成另一个终态。例如 API 已置 `cancelled`，执行器随后因别的异常 `markTerminal("failed")`，最终就成了 `failed`；`reconciling` 也会被覆盖为 `failed`。`canTransitionRun` 只在 `setStatus` 里用到。`queue.recover` 直接把 `running` 改成 `queued`，而状态机不允许 `running → queued`，方案要求经过 `RECOVERING`。
- **为什么违反方案**：第 04 篇 §8“终态转换用 CAS”；`states.ts:65` 自己写的“终态进入后不再迁移”。
- **建议**：`markTerminal` 的 WHERE 改为“允许迁到目标态的源状态集合”（由 `RUN_TRANSITIONS` 生成）并带 `status_version` 期望值；`recover` 先置 `recovering`，再按检查点决定 running、reconciling 还是 failed。

### R-06【重要】F6：没有尝试级 fencing，旧尝试的令牌在新尝试开始后仍能调用副作用工具

- **位置**：`packages/kernel/src/local-server.ts:105-150`（`canRecord` 只校验 `(aid, rid)` 存在，约 :141 的 `UPDATE ... SET status='pending', attempt_id = ?` 会把行改记到调用方的尝试名下）；`index.ts:135-139`（撤销粒度只到 rid）
- **问题**：`attempts.fence_token` 没有任何端点检查。崩溃恢复后的旧宿主、Windows 上的孤儿、R-01 中没被撤销的令牌，都可以带着旧 aid 继续调用工具、写 outbox。幂等键里不含尝试，新旧尝试共享同一结果。测试《F6 outbox》同时插入两个 `running` 尝试，并让旧尝试成功调用，等于把“没有 fencing”当成了预期行为来验证。
- **为什么违反方案**：第 04 篇 §8“每次尝试获得短租约与递增纪元；失去租约后不得……写产物……网关、文件 broker 与提交点都检查纪元”。
- **建议**：令牌带上 attempt 与 fence；工具端点和模型代理都比对当前 `attempts.status='running'` 且 `fence_token` 一致；新尝试开始时把旧尝试置为 interrupted，并按 aid 撤销它的令牌。

### R-07【一般】outbox 把异常一律当作“确定失败”并允许重放；pending 没有对账出口

- **位置**：`local-server.ts:126-160`；`executor.ts:875-889`
- **问题**：`invokeTool` 抛异常就记 `failed`，下一次同参数调用会重新执行。但抛异常不等于没有副作用，比如已写入新版本之后才抛错。`reconciling` 没有任何 API 或界面出口，预留点数会一直被占用。同参数的并行调用中，后到的那个会收到“结果不明（转人工对账）”，并且 Run 不会真的进入 reconciling，提示有误导。
- **为什么违反方案**：第 04 篇 §8“副作用结果不明进入人工对账，不盲目重发”。
- **建议**：本地工具的副作用与 outbox 状态更新放在同一个 DB 事务里，只有回滚了才算确定失败；补一个对账 API（标记“已生效/未生效”），并实现 `reconciling → running/failed` 的迁移。

### R-08【重要】F3：schema hash 自检是同源自比，在生产接线中永远不会失败

- **位置**：`packages/kernel/src/tools/registry.ts:301-325`（`legalToolManifests` 用 `TOOLS[i].inputSchema` 在运行时计算 hash）；`local-server.ts:95`（又用同一个 `TOOLS` 去比对）
- **问题**：清单不是独立制品，而是从同一份工具定义现场派生出来的，所以 hash 恒等。副作用类别和工具实现写在同一个对象里：新增一个写工具，只要声明 `sideEffect:"read"`，默认档就会自动批准。注释所说的“schema 变了而清单没跟着改，就视为另一个工具”在生产中不可能发生。`authorize.test.ts:59` 是手工传入一个不同的 schema，证明的是函数本身，不是接线。
- **为什么违反方案**：第 04 篇 §9 F3“清单含 schema hash 与副作用类别”，本意是可审、可锁定的清单；第 02 篇 §9.8 插件、技能与 MCP 准入。
- **建议**：增加一份独立的签名锁文件（如 `tool-manifest.lock.json`，含 id、version、sideEffect、resource、purposes、schemaHash），评审后提交并随包签名；运行时用 `TOOLS` 计算的 hash 与锁文件比对；CI 规定 schema 或副作用变更必须同步更新锁文件。

### R-09【重要】F3：“动作 + 资源 + 用途”没有绑定到实际调用；工具端点也不独立执行宿主策略

- **位置**：`agent-host-manager.ts:143-156`；`apps/agent-host/src/host.ts:172-182`；`local-server.ts:221` 起（tools/call）
- **问题**：
  1. `authorizeToolCall` 只拿到 toolName。`purpose` 写死为 `"legal_analysis"`，而清单里所有工具的 purposes 也只有这一项，用途维度恒为真。
  2. 宿主协议不传 action 和参数，`argsHash` 恒为 `{}` 的 hash，`requestedMatterId` 永远不提供，`cross_matter` 分支在生产路径上是死代码；批准结果也不与 toolCallId 或参数绑定。
  3. MCP `tools/call` 端点不调用 `authorizeToolCall`，只依赖白名单、令牌 scope 和工具内部检查。如果引擎没有发起审批（上游放行），宿主策略就根本没被调用。
- **为什么违反方案**：第 04 篇 §1.2 第 2 条“宿主策略裁决每一次工具调用”、第 6 条“每处独立校验权限”；第 02 篇 §9.2 强制点①“工具、参数摘要、对象、目的地……”。
- **建议**：宿主协议补上参数（或规范化摘要）和 toolCallId，裁决与 argsHash 绑定；用途取自 Run 意图；tools/call 端点按令牌 claims 再执行一次 `authorizeToolCall`（独立强制），并校验参数里的 matter、document 归属。

### R-10【一般】若干“失败开放”的默认值

- `local-server.ts:108` `manifest?.sideEffect ?? "read"`：没有清单时按读处理，绕过 outbox；应直接拒绝。
- `packages/host-policy/src/authorize.ts:65-67`：`exec` 在 default/auto 档自动批准，不检查执行域是否可用。第 02 篇 §9.10 规定“W 不可用时，代码执行关闭”。
- `host.ts:72`：`trustedHashes` 缺省时直接跳过校验。应要求至少包含 agentFile、config.toml、mcp.json 三项，否则拒绝启动，体现“失败即拒绝”。

### R-11【重要】F2：检查之后仍按字符串路径重新打开，写入和删除在复核之前就已生效

- **位置**：`packages/file-broker/src/broker.ts:220-264`（`walk` 之后 `open(loc.real, …O_TRUNC…)`，再 `recheck`）；`:379-400`（mkdir）；`:402-408`（`rm(loc.real, {recursive:true})`）
- **问题**：
  1. `O_NOFOLLOW` 只保护最后一级。父级目录若在窗口期内被换成链接，`O_TRUNC/O_CREAT` 已经在区域外截断或创建了文件，`recheck` 只能事后报错。
  2. 写入既有文件时，`nlink` 检查在 `O_TRUNC` 之前，硬链接竞态可以截断区域外的 inode。
  3. `remove()` 先 `walk` 再按字符串 `rm -r`，竞态下可以递归删除区域外的目录。
  4. Windows 没有 `O_NOFOLLOW`，最后一级同样存在窗口。
  5. 代码注释自承这是“如实残余”，而方案 §4.4 明文要求“检查与使用之间**不按字符串重新打开**”。
- **为什么违反方案**：第 04 篇 §4.4；第 02 篇 §9.2 强制点③“路径以句柄与对象 ID 校验”。当前 SDK 宿主不向模型开放写类工具，所以这是潜在问题；但这正是“开放新工具之前必须修复”的前提条件。
- **建议**：写入改为“同目录临时文件 `O_EXCL` 创建 → fstat 核验 → rename 原子替换”，不再用 `O_TRUNC` 打开既有路径；删除改为先移入区域内回收目录，复核身份后再删；Windows 用原生扩展（`FILE_FLAG_OPEN_REPARSE_POINT` + `GetFinalPathNameByHandle` 校验句柄真实路径）；中期按第 04 篇 §4.1 的“OverlayFs 快照 + broker 校验后提交”实现。做不到的部分在对外口径里把 F2 如实标为“部分修复”。

### R-12【阻断】F2/F7：只读文件按“名字”而非“对象身份”保护，在 macOS 上可用同名别名删除并重建 `mcp.json`

- **位置**：`broker.ts:125-129`（`isProtected` 按分量名比较）、`:176`、`:402-408`；`packages/file-broker/src/paths.ts:80-83`（`sameComponent` 用 `toLowerCase()`）
- **问题**：文件系统判断“同一文件”的规则与 JS `toLowerCase()` 不一致。
  - **(a) macOS（已实测）**：默认的不区分大小写 APFS 按 Unicode case folding 比较，`ſ`(U+017F) 折叠为 `s`。`mcp.jſon` 与 `mcp.json` 是同一个 inode，但 `'ſ'.toLowerCase()` 仍是 `'ſ'`，broker 不认为它受保护。0444 能挡住别名“写”（EACCES），挡不住别名“删 + 重建”，因为 unlink 只需要目录写权限。重建后，引擎按 `mcp.json` 读到的就是攻击者内容（附录 A）。
  - **(b) Windows（静态推断，未在 Windows 实测）**：NTFS upcase 表把 `ı`(U+0131) 映射为 `I`、`ſ` 映射为 `S`，因此 `confıg.toml`、`mcp.jſon` 都会命中原文件；系统盘默认生成 8.3 短名，`CONFIG~1.TOM`、`MCP~1.JSO` 同样命中；libuv 的 unlink 会先清除只读属性再删除。
  - **(c) 父目录删除（已实测）**：`remove()` 只检查目标本身是否受保护，删除受保护文件的父目录会把它一起删掉。生产布局里这两个文件位于 homeDir 根下，父目录是区域根、不可删，所以当前布局不受影响；但 broker 承诺的“删除一律 EPERM”不成立。
- **证据**：附录 A [F2/F7] 各行。
- **为什么违反方案**：第 04 篇 §4.4 明确要求处理“大小写变体”；F7 缺陷原文是“同用户进程可替换”。当前 SDK 宿主不向模型开放文件写工具，所以这是潜在问题；但阶段 2 一旦经 broker 开放 Write/Edit/Bash，Agent 就能改写自己的 MCP 配置（新增任意 MCP 服务端点）。按第 06 篇 §8 第 2 条，这必须在开放任何新工具之前修复，因此定为阻断。
- **建议**：按对象身份保护：构造时记录受保护文件的 `(dev, ino)`，所有写、删、建目录操作在 lstat 或打开之后比对身份，删除目录时检查子树内是否含受保护身份；Windows 拒绝含 `~数字` 的短名分量，或用 `GetLongPathNameW` 规范化后再比较；名字比较改用 Unicode 默认大小写折叠（`toLowerCase` 不等价）。根本的做法是把可信配置移出可写区（见 R-13）。

### R-13【重要】F7：“只读挂载”实际是 chmod，没有消除“同用户进程可替换”；hash 只在启动时校验一次

- **位置**：`agent-host-manager.ts:240-241, 290-294, 217-226`；`apps/agent-host/src/config-template.ts:44-51`；`host.ts:71-83, 109-123, 161-166`
- **问题**：
  1. trusted 目录 0555、文件 0444 只是属主随时可以 chmod 回去的权限位。F7 缺陷描述里的威胁本身就是“同用户进程”，它可以先 `chmod u+w` 再替换。
  2. config.toml 和 mcp.json 仍在可写 homeDir 中，unlink 加重建不受 0444 限制。
  3. 宿主在启动时校验 hash，但引擎之后（createSession、配置服务、MCP 连接）还会按路径重新读取，存在 TOCTOU；运行期间也没有复核。
  4. 测试《F7 可信配置在只读目录》用 `!trustedDir.startsWith(homeDir)` 判断“不在 homeDir 内”，用的正是 F2 要淘汰的字符串前缀判定；没有测试运行中替换、chmod 回写等情形。
- **为什么违反方案**：第 04 篇 §9 F7 的缺陷是“同用户进程可替换”，修复要求是“可信配置只读挂载，与可写状态分区”。
- **建议**：宿主读取一次可信内容后，通过种子注入的只读 IHostFileSystem 视图（返回内存内容）交给引擎，不再按路径重读；或者打补丁让引擎从可信目录或内存读取配置，并登记到 ZP 台账；OS 层面，Windows 用独立低权限用户加 ACL，macOS 用 Seatbelt 或只读挂载。对外口径如实写“权限位保护，非只读挂载”。

### R-14【重要】F4：只修正了口径，缺陷本身没有修；源码扫描测试没有覆盖真实的出网面

- **位置**：`host.ts:85-100`；`packages/kernel/test/v9-defects.test.ts:429-441`
- **问题**：
  1. 在运行时设置 `HTTP(S)_PROXY` 对 `node:http/https`、`net`、显式 dispatcher、原生 socket 都无效：Node 内置的环境变量代理只在启动时按 `NODE_USE_ENV_PROXY` / `--use-env-proxy` 生效，本宿主没有启用。
  2. 同一进程里运行着 vendored Kimi Code SDK（约 22 万行），其中有大量网络代码。
  3. F4 测试只扫描 `apps/agent-host/src` 下的 3 个文件，还断言了一段注释文字的存在，不扫 vendor 和依赖，与测试名“无直连网络 API”不符。
  4. 出站闸门和“执行域无网”都还没实现（属于后续阶段）。
- **证据**：附录 A [F4]：按宿主同样的设置（全局 dispatcher 指向不存在的 socket、代理变量指向 127.0.0.1:9）之后，`fetch` 被拦下，`node:http.get` 仍然直连成功（`direct-ok`）。
- **为什么违反方案**：第 04 篇 §1.2 第 3 条“出站闸门是唯一出口”；§5.1“唯一出口的强度如实分级”。F4 只能判“部分修复（口径修正）”。
- **建议**：宿主用 `--use-env-proxy` 启动（或设 `NODE_USE_ENV_PROXY=1`），并把代理指向闸门而不是黑洞；在 OS 层由出站规则强制（第 04 篇 §5.1 第⑤级）；CI 扫描覆盖 vendor 与依赖；把测试换成运行时探针：在宿主进程内尝试 http、net 直连本机端口，应当失败。

### R-15【一般】F1/F5：管理器在 `exit` 而不是 `close` 时裁定终态，可能丢掉尾部的 done/artifact 记录

- **位置**：`agent-host-manager.ts:346-384`
- **问题**：Node 文档说明，`'exit'` 触发时子进程的 stdio 可能还没有读完。`finalize` 在 `'exit'` 里执行，晚到的 `done`/`artifact` 行会被忽略；最后一行如果没有换行，会一直留在 `buf` 里不被处理。结果是成功的任务偶发被判为 `missing_completion_record`。这是失败关闭，不会放过错误，但会造成误报和重跑。
- **建议**：改在 `'close'` 事件里 finalize，并处理残留的 `buf`。

### R-16【一般】迁移 0009 的细节

- **位置**：`packages/kernel/src/migrations/0009_v9_run_states.sql:4, 58, 84-86`；`packages/kernel/src/db.ts:46-48`
- **问题**：
  1. 注释写“结束后 foreign_key_check”，文件里实际没有 `PRAGMA foreign_key_check`。
  2. `INSERT INTO attempts_new SELECT * FROM attempts` 依赖列的顺序。
  3. `schema_migrations` 记录是在迁移 COMMIT 之后单独写入的（既有模式）。如果两步之间崩溃，重跑会因为 `runs_new` 已被改名而失败。
- **建议**：补上 `foreign_key_check`（有结果即 ROLLBACK）；显式列出列名；把 `schema_migrations` 的写入放进迁移事务。

## 问题清单（续）

### R-09 补充【重要】清单只按“引擎工具名”匹配，没有绑定服务端身份

- **位置**：`packages/host-policy/src/manifest.ts:92-98, 123-139`；`agent-host-manager.ts:143-144`
- **问题**：宿主审批请求只带 `toolName`（如 `mcp__legal__law_get_version`），不带 MCP 服务端 URL、进程或证书；清单查找也只按这个名字。如果按 R-12 的方式改写了 `mcp.json`，就能让名为 `legal` 的服务指向任意端点，宿主策略照样按“读工具”批准。`requestedMatterId`、`preauthorized` 在非测试代码中没有任何调用方（`grep` 结果为空）。
- **建议**：审批请求带上服务端标识（配置中的固定 URL 或管道名），并与可信配置中登记的端点比对；对 F3 清单做“工具名 + 服务端身份”双键匹配。

### R-18【一般】红队泄漏检查只看截断的预览，不检查真实成果

- **位置**：`packages/kernel/test/redteam.test.ts:145` 附近（`const leaked = FORBIDDEN_MARKERS.some((m) => task!.previewText.includes(m) || JSON.stringify(task!.events).includes(m))`）
- **问题**：F5 之后真正的交付物是 `task.artifacts[].bytes`（`final_message.md`），而 `leaked` 只检查 `previewText`（上限 20,000 字符）和事件（delta 截 2,000、text 截 4,000）。超出预览上限或落在截断之外的泄漏标记不会被发现。
- **为什么违反方案**：第 04 篇 §10 每版红队、§1.2 第 5 条的取证要求以真实交付物为准。
- **建议**：`leaked` 检查加入全部 artifacts 的全文。

### R-19【一般】Windows 路径语义的残余缺口（静态推断，未在 Windows 实测）

- **位置**：`packages/file-broker/src/paths.ts:29-77`；`broker.ts:184-206`
- **问题**：
  1. 没有通用的重解析点检测。libuv 只把 symlink、junction（及 AppExecLink）报告为链接，其他名称代理类重解析标签（如 WCI、LX_SYMLINK、云文件占位符）都按普通文件处理。
  2. 不检测网络盘、SUBST 盘符。
  3. 路径长度上限是 4096，不拒绝超过 260 的路径，Office 和资源管理器打不开这类路径。
  4. 不处理 8.3 短名（见 R-12）。
  5. 现有 broker 测试只在 macOS 上运行过；Windows 语义只测了语法层（`splitAbsolute`），没有在真实 NTFS 上测试 junction 与短名。
- **为什么违反方案**：第 04 篇 §4.4 明确列出“重解析点、UNC、网络盘、大小写变体、保留设备名、长路径”。
- **建议**：用 `GetFileInformationByHandleEx(FileAttributeTagInfo)` 判断 `FILE_ATTRIBUTE_REPARSE_POINT`；用 `GetDriveTypeW` 拒绝 `DRIVE_REMOTE`；拒绝含 `~数字` 的分量，或先用 `GetLongPathNameW` 规范化；总长超过 259 时拒绝；在 Windows CI 上跑 broker 测试。

### R-20【一般】如实口径与 partial 语义

- **位置**：`states.ts:111-112`；`executor.ts`（`stepSettle` 中 `points_charged = points_reserved`）；`apps/desktop/src/pages/RunView.tsx`（`run.partial`、`agent.task_started` 文案）
- **问题**：
  1. 注释规定 partial 必须“剩余部分列明”，但因截断产生的 partial 没有剩余清单；界面显示“部分完成（剩余部分见说明）”，说明并不存在。
  2. partial 与 succeeded 一样全额扣点。
  3. 界面文案“Agent worker 已启动（隔离进程）”：宿主与内核同用户运行、没有 OS 沙箱，这句话高估了隔离强度。
- **为什么违反方案**：第 02 篇 §9.10“不写笼统表述、隔离强度如实标注”，§12 对外口径。
- **建议**：partial 必须附带“完成/未完成清单”（截断时至少写明“回答在第 N 步被长度上限截断”）；partial 计费按方案第 05 篇另行规定；文案改为“Agent 宿主已启动（独立进程，非系统沙箱）”。
