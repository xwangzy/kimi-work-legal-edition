## 1. 开通与成员入组协议

已跑测试：`node --test services/control-plane/test/onboarding.test.ts`（5/5 通过）、`node --test packages/kernel/test/onboarding.test.ts`（1/1 通过）。现有用例只覆盖正常路径与“未出示认领不能登记根”，下列发现均不在现有用例覆盖之内。

### A-01【阻断】批准时不绑定管理员核对过的公钥：控制面可在“列表”与“批准”之间换掉申请内容，核对码形同虚设

- 证据：
  - `apps/desktop/src/components/MembersAdmin.tsx:147`：批准确认框只调用 `members.approve(r.id)`；`apps/desktop/src/api.ts:943` 只传 `join_request_id`。
  - `packages/kernel/src/services/onboarding.ts:417-449`：`approve()` 在批准时**重新** `GET /v1/join-requests`，取控制面**此刻**返回的 `device_id / sign_pub / enc_pub / member_slug` 签证书；核对码只在 `list()`（:404-412）里算给界面看，批准时既不重算、也不与界面显示过的核对码比对。
  - `onboarding.ts:424-427`：`local` 取的是 `memberships` 里**任意**成员行（包括创始管理员本人与已入组成员），并非“本机发出、尚未入组的邀请”；证书角色取该行的角色。
- 推演：设计 §5 写明“控制面被攻破：可以把申请里的公钥换掉——由核对码挡住”。现实现下，被攻破（或被内部人员操纵）的控制面无需任何算力即可绕过：列表时返回成员真实公钥（两边核对码一致，管理员点“已核对一致，批准”），批准这一刻的 `GET` 返回同一申请编号、但公钥换成攻击者的，并可把 `member_slug` 改成创始管理员的标识——管理员本机即用律所根为攻击者公钥签出 `memberId = 创始管理员、role = admin` 的设备证书，控制面（已被攻破）放行。攻击者设备随后以律所根签发的管理员证书出现在律所目录中：可被加入团队事项、接收包裹给它的事项密钥，可做管理员设备签名的放宽类操作（受门限约束的除外）。这直接打穿 v9 信任模型“控制面只能收紧、不能往律所里加人”。
- 建议修法：
  1. 批准请求必须携带界面上显示过的核对码（或 `sha256(tid‖device_id‖sign_pub‖enc_pub‖member_slug‖role)` 全长摘要），内核用批准时取到的条目重算，不一致即拒绝；更稳妥的是 `list()` 时把条目快照存在内核内存/账本里，`approve()` 只用快照、不再向控制面取。
  2. `member_slug` 只接受“本机发出、未消费、未作废的邀请”：`invite()` 时在本机记下 `activation_id ↔ member_slug ↔ role`（现在只写了 users/memberships），批准时三者须与申请一致；已有活动设备的成员不得经此路径再签（换机走专门流程）。
  3. 角色以本机邀请记录为准（现已如此），但须同时核对申请里的 `role` 与之相同，否则拒绝并提示。
- 建议补的测试（kernel 单元测试，注入假 `call`）：① 第一次 `GET` 返回真公钥、第二次返回另一把公钥 → `approve` 必须拒绝；② 申请 `member_slug` 指向创始管理员或已入组成员 → 拒绝；③ 申请 `role` 与本机邀请不一致 → 拒绝；④ 同一邀请已批准过一次后再批准 → 拒绝。

### A-02【重要】核对码只有 40 bit，且设备编号可由控制面任意选取：离线“第二原像”只需哈希运算

- 证据：`packages/firm-trust/src/onboarding.ts:56-66`（`readUIntBE(0,5)` 取 40 bit）；成员端设备编号是确定的 `dev_${firmSlug}_${memberSlug}`（`kernel/src/services/onboarding.ts:234`），但管理员端 `approve()` 与控制面 `/v1/join-requests`（`services/control-plane/src/server.ts` 入组申请段）都只按 `DEVICE_ID_PATTERN = /^[A-Za-z0-9_-]{1,128}$/`（`packages/keys/src/device.ts:18`）校验，不要求等于 `dev_<律所>_<成员>`。
- 推演：即便修好 A-01，被攻破的控制面仍可在成员提交申请后、管理员批准前，固定自己的两把公钥、只变动 `device_id` 字符串去撞 40 bit 核对码——每次尝试只是一次 SHA-256，单张 GPU 量级为分钟级；若 `device_id` 被钉死，改为变动 X25519 加密公钥（每次一次标量乘），2^40 次在云上也是小时到天级，仍落在“7 天待批准”窗口之内。文件注释“40 bit 抵御在线替换足够”只对“在线逐次猜测”成立，对“看到真申请后离线碾磨”不成立（没有承诺—揭示环节）。
- 建议修法（任选其一，推荐 3）：
  1. 两端与控制面都强制 `device_id === dev_<律所>_<成员>`，消除最廉价的碾磨维度；
  2. 核对码加长到 ≥ 64 bit（如 20 位数字分 5 组），或改为对“成员公钥摘要”的承诺—揭示（成员先提交承诺、管理员确认收到后再揭示）；
  3. **邀请码后缀由管理员本机生成、不经控制面**：管理员内核在控制面返回的 20 位码后附加本机随机段 S（例如 8 位 Crockford，40 bit，再加律所根指纹段）；成员内核用由 S 派生的密钥对入组申请做 MAC，管理员本机核 MAC——控制面不知 S，既不能换公钥，也无从碾磨；同一段里的律所根指纹还可同时消除 A-03 的首次信任。
- 建议补的测试：① 申请 `device_id` 不等于 `dev_<律所>_<成员>` → 控制面 400、管理员内核拒绝；② 核对码位数断言（防回退）；③ 若采用方案 3：控制面改动申请任一字段 → 管理员端 MAC 失败。

### A-03【重要】成员首次信任律所根且不阻断：被攻破的控制面可绕开管理员“批准”，并把恢复托管公钥换成自己的

- 证据：`kernel/src/services/onboarding.ts:293-316`：证书、律所公钥包只按**控制面同一应答里给的** `root_public_key_pem` 验；律所核对码只在批准后的返回值与“设置 · 本机与安全”里显示（`MembersAdmin.tsx:190` 文案“同事加入后……应显示同一串数字”），不要求核对通过才完成入组；`devices.ts applyStagedJoin` 随即把该根与 `recovery_public_key_pem` 写入 `firm_identity`。偏离登记 D-97 已如实写“首次信任”。
- 推演：控制面无需管理员参与，即可对成员的 `fetch` 回 `approved` + 自造根签发的证书（成员真实公钥）+ 自造根签名的公钥包（攻击者的恢复托管公钥）。成员机全部核验通过，此后新建事项的事项密钥同时包裹给攻击者的恢复托管公钥。内容本身在本机，但一旦包裹密钥与密文经中继（第 11/12 批团队共享）或将来的云端备份（第 14 批设计）到达云端，即可解密。与管理员核对律所核对码是唯一防线，且在使用之后。D-97 登记了“首次信任”，但未登记“恢复托管公钥同样随之首次信任，后果是事项密钥被包裹给第三方”。
- 建议修法：采用 A-02 方案 3，把律所根指纹段放进邀请码（管理员本机计算、不经控制面），成员内核在写入前比对，不符即拒；若暂不改码格式，至少在“取回证书”后、写 `activation.json` 前设一个**必须完成**的步骤：成员输入管理员念出的律所核对码（或勾选“已与管理员核对一致”并留痕），未完成不进入正常模式；D-97 补记恢复托管公钥的后果。
- 建议补的测试：kernel 测试中假 relay 返回“另一把根签发的证书 + 另一把根签名的公钥包” → 有指纹段时必须拒绝；无指纹段时必须停在“待核对律所核对码”而不是直接重启进入正常模式。

### A-04【重要】已认领未消费的码可无限次再兑换，每次换发新凭据并作废旧凭据

- 证据：`server.ts` `activationLive()` 把 `claimed` 视为可兑换；`/v1/activation/redeem` 每次都重置 `claim_hash`、`claimed_at`，没有次数或时间窗；`ActivationRecord` 注释写“同一码在消费前可再兑换一次”，设计 §4.1 写“原子地标记已认领”。
- 推演：
  - 创始码：合法创始设备兑换后到根公钥登记成功之前（正常几秒；离线、闸门或控制面故障时可达认领 7 天有效期），任何拿到码的人（运营发码渠道、截图、转发）再兑换即得新凭据，可先于合法设备登记自己的根——A-05 之外又一条“租户抢注”回路；合法设备登记时得到 `claim_invalid`。
  - 邀请码：泄露者再兑换后，合法成员的 `fetch` 永久 403（被锁死，只能重发邀请）；待管理员拒绝或 7 天过期后，泄露者可提交自己的申请，此时只剩核对码一道防线（见 A-01/A-02）。
- 建议修法：再兑换只在“首次兑换后 N 分钟内（如 10 分钟）且尚未提交入组申请 / 尚未登记根”时允许（覆盖“应答丢失重试”的本意），并计数；超过即与错码同一句话；再兑换写审计并在管理员“成员”页显示“该邀请被兑换 N 次”。更进一步：首次兑换时让客户端带一把临时公钥，后续再兑换须用它签名。
- 建议补的测试：① 兑换 → 再兑换（窗口内、未提交申请）成功且旧凭据失效；② 已提交入组申请后再兑换 → `code_invalid`；③ 超出窗口再兑换 → `code_invalid`；④ 创始码兑换后再兑换 → 不能用新凭据登记另一把根（或明确只能有一次）。

### A-05【重要】`activationRequired` 缺省为 false，与设计“生产缺省 true”相反

- 证据：`server.ts:468` `createTenant({ …, activationRequired = false })`；全仓唯一传 `true` 的是 `scripts/dev-cloud-v0.mjs:59`（且仅在 `KWL_ACTIVATION=1` 时）；生产入口 `scripts/cloud-serve.mjs` 没有运营建租户的接口（运营操作仍是进程内 `ops`）；旧状态读回 `activation_required` 缺省为假。
- 推演：将来写运营工具时只要沿用缺省，租户就回到“知道租户编号即可抢先登记律所根”（评审 Z4 指出的问题原样存在）。租户编号是 `ten_<律所标识>`，可猜。
- 建议修法：缺省改为 `true`，只有测试显式传 `false`；`cloud-serve.mjs` 启动时若发现“未登记根且不要求开通码”的租户，拒绝启动或至少告警；运营工具发码与建租户同一步。
- 建议补的测试：`createTenant` 不传参数时 `activation_required === true`；未出示认领的 `/v1/enroll` 对缺省租户 403。

### A-07【一般】兑换限速可被用来阻止全平台激活；部署在七层代理后会退化

- 证据：`server.ts` `redeemAllowed()`：按 `req.socket.remoteAddress` 每源 10 次/分钟，另有全平台 600 次/分钟桶；表项超过 50,000 时 `redeemWindow.clear()`。兑换时遍历所有租户的所有码记录（含已消费、已作废，从不清理）。
- 推演：① 任何人从多个来源每分钟发 600 次无效兑换，即可让该分钟内所有律所的真实激活得到 429（拒绝服务，成本极低）；② 用大量来源地址（IPv6）把表撑过 50,000 可清空每源计数；③ 若将来部署在七层代理之后，`remoteAddress` 全是代理地址，全平台合计 10 次/分钟；④ 线性扫描随历史码记录增长。码有 100 bit，限速本不承担防猜测，主要风险是可用性。
- 建议修法：以 MAC 为键建索引（MAC 由胡椒保护，按键查找不产生可利用的时序）；全局桶去掉或改为“只在每源桶之外兜底、并对已成功兑换过的来源放行”；淘汰改为按分钟滚动而非整表清空；部署文档写明 TLS 终止在本进程或四层（D-99 已写四层，补一句“不得置于七层代理之后，否则限速失效”）；已消费/作废超过保留期的码记录定期清理。
- 建议补的测试：每源第 11 次 429、下一分钟恢复；全局桶被打满时已登记设备的其他路由不受影响。

### A-08【一般】`activation.json` 未签名，其中的角色每次启动覆盖账本成员角色

- 证据：`kernel/src/index.ts:89-93` 每次启动执行 `UPDATE memberships SET role = activation.role`；`config.ts readActivationFile()` 只做格式校验；本机 `requireFirmAdmin`（`api/index.ts:3324-3327`，用于 `control_plane.alerts.ack / audit / audit_export`、`eval.*`）与 `devices.revoke`（:2572-2573）只看 `memberships.role`。

已跑测试：`node --test services/control-plane/test/cloud-serve.test.ts`（2/2 通过）。

正面：只接受 HTTPS（`minVersion: TLSv1.2`），测试例外只许 127.0.0.1；签名密钥、服务凭据、上游密钥、状态封装密钥都从文件读，不生成、不打印；`fail()` 的提示不含任何值；控制面状态 `fileStateStore(..., { requireKey: true })` 无密钥即拒绝构造；非控制面角色首次必须取到并核验通过吊销集（`openEnvelope` 验签后才置 `lastOkAt`）才对外服务；网关与检索只接真实上游。HTTPS 服务挂接原服务的 `request` 监听：各服务的请求体上限、限速、鉴权都在请求处理函数内（例如控制面 `maxBodyBytes`），挂接后仍生效；原服务对象上本来就没有设置 `headersTimeout`/`requestTimeout`/`maxConnections` 等服务器级参数，因此挂接没有丢失任何已有设置。

### A-15【一般】生产入口的几项缺口

- 开通码胡椒未配置：控制面角色没有 `code_pepper_file`，胡椒由信封签名私钥派生（见 A-06）。信封密钥轮换会使在途开通码与邀请码全部失效；也与设计“与签名密钥分开、KMS 下发”不符。建议增加 `code_pepper_file`（32 字节十六进制，缺失即拒绝启动）。
- 服务器级参数全用 Node 缺省：建议生产入口显式设置 `headersTimeout`（如 20 秒）、`requestTimeout`（按角色，中继/分发的大包上传另定）、`keepAliveTimeout`、`maxConnections`，并挂 `clientError` 处理（回 400 后销毁连接，不打印请求内容），压低慢速连接耗尽的风险。
- 来源地址与限速：控制面兑换限速按 `req.socket.remoteAddress`（A-07）。D-99 允许置于四层负载均衡之后——多数云上四层负载均衡做源地址转换，后端看到的是负载均衡地址，此时每源 10 次/分钟会变成全平台合计。建议部署文档写明“须保留客户端源地址（直通或 PROXY 协议）”，入口支持 PROXY 协议或可信代理头的显式配置（待确认目标环境）。
- 服务间凭据强度不检查：`service_secret_file` 只要求可读、非空。建议要求 ≥ 32 字节随机（十六进制 64 位），否则拒绝启动。
- 首次吊销集不检查新鲜度：`openEnvelope`（`firm-trust/src/envelope.ts:38`）只验签不验时刻，订阅者的版本单调只在进程内；重启后的首次获取可接受一份签名有效但较旧的吊销集（回滚吊销）。前提是攻破 TLS 或控制面从旧备份恢复，风险低。建议首次获取要求信封签发时刻在 N 分钟内，或把最大已见版本落盘。
- 未发现错误信息泄露秘密：配置文件解析失败已捕获；公钥表与内容安全策略文件 `JSON.parse` 失败时 V8 的报错可能带出文件片段，这两类文件只有公开材料；私钥 PEM 解析失败的报错不含密钥内容。
