## 重要

### RA10B-01 名册把私钥当公钥收下：误传私钥文件后，私钥随名册分发到所有服务

- **问题**：
  - `validateOpsRosterBody` 判断公钥合法，只看 `signAlgOfPublicKey(pem)`，内部就是 `createPublicKey(pem)`。Node 的 `createPublicKey` 接受 PKCS#8 私钥 PEM，会自己派生出公钥。
  - `opsKeyFingerprint(私钥PEM)` 算出的指纹与对应公钥的指纹**完全相同**，所以文档要求的“当面或电话核对指纹”拦不住。
  - 生产入口的 `pubMap` 同样直接 `createPublicKey(String(pem))`。
- **位置**：
  - `packages/ops-auth/src/index.ts:108`（公钥校验）、`:77-79`（指纹）
  - `scripts/ops-cli.mjs:114`（`--pub` 原样读入）、`:144`（名册按 0644 写出）
  - `scripts/cloud-serve.mjs:83-86`（`roster_keys_file`）
- **后果（已复现）**：
  - 安全管理员执行 `roster add --pub op_0005.k1.key.pem`（把 `.key.pem` 当成 `.pub.pem`）时，命令返回 `ok`，名册里出现 `-----BEGIN PRIVATE KEY-----`，文件权限 0644。
  - 这份名册部署到控制面、支持、中继、通知四个服务的 `ops.roster_file`，也会进备份。任何能读到其中一份的人，都能以 op_0005 的身份签请求。临时脚本里用“从名册里取出的那把私钥”签的请求，`authorize` 通过了。
  - `roster_keys_file` 如果误放了名册签名**私钥**，服务照常启动。这样“名册签名私钥离线、不在任何服务上”就不成立了：拿到任意一台服务机，就能签发任意名册。
- **建议**：
  - 公钥校验加两道：PEM 头必须是 `-----BEGIN PUBLIC KEY-----`，并且 `createPrivateKey(pem)` 必须失败。这两道同时加在 `validateOpsRosterBody`、`pubMap` 和命令行 `--pub` 三处。
  - `roster add / add-key` 输出新加那把钥的指纹，并要求带 `--fingerprint <运营报来的指纹>`，对不上就拒绝。
  - 这项处置只会收紧，不会被滥用。
- **用例**：无。现有用例只校验了“同一公钥给两个人”和“签名不符”。应在 `ops-auth.test.ts` 补“私钥 PEM 当公钥 → `roster_keys_invalid`”，在 `cloud-serve-ops.test.ts` 补“`roster_keys_file` 里放私钥 → 拒绝启动”。

### RA10B-02 “运维网段以外的来源一律 404”的端到端用例在实现回退时照样通过

- **问题**：far 实例用的是全新的 `data_dir`（`far`），里面没有租户 `ten_e2e`。即使入口不拦，请求进到控制面也只会得到 `404 tenant_unknown`。第二条断言“`rejects.jsonl` 为空”在请求成功通过守卫时同样成立，因为守卫只在拒绝时才写这份记录。
- **位置**：`services/control-plane/test/cloud-serve-ops.test.ts:152-155`；被测代码是 `scripts/cloud-serve.mjs:152-168`、`:245-249`。
- **后果（已复现）**：用同样的名册和全新数据目录，把来源放行（`allow_cidrs: ["127.0.0.1/32"]`，等价于删掉入口检查）后，`call` 得到 `{"status":404,"body":{"error":{"code":"tenant_unknown",…}}}`，`rejects.jsonl` 0 行，而 `ops/access.jsonl` 里有 `requested` 和 `rejected:tenant_unknown` 两行。也就是说，删掉 `opsPathBlocked` 后这两条断言全过。这是 A-10 里最关键的网络边界，事实上没有能失败的用例。另外，入口的规范化分支（绝对形式 URL、点段、反斜杠、`::ffff:` 映射地址）都没有用例。
- **建议**：
  - 断言入口 404 的正文（`{"error":"not_found"}`，与控制面的 `{error:{code}}` 不同），并断言 `far/control-plane/ops/access.jsonl` 不存在或为空。工作区里未提交的改动正是这样改的，已试跑通过，建议提交。
  - 再补一条：从允许网段发 `GET /v1/x/../ops/tenants/…`（原样发出）和绝对形式请求，应当都被入口挡下，或在控制面得到 404。
- **用例**：在 058b883 中无有效用例。

## 一般

### RA10B-03 命令行在 `--roster` 缺省或路径写错时，静默从版本 1 新建名册并覆盖 `--out`

- **位置**：`scripts/ops-cli.mjs:70-71`（`!rosterFile || !existsSync(rosterFile)` 时返回 null），`:106`（null 时从 `version: 0` 开始）。
- **后果（已复现）**：现有 v2 名册里有 op_0002、op_0003。执行 `roster add --id op_0004 … --out roster.json` 但忘了写 `--roster`，命令输出 `{"ok":true,"version":1}`，原名册被一份只含 op_0004 的 v1 覆盖。
  - 部署到已有节点：`roster_rollback`，所有运营接口 503。
  - 部署到新节点（没有 `roster-seen.json`）：被接受，其他运营人员全部失效。
- **建议**：新建名册必须显式带 `--init`。`--out` 指向已存在的名册、而新版本号不高于它时拒绝写出。
- **用例**：无（`cloud-serve-ops.test.ts` 只走了正常路径）。

### RA10B-04 名册签名密钥没有轮换路径

- **位置**：`scripts/ops-cli.mjs:102`（只用 `--sign-kid` 对应的那一把公钥核验现有名册），`:66`（`roster-keygen` 用新 kid 覆盖 `ops-roster-keys.json`，旧 kid 丢失）。服务端 `roster_keys_file` 本身支持多个 kid（`cloud-serve.mjs:83-88`）。
- **后果（已复现）**：现有名册由 sec-1 签发，执行 `roster perms … --sign-kid sec-2` 时报 `roster_signer_unknown`，退出码 1。唯一绕法是不带 `--roster` 新建，但那会落到版本 1（见 RA10B-03），各节点按回滚拒收，只能手工删掉每台服务的 `roster-seen.json`，回滚保护也就一起没了。安全管理员的名册签名密钥丢失或人员轮岗时，实际上无法操作。
- **建议**：
  - 加 `roster rotate --prev-keys <旧公钥表> --sign-key <新私钥> --sign-kid sec-2`：用旧公钥核验现有名册，版本加一后用新密钥签发。
  - `roster-keygen` 合并写入公钥表，不覆盖。
  - 文档写明步骤：先把新 kid 加进各服务的 `roster_keys_file`，再换名册，最后删掉旧 kid。被滥用的风险：旧 kid 删除之前，旧密钥仍能签名册，文档要写明“全量切换后立即移除”。
- **用例**：无。

### RA10B-05 租户概要的 `activations[].created_by` 带出成员标识，与“不含成员姓名与标识”不符

- **位置**：`services/control-plane/src/server.ts:968`。成员邀请码由管理员设备发出，`by: dev.cert.deviceId`（`server.ts:1521`），而设备编号的形态是 `dev_<律所标识>_<成员标识>`（`packages/kernel/src/devices.ts:257`）。文档在 `docs/部署-云端生产入口.md:91`。
- **后果（从代码推断）**：律所管理员发过邀请后，运营执行 `GET /v1/ops/tenants/<租户>` 就能看到 `created_by: "dev_alpha_zhangsan"`。驻留面已经写明“创始成员的成员编号可能是姓名拼音”。`ops-routes.test.ts:80` 断言“概要里没有 admin”，但那个租户从没有设备发过邀请，所以覆盖不到这种情况。
- **建议**：`created_by` 只给种类（`ops` / `device`），或者只在 `op_…` 时原样给出，设备编号换成证书指纹。
- **用例**：无。

### RA10B-06 运营凭 `activation.issue` 能作废律所管理员发的成员邀请码

- **位置**：`server.ts:1015-1016`（路由只校验 `act_` 前缀）。`rawOps.revokeActivationCode`（`:637-645`）不区分 `kind`。概要又会列出全部码的 `id` 和 `kind`。
- **后果（从代码推断）**：持 `activation.issue` 的运营可以先读概要，再逐个作废 `kind: "member"` 的邀请码。待批准的入组申请会被改成 `rejected`，`decided_by` 为运营编号。设计上运营的职责是“发与作废开通码”，邀请码属于律所自己的事务（Y2 §3.12：运营不能动律所侧的事）。这些动作会进律所可见的流水，所以可追溯，但这是把进程内的能力开到了网络上。
- **建议**：运营路由只允许作废 `kind === "founder"` 的码（其他回 404 `activation_unknown`），概要也只列创始开通码。
- **用例**：无。

### RA10B-07 开通租户时附带点数，只需要 `tenant.manage`，绕开了 `quota.manage` 的划分

- **位置**：`server.ts:977`（`perm: "tenant.manage"`），`:988`（`points` 0 到 `MAX_SAFE_INTEGER`，再由 `quotaGrant` 按 `MAX_POINTS` 封顶）。
- **后果**：
  - 临时脚本复现：`POST /v1/ops/tenants` 带 `points: 1e9` 返回 200，概要里 `pool_remaining` 为 1e9。
  - 从代码推断：只持 `tenant.manage` 的人走的是同一条路由，所以只要有 `tenant.manage` 和 `activation.issue`，就能造出一个预装大量点数的租户并发出开通码，等于绕过了“加量须 `quota.manage`”。
- **建议**：`points > 0` 时同时要求 `quota.manage`，守卫按两项分别授权。或者从开通接口里去掉 `points`，加量统一走 `/points`。
- **用例**：无（`ops-routes.test.ts:63` 用的 op_0001 两项权限都有）。

### RA10B-08 运营请求被拒的记录没有限量，会撑大律所可见、不可删的流水

- **位置**：`server.ts:724-731`。运维包装出错时，只要租户存在就 `auditLog.append(rejected:…)`。限速函数 `rejectedAllowed`（`:811`，复核 S9A-10）只用在设备路由（`auditCtx`）上。
- **后果（已复现）**：已认证的运营连发 30 次 `POST /v1/ops/tenants/ten_x/points {"points":-1}`，律所流水从 1 条涨到 31 条，全是 `quota.grant/op_0001/rejected:points_invalid`，而且每条都同步落盘。S9A-10 当时定的口径是“已认证设备反复发被拒请求不能撑大流水”，运营接口现在走网络，同类问题重新出现。被滥用的场景：运营密钥失窃，或运营人员恶意刷律所的流水。
- **建议**：运维包装里对 `rejected:*` 同样按“租户 + 执行者 + 动作 + 分钟”限量（可直接复用 `rejectedAllowed`），超出的只记内部访问审计。
- **用例**：无。

### RA10B-09 两道门禁有漏网形态

- **位置**：
  - 运营路径扫描：`packages/ops-auth/test/ops-auth.test.ts:226`、`:232`
  - 闸门外发：`packages/egress-gate/test/egress-paths.test.ts:61-63`
- **后果（已复现）**：
  - 扫描正则只认 `"` 结尾、正则字面量 `\/` 结尾，服务段只认 `[a-z]+`。`'/v1/billing/ops'`、`` `/v1/billing/ops` ``、`/^\/v1\/anon-matters\/ops\/x$/`、`/^\/v1\/dist2\/ops\/x$/`、`` `${PREFIX}/ops/` `` 都**认不出**。仓库里已经有带连字符的前缀，例如 `/v1/anon-matters/`。“有运营路由必须经守卫”只检查文件里是否出现过一次 `opsGuard.authorize(`，同一文件里新增一条不经守卫的运营路由不会失败。
  - 闸门门禁是“白名单正则对 8 个样例路径”。`^\/v1\/ops\/tenants\/[^/]+\/points$`、`^\/v1\/[a-z]+\/tenants\/[^/]+\/(?:renew|terminate)$`、`^\/v1\/relay\/ops\/tenants\/[^/]+\/matters\/[^/]+$` 都**测不出**。
- **建议**：
  - 扫描改为找所有 `ops` 路径段，三种引号、`\/`、连字符和数字都要认。
  - 守卫检查改为按每条运营路由的位置，确认附近调用了 `opsAuth`、`authorize` 或 `opsRoute`。
  - 闸门门禁的样例补齐控制面全部运营子路径，以及中继的 `…/matters/<事项>`，或者直接断言白名单正则源码里不出现 `ops`。
- **用例**：门禁本身就是用例，漏网形态没有被覆盖。

### RA10B-10 `allow_cidrs` 依赖保留源地址，部署文档却写“直通或 PROXY 协议”

- **位置**：`scripts/cloud-serve.mjs:162-166` 只看 `req.socket.remoteAddress`。`docs/部署-云端生产入口.md:61` 写的是“直通或 PROXY 协议”。入口不解析 PROXY 协议，进度文档 `docs/v9-开发计划与进度.md:806` 也记着“PROXY 协议（A-15，G1）”未做。
- **后果（从代码推断）**：前置四层负载均衡如果做了源地址转换，而它的地址恰好落在 `allow_cidrs` 里（常见：负载均衡就在运维网段），运营路径对所有来源开放，只剩签名这一道。开了 PROXY 协议则 TLS 握手直接失败，服务不可用。之前这个依赖只影响兑换限速，现在成了运营接口的网络边界。
- **建议**：“运营按人鉴权”一节写明：`allow_cidrs` 不得包含负载均衡或 NAT 的地址，入口目前不解析 PROXY 协议。把 :61 的“或 PROXY 协议”改成“（PROXY 协议待 G1）”。
- **用例**：无。

## 建议

### RA10B-13 再次吊销会覆盖原吊销时刻；已吊销的人仍能改权限

- **位置**：`scripts/ops-cli.mjs:131-132`、`:123-124`。
- **后果（已复现）**：对同一人执行两次 `roster revoke`，`revoked_at` 从第一次的时刻变成第二次的时刻，版本号照样加一，吊销时间的证据被覆盖。
- **建议**：已吊销的人再执行 `revoke` 或 `perms` 时直接拒绝。

### RA10B-14 `roster add` 的 `--kid` 缺省为 k1，与运营人员生成密钥时用的 kid 脱节

- **位置**：`ops-cli.mjs:114`。`keygen` 必须带 `--kid`（`:55`），公钥文件名里也带着 kid（`op_0001.usb1.pub.pem`）。
- **后果**：安全管理员漏写 `--kid` 时，这把钥被登记成 k1；运营人员用 `call --kid usb1` 得到 `ops_operator_unknown_or_revoked`，很难查原因。
- **建议**：从文件名推断 kid，与 `--kid` 不一致时拒绝；输出指纹（见 RA10B-01）。

### RA10B-15 `call` 的几处可用性问题

- **位置**：`ops-cli.mjs:148-168`。
- **问题**：
  - `--aud` 不校验，写错只会得到 `ops_auth_signature_invalid`。
  - 没有超时。
  - IPv6 地址 URL 用的是 `url.hostname`，带方括号，连不上（已复现：`[::1]` → ECONNRESET）。
  - 路径里有未转义字符（例如中文成员编号）时，`http.request` 同步抛错，输出堆栈，而不是“连不上服务”。
  - DELETE 带 `--body` 时，签名按请求体算，但支持、中继、通知服务按空请求体核验，必然 401。
- **建议**：
  - 校验 `--aud` 是否在 `OPS_AUDIENCES` 里；
  - 加 30 秒超时；
  - IPv6 地址去掉方括号；
  - 发出前先用 `new URL(path, url)` 规范并核对；
  - DELETE 和 GET 带 `--body` 时直接拒绝。

### RA10B-16 守卫的错误码能用来枚举运营编号与 kid；503 的提示有误导；被拒记录不带名册故障原因

- **位置**：`ops-auth/src/index.ts:404-408`；`server.ts:1067`；`cloud-serve.mjs:148`。
- **问题**：
  - 运维网段内的人可以声称 `op_xxxx`/`k1` 并附上乱签名：编号存在且未吊销时回 `ops_auth_signature_invalid`，否则回 `ops_operator_unknown_or_revoked`，据此可以枚举有效的编号和 kid（工号不算秘密，影响很小）。
  - 503 名册不可用时，控制面的提示仍是“运营凭据无效、已吊销或没有这项权限”。
  - 运行期 `rejects.jsonl` 只记 `ops_roster_unavailable`，看不出是 `roster_rollback`、签名不符还是文件读不出。
- **建议**：对外统一回 401 `ops_auth_invalid`，内部记录保留细分原因；503 换专门的提示；被拒记录增加 `roster_reason` 字段。另外，被拒记录的每分钟 60 条额度是全局共用的，运维网段内的人可以用垃圾请求把真正有用的被拒记录（例如已吊销者的尝试）挤掉。可以给“声称的编号格式合规”的记录单独留一份额度。

### RA10B-17 随机数到期与时刻窗口在边界上差 1 毫秒

- **位置**：`ops-auth/src/index.ts:268`（到期时刻为现在 + 10 分钟，判定为 `e > now`），`:402`（时刻偏差判定为 `> 5 分钟`）。
- **后果（从代码推断）**：一个请求的 `ts` 等于首次见到时刻加 5 分钟。到“首次见到时刻 + 10 分钟”整的那一毫秒，这个请求仍在时刻窗口内，而它的随机数已判为过期，于是可以重放一次。窗口极小。
- **建议**：到期时刻取 `now + 2*skew + 1`，或判定改为 `e >= now`。`memoryNonceStore` 也按同样方式改。

### RA10B-18 几处执行者记录不准确

- **位置与问题**：
  - 律所管理员经 `/v1/invitations/<id>/revoke` 作废邀请时，路由代调（`server.ts:1546`），相关入组申请的 `decided_by` 记为 `"ops"`（`:644`）。这个错标是早先就有的，这次改成了 `opsActor.id` 后更显眼。
  - 运营执行预先吊销时，`preRevoked.by` 为 null（`:1033`，没有传 `by`）。
  - `seat.revoke` 的内部访问审计 `target` 为 null（`:1041` 一带），内部审计查不出吊销的是哪个席位，必须对照律所流水。
  - 这三处都不对外展示。
- **建议**：
  - 路由代调时传入设备编号作 `decided_by`；
  - `by` 传运营编号；
  - 内部访问审计记席位编号（sid）。

### RA10B-19 名册没有有效期：新节点或从备份恢复的节点会接受任何旧版本

- **问题**：回滚保护靠每个节点自己的 `roster-seen.json`（`<data_dir>/<角色>/ops/`）。
- **后果（从代码推断）**：以下三种情况，节点都会认一份被吊销者仍有效的旧名册：
  - 新扩容的节点；
  - `data_dir` 从旧备份恢复的节点；
  - `roster-seen.json` 被删掉的节点。
  文档的 D-107 只写了“多实例共享随机数与名册版本记录”。
- **建议**：名册增加 `expires_at`（例如 90 天，到期须重签），或在服务配置里给 `ops.min_roster_version`。D-107 的登记里补上“新节点、恢复备份”这两种情形。

### RA10B-20 进度文档的既往偏离登记已过时；D-106、D-107 尚未登记

- **位置**：`docs/v9-开发计划与进度.md:613`、`:924`（D-80 仍写“运营凭据为共享密钥 + 操作人头”）。代码和部署文档已经引用了 D-106、D-107，进度文档的偏离表里还没有这两行。
- **建议**：随本批的处置一并更新 D-80，并补登 D-106、D-107。

### RA10B-21 两处小毛病

- **生产入口**：`ops.roster_keys_file` 不是 JSON 或 PEM 不合法时，`pubMap` 里的 `JSON.parse` 和 `createPublicKey` 直接抛异常，进程带堆栈退出，而不是“拒绝启动：…”。这个问题早先就有，`ops` 配置沿用了它（`cloud-serve.mjs:83-86`）。
- **控制面**：`opsRoute` 先 `parseJson` 再鉴权（`server.ts:1063`）。未签名的畸形请求体得到 400 `body_not_json`，不进被拒记录。可以改成先按方法和路径确定权限、完成鉴权，之后再解析请求体。

## 已核对、未发现问题

**控制面运营路由**
- `opsActor` 只在同步的 `asOperator` 里切换，`finally` 一定复位。经 HTTP 调用之后，进程内调用仍记 `"ops"`（`ops-routes.test.ts:99-100`，反向对照有效）。整个路由从守卫到 `send` 中间没有 `await`，不会串到别的请求。
- 流水“先记 `ok` 再写盘，写盘失败补记 `rolled_back`”在 HTTP 路由下仍成立：路由不设 `auditCtx`，`send` 里的 `persistNow` 不会重复记。内部访问审计“已请求”写不进去时回 503、不执行（`ops-routes.test.ts:162-169`，反向对照有效）。
- `path !== p` 挡住了查询串、点段和绝对形式（`ops-routes.test.ts:122-135`；去掉这道检查，用例会得到 200 而失败）。
- 已存在的租户回 409（进程内调用是 500）；未知租户回 404；不是 `ten_` 形态的编号回 400；吊销尚未登记的设备必须附证书，与运维操作同一口径（有用例）；`seat_unknown` 回 404；`decodeURIComponent` 有防护。
- 对已登记律所根的租户发创始开通码，不能借此重登律所根（`server.ts:1121` `root_already_enrolled`）。

**守卫与名册**
- 签名绑定受众、方法、路径（原样）、请求体摘要、运营编号、kid、时刻、随机数，并有域分隔前缀；签名只收规范 base64url 与低 S 形式；随机数在签名有效之后才落盘，并按运营编号分开、fsync 后才放行；未认证的请求填不进随机数存储。
- 名册：同版本不同内容（`roster_conflict`）、回滚（`roster_rollback`）、版本记录写不进去时都失败关闭；版本记录损坏时拒绝启动；按 inode、大小和两个时刻判断文件变化，吊销即时生效。
- 双因素只认 `none`，名册里标了别的值而服务没接核验器时拒绝。

**支持、中继、通知**
- 三个服务和生产入口都拒绝共享口令；受众不符时构造即拒绝。
- 访问审计记的是核验出的运营编号与 kid；自报的 `x-kwl-operator` 头不影响记录（`support-api.test.ts` spoof 用例）。
- 权限划分 `support.read` / `support.delete`、`relay.reset` / `tenant.purge` 都有反向用例。
- 中继登记日志里的重置记录读回时只校验 `typeof operator === "string"`，旧记录 `ops.zhang` 照常读回。

**生产入口**
- `ops` 只许四个角色配置；`/0` 和空的 `allow_cidrs` 拒绝启动；名册首次加载失败拒绝启动；`ops_secret_file` 一出现就拒绝启动（均有用例）。
- 入口按原样路径和规范化后路径各判一次，`::ffff:` 映射地址会还原成 IPv4 再判，取不到来源地址时按挡下处理。
- `ops/` 子目录不会和各服务的存储冲突：支持服务清扫只匹配 `SUP-`/`.tmp-`，中继的租户数据在 `t/` 下，通知只清 `reminders.json.tmp-*`。

**律所侧显示与门禁**
- 运营编号符合流水执行者编号规则 `AUDIT_ID_RE`，内核验链不受影响。桌面端显示“中软运营（op_…）”，律师层文字门禁通过。
- 驻留面清单把 `packages/ops-auth/` 列为云端，“律师电脑上的代码不引用本包”的门禁成立（只扫字面量 `@zr-legal/ops-auth`，相对路径引用不在扫描内，目前也没有）。

**工程**
- 锁文件和各工作区 `package.json` 一致，在临时目录跑 `npm ci --dry-run --offline` 会创建 `@zr-legal/ops-auth` 链接。全新 `npm ci` 不依赖本 worktree 手工加的符号链接。
- 类型检查通过。
- `dev-cloud-v0.mjs` 只给支持服务挂运营守卫，与文件头说明一致。
