## 方法

1. 回读方案条文，抽出“必须 / 禁止 / 绑定 / 失败即拒绝”类要求作为核对清单（下文各表“要求”列）。

3. 定位对应测试，逐条判定“有测试 / 无测试 / 只有静态字符串检查”。
4. 在 `platform` 目录逐个运行指定的 11 个测试文件（`node --test --test-reporter=spec <文件>`，Node v26.8.1，macOS）；运行输出只存会话临时目录（日志）。
5. 按约束：不编写新的测试样本、构造文件或脚本，不改产品代码与测试，不访问网络与开发服务端口。因此下文问题除注明“测试已覆盖”外，
   均为**静态推断（按代码路径推演，未复现）**，并给出建议补测的用例。
6. 结论分级：成立 / 部分成立 / 不成立 / 无证据；问题编号 S5-B01 起，级别：阻断 / 重要 / 一般。

### 2. 等待律师不计时（kap-host 与内核两侧）——部分成立（正常路径成立；异常出口不成立）

- **宿主侧**（`runtime.ts`）：工作时限 `deadline = start + min(time_limit_ms, maxRunMs=30 分钟)`（`:393`），总时长 `wallDeadline = start + 8 小时 5 分钟`（`:395`）；
  `setStatus` 进入 waiting_* 记 `waitingSince`、离开时 `deadline` 顺延等待时长（`:325-337`）；`overdue` 先判总时长、再判（等待中按冻结计算的）工作时限（`:340-344`）；
  看门狗每秒执行 `overdue` 并处理审批卡 30 分钟过期（按拒绝解除引擎等待，`:615-631`）；`settleWhenIdle` 同样调用 `overdue`（`:583-612`）。提问卡无单独期限。
- **内核侧**（`executor.ts:913-958`）：`pollDeadline = 开始 + 工作时限 + 宽限（时限的 1/10，5～60 秒）`；每 ~800 ms 轮询，若库内状态为 waiting_* 则把这一间隔计入顺延；
  总时长 8 小时（等待中 → `expired`，否则 `timed_out`，`:930-934`）。库内状态由 kap 宿主的审批/提问事件经 `onWaiting → setWaiting` 写入（`kap-agent-client.ts:139-144`、`kernel/src/index.ts:481-490`）。
- **两侧一致性**：都以宿主的待决审批/提问为准，正常路径语义一致；内核按采样时刻判定整段间隔，误差不超过一个轮询周期，被宽限吸收。不一致之处见 S5-B08（终态、上限、令牌起算）。
- **状态迁移**：running ↔ waiting_approval / waiting_input（两种等待之间经 running 两步，`index.ts:486-489`）；waiting_* → cancelled / expired / timed_out 均在
  `RUN_TRANSITIONS`（`states.ts:90-92`）。**waiting_* → failed 不在状态机内**，而宿主退出时执行器按 failed 收尾 → 任务停在等待（S5-B03）。
- **令牌与活性**：运行令牌有效期 = 总时长 + 60 秒（`kap-agent-client.ts:300,322-326`），活性由端点与闸门逐次复核（`identity.ts:98-123`：jti/rid 撤销集、尝试 running、纪元、
  运行状态在 `LIVE_RUN_STATUSES` 内——含 waiting_*；闸门在途 500 ms 复核 `server.ts:132-145`）。二者配合成立：等待期间令牌可用，任务结束或尝试被取代即失效。
  有效期本身与方案 §10 不一致且未登记（S5-B10）。

### 4. 渲染进程隔离配置（04 §1.1、§5.1 ③）——基本成立（与进度文档描述一致；口径与纵深各有一处过宽）

- **预览**（`safe-preview.ts`、`SafePreview.tsx:13-19`）：DOMParser 惰性解析 → 删除脚本/框架/嵌入/base/link/meta/表单/音视频等元素、`on*` 属性与非 data: 的地址属性、

  Markdown/文本成果走 React 元素渲染（无 `dangerouslySetInnerHTML`、不渲染链接与图片）。
- **主进程**（`main.cjs`）：默认会话 `webRequest.onBeforeRequest(<all_urls>)` 只放行 file/devtools/data/blob/about 与开发形态的 vite（`:124-139`）；权限请求与检查一律拒绝（`:137-138`）；
  `setWindowOpenHandler` 拒绝、`will-attach-webview` 阻止、主框架导航只认应用地址、子框架导航只认 about:srcdoc/blank（`:141-152`）；窗口 `sandbox/contextIsolation/nodeIntegration:false`

### S5-B03【重要】等待律师期间的异常出口缺失：宿主退出或内核重启后，任务永久停在 waiting_*，8 小时“过期”不再执行

  再调宿主，宿主（被重新拉起）报“审批不存在”（凭据因尝试已中断不可用）。②等待中关闭应用（内核重启）→ `recover` 保留 waiting_*，待决项只在宿主与 kap-agent-client 内存中，

  或转 recovering；增加过期清扫；`AGENT_WALL_MS` 可配置以便测试。**补测**：等待中杀宿主 → 任务进入终态、卡片消失、批准接口不再签发；等待中重启内核 → 任务不停在 waiting_*；总时长到期 → expired。

### S5-B07【一般】图像凭据 15 分钟有效：绑定后同一运行重发同一图像在 15 分钟后被闸门拒绝，与卡片“本运行内重发同一张图片无需再次确认”不符

### S5-B08【一般】工作时限的两侧语义有三处不一致

- ①**终态**：宿主把工作时限与总时长超时都报为 failed（`runtime.ts:141` 无 timed_out；`:620,633-654`），内核把宿主 failed 一律记 failed（`executor.ts:967-978`），只有内核兜底才记
  `timed_out`（`:935`）；第 04 篇 §8 有 TIMED_OUT，同一事实两种终态（通常是 failed）。
- ②**上限**：`ZR_AGENT_WORK_LIMIT_MS` 可调（`kernel/src/index.ts:263-264`），但宿主另按 `maxRunMs` 缺省 30 分钟取小（`runtime.ts:393`，`kap-host/src/main.ts` 未配置），调到 30 分钟以上时宿主先判超时。
- ③**令牌起算**：令牌在构造 `startRun` 参数时签发（`kap-agent-client.ts:300,322`），内核总时长从 `start` 返回后起算（`executor.ts:913`）；宿主冷启动（`ensureHost` 最长 60 秒 + `startRun` 最长 120 秒）
  超过 60 秒宽限时，令牌先于内核的过期/超时判定失效，任务以令牌失效收尾。
- **建议处置**：宿主上报 timed_out（或内核按原因映射）；宿主工作时限上限以内核下发为准；令牌有效期按内核 deadline 另加足够宽限。**补测**：非等待状态超过工作时限 → 任务终态 timed_out。

### S5-B09【一般】“等待不计时”以整个运行为粒度：任一 Agent 的待决卡都会冻结整个运行的工作时限，期间其他 Agent 照常工作而不计时

- **建议处置**：在进度文档与能力账本如实说明；或改为“主 Agent 阻塞等待时才冻结”。

### S5-B10【一般】运行令牌有效期约 8 小时（总时长 + 60 秒），与第 02 篇 §10“任务能力令牌 5 分钟、可续租”不一致，未登记偏离

### S5-B13【一般】Office 外取引用的识别依赖固定写法，构造过的原件可绕过；部分类别无用例

- **代码位置**：`external-refs.ts:132-137`（简单域正则遇嵌套 `w:fldSimple` 时在内层结束标签处截断：外层不取外则原样返回、内层不再被扫描；外层取外则解包出的内层也不再扫描）；

### 5.2 新问题

#### S5-B17【重要】等待中到总时长的“过期”收尾失败：任务停在 running，内核下次重启时被当作崩溃恢复、从头重跑

- **方案出处**：第 04 篇 §8（终态转换用 CAS；EXPIRED）；进度文档“总时长 8 小时，等待中超过即‘过期’”；第 02 篇 §9.6“遇确认即暂停等人”（人的决策点不得自动越过）。
- **代码路径**（静态推断，未复现；提问卡没有单独期限，所以“律师一夜未答”就会走到这里）：
  1. 执行器在等待中到总时长：`throw new RunTerminal("expired")`（`executor.ts:936-941`）。随后 `finally` 先取消宿主（`executor.ts:963`），而 `kap-agent-client.cancel` 因任务状态仍为 running 照常调用宿主取消（`kap-agent-client.ts:365-372`）；
  2. 宿主 `cancel → finish` 先发 `run.cancelled` 事件，再回调用结果（`kap-host/src/runtime.ts:636-660,740-750`；`kap-host/src/main.ts:186-187` 发事件、`:208` 发结果，IPC 保序）；
  3. 内核收到终态事件：清空待决项并 `syncWaiting` → `onWaiting(null)` → `setWaiting` 把库内状态从 waiting_* 改回 running（`kap-agent-client.ts:264-268`、`kernel/src/index.ts:254-256,486-494`）；

### 6.2 新问题

#### S5-B19【一般】S6 对 CSV 按纯文本处理，公式单元格原样进入“脱敏件”，Excel 打开时会被当作公式计算

- **方案出处**：第 04 篇 §1.2 第 3 条（Office 打开产物零外部请求）、§11 P5。
- **代码位置**：S6 白名单放进了 `.csv`（`tools/tools/docx.ts:87-90`）。零命中时原样保存字节，有命中时只替换标识符（同文件，零命中分支与文本替换分支）。成果名为“脱敏件-<原文件名>”（`executor.ts:683`），仍是 .csv，登记检查不拦 .csv（`executor.ts:532-536`）。材料解析按 `text/*` 接收 CSV（`services/parser.ts:21`）。
- **证据**（静态推断）：材料里以 `=`、`+`、`-`、`@` 开头的单元格会原样留在脱敏件中。Excel 打开 CSV 时把这类单元格当公式计算；其中可外取的函数（例如 WEBSERVICE）可能在打开时发请求，并可把其他单元格的内容拼进地址。会不会真的发出请求，取决于 Excel 版本与信任中心设置，本机没有核实。原件本身也带同样的公式，所以产品没有新增风险，但“脱敏件”这一产品成果没有做到“打开零外部请求”。
- **建议处置**：S6 输出 CSV 时中和公式（对以 `= + - @` 开头的单元格加前导单引号或制表符），或改为输出 .txt。**补测**：含 `=WEBSERVICE(...)` 单元格的 CSV 走 S6，脱敏件中没有以公式字符开头的单元格。
