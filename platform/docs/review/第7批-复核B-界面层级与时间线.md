## 发现

### S7B-01 · 重要 · “每屏最多 1 个黑色主按钮”在完成页、审查工作台、发起面板和首页仍不成立

- **结论**：不成立（#27 / V-5 的核心规则；文档写“每屏一个主按钮”）。
- **依据**：
  - 执行页完成态（有审查意见、Agent 任务、本人发起）：中栏“打开审查工作台” `RunView.tsx:603`（单份文书时即主按钮）；右栏默认切到“审查摘要” `RunView.tsx:148`，其中“打开审查工作台” `RunView.tsx:757` 是**同一动作的第二个黑色主按钮**；底部“追问” `RunView.tsx:680` 是第三个。切到“成果”标签后，“提交复核” `RunView.tsx:833` 或“去复核 / 签发” `:846` 也是主按钮。失败态的“重新运行” `:583` 同样会和审查入口、提交复核同屏。
  - 审查工作台：每张待处理意见卡都有黑色“接受 / 知悉（不改动）” `ReviewWorkbench.tsx:362/364`。编辑某张卡时“保存并接受” `:355` 与其他卡的“接受”并存；生成修订稿后的“查看修订稿” `:235` 也会和头部按钮 `:217` 同屏。
  - 发起确认面板：`RunSheet.tsx:204-212` 的主按钮（被拦时为置灰的黑色按钮）和内嵌 `SendSummary.tsx:303`“保存判断”同屏；`ScenarioStart.tsx:250/264` 同样。
  - 首页 / 事项页：黑色发送圆钮 `Composer.tsx:134`（`styles.css:120` 用 `--btn-primary`）、建议条“使用…” `Composer.tsx:85`、空状态“新建事项” `Home.tsx:202` 可以同屏出现。
- **影响**：律师看到同屏多个同样“醒目”的按钮，分不清下一步该点哪个，违背免培训目标。审查意见场景最典型：同一个“打开审查工作台”出现两次，旁边还有“追问”。审查工作台一屏十几个黑色“接受”，会诱导逐项点接受，正好与“逐项判断”的意图相反。
- **建议修法**：
  1. 执行页：右栏审查摘要里的按钮改 `btn-ghost`，或有中栏入口时不再渲染；有审查入口时，“追问”和“提交复核”降为次按钮。按状态定一个唯一主动作：有待处理意见就打开工作台，否则提交复核，再否则追问。
  2. 审查工作台：“接受”改为次按钮，只给当前选中卡（`activeId`）用主按钮；或者全部用次按钮，只把“生成修订稿”留作全屏唯一主按钮。
  3. `SendSummary` 在面板内的“保存判断”改为次按钮。
  4. 加静态门禁：每个页面 / 面板组件里同一渲染分支下 `btn-primary` 不超过 1 个，或者在组件测试里数 DOM。

### S7B-02 · 重要 · 子任务组展开后，组内步骤的状态圆点被组的状态色覆盖（后代选择器层叠）

- **结论**：样式缺陷，展开后显示的状态与事实不符。
- **依据**：`styles.css:218-220` 是 `.step-ok .step-dot`、`.step-fail .step-dot`、`.step-wait .step-dot`，都是**后代**选择器，特异性相同，按源码顺序 ok < fail < wait。新增的 `<details className="step step-fail|ok|wait … step-group">` 包住组内每一个 `StepRow` `RunView.tsx:508-522`。于是：
  - 失败组（组内任何一步失败即为失败，`timeline.ts:90`）里，成功步骤的圆点同时命中自身的 `.step-ok` 和祖先的 `.step-fail`，后者在后，结果是**红圈加红色对勾**；
  - 进行中组里，所有步骤（包括失败步骤）都命中祖先的 `.step-wait`，结果是**蓝圈蓝底**，失败步骤显示为蓝圈加红叉。
- **影响**：律师展开子任务看逐步时，成功的步骤看起来像失败，失败的步骤看起来像进行中，状态信号不可信。现有测试只覆盖纯函数，没有样式层面的检查。
- **建议修法**：状态选择器改为子代选择器，例如 `.step-ok > .step-dot`，组汇总行用 `.step-group.step-ok > summary > .step-dot`，fail、wait 同理。也可以只给汇总行加状态类（例如放在 `<summary>` 上），`<details>` 本身不带 `step-ok/fail/wait`。

### S7B-03 · 重要 · 当事人词典“删除”与派生字号“停用”一点即生效，没有危险样式和确认，且会降低去标识覆盖

- **结论**：不符合“危险操作一律红字描边、先二次确认”（V-5），文档的“一律先确认”声明不成立。
- **依据**：`Parties.tsx:88` 的 `<button className="btn-link">删除</button>` 直接调用 `api.removeParty`，内核侧对应 `tokens.removeParty`（`packages/kernel/src/api/index.ts:2193`）；`Parties.tsx:74` 的“停用”是没有任何样式类的按钮，直接调用 `alias(…, "reject")`。按组件头注释 `Parties.tsx:1-4`，当事人词典是自然人姓名识别的依据。删除或停用后，这个名称或字号不再被代号化，之后对外发出的文字里可能出现真实名称。
- **影响**：这是对外发出内容去标识的控制项。误点一下就会削弱保护，而且没有任何提示；蓝色链接样式还让它看起来像普通导航。
- **建议修法**：“删除”改为 `btn-ghost btn-sm btn-danger`，确认文案写明后果，例如“删除后，『X』不再自动换成代号；之后发出的内容可能包含这个名称。[确定删除] [保留]”。“停用”改为次按钮，配同类确认，或改成可以撤销的提示条（已有“撤销”入口）。二次确认最好用应用自己的 `Modal`，不用原生对话框（见 S7B-04）。

### S7B-04 · 一般 · 其余危险操作：取消任务用原生确认框；解除保全、发布律所策略没有确认

- **结论**：部分成立。
- **依据**：
  - 取消任务 `RunView.tsx:482` 用 `window.confirm`。Electron 主进程没有接管 JS 对话框（`electron/main.cjs` 中没有相关处理）。按 Electron 默认实现，按钮文字是系统或英文的“OK / Cancel”（需实机确认），标题栏显示应用源地址。对“取消任务？”这个问题，按钮“取消”反而表示“不取消”，零 IT 背景的用户容易点反。R-10 给的文案“取消后，已完成的步骤会保留为草稿。[确定取消] [继续运行]”没有采用。另外，`.btn-danger` 的注释写“一律先二次确认再出现这个按钮” `styles.css:94`，与取消任务“先出现按钮、点了再确认”的实际流程不一致。
  - “解除保全” `MatterLifecycle.tsx:147` 是普通次按钮，一点即解除。解除后，事项数据就可以删除了（`MatterLifecycle.tsx:144` 的说明）。
  - 律所策略“发布” `Connections.tsx:827` 是链接样式，一点即发布，“同号草稿其余自动作废” `:815`。
- **影响**：取消任务的确认框可能出现英文按钮，而且按钮含义有歧义；解除保全和发布都是带法律或全所后果的操作，却没有确认。
- **建议修法**：取消任务改用 `components/Modal.tsx`，采用 R-10 文案，危险按钮写“停止任务”、安全按钮写“继续运行”。“解除保全”“发布”加确认，样式改为 `btn-danger`；“发布”也可以用次按钮加确认，确认里写明“其余草稿将作废”。修正 `.btn-danger` 的注释。

### S7B-05 · 一般 · 子任务折叠：并发交错时几乎不合并；单步组冗余；组状态与标题会误导；没有展开提示

- **结论**：部分成立（#33）。
- **依据**（`timeline.ts:84-98`、`RunView.tsx:503-522`）：
  1. **交错**：只合并“连续”的同一子任务步骤。集群并发时（宿主上限 3），工具事件按 a、b、c、a、b、c 交错到达，每组只有 1 步，等于没折叠。测试 `batch7-lib.test.ts:28-39` 只验证了“分开”，没有覆盖并发场景。
  2. **单步组**：1 步也包成可展开组，汇总行不显示时刻和说明，展开后又把同一步完整显示一遍。
  3. **完成判定**：`done = 最后一步不是 wait` `timeline.ts:91`。子任务在两次工具调用之间仍在运行，组却显示绿色对勾；同一子任务并行调用工具时，只要最后一个先结束，也会误显“完成”。
  4. **失败判定**：`failed ||=` 会粘住 `timeline.ts:90`。组内任意一次工具出错（Agent 常见的可恢复错误，例如读不到某个文件），整组都显示红叉；汇总标题又取最后一步（例如“读取材料”），看起来像最后这一步失败了。
  5. **信息被藏**：子任务里的联网步骤，“发出：某公司 违约（已去掉当事人名称）”这类说明（Y4 P0-A / R-1）和“实际发出的内容见右侧‘数据去向’”默认都折叠在组里。
  6. **展开提示**：`list-style:none` 并隐藏 webkit 标记 `styles.css:229-230`，没有 ▸ / ▾ 之类的提示，只有多步组带“· 共 N 步”。律师不知道这一行可以点开（免培训）。
  7. 汇总行显示“子任务 {agent_id}” `RunView.tsx:513`。`agent_id` 是引擎内部编号（`kap-host/src/runtime.ts:504`），原样展示给律师。这是之前就有的问题，现在它成了折叠行最显眼的标签。
- **建议修法**：按 `agent` 分组，而不是按连续步骤分组：组放在该子任务首次出现的位置，后续步骤并入；或者按 `agent.subagent` 的 spawned / done 事件界定组。完成状态取子任务生命周期事件（`agent.subagent` 的 done / failed / cancelled），不取最后一步。失败只在子任务失败或最后一步失败时标红，中途出错标成“有 N 步出错”。单步组直接按普通步骤渲染。组内有联网步骤时，在汇总行附注“含联网 N 次”。汇总行加 ▸ / ▾ 提示。子任务按出现顺序编号为“子任务 1 / 2 / 3”。补充交错、并行和生命周期的单测。

### S7B-06 · 一般 · 相对时间显示在每一个律师层步骤上，没有只限“关键步骤”

- **结论**：部分成立（R-12）。
- **依据**：`StepRow` 对所有律师层步骤都调用 `stepTime(…, "lawyer")` `RunView.tsx:874`。R-12 原文是“只在律师层的关键步骤上显示相对时间”。
- **影响**：一个几分钟的任务，十几行都写“刚刚 / 1 分钟前”，信息重复。查看几天前的任务时，每一行都是“3 天前”，看不出步骤先后的间隔，只能逐行悬停。
- **建议修法**：只在关键步骤上显示：开始、需要你确认 / 已确认、草稿已生成、核对引用、终态，以及与上一步间隔超过 1 分钟的步骤；其余不显示时刻。终态超过 24 小时的任务，律师层改显示“10-12 14:03”这类绝对时刻。

### S7B-07 · 一般 · 16 处 `className="btn btn-sm"` 没有对应样式，次按钮未统一为“白底描边”

- **结论**：V-5“次按钮白底描边”部分成立。这是之前就有的问题，但属于 #27“按钮层级统一”的范围。
- **依据**：`styles.css` 和 `design-tokens/tokens.css` 都没有 `.btn` 规则（只有 `.btn-sm` `styles.css:471`）。这些按钮只得到内边距和圆角，背景与边框是浏览器默认的灰底按钮。涉及：`RunView.tsx:697`、`SendSummary.tsx:198/300`、`RunSheet.tsx:159/189`、`Matter.tsx:163`、`Connections.tsx:159/335/351/378/456`、`RecallEval.tsx:84/103/359/443/600`。
- **影响**：执行页的“查看进行中的任务”、发起面板的“稍后”等按钮和 `btn-ghost` 外观不一致。
- **建议修法**：统一改用 `btn-ghost btn-sm`，或补一条 `.btn` 规则等同 `.btn-ghost`。

### S7B-08 · 一般 · 执行页中栏的过程面板仍是浅底、无色条

- **结论**：V-6 部分成立。
- **依据**：`.progress-panel` 的背景仍为 `var(--bg-sidebar)`，边框是另一种颜色 `#e7e2dc` `styles.css:520`。运行中它和确认卡、流式框同屏出现在中栏 `RunView.tsx:539`。首页建议条 `.suggest-bar` 也是蓝底 `styles.css:469`（不在执行页中栏，影响较小）。
- **建议修法**：过程面板改为白底，边框用 `var(--line)`，左边加 3px 灰色条，与“信息 = 灰”一致。

### S7B-09 · 建议 · 方法页整卡按钮的语义、读屏名称与跳转去向

- **依据**：`Methods.tsx:54-61/75-83`。
  - `<button>` 内放 `<div>`，不符合 HTML 内容模型（只允许短语内容）。浏览器照常渲染，首页场景卡也这样写 `Home.tsx:233-245`。
  - 首页卡有概括性的 `aria-label`，方法页没有，读屏会把“试用 / 给：… / 得：… / 开始 →”连读成按钮名称。
  - 通用模板卡整卡跳到首页 `nav("/")`，不带上所选方法。整卡可点会让律师以为“点了就用这个方法”，到首页却是空输入框（之前的链接也跳到首页，但现在点击区域更大，预期也更强）。
- 焦点环由全局 `:focus-visible` `styles.css:536` 提供，键盘可达，成立。
- **建议修法**：内部的 `div` 改为 `span` 并加 `display:block`；补 `aria-label`，写法与首页一致；通用模板卡跳到首页时带上方法（例如预填“按《…》的方法”），做不到的话就保留“只有一个明确按钮”的卡片形态。

### S7B-10 · 建议 · 减少动效没有覆盖脚本发起的平滑滚动

- **依据**：`scroll-behavior: auto !important` `styles.css:696` 管不到 `scrollIntoView({ behavior: "smooth" })` 显式指定的滚动行为：`ReviewWorkbench.tsx:116/156/192`、`Chat.tsx:35`。
- **建议修法**：抽一个 `smooth()` 帮助函数，内部判断 `matchMedia("(prefers-reduced-motion: reduce)").matches`，命中时用 `"auto"`。

### S7B-11 · 建议 · 新测试依赖时区，且没有覆盖本批真正的风险点

- **依据**：`batch7-lib.test.ts:15` 断言 `/^\d{1,2}:58:00$/`。在半小时偏移的时区（例如 UTC+5:30）会得到 `07:28:00`，测试失败。另外，测试没有覆盖 S7B-02 的样式层叠，也没有覆盖 S7B-05 的交错、并行与完成判定。
- **建议修法**：细节层断言改为与 `fmtShortTime(at)` 相等；补交错、并行和单步的用例。样式至少加一条静态检查：状态圆点选择器必须用子代组合符。

### S7B-12 · 建议 · 字体栈与令牌

- **依据**：正文字体栈直接写在 `body` 上 `styles.css:7`，令牌包没有 `--font-sans`；`.ev-mark::after` 用 `var(--font-sans, sans-serif)` `styles.css:633`，回落到通用 `sans-serif`，不会跟随新的字体栈。实现在苹方之前插入了 `-apple-system, BlinkMacSystemFont`，与 V-8 原文顺序不同，但只影响 macOS 开发机，可以接受。
- **建议修法**：在令牌包里定义 `--font-sans`，内容就是这一套字体栈，`body` 和各处统一引用。

## 总体结论

- **成立**：字体栈与等宽数字（V-8）；三层时刻显示和终态后刷新（R-12 的机制部分）；全局减少动效且不吞掉状态反馈（V-11）；确认、提问、计划、对账、重试、流式框改为白底加色条（V-6 主体）；方法页整卡可点且键盘可达；没有类型、导入、key 或 tokenMap 方面的回归，相关测试全部通过。
- **未达成**：#27 的两条硬规则。“每屏最多 1 个黑色主按钮”在完成页（同一动作出现两个主按钮）、审查工作台（每卡一个主按钮）、发起面板和首页都不成立（S7B-01）；“危险操作一律先确认”在当事人词典删除 / 字号停用（会降低去标识覆盖，S7B-03）、解除保全、策略发布上不成立，取消任务用原生确认框（S7B-04）。文档里这两句声明应改为如实描述，或者先补齐实现。
- **新引入缺陷**：子任务组展开后，组内状态圆点被组的状态色覆盖（S7B-02），建议本批内修复（改成子代选择器即可）。
- **建议本批内处置**：S7B-01、S7B-02、S7B-03。S7B-04～S7B-08 可以列入下一批；S7B-09～S7B-12 为建议项。
