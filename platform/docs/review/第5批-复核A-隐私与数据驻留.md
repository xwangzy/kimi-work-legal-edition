## 结论：有条件通过

本批的主体设计已落地，在本批声明的范围内成立：
- 日志器只接受登记的事件码和封闭字段类型，异常只记 name 和 code；
- 子进程 stderr 由内核重新核验；
- 3 个导出方法在主进程剥掉渲染进程自带的 `save_path`；
- 导出直写采用原子写法；
- 发送视图不返回代号真值；
- 闸门令牌化器与内核令牌化器的配置一致；
- L3a 在估价和发起两处都做判定；
- `x-kwl-tool-call` 不参与授权。

没有发现阻断级问题。有 2 个重要问题应在本批收尾或下一批开头处置：

1. **S5A-01**：渲染进程仍能让内核写到任意位置，也能读取任意位置（包括网络路径）。`resolveFileParams` 只覆盖 5 个方法，`recovery.export_device`、`sync.*` 以及无句柄的 `materials.import/mount` 不在覆盖范围内。
2. **S5A-02**：L3a 疑似姓名核对只预跑每份材料的前 40 万字，而 A1 快照最多给到 200 万字。截断时不拦截，“未核对不得发出”在大材料上不成立。

另有 7 个一般问题和 6 条建议。

## 问题清单

### S5A-01 · 重要 · 渲染进程仍可指定内核的读写路径，“只往对话框选定的位置写”只对 3 个方法成立

**位置**
- `apps/desktop/electron/file-dialogs.cjs:14-15`（`OPEN_METHODS`、`SAVE_METHODS`）
- `apps/desktop/electron/file-dialogs.cjs:89-111`（`resolveFileParams`）
- `apps/desktop/electron/main.cjs` 中的 `wireIpc` / `kwl:invoke`：除了换句柄，原样转发任意方法名和参数
- `packages/kernel/src/api/index.ts`：`recovery.export_device`（约 2739–2758）、`recovery.import_device`（约 2767）、`sync.export` / `sync.import` / `sync.status`（约 2574–2600）、`materials.import`（约 787–797）、`materials.mount`（约 843）

**事实**
1. 主进程只对 `artifacts.download`、`diagnostics.export`、`matters.archive` 剥掉 `save_path`。只有在给出 `file_handle` 时，才对 `materials.import/mount` 用句柄换出的路径覆盖 `path`；其余参数一律原样交给内核。
2. `recovery.export_device` 接受调用方给的 `path` 和 `password`，然后执行 `mkdirSync(..., {recursive:true})` 和 `writeFileSync(outPath, …)`：
   - 不检查数据根、符号链接，也不检查 UNC；
   - 已有文件会被覆盖；
   - 写入内容是设备签名私钥和加密私钥，包裹口令同样由调用方提供（scrypt 包裹）。
3. `sync.export` 按调用方给的 `share_dir` 写段文件；`sync.import`、`recovery.import_device` 从调用方给的路径读取。
4. `materials.import/mount` 在没有句柄时直接采用 `path`（D-64 为拖放保留了这条通路）。内核对该路径执行 `lstatSync`/`readFileSync`，没有限定为本机卷。`mount` 还会把 `file://<path>` 持久化，之后每次使用都会重读。

**为什么构成风险**
- `file-dialogs.cjs:4` 写的是“渲染进程拿不到、也不能指定路径”，第 5 批进度也写“内核只往对话框选定的位置写”。Y5 P1-4 的目标是渲染进程不拿路径。
- 一旦渲染进程主框架被攻破（例如 Markdown 或成果渲染出现 XSS），就能一键把设备私钥以已知口令导出到 `\\host\share\x.json` 或 OneDrive 同步目录。这条网络出站不经过出站闸门。
- 读 `\\host\share\…` 会让内核发起 SMB 连接，并与对方进行 NTLM 质询交互，同样在闸门之外。
- D-64 只登记了“读取范围 = 本账户可读的文件”，没有登记网络路径会引发出站。

**建议修复**
- 主进程对 `kwl:invoke` 统一剥掉路径类参数：`path`、`file`、`share_dir`、`save_path`、`out`、`dir`。这些位置只能来自主进程对话框给出的句柄；文件夹需要新增一种 `dir` 句柄。
- `recovery.export_device` 改走 `save` 句柄和 `writeExportFile`，不再接受调用方路径。
- 拖放路径在主进程（preload 换取）一侧拒绝以下路径：UNC、`\\?\` 与 `\\.\` 设备路径，以及映射网络驱动器（`GetDriveType` = REMOTE）。
- 从长期看，按 D-64 的回归计划改为 preload 登记句柄。
- 内核侧可以给渲染通道的调用加来源标记，拒绝来自渲染通道的路径参数，作为双保险。

**应补的测试**
- `file-dialogs.test.ts`：`recovery.export_device`、`sync.export` 带 `path` / `share_dir` 时，参数被剥掉或调用被拒；`materials.import` 带 `\\\\host\\share\\a.pdf`、`\\\\?\\UNC\\…` 时被拒。
- 内核用例：`recovery.export_device` 不接受调用方路径。

### S5A-02 · 重要 · L3a 疑似姓名核对只覆盖每份材料的前 40 万字，截断时不拦截

**位置**
- `packages/kernel/src/services/send-preview.ts:18`（`SUMMARY_CHARS_PER_DOC = 400_000`）、`:83-86`
- `api/index.ts` 中 `runs.estimate`（约 1144–1146，`suspectsBlock` 只看 `unreviewed`）、`runs.start`（约 1274–1277）
- `executor/executor.ts:857`（`AGENT_SNAPSHOT_MAX_CHARS = 2_000_000`）、`:884-889`

**事实**
- 估价和发起时的二次检测只截取每份材料前 400,000 字预跑。超出部分只把 `truncated` 标为 true，`start_blocked` 不看这个标志。
- A1 实际交给 Agent 的快照最多 2,000,000 字，令牌化后由 Agent 按需读取并发送。
- 结果：L3a 事项中，单份材料第 40 万字以后出现的疑似姓名既不展示也不拦截，但可能在运行中以原文发出。卷宗、案卷汇编超过 40 万字并不罕见。

**为什么违反方案**
- v9.2 §3.3 要求“L3a 未核对不得发出”，Y5 §3.3 验收写明“L3a 事项‘疑似姓名’未核对时‘确认发起’不可用”。
- D-62 把兑现方式改为“发起前核对覆盖材料快照与任务说明”。当快照比预跑长时，覆盖不完整。

**建议修复**
- 预跑上限与 `AGENT_SNAPSHOT_MAX_CHARS` 取同一常量。
- 如果出于性能考虑必须截断，L3a 在 `truncated` 时一律 `start_blocked`（新增 block_kind，或复用 `suspects` 并在文案中说明），或者分段扫描全文。

**应补的测试**
- L3a 事项导入一份 45 万字的材料，第 42 万字处有一个疑似姓名：估价与发起都被拦下。
- 同一材料核对完之后放行。

### S5A-03 · 一般 · 预跑输入与实际发送的组成不同：文件名、事项口径文字和发起后的重新解析不在检测范围内

**位置**
- `executor/executor.ts:873`（`fullGoal` 拼入 `ctxM.stance`、`ctxM.jurisdiction` 与方法行）、`:888`（材料文件名与正文一起令牌化后发送）
- `send-preview.ts:80-87`（`summarizeSend` 只取材料正文与 `goal`）

**事实**
1. A1 发送的提示是 `fullGoal`，其中“立场”是律师填写的自由文本，可能含姓名，例如“代理原告张某某”。预跑只扫描 `goal`。
2. 材料文件名令牌化后进入 Agent 可见的材料目录并随上下文出站，但不参与疑似姓名检测。
3. 执行时取最新的解析版本：发起之后、执行之前若执行了 `materials.reparse`（例如 OCR 重扫），新文本没有经过核对。
4. A1 在令牌化之前会先 `learnAliases`，这一项只会使实际替换更多，偏保守，不构成问题。

**为什么构成风险**：v9.2 §3.4、Y5 §3.3 要求“将发送什么”与实际发送采用同一口径。上面三处使 L3a 的“未核对不得发出”留有缺口。

**建议**
- 把执行器组装“文件名 + 正文 + 完整提示”的逻辑抽成一个共用函数，预跑与执行都调用它。
- 执行开始时，若材料的解析版本与发起时不同，则对 L3a 再核一次，或者把发起时的 `parse_version_id` 写入 `input_snapshot` 并固定使用。

**应补的测试**
- L3a 事项的立场文字或文件名含有未登记的姓名：估价被拦。
- 发起后重新解析，新文本出现疑似姓名：执行前被拦，或继续使用发起时的解析版本。

### S5A-04 · 一般 · 导出直写的“数据根”只是律所工作区，不含 userData；在 macOS 上大小写不敏感

**位置**
- `packages/kernel/src/services/export-file.ts:13-17`（`inside`）、`:38`
- 调用处 `api/index.ts`：`writeExportFile(..., config.workspaceDir)` 共 3 处
- `config.ts:192`（`workspaceDir = join(root, firmSlug)`）
- `apps/desktop/electron/main.cjs:27-29`（Windows 上的 userData 为 `%LOCALAPPDATA%\KimiWorkLegal\.electron`）

**事实**
1. 用于比较的根是 `<数据根>\<律所>`，不包括它的上级 `KimiWorkLegal`，也不包括 Electron userData。userData 中有 DPAPI 包裹的 `ledger-key`、`Local Storage` 和 `crash`。macOS 上 userData 在另一个目录。
2. 因此律师在对话框中选择 `…\.electron\ledger-key` 时不会被拒，覆盖后账本无法再打开。这需要律师本人在对话框里选中该位置，渲染进程不能指定路径（另见 S5A-01）。
3. `inside()` 只在 win32 上折叠大小写。macOS 默认卷大小写不敏感，正确性依赖 `realpathSync.native` 是否返回规范大小写，本次未实测。

**为什么构成问题**：模块注释写的是“防止覆盖账本与密钥文件”，但对 `ledger-key` 不成立。

**建议**
- 主进程把 `DATA_DIR` 与 `userData` 一并交给内核，例如经 `kernelChildEnv` 新增一个只读变量。`writeExportFile` 对每个根都做判定。
- darwin 上同样折叠大小写，并做 NFC 规整。

**应补的测试**
- 目标位于 userData 或 `DATA_DIR` 根下时被拒。
- 在 darwin 上用不同大小写写出数据根路径时被拒（用临时目录构造，不碰真实数据）。

### S5A-05 · 一般 · 保存位置的同步与网络风险识别不全

**位置**：`apps/desktop/electron/file-dialogs.cjs:62-77`（`classifySaveTarget`）

**事实**：只识别三类位置：
- OneDrive（环境变量或路径名）；
- macOS 的 `Library/Mobile Documents|CloudStorage`；
- 以 `\\` 开头的 UNC。

以下情形均返回 null，不会提示：
- 映射网络驱动器（例如 `Z:` 指向律所文件服务器，在律所很常见）；
- 可移动盘（Y5 P1-4 原文列为提示项）；
- 坚果云、百度网盘同步空间、WPS 云文档、Dropbox、Google Drive for desktop 虚拟盘等同步客户端；
- macOS 开启“桌面与文稿”iCloud 同步时的 `~/Documents`，这正是保存对话框的默认位置。

提示在渲染进程中以 `window.confirm` 弹出，并且先于写入。这一点成立。主进程不强制，可以接受。

**为什么违反方案**：Y5 P1-4 要求“保存目标的 OneDrive/网络盘/可移动盘提示”；v9.2 §3.7 把 OneDrive 检测与提示列为产品应自动完成的事项。

**建议**
- Windows 上由主进程按盘符查询驱动器类型（REMOTE/REMOVABLE）。
- 按已知同步客户端的环境变量与注册表位置识别（坚果云、Dropbox 的 `info.json`、Google Drive 的盘符）。
- 实机标定前，至少把“映射盘”与“可移动盘”纳入识别。

**应补的测试**：在 `file-dialogs.test.ts` 中注入驱动器类型探针，断言 REMOTE、REMOVABLE 返回风险标记。

### S5A-06 · 一般 · 日志面门禁可被别名绕过，主进程已有一处实例（自动更新模块仍经 console 输出自由文本）

**位置**
- `apps/desktop/electron/updater.cjs:31`（`log = console` 默认参数）、`:133`、`:148`、`:157`
- `apps/desktop/electron/main.cjs:209`（`initUpdater({...})` 未传 `log`）
- `packages/safe-log/test/log-surface.test.ts:26`（`CONSOLE` 只匹配 `console.x(`）

**事实**
- 主进程调用 `initUpdater` 时不传 `log`，于是实际使用 `console`。
- 输出内容包括 `` `[update] ${e.message}` ``、electron-updater 的 warn/error 原文，以及“放弃安装”的原因。这些文字可能含更新缓存路径，从而包含 Windows 用户名。
- 门禁正则只认 `console` 后紧跟成员调用的写法，所以 `log.error(...)` 不会被发现。

**为什么违反方案**
- 第 5 批写明“Electron 主进程不写文件、不用 console”“生产源码原有 34 处 console.* 全部改为登记事件”。
- Y5 §5.2 禁止自由文本、异常 message 与路径。
- 默认情况下主进程控制台不落盘；但 IT 以 `--enable-logging` 或 `ELECTRON_ENABLE_LOGGING` 排障时会落盘。

**建议**
- updater 改用登记事件，例如 `MAIN_UPDATE_FAILED { stage: [...], ...errFields }`，去掉 `log = console`。
- 门禁另加一条规则：`console` 作为值出现（赋值、默认参数、实参、解构）一律算违规。

**应补的测试**：在 `log-surface.test.ts` 的自检中加入 `function f(log = console)`、`const c = console`、`const { log } = console`，断言能识别。

### S5A-07 · 一般 · 写盘面扫描器存在漏判写法；“新增未登记的写盘点即失败”的表述过宽；引擎 vendor 目录被静默排除

**位置**
- `scripts/lib/source-scan.mjs:83`（walk 跳过 `vendor`）、`:122-127`（`FS_WRITE_APIS`）、`:135-174`（`fsWriteCalls`）
- `packages/kernel/test/privacy-residency.test.ts:71-90`

**事实（按写法列出漏判）**

| 写法 | 是否识别 |
|---|---|
| 别名：`const w = fs.writeFileSync` | 不识别 |
| 从命名空间解构：`const { writeFile } = fs` | 不识别 |
| 别名：`const fsp = fs.promises` | 不识别 |
| 方括号访问：`fs["writeFileSync"]` | 不识别 |
| `new fs.WriteStream(p)` | 不识别 |
| 异步 `fs.write`（不在接口表内） | 不识别 |
| `await import("node:fs")` 后调用 | 不识别 |
| `createRequire(...)("fs")` | 不识别 |
| Electron 的 `require("original-fs")` | 不识别 |
| `process.binding("fs")` | 不识别 |

另外两点：
- `FileHandle.write` 依赖 `open` 被识别，这一点成立。
- 经包装函数的新调用点不会被发现，例如 `writeExportFile`、`BlobStore.put`、`writeSecret0600`。门禁按“文件 × 接口”比对，所以在已登记的文件里再加一处同名接口调用也不会失败。

已 grep 当前生产源码，没有发现利用上述写法的实例（`local-server.ts:593` 的动态导入只取 `mkdirSync`、`rmSync`）。

引擎制品 `packages/kap-host/vendor/kap-embed/kap-embed.mjs` 中约有 95 处写接口字样，被扫描整体跳过，`residency.json.out_of_scope` 也没有声明这一点。目前只能依靠 kap-a1 的金丝雀扫描兜底。

**为什么构成问题**：Y5 §1.4 的目标是写盘 API 只出现在登记模块。现在的门禁对“直接、规范写法”有效，对别名、包装、引擎内部写入无效，进度文字的口径偏宽。

**建议**
- 扩充扫描器：别名赋值与解构、`fs.promises` 别名、方括号访问、`WriteStream` 构造、`write`、动态导入、`createRequire`、`original-fs`，并对 `process.binding` 直接报错。
- `out_of_scope` 显式列出 `packages/kap-host/vendor/` 及理由（由 sealed-storage 注入和金丝雀覆盖）。
- 进度与 residency 的 `gate` 字段改为如实表述：“新增‘文件 × 接口’组合即失败”。
- 可选：对已登记的写盘点记录调用点数量，新增调用点时要求更新清单。

**应补的测试**：扫描器自检为上表每种写法各加一条正例。

### S5A-08 · 一般 · 诊断包读回日志时的“再核验”不完整：保留原对象（包括顶层未知键），不比对级别

**位置**
- `packages/safe-log/src/index.ts:385-408`（`readLogs` 中的 `records.push(o)`）
- `packages/kernel/src/services/diagnostics.ts:132`（`recent: records.slice(-200)`）

**事实**
- `readLogs` 只核验 `t/lvl/code/proc/f`，然后把解析得到的原对象整条放入结果。
- 日志行若带有额外的顶层键，例如 `{"t":…,"code":"KERNEL_CLOSED","proc":"kernel","f":{},"x":"任意文字"}`，会原样进入诊断包的 `logs_7d.recent`。
- `lvl` 只检查是不是合法级别，不检查是否等于登记的级别。
- 内核 FileSink 自己不会写出这样的行。风险来自同一账户下其他程序改写、文件损坏，或者今后有别的写入方。诊断包的自证只能拦住本机词典与标识符规则命中的内容，拦不住案情文字。

**为什么构成问题**：第 5 批写明“读回时再核验”。Y5 §5.3 要求诊断包绝不包含内容，读回这一环应当把记录按登记表重建，而不是原样转出。

**建议**：读回时只输出重建后的 `{t, lvl: spec.level, code, proc, f: 已核验字段}`。级别不符，或出现顶层未知键，都计入 `skipped`。

**应补的测试**：`safe-log.test.ts` 中植入带额外顶层键、级别不符的行，断言 `readLogs` 的输出没有这些键或这些行，并且 `skipped` 增加。

### S5A-09 · 一般 · residency.json 与代码事实有几处不一致（门禁只查存在性，查不出来）

**位置**：`platform/docs/privacy/residency.json`

**事实**
1. 新表 `matter_suspect_reviews`（迁移 0026）存放疑似姓名原文和律师判定，属于本机原文（SQLCipher），但没有出现在任何数据类行中。按内容应列入 #3 的磁盘列。
2. `write_points["apps/desktop/electron/main.cjs"].rows` 只有 `[19]`，但理由中写了删除回执，删除回执属于 #17。
3. #7 的内存列仍写着“下载时还原真名后经渲染进程”。桌面形态已改为内核直写，只有 web 开发形态仍是如此。
4. #14 写的是“数据根 logs/kwl-YYYYMMDD.jsonl”，实际位置是 `<数据根>/<律所>/logs/`，并带有 `-N` 轮转后缀；本机盐文件 `.log-salt` 没有列出。
5. #17 和 #20 把设备恢复包写成“scrypt”落盘，但落点由调用方路径决定（见 S5A-01），残余列没有说明这一点。

**为什么构成问题**：v9.2 §3.2 要求清单成为每版门禁，Y5 §1.4 要求“新增落点必须有强制点与测试”。现行测试只核对字段齐全、符号与文件存在，以及写盘面，不核对账本表与清单是否对应。

**建议**
- 修正上述 5 处。
- 门禁增加一条：迁移中凡是含 `matter_id` 且有文本列的表，必须在某一行的 `disk` 中被点名，或列入豁免表并给出理由。

### S5A-10 · 建议 · 日志器字段类型仍偏宽；事件码未绑定来源进程；没有速率上限

**位置**：`packages/safe-log/src/index.ts:34-41`；`events.ts`

**事实**
- `ident` 允许 48 个小写字母、数字、点、连字符，足以承载拼音姓名或主机名（例如 `zhangsan-law.com`）。
- `errcode` 的小写分支 `[a-z][a-z0-9_]{1,47}` 同样宽。
- `ver` 的后缀允许字母，这与诊断包 B4-R03 收紧版本号时的理由相悖。目前没有事件使用 `ver`。
- 当前使用 `ident` 的 4 处（`step`、`status`、`tool`、`reason`）取值都来自常量或已过滤的名称，没有发现内容进入。
- 子进程可以写 `KERNEL_*` 或 `MAIN_*` 事件码，进程名由内核标注，但事件码不限定来源进程。
- 被拒事件也会写一行 `SAFE_LOG_REJECTED`，没有速率上限。异常或被控的子进程可以把 50 MB 写满，把旧日志轮转出去。这只影响可用性。

**建议**
- `step`、`status` 改为封闭枚举；`errcode` 只认 Node/SQLite 形态和登记的产品错误码表；`ver` 改为纯数字点分。
- `EventSpec` 增加 `procs` 字段，`ingest` 校验来源进程。
- 按进程设每分钟条数上限，超出只计数。

### S5A-11 · 建议 · 导出临时文件残留与删除回执写入

**位置**
- `export-file.ts:47-56`
- `apps/desktop/electron/main.cjs:410-420`（`kwl:save-text`）

**事实**
- 在 `openSync` 与 `renameSync` 之间进程崩溃或断电时，目标目录会留下 `.<文件名>.kwl-xxxxxx.part`。内容是还原真名后的明文；Windows 上以点开头的文件名并不会被隐藏；启动时也没有清扫。
- 删除回执经 `writeFileSync` 直接写入：不原子，不检查数据根，会跟随目标位置的符号链接。回执不含内容，风险低。

**建议**
- 内核在本机账本中记录“进行中的导出（目录 + 临时名）”，启动时清扫。
- 回执改为与成果导出同一套写法，可在主进程实现等价函数。
- 测试：模拟写入中途抛错（已有），再补“残留 `.part` 在下次启动被清理”。

### S5A-12 · 建议 · 宿主出口没有剥掉引擎自带的 `x-kwl-*` 请求头

**位置**：`packages/kap-host/src/host-egress.ts:62`（`STRIPPED_HEADERS`）、`:207-211`

**事实**
- `normalizeHeaders` 只剥 authorization、cookie 等头。
- 当 `callId` 格式不符时，`callHeader` 为空对象，引擎请求中自带的 `x-kwl-tool-call` 会原样送到闸门并记入去向记录。`binding.decision` 为空时的 `x-kwl-host-decision` 同理。

已核对这不影响授权：
- 闸门只认绑定给出的 bearer；
- `toolCallOf` 只作记录；
- 上游请求头由闸门自建，不转发这些头。

**影响**：引擎（或被攻破的宿主内代码）可以使时间线中某一步错配到另一条去向记录。

**建议**：合并前删除所有以 `x-kwl-` 开头的引擎头。测试：引擎请求带伪造的 `x-kwl-tool-call`、且 `x-msh-tool-call-id` 格式非法时，闸门记录中不含 `tool_call_id`。

### S5A-13 · 建议 · 发送视图只要求读权限却写回令牌表；节点执行 L3a 任务会因缺少本机判定而被拦

**位置**
- `api/index.ts` 中 `materials.send_preview`（约 2248；`requireMatterAccess`）
- `send-preview.ts:136`（`tokenizeAll` 写回）
- D-65、D-66

**事实**
- 只有读权限的成员打开发送视图，也会向令牌表追加行，而令牌表随团队同步。
- “不是姓名”的判定只保存在本机（D-66）。L3a 任务转交所内节点（`runs.node_enqueue` → 节点上 `runs.estimate/start`）时，节点没有这些判定，会被疑似姓名拦下。这是失败关闭，不泄露，但功能上不可用。

**建议**
- 发送视图改为要求写权限；或者不写回，由还原接口按本事项密钥重算并接受“可推导的代号”。
- D-66 的 G1 评估中一并考虑节点场景，或者在 L3a 转交节点时就在本机核对完，并把核对结果作为一次性凭据随任务下发。

### S5A-14 · 建议 · 日志链路的两处细节：主进程事件可能丢失；金丝雀断言不足

**位置**
- `packages/kernel/src/electron-entry.ts:56-74`（`waitForInit` 期间的消息）、`:99-107`
- `apps/desktop/electron/main.cjs:45-61`
- `packages/kernel/test/kap-a1.test.ts:587-592`

**事实**
- 主进程在 `utilityProcess.fork` 之后就直接 `postMessage`。内核在注册主消息处理之前只有 `waitForInit` 的监听器，而它忽略非 init 消息，所以 fork 与内核就绪之间发出的事件会丢失（例如后台运行时核验在这个窗口内报的问题）。不泄露。
- kap-a1 的注释写“宿主子进程的事件经内核写入”，实际只断言了 `KERNEL_STARTED` 和记录编号不以原值出现。

**建议**
- 主进程在收到 `kernel.ready` 之前一律先入队。
- kap-a1 增加断言：存在 `proc=kap_host` 的 `CHILD_EXIT`，或宿主事件的记录；不含任何 stderr 原文片段。

### S5A-15 · 建议 · 错误页“复制诊断信息”仍复制异常 message

**位置**：`apps/desktop/src/components/ErrorBoundary.tsx:24-27`、`:43`；residency #15 把它列为强制点

**事实**：复制内容包括错误 message 的首行（≤200 字），会进入系统剪贴板（Win+V 历史或云剪贴板）。内核 DomainError 的 message 可以含当事人名称，例如“当事人不存在：某某”“以下写法是常用词或泛称…：某某”。这与本批“异常只取 name/code”的口径不一致（属于既有问题，本批未改动）。

**建议**：只复制页面名、错误 name/code 和时间；需要更多信息时引导用户使用“导出诊断包”。

## 核对过且成立的要点

### 日志器
- 接口只有 `event`、`ingest`。未登记的事件码、字段或类型都会被拒，只记原因和来源，不记原值。
- `errFields` 只取 name/code。
- `id` 写盘前按本机盐 HMAC 取 12 个字母（a–p）；读回时 `id` 必须是 hash 形态。
- FileSink 单文件 5 MB、保留 14 天、总量 50 MB；当前文件不会被删除；盐文件为 0600。
- 子进程 stderr 采用 pipe，由内核 `relayChildStderr` 按登记表重新核验，进程名由内核标注。超长行、非 JSON 行、非 `kwl:1` 行只计数，结束时记 `CHILD_STDERR_UNSTRUCTURED`。UTF-8 跨块经 `setEncoding` 处理。
- 闸门、kap-host、解析进程三处都已接入；解析进程 stderr 已由 inherit 改为 pipe。
- 主进程转交路径：渲染进程的调用由主进程封装为 `{id, method, params}`，不带 `type`，因此不能伪造 `log.event`。内核只在 `type === "log.event"` 时 `ingest("main", …)`。`kernel.fatal` 和 `kernel.ready` 中的 message 与工作区路径不再打印。
- 内核 utilityProcess 为 `stdio: "ignore"`。
- `diagnostics.set_log_level` 只接受 debug/info，24 小时后自动回落；内核重启后回到 info。
- 诊断包 `logs_7d` 只放计数和最近 200 条，整包仍经过本机词典与标识符自证。

### 驻留面门禁
- 清单共 20 行，字段齐全，强制点符号与测试文件均存在。
- 写盘面扫描结果与 `write_points` 逐一相符；出站闸门源码中没有写盘点。
- 渲染存储只有 3 个登记的 localStorage 键，分布在 2 个登记文件中；没有使用 sessionStorage、indexedDB、cookie 或 Cache Storage。
- #3“闸门按事项懒加载、空闲 15 分钟逐出并清零”与 `server.ts` 中的 `evictTokenizers` 一致。

### 文件对话框与导出直写
- 句柄为 128 位随机数，10 分钟有效，用一次即作废，分“open/save”类型。
- 两个对话框都带 `dontAddToRecent`。
- 3 个导出方法剥掉渲染进程自带的 `save_path`。
- 风险提示由渲染进程在调用内核之前确认。
- `writeExportFile`：
  - 写法为同目录 `wx`/0600 临时文件 → fsync → 改名；
  - 拒绝相对路径、不存在的目录、符号链接目录或联接点（Node 在 Windows 上把联接点报告为链接）、目录目标；
  - 判定前对父目录做 realpath；
  - 改名不会跟随目标处的硬链接或符号链接。
- 直写时响应中不带文件内容，并记审计 `artifact.saved`。
- 四处“添加文件”入口都改走主进程对话框。

### 发送前核对
- `materials.send_preview` 只返回令牌形态、代号位置和疑似姓名位置，不含代号真值。
- 估价预跑不写回令牌表（用例已断言）。
- 闸门的令牌化器与内核 `MatterTokenStore.tokenizer` 配置一致：同一密钥、当事人、令牌表；`fullPseudonym` 与 `caseNumbers` 取同一条件。
- `runs.start` 对 L3a 的 a1/s1 再核一次：使用发起时的 goal 和当前账本状态（当事人名单、判定、事项级别），所以估价后修改 goal、名单或级别都能拦住。
- 节点路径同样经过 `runs.start`。
- 判定审计只记条数。
- 删除事项时一并清除 `matter_suspect_reviews`，删除用例按 `sqlite_master` 逐表检查。

### 时间线
- `x-kwl-tool-call` 只在宿主完成绑定核对之后设置，值就是那次被放行调用的编号。
- 闸门只把它写入记录；上游请求头由闸门自建，不转发；内核写入时再按格式核验。
- 时间线联网步骤只显示 `query.sent`（检索守卫已把代号改为“某人/某公司”、去除标识符或泛化）或抓取的网址。被拦下的显示“没有发出/没有打开”。没有去向记录时只提示去“数据去向”，不显示 Agent 自述的检索式。
