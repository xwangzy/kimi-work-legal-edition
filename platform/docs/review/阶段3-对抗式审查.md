### S3-03【阻断】冲突判定和写入不在同一个临界区：同一事项的并发提交、Write/Edit 与提交交错时，一方的改动被静默覆盖，不生成冲突副本

- **位置**：`exec-wasm/src/domain.ts:175-187`（每条命令结束后各自调用 `commitChanges`，同一事项没有提交锁或串行队列）；`commit.ts:218-249`（冲突判定在“写入任何东西之前”一次做完）、`commit.ts:252-262`、`292-296`（随后按判定结果写入，写入时不再核对盘上状态）；`file-broker/src/broker.ts:371-386`（`writeBytes` 只复核“受保护对象/目录”，不比对调用方期望的目标身份，没有“期望版本不符即失败”的语义）。
- **复现**：
  - `prior/c-commit.mts` C6（重跑 5/5 成立）：同一事项两条命令同时结束，都修改已有文件 `same.txt`（基线 `BASE`）。最终盘上只有 `BASE\nA\n` 或 `BASE\nB\n`，两方的提交报告 `conflicts` 都为空，也没有冲突副本，模型和律师都看不到“有一方丢了”。C6b（重跑 3/3 成立）：两条命令同时新建同名文件 `brand.csv`，结果同样是后写者覆盖，没有副本。
  - 对照 `prior/c-concurrent-control.mts`：两条命令错开 1 秒结束时，后提交者正确得到冲突副本；同时结束时，有一次以 `提交失败（ELOOP）` 告终。这说明丢失来自两次提交在宿主内交错执行。
  - 本审查 `v-integrity.mts` V2：包装 `broker.writeBytes`，把交错顺序固定为“提交已判定 → Write 经同一 broker 写入律师版本 → 提交写入 W 版本”。结果盘上为 `BASE\nW\n`，律师写入的 `LAWYER-EDIT` 被静默覆盖，`conflicts=[]`，也没有副本。真实环境里这个窗口覆盖整段冲突判定（逐个 lstat，同长文件还要整读比较）加上 16 路并发写入，改动集越大窗口越长。主 Agent 的 Write/Edit、子 Agent 和后台 Bash 本来就会并发。
- **为何违反**：第 04 篇 §4.1“工作区并发写”行要求“若期间文件在盘上已变化（Write/Edit、Office 写回、同步客户端），生成冲突副本而不覆盖”；§11 P2 通过标准列明“工作区快照提交与冲突副本正确”。同一事项默认就有 2 个并发 worker，主 Agent、Swarm 和后台任务并发跑 Bash 正是方案“并发”行描述的常态，不是边缘场景。进度文档把“工作区快照提交与冲突副本”判为“通过”，证据 w-core 只覆盖“外部进程在命令运行期间改文件、提交串行发生”这一种情形。
- **建议**：(1) 同一事项（同一工作区根）的提交串行化，用事项级互斥队列。即便如此，W 提交与 Write/Edit、Office 写回之间仍有交错，所以还要 (2) 把冲突判定下沉到每个文件的写入点：broker 提供 `writeBytesIfUnchanged(path, expected{ino,size,mtime}|absent)`，在 rename 前最后一次复核目标身份，不符就转为冲突副本。新建文件用独占创建（`createExclusive`），不用“判定不存在 → rename 覆盖”。Write/Edit 经 broker 写入时也走同一把事项锁。(3) 补回归用例：两条命令同时结束并修改同一文件；同时新建同名文件；提交进行中插入 Write。三种情形都必须得到“一份原样 + 一份冲突副本”。

### S3-04【阻断】按 inode 找别名的规则太宽：命令运行期间律师把文件改名，W 恰好新建了同名文件，提交会把改名后的律师文件当作“基线未变”而直接覆盖

- **位置**：`commit.ts:201-207`（`baselineFor`：路径不在基线里时，按当前盘上对象的 inode 去基线里找别名）；`commit.ts:208-214`、`239`（找到别名并且 ino/size/mtime 一致，就判“未变”，动作为 `write`）。
- **复现**：`prior/c-commit.mts` C1（重跑成立）。基线时有 `x.txt`；W 运行期间，外部（律师在资源管理器或 Office 里）把 `x.txt` 改名为 `new.txt`，inode 和 mtime 都不变；W 新建 `new.txt`。提交时 `new.txt` 不在基线里，按 inode 找到了 `x.txt` 的基线条目，三项一致，于是判“未变”并覆盖。结果盘上 `new.txt = "W-VERSION\n"`，律师的原文件内容没了，`conflicts=[]`，stderr 为空。
- **为何违反**：同 S3-03（第 04 篇 §4.1“生成冲突副本而不覆盖”、§11 P2）。别名规则本来只为大小写不敏感卷上的 `mv a A` 而设（注释 `commit.ts:14`），现在却对任何“盘上出现、基线没有”的路径生效，把外部改名进来的对象当成了 W 自己的旧文件。
- **建议**：只有同时满足以下条件才按别名判定：W 的改动集删除了别名路径（`cs.deleted` 含 `alias`），并且两条路径在卷的大小写/Unicode 规范化下相等（同一目录项的不同写法）。其余情况下，“路径不在基线、盘上却存在”一律算冲突，转冲突副本。补回归用例：外部改名到 W 新建的路径上。

### S3-05【重要】10 MB 输出上限把一次调用里所有重定向写文件也算在内：上游能成功的命令在 W 内以 126 失败，截断或清空的文件照常提交，律师原文件因此被覆盖

- **位置**：`domain.ts:41`（`maxOutputSize = 10 MB`）；`worker.ts:75`（作为 just-bash `executionLimits.maxOutputSize` 下发）；`domain.ts:175-181`（无论 `reason`、退出码如何，只要有改动集就提交）。
- **复现**：本审查 `v-integrity.mts` V4：工作区已有律师文件 `data.csv`，运行 `cat src.txt src.txt > data.csv`（src 为 6 MB，合计 12 MB）。结果退出码 126，`cat: output size limit exceeded (10485760 bytes)`，后续语句没有执行；提交报告 `written=["data.csv"]`，盘上 `data.csv` 变为 **0 字节**，原内容没有任何副本。`v-bigfile.mts` B2：分 12 次追加，每次 `cat src.txt >> big.bin` 只有 6 MB，第 2 次就报 `redirection: total output size exceeded`，说明上限按整次调用累计。6 MB 的半成品 `big.bin` 和前面写的 `small.txt` 都被提交。对照：python 直接写 8 MB 文件不受此限（B1，193 ms 完成）。
- **为何违反**：上游只限制回给模型的任务输出（`taskService.ts:151-159`，超过 16 MiB 即终止命令，并明确建议“把大输出重定向到文件，再分段查看”），命令写文件不受限。W 恰好让上游推荐的这条做法在 10 MB 处失效。W 在 shell 写文件这条路径上多出一道 10 MB 硬上限，比提交层自己的单文件 100 MB、总量 256 MB 低一个数量级，与第 04 篇 §4.1 规格表“输出总量与文件大小上限”分列的本意不符。合并流水、按对手方拆分大 CSV、`sort big.csv > out.csv` 这类律师常见任务会失败。更要紧的是，失败之后截断或清空的文件被当作正常结果提交，直接毁掉已有文件，违背 §4.1“超限即终止 worker 并返回明确错误”。这里错误给了，结果却没有关闭。
- **建议**：(1) 输出上限只计 stdout/stderr 这类回给模型的输出；重定向写文件只受内存层 `maxMemoryBytes` 与提交上限约束。just-bash 若分不开，就以自维护补丁区分，或者把两个上限对齐。(2) 命令因 W 自身的资源上限（输出、内存、时长、看门狗）终止时，基线中已存在的文件不得被覆盖：W 的版本另存为冲突副本，或整体不提交并说明。(3) 补用例：重定向写出超过 10 MB 的文件；超限时已有文件保持原样。

### S3-06【重要】改动集被整体拒绝、部分写入失败或结果另存为冲突副本时，Bash 仍返回退出码 0，上游判为成功

- **位置**：`domain.ts:188`（退出码只取 worker 的 `exitCode`/`reason`，不看提交报告）；`commit.ts:356-380`（说明只写进 stderr）；上游 `bashTool.ts:340-345`（`exitCode === 0` 即成功结果，非 0 才是 `Command failed with exit code`）。
- **复现**（`prior/c-commit.mts`，重跑成立）：C8，改动集含保留名路径，被整体拒绝：`code=0`，`ok.txt` 没有落盘，模型只在 stderr 里看到一句说明。C3，文件换目录：`code=0`，stdout 为 `ok`，`failed=[f.txt: ENOTDIR, f.txt/g: ENOTDIR]`，盘上仍是旧文件。本审查 V1：W 的结果被另存为冲突副本时 `B.code=0`（C7“外部删除后另存副本”同理，依据 `domain.ts:188`）。模型以为写进去的路径上，其实不是它的结果。
- **为何违反**：进度文档写的是“命令结束先提交、再……返回退出码（Bash 返回时文件已在盘上）”，在这些情形下不成立。第 04 篇 §8“未知状态、缺成果、截断、超时都不能成功”。上游以退出码区分成功与失败，模型和运行终态都据此推进：Agent 会在文件并未落盘时报告“已生成”，运行照样判 `succeeded`。
- **建议**：`rejected` 或 `failed` 非空时，退出码改为非 0（命令本身的退出码已非 0 则保留；否则用一个固定值，并写进模型可见说明）。有 `conflicts`/`kept` 时同样返回非 0，或者至少在 stdout 末尾追加可机读的一行。`exec.finished` 事件已经带有提交摘要，运行收尾时，凡有提交失败的不得判 `succeeded`，按 §8 判 `partial`。补用例，断言上述各情形的退出码。

### S3-07【重要】取消传播有漏洞：取消如果落在基线采集窗口里，或者已获批的 spawn 在运行判终态之后才到达路由，命令照常执行并提交

- **位置**：`domain.ts:144-172`（`run()` 先 `await captureBaseline`，工作区加每个只读挂载各遍历一次，之后才 `supervisor.exec` 把调用登记进 `pending`）；`host.ts:236-240`（`killAll` 只遍历 `pending`）；`runtime.ts:538`（只在终态时调用一次 `abortAll`）；`exec-router.ts:173-196`（路由不核对会话或运行是否仍然有效，没有 fencing）。
- **复现**：`prior/c-cancel.mts` K3（重跑成立）：在 `run()` 的基线采集期间调用 `abortAll`，命令照常执行，`code=0`，`k3.txt=after-cancel` 被提交。窗口长度等于基线采集耗时。2 万个文件约 258 ms（R3），材料快照和可信区越大，窗口越长。同类情形（静态推断，未复现）：宿主策略在 `finish()` 之前已批准的 Bash，其 spawn 在 `finish()`（解绑）之后才到达路由，也会被执行。
- **为何违反**：进度文档写“运行取消、超时、失败时终止本事项在途 Bash（取消传播）”，能力账本“后台任务”行把“取消传播到执行域”列为证据（`capabilities.ts:165-174`）。第 04 篇 §4.1 终止行（取消发 SIGTERM，强制停止发 SIGKILL）和进度文档的取消传播口径都意味着：运行被取消之后，不应再有它发起的命令改动工作区。
- **建议**：调用在采集基线之前就登记（领取 ID，进入 `pending` 或 WCoreDomain 自己的在途集合，带“已取消”标记）；或者设一个事项级纪元，`abortAll` 时递增，`run()` 在采集基线之后、真正执行之前核对纪元，不符即以 143 结束且不提交。路由按会话做 fencing（spawn 携带会话或运行标识，解绑后拒绝），与阶段 2 S2-12 的方向一致。补用例：取消落在基线采集窗口；终态之后到达的 spawn。

### S3-08【重要】W 起不来时，能力账本和设备页仍标“运行时隔离：W-core”；自检不覆盖 just-bash 摘要与补丁，摘要不符时执行域仍对外“可用”

- **位置**：`runtime.ts:650-655`（`capabilities()` 用工厂的 `id/label`，不看事项引擎的实际状态）；`capabilities.ts:148-154`（据此给出 `current: "pending"` 和“执行域：运行时隔离：W-core…”）；`matter-engine.ts:135-138`（引擎已记录 `execDomainError`，Bash 已关闭）；`kap-host/test/p2-w-domain.test.ts:221`（用例标题写“能力账本标‘待实现/关闭’”，用例里却没有任何账本断言）；`host.ts:160-166` 与 `supervisor.ts:93-124`（自检只在监督进程里查权限、DNS 和 Node 版本，不起 worker，也不装载 just-bash）；`jb-loader.ts:71-79`（摘要和补丁锚点在每次调用的 worker 里才校验）；`host.ts:72`（版本只匹配 `^v2[6-9]\.`）。
- **复现**：`prior/c-ledger.mts` L1（重跑成立）：随包 Node 不可用时，`engine.router.currentDomain().id = "none"`，`execDomainError = "执行域进程启动失败（退出码 1）"`，账本这一行却是 `current = pending`，note 为“执行域：运行时隔离：W-core（模拟 bash + 零 JS 桥 Python…）”。摘要不符（静态推断，未复现）：W 进程能起、自检能过，于是 Bash 可见，宿主策略放行，账本标 W-core。每次调用都在 worker 里抛出“just-bash 随包代码摘要不符…执行域失败关闭”，以退出码 1 返回。代码没有在执行域之外运行，但对外的标注和事实不符。
- **为何违反**：第 02 篇 §9.10 写明“W 不可用时，代码执行关闭，只运行可信工具”，设备页标注应为“**未隔离：不运行代码**”，不写笼统表述。阶段 2 S2-07 已确立“账本当前状态不得高于事实”。进度文档写“任一不成立即不可用”，自检项里没有 just-bash 完整性。第 04 篇 §4.1 要求“随包 Node 26 LTS（锁定小版本与 digest）”，现在的版本判定接受 v26 到 v29 任意版本。D-05 的产品化一栏提到“随包 Node 26 锁定小版本与 digest”，但没有说明当前自检接受 v26 到 v29 任意版本。
- **建议**：`capabilities()` 按事项返回实际执行域（`router.currentDomain()` 加 `execDomainError`），任何事项不可用时设备页显示“未隔离：不运行代码”及原因。自检增加一次真实 worker 往返：装载 jb-loader（摘要和补丁），跑一次 `echo` 和 `python3 -c 'print(1)'`，失败即不可用。版本判定改为锁定的小版本（产品形态再加 digest），并登记偏离。修正 p2 用例，断言账本。

### S3-09【重要】随包 Node 路径失效时宿主进程直接崩溃，不是失败关闭；W 进程异常退出的窗口里向它发消息，同样会崩溃

- **位置**：`host.ts:124-139`（`fork()` 之后没有注册 `child.on("error")`）；`host.ts:227-240`、`261`（`abort/kill/killAll/close` 调用 `child.send()` 时不带回调）。
- **复现**：`prior/c-badnode.mts`（重跑成立）：`nodePath = /nonexistent/kwl-node26/bin/node` 时，进程以 `Unhandled 'error' event … spawn … ENOENT` 退出（exit=1），`WCoreDomain.start` 没有机会 reject。对照 `nodePath=/usr/bin/false`（`c-badnode2.log`）则正确返回 `执行域进程启动失败（退出码 1）`，宿主存活。另一种情形（静态推断，未复现）：W 进程崩溃时 IPC 先 `disconnect` 再 `exit`，这期间 `this.child` 仍在、`pending` 未清。此时取消运行（`killAll`）或 `close()` 调用 `send()`，Node 会在 ChildProcess 上异步发出 `ERR_IPC_CHANNEL_CLOSED` 的 `error` 事件，同样无人监听；`host.ts:260-264` 的 try/catch 接不住。
- **为何违反**：第 02 篇 §9.10“W 不可用时，代码执行关闭，只运行可信工具”。随包 Node 被杀软隔离、被删除，或者安装不完整，都是 Windows 律所环境的常见情形。宿主一崩溃，所有事项和运行一起中断，重启后只要还在同一事项建引擎就会再崩。这是可用性上的降级，不是关闭。
- **建议**：`fork()` 之后立即注册 `error` 监听：启动阶段 reject `ready`（WUnavailableError），运行阶段按 `exit` 同样处理在途调用。所有 `send` 改为带回调，或先判 `child.connected`。拉起前校验 `nodePath` 存在且可执行。补用例：路径不存在；W 进程被杀后立即 `killAll`。

### S3-10【一般】停止语义分成两套：SIGTERM 提交已执行部分，SIGKILL、取消运行、看门狗、W 崩溃则丢弃全部改动；与上游不一致，未登记，模型也看不到

### S3-11【一般】内存看门狗按进程总常驻内存判定，一旦超限就终止进程内全部 worker，同事项无关的命令一并被杀

### S3-12【一般】排队命令的基线在排队前就采集了：命令拿到的是最新版本，改完提交仍被判冲突（假冲突）；`exec.started` 早于实际开始

### S3-13【一般】提交层与上游 shell 语义还有几处差异（未登记）：大小写更名不生效、`touch` 不更新修改时间、目录换成文件得到假冲突副本、文件换成目录不能提交

### S3-14【一般】资源上限的几处缺口：python 输出放大、python 单次写大文件挂起、没有宿主侧硬时限、排队无上界、每次全量遍历、改动集整块经 IPC

- **python 输出放大**（前序日志 `c-resource.log`、`c-resource2.log`、`c-resource3.log`）：打印 1、3、6 MB 时 W 进程 RSS 峰值约 266、457、533 MB；打印 9 MB 及以上，Python 在刷新时报 `OSError: [Errno 29] I/O error`，退出码 1，stdout 为空，远在 10 MB 输出上限之前，RSS 峰值约 1.5 GB。
- **python 单次写大文件挂起**（本审查 `v-pybig.mts`、`v-bigfile.mts`）：`open('p.bin','wb').write(b'x'*N)`，N = 8 MB 时 193 ms 完成；N = 40 MB 和 70 MB 时 60 秒观察窗内都没有结束，也没有任何报错。`v-integrity.mts` V5（80 MB）把整个脚本拖到了 300 秒闹钟。原因未定位（静态推断：疑似 just-bash 同步桥对单次大写入的缓冲处理）。W 自己的上限是 `maxPythonTimeoutMs = 60 分钟`；在产品里只能靠上游超时收尾，前台 60 秒转后台，再等 10 分钟后终止，改动全部丢弃。
- **没有宿主侧硬时限**（静态推断，未复现）：`supervisor.ts` 不为每次调用设计时器。just-bash 的 `maxExecutionTimeMs` 是协作式的，worker 线程如果卡在同步代码里，例如某个 JS 实现的命令遇上病态正则，就连 abort 消息也处理不了，只能等上游超时之后 5 秒强杀。进度文档称之为“W 自身另有每次调用的硬上限”，名不副实。
- **排队无上界**（静态推断）：`supervisor.ts:32`、`132`；宿主侧每个排队调用都持有一份基线 Map，最多 20 万条。
- **每次全量遍历**：每次 Bash 都遍历工作区、材料快照和可信区。R3：2 万个文件约 258 ms/次。R4：条目超过 20 万（保留名之下也计入，`commit.ts:82`）后 Bash 一律拒绝，清理命令也不例外，模型无法自救，只能人工清理。
- **改动集整块经 IPC 结构化克隆回传**（静态推断，未实测）：每次调用最多约 256 MB，并发 2 路，宿主侧没有对应的内存约束。本次因 S3-05 和上一项，shell 和 python 都构造不出超过 10 MB 的改动集。
- **为何违反**：第 04 篇 §4.1 资源行要求“超限即终止 worker 并返回明确错误；输出总量与文件大小上限”，性能目标也假定数据规模在 MB 级以上。
- **建议**：worker 内对 python 输出做流式转储，或限制累积；定位大写入挂起并加单次写入上限，超限时明确报错；监督进程为每次调用设硬计时器（`maxExecutionTimeMs` + 宽限 → terminate）；排队设上限，超出即拒绝并说明；基线改为按需记录（S3-12）；改动集分块回传，或在 worker 内先比对，只回传差异。

### S3-15【一般】测试与红队的覆盖缺口（隔离性审读结论附后）

### 已核实、未发现问题的部分

- `durable: false` 只作用于新建文件：`broker.ts:367-379` 中 `writeTemp(…, opts.durable !== false || leaf !== null)`，已有目标一律 fsync 后再 rename。冲突副本用独占创建（`createExclusive`），不会覆盖已有文件。

## 三、结论

**P2 现在不能判通过。** 运行时隔离本身没有发现越界缺陷：103 例红队重跑通过，三层边界的实现与方案一致。KJ 流式补丁与上游输出逐字节一致，失败关闭的主路径成立。问题集中在律师最在意的那一层，也就是提交层：已复现两条律师或 Agent 的写入被静默覆盖、又不留冲突副本的路径（S3-03、S3-04），直接违反 §11 P2“工作区快照提交与冲突副本正确”。此外，超限的命令会把已有文件截断后提交（S3-05），提交失败时 Bash 仍报成功（S3-06），取消会漏网（S3-07），账本在 W 不可用时失实（S3-08），随包 Node 缺失会让宿主崩溃（S3-09）。

**判通过所需条件**：

1. 修复 S3-03、S3-04（事项级提交串行化，加上写入点的“期望身份”核对；收紧别名规则），并补上三类并发与改名回归用例。
2. 修复 S3-05 到 S3-09。确实修不了的，降级相应能力，在账本、设备页和偏离登记里如实标注；每项都要有用例断言退出码、账本和失败关闭。
3. 在 Windows 10/11 × 三款杀软真机上完成 P2 用例（含随包 Node 被隔离的失败关闭）。
4. 纯 Python 包随包（D-08，需用户授权下载），或者由决策人明确接受“20 类任务以标准库 + 可信命令通过”作为偏离。
5. 补登未登记的偏离（见上表末行），之后安排一次复核。

一般项（S3-10 到 S3-16）可以排期，但 S3-10 的模型可见说明和 S3-14 的宿主侧硬时限建议与第 2 条一并处理。

上述阻断与重要问题都是提交层和宿主集成层的工程缺陷，可以在 G0 窗口内修复，不说明 W-core 路线本身不可行。现在不需要启动 §11 写死的 P2 退路（默认档代码执行改为“逐次确认 + 只在 N 域或可信工具中运行”）。如果到 G0 退出评审（11-20）时阻断项仍未关闭，或者 Windows 真机验收不过，则按退路执行。

### 5.2 新问题

#### S3-17【阻断】删除没有写入点比较：提交写入阶段里区外写入者保存的新版本，会在删除阶段被永久删除，不留副本、退出码 0

- **位置**：`exec-wasm/src/commit.ts:311-319`（删除计划在写入之前判定“未变 → delete”）、`393-417`（4d 删除前只看“是否存在、是否目录、是否本次写成的对象”，不再与基线身份比较）；`file-broker/src/broker.ts:590-612`（`remove` 只核对“移入回收目录的对象 = 刚才 walk 到的对象”，不接受期望身份，移入后立即 `rm -rf`）。
- **复现**（`review3d/r-delete.mts`，故障注入手法同原审查 V2：包装 `broker.createExclusive`，在 4b 写 `归档/合同.docx` 时由区外写入者更新 `合同.docx`）：W 执行 `mkdir -p 归档 && mv 合同.docx 归档/`。模拟 Word 安全保存（写临时文件后 rename，新 inode）与原地覆盖（同 inode）两种情形，结果相同：`合同.docx` 被删除，`归档/合同.docx` 是旧版本 `OLD-VERSION`，工作区（含 `.kwl-*`）里找不到律师的新版本；`report.deleted=["合同.docx"]`、`conflicts=[]`、`kept=[]`，退出码 0，stderr 为空。

#### S3-18【重要】“触及执行域资源上限”的识别口径不可靠：漏判时截断或清空的文件照常提交，误判时正常改动被整体丢弃

- **复现**（`review3d/r-integrity.mts`）：
  - 漏判 R2-awk：工作区已有律师文件 `o_awk.csv`，运行 `awk '{print toupper($0)}' big.csv > o_awk.csv; echo rc=$?`（70 MB）。awk 报 `aggregate input size limit exceeded (67108864 bytes)` 并以 126 结束，脚本继续，整体退出码 0；`o_awk.csv` 变成 0 字节并提交，没有“资源上限”说明。用 `&&` 连接时退出码非 0，能判出来——结果取决于模型写的是 `;` 还是 `&&`。

#### S3-19【一般】类型变化先永久删除旧对象再写新内容，写失败时原内容丢失；“经 broker 回收”不是可恢复回收

- **位置**：`commit.ts:418-439`（文件换目录：`broker.remove` 旧文件 → 建目录 → 写子文件，失败不恢复）、`440-456`（目录换文件：子树已在 4d 删除，写文件失败不恢复）；`broker.ts:590-612`（`remove` 移入 `.kwl-trash` 后立即 `rm -rf`）。
- **复现**（`r-integrity.mts` R5，包装 `broker.createExclusive` 对 `rep/v1` 注入 EIO，模拟磁盘满或杀软占用）：律师文件 `rep`，W 执行 `mv rep tmpx && mkdir rep && mv tmpx rep/v1`。结果 `rep` 是空目录，`report.deleted=["rep"]`、`failed=[rep/v1: EIO]`，退出码 75；工作区（含 `.kwl-*`）里找不到原内容。
- **为何违反**：`commit.ts` 头注释自称“任何写入失败时一个都不删，源文件保留（`mv` 不会丢稿）”，这条路径违反它；原审查对这一项的建议是“先移入回收区（可恢复）……失败则移回”，处置只做了“核对未变后删除”。触发需要同名类型变化与写入失败同时出现，律师业务里少见，Windows 杀软占用会提高写失败的概率。
- **建议**：旧对象先 rename 到保留名下的暂存位置，新内容全部写成后再删除；任何失败即删掉已写的部分并移回。处置表措辞改为如实描述。

#### S3-20【一般】python3 处理超过 64 MiB 的数据：写出仍然挂起、读入报“文件不存在”；60 MB 中文数据在上限以内即 MemoryError；两条并发超过 ≤ 8 GB 设备的看门狗上限

- **复现**：重跑 `v-pybig` P2（写 70 MB）60 秒观察窗内未结束；`v-integrity` V5（写 80 MB）撞上 300 秒闹钟（exit=142）。`r-integrity` R1：读入 70 MB 在 239 ms 内报 `FileNotFoundError`。R7（看门狗上限设为 1 GB）：60 MB 中文 CSV 做 `read().upper()` 后写出，单条即 `MemoryError`（W 进程峰值约 537 MB），两条并发都 `MemoryError`，峰值约 1291 MB。
- **为何违反**：第 04 篇 §4.1 资源行要求“超限即终止并返回明确错误”。挂起会占住一个并发槽，直到上游超时或 60 分钟 + 15 秒的硬计时器；“文件不存在”会误导模型。处置表“KJ-4 ……大文件读写不再报错或挂起”不属实；D-15 与模型可见说明“单个文件经 python3 读入上限约 64 MB”高于中文数据的实测可用规模。
- **建议**：KJ-4 在两侧对超过缓冲的数据返回明确错误（并入 S3-18 的上限标记）；用含中文的数据重新标定 python3 的可用规模，写进 D-15 和模型可见说明（例如“几十 MB 以上请分块或用 sqlite3”）；≤ 8 GB 设备考虑 python3 并发降为 1。

#### S3-21【一般】写入临界区的持有范围偏大：每次 Bash 的全量基线遍历（含只读挂载）都持锁，引擎写入随工作区规模线性变慢

- **位置**：`domain.ts:312-316`（工作区与每个只读挂载的 `captureBaseline` 都在 `broker.exclusive` 内）、`366`（整批提交持锁）。
- **复现**（`r-integrity.mts` R6）：工作区 2 万个文件时，无 Bash 时引擎写入约 8 ms，`true` 这样的空命令进行中约 207～209 ms；150 × 1 MB 覆盖写的提交进行中，引擎写入等待约 512 ms。按线性外推，20 万条目时每条 Bash 约阻塞 2 秒（静态推断）。审读未见死锁：锁不可重入，但临界区内只调 broker 核心方法，引擎侧包装不嵌套。
- **建议**：材料快照与可信区不经 broker 写入，链接预检移到锁外；工作区基线可考虑在锁外采集（写入已有比较—替换，删除按 S3-17 补上后，基线早一点只会多出假冲突，不会丢数据），锁只覆盖提交。

#### S3-23【一般】设备执行域自检结果永久缓存：首次失败之后不再重试；首次成功之后，W 在运行中重启失败也不反映到账本

- **位置**：`kap-host/src/runtime.ts:682`（`deviceExecCheck ??=`，成功与失败都缓存到宿主进程结束）；`matter-engine.ts:122-139`（`execDomainError` 只在事项引擎创建时写入）；`domain.ts:334-337`（W 重启失败时每次 Bash 返回“执行域不可用”，退出码 1）。
- **推断**（静态推断，未复现）：首次自检若因冷启动慢或杀软首次扫描超时（启动上限 20 秒）而失败，账本此后一直是“未隔离：不运行代码”，而各事项的执行域可能正常可用（低于事实，方向安全但误导）。反过来，首次自检成功、之后随包 Node 被杀软隔离，已打开的事项里 Bash 仍可见、每次都返回“执行域不可用”，账本仍标“运行时隔离：W-core”，与 S3-08 原问题同类（代码不在执行域外运行，失败关闭本身成立）。
- **建议**：失败结果设短时效并带退避重试；W 监督进程拉起失败时回写事项引擎的执行域状态（Bash 改为不可见、账本标原因）；补用例。

### 5.3 其他审读结论（未发现问题或已归入上文）

- 新增回归在本机重跑通过：`w-s3-regressions` 18/18、`p2-w-domain` 7/7（日志 `review3d/t-w-s3.log`、`t-p2.log`）；全量 430/430 采用主审数据，本复核未重跑。
- 比较—替换的期望身份：内容相同而跳过的分支不写，不需要比较；大小写别名分支用别名的基线身份，写入目标在大小写不敏感卷上解析到同一对象，身份一致才 rename；大小写敏感卷上 `aliasOf` 因目标不存在返回 null，走独占创建。审读未见错配。
- 类型变化会不会误删 W 没删的律师文件：文件换目录要求盘上文件自基线未变、且 W 在同一路径建了目录（W 视图里必先删过它）；目录换文件要求基线子树全部在删除集合内、删后目录已空，否则另存副本。审读未见误删；写失败时的丢失见 S3-19。
- 写入临界区：FIFO、不可重入；临界区内只调 broker 核心方法；`matterHostFileSystem` 只转调 `asHostFileSystem`，没有嵌套加锁；审读未见死锁。阻塞时长见 S3-21。
- 退出码 75：上游以非 0 判失败（`Command failed with exit code 75`），模型同时看到 stderr 说明；运行只把 `rejected/failed` 判 partial，冲突副本不改判，口径与处置表一致。命令自身恰好以 75 退出时与提交未完整无法区分，靠说明行区分（说明行的问题见 S3-22）。
- KJ-4 对隔离的影响（只审读，未写越界脚本）：python3 块与其 worker 由摘要校验过的源码在内存中修补后以 `data:` URL 装载，不读修补后的磁盘文件；worker 内 `import.meta.url` 换成原文件 URL，`createRequire` 与 `assertApprovedPath`（CPython 入口须以 `/vendor/cpython-emscripten/python.cjs` 结尾，`worker.js:2287-2296`、`2350-2358`）照常执行；Node 权限模型是进程级的，`data:` URL worker 同样受 `--allow-fs-read` 约束，没有新增授权。放宽的规模上限只扩大单个 worker 的内存占用（JS 堆仍限 768 MB，WASM 线性内存只受看门狗约束，见 S3-20），不改变边界。
- 自检的真实 worker 往返在每次拉起 W 时执行（含重启），`c-cancel` K4 重启 + 自检约 346 ms，对首个 Bash 的延迟影响可接受。

- **为何**：与 S3-18 的失败模式相同（执行域上限漏判 → 已有文件被截断版本替换），违反 D-10“触及执行域资源上限时一律不写回”；处置表“执行域上限改为结构化识别……上限置位即整体不写回”覆盖不全。
- **建议**：在两个字节上限的抛出点记录结构化信号（同错误类记录器手法：包装 OverlayFs、InMemoryFs 实例的这两个方法，抛出前记录）；内存层上限与提交总量上限的关系改为“撞内存层上限即整体不写回”。补 N3、N4 回归。

#### S3-27【一般】时限判定实际是“退出码 124 或 exec 抛异常”：脚本或子命令自身返回 124 时改动被丢弃并被说成“超过执行时限”；内部异常也被说成时限

- **位置**：`worker.ts:155-161`（`out.exitCode === 124` 且有 deadline 记录即 `timeout`；catch 分支有 deadline 记录即 `timeout`）；`jb-loader.ts:105-108`（中止错误一经构造即记录）。
- **复现**（`review3e/e-limit.mts`，时限 3 秒）：T2 `echo data > t2.txt; exit 124`（73 ms，不含 python3）→ `reason=timeout`、`t2.txt` 不写回、说明“命令超过执行时限”；T1 同样情形带 python3；T4 `echo data > t4.txt; timeout 1 sleep 3`（真实 bash 返回 124 且保留 `t4.txt`）→ 同样丢弃并说超时；N1、N2 的 overlay ENOSPC 异常 → 退出码 124、说明“命令超过执行时限”、事件 `reason=timeout`。可见 deadline 记录在普通执行里同样存在（来源未逐一定位；`index.js` 中至少有一处在 `Promise.race` 之后无条件构造中止错误），worker 注释“python3 等命令会预先构造”低估了范围。
- **为何**：数据方向安全（多丢不多写），但这是处置表声称已消除的“误判”的另一个入口：`timeout N cmd` 是常见写法，模型会被告知 W 时限已到而改变策略；内部错误被说成超时，事件统计失真。
- **建议**：时限改由 worker 以自身计时判定（开始时刻 + `maxExecutionTimeMs`），或只认解释器全局时限路径上的那一处构造；catch 分支没有时限证据时判 `error`（退出码 1，“执行域内部错误”）；模型可见说明注明 124 也可能来自命令自身。补 T2、T4 回归。

#### S3-28【一般】执行域健康的“恢复”在产品路径上走不到；设备自检重试进行中会重复拉起

- 依据见 S3-23 行（静态推断，未复现）。

#### S3-29【一般】说明、账本与进度文档仍有几处高于事实或不准确

### 9.2 新问题

#### S3-30【重要】OverlayFs 的单文件读入上限（`maxFileReadSize`，默认 128 MiB）抛普通 Error，不在结构化信号之内：sort、cat、awk 报“文件不存在”，重定向目标若是律师已有文件，会以 0 字节版本提交

- **位置**：just-bash OverlayFs 的读入检查抛 `new Error("EFBIG: file too large, read …")`（`node_modules/just-bash/dist/bundle/index.js`）；同族还有“EFBIG: file too large for copy-on-write”“EFBIG: file too large to copy”（未复现）。`worker.ts` 的 `interceptByteLimits` 只匹配两种 ENOSPC。python3 的读入因 KJ-4 匹配“too large”而计为上限（RS4），shell 命令没有。
- **复现**（`review3f/f-check.mts`，读入上限设 1 MiB 模拟，输入约 1.6 MB，`out.csv` 为律师已有文件）：RS1 `sort f.csv > out.csv; echo rc=$?`、RS2 `cat …`、RS3 `awk '{print}' …` → 命令报“f.csv: No such file or directory”（rc=1），整体退出码 0，`out.csv` 变成 0 字节并提交，没有任何说明；RS4 python3 → 126、原样。默认限值下即读入超过 128 MiB 的文件（静态推断，未按默认限值复现）。
- **为何**：与 S3-18、S3-26 的失败模式相同（执行域上限漏判 → 已有文件被截断版本替换），违反 D-10；“文件不存在”还会误导模型。模型可见说明“单个文件……经 awk 等命令读入的上限是 64 MB（超出即报 File too large 或资源上限）”对 cat、sort 不成立。第七节复核没有发现这一项。
- **建议**：同 S3-26 的手法，在 OverlayFs 的读入与写时复制检查处记录结构化信号（匹配 `^EFBIG: file too large`），撞限即整体不写回；说明补“单个文件超过 128 MB 不能读入”。补 RS1～RS3 回归。

#### S3-31【一般】目录换文件的落位仍在删除之后：落位与冲突副本都失败时，被移成这个名字的源文件已删除，新内容只在保留区，说明不给位置
