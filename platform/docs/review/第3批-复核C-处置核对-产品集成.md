### 发现

#### C-B01（重要）追问请求带 `mode: null` 可绕过“升档须确认”，问答档追问静默变为默认档且不留痕

- 位置：`packages/kernel/src/api/index.ts:1004-1013`、`:1042-1049`
- 事实：`:1004` 以 `p?.mode !== undefined` 判断是否进入运行选项分支，`null` 满足条件，`:1006` `p?.mode ?? "default"` 把它变成 `"default"` 并写入 `runOptions`；随后 `:1042` 追问分支以 `p?.mode === undefined` 判断“沿用”，`null` 不满足；`:1044` `MODE_RANK[String(p.mode)]` 即 `MODE_RANK["null"]` 为 `undefined`，`undefined > 0` 为 false，于是既不要求 `mode_raise_confirmed`，也不记 `run.followup_mode_raised`。结果：上一轮问答档，追问以默认档运行（可写风险卡、事实、草稿），无确认、无审计。现有桌面不发 `null`，但这是内核层“每处独立校验”的口子，任何改动后的界面或所内节点渠道一个空值就会触发。
- 影响：B3-B09 处置声称“要更高档位须 `mode_raise_confirmed`”，在内核层对 `null` 不成立；与 B3-B01 叠加时，端点也不会拦（任务记录里已是 default）。
- 建议：追问分支判断改为 `p?.mode == null`（null 与 undefined 同视为“沿用”），或在 `:1007` 之前把非字符串的 `mode` 一律按校验错误拒绝；比较升降档时用 `runOptions.mode`（已校验后的值）而不是原始 `p.mode`。
- 建议补测：`run-mode-gates.test.ts` 增一例：上一轮 chat，追问带 `mode: null`（不带确认）→ 新运行 `run_options.mode === "chat"` 或被拒；无论哪种，都不得出现未留痕的 default。

#### C-B02（一般）追问“沿用档位”跳过事项策略上限检查；端点按原始档位、宿主按钳制后档位，两处口径不同

- 位置：`packages/kernel/src/api/index.ts:1042-1043`（沿用分支直接写 `runOptions = { mode: prevMode, ... }`，不经 `:1008` 的 `pol.maxMode` 检查）；`packages/kernel/src/identity.ts:142`（端点与执行器 fx 用 `runModeOf` 原始值）；`packages/kernel/src/index.ts:673-688`（宿主拿到的 `runOptionsOf` 按事项策略取 min）
- 事实：上一轮在 auto 档，之后事项被标为敏感（`index.ts:660` 敏感事项上限降为 default）或律所把上限调低，追问沿用时任务记录仍写 `auto`，不报错也不提示；宿主实际按钳制后的档位运行，界面“沿用上一轮：自动”与实际不符。若律所策略上限可以是 `chat`，则会出现“宿主按 chat 拒写、端点按原始档位放行 write_draft”的不一致（宿主更严，暂不构成越权，但违背“每处独立校验、同一来源”）。
- 影响：审计与界面显示的档位不是实际运行档位；三处校验的档位来源不同。
- 建议：沿用分支同样过 `pol.maxMode`（超限时按上限钳制并在确认行提示“事项策略已调整，本轮按××档”）；`liveRunForClaims` 与执行器改用与宿主相同的钳制后档位（或把钳制后的档位在 `runs.start` 时写死进 `run_options`）。
- 建议补测：上一轮 auto、事项改为敏感后追问 → 新运行 `run_options.mode` 为 default（或拒绝并提示），端点与宿主拿到的档位一致。

### 发现

#### C-B03（重要）`w:moveFrom` 只在解析文本里去掉，定位视图仍计入：移动过的条款在视图里出现两次，锚点判“多处”

- 位置：`packages/kernel/src/services/parser.ts:99-100`（去掉 `w:moveFrom`）；`packages/docx-engine/src/textmap.ts:36-37`（`DEL_OPEN = /<w:del\b/g`、`DEL_CLOSE = /<\/w:del>/g`，不含 `w:moveFrom`）、`:76-79`（只按 `inDel` / `w:delText` 判删除）
- 事实：D-51 与 `parser.ts:92-93` 注释都写“已删除的文字（w:del、w:moveFrom）不计入——与审查定位视图、结构化补丁同一口径”。实际定位视图（`extractParagraphs` → `mapParagraphs`）只把 `w:del` 内的 run 当删除；`w:moveFrom` 里的 `w:t` 被当作可见文字。对方在修订模式下调整条款顺序（Word 记为“移动”），视图里同一段文字出现两次（移出处 + 移入处），快照里只有一次。Agent 从快照逐字摘录的锚点在视图里判 `ambiguous`，补丁引擎同样判歧义，整份修订稿退回预览。
- 影响：回稿调整条款顺序很常见；B3-B14 声称的“同口径”在移动修订上不成立，且这次改动之前两边都含移出文字（同为两次），改动之后反而把不一致引入了快照一侧。
- 建议：`textmap.ts` 的删除判断同时覆盖 `w:moveFrom`（与 `w:del` 同义处理），或者解析器暂时保留 `w:moveFrom` 以与视图一致；两边最好共用同一个“可见文字”函数。D-51 的表述同步更正。
- 建议补测：`review-anchors.test.ts` 增“回稿含 `w:moveFrom`/`w:moveTo`”一例：快照与视图中被移动的条款各只出现一次，锚点 located，修订稿 applied。

#### C-B04（一般）“同口径”只覆盖删除文字；解析器版本号未变，旧材料仍是旧口径且无法区分

- 位置：`packages/kernel/src/services/parser.ts:17`（`PARSER_VERSION = "v0.1.0-crude"` 未变）、`:59`（质量标记仍为 `comments_revisions_ignored`）；`packages/docx-engine/src/textmap.ts:33`、`:76`（`T_RE` 非全局，每个 run 只取第一个 `w:t`；`w:tab`、`w:br`、`w:instrText` 都不进视图）
- 事实：① 解析文本的语义变了（删除文字不计入），但写入 `parse_versions.parser_version` 的值不变；改动前导入的回稿，快照仍含删除文字，B3-B14 的修复对它们不生效，系统也分不出哪份是新口径。质量标记“修订已忽略”与新语义不符。② 视图对“一个 run 内多个 `w:t`”只取第一个（例如 `<w:t>甲方：</w:t><w:tab/><w:t>某公司</w:t>`），域代码 `w:instrText`（交叉引用、页码）解析文本里有、视图里没有。空白差异可由 `locateQuote` 的忽略空白比较兜住，丢字与域代码兜不住。这两点是第 3 批之前就有的 docx-engine 限制，但 D-51 写成了“同口径”。
- 影响：存量回稿仍出现 B3-B14 描述的现象；遇到多 `w:t` run 或带交叉引用的合同，锚点会判“找不到”。
- 建议：升 `PARSER_VERSION`（例如 `v0.2.0-visible`）并改质量标记为 `revisions_visible_only`；事项页对旧口径的 DOCX 提示“重新解析以使用新口径”。`T_RE` 改为全局逐个取 `w:t`（并把 `w:tab` 记为 `\t`），D-51 增写“域代码与多文本 run 的口径待第 4 批”。
- 建议补测：docx-engine `textmap` 单测：一个 run 含两个 `w:t` 与一个 `w:tab`，段落文字完整；kernel 用例：旧版本解析文本（含删除文字）重新解析后为新口径。

## 三、修订稿以文档为单位之后：多轮重复卡与“知悉”语义（专项问题 3）

核对事实：

- 提交侧没有跨任务去重：`submitRiskCards`（`review-cards.ts:168-221`）只按本任务计数（`runSeqBase` `:158-164`），同一份合同再跑一次 contract-review（新任务而非追问）会把同样的卡再提交一遍。contract-review 第 2 节第 6 步“追问只补新卡”只约束追问，且依赖 Agent 自觉。
- 生成侧不会重复写同一处修改：`structured-patch.ts:154-176` 每条补丁先单独在原件上试定位，再两两检查同段重叠，重叠的后一条记为 `overlap`；任何冲突都整体退回预览（`:179`）。律师点“跳过这 N 项，生成其余修订”（`ReviewWorkbench.tsx:188`）只跳过被标冲突的后一条，前一条保留，因此**不会把同一处改两次，也不会因重叠永久退回**，但第一次一定失败一次。
- “知悉（不改动）”在内核与工作台口径一致（`changesDocument`），但 Agent 读到的 `riskcards.list`（`tools/tools/review.ts:99-116`）每张卡只有 `lawyer_status: "accepted"` 与 `suggestion: null`，没有显式的“知悉”标记；工具描述（`tools/registry.ts:363`）写“写修订稿时只采用 accepted 与 modified”，未说明例外。只有 contract-redline 模板第 37 行写明“accepted 但 suggestion 为空 = 知悉”。

### 发现

#### C-B05（一般）同一合同多次审查产生的重复卡：工作台不提示重复，修订稿第一次必然因“重叠”退回，计数虚高

- 位置：`packages/kernel/src/services/review-cards.ts:168-221`（无跨任务去重）；`services/structured-patch.ts:170-176`（重叠只标后一条，文案为“与第 N 条补丁的锚点重叠”）；`apps/desktop/src/components/ReviewWorkbench.tsx:118-122`（统一文案“原文不一致、出现多处或相互重叠”）；`pages/Matter.tsx:234`（“N 项（待处理 M）”含重复）
- 事实：B3-B20 把工作台缺省范围扩到“本事项所有任务”后，重新审查同一份合同会让每个问题出现两张卡。律师很可能两张都接受；生成修订稿时第一次整体退回，提示里的“第 N 条补丁”是内部序号，律师对不上是哪张卡。跳过后结果正确，但保留哪一张取决于排序（严重度、位置、序号），两张建议文本不同时，律师并不知道最终写进去的是哪一版。
- 影响：不会写错文件（全有或全无 + 跳过重叠项），但主路径多一次失败与困惑；事项页“待处理”数虚高。
- 建议：提交时按“同文档 + 规范锚点 + 同建议文本”识别与未否决的旧卡重复，结果里返回 `duplicate_of` 并在工作台折叠显示；重叠冲突的说明改成“与「卡 #seq：问题摘要」修改同一处，请保留其一”，并让律师选保留哪一张，而不是默认跳过后一条。
- 建议补测：两次任务提交同一锚点、不同建议的两张卡并都接受 → 生成修订稿返回 `overlap`，冲突项能映射到两张卡；跳过其一后 applied=1，且写入的是保留那张的文本。

#### C-B06（建议）勾选“只看本次任务”后，“生成修订稿”也只含本次任务的卡，按钮文案没有区分

- 位置：`apps/desktop/src/components/ReviewWorkbench.tsx:45`、`:109`、`:161-162`
- 事实：筛选与生成共用 `runFilter`。律师为了看清本轮意见勾了筛选，再点“生成修订稿（N 项）”，得到的又是 B3-B20 所说的“缺了另一轮已接受修改”的修订稿。N 是筛选后的数，有一定提示作用，但没有写明范围。
- 建议：修订稿始终按文档全量生成（筛选只影响显示）；或筛选时按钮改为“只按本次任务生成修订稿（N 项，另有 M 项已接受未纳入）”。

#### C-B07（一般）“知悉（不改动）”对 Agent 不可直接辨认：工具描述与 redraft-review 会把它当成“我方提出的修改”

- 位置：`packages/kernel/src/tools/tools/review.ts:113`（只给 `lawyer_status`）；`packages/kernel/src/tools/registry.ts:363`（描述未说明例外）；`content/skills/redraft-review/SKILL.md:30`、`:51`（取 accepted/modified 作为“我方上一轮已提出的修改”做采纳跟踪）；`content/skills/case-report/SKILL.md:30`（统计已处理张数）
- 事实：redraft-review 会把“知悉”的卡当作我方提出过的修改，去回稿里找“是否采纳”，得出“未采纳我方修改”的错误结论，并可能为此出新卡（`【未采纳我方修改】`）。contract-redline 已写明例外（第 37 行），其他读取方没有。
- 影响：回稿重审出现虚假的“未采纳”项，律师需要逐条排除。
- 建议：`riskcards.list` 每张卡增加 `changes_document: boolean`（或 `lawyer_status: "acknowledged"` 作为派生值），工具描述写明；redraft-review 第 4 步改为“只跟踪 changes_document 为真的卡”；锁文件与模板版本同步。
- 建议补测：`review-tools.test.ts`：知悉的卡在 `riskcards.list` 输出中可被区分（字段断言）。

#### C-B08（一般）跨轮次的卡在当事人词典变化后会“锚点不在视图中”；存量卡没有规范锚点

- 位置：`packages/kernel/src/services/review-cards.ts:68`（视图按当前令牌表令牌化）、`:204`（规范锚点以提交时的令牌形态落盘）、`:419`（生成修订稿时重新按当前令牌表生成视图）；`services/structured-patch.ts:122`；迁移 `0022` 的 `INSERT … SELECT`（存量 `anchor_text` 仍为 Agent 原话）
- 事实：规范锚点是提交时令牌视图里的文字。之后律师在当事人词典里新增当事人或别名，同一段原文在视图里变成代号，旧卡锚点不再出现在视图中，补丁引擎判 `anchor_not_in_view`。B3-B20 让一份修订稿合并多轮、跨更长时间的卡，这种情况更容易出现。另外，0022 之前提交、经忽略空白定位成功的存量卡，仍存的是 Agent 原话，修订稿仍可能失败（B3-B04 对存量数据不生效）。
- 影响：律师接受过的卡在修订稿阶段被判“找不到原文”，只能跳过；原因与律师的操作（改词典）相隔较远，难以理解。
- 建议：规范锚点改存原文形态的 `[start, end)`（相对未令牌化的段落视图）或同时存原文 hash，生成修订稿时按当前令牌表重新令牌化；冲突说明里区分“合同已变化”与“当事人词典已变化”。存量卡可在启动时按 `anchor_start/anchor_end` 回填规范锚点（只对 located 卡）。
- 建议补测：提交并接受一张卡 → 在当事人词典新增锚点里出现的名称 → 生成修订稿仍 applied（或给出“词典已变化”的明确原因）。

#### C-B09（建议）修订稿的决定快照与成果登记不在同一事务

- 位置：`packages/kernel/src/services/review-cards.ts:433-457`
- 事实：`applyStructuredPatches` 先登记成果，`buildRedlineFromCards` 再用第二条 UPDATE 写 `lawyer_decisions`。两步之间进程退出，会留下作者为“律师审定”、却没有决定快照的修订稿。概率低。
- 建议：把决定快照作为参数传入 `applyStructuredPatches`，在登记成果的同一事务里写入 manifest。

#### C-B10（建议）密级检测的“含删除内容全文”受条目数截断影响

- 位置：`packages/kernel/src/services/parser.ts:81-84`
- 事实：先过滤出页眉页脚与 `document.xml`，再 `.slice(0, 13)`；顺序取决于 zip 条目顺序。分节很多的文件若页眉页脚条目排在 `document.xml` 之前，含删除内容的正文会被截掉，只剩解析文本（已不含删除文字）参与检测。Word 通常把 `document.xml` 放在前面，属边缘情况。
- 建议：`document.xml` 始终纳入，再对页眉页脚计数截断。
