## 二、逐条结论

### B-01【重要】执行域：`>>` 追加与 python3 追加模式把“解不开”的盘上文件当作空文件，提交时覆盖原文件（数据丢失）

- 状态：已核实（代码阅读；未运行复现）。
- 位置：
  - just-bash `OverlayFs.appendFile`（`node_modules/just-bash/dist/bundle/index.js` 第 809 行，字节偏移约 466807）：`try{l=await this.readFileBuffer(s)}catch{l=new Uint8Array(0)}`，随后 `setMemoryEntry(s,{content:l,appendChunks:[o]})`。bash 的 `>>` 重定向、`exec 3>>f`、`: >> f`、`tee -a` 都走 `fs.appendFile`（同文件中 `e.fs.appendFile(t.path,r,s)` 与 `e.fs.appendFile(i,"","binary")`）。
  - python3 虚拟文件系统 `chunks/worker.js` 2554–2566 行：`stream_ops.open` 读失败时 `if (isCreate && isWrite) content = new Uint8Array(0)`——`open(p,'a')`、`open(p,'a+')` 命中。
  - 解密失败抛普通 `Error("EIO: …")`（`sealed-overlay.ts:53-63`），不匹配 `FS_LIMIT_RE`（`worker.ts:100`），不记为执行域上限 → `domain.ts:365-366` 不丢弃改动集 → `commit.ts:290-299` 的“内容未变”判定里 `broker.readBytes` 同样失败被 `.catch(() => null)` 吞掉 → `commit.ts:307-308` 盘上未变、按基线比较—替换覆盖写入。
- 条件：工作区（严格形态）里出现非空明文文件（设计口径：外部写入、漏网写盘路径；`commit.ts` 头注释本身列举了“Office 写回、同步客户端”等区外写入者），或密文认证失败（损坏、`wrong_zone`、密钥代缺失）。模型执行 `echo x >> f`、`printf … >> f`、`: >> f`、`tee -a f`、`python3 -c "open(f,'a').write(…)"`。
- 后果：原文件内容被替换为“仅追加的那几行”（`: >> f` 时被清空），退出码 0，无冲突副本、无说明。原本在 broker 层被严格拒读的文件，经执行域被静默改写。just-bash 对“读不到”的这种处理是上游既有行为，但本步新增的解密错误让它变得可达。
- 建议：解密层在 `decode` 失败时调用 worker 的结构化记录（与 `recordLimit` 同法，例如 `sealed_read_failed`），命中即整次改动不写回并给出 `[执行域]` 说明；或在提交层对“盘上存在但无法解封”的目标拒绝覆盖（转冲突副本）。
- 应补测试（`w-sealed.test.ts` 严格形态用例内，删除植入文件之前）：对 `植入.txt` 与 `他钥.txt` 分别运行 `echo x >> f`、`: >> f`、python3 `open(f,'a')`，断言盘上内容不变（仍是植入的明文/他钥密文）、退出码非 0 或有不写回说明。

### B-02【重要】宿主内检索：大文件与长行上的同步段不受时间片约束，kill/SIGKILL 无法打断，20 秒硬上界不成立

- 状态：已核实（代码阅读）；耗时量级为推断。
- 位置：
  - `engine.ts:576-610`：每个文件整读 → `broker.readBytes` 整文件 `codec.open`（`broker.ts:483-486`，AES-GCM 同步解密）→ `decodeText` → `split("\n")` → `pat.mayMatch(text)` 对**整段文本**跑一次 re2js；
  - 多行模式 `engine.ts:659`（`findAll(text)`）、`624`（`count(text)`）、`711`（`anyMatch` 用 `findAll(text)`）都是整段同步；
  - 非多行模式下单个超长行的一次 `test`/`count` 同步（D-55 已登记“单个超长行”这一项，其余各项未登记）；
  - `host-search.ts:88-93`：`kill()`（不论 SIGTERM 还是 SIGKILL）只置标志；上游 `runRg.ts:100-106` 在 SIGKILL 之后仍 `await proc.wait()`，因此 Grep/Glob 调用要等检索自己跑到下一个检查点才返回。真实 rg 被 SIGKILL 即终止；这里没有等价的硬终止。
- 条件：工作区里有几十 MB 的文本（设计与进度文档自己举例“律师的流水与台账常在几十 MB”；提交层单文件上限 100 MiB），模型用非字面量正则、`-U`、`count_matches` 检索。
- 后果：kap-host 是所有事项共用的进程（引擎、IPC、看门狗 `runtime.ts:469` 的 1 秒定时器都在同一事件循环），一次检索可阻塞事件循环数秒到数十秒；上游 20 秒超时到点后发 SIGTERM/SIGKILL 也不能让工具调用按时返回；律师的取消同样要等。
- 证据缺口：`exec-router.test.ts:116-125` 的 kill 用例在检索开始之前就 kill（`spawnHostSearch` 先 `setImmediate`），只证明“开始前取消返回 143”，不能证明运行中可被打断或事件循环保持响应；没有任何用例测事件循环延迟。设计 §6.2 承诺的“ReDoS 型模式在时限内返回”只对 glob 做了（`search-diff.test.ts:304-325`），正则没有。
- 建议：回到设计 2-5 的 worker_thread 方案（D-55 放弃它的理由是“分时已满足不阻塞其他事项”，本条与 B-03、B-04 说明这个前提不成立）；或把单文件处理改为按 64 KiB 分块解密（broker 本步已有 `readBytes(n, offset)` 随机读，检索没有使用）、去掉整段 `mayMatch`、多行模式设单文件上限。
- 应补测试：用 `perf_hooks.monitorEventLoopDelay` 在 Grep（正则、`-U`、`count_matches` 三种）检索 50～100 MB 单文件时测最大延迟并设门限；运行中途 kill，断言在限定时间内 `wait()` 返回 143。

### B-03【重要】`findAll` 物化全部匹配区间：内存随匹配数线性增长，可致 kap-host V8 堆溢出（不可捕获，整进程退出）

- 状态：已核实（代码阅读）；触发阈值为推断。
- 位置：`regex.ts:265-270`（`findAll` 返回 `[number, number][]`，每个匹配一个两元素数组）；`count` 经 `countOf(this.findAll(text))`（`regex.ts:262-264`）；字面量快路径 `pattern === ""` 时 `findAll` 推入 `text.length + 1` 个区间（`regex.ts:243-245`）；调用点 `engine.ts:624/627`（计数）、`659`（多行行内容）、`711`（多行 `-l`，只为判断“有没有”也构建全数组）。
- 条件：`count_matches` + 匹配频繁或可空匹配的模式（`.`、`\S`、`\p{Han}`、`\d*`、`\s*`）作用于单个超长行（压缩 JSON、Base64、无换行导出）或在 `-U` 下作用于大文件；`-l -U` 配可空匹配模式。
- 后果：千万级匹配即 GB 级堆占用；V8 堆溢出是致命错误，`spawnHostSearch` 的 try/catch 接不住 → kap-host 退出 → 内核把所有在途任务记为 `host_exited`（`kap-agent-client.ts:204-224`）。模式由模型给出。
- 建议：`count` 改为迭代计数不留数组；`anyMatch` 改为 `matcher(text).find()`；多行行内容模式边找边标记行；对计数设上限。
- 应补测试：在 `--max-old-space-size=256` 的子进程里对 20 MB 单行文件跑 `count_matches .`、对 20 MB 文件跑 `-l -U '\d*'`，断言正常结束。

### B-04【重要】上下文行判定为 O(行数 × C)，输出循环没有让出点；`-A/-B/-C` 由模型给出且无上限

- 状态：已核实（代码阅读）。
- 位置：`engine.ts:689-706`：对每一行，向前扫 `after` 行、向后扫 `before` 行找命中；整个循环只检查 `halted()`、不 `await`。上游 `grep.ts` 对 `-A/-B/-C` 只约束为非负整数。
- 条件：一个文件有命中（`any` 为真）且行数多、命中稀疏，`-C` 取较大值。例如 100 万行、1 处命中、`-C 10000` → 约 2×10¹⁰ 次比较，全程同步、不可 kill。ripgrep 在这里是线性的。
- 建议：先一次线性扫描求每行到最近命中的距离（或按命中区间展开），输出循环每若干行让出；对 C 设合理上限。
- 应补测试：20 万行单命中文件、`-C 100000`，断言 1 秒内完成、事件循环延迟在门限内，输出与 rg 一致。

### B-05【重要】超大文件“先整读整解再判上限”；跳过时的说明模型看不到（静默漏检）；二进制文件也被整读整解

- 状态：已核实（代码阅读）。
- 位置：`engine.ts:578-589`：先 `fs.read(abs)`（整文件读入并解密，峰值约为文件大小的 3～4 倍：盘上缓冲、分块明文、`Buffer.concat`、`Uint8Array` 拷贝；`broker.ts:147-156, 483-486`、`at-rest/src/index.ts:166-184`），然后才 `bytes.length > MAX_FILE_BYTES`；二进制检测同样在整读整解之后（ripgrep 遇 NUL 只读到 64 KiB）。跳过时只写 stderr、不置错误；上游 `grepTool.ts:188-193` 只在退出码非 0/1 时展示 stderr。
- 后果：(1) GB 级文件在共享进程里分配数 GB；(2) 每次目录检索都把工作区里的 docx/xlsx/pdf 整个解密一遍（性能）；(3) >256 MiB 的文件被跳过时模型得到“无匹配”，不知道检索不完整。
- 建议：先 `stat`（broker 已报明文长度）再决定是否读；二进制探测先 `readBytes(64 KiB, 0)`；跳过视为“检索不完整”（退出码 2 或其他上游可见的方式），或至少在模型可见说明里写明上限。
- 应补测试：工作区放一个超过上限的稀疏/密文文件，断言检索不整读（堆/外部内存增量有界）且 Grep 结果对模型可见地标出不完整。

### B-06【重要】内核：取区密钥或派生 work 编解码器抛错时，运行槽位（Semaphore）泄漏

- 状态：已核实（代码阅读）。
- 位置：`kap-agent-client.ts:343` 先 `await opts.ioMutex.acquire()`；`364-370` 在 `try` 之外调用 `opts.atRest.keys(id.mid)`（`ws-keys.ts:40-56` 的 `zoneKeysFor`：解包失败、数据库错误都会抛）、`MatterKeyRing.fromWire`、`ring.zone("work")`（当前代缺 work 用途时抛“缺少用途 work 的区密钥”）、`ZoneCodec.fromWire`；释放槽位的 `catch` 在 `373-425`，这些异常走不到；任务此时尚未放入 `tasks`，没有其他收尾路径。

- 应补测试：`atRest.keys` 抛错时 `start()` 拒绝，且紧接着的第二次 `start()` 不挂起。

### B-08【一般】`\w` 的改写不等价：缺 `\p{Nl}`（含“〇” U+3007、罗马数字 Ⅰ–Ⅻ）、Other_Alphabetic、Join_Control

- 状态：已核实（代码阅读）；ripgrep 一侧按 Rust regex 文档（`\w` = Alphabetic + Mark + Decimal_Number + Connector_Punctuation + Join_Control）。
- 位置：`regex.ts:12`（`W_CLASS = \p{L}\p{M}\p{Nd}\p{Pc}`），注释 `regex.ts:4` 称“改写为等价的 Unicode 类”。
- 后果：中文日期“二〇二四年”在 rg 里是一个 `\w+`，宿主检索里被“〇”断开：`count_matches` 计数不同，`-U` 的匹配边界不同；行内容/`-l` 在一行里只有被断开的词时也可能不同。
- 建议：加入 `\p{Nl}`、`\x{200C}\x{200D}`（re2js 不支持 Alphabetic 属性时，如实残余只剩 Other_Alphabetic 的少量字符，如带圈拉丁字母）。
- 应补测试：语料加入“二〇二四年三月”“第Ⅱ部分”，模式 `\w+`、`\w+年` × 三种输出模式。

### B-09【一般】若干合法模式被误判为语法错误或语义不同

- (a) `[^\n]`、`[^\r\n]`、`[\na]`：`hasLiteralNewline`（`regex.ts:182-191`）一律报错；ripgrep 只拒绝“必须匹配换行”的字面量或单字符类（`crates/regex/src/ban.rs`），这些模式在 rg 里可用。——推断（rg 侧据源码记忆，未在本机实测）。
- (b) 没有传 `-i`、但模式自带内联 `(?i)` 时，`\d`、`\w`、`\s`、`\p{Han}` 不会被包进 `(?-i:…)`（`regex.ts:110-111` 只看 `-i` 参数）；re2js 解析 Unicode 类时以**当前标志位**（含内联 `(?i)`）决定是否取折叠表，`Map.get` 返回 `undefined` 而代码只判 `null`（`node_modules/re2js/build/index.esm.js:5219-5233`）→ 崩溃 → 被当作“regex parse error”、退出码 2。——已核实（代码阅读，未运行）。`(?i)合同\d+` 这类写法模型会用。
- (c) 嵌套字符类 `[[a-z]]`：`classBodyEnd` 停在第一个 `]`，RE2 得到“`[`与 a-z 的类 + 字面 `]`”，与 Rust（嵌套类）语义不同且不报错。——已核实（代码）。
- (d) rg 15 支持的 `\<`、`\>`、`\b{start}` 在 RE2 报错；(e) 非多行模式下 `\x0A` rg 报错、宿主静默无匹配。——推断。

## 四、按任务要点的核对结果

### 1. 宿主内检索与上游契约

- 参数面：上游 `buildRgArgs`（Grep：`--hidden`、非 content 时 `--max-columns 500`、`--null`、6 个 `--glob !VCS`、`-l` 或 `--count-matches --with-filename`、`-i`、content 时 `--with-filename` + `-n` 或 `--field-context-separator :`、`-C` 或 `-A/-B`、`--glob`、`--type`、`-U --multiline-dotall`、`--no-ignore`、敏感 glob、`-- 模式 路径`；EAGAIN 重试时 `-j 1`。Glob：`--files --hidden --sortr=modified`、VCS glob、`--glob 模式`、敏感 glob、`--no-ignore`、`.`）全部被 `parseArgs` 接受；`--field-context-separator`、`--max-columns` 在 `--null` 与非 content 模式下确实不影响输出。——已核实。
- 输出格式：`-l --null` 为 `路径\0`；计数为 `路径\0计数\n`；行内容为 `路径\0行号:内容`，上下文行号后为 `-`，跨文件上下文组以 `--` 分隔；多行区间整行标为命中行。与上游 `parseRipgrepOutput` 的解析一致。——已核实（并由差分测试覆盖所测组合）。
- 退出码：0/1/2 语义与 rg 一致，有错误且有命中时为 2（与 rg 相同）；kill 后 143。上游 Grep 在 2 时丢弃全部输出（B-11）。——已核实。
- 超时与 kill：见 B-02、B-13、D-01。
- 输出上限：引擎在 10 MiB + 64 KiB 后停写，上游按 10 MiB 截断并提示，语义正确；stderr 无上限（上游自有 10 MiB 截断）。——已核实。
- cwd：Grep 不给 cwd → 按工作区；Glob 以搜索根为 cwd、路径 `.`、输出 `./…`；`checkRgArgs` 与引擎都按同一 `searchCwd` 解析，cwd 本身也经区域与链接校验。——已核实。
- 忽略文件：`.rgignore > .ignore > .gitignore（仅仓库内）> .git/info/exclude`，由近及远各取第一个命中、`saw_git` 截断、覆盖规则优先、白名单覆盖要求文件命中、类型白名单、隐藏文件，与 ignore crate `Ignore::matched`/`matched_ignore` 的顺序一致；上级目录只读到区域根为止（rg 会一直读到 `/`，并读全局 gitignore——区外目录不受 Agent 控制，作为如实残余可接受，建议在 D-55 残余里写明）。——已核实（ignore crate 一侧据源码记忆）。
- 二进制：遍历到的文件按 rg 的 64 KiB 缓冲滚动逻辑模拟“遇 NUL 即停”，命令行给出的文件 NUL 当换行；与 grep-searcher 的 `LineBuffer::fill`/`ReadByLine::fill` 行为一致。细节残余：rg 经 BOM 嗅探的首次读取只返回 3 字节，若前 3 字节内有换行，分块边界与模拟相差最多 3 字节（推断，影响仅限 NUL 恰在 64 KiB 附近的文件）。

### 8.4 本轮新发现

**N-01【一般，推断】检索 worker 没有并发上限；总内存不受 `resourceLimits` 约束**
- `host-search.ts:110-115` 每次 Grep/Glob 新建一个 worker，堆上限 1536 MB；`resourceLimits` 只约束 V8 堆，不约束 Buffer（ArrayBuffer）外部内存：单文件 256 MiB 时盘上缓冲、分块明文、拼接、拷贝约 1 GB。
- 上游的访问冲突模型里 search 与 search 不冲突（`toolContract.ts` 的 `ToolAccesses.conflict`），并行的 Grep、子 Agent、多个事项会同时拉起多个 worker。
- 首轮单堆实现至少有一个进程级堆上限；现在是 N × 1.5 GB 加外部内存，在 8 GB 的目标设备上可能耗尽物理内存，殃及同进程的其他事项与执行域。
- 建议：宿主级检索信号量（例如 2，其余排队），堆上限按 `totalmem()` 缩放。

**N-02【建议，推断】worker 未捕获异常时可能在流结束后写入**
- 非 OOM 的 `error` 事件（worker 内未捕获异常）来自内部端口，到退出时才排空公共端口里尚未送达的 `out` 消息；此时 `finish(2)` 已经结束了 stdout，再写入会触发 PassThrough 的 `error`，没有监听者即成为宿主的未捕获异常。
- 可达性很低：`search-worker.ts` 的 `main()` 已把异常收进 promise 链。
- 建议在 `message` 处理里加 `if (exitCode !== null) return`。

**N-03【一般，推断，原有问题、第一轮漏看】`-U` 模式下的二进制判定与 rg 不同**
- 多行模式下 ripgrep 把整份文件读入，只在前 64 KiB 内找 NUL（grep-searcher `MultiLine::run` 的 `binary_upto = min(len, DEFAULT_BUFFER_CAPACITY)`）：64 KiB 之后的 NUL 既不截断也不告警；命令行直接给出的文件则原样输出含 NUL 的行。
- 宿主在 `-U` 下仍按逐行模式的滚动规则截断并附 WARNING（`engine.ts:621-630`）；命令行给出的文件报“binary file matches”。
- 语料 `late-nul.txt` 在现有 4 个 `-U` 用例中都不命中，差分覆盖不到。
- 建议：加 `-U` + `after nul` 的用例（目录根与单文件根各一），以 rg 实测为准调整，并重写金标准。

**N-04【建议】正则改写的几处静默差异**
- `caseless` 是全局判定（`regex.ts:165`）：只要模式某处出现 `(?i:…)`，区分大小写部分里被整类包住的字符类也会补 ASCII 大小写，造成过匹配。
- 取反嵌套类（`[a[^b]]`）与字符类集合运算（`[a-z&&[aeiou]]`、`--`、`~~`）按 RE2 语义被静默解析成另一种类，不报错；`regex.ts:7` 写“不支持”、`regex.ts:10` 写“报语法错误”，与实际不符。
- `[[]`、`[a[]` 在 rg 报“未闭合”，宿主照常匹配。
- 建议：对取反嵌套类和 `&&`/`--`/`~~` 直接报语法错误，或至少改写注释与 D-55 残余。

**N-05【建议】忽略文件按 1 MiB 截断时，最后一行可能是不完整的规则**
- 例如 `*.log.bak` 截成 `*`，会把忽略范围扩大到全部文件，造成静默漏检（只有模型自己写入超大忽略文件时才会发生）。
- 建议截断时丢弃最后一个不完整的行。

**N-06【建议】检索线程间区密钥的“清零”是部分的**
- 主线程每次 `toWire()` 生成的 base64 串、`workerData` 的结构化克隆、`ZoneCodec.fromWire` 的中间 Buffer 都不清零；worker 被 terminate 或 OOM 时 `wipe()` 不执行。
- 与复核 A 的 A09（IPC 上的 base64 密钥串）同类，建议并入同一残余登记，并把 `host-search.ts:9`“worker 结束时清零”改为“正常结束时清零”。

**N-07【建议】证据与性能数字**
- worker 的 OOM、构造失败、异常退出路径没有用例；B-18 终态幂等没有专门用例。
- 进度文档与设计 §10 的性能粗测（Grep 0.5–0.8 s 等）是主线程实现时测的。worker 化后每次检索新建 isolate 并装载模块，每个文件多一次 `stat`，这些数字需要重测。

**N-08【建议】有效单文件上限低于 256 MiB**
- 接近 256 MiB 的短行文件（解码后的字符串加千万级行数组）可能超过 1536 MB 堆，表现为“检索内存超限”错误。
- 失败可见、可以接受，建议写进 D-55 残余。
