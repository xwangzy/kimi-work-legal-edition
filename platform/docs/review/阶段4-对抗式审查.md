### 4. 闸门与内核的信任边界——基本成立（取消路径与去向记录除外）

- **授权来源**：`createGateAuthorizer`（`gate-host.ts:59-94`）先验任务令牌与用途 scope，再按 `attempts` 行核对活性与纪元，事项须与令牌所属运行一致，
  数据级别、四项依据、模型端点、全部化名、令牌化上下文全部从 `matters`/令牌存储读出；请求方只决定路径中的事项编号（与令牌核对）与路由（决定 scope）。成立。
- **在途复核**：**已复现**——复核周期 200 ms 时，令牌在流式返回途中失效，闸门 202 ms 中止上游、客户端得到截断流、记录 `failed/stream_interrupted`。
  `light` 复核结果只取 `ok/runId/matterId`，内核对 `light` 只回空令牌化上下文（`tableVersion=-1`），不会进入 `tokenizerFor`。成立。
- **撤销即中止**：**已复现**——`abortRun` 后 161 ms 上游连接关闭。但若客户端先断开（kap-host 取消或超时中止请求），`res 'close'` 只把条目移出跟踪表，
  之后撤销与复核都找不到它（见 S4-01）；`revokeToken(jti)` 不通知闸门，靠 ≤500 ms 复核兜底（可接受）。
- **内核回写令牌条目**：按事项密钥重算代号，对不上即丢弃（`matter-tokens.ts:104-121`），闸门不能把任意代号映射到任意原文。成立；碰撞竞态见 S4-08。
- **去向记录与用量**：每条去向记录写入 `egress_records` 并在同一事务中追加签名事件链（`kernel-gate.ts:180-207`）；用量按闸门请求 ID 入账，
  broker 取闸门回送的 `x-kwl-gate-request-id`，`usage_records UNIQUE(tenant_id, request_id)` 保证去重。成立（静态推断）。
  与 04 §8 EgressRecord 对照：目的地类别、用途、字数/段数、遮蔽与化名计数、请求 ID、策略版本齐；**来源对象缺失**（`doc_refs` 恒为 `"[]"`，`gate-host.ts:137`）、
  **审批缺失**（检索/抓取所依据的宿主裁决或律师批准未关联）。记录在流结束后才写（非预写）：客户端断开时**不写**（S4-01 已复现）、内核或闸门中途崩溃时也不会有记录；
  流中断时不入账用量（网关侧仍按预占结算），本机账本系统性少计。→ S4-03。
- **审计摘要**：`matters.parties.upsert/remove` 的审计载荷是**未加盐**的 `sha256(姓名)`（`api/index.ts:1245,1255`），姓名熵很低，可字典还原；
  审计链若按 02 §9.12 上送云端，等于把当事人姓名送上云。当前 G0 不上送，属潜在问题。→ S4-14。

### 5. 网关与检索服务 v0（04 §5.2–§5.3、02 §1.2-5）——部分成立；取消路径不成立

- **只有元数据**：网关计量记录字段为请求 ID、租户、席位、匿名事项编号、模型、token、耗时、状态与原因码（`gateway.ts:18-33`）；异常统一回固定文案，不记正文与上游错误体；
  检索服务计量只记席位、上游调用数、结果数、耗时、状态。成立（静态推断）。
- **席位令牌**：Ed25519 按 `kid` 选公钥、校验签名与过期、按设备与席位吊销（`seat-token/src/index.ts`）。成立；但**检索服务只传 `revokedDevices`、不查 `revokedSeats`**
  （`search-service/src/index.ts`），被吊销的席位仍可检索。→ S4-15。
- **匿名事项编号**：`HMAC(租户盐, tid‖mid)` 截 22 字符，无盐不可还原。但盐在**本机内核库**首次使用时随机生成（`kernel-gate.ts:92-97`），同一律所不同设备对同一事项得到不同编号；
  网关的“二次检查”只核对请求头自报的 `x-kwl-data-level` 与是否带编号，没有服务端的事项属性（端点许可、密级）。这是 G0 无控制面下的必然简化，但未登记为偏离，
  进度文档写“匿名事项编号与数据级别二次检查”高于事实。→ S4-04。
- **流式透传**：网关逐块透传、内存取用量、上游流式强制 `include_usage`。成立（测试覆盖）。缓存头不透传（provider 只转 `content-type`、`x-request-id`），进度文档已列为外部条件。
- **取消**：**已复现不成立**——网关在读完请求体后才注册 `req 'close'`，客户端断开后 provider 的中止信号从未触发；写回循环在已销毁的响应上等待 `drain` 永不返回，
  `finally` 不执行：`tenantConcurrency=1` 时一次断开后 3 秒再发正常请求得到 `429 tenant_queue_timeout`（`c-leak-and-scan.mts`），预占点数也不结算。
  `gateway.test.ts` 中没有任何断开用例，进度文档 P7 行“客户端断开即中止上游”无证据。→ S4-01。
- 其他：额度“先查后扣”跨越 `await acquire()`，并发下可超扣（v0 内存账本）；每次 WebSearch 扇出 3 次上游调用（2 组 `search_pro` + 1 次 `search`），
  按 04 §5.3 单价约 ¥0.04/次，单位经济测算应按实际扇出计。→ S4-15。

### 6. 结构化补丁（02 §8.4、P6）——实现成立，证据代表性不足

  真正的绑定是“还原后的锚点能在当前版本中唯一定位”。`run_id` 由调用方给出、未校验其属于本事项（只作溯源字段）。→ S4-16。

  绝对口径受 S4-08 的碰撞竞态影响。
- **100 份用例的代表性**：同一借款合同模板（6 段）、每份 1 个自然人 + 1 个手机号、每份 2 条补丁（1 条含代号锚点、1 条纯文本），文档由本仓库 `createDocx`

### 8. 总体判断

阶段 4 的骨架是对的：唯一出口的进程边界、内核作为唯一授权来源、按任务与事项记录派生出站上下文、确定性令牌、响应流原样、逐跳白名单与 DNS 钉住、
宿主按裁决一次性换令牌、结构化补丁的全有或全无，都有代码与测试支撑，且失败方向普遍是关闭。主要问题集中在三处：
**取消/断开路径**（闸门与网关都不中止上游，闸门不写去向记录，网关泄漏并发槽——阻断 P7 的“取消”项）；
**实体筛查只做逐字匹配**（P5“100%”口径不成立）；以及若干**失败开放的字段/写法覆盖**与**未登记偏离**。

## 问题清单

### S4-01 【阻断】取消/客户端断开：闸门与网关都不中止上游；闸门请求挂起且不写去向记录；网关泄漏租户并发槽（已复现）

- **位置**：`packages/egress-gate/src/server.ts:163-166`（`track()` 在 `readBody` 之后才注册 `req.on("close")`，该事件此时已发生；`res.on("close")` 只执行 `done()`
  移出跟踪表、不 abort）、`:310`（`await` 一个只等 `drain` 的 Promise，不与 `close` 竞争）；`services/legal-gateway/src/gateway.ts:214-216,228`（同一模式，`release()` 在 `finally` 中）；
  `services/search-service/src/index.ts`（同样在读完请求体后注册 `req 'close'`）。
- **复现**：`b-abort.mts`——客户端收到首块即断开，假上游 1.5 s 后仍在发送（15 块、未被关闭）；`c-leak-and-scan.mts`——断开 8 s 后（上游 2 s 已结束）
  该请求**没有任何去向记录**，跟踪表为空（撤销与周期复核都无从中止）；网关 `tenantConcurrency=1` 时一次断开后 3 s 再发正常请求返回 `429 tenant_queue_timeout`，
  provider 的中止信号从未触发。对照：先撤销后断开（`abortRun`）与复核失败两种顺序均能在 ≤ 一个周期内中止。
- **为何违反方案**：04 §11 P7 通过标准明列“取消”；04 §8 “失去租约后不得……调上游……结算费用”；`server.ts` 头注释“每一次出网（含被拦截的）都写一条去向记录”；
  进度文档 P7 行“客户端断开即中止上游”无测试支撑。真实链路中 kap-host 取消、超时或宿主退出都会先断开到闸门的连接：闸门挂起 → 不再读网关的流 → 网关写回阻塞、槽位不释放；
  缺省 4 个槽位，四次取消即可让全所模型通道持续 429 直到网关重启；预占点数不结算；本机账本缺少已发生出站的记录与用量。
- **建议**：以 `res.on("close", () => { if (!res.writableFinished) ac.abort(); })` 取代 `req 'close'`；写回改用 `stream.pipeline` 或让 `drain` 等待与 `close`/`abort` 竞争；
  `done()` 之前先 abort；网关与检索服务同改，并保证任何路径都执行 `release()` 与结算；补三类回归测试（客户端中途断开、断开后撤销、断开后再发请求不被 429）。
  内核本机端点（旧 SDK 宿主经 `/v1/chat/completions`）与 kap-host 出口宜同查同一模式（本次未核）。

### S4-02 【重要】实体筛查只做原文逐字匹配：简称、插空格、零宽字符、繁体、全角拉丁均漏过（已复现）

- **位置**：`packages/egress-gate/src/search-guard.ts:59-60`；`packages/tokenizer/src/names.ts` `matchDictionary`（`indexOf`）；`packages/egress-gate/src/url-guard.ts:172-173`。

#### S4-23 【一般】插入字符不设上限且含换行、制表：跨行、跨段落、跨表格单元的拼接被当成姓名（已复现）

### 新问题

#### S4-26 【一般】`FOLD_VERSION=2` 时存下的令牌条目在 v3 下仍按旧（含繁转简的）规范值命中，错名可复现

#### S4-27 【重要】单个换行即硬边界：被折行断开的词典姓名在材料快照与模型请求中以明文出站（已复现）

- **复现**：词典“张三”，材料或请求正文 `原告：张⏎三，男，汉族…`（以及 `\r\n`）——`tokenize` 结果原样，`processChatPayload` 出站体中为明文 `张\n三`；姓名识别器也因“张”后紧跟换行而放过。
  同一字符串作为检索式或 URL 照常被拒，说明筛查层面已知这种写法，只是推理请求不处理。
- **为何重要**：02 §8.3 与 06 T20 要求词典内的自然人姓名在推理请求中均为令牌，tokenizer 自身的原则是“偏向召回，漏识别则姓名出站”。

  S4-02/S4-18 的版本能命中这种写法，S4-23 的修复把它重新放开。

#### S4-28 【一般】“还原逐字等于原文字形”的口径仍偏高

- 已复现：机构“ABC科技有限公司”在全部化名下，原文 `abc科技有限公司`、`Abc科技有限公司` 都还原为 `ABC科技有限公司`（大小写被改写，进度文档只写了“插入字符、全角还原为半角”）；
