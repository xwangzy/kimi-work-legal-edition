## 结论：不通过

第 12 批要解决的问题方向是对的，设计里多数规则也有用例覆盖。但当前实现有 4 个阻断问题，全部稳定复现：

- **S12B-01**：第三遍判定把“自身已被拒收的降级”也算作降级。结果是互相降级后两位负责人被永久锁死，自动处置还会无限出段。
- **S12B-02**：本机写出的轮换被链拒收后，本机仍用那把未声明的密钥加密之后的内容。别人永远收不到，两边都没有任何告警。
- **S12B-05**：“本机重新引导”之后，所内任何一台设备（不必是成员）都能让本机采用它伪造的起点和密钥，本机之后写的内容随之可被对方解密。另外，“中继只认控制成员”“编号最小的合格起点”这两条在重新引导路径上都没有实现。
- **S12B-06**：唯一负责人的设备被吊销且没有交接时，所有成员设备一得知吊销，就把这台设备写过的全部成员事件当作“待定”，从投影里去掉。成员本人在本机被标为已移出，事项打不开。这同时满足了本机 Agent 数据不可逆擦除的触发条件。有两位负责人时，在吊销标记送到之前也有同样的窗口。

此外有 5 个重要问题：纪元胜者会翻转、恢复轮换的排除被自动补包裹抵消、无效事件被无上限转发、重新引导绕过暂停、处置者是单点。

## 二、逐项结论（摘要）

| 关注点 | 结论 | 条目 |
|---|---|---|
| 不同到达顺序下的一致性（有效集、投影、链头） | 同一事件集合的计算是确定的，`member-log.test` 的到达顺序用例成立。但有效性不单调：后来的事件可以让早已有效的事件失效，失效还会连带到它的后代。由此产生锁死、纪元翻转和内容永久送不到 | S12B-01、02、03 |
| 三遍判定的顺序依赖 | 第三遍用“第二遍之后的投影”找降级事件，没有排除第三遍自己拒收掉的降级。被拒收的降级仍然会让被降级者此后写的每一条事件都被拒收 | S12B-01 |
| 纪元胜者 | 规则是“作者此刻仍是负责人”的声明优先，不只看并发关系。胜者作者之后被正常降级（不是并发降级）时，旧纪元的胜者会翻转 | S12B-03 |
| 视图缓存 viewKey | 缓存键是事件条数 + `MAX(received_at‖event_id)` + 起点 + 吊销计数。事务回滚后，只要本机时钟回拨，就会返回包含已回滚事件的过期视图。吊销、重新引导、删除都会改变缓存键，没有发现问题 | S12B-04 |
| 自动处置的活性 | 本机写出的事件一旦在链上被拒收，自动处置会每个周期再写一条，没有上限，没有退避，也没有告警。处置者唯一，它离线或设备被吊销时没有回退。暂停期间只发成员链，链摘要按介质记、不按目录记 | S12B-01、10、12 |
| 吊销按链上位置 | “待定”事件被当作无效来计算投影，没有冻结在吊销前的状态。只有一位负责人、或吊销标记还没送到时，成员会在本机被投影为已移出 | S12B-06 |

| 存量锚定与混合版本 | 锚定者规则、旧成员行核对、legacy 纪元声明都按设计实现。`ZR_MEMBER_LOG=off` 只在测试运行器里生效，成立。旧客户端会忽略未知表（返回 false），成立。锚定之后，锚定者的成员行签名被全部清空，还没采用起点的设备从此收不到可采信的成员行 | S12B-14 |
| 未锚定事项的第 11 批行规则 | 逐行对比旧代码，行规则路径完整保留：`forwarderTrusted` 在应用本段之前取值，与旧代码的“段前负责人”一致；纪元冲突的判断只在未锚定事项上生效 | — |
| 迁移 0042 | 重建 `sync_alerts`：受管事务，0040/0041 的列全部复制，主键不变，没有索引或触发器丢失。安全 | — |
| 本机操作（加人、移出、节点授权与撤销、恢复轮换、移交） | 加人、移出、节点授权与撤销、恢复轮换和移交本身都按链实现；“控制成员降级须先移交”不会造成锁死（先把别人设为负责人、等对方同步一次、再移交即可）。`refreshChain` 只在本人按乐观视图是负责人时才写标记，没有发现“不该写时写”。问题有三：链上被拒收时 API 仍返回成功（S12B-01）；恢复轮换的排除会被自动补包裹抵消（S12B-09）；落选方在等待期间加人会声明落选的包裹（S12B-11） | S12B-01、09、11 |

## 三、问题清单

### 阻断

#### S12B-01　第三遍把已被拒收的降级也算作降级：互相降级后两位“负责人”被永久锁死，自动处置无限写事件

- **位置**：`member-log.ts:454-469`（第三遍）、`:946-989`（maintainChain）、`:908-929`（writeDueMarks）；`api/index.ts` 中 `matters.members.add/remove` 等的链分支（第 2595 行起）。
- **失败场景**：A、bob 两位负责人互相降级（设计第 3 节第 5 步：两条都不成立，维持原状）。
  1. 第三遍用 `p1 = project(pass2)` 判断谁“最终不是负责人”。`pass2` 里仍然包含这两条降级，所以 `demotions` 里既有 A 也有 bob。
  2. 之后 A 写的任何事件，前序都只能引用有效链头，而 bob 那条降级已被拒收、不是链头。因此 A 的新事件永远与这条降级并发，于是被拒收（`author_demoted_concurrently`）。bob 一侧同样如此。
  3. 投影里两人仍是负责人，界面和 API 都放行操作，但所有成员变更、轮换、补包裹、吊销标记都会在本机链上被拒收。
  4. 第三位负责人 C 也会被波及。例如 A 降级 bob、bob 并发降级 C、C 并发写了 X：bob 的降级被拒收，C 最终仍是负责人，但 X 和 C 之后写的事件同样被拒收（推演）。
- **活性后果**：maintainChain 的处置者按投影算出是 A，于是每次导出都给后登记的设备写一条 `wrap` 事件，这条事件被拒收，下个周期再写一条，没有上限。同理还有：`rekey_needed` 时每周期轮换一次，并且每次都 `rewindExport` 把事项内容全量重发；吊销标记被拒收时每次补写一条。中继介质上任何新的成员事件都会触发出段（`sync-engine.ts:323`），所以这些循环会变成无限出段。
- **证据（已复现）**：`r12b-member-log.test.ts`“S12B-01”。
  - 互相降级后两人都是 owner。
  - A 调用 `members.add carol` 返回成功，但投影里没有 carol，事件状态为 `rejected/author_demoted_concurrently`。bob 一侧同样。
  - erin 的设备登记后，A 连续导出 3 次，产生 3 条全部被拒收的 `wrap` 事件。
- **建议修正**：
  - 第三遍只承认本身有效的降级。可以迭代到不动点；对互相降级按 (lamport, 事件编号) 定一个确定的胜者，而不是两条都不成立或两条都成立。
  - `writeEvent` 写完后用新视图核对本条是否有效，无效就抛错，让调用方的事务回滚、API 返回失败。
  - maintainChain 对“本机刚写的事件被拒收”要记失败、退避并告警，不能每周期重写。
  - 补一条用例：互相降级之后，任意一方仍能做成员操作。

#### S12B-02　本机的轮换被链拒收后，本机仍用这把未声明的纪元加密此后的内容：别人永远收不到，两边都没有告警

- **位置**：`sync-engine.ts:145-148`（`currentMatterEpoch` 取本机持有面向自己包裹的最高纪元，不看链）、`:1019`（接收方要求段内包裹已在链上声明，否则延后）、`member-log.ts:866-867`（`superseded` 只判断“本机最高纪元在链上被别人胜出”，链上没有声明时视为没问题）、`:698-724`（rotateChainKey 先写本机包裹，再写事件，不核对事件是否有效）。
- **失败场景**：
  1. A 移出 carol，轮换到纪元 2。同时 bob 把 A 降为编辑，A 仍是成员。
  2. 合并后，A 的移出与“移出优先”规则冲突而被拒收（设计第 11 节登记了这一代价）。
  3. 但 A 本机仍持有并使用纪元 2。A 作为编辑此后写的全部内容都用纪元 2 加密。
  4. 收方没有纪元 2 的已声明包裹，整段延后；每次重试都一样。
  5. A 侧没有任何告警（链上没有纪元 2 的声明，所以 `ownKeyIsWinner` 视为没问题），bob 侧也没有。
- **同一机制的推演变体**：
  - 锚定前一刻，另一位负责人按行规则轮换出了更高的纪元（锚定者还没收到）。锚定后这个纪元没有声明，这台设备上的内容同样送不出去，要等到下一次链上轮换撞到同一个纪元号才能恢复。
  - 混合版本下，旧客户端在锚定事项上做的轮换，情形相同。
- **证据（已复现）**：“S12B-02”。
  - A 降级后 `ownEpoch = 2`。
  - A 写的“甲-降级后.txt”“甲-降级后2.txt”，bob 和 carol 都收不到。
  - `alerts(A) = alerts(bob) = []`。
- **建议修正**：
  - 链模式下，加密纪元取“链上已声明、且本机持有胜者密钥的最高纪元”。
  - 本机持有未声明的更高纪元时记告警（可复用 `epoch_superseded`，或新增一类），并回退到已声明的纪元，同时退回导出水位后重发。
  - rotateChainKey 和 addOrUpdateMember 写完后核对事件有效，无效就回滚，连同本机包裹一起撤销。

#### S12B-05　“本机重新引导”之后，所内任意设备的伪造起点即被采用：本机收下对方的密钥，此后内容可被对方解密

#### S12B-06　唯一负责人的设备被吊销（或吊销标记尚未送到）时，成员设备把它写过的全部成员事件当“待定”剔出投影：成员本人在本机被标为已移出，并触发擦除条件

- **位置**：
  - `member-log.ts:421-451`：第二遍里，未被在用设备认可的事件为 pending，并且不进入有效集。
  - `:485`：投影只看有效集。
  - `:560-564`（applyProjection）：本机行不在投影里就写 `removed_at`。
  - `index.ts:589-600`：每次同步后运行的擦除，条件是“本人成员行 removed_at 非空且没有有效行”，即复核 B3-A19 所说的“正向证据”。
- **失败场景**：
  1. 律所里最常见的形态是创建者 A 一人担任负责人，成员都由 A 的设备加入。
  2. A 的电脑丢失或离所，控制面下发吊销。
  3. 每台成员设备只要收到任意一段带链的段，就重算投影。A 设备写的“加 bob”“加 carol”变成 pending，bob、carol 在各自本机都被写上 `removed_at`。结果是打不开事项（requireMatterAccess 返回 404），并满足 Agent 数据的不可逆擦除条件（推演：需要本机有该事项的 `matter_ws_keys`）。
  4. 只有在用的负责人设备写吊销标记才能恢复，但唯一的负责人就是 A。设备编号由成员 slug 决定（`dev_<律所>_<成员>`），A 的“新电脑”沿用同一编号，这个编号已在吊销墓碑里，所以没有任何在用负责人设备能写标记。
  5. 有两位负责人时，同样的窗口出现在“成员设备先从控制面得知吊销、后收到另一位负责人的标记”之间。控制面的吊销通常先到，所以这个窗口在实际中很常见（推演）。
- **证据（已复现）**：“S12B-06”。
  - carol 导出时出现 `chain_pending` 并暂停。
  - bob 摄取 carol 的段后，`role(bob, bob).live = 0`，`role(bob, carol).live = 0`。
  - `matters.member_log` 报“事项不存在或无权查看”。
- **建议修正**：
  - 被吊销设备写的待定事件只用于冻结（暂停发出、禁止新的成员变更），不应从投影里拿掉。投影在标记到达之前保持吊销前的状态，或者把“吊销之前收下的事件”默认按在用对待，与写标记时的 `liveBefore` 同一口径。
  - applyProjection 在链上有待定事件时，不应把行标为已移出。
  - 擦除只应凭链上有效的移出事件触发。
  - 补一个单负责人吊销的用例。设计第 12 节的残余里应写明“唯一负责人设备吊销且未交接”的出路（例如经恢复托管由律所管理员重新锚定）。

### 重要

#### S12B-03　纪元胜者按“作者此刻是否负责人”判定，结果不单调：胜者作者之后被正常降级，旧纪元的胜者就会翻转，全员落入 epoch_superseded，而无人持有新胜者的密钥

- **位置**：`member-log.ts:486-498`（`ownerNow` 用最终投影来排序声明）、`:761-801`（落选方的包裹行早已被胜者的替换）、`:964`（superseded 时不自动轮换）。
- **失败场景**：
  1. A、bob 并发移出 carol，纪元 2 分叉。按编号，一方 W 胜出；败方 L 本机的纪元 2 已换成 W 的密钥（替换 UPDATE 了原行）。
  2. 之后 L 把 W 正常降为编辑。这条降级不与 W 的声明并发。
  3. `ownerNow(W) = false`，纪元 2 的胜者翻转为 L 原来那份声明。可是 L 手里的已是 W 的密钥，L 原来那把已不在任何设备上。
  4. L 和 W 都进入 `epoch_superseded` 并暂停。界面写的“收到被采用的那把后自动恢复”永远不会发生。
  5. 翻转如果发生在较旧的纪元（不是最高纪元），不会告警，但该纪元的已声明包裹全部换成了落选那份的摘要。之后加入的设备、恢复托管都拿不到能解开该纪元内容的密钥（推演）。
- **证据（已复现）**：“S12B-03”。
  - 降级之后 L 导出：`alerts = ["epoch_superseded"]`，`pausedConflict = [m]`。
  - W 收到后同样如此。
  - 往返同步两轮仍不解除。
- **建议修正**：去掉 `ownerNow` 排序。被降级者并发的轮换已经由第三遍拒收，纪元胜者只按 (lamport, 编号) 定，与之后的成员变化无关。界面同时给出手工出路（负责人再轮换一次）。

#### S12B-09　恢复轮换排除的“吊销候选”设备，会被处置者下一次导出时自动补包裹，排除失效

- **位置**：`api/index.ts:3038-3043`（`rotateChainKey` 带 `exclude`）、`member-log.ts:964-985`（补包裹：在册成员的在用设备不在当前纪元包裹里就补）。
- **失败场景**：`recovery.restore_matter` 的返回提示是“revoke_device_ids 中的设备……解不开新内容（请随后 devices.revoke 吊销丢失设备）”。轮换之后、吊销之前，丢失设备仍是在用状态，处置者（刚轮换的本人）下一次导出就写 `wrap` 事件把它补回去。第 11 批的行规则路径没有自动补包裹，这是本批引入的回退。
- **证据（已复现）**：“S12B-09”。
  - 轮换当下，bob 的设备不在纪元 2。
  - A 同步一次后出现 `wrap` 事件，A 本机有给 bob 设备的纪元 2 包裹。
  - bob 读到“轮换后.txt”。
- **建议修正**：在 rekey 事件里声明被排除的设备（例如 `excluded: [...]`），补包裹时跳过。或者只给晚于该纪元声明登记的设备补包裹。另要求 `revoke_device_ids` 先吊销再轮换。

#### S12B-07　无效事件（被拒收的、缺前序的、外来起点）永久存下，并由每台设备在之后每一段里全量转发，没有条数和体积上限

- **位置**：`member-log.ts:121-123`（exportEventRows 导出全部事件）、`:216-228`（入库不设上限）、`sync-engine.ts:172`（每段全量附带）、`:323`（中继介质任何成员事件都触发出段）。
- **失败场景**：任一成员可以签发大量 `author_not_owner` 或缺前序的事件。单条最大 256 KiB，条数不限。每台收到的设备都会存下，并在此后每一段里转发，在中继介质上还会触发出段。设计说的“只计不停”只做到了“不停”，没有限量。
- **证据（已复现）**：“S12B-07”。bob（编辑）伪造 40 条缺前序事件，dave 不告警但全部存下，dave 的下一段里全量带上，A 收到后同样存下。
- **建议修正**：
  - 只转发有效事件和作者确曾是链上负责人的待定事件。7886ac7 已不转发拒收的事件，但缺前序的仍会转发。
  - 按作者设置待定事件的条数和体积上限。
  - 链行按增量导出（例如带上对方已知的链头），不要每段全量。

#### S12B-08　重新引导会解除暂停（失败即关闭被绕过），而且解决不了 chain_pending；界面却引导用户去点

- **位置**：`member-log.ts:1007`（清 `sync_alerts`）、`sync-engine.ts:442`（重新引导待定时 prepareChain 直接返回）、`index.ts:709-710`（定时器先导出、后摄取）、`TeamShare.tsx:67`、`relay-text.ts:15`。
- **失败场景**：
  1. carol 有 chain_pending（例如被吊销设备写的事件待定），点“本机重新引导”。
  2. 告警被清掉，下一次导出不再暂停，照常发出内容，用的仍是本机当前纪元，被移出者可能持有这一纪元的密钥。
  3. 重新收到链之后，又回到同样的 chain_pending，因为同一批事件、同一个吊销状态得出同样的结果。
- **证据（已复现）**：“S12B-06”中 S12B-08 那一段。
  - 重新引导后导出：`pausedConflict = []`，`rowsExported > 0`。
  - 收到 bob 的段之后，再次出现 `chain_pending`。
- **建议修正**：重新引导期间保持暂停（7886ac7 已写入一条 chain_pending）。chain_pending 的说明不要再引导用户点“本机重新引导”。只在 root_conflict 时显示这个按钮，并写明它解决不了“等待在用负责人确认”。

#### S12B-10　处置者是单点：处置者离线、设备被吊销或已不在所时，rekey_needed 会让全员无限期暂停；各设备视图不同时，“处置者唯一”也不成立

- **位置**：`member-log.ts:956-957`、`:992-996`（defaultRotator）、`sync-engine.ts:431-433`（中继事项固定为控制成员）。
- **失败场景**：
  - 中继事项的处置者固定为控制成员。他离线或离所（设备被吊销）时，`rekey_needed` 下所有成员设备都只发成员链、不发内容。其他负责人不能接手，界面也没有说明要等谁。
  - 共享文件夹事项的处置者是“当前纪元胜者作者，否则编号最小的负责人”。胜者作者的设备全部被吊销、但他在链上仍是负责人时，同样没人轮换。
  - 两台设备的视图不同时，两边各自认定处置者，会并发轮换。之后能收敛，但“只有一位”的说法不准确（推演）。
- **建议修正**：
  - 处置者超时（例如 N 小时没有新的有效事件）后，由下一位在册负责人接手；处置者的设备全部被吊销时，直接跳过他。
  - 告警说明写出在等谁。
  - 中继事项的控制成员离所只能找客服，这一点写进告警说明。

### 一般

#### S12B-04　视图缓存键在“事务回滚 + 本机时钟回拨”时会命中过期视图

- **位置**：`member-log.ts:316-338`。
- **失败场景**：
  1. 在事务里插入事件 e1 后，有人读过视图，然后事务回滚。
  2. 之后插入另一条事件 e2。如果 e2 的 `received_at` 早于库里已有的最大值（本机时钟被同步回拨），条数和 `MAX(received_at‖event_id)` 都与回滚前的缓存键相同。
  3. 结果返回的视图里有已回滚的 e1，没有已落库的 e2。
- **证据（已复现）**：“S12B-04”，直接插行模拟。
- **建议修正**：缓存键改用单调计数，例如在 `member_chain` 里存一个随事件写入递增的版本号（用触发器维护），或者用 `MAX(rowid)`。

#### S12B-11　落选方在等待期间加人：用落选的密钥给新设备包裹，并在胜者的纪元上声明摘要，处置者因此认为“已有包裹”、不再补

- **位置**：`member-log.ts:729-748`（addOrUpdateMember 取本机最高纪元和本机密钥，不检查是否落选）、`:499-509`（追加的包裹只要是胜者声明的后代就计入）、`:970`（补包裹只看 `top.wraps.has(device)`）。
- **失败场景**：本机处于 `epoch_superseded` 时，负责人仍可加人（`requireNoSyncAlert` 只拦 `owner_unverifiable`）。新成员设备收到包裹后，指纹不符，不落库；而处置者认为它已有包裹，不会再补，直到下一次轮换（推演）。
- **建议修正**：链模式下 `requireNoSyncAlert` 同时拦 `epoch_superseded`；或者 addOrUpdateMember 在本机密钥不是胜者时不写 `wraps`。补包裹不要只看“有没有声明”，还要看“声明的是不是胜者的密钥”（可以要求追加声明里带指纹）。

#### S12B-12　暂停期间“只发成员链”的去重摘要按介质记，不按目录或接收方记，也不含包裹

- **位置**：`sync-engine.ts:475-494`（`chain_paused_export`）。
- **失败场景**：
  - 换了共享目录、或同一介质下有多个接收方时，链没变就不会再发，新目录里永远收不到这条链。复现 S12B-03 时，对第二个目录导出就没有出段，可以观察到。
  - 摘要只包含事件编号。本机补了包裹但链没变时（例如 `acceptKeyRows` 收下了别人转发的包裹），也不会再发。
- **建议修正**：摘要里加上共享目录（或中继实例）和 `matter_keys` 的摘要。

#### S12B-13　界面与提示文字

- `relay-text.ts:15`（chain_pending）：“长期不恢复可点‘本机重新引导’”。重新引导解决不了这类告警，在 e446567 上还会解除暂停、引入抢占（S12B-05、08），应删去。
- `relay-text.ts:21`（root_conflict）、`TeamShare.tsx:38` 的确认框、`api/index.ts:2873` 的返回提示：“按最先同步该事项的负责人重新确认成员”。实际情况是：
  - 共享文件夹介质：第一个被处理的、带合格起点的段说了算。
  - 中继介质：不核对控制成员。
  - 移交之后，控制成员也已不是“最先同步者”。
- `relay-text.ts:19`（epoch_superseded）：“收到被采用的那把后自动恢复并补发”。S12B-03 中永远不会恢复，应写出手工出路：负责人在其电脑上再轮换一次，即移出后再加回任一成员。
- `relay-text.ts:17`（rekey_needed）：“等负责人的电脑自动换新密钥”。没有说是哪一位。中继事项只有控制成员能处理（S12B-10）。
- `api/index.ts:3413-3414`（requireRelayController）：仍写“最先同步该事项的负责人（X）”“请联系中软客服办理负责人交接”。移交之后 X 不是最先同步者；控制成员仍是负责人时，交接可以自助完成（`matters.relay_handoff`）。
- `relay.status` / `sync.status` 不含链概况（是否锚定、待定条数、本机加密纪元是否已在链上声明）。S12B-02 的状态（本机内容送不出去）在任何状态接口和界面上都看不到。建议在 `sync.status` 的事项项里加上 `chainSummary`，以及“本机加密纪元是否已声明”。

#### S12B-14　锚定之后，锚定者的成员行签名全部清空：还没采用起点的设备从此收不到可采信的成员行

- **位置**：`member-log.ts:545-552`（投影写回时把 `author_sig/author_cert` 置空）、`sync-engine.ts:302-303`（链模式下不再签名成员行）。
- **失败场景**：
  1. 某成员设备的旧成员行还认不出锚定者是负责人，例如提升他的那一行是由已吊销设备签的，即第 11 批的 S11A-52 情形。这台设备不能采用锚定（`rootAcceptable` 非引导时要求本机旧行里锚定者是负责人）。
  2. 而锚定者和所有已锚定的设备此后发出的成员行都不带签名，行规则路径一律不收。
  3. 这台设备只能等到所有尚未锚定的设备都不再发出带签名的旧行，之后就永远停在旧状态，只有人工重新引导能解（推演）。
- **建议修正**：锚定后继续按第 11 批规则签名并随段附带锚定前那一版成员行（只读，供未锚定设备认出锚定者）。或者让 `owner_unverifiable` 告警也提供“本机重新引导”入口，并写明后果。

#### S12B-15　测试：互相降级用例断言的正是锁死状态，中继介质的成员链几乎没有覆盖

- `member-log.test.ts` 的“并发……互相降级”只断言“两人都仍是 owner、两条降级都被拒收”，没有断言之后两人还能操作，恰好断言在 S12B-01 的锁死状态上。7886ac7 已改成“两条都成立”。如果事项只有这两位负责人，这样会变成“零负责人”，没有人能再写任何事件，也没有人能补轮换（推演，供处置时参考）。
- `member-log-relay.test.ts` 文件头声称覆盖“经中继的存量事项由控制成员锚定”，但文件里只有移交这一个用例。以下路径都没有用例：
  - 中继介质的锚定；
  - `exportChainOnly` 经中继发出；
  - 中继上的重新引导与 `refetchHistory`；
  - “任何新成员事件都触发出段”的收敛；
  - 中继介质的 `rewindExport`。
- 没有覆盖的设计行为：
  - 唯一负责人吊销（S12B-06）；
  - 缺前序事件的 `chain_pending`（`pendingMissing` 路径）及其解除；
  - `epoch_superseded` 在中继介质上的解除与补发；
  - `root_conflict` 中同一作者的另一个起点自动切换（e446567 的 `adoptRoot` 第 579-583 行）。

#### S12B-16　改写后的第 11 批用例有几处变弱或名不副实

#### S12B-17　其他

- `rewindExport` 退到 `"0000"` 全量重发（`sync-engine.ts:458-462`），而设计第 5 节写的是“退回到输家声明之前”。中继介质上，大事项每次落选或补轮换都会全量重发；与 S12B-01 的轮换循环叠加时，代价会被放大。建议按落选声明的时刻退回。

- `matters.sync_rebootstrap` 允许已被移出的成员调用（只要求曾有成员行）。如果它在本机只用于清理，没有问题；但它会触发中继重取全部历史，建议限流。
