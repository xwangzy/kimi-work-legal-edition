## 结论：不通过

第 12 批要解决的问题方向是对的，设计里多数规则也有用例覆盖。但当前实现有 4 个阻断问题，全部稳定复现：

- **S12B-01**：第三遍判定把“自身已被拒收的降级”也算作降级。结果是互相降级后两位负责人被永久锁死，自动处置还会无限出段。
- **S12B-02**：本机写出的轮换被链拒收后，本机仍用那把未声明的密钥加密之后的内容。别人永远收不到，两边都没有任何告警。
- **S12B-05**：“本机重新引导”之后，所内任何一台设备（不必是成员）都能让本机采用它伪造的起点和密钥，本机之后写的内容随之可被对方解密。另外，“中继只认控制成员”“编号最小的合格起点”这两条在重新引导路径上都没有实现。
- **S12B-06**：唯一负责人的设备被吊销且没有交接时，所有成员设备一得知吊销，就把这台设备写过的全部成员事件当作“待定”，从投影里去掉。成员本人在本机被标为已移出，事项打不开。这同时满足了本机 Agent 数据不可逆擦除的触发条件。有两位负责人时，在吊销标记送到之前也有同样的窗口。

此外有 5 个重要问题：纪元胜者会翻转、恢复轮换的排除被自动补包裹抵消、无效事件被无上限转发、重新引导绕过暂停、处置者是单点。

## 二、逐项结论（摘要）

| 关注点 | 结论 | 条目 |
|---|---|---|
| 不同到达顺序下的一致性（有效集、投影、链头） | 同一事件集合的计算是确定的，`member-log.test` 的到达顺序用例成立。但有效性不单调：后来的事件可以让早已有效的事件失效，失效还会连带到它的后代。由此产生锁死、纪元翻转和内容永久送不到 | S12B-01、02、03 |
| 三遍判定的顺序依赖 | 第三遍用“第二遍之后的投影”找降级事件，没有排除第三遍自己拒收掉的降级。被拒收的降级仍然会让被降级者此后写的每一条事件都被拒收 | S12B-01 |
| 纪元胜者 | 规则是“作者此刻仍是负责人”的声明优先，不只看并发关系。胜者作者之后被正常降级（不是并发降级）时，旧纪元的胜者会翻转 | S12B-03 |
| 视图缓存 viewKey | 缓存键是事件条数 + `MAX(received_at‖event_id)` + 起点 + 吊销计数。事务回滚后，只要本机时钟回拨，就会返回包含已回滚事件的过期视图。吊销、重新引导、删除都会改变缓存键，没有发现问题 | S12B-04 |
| 自动处置的活性 | 本机写出的事件一旦在链上被拒收，自动处置会每个周期再写一条，没有上限，没有退避，也没有告警。处置者唯一，它离线或设备被吊销时没有回退。暂停期间只发成员链，链摘要按介质记、不按目录记 | S12B-01、10、12 |

| 未锚定事项的第 11 批行规则 | 逐行对比旧代码，行规则路径完整保留：`forwarderTrusted` 在应用本段之前取值，与旧代码的“段前负责人”一致；纪元冲突的判断只在未锚定事项上生效 | — |
| 迁移 0042 | 重建 `sync_alerts`：受管事务，0040/0041 的列全部复制，主键不变，没有索引或触发器丢失。安全 | — |
| 本机操作（加人、移出、节点授权与撤销、恢复轮换、移交） | 加人、移出、节点授权与撤销、恢复轮换和移交本身都按链实现；“控制成员降级须先移交”不会造成锁死（先把别人设为负责人、等对方同步一次、再移交即可）。`refreshChain` 只在本人按乐观视图是负责人时才写标记，没有发现“不该写时写”。问题有三：链上被拒收时 API 仍返回成功（S12B-01）；恢复轮换的排除会被自动补包裹抵消（S12B-09）；落选方在等待期间加人会声明落选的包裹（S12B-11） | S12B-01、09、11 |

## 三、问题清单

### 阻断

#### S12B-01　第三遍把已被拒收的降级也算作降级：互相降级后两位“负责人”被永久锁死，自动处置无限写事件

- **位置**：`member-log.ts:454-469`（第三遍）、`:946-989`（maintainChain）、`:908-929`（writeDueMarks）；`api/index.ts` 中 `matters.members.add/remove` 等的链分支（第 2595 行起）。
- **失败场景**：A、bob 两位负责人互相降级（设计第 3 节第 5 步：两条都不成立，维持原状）。
  1. 第三遍用 `p1 = project(pass2)` 判断谁“最终不是负责人”。`pass2` 里仍然包含这两条降级，所以 `demotions` 里既有 A 也有 bob。
  2. 之后 A 写的任何事件，前序都只能引用有效链头，而 bob 那条降级已被拒收、不是链头。因此 A 的新事件永远与这条降级并发，于是被拒收（`author_demoted_concurrently`）。bob 一侧同样如此。
  3. 投影里两人仍是负责人，界面和 API 都放行操作，但所有成员变更、轮换、补包裹、吊销标记都会在本机链上被拒收。
  4. 第三位负责人 C 也会被波及。例如 A 降级 bob、bob 并发降级 C、C 并发写了 X：bob 的降级被拒收，C 最终仍是负责人，但 X 和 C 之后写的事件同样被拒收（推演）。
- **活性后果**：maintainChain 的处置者按投影算出是 A，于是每次导出都给后登记的设备写一条 `wrap` 事件，这条事件被拒收，下个周期再写一条，没有上限。同理还有：`rekey_needed` 时每周期轮换一次，并且每次都 `rewindExport` 把事项内容全量重发；吊销标记被拒收时每次补写一条。中继介质上任何新的成员事件都会触发出段（`sync-engine.ts:323`），所以这些循环会变成无限出段。
- **证据（已复现）**：`r12b-member-log.test.ts`“S12B-01”。
  - 互相降级后两人都是 owner。
  - A 调用 `members.add carol` 返回成功，但投影里没有 carol，事件状态为 `rejected/author_demoted_concurrently`。bob 一侧同样。
  - erin 的设备登记后，A 连续导出 3 次，产生 3 条全部被拒收的 `wrap` 事件。
- **建议修正**：
  - 第三遍只承认本身有效的降级。可以迭代到不动点；对互相降级按 (lamport, 事件编号) 定一个确定的胜者，而不是两条都不成立或两条都成立。
  - `writeEvent` 写完后用新视图核对本条是否有效，无效就抛错，让调用方的事务回滚、API 返回失败。
  - maintainChain 对“本机刚写的事件被拒收”要记失败、退避并告警，不能每周期重写。
  - 补一条用例：互相降级之后，任意一方仍能做成员操作。

#### S12B-02　本机的轮换被链拒收后，本机仍用这把未声明的纪元加密此后的内容：别人永远收不到，两边都没有告警

- **位置**：`sync-engine.ts:145-148`（`currentMatterEpoch` 取本机持有面向自己包裹的最高纪元，不看链）、`:1019`（接收方要求段内包裹已在链上声明，否则延后）、`member-log.ts:866-867`（`superseded` 只判断“本机最高纪元在链上被别人胜出”，链上没有声明时视为没问题）、`:698-724`（rotateChainKey 先写本机包裹，再写事件，不核对事件是否有效）。
- **失败场景**：
  1. A 移出 carol，轮换到纪元 2。同时 bob 把 A 降为编辑，A 仍是成员。
  2. 合并后，A 的移出与“移出优先”规则冲突而被拒收（设计第 11 节登记了这一代价）。
  3. 但 A 本机仍持有并使用纪元 2。A 作为编辑此后写的全部内容都用纪元 2 加密。
  4. 收方没有纪元 2 的已声明包裹，整段延后；每次重试都一样。
  5. A 侧没有任何告警（链上没有纪元 2 的声明，所以 `ownKeyIsWinner` 视为没问题），bob 侧也没有。
- **同一机制的推演变体**：
  - 锚定前一刻，另一位负责人按行规则轮换出了更高的纪元（锚定者还没收到）。锚定后这个纪元没有声明，这台设备上的内容同样送不出去，要等到下一次链上轮换撞到同一个纪元号才能恢复。
  - 混合版本下，旧客户端在锚定事项上做的轮换，情形相同。
- **证据（已复现）**：“S12B-02”。
  - A 降级后 `ownEpoch = 2`。
  - A 写的“甲-降级后.txt”“甲-降级后2.txt”，bob 和 carol 都收不到。
  - `alerts(A) = alerts(bob) = []`。
- **建议修正**：
  - 链模式下，加密纪元取“链上已声明、且本机持有胜者密钥的最高纪元”。
  - 本机持有未声明的更高纪元时记告警（可复用 `epoch_superseded`，或新增一类），并回退到已声明的纪元，同时退回导出水位后重发。
  - rotateChainKey 和 addOrUpdateMember 写完后核对事件有效，无效就回滚，连同本机包裹一起撤销。

#### S12B-05　“本机重新引导”之后，所内任意设备的伪造起点即被采用：本机收下对方的密钥，此后内容可被对方解密

#### S12B-06　唯一负责人的设备被吊销（或吊销标记尚未送到）时，成员设备把它写过的全部成员事件当“待定”剔出投影：成员本人在本机被标为已移出，并触发擦除条件

- **位置**：
  - `member-log.ts:421-451`：第二遍里，未被在用设备认可的事件为 pending，并且不进入有效集。
  - `:485`：投影只看有效集。
  - `:560-564`（applyProjection）：本机行不在投影里就写 `removed_at`。
  - `index.ts:589-600`：每次同步后运行的擦除，条件是“本人成员行 removed_at 非空且没有有效行”，即复核 B3-A19 所说的“正向证据”。
- **失败场景**：
  1. 律所里最常见的形态是创建者 A 一人担任负责人，成员都由 A 的设备加入。
  2. A 的电脑丢失或离所，控制面下发吊销。
  3. 每台成员设备只要收到任意一段带链的段，就重算投影。A 设备写的“加 bob”“加 carol”变成 pending，bob、carol 在各自本机都被写上 `removed_at`。结果是打不开事项（requireMatterAccess 返回 404），并满足 Agent 数据的不可逆擦除条件（推演：需要本机有该事项的 `matter_ws_keys`）。
  4. 只有在用的负责人设备写吊销标记才能恢复，但唯一的负责人就是 A。设备编号由成员 slug 决定（`dev_<律所>_<成员>`），A 的“新电脑”沿用同一编号，这个编号已在吊销墓碑里，所以没有任何在用负责人设备能写标记。
  5. 有两位负责人时，同样的窗口出现在“成员设备先从控制面得知吊销、后收到另一位负责人的标记”之间。控制面的吊销通常先到，所以这个窗口在实际中很常见（推演）。
- **证据（已复现）**：“S12B-06”。
  - carol 导出时出现 `chain_pending` 并暂停。
  - bob 摄取 carol 的段后，`role(bob, bob).live = 0`，`role(bob, carol).live = 0`。
  - `matters.member_log` 报“事项不存在或无权查看”。
- **建议修正**：
  - 被吊销设备写的待定事件只用于冻结（暂停发出、禁止新的成员变更），不应从投影里拿掉。投影在标记到达之前保持吊销前的状态，或者把“吊销之前收下的事件”默认按在用对待，与写标记时的 `liveBefore` 同一口径。
  - applyProjection 在链上有待定事件时，不应把行标为已移出。
  - 擦除只应凭链上有效的移出事件触发。
  - 补一个单负责人吊销的用例。设计第 12 节的残余里应写明“唯一负责人设备吊销且未交接”的出路（例如经恢复托管由律所管理员重新锚定）。

### 重要

#### S12B-03　纪元胜者按“作者此刻是否负责人”判定，结果不单调：胜者作者之后被正常降级，旧纪元的胜者就会翻转，全员落入 epoch_superseded，而无人持有新胜者的密钥

- **位置**：`member-log.ts:486-498`（`ownerNow` 用最终投影来排序声明）、`:761-801`（落选方的包裹行早已被胜者的替换）、`:964`（superseded 时不自动轮换）。
- **失败场景**：
  1. A、bob 并发移出 carol，纪元 2 分叉。按编号，一方 W 胜出；败方 L 本机的纪元 2 已换成 W 的密钥（替换 UPDATE 了原行）。
  2. 之后 L 把 W 正常降为编辑。这条降级不与 W 的声明并发。
  3. `ownerNow(W) = false`，纪元 2 的胜者翻转为 L 原来那份声明。可是 L 手里的已是 W 的密钥，L 原来那把已不在任何设备上。
  4. L 和 W 都进入 `epoch_superseded` 并暂停。界面写的“收到被采用的那把后自动恢复”永远不会发生。
  5. 翻转如果发生在较旧的纪元（不是最高纪元），不会告警，但该纪元的已声明包裹全部换成了落选那份的摘要。之后加入的设备、恢复托管都拿不到能解开该纪元内容的密钥（推演）。
- **证据（已复现）**：“S12B-03”。
  - 降级之后 L 导出：`alerts = ["epoch_superseded"]`，`pausedConflict = [m]`。
  - W 收到后同样如此。
  - 往返同步两轮仍不解除。
- **建议修正**：去掉 `ownerNow` 排序。被降级者并发的轮换已经由第三遍拒收，纪元胜者只按 (lamport, 编号) 定，与之后的成员变化无关。界面同时给出手工出路（负责人再轮换一次）。

#### S12B-09　恢复轮换排除的“吊销候选”设备，会被处置者下一次导出时自动补包裹，排除失效

- **位置**：`api/index.ts:3038-3043`（`rotateChainKey` 带 `exclude`）、`member-log.ts:964-985`（补包裹：在册成员的在用设备不在当前纪元包裹里就补）。
- **失败场景**：`recovery.restore_matter` 的返回提示是“revoke_device_ids 中的设备……解不开新内容（请随后 devices.revoke 吊销丢失设备）”。轮换之后、吊销之前，丢失设备仍是在用状态，处置者（刚轮换的本人）下一次导出就写 `wrap` 事件把它补回去。第 11 批的行规则路径没有自动补包裹，这是本批引入的回退。
- **证据（已复现）**：“S12B-09”。
  - 轮换当下，bob 的设备不在纪元 2。
  - A 同步一次后出现 `wrap` 事件，A 本机有给 bob 设备的纪元 2 包裹。
  - bob 读到“轮换后.txt”。
- **建议修正**：在 rekey 事件里声明被排除的设备（例如 `excluded: [...]`），补包裹时跳过。或者只给晚于该纪元声明登记的设备补包裹。另要求 `revoke_device_ids` 先吊销再轮换。

#### S12B-07　无效事件（被拒收的、缺前序的、外来起点）永久存下，并由每台设备在之后每一段里全量转发，没有条数和体积上限

- **位置**：`member-log.ts:121-123`（exportEventRows 导出全部事件）、`:216-228`（入库不设上限）、`sync-engine.ts:172`（每段全量附带）、`:323`（中继介质任何成员事件都触发出段）。
- **失败场景**：任一成员可以签发大量 `author_not_owner` 或缺前序的事件。单条最大 256 KiB，条数不限。每台收到的设备都会存下，并在此后每一段里转发，在中继介质上还会触发出段。设计说的“只计不停”只做到了“不停”，没有限量。
- **证据（已复现）**：“S12B-07”。bob（编辑）伪造 40 条缺前序事件，dave 不告警但全部存下，dave 的下一段里全量带上，A 收到后同样存下。
- **建议修正**：
  - 只转发有效事件和作者确曾是链上负责人的待定事件。7886ac7 已不转发拒收的事件，但缺前序的仍会转发。
  - 按作者设置待定事件的条数和体积上限。
  - 链行按增量导出（例如带上对方已知的链头），不要每段全量。

#### S12B-08　重新引导会解除暂停（失败即关闭被绕过），而且解决不了 chain_pending；界面却引导用户去点

- **位置**：`member-log.ts:1007`（清 `sync_alerts`）、`sync-engine.ts:442`（重新引导待定时 prepareChain 直接返回）、`index.ts:709-710`（定时器先导出、后摄取）、`TeamShare.tsx:67`、`relay-text.ts:15`。
- **失败场景**：
  1. carol 有 chain_pending（例如被吊销设备写的事件待定），点“本机重新引导”。
  2. 告警被清掉，下一次导出不再暂停，照常发出内容，用的仍是本机当前纪元，被移出者可能持有这一纪元的密钥。
  3. 重新收到链之后，又回到同样的 chain_pending，因为同一批事件、同一个吊销状态得出同样的结果。
- **证据（已复现）**：“S12B-06”中 S12B-08 那一段。
  - 重新引导后导出：`pausedConflict = []`，`rowsExported > 0`。
  - 收到 bob 的段之后，再次出现 `chain_pending`。
- **建议修正**：重新引导期间保持暂停（7886ac7 已写入一条 chain_pending）。chain_pending 的说明不要再引导用户点“本机重新引导”。只在 root_conflict 时显示这个按钮，并写明它解决不了“等待在用负责人确认”。

#### S12B-10　处置者是单点：处置者离线、设备被吊销或已不在所时，rekey_needed 会让全员无限期暂停；各设备视图不同时，“处置者唯一”也不成立

- **位置**：`member-log.ts:956-957`、`:992-996`（defaultRotator）、`sync-engine.ts:431-433`（中继事项固定为控制成员）。
- **失败场景**：
  - 中继事项的处置者固定为控制成员。他离线或离所（设备被吊销）时，`rekey_needed` 下所有成员设备都只发成员链、不发内容。其他负责人不能接手，界面也没有说明要等谁。
  - 共享文件夹事项的处置者是“当前纪元胜者作者，否则编号最小的负责人”。胜者作者的设备全部被吊销、但他在链上仍是负责人时，同样没人轮换。
  - 两台设备的视图不同时，两边各自认定处置者，会并发轮换。之后能收敛，但“只有一位”的说法不准确（推演）。
- **建议修正**：
  - 处置者超时（例如 N 小时没有新的有效事件）后，由下一位在册负责人接手；处置者的设备全部被吊销时，直接跳过他。
  - 告警说明写出在等谁。
  - 中继事项的控制成员离所只能找客服，这一点写进告警说明。

### 一般

#### S12B-04　视图缓存键在“事务回滚 + 本机时钟回拨”时会命中过期视图

- **位置**：`member-log.ts:316-338`。
- **失败场景**：
  1. 在事务里插入事件 e1 后，有人读过视图，然后事务回滚。
  2. 之后插入另一条事件 e2。如果 e2 的 `received_at` 早于库里已有的最大值（本机时钟被同步回拨），条数和 `MAX(received_at‖event_id)` 都与回滚前的缓存键相同。
  3. 结果返回的视图里有已回滚的 e1，没有已落库的 e2。

- **建议修正**：缓存键改用单调计数，例如在 `member_chain` 里存一个随事件写入递增的版本号（用触发器维护），或者用 `MAX(rowid)`。

#### S12B-11　落选方在等待期间加人：用落选的密钥给新设备包裹，并在胜者的纪元上声明摘要，处置者因此认为“已有包裹”、不再补

- **位置**：`member-log.ts:729-748`（addOrUpdateMember 取本机最高纪元和本机密钥，不检查是否落选）、`:499-509`（追加的包裹只要是胜者声明的后代就计入）、`:970`（补包裹只看 `top.wraps.has(device)`）。
- **失败场景**：本机处于 `epoch_superseded` 时，负责人仍可加人（`requireNoSyncAlert` 只拦 `owner_unverifiable`）。新成员设备收到包裹后，指纹不符，不落库；而处置者认为它已有包裹，不会再补，直到下一次轮换（推演）。
- **建议修正**：链模式下 `requireNoSyncAlert` 同时拦 `epoch_superseded`；或者 addOrUpdateMember 在本机密钥不是胜者时不写 `wraps`。补包裹不要只看“有没有声明”，还要看“声明的是不是胜者的密钥”（可以要求追加声明里带指纹）。

#### S12B-12　暂停期间“只发成员链”的去重摘要按介质记，不按目录或接收方记，也不含包裹

- **位置**：`sync-engine.ts:475-494`（`chain_paused_export`）。
- **失败场景**：
  - 换了共享目录、或同一介质下有多个接收方时，链没变就不会再发，新目录里永远收不到这条链。复现 S12B-03 时，对第二个目录导出就没有出段，可以观察到。
  - 摘要只包含事件编号。本机补了包裹但链没变时（例如 `acceptKeyRows` 收下了别人转发的包裹），也不会再发。
- **建议修正**：摘要里加上共享目录（或中继实例）和 `matter_keys` 的摘要。

#### S12B-13　界面与提示文字

- `relay-text.ts:15`（chain_pending）：“长期不恢复可点‘本机重新引导’”。重新引导解决不了这类告警，在 e446567 上还会解除暂停、引入抢占（S12B-05、08），应删去。
- `relay-text.ts:21`（root_conflict）、`TeamShare.tsx:38` 的确认框、`api/index.ts:2873` 的返回提示：“按最先同步该事项的负责人重新确认成员”。实际情况是：
  - 共享文件夹介质：第一个被处理的、带合格起点的段说了算。
  - 中继介质：不核对控制成员。
  - 移交之后，控制成员也已不是“最先同步者”。
- `relay-text.ts:19`（epoch_superseded）：“收到被采用的那把后自动恢复并补发”。S12B-03 中永远不会恢复，应写出手工出路：负责人在其电脑上再轮换一次，即移出后再加回任一成员。
- `relay-text.ts:17`（rekey_needed）：“等负责人的电脑自动换新密钥”。没有说是哪一位。中继事项只有控制成员能处理（S12B-10）。
- `api/index.ts:3413-3414`（requireRelayController）：仍写“最先同步该事项的负责人（X）”“请联系中软客服办理负责人交接”。移交之后 X 不是最先同步者；控制成员仍是负责人时，交接可以自助完成（`matters.relay_handoff`）。
- `relay.status` / `sync.status` 不含链概况（是否锚定、待定条数、本机加密纪元是否已在链上声明）。S12B-02 的状态（本机内容送不出去）在任何状态接口和界面上都看不到。建议在 `sync.status` 的事项项里加上 `chainSummary`，以及“本机加密纪元是否已声明”。

#### S12B-14　锚定之后，锚定者的成员行签名全部清空：还没采用起点的设备从此收不到可采信的成员行

- **位置**：`member-log.ts:545-552`（投影写回时把 `author_sig/author_cert` 置空）、`sync-engine.ts:302-303`（链模式下不再签名成员行）。
- **失败场景**：
  1. 某成员设备的旧成员行还认不出锚定者是负责人，例如提升他的那一行是由已吊销设备签的，即第 11 批的 S11A-52 情形。这台设备不能采用锚定（`rootAcceptable` 非引导时要求本机旧行里锚定者是负责人）。
  2. 而锚定者和所有已锚定的设备此后发出的成员行都不带签名，行规则路径一律不收。
  3. 这台设备只能等到所有尚未锚定的设备都不再发出带签名的旧行，之后就永远停在旧状态，只有人工重新引导能解（推演）。
- **建议修正**：锚定后继续按第 11 批规则签名并随段附带锚定前那一版成员行（只读，供未锚定设备认出锚定者）。或者让 `owner_unverifiable` 告警也提供“本机重新引导”入口，并写明后果。

#### S12B-15　测试：互相降级用例断言的正是锁死状态，中继介质的成员链几乎没有覆盖

- `member-log.test.ts` 的“并发……互相降级”只断言“两人都仍是 owner、两条降级都被拒收”，没有断言之后两人还能操作，恰好断言在 S12B-01 的锁死状态上。7886ac7 已改成“两条都成立”。如果事项只有这两位负责人，这样会变成“零负责人”，没有人能再写任何事件，也没有人能补轮换（推演，供处置时参考）。
- `member-log-relay.test.ts` 文件头声称覆盖“经中继的存量事项由控制成员锚定”，但文件里只有移交这一个用例。以下路径都没有用例：
  - 中继介质的锚定；
  - `exportChainOnly` 经中继发出；
  - 中继上的重新引导与 `refetchHistory`；
  - “任何新成员事件都触发出段”的收敛；
  - 中继介质的 `rewindExport`。
- 没有覆盖的设计行为：
  - 唯一负责人吊销（S12B-06）；
  - 缺前序事件的 `chain_pending`（`pendingMissing` 路径）及其解除；
  - `epoch_superseded` 在中继介质上的解除与补发；
  - `root_conflict` 中同一作者的另一个起点自动切换（e446567 的 `adoptRoot` 第 579-583 行）。

#### S12B-16　改写后的第 11 批用例有几处变弱或名不副实

#### S12B-17　其他

- `rewindExport` 退到 `"0000"` 全量重发（`sync-engine.ts:458-462`），而设计第 5 节写的是“退回到输家声明之前”。中继介质上，大事项每次落选或补轮换都会全量重发；与 S12B-01 的轮换循环叠加时，代价会被放大。建议按落选声明的时刻退回。

- `matters.sync_rebootstrap` 允许已被移出的成员调用（只要求曾有成员行）。如果它在本机只用于清理，没有问题；但它会触发中继重取全部历史，建议限流。

  - 报复例外只放行不带 `key`、`wraps` 的成员事件；带了就按 `author_demoted_concurrently` 拒收（或者只承认其中的成员变更、忽略声明）。
  - 同理，纪元声明的作者如果在最终投影里不是负责人，且这条声明与他的降级并发，则这条声明不参与胜者。这不同于 S12B-03 的 `ownerNow`：只排除“与降级并发”的声明，不影响已正常生效的声明。
  - 补用例：本用例反转断言。

#### 重要

##### S12B-18　缓存键没有覆盖“删除后重新收下同一批事件”：重新引导后返回过期视图，`r12b` S12B-06/08 末段靠它通过

- **位置**：`member-log.ts:358-367`（键为起点、条数、最后一行的编号、吊销计数）、`:1089-1099`（rebootstrapMatter 删除事件），以及 `:462-465`（有效性取决于本机收下时刻 `received` 与吊销时刻的比较）。
- **失败场景**：
  1. carol 在唯一负责人 A 的设备被吊销后导出过一次，视图进入缓存。
  2. 她随后重新引导，再从 bob 收回同一批事件。
  3. 起点、条数、最后一行编号都与之前相同，于是返回旧视图：全部有效，没有告警。
  4. 按真实状态，这批事件是吊销之后才收下的，A 的加人事件为 `revoked_unvouched` 待定，应当 `chain_pending` 并永久暂停（没有在用负责人能写标记）。
  5. 任何一次缓存失效（新事件、新的吊销记录、重启）后，真实状态才出现。
  6. 新登记的成员设备首同步时，同样会永久停在 `chain_pending`。设计第 12 节的残余写的是“成员不受影响”，对新设备和重新引导的设备不成立。另外，设计第 3 节开头写“确定性，与到达顺序无关”，但实际上有效性取决于本机收下时刻，同一组事件在不同设备上可以永久得出不同的有效集。
- **证据（已复现）**：`r12b2` S12B-18。
  - 缓存视图全部为 `valid`，`alerts = []`。
  - 不走缓存的视图（`liveBefore = new Map()`）里，两条加人事件为 `pending/revoked_unvouched`。
  - 插入一条不相干的吊销记录使缓存失效后，导出得到 `alerts = ["chain_pending"]`、`pausedConflict = [m]`。
- **建议修正**：
  - 缓存键改用单调版本号，例如 `member_chain` 里随每次增删递增的计数，或 `MAX(rowid)` 加删除计数。
  - `r12b` S12B-06/08 的末段改写为如实断言。
  - 重新引导时保留原来的 `received_at`（按 `event_id` 记在独立表里），或在设计里写明“唯一负责人吊销后，新设备和重新引导的设备永久暂停”，并改正第 3 节的表述。

##### S12B-19　第三遍“迭代到不动点”在循环降级时不收敛：8 轮后取最后一轮的结果，被降级者并发的操作成立

- **位置**：`member-log.ts:491-518`。
- **失败场景**：
  1. 负责人 A、bob、carol、dave。A 把 bob 降为编辑，bob 把 carol 降为编辑，carol 把 A 降为编辑，三条互相并发。另外 bob 在降级 carol 之后，又把 mallory 加为负责人。
  2. 第 0 轮：三条降级都在，三条都被拒收，bob 的加人作为后代也被拒收。
  3. 第 1 轮：没有降级，什么都不拒收。之后第 0、1 轮的结果交替出现，8 轮结束时停在第 7 轮的结果（拒收集为空）。
  4. 结果：三人都被降级，但 bob 与降级他的事件并发写的“mallory 为负责人”成立，违反“移出优先于被移出者的并发操作”。
  5. 这种情形本来就不存在不动点，每一种取舍都与规则矛盾。现在的结果只是轮数奇偶的产物。
- **证据（已复现）**：`r12b2` S12B-19。dave 那里 8 条事件全部为 `valid`，A、bob、carol 都是 editor，mallory 是 owner。
- **建议修正**：
  - 检测到振荡（或到达轮数上限）时，取保守的确定结果。例如：所有轮里出现过的降级都成立；同时，这些降级的对象与降级并发写的、不属于报复的事件，全部拒收。
  - 或者在第三遍里对循环降级按 (lamport, 编号) 定一个胜者。
  - 补用例。

##### S12B-21　待定事件“冻结”成员行：任一成员伪造一条缺前序、关于某人的事件，就能让负责人移不掉新加的人，并让被移出者在各设备上仍显示在册（也不擦除）

- **位置**：
  - `member-log.ts:573-581`、`:606-610`（applyProjection 对 `pendingUsers` 整行跳过，包括有效事件带来的加人、改角色和移出）。
  - `:128-137`、`:900-903`：缺前序的伪造事件“只计不停”、不转发，但每台直接读取伪造者段的设备都会存下。
  - `api/index.ts:2664`（移出时按 `matter_members` 找目标）。
  - `api/index.ts:220-229`、`index.ts:590-600`（访问与擦除都读 `matter_members`）。
- **失败场景**：
  1. 编辑 bob 签一条 `prev` 指向不存在编号、关于 erin 的成员事件，放进共享文件夹。所有成员设备都存下，事件状态为待定，不告警。
  2. 负责人 A 随后加入 erin：接口返回成功，链上有效，erin 的设备也拿到了包裹。但 A 的本机成员表里查不到 erin，`members.remove erin` 返回“事项成员不存在”，A 没有办法通过接口移出 erin。之后每次轮换仍按链上投影把 erin 包进去。
  3. 在 erin 自己的设备上没有她的成员行，她打不开这个事项。
  4. 同理，对已在册的 carol 伪造一条后，A 移出 carol 成功，但 A 和 carol 本机的成员行都停在“在册”：carol 照样能打开事项，也不触发擦除。
  5. 合法的缺前序事件（中继上到达顺序不同）也会造成短暂冻结。
- **证据（已复现）**：`r12b2` S12B-21。
  - 加入 erin 后，`role(A, erin) = undefined`，移出时报“成员”不存在。
  - 移出 carol 后，`role(A, carol).live = 1`，`role(carol, carol).live = 1`。
- **建议修正**：
  - 冻结只针对 `chainHealth` 计入的待定事件（`pendingRevoked`，以及作者是在册负责人、经在册成员转发的 `pendingMissing`），不针对任意待定事件。
  - 冻结只抑制“据待定把人移出”这一方向；有效事件带来的加人、改角色、移出照常写回。
  - 成员管理接口按链上投影查找目标。

##### S12B-22　恢复轮换的 `excluded` 只在自动补包裹里生效

- **位置**：`member-log.ts:780-800`（addOrUpdateMember 给对方全部在用设备包当前纪元）、`:749-767`（rotateChainKey 只用本次传入的 `exclude`）。
- **失败场景**：

##### S12B-24　`relay_handoff` 先改中继、后写链：链上写入失败时接口报 409，但控制成员实际已经移交

- **位置**：`api/index.ts:2843-2867`。负责人检查在 `await handoffControl` 之前，写 `control` 事件在之后。
- **失败场景**：等待中继答复期间，同步摄取到“本人已被降级”，`writeEvent` 随即不成立、抛错。用户看到“这次成员变更在成员链上不成立”，但中继上控制成员已经是对方。再试一次会报“只有中继上的控制成员可以移交”。链上没有 `control` 事件，其他设备看不到移交（推演）。
- **建议修正**：
  - 写链失败时，按中继的回复如实说明“中继上已移交，链上记录未写入”。
  - 或者先在本机核一次（`writeEvent` 之前用视图判断本人是否仍是负责人），再调中继；中继成功后写链失败的，下次 maintainChain 补写 `control`。

##### S12B-25　存储上限只按条数，伪造者的段仍被直接读取全量存下

- **位置**：`member-log.ts:140-153`、`:235-253`、`:114-121`（每次重算视图都 `loadEvents` 全量解析）。
- **失败场景**：
  - 共享文件夹和中继上，各设备直接读取伪造者自己的段，转发过滤管不到。
  - 单条可达 256 KiB，5000 条约 1.25 GiB，每个事项、每台设备都要存一份，每次缓存失效都要全量 `JSON.parse`。
  - 达到上限后，判断“在册负责人”用的是 `matter_members`，而它可能被 S12B-21 冻结：新晋负责人的事件在该设备上被丢弃，其后代缺前序待定。
- **证据（推演）**：上一轮的 S12B-07 复现中，dave 直接存下了 bob 的 40 条伪造事件，这条路径本轮没有变。
- **建议修正**：
  - 按作者限制待定事件的条数和字节数。
  - 单条体积上限按种类收紧（成员、标记、控制事件远小于 256 KiB）。
  - 上限判断改按链上投影。

##### S12B-26　maintainChain 的自动处置失败没有任何可观测性

- **位置**：`sync-engine.ts:431-440`（`maintain` 吞掉所有异常）、`:1157-1162`（摄取后的 catch 已不可达，`member_log_maintain_failed` 永远不会出现）、`member-log.ts:1069-1071`。
- **失败场景**：处置者的补轮换或补包裹在链上一直不成立（例如本人已被并发降级）时，每个周期都尝试、回滚，没有警告。告警文字仍写“等负责人（X）的电脑同步时自动换新密钥”。
- **建议修正**：
  - 失败时把原因写进该事项的告警 `detail`，或新增一类，并做退避。
  - 删掉不可达的 catch，或让 `maintain` 把错误返回给调用方。

##### S12B-27　文字与状态

- `matters.members.add`：本机密钥落选、不包裹时，返回的提示是“对方尚无登记设备”，与实际不符，应写“由处置者稍后补包裹”。
- `sync.status.member_log` 没有本机加密纪元，无法看出 S12B-20 或 S12B-02 变体的状态。桌面端也不读 `member_log`。
- 告警里的 `peer_member` 显示的是成员编号，例如 `usr_xxx_bob`，不是姓名。
- `root_conflict` 的说明和确认框没有写明：重新引导后采用哪一个起点，取决于先收到谁的段。

#### 建议

- **S12B-28**：收回纪元（删除包裹）和退回导出水位不在同一事务里，`maintainChain` 返回 `rewindSince` 之后由调用方再退水位。如果在两步之间崩溃，下一次就找不到那些包裹了：`continue` 跳过，不再退水位。按 S12B-20 改为“撤回使用、不删除”后，这个问题自然消失。
- **S12B-29**：超时接手是所有其他负责人同时轮换，之后靠纪元分叉的规则收敛。这样可行，但告警说明里的“其他负责人的电脑会接手”可以写明“可能各自换一次，随后自动统一”。另外建议在 `rekey_needed` 的 `detail` 里写出预计接手的时刻。
- **S12B-30**：`r12b` S12B-02 和 S12B-09 只覆盖了最简单的情形。建议把 S12B-20、22 反转后补进这两个回归用例。S12A-02 的回归用例里，报复事件不带纪元，覆盖不到 S12B-23。

### 7.4 结论：不通过

第一轮的 4 个阻断里，01、05、06 的所述形态已修复，02 部分修复。但处置本身引入了 2 个新的阻断，都已稳定复现，后果都是“被移出者读到新内容，且全员没有告警”：

- **S12B-20**：被拒收后删除的轮换又成立，链上纪元无人持有，全员退回旧纪元。
- **S12B-23**：报复例外和“胜者只按全序”叠加，被移出者自己生成的纪元胜出。

另有 3 个重要问题：缓存在重新引导后返回过期视图，回归用例因此误报通过（S12B-18）；循环降级不收敛（S12B-19）；待定事件冻结成员行，导致负责人移不掉成员（S12B-21）。

建议修正 S12B-20、23、18、21 并把对应用例反转后，再做一轮复核。

#### 阻断

##### S12B-31　材料块按“本机持有包裹的最高纪元”加密，不看链：在册成员本机留着被移出者生成、链上已不成立的纪元，新材料用它加密，被移出者解得开

- **位置**：
  - `blob-cipher.ts:25-29`：`encrypt` 取 `MAX(epoch) FROM matter_keys WHERE wrapped_for = 本机`。
  - `sync-engine.ts:341-361`：块以“同一份密文，不经二次加解密”原样复制到共享目录。
  - `member-log.ts:881-921`：`acceptKeyRows` 在声明有效时收下包裹，之后声明不成立也不清理，本轮起也不再删除任何纪元。
- **失败场景**：
  1. A、bob 是负责人，carol 是编辑。A 把 bob 降为编辑并移出，轮换到纪元 2。
  2. 同时，尚未收到 A 的段的 bob 用正常客户端先后移出 dave、erin，在他那边轮换到纪元 2、3。
  3. carol 先收到 bob 的段。那时 bob 的轮换有效，carol 收下纪元 2、3 的包裹（密钥都是 bob 生成的）。
  4. carol 再收到 A 的段：bob 的两次移出被拒收（`author_demoted_concurrently`），纪元 2 的胜者换成 A 的那份，本机的纪元 2 被替换。但纪元 3 的包裹（bob 的密钥）仍留在 carol 本机。
  5. carol 的段按纪元 2 加密，不暂停、没有告警。她此后导入的材料，块按本机最高纪元 3 加密，随段复制到共享目录。
  6. bob 已被移出，但仍能读共享目录，用他自己的纪元 3 密钥即可解开。
- **证据（已复现）**：`r12b3` S12B-31。
  - carol 那里 `encrypt_epoch = 2`，本机最高纪元为 3，`alerts = []`。
  - 共享目录里该材料块的块头纪元为 3。
  - 用 bob 设备解出的纪元 3 密钥 `openBlob` 得到原文。
- **说明**：第二轮时段和块都按本机最高纪元加密，所以第二轮也有这个问题（7.1 中 S12B-02 未处理的变体）。本轮只改了段。中继介质上，纪元提升后 bob 不再是读者，下载不到块，所以泄露限于共享文件夹介质，以及其他能拿到块密文的途径。
- **建议修正**：
  - 链模式的事项，块加密纪元一律取 `chainEncryptEpoch`；取不到时不写块，或暂不出段。
  - 链上不成立、又不是本机写的纪元，其包裹不得用于任何加密：`acceptKeyRows` 标记来源，或在视图变化时把这类纪元记为“只可解密”。
  - `recovery.restore_matter` 取链上已声明的最高纪元，不取托管包裹的最高纪元。
  - 补用例：本用例反转断言。

##### S12B-35　“认可”与“已标记”的判据不一致：两位负责人的设备先后吊销后，在册成员的加入事件被拒收，成员被移出并触发擦除

- **位置**：`member-log.ts:478-486`。`vouched` 只算 `!devState(...).revoked` 的事件；`marked` 仍按 `isLive(x)`，即吊销前收下的标记也算。
- **失败场景**：
  1. A、bob 是负责人。A 加入 carol（事件 E）。A 的设备被吊销。
  2. bob 写吊销标记 M，M 引用 E。carol 第一次收到这条链：E 是在 A 吊销之后收下的，由 M 认可，有效。
  3. 之后 bob 换电脑，旧设备被吊销。
  4. 在 carol 那里：M 的作者设备已吊销，M 不再“认可”E；但 M 是在 bob 吊销之前收下的，`marked` 仍含 A 的设备。于是 E 变为 `rejected/revoked_after_mark`，其后代（包括 M 本身、A 加 bob 为负责人的事件）全部 `parent_rejected`。
  5. carol 不在投影里，也不在 `pendingUsers` 里（她的加入事件是拒收，不是待定）。`maintainChain` 末尾的 `applyProjection` 在下一次导出时把她的行标为已移出，`purgeLocalAgentData` 随即擦除本机的 Agent 数据，访问检查也拒绝她。
  6. 即使之后有在用的负责人再写事件认可回来，擦除已经发生。在只有这两位负责人的事项里，也没有人能再认可回来。
- **证据（已复现）**：`r12b3` S12B-35。
  - 吊销 bob 之前，carol 那里全部有效，她在册。
  - 吊销之后，不走缓存的视图里 E 为 `rejected:revoked_after_mark`，`role(carol).live = 0`，`matters.member_log` 返回“事项不存在或无权查看”。
- **建议修正**：
  - 认可与标记用同一个判据。要么都按 `isLive`（吊销前收下的标记既算认可也算标记，恢复原来的行为），要么都按“未吊销”（这时 E 是待定，受 `pendingUsers` 保护，暂停而不移出）。
  - 再加一道兜底：成员的移出只由“有效的移出事件”触发，“因拒收而从投影里消失”不触发擦除，只告警。
  - 补用例：本用例反转断言。

##### S12B-36　两步报复 + 正常段：两份纪元 2 声明都不算，“延后段只收在册成员签发的链”这道闸门让先收到不同一方的成员永久各认一套成员，被移出者读到新内容

- **位置**：
  - `member-log.ts:562-568`（`keyIgnored`：作者有并发且成立的降级的事件，其声明不算，移出者自己的那份也包括在内）。
  - `sync-engine.ts:1044-1046`：用段里的包裹解开的段，链上不认可就 `BootstrapDeferred`，整段回滚。
  - `sync-engine.ts:1142-1152`：延后时只在“签发成员在本机未移出”时另存链。
- **失败场景**：
  1. A 把 bob 降为编辑并移出（纪元 2）。bob 用正常客户端，先把 A 降为编辑、再移出 A（他那边的纪元 2）。两边的段都用各自的纪元 2 加密。
  2. dave 先收到 bob 的段：A 被移出，bob 是负责人，纪元 2 是 bob 的。
  3. dave 再收到 A 的段：用段里的包裹解开、存链，按全量链判，两份纪元 2 声明都在 `keyIgnored` 里，纪元 2 无人声明，于是 `segmentKeyDeclared` 不成立，整段回滚。A 在 dave 那里已被移出，延后时也不另存他的链。此后 A 的每一段都是同样结果，dave 永远收不下 A 的链。
  4. carol 先收到 A 的段，情形对称：她永远收不下 bob 的链。
  5. 结果：dave 认为 bob 是负责人、A 已移出；carol 认为 A 是负责人、bob 已移出。dave 不暂停、没有告警，此后按 bob 的纪元 2 加密，A 移出的 bob 读得到 dave 的新内容。
- **证据（已复现）**：`r12b3` S12B-36。
  - 双方的段反复互送两轮后：`role(dave, bob) = owner`，`role(dave, A).live = 0`；`role(carol, bob).live = 0`，`role(carol, A) = owner`。
  - dave 的链里没有 A 移出 bob 的事件，`alerts(dave) = []`。
  - dave 之后的段 `key_epoch = 2`，用 bob 的纪元 2 密钥 `openSegmentBody` 能看到“丁-之后.txt”。
- **说明（推演）**：第二轮按 (lamport, 编号) 定纪元胜者，胜者那一方的段能被另一侧收下，所以约一半的情形会收敛。本轮两份声明都不算，于是这种情形必然分裂。
- **建议修正**：
  - 根因是摄取的闸门：链事件可以独立核验，延后时另存链不应取决于“签发成员此刻在本机是否在册”（这一点恰恰由尚未收全的链决定）。改为：只要事件核验通过、作者曾是该链的成员，就另存，由条数与字节上限防滥用。
  - 或者在 `keyIgnored` 导致某纪元无人声明时，允许用该纪元任一份声明（按全序最小者）的包裹解段、只取链行，不收内容与包裹。
  - 补用例：正常客户端、正常段、两侧先收到不同一方。

##### S12B-32　本机的轮换被拒收后，新材料块仍按那把链上不存在的纪元加密：其他成员收不下材料（本轮不删密钥带来的回退）

- **位置**：`blob-cipher.ts:25-29`；`member-log.ts:1094-1103`（只退导出水位、重发行，不重封块）。
- **失败场景**：
  1. A 移出 carol，轮换到纪元 2；同时 bob 把 A 降为编辑。A 收到 bob 的段后，自己的轮换不成立，段改按纪元 1 加密。
  2. 但 A 此后导入的材料，块仍按本机最高纪元 2 加密。
  3. bob 收到文档行，块却解不开（`blob_mismatch`，未复制），永远读不到这份材料。
  4. 第二轮删除密钥时，这种情形下的块是按纪元 1 加密的，所以这是本轮的回退。
  5. 同理（推演）：轮换不成立之前，用那把密钥写下的块，在“重发一次”时只重发行，块密文不变，收方仍解不开。所以“重发”对材料本身无效。
- **证据（已复现）**：`r12b3` S12B-32。A 的 `encrypt_epoch = 1`，`alerts = []`；共享目录里块头纪元为 2；bob 摄取结果含 `blob_mismatch`，`blobs.read` 抛错。
- **建议修正**：
  - 同 S12B-31：块加密取 `chainEncryptEpoch`。
  - 重发时，把本机按不成立纪元封的块用加密纪元重封。块名是明文摘要，可以原地重封，再退水位。

##### S12B-33　两步报复：“移出只在对方于该事件因果过去里已不是负责人时才算报复”挡不住正常客户端——先降级、再移出，移出者自己也被移出

- **位置**：`member-log.ts:522-530`（`ownerInPast`）；`api/index.ts` 的移出要求先降级负责人。
- **失败场景**：
  1. A 把 bob 降为编辑并移出。bob 用正常客户端，先降级 A、再移出 A。
  2. 第二步的因果过去里含 bob 自己刚做的降级，A 已不是负责人，于是按报复成立。
  3. 结果是 A、bob 两人都被移出。A 本机的成员行标为已移出、触发擦除。纪元 2 的两份声明都不算，纪元 1 仍包含两人，需要轮换，却再无负责人，于是全员永久暂停。
- **证据（已复现）**：`r12b3` S12B-33。carol 那里 bob 移出 A 的事件为 `valid`，A、bob 都 `live = 0`，导出后告警含 `rekey_needed`。

##### S12B-37　`member_rewinds` 只重发一次：本机轮换“不成立 → 成立 → 再不成立”时，第二段成立期间按新纪元发出的内容永远送不到

##### S12B-39　恢复轮换的排除是永久的、没有撤回途径；被排除设备的告警文字误导

##### S12B-41　`chainEncryptEpoch` 为空时退回本机最高纪元

### 9.2 新发现

#### 阻断

##### S12B-43　链上在用标记即视为吊销，对目标不做任何核对：任何负责人（包括正被移出者）给一台在用的负责人设备写一条标记，就能撤销对方并发的移出，并永久锁死对方

- **位置**：
  - `member-log.ts:475-492`：`liveMarks` 取第一遍的全部标记，只排除本机已知被吊销作者写的；`devState` 里 `revoked = local || liveMarks.has(dev)`，`at = null`。
  - `member-log.ts:512`、`:591`：未认可的事件，只要目标设备有在用标记就判 `rejected/revoked_after_mark`。
  - `member-log.ts:199`：`mark` 的正文只核名字格式。
- **失败场景**：
  1. A、bob 是负责人，carol 是编辑。A 把 bob 降为编辑并移出（纪元 2）。
  2. bob 尚未收到。他用改过的客户端签一条 `mark {device: A 的设备}`（他在因果过去里是负责人，第一遍成立），随纪元 1 的段送出。
  3. carol 与 A 都有纪元 1，都收下这条链。A 的设备在所有电脑上都被当作已吊销、吊销时刻不明。A 的降级与移出不在这条标记的祖先里，没有在用设备认可，判为拒收。
  4. 结果：
     - bob 仍是负责人，没有被移出；纪元 2 的声明随之不成立，所有人回到纪元 1 加密，bob 读得到此后的全部内容。
     - carol 只得到一条 `revoked_change`（只提示、不暂停），文字是“一台已停用的电脑做过的移出没有生效”，而 A 的电脑并没有停用。A 本机没有任何告警。
     - A 本机也把自己的设备当作已吊销，此后写的任何成员事件都核效失败，接口返回“负责人身份已被其他负责人的变更取消”。
     - 正常客户端不会给未吊销的设备写标记，A 无法反制。第三位负责人也认可不了 A 在标记之后写的事件。降级或移出 bob 也撤不掉这条标记，因为它写下时 bob 还是负责人。
  5. 不涉及并发时同样成立：任何负责人随时都能这样把另一位负责人静默废掉。被盗设备在吊销传开之前也能这样做，期间被拒收的加人事件会让成员被标为已移出，并触发擦除。
- **证据（已复现）**：`r12b4` S12B-43。
  - carol 那里 A 的降级为 `rejected:revoked_after_mark`，bob 为 `owner`、在册，`encrypt_epoch = 1`，导出 `pausedConflict = []`，告警只有 `revoked_change`，`peer_device` 是 A 的设备。
  - A 本机 bob 恢复为负责人，`alerts = []`，`matters.members.add` 被拒。
- **建议修正**：
  - 本机不知道 d 已吊销时，标记只能让 d 写的、不在标记祖先里的事件变为**待定**（暂停、受冻结保护），不能拒收。同时立即同步一次控制面设备目录。目录确认 d 未吊销后，这条标记不算，并记一条“负责人对在用设备写了吊销标记”的告警（点名作者）。
  - `revoked_change` 只给本机已知被吊销的设备记，文字不能把在用设备说成已停用。
  - 补用例：本用例反转断言，另加“被盗设备在吊销传开之前给在用负责人写标记”。

##### S12B-44　并发轮换落选后，本机纪元 N 的密钥被原地换成胜者的那把：之前用落选密钥封的块不重封，密钥缓存也不失效——别人收不下，本机重启后自己也读不出

- **位置**：
  - `member-log.ts:956-960`：`acceptKeyRows` 用 `UPDATE` 覆盖本机纪元 N 的包裹，落选的那把从库里消失。
  - `blobs.ts:142`：`reseal` 在 `h.epoch === currentEpoch` 时直接返回。
  - `sync-engine.ts:446`：`good(N)` 按“已声明，且本机此刻持有的是胜者”判断，替换之后为真。
  - `blob-cipher.ts:26-35`：缓存键是“事项 + 纪元号”，替换之后不失效。
- **失败场景**：
  1. A、bob 并发移出不同的人，各自轮换到纪元 2。A 的那份 lamport 更小，胜出。
  2. bob 在收到 A 的段之前导入材料，块按 bob 的纪元 2 封。
  3. bob 收到 A 的段，本机纪元 2 换成 A 的那把，`replacedSelf` 让导出水位退回。
  4. bob 之后导出：这个块的纪元号与当前纪元相同，不重封，原样复制出去，carol 那里块不符、读不到。bob 在同一进程里新写的材料，由于缓存，仍用落选密钥封，结果相同。carol 发来的、按胜者纪元 2 封的块，bob 用缓存里的落选密钥核对，也是块不符、不复制。
  5. bob 重启之后缓存清空，库里只有胜者的那把，他在落选期间写的材料自己也解不开，而且没有任何地方还留着落选的那把。这是数据丢失。
- **证据（已复现）**：`r12b4` S12B-44。
  - 两份材料在共享目录的块头都是纪元 2，carol 收到文档行但 `blobs.read` 抛错。
  - bob 摄取 carol 的段时 `originConflicts` 含 `blob_mismatch`。
  - 用不带缓存的新块加密器读 bob 自己落选期间写的材料，抛错。
- **说明**：替换包裹的做法在第二轮就有，本轮处置宣称“落选纪元封的块先重封”，但这一种情形没有覆盖到。
- **建议修正**：
  - 替换本机包裹之前，先把用旧密钥封的该事项全部块解开、按胜者密钥重封（或者保留落选密钥为“只可解密”，不覆盖）。
  - 替换时清空该事项、该纪元的块密钥缓存，或者缓存键加上密钥指纹。
  - 更稳妥的做法是在导出时统一处理：每个随段发出的块，纪元或指纹与本段的加密密钥不一致的，先重封再复制或登记。这样可以同时堵住 S12B-31、32、44、45。
  - 补用例：本用例反转断言。

##### S12B-45　`rekey_needed` 暂停期间写下的材料块按当前纪元封，而这个纪元仍包给已移出的成员；轮换之后块原样发出，被移出者从共享目录解开

- **位置**：
  - `blob-cipher.ts:17-24`、`member-log.ts:898-909`（`chainEncryptEpoch` 只看“已声明 + 本机持有胜者”）。
  - `sync-engine.ts:358-362`：块原样复制。
  - `resealUndeclared` 只在本机自己的轮换不成立时运行，而且不重封已声明的纪元。
- **失败场景**（正常客户端，不需要任何恶意行为）：
  1. A 移出 dave，bob 移出 carol，两人并发，各自轮换到纪元 2。A 的胜出，A 的纪元 2 包给了 carol。
  2. carol 收到 A 的段，持有 A 的纪元 2。bob 合并之后，纪元 2 里有已移出的 carol，于是 `rekey_needed`，bob 暂停，等处置者 A。
  3. 暂停期间 bob 导入材料，块按纪元 2 封。设计的意图正是“这个纪元已不安全，所以暂停”。
  4. A 轮换到纪元 3，bob 恢复，导出时把这个块原样复制到共享目录。
  5. carol 已被移出，用纪元 2 解开这份材料。块名是明文摘要，共享目录里可以逐个尝试。
- **证据（已复现）**：`r12b4` S12B-45。bob 恢复后 `encrypt_epoch = 3`、`alerts = []`；共享目录里块头纪元为 2；carol 的纪元 2 密钥 `openBlob` 得到原文。
- **说明**：
  - 第三轮之前同样存在（当时按本机最高纪元，也是 2）。它和 S12B-31 都是“被移出者读到新材料”，本轮的块加密修正没有覆盖到。
  - 只影响共享文件夹介质。中继介质上，纪元提升后 carol 不是读者，取不到块。
  - 同类情形（推演）：本机在等新纪元包裹时（`epoch_superseded`），`chainEncryptEpoch` 退回更低的已声明纪元，那个纪元可能包含在新纪元里被移出的成员，期间写下的块同样会原样发出。
- **建议修正**：
  - 同 S12B-44 的“导出时统一重封”，块一律按本段的加密纪元封；
  - 或者在有 `rekey_needed`、`epoch_superseded` 告警时拒绝写入新材料，像 `null` 一样处理。
  - 补用例：本用例反转断言。

##### S12B-46　两步报复时只要有第三位负责人，他的电脑就在同一次处置里自动轮换：`member_conflict` 随即算作已处置，从未暂停、从未提示，两位负责人都被移出，各自不知情

- **位置**：
  - `member-log.ts:1213`：`iRotate` 不看 `memberConflict`。
  - `member-log.ts:1055-1057`：任何第三位在册负责人写的、以两条为祖先的事件都算作“已处置”，包括自动轮换、补包裹和标记。
- **失败场景**：
  1. A、bob、carol 是负责人。A 降级并移出 bob，bob 降级并移出 A，两边都用正常客户端。
  2. carol 收齐两条链：两份纪元 2 的声明都不算，纪元 1 仍包给两人，于是 `rekey_needed`。处置者按 `defaultRotator` 落到 carol（纪元 1 的胜者 A 已不是负责人）。carol 的电脑立即自动轮换，冲突解除，告警在同一次 `refreshChainAlerts` 里就被清掉。
  3. 结果：
     - A、bob 都被移出。新纪元不包给他们，两人都收不到 carol 的段，本机仍以为自己是负责人、没有告警，此后写的内容在别人那里一直延后。
     - carol 那边从没见过告警。这与告警文字“请其他负责人核实后重新调整成员”、设计第 6 节“其他负责人重新调整成员”都不符。
- **证据（已复现）**：`r12b4` S12B-46。
  - carol 的链里有成立的 `rekey`，A、bob 都 `live = 0`，没有 `member_conflict`，导出不暂停。

- **建议修正**：
  - 有 `memberConflict` 时不自动轮换、不自动补包裹。解除条件改为第三位负责人的**人工**成员操作（接口路径写的 `member` 或 `rekey` 事件，不算 `wrap`、`mark`，也不算自动处置的事件）。
  - 在第三位负责人那里显示告警，写明需要通知两人。
  - 补用例：本用例反转断言。

#### 一般

##### S12B-48　`revoked_change` 的解除条件过宽：按 lamport 大小、不按因果，自动写的事件也算“已处理”

- **位置**：`member-log.ts:1072-1075`。
- **场景（推演）**：解除的第三个条件是“任何在用负责人设备写的、lamport 更大的非标记事件”。这包括：
  - 与被拒收的移出并发、根本没看到它的事件；
  - 处置者自动写的 `wrap` 或 `rekey`。
  在 S12A-10 的场景里，只要处置者给后登记的设备补一次包裹，“请负责人重做移出”的提示就消失，而墙并没有立起来。
- **建议**：只认以该事件为祖先的、人工发起的成员事件（同 S12B-46 的“人工”判据）。

##### S12B-49　S12A-14 的“再判一次”不是不动点：再判后不成立的降级，在第三遍造成的拒收不撤回

- **位置**：`member-log.ts:584-597`。
- **场景（推演）**：
  1. 被吊销设备 d 在吊销后写了降级 X 的事件 D，只由负责人 Y 的事件 v 认可。Y 同时被 Z 降级，v 在第三遍拒收。
  2. 第三遍里，X 与 D 并发的事件（例如 X 移出 mallory）已因 D 拒收。
  3. 再判一次时 D 失去认可，判为拒收（有标记时）或待定，但 X 的那些事件仍是 `author_demoted_concurrently`。
  4. 有标记时，X 的移出被静默拒收，`revoked_change` 只看 `revoked_after_mark`，不会提示。
- **建议**：再判之后，用剩下的集合回到第三遍重新迭代到不动点（迭代上限已有）；或者在设计第 12 节如实登记。

##### S12B-50　S12B-40/41 的剩余部分

- 摄取侧的处置失败（`sync-engine.ts:1188`）：定时器（`index.ts:719`）和中继收件都不记。
- 桌面端不读 `relay.status.chain_last_error`，也不读 `member_log.encrypt_epoch`。`KERNEL_MEMBER_LOG_MAINTAIN_FAILED` 只有条数，用户看不到。

- `writeDueMarks` 仍吞掉失败（`member-log.ts:1149`）。
- `exportChainOnly` 与 `addOrUpdateMember` 仍按 `?? currentMatterEpoch`、`?? ownEpoch` 退回（`sync-engine.ts:275`、`member-log.ts:875`）。

##### S12B-51　中继出件箱里的段，在其引用的块被重封之后永远上传不成功，按可恢复错误无限重试

- **位置**：`share-relay.ts:408`（块摘要变了即 `local_blob_changed`）、`:116`（归为可恢复）、`:480-486`（退避至多 1 小时，不转“卡住”、不丢弃）。
- **场景（推演）**：
  1. 本机导出了引用块 B 的段，还没上传（离线或退避中）。
  2. 之后本机的轮换被判不成立，`resealUndeclared` 重封了 B。
  3. 这一段每次上传都报 `local_blob_changed`，`retrying` 计数和 `errors` 一直不为空。
  4. 内容会随退回的水位另出新段送达，所以不丢数据，但这条出件永远清不掉。
- **建议**：重封时作废出件箱里引用该块的段（重发由退回的水位保证）；或者把 `local_blob_changed` 当作“丢弃，依赖重发”处理。

##### S12B-52　块加密在“链上没有可用纪元”时拒绝写入：v0 里罕见，报错口径一般

- **核对结论**：本轮要求重点核对的几种正常使用情形，`chainEncryptEpoch` 的结果如下：
  - 新成员刚加入：加人事件带新成员的包裹，取得到。
  - 刚轮换：包裹随段一起到，取得到。
  - 等待新包裹（落选，或包裹还没送到）：退回更低的已声明纪元，**不是 `null`**，问题是 S12B-45 所说的泄露，而不是写不进。
  - 个人事项、旧客户端模拟：`chainEpoch` 为 `undefined`，走原路径。
  `null` 只出现在本机对任何已声明纪元都没有密钥时，例如成员的新设备还没被补包裹；v0 一人一台设备，几乎不出现。
- **问题**：出现时抛的是普通 `Error`，接口返回 500、错误码 `internal`（`local-server.ts:97-100`），执行器写交付物也会让整次运行失败。
- **建议**：抛 `DomainError`（例如 409 `matter_key_pending`），执行器对它可重试。

#### 建议

- **S12B-53**：
  - 每写一个块，`chainEpoch` 都要查一次视图键，再对每个纪元做一次非对称解包（`ownKey`）。导入大文件或 OCR 分页时开销明显，建议按“事项 + 视图键 + 本机包裹”缓存结果。
  - `reseal` 为了读块头要整份读入文件。`resealUndeclared` 每次退回水位都把事项全部块读一遍，建议先只读块头。
  - `chainHealth` 判 `member_conflict` 时对每个有效成员事件做一次 `project`，是 O(n²)，而 `applyProjection` 每次写回都会调用它，建议缓存。
  - 设计第 12 节补上：两位负责人设备先后吊销、又没有其他在用负责人时，事项永久暂停，只能走恢复；放弃的起点不可撤回；等新包裹期间可能短暂误报 `rekey_needed`。
  - 第 12 节残余里“被移出者借报复降级移出他的人：机密性不受影响”在 S12B-43 修正之前不成立。

### 9.4 结论：不通过

8.5 节的处置里，S12B-34/37/38 与复核 A 的中继移交各条已修复。S12B-31/35/36 按所述形态成立。S12B-32、33、40、41、42 与 S12A-14 只部分修复。

本轮发现 3 个新的阻断，都已稳定复现：

- **S12B-43**：这一轮引入。“链上有在用标记即视为吊销”不核对标记的目标，拒收而不是待定。任何负责人一条标记就能撤销对方的移出（伦理墙），并永久锁死对方，没有正确的告警。
- **S12B-44**：S12B-32 没有覆盖的那一种。落选纪元的密钥被原地替换，之前封的块不重封，缓存不失效。结果是别人收不到，本机重启后材料丢失。
- **S12B-45**：早就存在，块加密的修正没有覆盖到。`rekey_needed` 暂停期间写的块，在恢复后原样发出，被移出者能读到。

另有 2 个重要问题：

- **S12B-46**：有第三位负责人时，互相移出由自动轮换“处置”，从未提示。
- **S12B-47**：0043 原地改过，旧开发库上自动处置持续失败。

建议修正：

- **标记**：本机不知道吊销时，标记只造成待定加上同步设备目录；目录确认没有吊销时，这条标记不算并告警（S12B-43）。
- **块**：改为导出时按本段的加密密钥统一重封；替换本机包裹前先重封或保留旧钥；缓存键带指纹（S12B-44/45）。
- **冲突解除**：有冲突时不自动轮换，解除只认人工成员操作（S12B-46/48）。
- **迁移**：另立 0044，或在进度文档里写明须重建开发库（S12B-47）。
