### 4. 认证与完整性

- AAD = 头（含盐、代、用途标签）‖ 块序号 ‖ 末块标志。块重排、按分块边界截断、改字节、错用途、错代都会被检出（`at-rest.test.ts` 已覆盖，已核实）。
- stat 报告的明文长度一律 ≤ 盘上长度：分块格式按闭式计算；日志格式只累加完整落在文件内的记录。`readSealed` 用 `subarray` 截取。构造的盘上文件不会让读取越界，也不会让长度膨胀（已核实）。
- 写回：W 提交的“内容未变则跳过”用整读（全认证）比对（`commit.ts:290-292`）；Edit 也走整读；上游文件历史用 `readBytes(size+1)` 后比对长度（`kap-embed.mjs:174906-174915`）。构造的文件只会导致报错或“当作已改动、整份写回”，不会写出错误内容。例外是 A03 中 Read 工具会看到被截短的内容，模型可能据此 Write，属于推断。

### 5. 文件名与元数据

- 材料快照的盘上名是 `001.txt`…；W 的 `ls`、Grep 输出、工具事件里的路径都是中性名；原文件名（令牌形态）只在提示词清单里出现（`main.ts:179-182`）。提示词经事件进入加密的会话转录，并经闸门令牌化后送模型（已核实）。
- 残余口径中的“大小量级”不准确，见 A06。

### 6. 原生 ripgrep

- 路由只认两个字面量：占位 shell 交给执行域，检索入口交给宿主内检索。其余可执行文件一律拒绝并记审计（`exec-router.ts:189-235`）。
- 上游 `workspaceFs.resolveRg` 用 `probe.exec(["rg","--version"])` 探测系统 rg（`kap-embed.mjs:153779-153790`），这个探测走 `runtime.process`，也就是种子注入的路由，所以被拒绝；`allowCachedFallback` 未开启，不会去试 `~/.kimi-code/bin/rg`。
- `rgLocator`（ZP-20）只认宿主登记的占位文件（`:185677-185689`）。`kap-embed.mjs` 中 rg 下载代码出现 0 次。
- `build-runtime.mjs`、`fetch-win-runtime.mjs`、`win-runtime.lock.json`、`runtime-paths.cjs` 的清单键都不含 rg。
- 含 rg 下载器的 v5 `agent-host.bundle.mjs` 不在 `electron-builder.yml` 的 files 清单里。安装包环境固定 `ZR_AT_REST=required`（`release-config.cjs:98`），这时内核不会选用 SDK 宿主（`kernel/src/index.ts:291`）。

结论：没有拉起原生进程或下载 rg 的路径（已核实）。

### S3B-A03【一般】分块随机读在两种边界上不认证末块：截断会被当成“更短”或“空文件”；stat 报告的长度也随之失真

- **位置**：`packages/file-broker/src/broker.ts:488-498`（`readSealed` 的末块认证与返回长度）、`:646-662`（`plainStat`）；`packages/at-rest/src/index.ts:86-91`（`plainSizeOf`）、`:281-294`（`openChunks`）、`:318-328`（`chunkSpan`）。
- **条件与后果（已核实，由代码逐步推导；未运行构造样本）**：
  - (a) 多块文件被截到“k 个完整分块 + r 字节残片”，1 ≤ r ≤ 27、k ≥ 1：
    - `plainSizeOf` 得出 `k·65536 − (28 − r)`。
    - 末块认证取 `chunkSpan(size, plainSize−1, plainSize)`，落在第 k−1 块，并以 `total = k+1` 认证。这一块原本就是非末块（标志 0），所以认证通过。
    - 结果：`readBytes(p, n[, offset])` 不报错，返回被截短的内容。可达的调用方是上游 Read 工具的取样与窗口读（`kap-embed.mjs:153069, 153094`）和文件历史的 `readBytes(size+1)`。文件历史因为长度不符记为 unreadable；Read 工具则会向模型展示截短后的文件。
    - 整读（readText、Edit、宿主检索、W、内核）都会报“分块残缺”。
  - (b) 文件只剩 64 字节头（或头加不足 28 字节）：
    - `plainSize = 0`，`span.count === 0`，末块区间为空；`openChunks` 收到空缓冲直接返回，**不做任何认证**。
    - 结果：Read 工具与文件历史都把它当合法空文件。
    - 头部不含秘密：魔数、版本、gen、用途标签（`sha256("kwl-zone:"+用途)` 的前 4 字节）都可以公开推算。因此**无需密钥**就能在严格区放一个“看似合法”的空文件，绕过“外部植入一律拒读”。
  - (c) 情形 (a) 下，`readSealed` 的返回长度以解出的分块长度为界，而不是 `span.plainSize`（`:496-498`），会比 stat 报告的多出最多 28 字节。不越界。
- **口径**：设计 §10 与进度文档说“区间不含末块时另认证末块（截断不被当成“更短”）”，对上面两种边界不成立。
- **影响**：只涉及完整性，前提是攻击者能离线写盘；不泄露明文、不越界。模型可能基于截短后的 Read 结果覆盖文件（推断）。
- **建议**：
  - 分块格式做结构校验：`(diskSize − 64) % (65536+28)` 为 0 或 ≥ 28，否则判 corrupt。
  - 末块认证直接取第 `total−1` 块（`diskStart = 64 + (total−1)·step`、`diskEnd = size`），空文件也一样：必须恰好是一个 28 字节空块，即盘上 92 字节。
  - 返回长度以 `span.plainSize` 为界。
  - `plainStat` 与 W 的 `plainSizeAt` 同步做结构校验。
- **建议测试**：在 at-rest 与 broker 中分别截到 k 块 + r 字节（r = 1、27、28），以及只留 64 字节头、头 + 10 字节。对每种情形，`readBytes(p,10,0)`、`readBytes(p,size+1)` 必须报错，`stat` 不得报出与分块结构不符的长度。

### S3B-A04【一般】工作区与材料区接受“追加日志”格式：无需密钥即可伪造出被所有读者当作“空文件”的文件，内核还会登记为成果

- **位置**：`packages/at-rest/src/index.ts:166-171`（`open` 遇到 kind 0x02 就转 `readLog`）、`:222-250`（只有头的日志返回空；单条记录“恰好到文件尾却认证失败”按断电残尾丢弃，`:243-244`）；`broker.ts:483-486`；`sealed-overlay.ts:53-63`；`kernel/src/executor/workspace-artifacts.ts:35-40, 144-151`。
- **问题（已核实，代码推导）**：broker 从不在工作区和材料区写日志格式，但这两区的编解码器仍接受它。以下两种文件都可以不用密钥伪造：
  - 头为 `KWE1|1|0x02|…|gen|用途标签` 的 64 字节文件；
  - 64 字节头后跟一条“长度恰好到文件尾”的垃圾记录。
- 后果：broker、W 读层、宿主检索读出的都是空内容，不报错；stat 报 0。内核在下一次运行终态时发现它与快照的大小不同，解出空内容、摘要不同，于是**登记为“改动”成果**（0 字节）。离线篡改者因此可以把一份草稿替换成“空文件”而不被检出，并让一个空成果入库。
- **口径**：`broker.ts:51-55`、`matter-engine.ts:52-54` 的注释与 B3-A18 的处置说严格形态下“区内出现的非空明文一律拒读”。对这种伪造形态，结果是静默读空，而不是拒读。
- **建议**：工作区与材料区只接受分块格式。例如 `ZoneSpec` 增加 `formats: ["chunked"]`，或给编解码器加 `allowLog`；W 的 `decode` 与内核的 `readPlain` 做同样约束。日志格式与“残尾丢弃”只留给引擎状态区和事件日志。
- **建议测试**：在加密工作区放 `codec.newLog()` 的纯头文件，以及“纯头 + 一条伪记录”，断言 broker 报 EIO、W 读取失败、内核记 unreadable 且不登记成果。

### S3B-A05【一般】迁移切换有跨进程窗口：内核在宿主迁移之前就以严格形态做快照，升级后第一次运行会把存量文件全部登记为“改动”成果

- **位置**：`kernel/src/executor/kap-agent-client.ts:364-370`（先快照，再 `startRun`）；`kap-host/src/matter-engine.ts:123-126`（宿主在第一次打开引擎时才迁移）；`workspace-artifacts.ts:35-40, 116, 145`。
- **问题（已核实，代码推导）**：
  1. 升级前工作区是明文。内核快照时，`readPlain` 对非空明文返回 null，快照记下的摘要是空串。
  2. 宿主随后迁移：rename 产生新 inode，大小增加 `64 + 28·n`，修改时间改变。
  3. 终态比对时大小与时间都不同，解封后的摘要也不等于空串，于是每个支持格式的存量文件都被登记为本次运行的“modified”成果（受 20 个 / 60 MB 上限约束，超出部分记 limit）。
- **口径**：D-57 写“严格形态在迁移完成后才生效”，这只对宿主一侧成立；内核一侧立即生效。
- **影响**：成果归属错误，本次运行的成果里混入旧草稿；工作区本是本机私有，成果则随事项共享（推断：跨任务去重能挡住多少未核实）。目前还没有发出过安装包，实际影响限于开发与演示机。
- **建议**：二选一，或者都做：
  - 内核等宿主完成迁移后再快照。例如新增 `openMatter` IPC（下发密钥、迁移、返回），内核 await 之后再 `snapshotWorkspace`。
  - 快照中遇到严格区的存量明文时，仍计算明文摘要（只用于比对，不登记），终态按明文摘要判断“未改”。
- **建议测试**：内核用例预置明文工作区（模拟升级前），运行一次后断言未改动的存量文件不出现在成果里。

### S3B-A06【一般】残余口径“大小量级”不准确：精确明文长度、日志的逐条长度与条数都以明文可见

- **位置**：`packages/at-rest/src/index.ts:86-91`（分块明文长度可由盘上长度精确算出）、`:213-215`（日志每条记录的 `len u32` 以明文写在记录头）；口径出现在 `sealed-storage.ts:9`、`capabilities.ts:86`、进度文档 D-48、设计 §8.5（“近似大小”）。
- **问题（已核实）**：任何拿到磁盘的人都能得到：
  - 每个工作区文件、材料快照的**精确**明文字节数；
  - wire.jsonl、事件日志、任务输出里**每条记录**的明文长度与记录数（例如每轮提示与回复的长度、工具调用次数）。

- **建议**：口径改成“文件名、目录结构、文件数量、精确明文长度（分块格式可由盘上长度算出；追加日志可见每条记录的长度与条数）与时间不加密”。如果评审认为需要，可对日志记录长度做分桶填充；不强制。

### S3B-A07【一般】能力账本没有如实写明“区密钥进入 W 进程内存”；检索行仍沿用“可信 ripgrep”的事实名

### S3B-A08【一般】“W 临时目录不落明文”缺少持续证据：红队不变量排除了 `w-tmp`，w-sealed 的用例标题也宣称了没有断言的性质

- **位置**：`packages/exec-wasm/test/w-redteam.test.ts:103`（`filter((n) => n !== "w-tmp")`）；`w-sealed.test.ts:165-177`。
- **问题（已核实）**：
  - `w-tmp` 是 W 进程唯一能写的真实目录，也就是 W 内代码唯一可能把明文写到真实磁盘的渠道。100 余例红队的不变量正好把它排除了。
  - w-sealed 只在一次 `ls -la /tmp` 之后检查，并且忽略了点文件（`!n.startsWith(".")`）。
  - 该用例标题写“W 内看不到区密钥以外的任何解密能力（只读挂载与工作区各一把）”，用例体没有任何与密钥相关的断言。
- 监督进程只在拉起与关闭时清空 `w-tmp`（`host.ts:174, 396`），不是每次执行后清空。如果出现写入渠道，明文会在宿主整个生命周期内留在盘上，强杀后也还在（推断）。
- **建议**：
  - 红队 `invariants` 增加“`w-tmp` 为空（含点文件）”。
  - w-sealed 去掉点文件过滤；用例标题改成与断言一致，或补上对 `req.mounts[*].sealed` 用途的断言（例如在 `domain.ts` 暴露只读的挂载用途清单供测试检查）。

### S3B-A09【建议】密钥内存卫生（威胁模型之外，按设计“尽力而为”）

以下各点均已核实：

- base64 形态的区密钥是不可清零的 JS 字符串，出现在：内核的 `atRestKeys`（`kap-agent-client.ts:364`）、宿主收到的 `p.at_rest`、`MatterEngine` 的 `toWire()`（存进 `WCoreDomain.mounts`，存活到引擎关闭）、每次执行的 IPC 消息与 `workerData`。
- 中间缓冲没有清零：
  - `MatterKeyRing.fromWire` 解出的 Buffer 和 `ZoneCodec` 构造器（`at-rest/src/index.ts:133`）复制前的原件；
  - 内核 `unwrapMatterKey` 的返回值（`ws-keys.ts:47` 只清零了它的副本）；
  - 每文件派生的 `fileKey`。
- 内核侧兜底超时或过期（`executor.ts:958-990`）只发 `cancel`。如果宿主没有回终态事件，`task.workCodec` 不会清零，而 `tasks` 表从不删除条目。
- 宿主的区密钥按设计常驻宿主整个生命周期（不是“运行结束即清零”）。文档口径一致，记在这里作为提醒。

建议：

- 区密钥在 IPC 上改用 `Uint8Array`（advanced serialization 下按二进制传递），用后 `fill(0)`。
- `ZoneCodec` 构造器接管调用方的缓冲，或清零调用方的原件。
- 内核在 `markTerminal` 路径上调用客户端的 `release(taskId)`，清零 `workCodec` 并删除 `tasks` 条目。

### S3B-A10【建议】宿主密钥环只在第一次下发时建立，之后的 `at_rest`（包括新代）一律忽略

- **位置**：`packages/kap-host/src/main.ts:159`（`if (p.at_rest && !keyrings.has(mid))`）。
- **问题（已核实）**：换代（B3-A21）落地后，宿主会继续按旧代写入，内核则按新的代集合读取。旧代一旦退役，内核登记会全部变成 unreadable。
- 另外，开发形态（optional）下第一次运行如果没带密钥，引擎以明文形态打开并缓存；之后带密钥的运行仍复用这个明文引擎，导致工作区明文与密文混合（`runtime.ts:292-321`；推断，只在开发形态）。
- **建议**：`gen_current` 或代集合变化时关闭引擎、替换密钥环后重开；optional 形态下，如果事项目录已有 KWE1 文件而本次没带密钥，就拒绝运行。

### S3B-A11【建议】存量迁移的残留面比文档描述的大

以下各点均已核实：

- `sealFileInPlace` 跳过 `nlink > 1` 的文件（`sealed-storage.ts:413`）。如果 broker 在明文时代的 `link(tmp,target)` 之后、`unlink(tmp)` 之前崩溃，并且 `readdir` 先返回 target（APFS、ext4 的顺序不固定；NTFS 按名字排序，通常先返回 `.kwl-tmp-*`），target 会保持明文，直到下一次宿主重启再迁移。在这期间它在严格区里不可读。
- 回收区、临时文件（`:389-402`）、材料快照（`main.ts:138, 165`）、引擎日志与查询库（第 1 步）中的存量明文都是直接删除，不做零覆写。“POSIX 上零覆写”只适用于就地改写的文件。D-57“零覆写被替换的明文”这一措辞容易让人读成覆盖全部存量。
- `migrateWorkDir` 与 `SealedLogFiles.write` 的 rename 没有 `retryWin`（`sealed-storage.ts:94, 441`）。Windows 上杀软短暂持有句柄会让迁移失败，事项随之无法运行（失败关闭，属可用性问题）。

建议：先删除 `.kwl-tmp-*`，再处理其余文件（两遍遍历）；口径写成“只有就地改写的文件做尽力零覆写，其余存量删除不擦除”；迁移的 rename 复用 `retryWin`。

### S3B-A13【建议】宿主内检索先整读解封再判断 256 MiB 上限；`plainStat` 对日志格式整读且不复核

### 3. 处置后的新增观察（均为建议级，不影响机密性）

- **N1：检索 worker 也持有工作区与材料两把区密钥。**
  - 现状：`exec-router.ts:242-249` 每次检索调用 `toWire()`，得到 base64 字符串，经 `workerData` 传给检索线程（`host-search.ts:111`）。正常结束时 `codec.wipe()`（`search-worker.ts:59`）；被 kill（`terminate()`）时不清零，而且每次检索都会多出一份不可清零的字符串。
  - 判断：检索线程与宿主同一进程，宿主本就持有这两把密钥，所以不扩大暴露面。
  - 建议：把这一点并入 A09 的残余口径。D-55 写了“worker_thread”，但没有提密钥。
- **N2：A10 的签名只包含代集合，不包含密钥指纹。**
  - 风险：如果同一代的密钥值变了（例如账本中 `matter_ws_keys` 丢失后 `ensureWsKey` 重新生成第 1 代），宿主会继续用旧密钥写，内核却用新密钥读，结果是成果登记全部 unreadable，宿主重启后数据也无法再读（推断，只会出现在账本异常时）。
  - 建议：签名加上区密钥的单向指纹（例如 HMAC），只在内存中计算。
- **N3：`w-sealed.test.ts:195-196` 的“W 只拿到两把区密钥”断言没有覆盖生产装配。**
  - 现状：它检查的是测试夹具自己传给 `WCoreDomain` 的挂载，相当于自证；生产装配在 `matter-engine.ts:152`（已读码核实只给两把）。
  - 建议：如果要有回归保护，应经 `MatterEngine.open`（或宿主运行时）断言执行域挂载的用途集合。
- **N4：反向对照中 A03 那一项对应的用例名不准确。**
  - 按代码推理：只去掉“末块认证”时，`broker.test.ts:411` 截断边界例中的长度都会先在 `chunkSpan` 的结构校验处报错，这个用例仍然通过。真正会失败的是 `broker.test.ts:341` 的“随机读”例：截到分块边界、去掉末块后，部分读须报“认证失败”。
  - 判断：不影响结论。建议改正描述，或者把“结构合法、去掉末块”的情形也放进截断边界例。
