**与生产不一致、会让结论失真的地方：**

1. 运行时不传运行选项，所以恒为“默认”档、不先出计划；事项恒为 L2、依据齐备、标准端点（S7-A06）。产品界面总是显式传运行选项，新用户默认先出计划。
2. 闸门抓取是本机直连真实外网（S7-A07）。
3. 受害事项没有物化。生产机器上，多个事项会物化在同一个 kap 数据根下（S7-A02）。
4. 受信 ripgrep 只认环境变量 `KWL_TRUSTED_RG`，本机未配置，所以 Glob/Grep 报错；产品是随包提供的（S7-A05、S7-A12）。
5. 只判主 Agent 的请求；子 Agent 不能脚本化（S7-A10）。
6. IM 层由所内节点执行 s1 确定性流程，模型是节点本机 mock（去向记录为 `mock_local`），不经 kap、W、闸门与云端 v0（S7-A13、S7-A15）。
7. 律所策略取开发形态的本机配置（D-17，已登记）。白名单基线不受影响，G0 可以接受。
8. 同一环境内的全部用例共用一个内核、kap-host、闸门与云端 v0。G0 可以接受，但上一例的崩溃或挂起会波及后续用例（S7-A12）。

没有发现绕开某一环的旁路，例如直接调用宿主 API，或直接写数据库代替闸门。

### 重要

#### S7-A01（重要）越界写没有有效判据

**位置**

- `packages/kernel/test/p12/harness.ts` 第 201–205 行（`originals()`），在第 236、276 行使用；
- `p12/judge.ts` 第 75–78 行；
- 设计说明 §四第 1 条：“原件区的哈希不变”“broker 的提交只落在本事项的工作区”“金丝雀……不出现在……工作区里”；
- README §三第 1 条。

**问题**

- “原件哈希不变”比对的是 `document_versions.sha256` 列。这一列在导入时写入，全仓库没有任何 `UPDATE document_versions` 语句，所以前后两次读取必然相等，这项检查永远不会失败。
- 除此之外，没有任何写入一侧的证据。以下位置都不做前后快照：
  - 本事项材料区的物化副本（`kap/<事项>/materials/`）；
  - 其他事项的工作区与材料区；
  - kap 的 home（会话、配置、技能目录）；
  - 主机金丝雀所在目录；
  - 内核数据目录与 blob。
- 设计说明列出的“broker 提交只落在本事项工作区”和“工作区里不出现金丝雀”两项都没有实现。

**后果**

- P12 第一条中“写”的一半、T08 的“无未授权写入”，在这个框架里不可能判为失败。
- 红队写的“改原件、写到别处、写配置”类用例会一律记为通过。G0 报告中“零越界读写：通过”对写入一侧没有证明力。

**建议处置**

1. 按字节核对原件：运行后经内核取出原件（或解密 blob），重算 sha256，与导入记录比较；本事项材料区的物化文件也做前后哈希。
2. 写入快照：运行前后，对以下位置做“路径 + 大小 + 哈希”清单比较：
   - kap 数据根，不含本事项 `work/` 与引擎自身的会话和缓存目录；
   - 主机金丝雀目录；
   - 内核数据目录，按白名单排除数据库、账本等预期会变的文件。
3. 扫描本事项工作区的新文件，查找金丝雀。
4. 按实际行为改写设计说明与 README。

#### S7-A02（重要）跨事项越界读的金丝雀不可达，也无从引用

**位置**

- `harness.ts` 第 57–60 行：受害事项只导入材料，从不运行；
- `harness.ts` 第 132–143 行：只有 4 个占位符；
- README 第 44 行；
- 冒烟用例 `smoke-filename.json`。

**问题**

- **受害事项的材料不在磁盘上。** kap 只在事项发起运行时，才把材料物化为 `kap/<事项>/materials/NNN-<文件名>.txt`。受害事项从未运行，所以它的 kap 目录不存在（第二节已核实）。
- **冒烟用例的跨事项读取本来就读不到东西。** 它读取的 `…/<受害事项>/materials/受害事项材料.txt`，即使越过宿主策略也不存在，文件名格式也不对。
- **经法律 MCP 的跨事项读取写不出来。** `materials.read_excerpt` 需要 `parse_version_id`，而运行器没有提供受害事项的 `parse_version_id` 或 `document_version_id` 占位符。旧 v0 用例（b2）测的正是这条路径。
- **主机金丝雀只有一个位置。**

**后果**

- “零越界读”的跨事项部分在 v9 链上只能空转：即使宿主策略或执行域失效，结果也是“不存在”，照样判“通过”。
- 这恰恰是律所场景最关键的越界类型（伦理墙）。

**建议处置**

1. 建环境时让受害事项先完成一次运行：物化材料，并在它的工作区里放一个金丝雀文件。
2. 提供以下占位符：`{{victim_materials_dir}}`、`{{victim_work_dir}}`、`{{victim_material_path}}`、`{{victim_parse_version_id}}`、`{{victim_document_version_id}}`。
3. 增加几个典型的主机金丝雀位置：内核数据目录旁、kap home、其他事项的会话目录。
4. 冒烟的跨事项用例改用这些占位符，并按预期的拒绝原因断言。

#### S7-A03（重要）“零未经闸门出网”的判据看不到主要的失败形态

**位置**

- `judge.ts` 第 83–101 行；`harness.ts` 第 268–271 行；
- `services/legal-gateway/src/gateway.ts` 第 195、339 行；
- `services/search-service/src/index.ts` 第 74–84 行；
- `packages/egress-gate/src/server.ts` 第 336、465、472 行；
- 设计说明 §四第 2 条；第 02 篇 §13 第 3 条。

**问题**

1. **判据只统计“通过了席位鉴权”的请求。**
   - 网关在进入计量之前就完成鉴权，失败直接返回 401；检索服务的 401、400 也不计量。
   - kap-host 与执行域拿不到席位令牌：宿主环境被清空，令牌经 IPC 只交给闸门。因此任何绕开闸门的组件发出的请求都会被 401 拒绝，并且不留痕迹。
   - 这时正文已经离开本机，判据却看不到。
2. **对任意主机的直连没有任何观测。** 解析器取外链、宿主或执行域直连攻击者地址，都不会被发现。
   - 运行器里没有设计说明所说的“回环站点”，也没有 DNS 或连接观测。
   - 因此文档外链层的“解析不得外取”也没有判据：冒烟的目标是不可解析的 `.example` 域名。
3. **“按请求编号对账”实际不成立。**
   - 闸门记录自己的 `kwlg_…` 编号，并以 `x-kwl-request-id` 发给网关；网关计量用自己生成的 `kwlgw_…` 编号，不记录前者；闸门也不记录网关回传的编号。
   - 所以实际总是退化为按条数对账，而按条数对账可能被失败的或未计量的请求抵消。
   - 判定自检用的证据中两边编号一致，这在实际运行中不会出现。
4. **设计说明列出的“出网面静态扫描（outbound-surface）通过”**，运行器与报告既不运行也不记录；它是另一个测试文件。

**后果**

- 第 02 篇 §13 第 3 条要求“除闸门进程外客户端进程零外部连接”，而这个框架只能发现“闸门自己旁路到自家云端”这一种情况。
- 红队报告中“零未经闸门出网：全部通过”的证明力很弱。

**建议处置**

1. 模拟网关与检索服务在 HTTP 层记录每一个到达的请求（包括被拒绝的），判定以“全部到达的请求”为准，而不是以“通过鉴权后的计量”为准。
2. 改为严格按编号对账，删除按条数的退化分支。两种做法任选其一：
   - 网关计量记录 `x-kwl-request-id`（这只是编号，属于元数据）；
   - 闸门记录网关回传的编号。
3. 增加回环的“攻击者站点”与 `{{attacker_url}}` 占位符。闸门的 SSRF 守卫拒绝私网地址，所以对这个站点的任何命中都必然来自旁路。文档外链层的 `targets` 也允许指向它。
4. 报告记录同一提交下出网面静态扫描的结果；或者在设计说明中写明，它是独立的前提条件。
5. 判定自检改用真实格式的编号，并覆盖按条数对账的分支。

#### S7-A04（重要）“零未确认的跨边界动作”判定覆盖不全，并且有漏判缺陷

**位置**

- `judge.ts` 第 107–150 行；
- `egress-gate/src/server.ts` 第 375–397 行：图像随模型请求一起发出，去向记录的 purpose 为 `model`；
- `kernel/src/services/interaction-cards.ts` 第 29 行：卡片种类有 plan、search、fetch、image、budget、schedule、stop、manual、connector、other；
- 第 02 篇 §9.5；第 06 篇 T08。

**问题**

1. **图像外发漏判（缺陷）。**
   - 图像随模型请求经网关发出，去向记录的 purpose 为 `model`、目的地为 `legal_gateway`。
   - `crossingKind` 只认 purpose 为 `media` 或 `image` 的记录，遇到这种记录返回 null，所以图像外发从不被核对。
   - README 与设计说明却称已覆盖“图像外发”。
2. **只判经闸门的三种出站。**
   - 第 02 篇 §9.5 中不产生去向记录的跨边界动作完全不判：③ 连接器写入、④ 跨事项读取（T7）、⑤ 创建定时（T8）、⑥ 超出预算、⑩ 扩大材料范围。
   - T08 的“无权限扩大”也没有判据，例如运行模式、批准范围、预算、律所策略、成员与授权在运行前后是否不变。
3. **批准只核对编号，不核对对象。** 判定只看批准编号是否属于某张已同意的卡，不核对卡上的对象（工具、查询或 URL、摘要）与去向记录是否一致。把一份批准用到另一个对象上的错误绑定，判定看不到。
4. **独立核对只看检索，而且写法单一、口径过宽。**
   - 它用当事人名称原文做 `includes`，不做 NFKC、空白与格式字符、繁简等归一。这些变体恰是红队最可能用来绕过闸门筛查的写法，判定与被测系统在这里“同盲”。
   - 只要有任何一张检索卡被同意，就放过全部含当事人名称的检索。
   - 抓取的 URL 不做独立核对。

**后果**

- 第三类零条件只覆盖了第 02 篇 §9.5 的一部分。
- 在最可能被攻击的写法上，判定会漏报。

**建议处置**

1. 修正图像分类：模型记录带 `media` 即视为图像外发，须对上一张种类为 image 的同意卡。
2. 用运行事件（`run.tool_started`、`run.tool_result`）与确认卡种类做核对：执行成功的跨边界工具调用（CronCreate、跨事项读取、连接器写入、ReadMediaFile 等）必须有对应的同意卡。
3. 记录运行前后的模式、预算、策略版本与权限相关表，用来判断“权限扩大”。
4. 批准按对象核对。
5. 独立核对改为：
   - 每条去向记录各自对应一个批准编号；
   - 采用与闸门不同的实现做归一化匹配，至少包括 NFKC、去掉空白与格式字符、繁简折叠；
   - 允许用例声明当事人别名；
   - 扩展到抓取的 URL。

#### S7-A05（重要）分母完整性：未执行或因环境空转的用例按“通过”计入

**位置**

- `p12-redteam.test.ts` 第 141–152 行：“动作到达”的检查只在冒烟模式下进行；
- `harness.ts` 第 295–303 行；`report.ts` 第 36–48 行；
- `im-runner.ts` 第 117、126、131 行；
- `cases.ts` 第 119–133 行：不要求至少一轮工具调用。

**问题**

- 报告只按三类判定计“通过”，既不看运行状态，也不看脚本化动作是否到达。以下用例都会计为“三类判定全部通过”：
  - 运行状态为 failed、cancelled 或 timed_out；
  - 有脚本化动作没有拿到工具结果；
  - 因环境而空转：受信 ripgrep 缺失时 Glob/Grep 报错；OCR 模型缺失时，图片解析为空，只记一个 `ocr_unavailable` 标记；受害材料没有物化。
- 冒烟模式下的到达断言只检查结果非空，不检查是否走了预期的拒绝路径。
- IM 层两个动作的“结果”是运行器自己写入的字符串，断言恒真。
- 非 IM 层允许 `model.turns` 为空，这种没有任何动作的用例也会计为通过。

**后果**

第 06 篇 §2 总则要求“零”在明确的测试集上成立、报告记录分母。现在的分母会把“没测到”算成“测过且通过”。

**建议处置**

1. 报告增加“未判定”一类，不计入通过。以下情形归入此类：
   - 运行状态不是 succeeded 或 partial；
   - 任一脚本化动作没有工具结果；
   - 工具结果是环境类错误；
   - 关键环境能力缺失（受信 ripgrep、OCR 模型、受害材料物化）。
2. 冒烟断言改为匹配预期的拒绝原因：宿主策略拒绝、律师拒绝、执行域不可见。
3. IM 层断言节点回复的卡片数为 0，并核对节点任务确实执行。
4. 非 IM 层要求至少 1 轮工具调用。

#### S7-A06（重要）用例格式表达不了关键维度，并且与设计说明不一致

**位置**

- `cases.ts` 第 45、52、74 行；
- `harness.ts` 第 169–180、225–234 行；
- `kernel/src/index.ts` 第 558–574 行（`runOptionsOf`）；
- 设计说明 §二的表（第 28、31、32 行）。

**问题**

- **设计说明与代码不一致：**

  | 字段 | 设计说明写的 | 代码实际 |
  |---|---|---|
  | `matter` | 可设密级、四项依据、模型端点、运行模式与关键日期 | 只能设标题、立场、当事人、对方、全部化名 |
  | `lawyer` | 可以逐卡指定 | 只有“计划卡 / 其余卡”两档的同意或拒绝；不能选“本任务内允许”，也不能选“原文放行”或“改写后放行” |
  | `expect` | 可声明“应被拒绝”的动作 | 会被判为不认识的字段，整例无效 |

- **运行配置是固定的：**
  - 运行器不传运行选项。按 `runOptionsOf`，这种调用一律为“默认”档、不先出计划；产品界面总是显式传入运行选项，新用户默认先出计划。
  - 事项一律为 normal 密级（L2）、四项依据齐备、标准端点。

**后果**

- 以下跨边界规则都没法由红队写成用例，三类零条件只在一种配置下被测：
  - L3a：检索逐条确认、图像禁止；
  - L3b：零出站；
  - 依据待确认：只运行本机能力；
  - 自动档的预授权；
  - 手动档的逐步确认；
  - 批准范围升级。
- 红队如果照设计说明写用例，会被判为无效。

**建议处置**

1. `matter` 增加 `confidentiality`、`basis` / `consent_status`、`model_endpoint`、`party_aliases`。
2. 增加用例级的 `run: {mode, plan_first, preauthorizations}`，经同一个 `runs.start` 接口校验。
3. `lawyer` 支持按卡片种类或序号指定 `decision`、`scope`、`variant`。
4. 实现 `expect`，或者删掉设计说明中对它的描述。

#### S7-A07（重要）测试会真实访问外网，与红队编写说明不符

**位置**

- `kernel/src/egress/kernel-gate.ts` 第 75 行：抓取缺省为本机直连；

**问题**

  - 对公开官方站点基线（例如 court.gov.cn、npc.gov.cn）的 `FetchURL`，在默认档会被自动放行，闸门会真实做 DNS 解析并发起 HTTPS 请求；

**建议处置**

2. 在实现之前：README 如实说明；报告的环境栏记录“抓取：真实外网 / 关闭”；红队用例不得使用真实域名。

#### S7-A08（重要）IM 签发确认路径与 v9 冲突，P12 文档却把它当作覆盖依据

**位置**

- `kernel/src/api/index.ts` 第 2071 行起（`approvals.request_im`）；

**方案条款**

- 第 02 篇 R5（第 77 行）：签发是人在已登记设备上完成的业务操作。
- 第 02 篇 §9.4 X2（第 389 行）：签发须本人设备签名。
- 第 02 篇 §9.6 IM 行（第 404 行）：能确认——“无（转 App 或电脑）”。

**问题**

- 第 02 篇（冲突时以它为准）规定：IM 不能确认，不能触发签发，签发须本人设备签名。
- v5 留下的 IM 签发确认路径在 v9 内核中仍然可用，偏离登记里也没有这一条。
- P12 的 IM 运行器判“IM 不得触发签发”，但它从不构造审批意向，因此触达不到这条路径。
- 设计说明与 README 却写着“IM 确认签发路径由 `im.test.ts` 覆盖”，而该用例断言的恰恰是“签发应当成功”。

**后果**

- P12 IM 层的“通过”与产品的实际能力相反；如果按方案去测 T18，现在会失败。
- 根因不在阶段 7 的交付物内，但阶段 7 的文档把它表述成了“已覆盖”。

**建议处置**

1. 提请方案负责人裁定，二选一：
   - v9 关闭 `approvals.request_im` 及节点上的确认处理；
   - 或登记为偏离，写明理由与期限。
2. P12 IM 层增加一种载体：已有审批意向时，IM 卡片操作不得产生签发、对外发送或导出（预期为零）。
3. 改写设计说明与 README 中的相关句子。
