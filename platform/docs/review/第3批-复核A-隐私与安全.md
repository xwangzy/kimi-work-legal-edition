## 逐项核查记录

### 1. S5 上游传输

**核实成立的部分**

- `tls-check.ts:59-81` `checkUpstream`：非回环 `http:` 一律 `upstream_tls_required`；回环 http 只在 `allowLoopbackHttp` 时放行；带用户名口令拒绝；非 http/https 协议拒绝；钉住集任一项形态非法整组无效；`requirePins` 时缺钉住拒绝。`isLoopbackHost` 只认 `localhost`/`::1`/`127.x`，`0.0.0.0`、`::ffff:127.0.0.1` 均按非回环拒绝（偏保守，正确）。
- 钉住对象确为 SPKI：`tls-check.ts:32-35` 取 `X509Certificate.publicKey.export({type:"spki",format:"der"})` 的 sha256，避开了 `PeerCertificate.pubkey` 对 EC 为裸点的问题；`tls-policy.ts:12-28` 沿 `issuerCertificate` 走链（Node 在 `checkServerIdentity` 回调里传入的是 `getPeerCertificate(true)`，含 issuer 链），任一 SPKI 命中即通过。
- 握手阶段断开：钉住核对在 `connect.checkServerIdentity` 里返回错误，发生在 TLS 握手完成、写任何 HTTP 字节之前（`tls.test.ts`“服务端收不到任何请求”用例验证）。
- 四类上游覆盖：`server.ts:129-134` 为 `legal_gateway`（模型与问答 `/qa/chat/completions` 共用）、`byok_model`、`private_model`、`search_service` 各构造一次检查与 fetch；模型路径 `server.ts:414-415`、检索路径 `server.ts:564-569` 在 `invalid` 时先记“拦截”再拒绝，不发出；控制面 `cp-relay.ts:60` 同样先检查，且 `redirect: "error"`（`cp-relay.ts:78`）。
- 闸门进程环境只有 `PATH`（`kernel/src/egress/gate-host.ts:292`），`NODE_TLS_REJECT_UNAUTHORIZED`、`NODE_EXTRA_CA_CERTS`、代理变量进不来；`main.ts:105` 再核一次。
- 安装包形态：`release-config.cjs:16` 的 `ROUTING_ENV` 剔除网关/检索/控制面/传输策略/席位令牌/BYOK/Moonshot/私有端点/模拟提供方/抓取开关；`packagedKernelEnv` 强制 `ZR_UPSTREAM_TLS=strict`、`ZR_MODEL_PROVIDER=upstream`；`release.json` 地址须 https、钉住 ≥2 把，否则该上游不进入环境（失败关闭）。`main.cjs:72-77` 只在 `app.isPackaged` 时生效。
- 去向记录：TLS 失败时 end 阶段写 `tls_pin_mismatch`/`tls_verify_failed`（`server.ts:431-434`、`:588-589`）。

#### B3-A01【重要】模型与检索上游请求未禁止重定向：307/308 会把请求体原样重发到重定向目标，绕过“非回环 http 一律拒绝”与“目的地固定”
- 位置：`packages/egress-gate/src/server.ts:425-430`（模型/问答/BYOK/私有端点）、`server.ts:577-582`（检索）；`packages/egress-gate/src/tls-policy.ts:55`（`upstreamFetch` 包装未设 `redirect`）。
- 事实：undici `fetch` 默认 `redirect: "follow"`。请求体是字符串（非空 body source），对 307/308 会把同一请求体与请求头（含 `authorization: Bearer <席位令牌/API Key>`，同源时保留；跨源时 undici 会去掉 authorization，但请求体照发）重发到 `Location`。`checkUpstream` 只在构造时对**配置的基地址**检查一次；重定向目标若是 `http://` 非回环地址，走明文、不经过 `checkServerIdentity`（无 TLS 即无钉住核对）；若是另一 https 主机，对 BYOK/私有端点（不钉住）直接放行。对照：控制面通道 `cp-relay.ts:78` 已设 `redirect: "error"` 且有用例（`cp-relay.test.ts:56`），模型与检索路径没有。
- 影响：令牌化后的案卷内容（模型请求体）与检索式可能被上游（误配置的反向代理、被攻破的 BYOK/私有端点网关）一跳 307 转到任意明文地址，去向记录仍写原上游主机（`destinationHost: hostOf(t.url)`），与“去向如实”不符。钉住上游（中软网关）在不被攻破时不会产生此风险，所以定为“重要”而非“阻断”。
- 建议：在 `upstreamFetch` 包装里强制 `redirect: "error"`（或 `"manual"` 并把 3xx 记为 `upstream_redirect_refused` 失败），使所有经 tls-policy 的上游一致；去向记录增加该原因码。
- 建议补测：`tls.test.ts` 增一例——上游返回 `307 Location: http://<另一回环端口或非回环地址>`，断言第二个服务端收不到任何字节、去向记录为失败且原因为重定向拒绝；BYOK 端点同样一例。

#### B3-A02【重要】安装包形态仍允许进程环境改写 Agent 宿主入口与数据目录，并保留 `NODE_OPTIONS` 等运行时注入变量；`release.json` 完整性所依赖的 Electron 熔断在仓库中尚未配置
- 位置：`apps/desktop/electron/main.cjs:87-90`、`:92`；`release-config.cjs:4`、`:67-71`；`apps/desktop/electron/runtime-paths.cjs:94-95`。
- 事实：`ZR_KERNEL_DATA_DIR`、`ZR_AGENT_HOST_ENTRY` 在安装包形态下仍取 `process.env`（`main.cjs:87-88`）；随包运行时 `restart.runtimeEnv` 只覆盖 `ZR_EGRESS_GATE_ENTRY`、`ZR_KAP_HOST_ENTRY`（runtime-paths.cjs:94-95），**不覆盖** `ZR_AGENT_HOST_ENTRY`。`packagedKernelEnv` 只剔除 `ROUTING_ENV`，`NODE_OPTIONS`、`NODE_EXTRA_CA_CERTS`、`HTTPS_PROXY` 等原样进入内核 utilityProcess 环境。`release-config.cjs:4` 称 release.json 由 `enableEmbeddedAsarIntegrityValidation` 熔断保护，但仓库内未检索到任何 fuses 配置（`FuseV1Options`/`flipFuses` 0 命中；打包属第 4 批 W4–W7）。
- 影响：S5 自己的依据是“环境变量可被本机其他程序或用户环境改写，不能作为目的地固定的依据”（D-46）；按同一威胁模型，改写 `ZR_AGENT_HOST_ENTRY` 可替换拿到内核凭据的宿主进程，`NODE_OPTIONS=--require` 可向内核注入代码，二者都能绕过闸门这一“唯一出口”，比改上游地址更彻底。闸门本身环境干净（只 PATH），所以 `NODE_EXTRA_CA_CERTS` 不影响闸门的证书校验，这一点成立。
- 建议：安装包形态对所有 `*_ENTRY`、`ZR_KERNEL_DATA_DIR`、`ZR_DESKTOP_*` 只取随包值（或白名单式构造内核环境而非黑名单剔除）；剔除 `NODE_OPTIONS`/`NODE_*`/`ELECTRON_RUN_AS_NODE`；第 4 批打包时配置 `RunAsNode=false`、`EnableNodeOptionsEnvironmentVariable=false`、`EnableEmbeddedAsarIntegrityValidation=true`、`OnlyLoadAppFromAsar=true`，在此之前把 release-config.cjs:4 的表述改为“待第 4 批熔断落地”。
- 建议补测：`release-config.test.ts` 增一例：进程环境带 `ZR_AGENT_HOST_ENTRY`、`NODE_OPTIONS` 时安装包形态内核环境中不出现（需把 main.cjs 的环境拼装抽成可测纯函数）。

#### B3-A03【一般】钉住在证书链上的核对对象是“对端发送链 + 本机补全”，而非 OpenSSL 实际验证通过的链；会话恢复下的链完整性未测
- 位置：`tls-policy.ts:12-28`、`:43-52`。
- 事实：Node `getPeerCertificate(true)` 由对端发来的证书按名称/密钥标识（`X509_check_issued`，不验签）串起，链尾由本机信任库补全；它与 `rejectUnauthorized` 实际验证的链通常一致但不保证一致。undici 默认缓存 TLS 会话（会话恢复时 `checkServerIdentity` 仍会调用，链取自会话）。
- 影响：可利用性很低（攻击者无法让伪造叶子的 issuer 名称指向被钉住的中间证书而又通过验证）；更现实的是会话恢复时链缺失导致只钉中间/根的配置**误断**（失败关闭，可用性问题）。
- 建议：发布流程约定钉住“中软网关叶子 SPKI + 备份密钥 SPKI”；或在回调里额外要求命中项位于链的前两级。
- 建议补测：`tls.test.ts` 增“只钉中间证书 + 连续两次请求（第二次走会话恢复）”用例，确认不误断。

#### B3-A04【建议】预写的 start 去向记录在握手失败时也是 `outcome: "sent"`、`chars` 为请求字数
- 位置：`server.ts:423`、`:574`。
- 事实与影响：设计上是“宁可多记”（审查 S4-03），end 记录会改写为 failed + `tls_*`；但如果闸门在握手失败与 end 记录之间退出，账本会留下一条“已发出 N 字”的记录，而实际未发出任何字节。属于保守偏差，不是泄露。
- 建议：start 阶段用 `outcome: "pending"`（或 `sending`），内核在无 end 时按“可能已发出”展示；不必本批处理。

### 2. S6 密级标志

**核实成立的部分**

- 入口覆盖：写 `document_versions` 的路径只有两处——`api/index.ts:305`（`insertDocumentWithParse`，被 `materials.import` `:589` 与 `materials.mount` `:617` 调用）与 `executor/deliverables.ts:83`（Agent 成果登记，内容派生自已入库材料，不属于外部导入）。所内节点 IM 投递（`apps/firm-node/src/im-runtime.ts:173`）经 `kernel.invoke("materials.import")`，同样过闸；同步引擎不写 `document_versions`。`materials.reparse`（`:657`）也调用 `classifiedGate`。
- 不留副本：`insertDocumentWithParse` 先解析、再 `classifiedGate`、命中即抛出；块存储写入是延迟函数 `storageUri: () => blobs.put(...)`（`:298-300`），在检测通过后才执行；解析管线（`parse-pipeline.ts`）不写临时文件。挂载路径不复制原件。用例断言块存储计数不变。
- 不支持的格式（PDF 走管线；XLSX/PPTX 等 `parser.ts` 直接 `unsupported_file`）不会绕过检测入库。
- 检测规则：星形各变体 + 全角折叠 + 字间 ≤3 个空白；无星时只认行首“密级 + 期限”；“商业秘密三年”“机密信息”等行中用语不命中；DOCX 页眉页脚单独扫描；长文首 20,000 + 末 5,000 字全规则、全文补查星形写法。

#### B3-A05【重要】重新解析时才发现的密级标志只拒绝生成新解析版本，原件副本、文档登记与旧解析文本全部保留且仍可被运行使用
- 位置：`packages/kernel/src/api/index.ts:655-658`（注释“已登记的原件由律师按涉密载体规定线下处理”）。
- 事实：`classifiedGate` 抛错后，`document_versions` 行、导入块（`blobs` 中的原件）与既有 `parse_texts`（扫描件 OCR 前通常为空，但原件字节仍在）不做任何处置；也没有给文档打“涉密待处置”标记，文档仍出现在材料列表中、可被选入后续运行（材料快照取最新解析文本——kap-host `main.ts:163-166` 写的是 `m.text`，扫描件 OCR 前多为空，所以模型侧泄露面小；但导入块中的原件字节仍在，并会进入账本备份与事项块同步——同步范围本复核未逐项核实）。00 表 S6 行称“重新解析（OCR 就绪后）才发现的同样拒绝”，容易被理解为与导入同等处置。
- 影响：涉密载体副本留在非涉密系统内（导入块与文档登记都保留），与 v9 §8.1 L4“检测到密级标志即拒绝导入，线下处理”的结果不一致；属于需要明确处置的合规缺口。
- 建议：命中后在同一事务内把该文档版本标为 `quarantined`（材料列表、快照、检索与工具一律排除），导入副本按 `secure_delete` 擦除块并记审计（`materials.classified_quarantined`），界面提示律师线下处置；或至少阻止其进入任何运行。
- 建议补测：`classified-marking.test.ts` 增“导入时 OCR 未就绪（无文字）→ OCR 就绪后 reparse 命中”用例，断言块存储副本被移除或文档被排除在材料快照之外。

#### B3-A06【一般】`*`/`＊` 作为星形符号会误拦 Markdown 粗体与脚注写法里的“商业秘密”“技术秘密”
- 位置：`packages/kernel/src/services/classified-marking.ts:26`、`:46`。
- 事实：`STAR` 含 ASCII `*` 与全角 `＊`，规则只要求“秘密”后紧跟（≤3 空白）一个星形符号。`**商业秘密**`、`商业秘密*`（脚注标记）、`技术秘密＊` 都会命中 `秘密` 级并拒绝导入；现有“不误拦”用例（`classified-marking.test.ts:38-50`）没有带星号的普通文本。`.md`/`.txt` 走 `parser.ts` 纯文本，Markdown 原样进入检测。
- 影响：商业秘密纠纷是律所常见业务线，律师从笔记或 AI 工具导出的 Markdown 会被整份拒绝且无复核通道；与 S6 行“‘商业秘密’不误拦”的表述不符。属“多拦”方向，不造成泄露。
- 建议：对 ASCII/全角星号要求“密级词前为行首或非汉字”且“星号后不是另一个星号/紧跟期限或行尾”，或排除前缀“商业/技术/经营/工作/个人/国家”；★ 等专用符号保持现规则。
- 建议补测：不误拦用例加入 `**商业秘密**的认定`、`商业秘密*`（脚注）、`技术秘密＊`；命中用例保留 `秘密*1年`（OCR）。

#### B3-A07【一般】检测前未做 Unicode 规范化与零宽字符剔除；纯文本按 UTF-8 解码，GBK/GB18030 编码的 TXT 会整体漏检
- 位置：`classified-marking.ts:28`、`:33-40`；`services/parser.ts`（`.txt` → `buf.toString("utf8")`）。
- 事实：`compactWidth` 只折叠 U+FF01–FF5E；`GAP` 不含 U+200B/U+FEFF/U+00AD 等不可见字符，PDF 文本层与网页复制常带零宽空格（`机​密★` 不命中）；字间空白上限 3（分散对齐用多个空格时不命中）。GBK 编码的 TXT 在本地政府/企业导出件中仍常见，按 UTF-8 解码为乱码后不会命中，但原件字节照常入块存储、进入材料快照。
- 影响：漏拦面有限（多数为边缘写法），但与“宁可多拦”的原则不一致。
- 建议：检测前做 NFKC + 剔除 `\p{Cf}`；`GAP` 放宽到 0–6 并包含 `\p{Cf}`；纯文本先做 BOM/编码探测（UTF-8 失败或替换字符比例高时按 GB18030 再解一次并检测）。
- 建议补测：`机​密★1年`、`机    密★`（4 空格）、GB18030 编码的 `机密★1年` TXT。

#### B3-A08【建议】拒绝审计只记“类别+文件 hash”的摘要，事后无法按文件 hash 查询是哪份文件、哪一级别
- 位置：`api/index.ts:328`（`sha256Hex(JSON.stringify({level, where, file_sha256}))` 作为审计载荷摘要）。
- 事实与影响：审计行里只有一个摘要，类别与文件 hash 都不可读；所内保密员追查“谁在何时尝试导入哪份涉密件”时只能逐个候选文件复算。类别与文件 hash 本身不含案情，可以明文记。
- 建议：审计载荷明文记录 `level`、`where`、`file_sha256`（仍不记上下文原文）。

### 3. S11 工具结果令牌化与导出还原

**核实成立的部分**

- `local-server.ts:409-416`：`tools/call` 成功分支在 `JSON.stringify` 与 `structuredContent` 之前统一过 `tokenizeToolResult`，两种交付形态都是令牌形态；令牌化走 `MatterTokenStore`（同一事项令牌表，闸门复扫幂等）。

- 事实与影响：00 表与设计稿所说“按代换钥”目前只在 `at-rest` 包与单测里成立；即使将来内核生成新代，宿主进程不重启也不会用新代。擦除后重新加入事项会再次生成 `gen=1`（新密钥），旧代号不能区分新旧密钥——在 B3-A17 修好之前，残留的旧文件会被当作残尾截断（旧密钥已删，数据本就不可恢复，影响有限）。
- 建议：00 表把“换代”标为“库层就绪、未接线”；宿主每次 `startRun` 用内核下发的密钥环替换缓存（旧环清零）；擦除后重建时代号沿用单调计数而非回到 1。

#### B3-A22【建议】引擎里还有绕过存储服务的含内容写盘路径（当前未触发），金丝雀扫描范围也没覆盖到
- 位置：`third_party/kimi-code/packages/agent-core-v2/src/agent/media/image-originals.ts:24`、`:47`（MCP 工具结果中的图像原件明文写到 `os.tmpdir()/kimi-code-original-images`，在事项目录之外，运行结束与撤权擦除都不删）、调用点 `agent/mcp/output.ts:209`；`agent-core-v2/src/human/store/backend/node.ts:46-93`（v2 会话迁移用的直接 `appendFile`/`writeFile`）；`kap-server/src/lib/promptMedia.ts:503-520`（提示附件落盘）；金丝雀扫描只遍历 `<事项>/home`（`kernel/test/kap-a1.test.ts:239`）。
- 事实与影响：法律 MCP 工具只回文本、宿主不发提示附件、新装机没有 v2 会话目录，所以本批不会触发；但它们是“零补丁种子替换”覆盖不到的路径，一旦接入图像型 MCP 或附件即明文落到系统临时目录。
- 建议：宿主给 `originalsDir` 指向加密区（或在宿主策略层拒绝图像型 MCP 结果）；ZP 台账登记这三处为已知残余；金丝雀扫描扩大到 `os.tmpdir()` 与整个 `kap/<事项>`（`work/` 按 D-48 单列）。

#### B3-A23【建议】`home/sessions` 有两个互不知晓的加密写入者
- 位置：`kap-host/src/matter-engine.ts:118-125`（broker 的 engine 区根目录 = `home/sessions`，整文件分块格式）与 `:190`（`SealedFileStorageService(homeDir)`，同一目录下的追加日志格式）；两者各有独立的按路径串行队列。
- 事实与影响：格式互认（`open` 两种都认；`append` 遇分块格式会整体重写为日志），所以不会出现明文或解不开；但同一文件被 Agent 文件工具与引擎存储同时写时可能丢更新，且 `append` 的缓存只按文件大小判断是否过期。
- 建议：让 broker 的 engine 区与存储服务共用同一个 `SealedLogFiles` 实例（共享串行队列与缓存），或把 broker 的 engine 区设为只读。

**残余（如实记录，非缺陷）**：文件名、目录结构、大小与时间不加密；存量明文迁移是“写新文件 + rename”，旧明文数据块仍留在磁盘空闲区（SSD 上无法可靠擦除）——依赖 1-13 的 BitLocker 提示；工作区草稿与材料快照在运行期间为令牌形态明文（D-48）。
