## 0. 结论先行

**推荐方案（一句话）**：以**应用层透明加密（方案 A）为主**——每台设备每个事项一把随机“事项工作区密钥”（存加密账本，不随同步外发），按“区”派生子密钥，在**文件 broker**（工作区、材料快照、引擎经 IHostFileSystem 的会话区）与**宿主注入的引擎持久化服务**（`IFileSystemStorageService` 种子、内存 `IQueryStore` 种子）两处统一做 AES-256-GCM 分块封装；Grep/Glob 从原生 rg 改为**宿主内 JS 检索**（re2js 线性时间正则，仍经执行域路由拦截，零补丁）；W 执行域的“快照 + 提交”保持不变，只把**读盘层**换成解密读层；Windows 能力（BitLocker 检测提示、EFS、非内容索引属性）只作纵深，**“运行期明文、结束封存”（方案 B）不作主方案**，只用于迁移。

**为什么不是 B**：引擎会话区在宿主进程存活期间一直被读写（会话索引定时对账、文件历史、任务输出），“运行期明文”实际等于“软件开着就明文”；崩溃、断电、杀进程后明文留盘，NTFS/SSD 上删除不等于擦除——B 达不到“拷盘读不出”的目标。A 的明文只在内存里。

**分两步：**

| 步骤 | 范围 | 对 Agent 工具语义的影响 | 预计改动规模 | Kimi Code 补丁 |
|---|---|---|---|---|
| **第 1 步：引擎状态区全加密 + 运行期外清理**（低风险高收益） | 会话转录 `wire.jsonl`、会话状态、文件历史块、后台任务输出（全部经 `IFileSystemStorageService`）；会话索引（minidb → 内存实现）；引擎文件日志关闭；WS 事件日志 `server/events/*.jsonl` 加密；计划文件（broker engine 区）；材料快照与 `w-tmp` 运行结束即删、启动时清扫；事项工作区密钥与 IPC；存量迁移；OS 纵深（非内容索引、BitLocker 检测） | **无**（Read/Write/Edit/Grep/Glob/Bash 行为不变） | 新增约 1,900–2,300 行（含测试约 700 行），约 3 人周 | **1 处最小补丁 ZP-9a**（`SessionEventJournal` 读写 I/O 可注入，约 40 行，落在已是本方补丁的 `kap-server/src/embed.ts` 与相邻文件）；其余全部经种子注入，零补丁 |
| **第 2 步：工作区与材料快照透明加密**（完整方案） | broker 按区透明封装（`work`、`materials`）；Grep/Glob 宿主内 JS 检索；W 读盘层解密（`SealedOverlayFs`）；提交路径的大小语义；内核成果登记解密读；材料快照文件名中性化；工作区存量迁移 | Grep/Glob 实现更换（输出格式对齐上游解析器，差分测试保证）；W 读层更换（需重跑 W 红队） | 新增/修改约 3,000–3,600 行（含测试约 1,200 行），约 5 人周 | **零 Kimi Code 补丁**（rg 拦截点在本方 `exec-router.ts`）；W 读层若选 D1，另需 just-bash 运行时补丁 KJ-5（约 30 行，与既有 KJ-1～4 同法锁定摘要） |

**完成后金丝雀扫描**：第 1 步完成时 `home/`、`materials/`（运行结束后）、`w-tmp` 命中为 0，`work/` 仍可能命中（如实标注为“第 2 步完成前的已知差距”）；第 2 步完成时整个数据根命中为 0，**包括运行中强杀宿主（崩溃）后的扫描**——这是 A 相对 B 的决定性区别。

**主要风险（详见 §8）**：① Grep 改 JS 后的语义差异与性能（re2js 吞吐低于 Rust regex；以差分测试与基准门禁兜底）；② W 读层替换触及已加固的执行域面（须重跑 100 例逃逸与上限用例）；③ 加密根仍是 DPAPI——**P0-2（safeStorage 不可用即明文账本）与 P0-1（设备私钥明文）必须先于或同时落地**，否则账本里的包裹密钥可被直接解开；④ 内存、页面文件、休眠文件、崩溃转储中的明文不在本方案能力范围内（只能靠 BitLocker 与 P0-4）；⑤ 文件名、大小、时间等元数据仍明文；⑥ 存量明文迁移后无法保证物理擦除（SSD 磨损均衡、NTFS 驻留、卷影副本）；⑦ 国产杀软对“批量把文件改写成高熵内容”的勒索防护误报。

## 2. 威胁模型与验收口径

| 场景 | 本方案目标 | 说明 |
|---|---|---|
| 律师电脑被盗/被拷盘（未开 BitLocker），攻击者**不知道 Windows 登录密码** | `kap/` 下任何文件（含保留区 `.kwl-*`、WAL、日志）读不出案卷内容；金丝雀扫描 0 命中 | 主目标 |
| 同上，但攻击者**知道或能离线破解登录密码** | 不承诺 | 密钥根是 DPAPI，与账本同根（§1.7）；如实口径 |
| 备份软件/同步盘/漫游配置文件把数据根复制走 | 复制走的是密文 | Roaming `%APPDATA%` 的域漫游同步属于此类（§4.3） |
| 同一 Windows 用户下的恶意程序 | 不在范围 | 可直接调 DPAPI、读进程内存（第 02 篇 §3.4 如实口径；broker 头注释 `broker.ts:23-27`） |
| 离线篡改密文 | 检出（GCM 认证失败即拒读），不保证可用性 | 同事项同区内整文件互换不检出（§3.3 取舍） |
| 内存、`pagefile.sys`、`hiberfil.sys`、崩溃转储 | 不在本方案能力范围 | 只能靠 BitLocker/设备加密与 P0-4（转储策略） |

**验收一句话**：导入含唯一金丝雀的材料，跑一次覆盖 Read/Write/Edit/Grep/Glob/Bash(W)/后台任务/文件历史/提问的 A1 任务，**正常结束与中途强杀两种情况下**，对数据根、`userData`、本次测试产生的临时目录做二进制扫描（多种编码），命中为 0；同时 Grep 能搜到工作区内容、会话可续接、成果可登记（§6）。

## 3. 密钥与文件格式（A 与 D 共用）

### 3.1 密钥来源：选“事项工作区密钥”，不直接用事项密钥纪元

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| ① `K = HKDF(matterKey_epoch, "kwl/at-rest/v1" ‖ 用途)` | 不增加密钥存储 | kap-host 需接触事项密钥派生物，且事项密钥行为保留旧块必须长期保存——**无法做“删钥即擦除”**；纪元轮换与 append-only 日志的“一个文件一个纪元”冲突（新内容须换纪元就得整文件重写）；而 `kap/` 目录本来只在本机、从不同步，轮换事项密钥对它没有防护意义 | 不选 |
| ② **每设备每事项随机 32 字节 `K_ws`（代号 gen），以本机设备加密公钥包裹后存账本新表 `matter_ws_keys`**（SQLCipher 内、不进同步） | 与事项密钥解耦：kap-host 永远拿不到事项密钥；撤权/移出时删行即“加密擦除”；与块语义互不干扰；复用 `wrapMatterKey/unwrapMatterKey`（`@zr-legal/keys`） | 多一张表；账本恢复到新机器时旧 `kap/` 状态不可读（本就不迁移，可接受） | **推荐** |

派生（HKDF-SHA256，`salt = "kwl-at-rest-v1"`）：
- `K_zone = HKDF(K_ws[gen], info = "zone:" ‖ 用途)`，用途 ∈ `work` / `materials` / `engine-fs`（broker engine 区与存储服务共用，二者写同一棵 `home/sessions` 树）/ `engine-journal`（WS 事件日志）；
- `K_file = HKDF(K_zone, salt = 文件头随机 32 字节, info = "file")`——**每次整文件写入都换盐**，因此同一文件的任何两版不共用密钥，随机 96 位 nonce 的碰撞界只在单个文件内计算。

生命周期：
- 生成：内核在第一次为该事项启动 kap 运行前于账本事务内生成并包裹落盘（失败即不启动运行：失败关闭）；
- 下发：内核经 IPC 把**本事项全部未退役 gen 的 `K_zone`**（不是 `K_ws`）交给 kap-host（新方法 `openMatter`，或并入 `startRun` 参数）；kap-host 只在内存持有，事项引擎关闭即清零（尽力而为：`Buffer.fill(0)`）；
- 下发前复核成员资格（与现有“非成员 404”同一判断）；
- 轮换：只在“本机用户被移出该事项后又被加回”、“怀疑泄露”、“管理员手动轮换”时 gen+1；新写入用新 gen，旧文件按文件头 gen 解；
- 退役与擦除：本机用户被移出事项、本机设备被吊销、事项删除 → kap-host `purgeMatter`（关引擎、删 `kap/<mid>`）→ 内核删除该事项全部 `matter_ws_keys` 行（账本开 `PRAGMA secure_delete=ON`，避免空闲页残留包裹密钥）。
- **成员移除后旧会话怎么办**：移出的是**别人** → 本机 `kap/` 不受影响、无需重加密（别人从未拿到本机的 `K_ws`）；移出的是**本机用户** → 本机会话随 `purgeMatter` 删除、密钥删除（对应第 02 篇 §9.13“在线设备收到后终止任务并清理缓存”）；离线被盗设备 → 无法远程处置，只剩 DPAPI 根 + 本方案的保护（如实）。事项密钥纪元轮换照旧只作用于共享块。

### 3.2 文件格式 `KWE1`

```
头（64 字节，作为每个分块的 AAD）：
  magic "KWE1"(4) | ver=1(1) | kind(1: 0x01 整文件分块 / 0x02 追加日志) | flags(2)
  gen(u32 LE) | zoneTag(u32：用途的截断哈希) | chunk=65536(u32) | salt(32) | 保留(12)
kind=0x01 分块：每块 [nonce 12][密文 ≤64 KiB][tag 16]，AAD = 头 ‖ 块序号(u64) ‖ 末块标志(u8)
           空文件 = 1 个空块（盘上 92 字节）。明文长度可由盘上长度闭式算出：
           body = disk − 64；n = max(1, ceil(body / (65536+28)))；plain = body − 28·n
kind=0x02 追加日志：每条记录 [len u32][nonce 12][密文 len][tag 16]，AAD = 头 ‖ 记录序号(u64)
           残尾（断电写了一半）按长度/认证失败识别 → 读时丢弃、下次追加前截断；明文长度需扫描记录头（按 (ino,盘上长度,mtime) 缓存）
```

- 分块 + 末块标志 = 防截断、防块重排（STREAM 构造的常规做法）；随机读：`readBytes(n, offset)` 只解所需分块。
- 追加日志用于 `IFileSystemStorageService.append`（`wire.jsonl`、`output.log`、索引脏标记）与 WS 事件日志；broker 的 `appendText` 对加密区改为“读—改—整文件重写”（tmp + rename，保持原子性；工作区追加极少：W 的 `>>` 经提交整文件写回）。
- 追加日志文件头的 gen 落后于当前 gen 时，下一次追加先整文件按新 gen 重写（一次性代价）。
- 不加密文件名（§8 残余）；保留名、临时名格式不变——**路径长度零增加**（Windows MAX_PATH 259，`paths.ts:31`、`broker.ts:239-243`）。

### 3.3 取舍：AAD 不含路径

AAD 绑定 `matter_id`（经 `K_ws` 隐含）、用途（`zoneTag` + 派生）、gen，但**不绑定相对路径**：broker 有大小写更名（`renameAlias :499-513`）、恢复副本改名（`putBack :666-676`）、暂存/落位（`:755-781`）等纯目录项操作，绑定路径就得在每次更名时重加密，破坏这些操作的原子性。代价：离线攻击者可在同一事项同一区内互换两个密文文件而不被发现——不影响机密性目标，如实登记。

### 3.4 新增共享包 `packages/at-rest`（建议名 `@zr-legal/at-rest`）

`seal/open`（分块）、`appendRecord/readRecords`（日志）、`plainSizeOf(diskSize)`、`isSealed(buf)`、`ZoneCodec`（持有 `K_zone[gen]` 环）、`MatterKeyRing`（内存、可清零）。只用 Node `crypto`（AES-256-GCM、HKDF），不引新依赖（第 02 篇 §9.11“使用经审阅的成熟库，不自创协议”——构造是标准 STREAM/分块 AEAD，需在实现评审中由第二人复核）。使用方：file-broker、kap-host、exec-wasm、kernel（成果登记）。

## 4. 方案比较

### 4.1 方案 A：broker 层与引擎持久化层透明 AES-256-GCM

**改哪里**
- `file-broker/src/broker.ts`：`ZoneSpec` 增 `codec?`（`:37-44`）；写路径在 `writeTemp` 写入点（`:326`）、`stageContent`（`:762`）封装；读路径 `readBytes`（`:380-398`）解封；`toStat`（`:515-524`）返回明文 `size` 并新增 `diskSize`；`appendText`（`:443-473`）对加密区改读—改—写；`ExpectedState` 与 `matchesExpected`（`:82-98`）继续比较**盘上**三元组（不变），调用方改用 `diskSize` 构造期望（§5.2）。
- 引擎状态：kap-host 新增 `SealedFileStorageService`（实现 `IFileSystemStorageService` 12 个方法，语义对齐上游 `persistence/backends/node-fs/fileStorageService.ts`：原子写、`append` 的 `durable`、`list(prefix)`、`read` 不存在返回 `undefined`）与 `MemoryQueryStore`（实现 `IQueryStore`，`persistence/interface/queryStore.ts:96-117`）；在 `seeds.ts:177-188` 追加两条种子。
- Grep/Glob：`exec-router.ts:212-224` 不再 `spawnTrusted` 原生 rg，改为返回一个 `HostProcessLike` 的“宿主检索进程”（worker_thread 内运行，re2js 正则，经只读 broker 解密读取）。
- 内核成果登记：`workspace-artifacts.ts` 经 codec 读。

**Kimi Code 补丁**：引擎状态部分零补丁（种子覆盖），**唯一例外是 WS 事件日志**（`SessionEventJournal` 直接 `appendFile`），需 ZP-9a 约 40 行：`createEmbeddedServer({ eventJournalIo? })` 透传到 `SessionEventBroadcaster`，`SessionEventJournal.open/append/readLines/remove` 改用注入的 I/O（缺省仍是 node fs，上游行为不变）。Grep/Glob 零补丁（`runRgOnce` 本就经 `processService.spawn`，`runRg.ts:43`）。

**对各功能的影响**

| 功能 | 影响 |
|---|---|
| Read / Write / Edit | 经 `IHostFileSystem` → broker，透明；`stat().size` 为明文长度，Read 的截断/分页语义不变 |
| Grep / Glob | 实现从原生 rg 换为宿主内 JS 检索；输出格式必须与 rg 逐字节一致（上游解析 `--null`、`--`分隔、`path:line:` 等，`grepTool.ts:485-600`）；以差分测试保证（§6.2） |
| Bash（W） | 见方案 D：读层解密；提交经 broker 自动封装 |
| 文件历史 | 快照块经 `IBlobStore` → 存储服务，透明；读取工作区当前版本经 `IHostFileSystem`（`fileHistoryService.ts:64,483`），透明 |
| 会话恢复/续接 | 转录与状态经存储服务读解密视图（满足 ZP-9“上下文恢复读取经解密视图”）；会话索引在宿主重启后由投影器全量重建（`sessionIndexService.ts:141-153`：无 manifest 即 `ensureProjection()`） |
| 成果登记 | 内核 `diffWorkspace` 解密读，sha256 仍按明文计算，与 BlobStore 一致 |
| 后台任务输出 | `output.log` 经存储服务追加日志格式；将来 G1 对模型只读放行（审阅 A9、`capabilities.ts:188`）须经同一解密视图提供，而非开放盘上路径 |

**性能（估算，待 §6.4 基准确认）**：AES-256-GCM 在带 AES-NI 的笔记本上单核吞吐通常为 GB/s 量级，MB 级文件的加解密开销是毫秒级，远小于 fsync 与杀软扫描；每文件额外 64 + 28×块数 字节。Grep：每文件多一次 broker 逐级校验 + 解密；re2js 吞吐显著低于 Rust regex（字面量走 `indexOf` 快路径，just-bash 的检索引擎已有此优化，`commands/search-engine/regex.d.ts` 的 `preFilter`），几千个文件、上百 MB 的复杂正则可能到秒级——以 worker 池并行、单次 20 秒上限（与上游 `DEFAULT_TIMEOUT_MS = 20_000` 一致，`runRg.ts:6`）兜底。

**崩溃一致性**：写入仍是“临时文件 + fsync + rename”，加密在内存完成后再落盘，原子性不变；追加日志残尾可识别丢弃；minidb 改内存后崩溃即丢，靠对账重建（它本是读模型，`miniDbQueryStore.ts:250` 自述“structural read model”）。**任何时刻盘上只有密文**——崩溃与断电不产生明文残留（除内存类，§8）。

**Windows 特有**：不改文件名与临时名 → 路径长度不变；杀软在 rename 前后持有句柄会导致 `EPERM/EBUSY`（现有 broker 无重试）——建议在 win32 上对 rename/unlink 做有界重试（5 次、20–200 ms 退避，身份复核不变）；高熵改写可能触发国产杀软勒索防护（主要在迁移批量改写时，§7）。

### 4.2 方案 B：运行期明文、结束即封存

做法：运行开始把 BlobStore 中的工作区/会话封包解到 `kap/<mid>`，运行结束（或宿主退出）打包加密回 BlobStore 并删除目录。

| 维度 | 评估 |
|---|---|
| 崩溃窗口 | 引擎会话区在**宿主进程存活期间一直被读写**（会话索引每隔一段时间对账 `sessionIndexService.ts:91,115-116`；文件历史；任务输出），因此“运行期”实际是“软件开着”。宿主被杀、蓝屏、断电、合盖休眠后电量耗尽 → 明文完整留盘，直到下次启动清扫 |
| 残留 | 删除不等于擦除：SSD 磨损均衡与 TRIM 时机、NTFS 小文件驻留在 MFT 记录中、卷影副本/系统还原点、杀软隔离区副本、Windows 搜索索引（若被索引）。每次“解封”还会**再写一遍明文**，残留面随运行次数增长 |
| 功能 | 零改动（这是它唯一的大优点）：rg、W、文件历史都读明文 |
| 一致性 | 封存需要对整个目录做一致性快照，运行中的后台任务与会话索引写入会与打包竞争；需要“封存期间禁止写”的全局锁 |
| 性能 | 每次运行开始/结束全量打包，工作区数百 MB 时为秒到十秒级 |
| 密钥 | 同 §3.1 |
| 结论 | **达不到“拷盘读不出”**；只适合作为：① 存量迁移的一部分；② “冷事项封存”增强（事项 N 天未用 → 关闭引擎、把整个 `kap/<mid>` 打成单个密文包，额外隐藏文件名与目录结构）——列为第 3 步可选项 |

### 4.3 方案 C：Windows EFS 及其他 OS 能力

| 能力 | 可用性 | 评估 | 用法 |
|---|---|---|---|
| EFS（`cipher /e /s:<dir>`） | 仅专业版/企业版/教育版；**家庭版不可用**——国内零售笔记本绝大多数预装“Windows 11 家庭中文版” | 密钥根同为 DPAPI（与本方案同强度）；复制到 FAT/U 盘/网络位置时被静默解密；域环境可能有数据恢复代理（DRA，律所 IT 可解）；对 Node 透明 | 纵深可选项：专业版上由设置页“额外启用系统文件加密”，默认关；**不能替代应用层** |
| BitLocker / 设备加密 | 专业版有 BitLocker；家庭版只有满足硬件条件且登录微软账户时的“设备加密” | 唯一能覆盖页面文件、休眠文件、崩溃转储、删除残留的手段 | 设备页**检测并提示**（无管理员权限可读：Shell 属性 `System.Volume.BitLockerProtection`）；未开启时安全中心显示“建议开启”，不阻断 |
| 非内容索引属性 | 全版本，无需管理员 | 防止 Windows 搜索为数据根建全文索引（AppData 默认不在索引范围，属保险） | 首次启动对数据根 `attrib +I`（或 `SetFileAttributesW FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`），新文件继承 |
| 数据根位置 | — | 当前在 Roaming `%APPDATA%`（`main.cjs:85`）：域漫游配置文件/文件夹重定向会在注销时把 `kap/` 同步到文件服务器 | 建议 `kap/` 迁到 `%LOCALAPPDATA%`（与本方案正交，单独登记） |
| 卷影副本排除（`FilesNotToSnapshot`） | 需管理员 | 收益有限 | 不做 |
| `cipher /w`（擦除空闲空间） | 全版本 | 迁移后可选的一次性“清理磁盘空闲空间”，耗时长，对 SSD 效果有限 | 设备页提供可选按钮（§7） |

### 4.4 方案 D：W 执行域与加密的协同

W 本就是“快照 + 提交”：**写路径**（ChangeSet → `commitChanges` → broker）在方案 A 下自动封装，无需改动；需要处理的只有**读路径**——worker 的 `OverlayFs` 直接读真实目录（`worker.ts:142-154`），以及 `w-tmp`。

| 读路径选项 | 做法 | 密钥是否进 W | 性能 | 改动 | 评估 |
|---|---|---|---|---|---|
| D1 KJ-5 钩子（**推荐**） | 仿 KJ-1～4（`third_party/PATCHES.md:43-50`，按 chunk sha256 锁定的 just-bash 运行时补丁），在 OverlayFs 读下层真实文件的位置（读字节、stat 取 size）加可选解码钩子；worker 以 `workerData` 收到 `work`/`materials` 两个 `K_zone`，钩子调用 `@zr-legal/at-rest` 解封与 `plainSizeOf` | 是（只给两个区子密钥） | 与现状同级（本地读 + 解密） | 小（钩子约 30 行 + 锁定摘要更新） | 保留 OverlayFs 已有的加固与上限拦截（`worker.ts:151`、KJ S3-26/S3-30）；just-bash 升级时需重做补丁 |
| D2 自写 `SealedOverlayFs` | 自实现 just-bash `IFileSystem`（`fs/interface.d.ts:114`），复刻 OverlayFs 的内存层/删除集合语义（worker 依赖 `memory`、`deleted`、`readFileBytes`、`readFileBuffer`、`assertMemoryCapacity`，`worker.ts:17-21,151`） | 是 | 同 D1 | 大（约 400 行 + 一致性测试） | D1 的退路（just-bash 升级使补丁不可维护时） |
| D3 宿主代理读 | worker 下层读经 MessagePort → 监督进程 → IPC → kap-host broker | 否；还可撤掉 W 对数据目录的 `--allow-fs-read` | 每次读一个跨进程往返，`grep -r` 几千文件为秒级 | 中（协议新增请求/应答） | 安全性最好；若红队认为“密钥进 W”不可接受时采用 |

密钥进 W 的边际风险：W 内运行的是 just-bash 解释器与零 JS 桥 CPython，模型代码拿不到 JS 堆；若发生解释器逃逸，攻击者本就能经已授予的读权限 + 解密层读到这些区的明文，且 W 无网络——所以 D1 的边际风险很小，但须在设备页能力说明与 W 红队用例中如实写明。

`w-tmp`：A1 实测为空（just-bash 的 `/tmp` 是内存，`worker.ts:155-158`）；它只是监督进程 cwd 与唯一写授权。处置：监督进程启动前清空、关闭后删除；增加断言测试（运行后为空）；确认不加 `--report-on-fatalerror`、`--heapsnapshot-*` 等会把内存写入 cwd 的 Node 选项。

## 7. 存量迁移（已有明文目录）

1. **标记**：每个事项目录写 `kap/<mid>/.kwl-atrest.json`（保留名，Agent 不可见）记录 `{version, step: 1|2, state: "migrating"|"done"}`；没有标记 = 明文存量。
2. **时机**：宿主 `init` 后、该事项引擎首次打开前（`runtime.ts:274-297` 的 `engine()` 入口处），在 broker 写入临界区内逐事项进行；迁移期间该事项拒绝新运行并在界面说明“正在加密本地数据”。
3. **处理**：可重建/冗余的直接删除——`home/logs/`、`home/cache/query-store/`、`home/server/events/`（运行已结束，事件已镜像进账本：`executor.ts:962`）、`materials/*`、`home/w-tmp/*`；需保留的逐文件“读明文 → 写 KWE1 临时文件 → fsync → rename 覆盖”——`home/sessions/**`、`home/*.json(l)`、（第 2 步）`work/**`；已带 `KWE1` 魔数的文件跳过（幂等，可在任意点中断重入）；全部完成后写 `state: "done"`。
4. **“安全删除”如实口径**：rename 覆盖与删除只移除目录项，旧明文所在的簇/页不会立即被覆盖。迁移对被替换的明文文件**尽力而为**地先以同长度零覆写并 fsync（对 HDD 有效；对 SSD 因磨损均衡基本无效；NTFS 上小于约 700 字节的文件驻留在 MFT 记录内，覆写同一文件可覆盖该记录）。卷影副本与系统还原点中的旧版本、杀软隔离区副本无法由应用清除。因此迁移完成后设备页提示：“此前的本地数据可能仍有物理残留；开启 BitLocker（加密整个驱动器而非仅已用空间）可消除残留风险”，并提供可选的“清理磁盘空闲空间”（`cipher /w:<数据根所在卷>`，耗时长）。
5. **杀软**：分批（每批 ≤ 200 文件、批间让出），只写新临时文件再 rename，不原地改写；随包程序签名一致；实机矩阵验证不触发勒索防护（§6.3）。
6. **失败处理**：单文件失败（被锁、权限）记录并重试，三次失败则该事项保持“迁移中”、拒绝运行并提示，不降级为明文继续运行。

## 8. 残余风险（如实表述）

1. **信任根是 DPAPI**：知道（或可离线破解）Windows 登录密码的人可以解开 safeStorage → 账本 → 包裹的 `K_ws`。这与账本、案卷块同强度，本方案不提高上限；对外口径应是“本地存储加密，密钥受 Windows 账户保护”，而不是“即使知道开机密码也读不出”。
2. **依赖 P0-1/P0-2**：safeStorage 不可用时以明文账本启动（P0-2 未修）会让本方案形同虚设；设备私钥明文（P0-1）降低攻击门槛。
3. **内存与系统文件**：明文必然出现在 kap-host、W、内核、渲染进程内存中；Windows 可能把这些页写入 `pagefile.sys`，休眠时整机内存写入 `hiberfil.sys`；崩溃转储（P0-4）可能含明文与密钥。未开 BitLocker 的机器上这些都可被拷盘读取——应用层无法覆盖。
4. **同用户恶意程序**：可调 DPAPI、注入或读取进程内存、在运行期经正常接口读取内容，不在本层防护范围（第 02 篇 §3.4）。
5. **元数据**：文件名（材料快照第 2 步中性化；工作区文件名为模型生成的令牌形态，仍可能含机构名）、目录结构、文件数量、精确明文长度（分块格式可由盘上长度算出；追加日志可见逐条记录的长度与条数）、修改时间仍明文。
6. **密钥进 W（D1）**：W 内存有 `work`/`materials` 两个区子密钥；解释器逃逸时可被取得（但逃逸者本就能读这些区的明文，且 W 无网络）。若评审不接受，改用 D3（宿主代理读，性能代价见 §4.4）。
7. **离线篡改**：同区内整文件互换不可检出（§3.3）；任何改动导致的认证失败只表现为“文件损坏、拒读”，可用性受损。
8. **存量物理残留**：迁移前的明文可能残留在 SSD/NTFS/卷影副本中（§7.4）。
9. **语义差异**：宿主检索与原生 rg 在冷门参数、编码探测（UTF-16 BOM 转码等）上可能有差异；差分测试只覆盖上游会生成的参数组合。
10. **密钥丢失 = 本机会话状态丢失**：账本恢复到新机器、或 `matter_ws_keys` 行损坏时，旧 `kap/` 不可读（权威记录在账本与块存储，不受影响）；界面须如实提示“本机 Agent 会话历史不可恢复”。
11. **旁注（不在本题范围）**：BlobStore 以明文 sha256 命名块文件（`blobs.ts:80-93`），持有候选文件的人可确认其是否在本机——建议后续改为 `HMAC(K, sha256)` 命名。

## 9. 待拍板
