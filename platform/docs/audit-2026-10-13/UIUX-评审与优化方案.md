## 0. 结论先行

1. **安全机制做得扎实，界面却是按工程师的视角组织的。** 权限、闸门、化名、留痕这些机制在界面上全部看得到，但呈现方式是把内核事实原样铺开：时间线里有“Agent 宿主已启动（Kimi Code 引擎，本机私有嵌入）”“执行域排队”“退出码 0，812 ms”；侧栏底部写着“本机 · 运行时隔离（W） / 唯一出口：应用层约束”；事项头一行挤了 7 个胶囊（L2、标准端点、运行时隔离……）；复核页会显示 `hash`、`pending_review`、`as_of`，未决项甚至直接 `JSON.stringify` 输出。律师第一眼看到的是“系统有多复杂”，看不出“我的活干到哪了”。
2. **首日主路径有三处走不通，30 分钟出首个交付件的目标在当前界面上达不到。**
   - 新建事项时，四项依据有三项默认“待确认”。到“发起前确认”时，“确认发起”按钮是灰的，弹窗里也没有任何修复入口。
   - 律师用自然语言写“审查这份股权转让协议”，系统不会路由到“审合同”，仍按“通用 Agent”发起。
   - 合同审查的主交付件是 DOCX 修订稿，右侧预览只显示“该格式不在预览范围内，请下载后在本机打开”。方案 §6.1 要求的风险卡逐条“接受 / 修改 / 拒绝”工作台，在客户端里不存在。
3. **执行态没有以交付件为中心。** 运行期间右栏（约 45% 宽）一直是“尚无成果”；Agent 的回复要等任务结束才一次性出现，没有流式输出；确认卡被挤在长时间线的最下方，需要滚动才能看到。
4. **确认卡的默认按钮选错了。** 检索确认卡的主按钮（黑色）是“本次允许”，含义是**按原文、带着当事人名称发出**。隐私更好的“改写后允许”反而是次按钮。安全设计应该让最安全的选项成为默认选项。
5. **视觉继承了 Kimi Work 的骨架**（#fbfaf9 侧栏、#191919 主按钮、16px 输入框、260px 侧栏、三栏执行态），**但令牌体系没收住**：样式里有 15 种字号、35 个硬编码色值、9 种圆角；次级文字 #888 在白底上对比度只有 3.54:1，Kimi 蓝链接 3.84:1，Beta 标签 3.34:1，都不到 WCAG AA；没有深色模式，也没有焦点样式；整个应用没有错误边界，任一页面抛错就整窗白屏（实测：设备页收到缺字段的数据后整窗白屏，切换路由也恢复不了）。
6. **历史 V4 演示的 UI 层值得大量继承**，场景内容不在本文评估范围：三条业务线加子领域的二级标签、场景专属“开始”弹窗（写明输入→产出、立场、法域、规则版本、所用工具）、“继续工作”列表、合同审查的“原文 | 审查建议”双栏工作台（锚点高亮、严重度、接受/修改/拒绝、已处理 n/N、“预览交付包”）。演示里也有反例不该继承：“MCP 连接”“法律 Skills”“指令/能力”这类面向配置者的步骤。
7. **改造优先级**：
   - P0（7 项）：堵住首日走不通的地方、建立交付件为中心的执行态、确认卡改为安全默认、技术术语退到二级页面、加错误边界。
   - P1（12 项）：降低信息密度、对比度与键盘可达、全局“等你处理”提醒、复核页律师化。
   - P2：令牌收敛、深色模式、中文排版细节。
   - 估算：P0 约 3～4 人周（前端 2 人），其中 DOCX 预览和风险卡工作台需要内核配合。

## 1. 问题清单

每条按“现状证据 → 问题 → 依据的原则 → 修改建议（文件/组件 → 改成什么）”的顺序写。

### P0（阻断首日或造成误操作，G0 退出前必须改）

#### P0-1 新建事项后第一个任务发不出去
- **证据**：`components/NewMatter.tsx` 的四项依据默认值是 `{ engagement: "pending", personal_info: "pending", sensitive: "not_applicable", subprocessor: "pending" }`。`components/RunSheet.tsx` 在 `estimate.data_where.start_blocked` 时把“确认发起”置灰，唯一的解释藏在按钮的 `title` 悬浮提示里；弹窗里只有一条橙色横幅（截图 `app-runsheet.png`：“个人信息处理依据、转委托与次处理者 待确认：本事项只运行本机能力”），没有任何可点的修复入口。方案 §5 第 3 步要求的“示例事项（虚构、已完成交付件、标‘示例’）”在客户端里也没有。
- **问题**：新律师建完事项、写好任务、点发送之后撞上一个灰按钮，要自己找到事项头里的“依据”胶囊，打开四段式编辑器，理解“转委托与次处理者”是什么意思，再回来重新发起。这是首日流失最大的一个点。
- **原则**：错误预防加原地修复（Nielsen #9）；渐进披露；不让用户为了满足系统前提去别处找入口。
- **修改**：
  1. `NewMatter.tsx`：把“四项依据”从四行分段按钮改成**一个律师听得懂的问题**，四项分别记录的合规语义仍保留在内核：
     > **客户是否同意本案使用 AI 辅助？**
     > ◉ 已取得同意（委托合同或书面确认）　○ 还没有，先只用本机功能　○ 客户明确不同意使用云端 AI
     > *选“已取得同意”即记录：委托/保密授权 = 已确认；转委托与次处理者（中软、月之暗面）= 已告知；个人信息处理依据 = 已确认（委托处理）。* [逐项调整 ▸]
     “敏感信息特别条件”只在密级选“敏感”时出现。“逐项调整”展开后才是现在的 `BasisEditor`。
  2. `RunSheet.tsx`：当 `start_blocked` 为真时，弹窗里直接内嵌上面那个问题，并给两个按钮：“记录同意并发起”（主按钮）和“只用本机功能发起”（仅在场景支持本机运行时出现，例如整理材料、回稿比对、脱敏）。原来的 `title` 提示删掉。
  3. 新增 `components/SampleMatter.tsx`，并在 `Home.tsx` 的空状态里放入口：首次打开时自动放入“示例 · 甲公司股权转让（受让方）”，四项齐备，带一份已完成的审查意见书和修订稿，全部标“示例”，不发真实请求。空状态文案改成：“先看一个示例，或拖入你的第一份合同。”

#### P0-2 自然语言不路由到业务场景，场景卡点了像没反应
- **证据**：`Home.tsx` 的 `value.scenario` 默认是 `a1.agent_task`。截图 `app-runsheet.png` 中输入“审查这份股权转让协议，我方为受让方”后，发起前确认显示“方法：通用 Agent”。场景卡的 `onClick` 只做了 `setValue(...)` 和 `window.scrollTo(top)`，没有任何打开、展开或选中的视觉反馈，律师只能从输入框下方多出来的一个蓝色小 chip 推断发生了什么。
- **问题**：律师按业务思考，而不是按“方法”思考（用户已拍板“按律师业务线组织”）。通用 Agent 不走确定性工作流，也不会产出原生修订稿，同一句话得到的交付件质量会明显差一截。
- **原则**：系统状态可见（Nielsen #1）；识别优于回忆；尽量让用户只描述任务，由系统建议方法。
- **修改**：
  1. `Composer.tsx`：在输入去抖 400ms 后做意图识别（G0 用本机关键词规则即可：审查/审核/修订 + 合同/协议 → `s1.contract_review`；回稿/对方修改 → `s1b`；证据/时间轴/整理案卷 → `s2`；研究/检索/法条/现行有效 → 研究；起草/起诉状/答辩状/律师函 → 起草）。在输入框上沿显示**建议条**（不自动切换）：
     > 💡 这看起来是**合同审查**：会生成带修订痕迹的合同和审查意见书。需要一份 Word 合同。 [使用合同审查] [仍按通用任务]
  2. `Home.tsx` 场景卡：点击后打开**场景开始面板**（新组件 `ScenarioStartSheet`，版式继承演示的 `demo-workflow.png`）。面板里写清“你给什么 → 你得到什么”，带立场下拉（从事项带入）、材料拖放区、预计用时与点数，主按钮写“开始审查”，不要写“确认发起”。
  3. `RunSheet.tsx` 的“方法”一行改叫“做什么”，显示场景中文名加产出物，例如“合同审查 → 修订稿 + 审查意见书”。

#### P0-3 执行态没有以交付件为中心（右栏空置、DOCX 和 XLSX 看不了、没有风险卡工作台、没有流式输出）
- **证据**：
  - 截图 `app-run.png`：运行中右栏写“尚无成果。”，占约 45% 宽。
  - `SafePreview.tsx`：非 md/txt/html/json 一律提示“该格式不在预览范围内，请下载后在本机打开”。
  - `RunView.tsx`：只有 `terminal && preview.text` 时才渲染“Agent 回复”，过程中没有任何文本流。
  - 全仓 `apps/desktop/src` 里没有风险卡、接受/拒绝相关的组件，`s1_issue_table` 只是交付物标签里的一个名字。
  - 方案 §6.1 明确的流程是“风险卡与替代条款 → 律师接受/修改/拒绝 → 文书引擎写原生修订”。
- **问题**：合同审查、材料整理、文书起草的主交付件都是 DOCX 或 XLSX，律师在应用里看不到，只能下载后去 Word 里看，再回来点“提交复核”。“看 → 改 → 定稿”这个核心动作没有发生在产品里，差异化价值就丢了。
- **原则**：以产出物为中心（Kimi Work 执行态就是右侧预览区约 45%）；直接操作；缩短“看 → 改 → 交”的闭环。
- **修改**：
  1. **右栏三态**（`RunView.tsx` 的 `exec-right`）：
     - 运行中：显示“工作清单”（来自 `plan.created` 加 TodoList 事件，逐项打勾）和“正在起草”的流式草稿。
     - 产生交付件后：自动切到交付件预览。
     - 结束后：交付件预览，下方一行“下一步：提交复核 / 在 Word 中打开”。
  2. **DOCX/XLSX 预览**：内核新增 `artifacts.render_html`，由 `packages/docx-engine` 输出带修订标记（`<ins>/<del>`）的安全 HTML，XLSX 输出前 500 行表格，再经现有 `SafePreview` 的隔离 iframe 渲染。修订用 `--hl-revision`，删除线用 `--risk-high`。
  3. **合同审查工作台**（新组件 `components/ContractReviewWorkbench.tsx`，在 `s1.contract_review` 的结果页替代通用三栏）：
     - 左侧：合同原文，条款锚点高亮。
     - 右侧：风险卡列表。卡片头部是严重度（重大/一般/提示）加一句话问题，展开后是“问题判断 / 建议文本 / 依据与核验状态 / 可退让方案”，底部三个按钮“接受 / 修改后接受 / 不采纳”。
     - 顶部：进度“已处理 3/12 · 2 项重大风险待处理”，主按钮“生成修订稿”（全部处理后才高亮）。
     - 版式直接继承演示 `demo-continue.png` 和 `legal-workspace.js`、`legal-workspace.css`。
  4. **流式输出**：宿主事件转发 `agent.text_delta`（或沿用 final_message 的增量），中栏追加一个“Agent 正在写”的气泡，并加 `aria-live="polite"`。

#### P0-4 执行时间线暴露引擎和系统细节，任务标题是“Agent 任务”
- **证据**：`RunView.tsx` 的 `buildSteps` 会产出“Agent 宿主已启动（Kimi Code 引擎，本机私有嵌入）”“执行域排队（第 1 位）”“本机执行域运行结束（退出码 0，812 ms）”“工作区提交：写入 1，删除 0”“数据级别 L2”“联网检索（经出站闸门）”“Agent 终态：……”；`SCENARIO_LABELS["a1.agent_task"] = "Agent 任务"` 被用作页面大标题（截图 `app-run.png`）。每一步还都带一个时分秒时间戳。
- **问题**：信息噪声大，律师分不清哪些步骤需要自己关心；“退出码”“执行域”会制造焦虑或困惑；标题也没法帮律师区分多个任务。
- **原则**：说用户的语言（Nielsen #2）；分层披露（律师层 / 审计层）。
- **修改**：
  1. `buildSteps` 输出两类：`level: "lawyer" | "detail"`。律师层只保留这些：
     - “开始处理”
     - “已读完 2 份材料”（有失败时写“1 份无法读取：扫描件过于模糊”）
     - “计划”
     - 每个计划步骤的进行中和完成状态
     - “需要你确认 …”
     - “正在联网查资料”
     - “核对引用：9 条中 1 条有问题”
     - “草稿已生成：审查意见书”
     - “完成 / 部分完成 / 未完成（原因）”
     其余事件（宿主启动、执行域排队、退出码、工作区提交、数据级别）归入折叠的“处理细节”，默认收起。
  2. 时间戳只给律师层步骤显示相对时间（“2 分钟前”），悬浮时显示绝对时间。
  3. 页面标题改成 `run.goal` 的前 24 个字。没有 goal 时用场景名，例如“合同审查 · 股权转让协议（对方初稿）”。`SCENARIO_LABELS` 里的“Agent 任务”改成“通用任务”。
  4. 工具名映射 `TOOL_LABELS` 去掉括号里的技术说明（见 §2 文案替换表）。

#### P0-5 确认卡：主按钮是风险更高的选项，按钮太多，过期处理也不友好
- **证据**：`components/Cards.tsx` 的检索卡里，`originalOk` 为真时“本次允许”（按原文、保留机构当事人名称发出）是 `btn-primary`，“改写后允许”是次按钮，另外还有“本任务内改写后允许”和“拒绝”，一共 4 个按钮（截图 `app-run-card.png`）。卡内字段有 6～8 个，包括“Agent 的说明（模型自述，仅供参考）”和一段关于“已批准”字样的工程化免责说明。`expires_at` 到期后“按拒绝处理”，没有任何主动提醒。
- **问题**：律师在赶时间时会点黑色按钮，结果就是带着当事人名称原文出站，这和产品的隐私承诺相反。字段多、按钮多，每张卡平均要读 10 秒以上。律师离开 10 分钟回来，任务已经静默拒绝并继续往下跑了。
- **原则**：安全默认（Secure by default / 默认最小披露）；一次只问一个问题；只为真正需要决策的事打断律师。
- **修改**（`Cards.tsx` 的 `ApprovalCardView`）：
  1. **检索卡**按下面的版式改，参数与内核 `variants` 一一对应，不改内核语义：
     ```
     ┌ 要联网查一条资料 ───────────────────────── 9:58 后自动跳过 ┐
     │ 将发给中软检索服务（不保存，不带事项信息）：                   │
     │   “某科技公司 股权转让 优先购买权 纠纷”                       │
     │    └ 已把「乙科技有限公司」改写为「某科技公司」（差异高亮）       │
     │ [ 用改写后的查询检索 ]（主按钮）   [ 不查了 ]                    │
     │ ☐ 本任务内同类检索都按改写后发出，不再询问                       │
     │ 更多选项 ▸  按原文检索（会发出「乙科技有限公司」）               │
     └──────────────────────────────────────────────────────────────┘
     ```
     “按原文检索”收进“更多选项”，点击后二次确认：“原文会包含当事人名称，确定吗？”
  2. 通用卡字段压缩成三行：**要做什么 / 会发给谁、发什么 / 预计费用**。“为什么需要确认”改成卡片标题下的一行灰字；“Agent 的说明”收进“查看 Agent 的理由 ▸”；底部那段关于“已批准”字样的免责说明删掉（这是系统不变式，写进帮助文档即可）。
  3. 过期：剩 2 分钟时卡片头部变橙并倒计时；`waiting_approval` 状态触发 Electron 系统通知、任务栏闪烁和侧栏事项橙点（见 P1-9）。过期文案改成：“已超时，Agent 跳过了这一步。需要的话可以 [重新发起这一步]。”
  4. 计划卡：主按钮“按这个计划开始”，次按钮“提修改意见”。修改意见输入框默认收起，点“提修改意见”后才展开。

#### P0-6 侧栏和全局状态栏使用技术术语，未开放入口占位
- **证据**：`Sidebar.tsx` 底部显示“本机 · 运行时隔离（W）”加“唯一出口：应用层约束 / 出站结果不明 N 条，待对账 / 内核未连接”。9 个入口里，“收件区 G2”“提醒与定时 G1”点进去是 `NotOpenPage`，正文里有“CronCreate”“宿主策略”等词。`Methods.tsx` 和 `Home.tsx` 底部的说明还引用了“第 06 篇 §3”“G0/G1”。

## 2. 文案替换表：技术术语改成律师语言

原则：
- 律师界面（首页、事项、执行态、确认卡、复核、交付件）一律用右列。
- “设置 · 本机与安全”和“管理”页可以保留左列术语，但首次出现时要加一句解释。
- `lib/labels.ts` 统一维护，组件里不要再写死文案。
- 文案依然遵守第 02 篇 §12 的禁用词（不写“绝对安全”“数据不出所”）。

| 位置（文件） | 现文案 | 改为 |

## 3. 隐私安全体验：放心，但不打扰

### 3.1 三档呈现规则

| 档 | 什么时候用 | 呈现方式 | 律师需要操作吗 |
|---|---|---|---|
| **静默自动** | 有利于隐私、可撤回、无外部副作用 | 只记进数据去向卡；执行态徽标可以一闪而过 | 不需要 |
| **告知不拦** | 已自动做了保护动作，律师应该知道但不必决定 | 行内灰字或一次性提示条，不弹窗、不停任务 | 不需要（可点“了解”） |
| **必须确认** | 会把含当事人信息的内容发到新去向、产生费用或不可逆 | 确认卡：一张卡只问一件事，主按钮选最安全的选项 | 需要 |
| **只能由人在界面上做** | 对外发送、签发、导出、改权限（X1–X4） | 不出现在 Agent 流程里，只能在复核/交付件页由律师主动发起 | 需要，并且要本人设备签名 |

### 3.2 安全动作分级清单（对应第 02 篇 §9.4、§9.5，不改变内核语义，只改呈现方式）

| 动作 | 档 | 律师看到的文案示例 |
|---|---|---|

| 检索式不含当事人名称时联网检索 | 静默自动 | （时间线）“联网查资料：股东未实缴出资 补足责任” |

| 对外发送、签发、导出、改权限 | 只能由人在界面上做 | 复核页：“签发只对当前这一版文件有效” |

### 3.3 写确认卡的 6 条规则（写入 `Cards.tsx` 头部注释，供后续开发遵守）

1. **一张卡只问一件事**，标题写成动词短语：“要联网查一条资料”“要打开一个新网站”。
2. **字段最多 3 个**：会发出什么（原文直接展示，改写处高亮）/ 发给谁 / 花费。“为什么”放在标题下一行灰字。
3. **主按钮永远是最安全、又能让任务继续的选项**（改写后检索、只发文字）；风险更高的选项放进“更多选项”，并二次确认。
4. **“本任务内不再询问”做成勾选框**，不单独占一个按钮。
5. **卡片出现在用户视线里**：中栏底部固定区（sticky），并自动滚动到可视区；任务离开当前视图时发系统通知。
6. **过期不惩罚**：过期文案说明跳过了什么、怎么补做，并提供“重新发起这一步”。

## 4. 四个核心场景的流程诊断

“步数”指从首页出发到拿到可交付文件的点击和决策次数，依据当前源码路径计算，假设事项已经存在。

| 场景 | 当前路径 | 步数 / 决策点 / 卡点 | 目标路径 | 目标步数 |
|---|---|---|---|---|
| **合同审查**（非诉 / 企业法务） | 首页 → 点“审合同”卡（页面只滚到顶部）→ 点“导入”选 DOCX → 输入框写目标 → 发送 → 发起前确认（若依据未齐则卡死）→ 确认发起 → 执行态等待（右栏空）→ 结束后在右栏下拉框选“修订稿” → **DOCX 不能预览** → 下载 → 去 Word 看 → 回来点“提交复核” → 复核页勾选 → 确认签发 | 约 13 步，4 个决策点，2 处卡点（依据、预览）；风险卡交互缺失 | 把合同拖到首页输入框 → 建议条“合同审查？我方立场：[受让方▾]” → 开始审查 → 运行中右栏显示进度，1～3 分钟后进入**审查工作台** → 逐条接受/修改/不采纳（重大风险优先）→ 生成修订稿（右栏预览修订痕迹）→ 提交签发（或在 Word 中打开） | ≤ 6 步（不含逐条处理风险卡） |

| **文书起草**（诉讼：起诉状、答辩状、律师函） | **首页和方法库都没有入口**，只能自己用通用 Agent 描述；产出 DOCX 后同样无法预览 | 入口缺失 | 诉讼仲裁标签下加“起草文书（试用）”卡 → 开始面板选文书类型、带入事项当事人与立场、选材料 → 计划 → 流式出稿，右栏 DOCX 预览 → 字段确认（当事人、金额、诉请）→ 提交复核 | ≤ 6 步 |

**等待与反馈的统一要求**：
- 发送后 1 秒内出现“开始处理”。
- 3 秒内出现计划或第一段流式文本；做不到时显示“正在读材料（2/5）”这类具体进度，不要只显示“执行中…”。
- 超过 30 秒的步骤显示预计剩余时间区间。
- 离开执行页不取消任务（当前已是这样），并在侧栏显示进行中的状态点。

## 8. 验收标准

### 8.1 可用性（试点前用 8～10 名无 IT 背景的执业律师做无培训测试，按方案 §5 分层报告）

| 指标 | 目标 |
|---|---|
| 首次打开到在**示例事项**里看到一份完成的交付件 | ≤ 3 分钟，10 人中 ≥ 9 人无需求助 |
| 首次打开到用**自己的 DOCX** 拿到第一份审查交付件（修订稿已预览） | P50 ≤ 30 分钟，P90 ≤ 45 分钟（不含模型运行时间超过 10 分钟的长合同） |
| 合同审查：首页到“生成修订稿”的点击和决策次数（不含逐条处理风险卡） | ≤ 6 |
| 法律研究：首页到看到流式备忘录 | ≤ 4 步 |
| 材料整理：首页到在应用内看到证据目录表格 | ≤ 4 步 |
| 典型 L2 事项研究任务（标准模式）的确认卡数量（计划卡 + 跨边界卡） | ≤ 2 张，其中跨边界卡 ≤ 1 张 |
| 确认卡理解度：看卡 10 秒后能正确回答“会发出什么、发给谁” | ≥ 90% |
| 确认卡上选中“按原文发出含当事人名称”的比例（非本意操作） | 可用性测试中 0 次误选 |
| SUS 量表 | ≥ 75 |
| 律师复述“我的数据去哪了”与“中软看得到什么”页一致 | ≥ 80% |

### 8.2 工程可验（进 CI）

1. **术语扫描**：对 `apps/desktop/src/{pages,components}` 里的 JSX 文本和 `lib/labels.ts` 跑词表：`执行域|闸门|令牌|端点|宿主|控制面|对账|吊销|退出码|hash|as_of|W）|MXC|W-core|kap|L3a|L3b|G0|G1|G2|第 0\d 篇|§`。设置·本机与安全页和管理页加白名单，其余页面命中数为 0。
2. **对比度**：axe-core 扫描首页、事项、执行态、复核、交付件 5 页，`color-contrast` 的 serious 问题为 0；所有正文文字 ≥ 4.5:1。
3. **键盘**：playwright 脚本只用键盘完成“新建事项 → 发起合同审查 → 处理确认卡 → 提交复核”，焦点始终可见。
4. **令牌**：stylelint 规定 `styles.css` 里不出现十六进制色值（令牌包除外），字号只取 7 个令牌值，圆角只取 5 个令牌值。
5. **容错**：给每个路由注入一次异常响应（字段缺失），页面显示兜底页，侧栏仍可用，不白屏。
6. **反馈时延**：模拟内核下，发送后 ≤ 1 秒出现首个律师层步骤；有流式事件时 ≤ 300ms 渲染到中栏。
7. **布局**：1280×720 和 1366×768 两种视口下，执行态能看到材料摘要、确认卡和交付件预览，不出现水平滚动。
8. **安全默认**：检索确认卡的主按钮对应 `variant: "generalized"`（单测断言）；L3b 事项的任何出站相关按钮不在 DOM 中。
