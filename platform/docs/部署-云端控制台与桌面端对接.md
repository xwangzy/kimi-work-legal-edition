# 云端控制台部署与桌面端（Windows exe）对接手册（第 37 批）

本手册是一条从零到“律师在 Windows 上用起来、中软在网页上管用量与计费”的操作路线。各服务配置项的完整说明与安全口径见
[部署-云端生产入口.md](部署-云端生产入口.md)，本文只写落地步骤，遇到细节以那份为准。

---

## 0. 先看全貌：三条对接线

```text
 律师电脑（Windows）                         中软云（服务器）                               运营人员（运维网段内的电脑）
┌──────────────────────┐   HTTPS + 钉住   ┌───────────────────────────────┐   HTTPS   ┌──────────────────────────┐
│ KimiWorkLegal.exe    │ ───────────────▶ │ 控制面 control-plane :8443     │ ◀──────── │ 浏览器 · 运营控制台        │
│  内核 / 出站闸门      │                  │   ├─ 签名服务 cp-signer（内网）│  签名请求  │ （静态页，私钥只在本页内存）│
│  release.json（asar） │ ───────────────▶ │ 法律模型网关 gateway           │           └──────────────────────────┘
│                      │ ───────────────▶ │ 检索 search（分发/支持/通知/中继可选）│
└──────────────────────┘                  └───────────────┬───────────────┘
                                                          │ 上游
                                                 中软 MaaS（kimi-k3.1-pro）
```

1. **地址与信任**：exe 只认打包时写进 asar 的 `release.json`——云端各服务地址、TLS 公钥钉住值、控制面与席位的签名公钥。
   改环境变量、改 hosts 都不能把客户端指到别处。所以**先部署云端、拿到证书，再生成 release.json，最后打 exe**（第 3～6 步）。
2. **开通与席位**：运营在控制台开通律所租户、发创始开通码 → 律所管理员在 exe 里输入开通码 → 律所根密钥登记、设备领到席位令牌 →
   之后律师的模型请求都带席位令牌进网关（第 7 步）。
3. **用量与计费**：网关每次请求先写计量日志、再向控制面领“额度租约”并回报每个席位的用量 → 控制面额度账本（池余额、月度上限、按席位用量）
   → 运营控制台查看、加量、设上限、导出对账 CSV（第 8 步）。

## 1. 服务器准备

| 角色 | 建议规格（试点，≤ 20 家律所） | 网络 |
|---|---|---|
| 控制面 + 签名服务 | 2 vCPU / 4 GB / 40 GB SSD，各一台（签名服务只在内网） | 控制面对公网 443；签名服务只许控制面访问 |
| 网关 + 检索 | 4 vCPU / 8 GB，可同机不同端口 | 对公网 443；出网到中软 MaaS |
| 运营控制台（静态页） | 可与控制面同机，另一个域名 | **只对运维网段开放** |
| 可选：分发、支持、通知、中继 | 2 vCPU / 4 GB | 对公网 443 |

- 系统：任意 64 位 Linux（以 Ubuntu 24.04 为例）；**Node.js ≥ 24.15**（CI 用 26.8.1，建议同版本）。
- 每个对外服务一个域名，例如 `cp.kwl.example.com`、`gw.kwl.example.com`、`search.kwl.example.com`、控制台 `ops.kwl.example.com`。
- **TLS 必须终止在服务进程本身**：前面只能放四层负载均衡（TCP 直通、保留客户端源地址）。**不要**放 WAF、CDN、七层反向代理——
  客户端钉住的是服务证书的公钥，被代理换了证书就连不上；控制面的限速与运营网段也按源地址判断。
- 时间同步（chrony）必须开：运营签名允许的时钟偏差只有 5 分钟，签名服务只有 5 秒。

```bash
# 每台服务器
sudo useradd --system --home /opt/kwl --shell /usr/sbin/nologin kwl
sudo mkdir -p /opt/kwl /etc/kwl /var/lib/kwl /run/secrets && sudo chown kwl:kwl /var/lib/kwl
sudo git clone <仓库地址> /opt/kwl/src && cd /opt/kwl/src/platform && sudo npm ci
```

## 2. 生成密钥与口令文件（在一台安全的离线电脑上做一次）

```bash
cd platform
node scripts/cloud-init-secrets.mjs --env prod --out /secure/kwl-prod --mount /run/secrets
```

输出两个目录：`secrets/`（私密，0600）和 `public/`（公钥表，可随配置分发）。脚本最后会列出每个文件放到哪台服务器。要点：

- `secrets/cp-envelope.pem`、`seat*.pem` **只放签名服务**；控制面进程配了签名私钥会拒绝启动。
- `secrets/cp-envelope-next.pem` 是预置的下一把控制面密钥，**离线保管、不部署**——它的公钥已经在 `public/cp-public-keys.json` 里，
  将来轮换时客户端不用升级。
- 放到服务器上统一挂在 `/run/secrets/`（属主 `kwl`、权限 0400）；公钥表放 `/etc/kwl/`。有 KMS / 密钥管理服务的，按它的方式挂载成只读文件。

## 3. TLS 证书与“备份钉住”

每个对外服务要一张证书（公共 CA 或中软自有 CA 都行）。客户端会钉住**叶子证书的公钥**，所以还要为每个域名**预先生成一对备用密钥**：

```bash
# 每个对外域名各做一次，备用私钥离线保管；证书续期时用备用私钥申请新证书，客户端不会断
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out /secure/backup/gw.backup.key
openssl pkey -in /secure/backup/gw.backup.key -pubout -out /secure/backup/gw.backup.pub.pem
```

续期纪律：**续期时要么复用当前密钥对，要么换成备用密钥对**。两样都不是的新证书，已安装的 exe 会拒绝连接。用过备用密钥后，
马上再生成一对新的备用密钥，下一版 exe 一起钉进去。

## 4. 配置并启动云端服务

配置文件放 `/etc/kwl/<角色>.json`，启动命令一律是：

```bash
node /opt/kwl/src/platform/scripts/cloud-serve.mjs --config /etc/kwl/<角色>.json
```

### 4.1 签名服务（先启动）`/etc/kwl/cp-signer.json`

`keys` 段直接用 `public/signer-keys.json` 的内容。`ledger_archive` 在 `environment: "prod"` 下必填（单独的、开了版本控制与对象锁的桶，
规则见生产入口文档“签名服务”一节）。试点阶段可以先用 `"environment": "stg"` 起步。

```json
{
  "role": "cp-signer",
  "environment": "prod",
  "listen": { "host": "10.0.1.10", "port": 8443 },
  "tls": { "cert_file": "/run/secrets/signer.crt", "key_file": "/run/secrets/signer.key", "client_ca_file": "/etc/kwl/internal-ca.crt" },
  "allowed_callers": ["spiffe://kwl/prod/cp-api"],
  "data_dir": "/var/lib/kwl",
  "keys": { "…": "粘贴 public/signer-keys.json" },
  "ledger_archive": { "kind": "s3", "endpoint": "https://obs.cn-north-4.myhuaweicloud.com", "bucket": "kwl-prod-signer-ledger", "region": "cn-north-4", "prefix": "ledger",
                      "access_key_id_file": "/run/secrets/ledger-ak", "secret_access_key_file": "/run/secrets/ledger-sk", "kms_key_id": "<KMS 密钥编号>" }
}
```

签名服务用内部 CA 做双向 TLS：给控制面签一张客户端证书，URI SAN 写 `spiffe://kwl/prod/cp-api`。

### 4.2 控制面 `/etc/kwl/control-plane.json`

```json
{
  "role": "control-plane",
  "listen": { "host": "0.0.0.0", "port": 8443 },
  "tls": { "cert_file": "/run/secrets/cp.crt", "key_file": "/run/secrets/cp.key" },
  "service_secret_file": "/run/secrets/service-secret",
  "data_dir": "/var/lib/kwl",
  "signer": { "url": "https://cp-signer.internal:8443", "client_cert_file": "/run/secrets/cp-api-client.crt", "client_key_file": "/run/secrets/cp-api-client.key",
              "ca_file": "/etc/kwl/internal-ca.crt", "servername": "cp-signer.internal" },
  "state_key_file": "/run/secrets/cp-state.key",
  "code_pepper_file": "/run/secrets/cp-code-pepper.key",
  "ops": {
    "deployment": "prod",
    "roster_file": "/etc/kwl/ops-roster.json",
    "roster_keys_file": "/etc/kwl/ops-roster-keys.json",
    "allow_cidrs": ["10.20.0.0/24"],
    "console_origins": ["https://ops.kwl.example.com"]
  },
  "metrics": { "host": "127.0.0.1", "port": 9464 }
}
```

- `ops.allow_cidrs`：运营人员电脑（或堡垒机出口）所在网段。**从别的地方访问运营接口一律 404**——控制台页面能打开，但登录会提示连不上接口。
- `ops.console_origins`：运营控制台的来源（`https://域名`，不带路径与末尾斜杠）。只给它跨源读运营接口的回复；不在名单里的来源浏览器读不到结果。
- 多实例高可用：再加 `state_store`（PostgreSQL）与 `nonce_store`（Redis），见生产入口文档“控制面一主多备”。

### 4.3 法律模型网关 `/etc/kwl/gateway.json`（接中软 MaaS）

```json
{
  "role": "gateway",
  "listen": { "host": "0.0.0.0", "port": 8443 },
  "tls": { "cert_file": "/run/secrets/gw.crt", "key_file": "/run/secrets/gw.key" },
  "service_secret_file": "/run/secrets/service-secret",
  "control_plane": { "url": "https://cp.kwl.example.com", "keys_file": "/etc/kwl/cp-public-keys.json" },
  "seat_keys_file": "/etc/kwl/seat-public-keys.json",
  "data_dir": "/var/lib/kwl",
  "upstream": { "base_url": "https://maas.jointpilot.com/v1", "api_key_file": "/run/secrets/maas.key" }
}
```

- 上游型号：网关对内核的稳定别名是 `legal/k3`，MaaS 实际型号用环境变量改写：**systemd 单元里加 `Environment=KWL_UPSTREAM_K3=kimi-k3.1-pro`**
  （按 MaaS 开通的型号填）。
- `maas.key` 是中软 MaaS 的 API 密钥，**只放网关这一台**、权限 0400。
- 计量日志写在 `/var/lib/kwl/gateway/meter.jsonl`（只有编号与 token 数，没有请求内容），是计费对账的依据，**要备份，保留不少于 6 个月**。

检索（`role: "search"`）同样写法，`upstream` 换成检索上游。分发、支持、通知、中继按需开，配置见生产入口文档。

### 4.4 systemd 单元（每个角色一份）

```ini
# /etc/systemd/system/kwl@.service    启用：systemctl enable --now kwl@cp-signer kwl@control-plane kwl@gateway kwl@search
[Unit]
Description=Kimi Work 法律版云端服务 %i
After=network-online.target
Wants=network-online.target

[Service]
User=kwl
WorkingDirectory=/opt/kwl/src/platform
ExecStart=/usr/bin/node scripts/cloud-serve.mjs --config /etc/kwl/%i.json
# 只给网关：Environment=KWL_UPSTREAM_K3=kimi-k3.1-pro（建议用 kwl@gateway.service.d/override.conf）
Restart=always
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/kwl
PrivateTmp=true
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target
```

启动顺序：签名服务 → 控制面 → 网关、检索、其他。验收：

```bash
curl -s https://cp.kwl.example.com/healthz          # {"ok":true}
curl -s https://gw.kwl.example.com/readyz           # 2 分钟内取到过控制面吊销集才是 200
journalctl -u kwl@control-plane -n 50               # 看到“control-plane 已就绪（https …）”
```

## 5. 运营名册与运营人员的私钥

运营控制台不设账号密码：**每个运营人员一把自己的签名私钥**，公钥登记在安全管理员签发的“运营名册”里。

```bash
# ① 安全管理员（离线电脑）：名册签名密钥，私钥永不上服务器
node scripts/ops-cli.mjs roster-keygen --kid sec-1 --out /secure/offline --keys-file ops-roster-keys.json
node scripts/ops-cli.mjs roster init --deployment prod --sign-key /secure/offline/sec-1.key.pem --sign-kid sec-1 --out ops-roster.json

# ② 每位运营人员（本人电脑）：生成自己的密钥，把 .pub.pem 和屏幕上的指纹交给安全管理员
node scripts/ops-cli.mjs keygen --id op_0001 --kid k1 --out ~/.kwl-ops --passphrase-env KWL_OPS_PASS

# ③ 安全管理员登记（电话或当面核对指纹），按职责给权限
node scripts/ops-cli.mjs roster add --roster ops-roster.json --id op_0001 --perms tenant.read,tenant.manage,quota.manage,quota.cap,tenant.terminate \
     --pub op_0001.k1.pub.pem --fingerprint <指纹> --sign-key /secure/offline/sec-1.key.pem --sign-kid sec-1 --out ops-roster.json
node scripts/ops-cli.mjs roster add --roster ops-roster.json --id op_0002 --perms tenant.read,activation.issue,device.revoke \
     --pub op_0002.k1.pub.pem --fingerprint <指纹> --sign-key /secure/offline/sec-1.key.pem --sign-kid sec-1 --out ops-roster.json

# ④ 把 ops-roster.json、ops-roster-keys.json 放到控制面的 /etc/kwl/（换文件即生效，不用重启）
```

- **同一人不能同时有 `tenant.manage`（开通）和 `activation.issue`（发开通码）**：开通律所和发码要两个人配合，这是有意的职责分离。
- 名册至多 31 天有效，到期前 `roster renew` 重签并重新放上去；过期时运营接口暂停（业务不受影响），控制台提示“运营名册暂不可用”。
- 人员离职：`roster revoke --id op_xxxx` 后放上新名册，立即生效。

## 6. 部署运营控制台（静态网页）

控制台是 `platform/apps/ops-console/` 下的四个静态文件（`index.html`、`console.js`、`ops-sign.js`、`console.css`）加一份 `config.json`，
没有后端、不存数据。所有请求都在浏览器里用运营人员自己的私钥签名后直连控制面。

```bash
sudo mkdir -p /srv/kwl-ops-console
sudo cp platform/apps/ops-console/{index.html,console.js,ops-sign.js,console.css} /srv/kwl-ops-console/
sudo tee /srv/kwl-ops-console/config.json >/dev/null <<'EOF'
{ "control_plane_base": "https://cp.kwl.example.com", "deployment": "prod", "point_price_cny": 0.001, "label": "生产环境" }
EOF
```

- `deployment` 必须与控制面 `ops.deployment`、名册的部署标识一致。
- `point_price_cny` 可选：每点参考单价（元），只用于页面显示“约 ¥”，不参与计费；不想显示就删掉。

nginx 示例（控制台只是静态文件，用 nginx 没问题；**控制面本身前面不要放 nginx**）：

```nginx
server {
  listen 443 ssl;
  server_name ops.kwl.example.com;
  ssl_certificate     /etc/kwl/tls/ops.crt;
  ssl_certificate_key /etc/kwl/tls/ops.key;
  root /srv/kwl-ops-console;
  # 只对运维网段开放
  allow 10.20.0.0/24;
  deny all;
  add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' https://cp.kwl.example.com; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'" always;
  add_header X-Content-Type-Options nosniff always;
  add_header Referrer-Policy no-referrer always;
  add_header Cache-Control "no-store" always;
  location / { try_files $uri =404; }
}
```

使用：

1. 运营人员在运维网段内用 **Chrome / Edge 137 以上**（Firefox 129+、Safari 17+ 也可）打开 `https://ops.kwl.example.com`；
2. 填运营编号（`op_0001`）、密钥编号（`k1`），选自己的私钥文件 `~/.kwl-ops/op_0001.k1.key.pem`，有口令就填口令；
3. 页面能做的事（每项都要名册里有对应权限，没有就提示“没有这项权限”）：

| 页面操作 | 权限 | 说明 |
|---|---|---|
| 租户列表、本月用量、池余额、状态 | `tenant.read` | 顶部汇总全平台本月用量、在用席位、暂停的租户 |
| 租户详情：12 个月用量、本月按席位明细、导出 CSV | `tenant.read` | 席位编号是假名，不含成员姓名 |
| 开通律所 | `tenant.manage`（附带点数另需 `quota.manage`） | |
| 加量（注入点数） | `quota.manage` | |
| 代设月度上限 | `quota.cap` | **只能调低**；调高或取消须律所管理员在客户端操作 |
| 续订 / 终止订阅 | `tenant.manage` / `tenant.terminate` | |
| 发创始开通码 / 作废 | `activation.issue` | 开通码只显示一次 |
| 收回席位 / 吊销设备 | `device.revoke` | 紧急情况用；成员编号、设备编号由律所提供 |

每次操作都先在控制面写“已请求”访问审计（`/var/lib/kwl/control-plane/ops/access.jsonl`），写操作另进律所可见的运营审计流水，执行者记为运营编号。

## 7. 生成 release.json 并构建 Windows 安装包

### 7.1 生成 release.json（exe 与云端的对接点）

在能连到云端各服务的电脑上（证书已经装好），写一份说明文件 `release-spec.json`：

```json
{
  "control_plane_base": "https://cp.kwl.example.com",
  "gateway_base": "https://gw.kwl.example.com/v1",
  "search_base": "https://search.kwl.example.com/v1/search",
  "control_plane_backup_pins": ["/secure/backup/cp.backup.pub.pem"],
  "gateway_backup_pins": ["/secure/backup/gw.backup.pub.pem"],
  "search_backup_pins": ["/secure/backup/search.backup.pub.pem"],
  "cp_public_keys_file": "/secure/kwl-prod/public/cp-public-keys.json",
  "seat_public_keys_file": "/secure/kwl-prod/public/seat-public-keys.json",
  "test_build": true
}
```

```bash
node scripts/make-release-config.mjs --spec release-spec.json --out apps/desktop/electron/release.json
```

脚本会连上每个服务取叶子证书公钥作当前钉住值，加上备份钉住，填好公钥表，再用**客户端同一份校验代码**核对，有问题不写文件。
服务还没上线时可加 `--offline`，在 `pins` 里手工给钉住值。要开自动更新、在线法规库更新，加 `update_base` / `dist_base` 等（见脚本头注释）。

`test_build`：试点测试包写 `true`。**正式发布去掉它**，并且必须同时满足打包门禁：用中软正式代码签名证书（`--sign env`）、
用生产内容签名公钥重新构建内核（`KWL_CONTENT_SIGNING_PUB_FILE`），否则 `package-desktop.mjs` 会拒绝构建。

### 7.2 方式一（推荐）：GitHub Actions 构建测试安装包

1. 把上一步生成的 release.json **整份内容**放进仓库变量（Settings → Secrets and variables → Actions → Variables）`KWL_RELEASE_JSON`
   （里面只有地址、钉住值与公钥，没有秘密；必须带 `"test_build": true`）；
2. Actions → `windows-desktop` → Run workflow（或推送到 main 自动触发）；
3. `package` 任务会：校验 release.json → 构建随包运行时与 NSIS 安装包 → 用一次性测试证书签名 → 在 Windows 上静默安装并冒烟
   （核验随包运行时、DPAPI 主密钥、内核、OCR、闸门与界面）→ 上传 `KimiWorkLegal-Setup-0.2.0.exe` 和冒烟结果；
4. 在运行页的 Artifacts 下载安装包。测试证书不受信任，Windows SmartScreen 会提示“未知发布者”，试点电脑上点“仍要运行”。

## 8. 一家律所从开通到计费的完整流程

| 步骤 | 谁 | 在哪 | 做什么 |
|---|---|---|---|
| 1 | 运营 A（`tenant.manage`、`quota.manage`） | 运营控制台 | “开通律所”：租户编号 `ten_<律所标识>`、名称、版本、席位数、订阅天数、首批点数 |
| 2 | 运营 B（`activation.issue`） | 运营控制台 → 租户详情 | “发创始开通码”：管理员标识 `admin`、有效 72 小时；**开通码只显示一次**，电话或当面告诉律所管理员 |
| 3 | 律所管理员 | exe 首次启动的开通页 | 输入开通码 → 本机生成律所根密钥并登记、领到席位；控制台状态从“待律所开通”变为“正常” |
| 4 | 律所管理员 | exe 设置 → 成员 | 发成员邀请码给律师；可设本所月度消费上限（硬停） |
| 5 | 律师 | exe | 安装、输入邀请码；开始使用。每次模型请求经网关计量并扣点 |
| 6 | 运营 | 运营控制台 | 看本月用量、池余额；点数快用完时“加量”；续订；月底“导出月度用量（CSV）”对账 |

**点数规则**（网关 `services/legal-gateway/src/gateway.ts` 的路由表）：`legal/k3` 每千 token（输入 + 输出）4 点，`legal/k2.6` 2 点，向上取整；
上游超时、上游错误不扣点。每单真实法律任务输入约 50～70 万 token，按 k3 约 2,000～3,000 点。

**额度怎么生效**：控制面维护每个律所的额度池（运营注入的点数）与月度上限。网关不逐请求问控制面，而是每次领一段点数（租约，5 分钟有效），
本地扣减、定期回报按席位的累计用量。所以：

- 控制台上的“本月已用”比实际请求**晚几分钟**；“在途”是已经发给网关、还没用完的点数；
- 池余额用完或达到月度上限 → 网关不再放行，客户端提示“点数用完”或“已达本月上限”，控制台状态显示同样原因；
- 加量立即可领；调低上限对已发出的租约几分钟后生效；
- 网关异常退出、租约到期没收到最终回报的，按已报用量结案并标“待对账”，详情页会提示。

**月度对账**（三方：网关计量日志 ↔ 控制面额度账本 ↔ MaaS 账单）：

```bash
# 在网关服务器上（多个网关实例的计量文件一起给，按请求编号去重）
node scripts/meter-report.mjs /var/lib/kwl/gateway/meter.jsonl --month 2026-11 --by tenant > meter-2026-11.csv
node scripts/meter-report.mjs /var/lib/kwl/gateway/meter.jsonl --month 2026-11 --by seat --out meter-2026-11-seat.csv
```

把 `meter-2026-11.csv` 的每所点数与控制台“导出月度用量（CSV）”的同月用量对照：两者应一致；
有“待对账”租约的租户，以网关计量为准。token 总数再与中软 MaaS 当月账单对照。

## 9. 排障

| 现象 | 原因与处理 |
|---|---|
| 控制台登录提示“连不上控制面” | ① 控制面 `ops.console_origins` 没写本页来源（要完全一致，含 https、不带末尾斜杠）；② 证书不受信任——先在浏览器里直接打开控制面地址确认；③ CSP 的 connect-src 没写控制面地址 |
| 登录提示“没有这条接口” | 你的电脑不在 `ops.allow_cidrs` 网段内（或经过了做源地址转换的代理） |
| “运营凭据无效” | 运营编号、密钥编号、私钥文件三者与名册不一致，或已被吊销；用 `ops-cli roster show` 核对 |
| “本机时间与服务器相差超过 5 分钟” | 校准运营电脑时间 |
| “运营名册暂不可用” | 名册过期（31 天）、被换成旧版本或签名不符：安全管理员 `roster renew` 后重新放上去 |
| exe 里开通失败 / 一直连不上云端 | release.json 地址或钉住值不对（证书换了密钥）：用 `make-release-config.mjs` 重新生成并重新打包；或网络出口有 TLS 解密代理（律所防火墙），须把这几个域名设为不解密 |
| 律师提示“点数用完” | 控制台给该所“加量”；或律所管理员调高月度上限 |
| 网关 `/readyz` 503 `feed_stale` | 网关 2 分钟没取到控制面吊销集：检查网关到控制面的网络与 `service_secret` 是否一致 |
| 模型请求 504 `upstream_timeout` | MaaS 上游超过 120 秒没响应（网关已中止，不扣点）；持续出现联系 MaaS 查配额与限流 |

## 10. 现状与限制（如实）

- **Windows 安装包**：本仓库的打包链路完整（`package-desktop.mjs` + `windows-desktop` 工作流），但本机（Apple 芯片）只能产出
  `win-unpacked` 未打包目录；`.exe` 安装包须在 Windows CI 或 Windows 电脑上构建。第 37 批没有在 Windows 真机上跑过。
- **运营控制台**：本机用回环测试形态（签名服务 + 控制面 + 控制台）在浏览器里走通了登录、列表、详情、加量、设上限、权限拒绝；
  没有在 HTTPS 正式环境与 Windows 浏览器上验证。双人复核、双因素、堡垒机仍未做（偏离 D-106）；硬件令牌（USBKey）浏览器侧不支持。
- **计费**：控制面只管“点数”（额度池、上限、按席位用量）；没有价格表、订单、发票与收款，`point_price_cny` 只是页面上的参考换算。
  按席位收费的订阅费用由订阅天数与席位数体现，账单在中软财务系统里出。
- 没有容器镜像与 IaC；签名私钥仍是挂载文件（KMS 解封待云选型）；服务间凭据仍是共享密钥（G1 改 mTLS）。
