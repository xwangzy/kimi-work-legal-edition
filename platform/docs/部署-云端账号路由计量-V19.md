# 云端部署与运维手册（第 44 批：自有账号、API 路由、按真实用量计费、运营控制台重做）

> 适用代码：分支 `v19-b44`。本手册取代《部署-云端控制台与桌面端对接.md》里“额度台”“Kimi 账号”“点数”相关段落；
> 签名服务的签名账外送、PostgreSQL 一主多备、对象存储等未变部分仍以《部署-云端生产入口.md》为准，这里只给落地必需的部分。
> 每条命令都在本机全链路演练里实际跑过（`scripts/stack-local.mjs` 与第 10 节的 TLS 演练）；没跑过的写明“未验证”。

## 0. 架构与对接线

```
律师电脑（Windows exe）                                 中软云（公网 443，TLS 终止在服务进程）                  上游
┌──────────────────────┐   ① 账号 / 设备 / 席位令牌   ┌──────────────────┐  mTLS  ┌────────────┐
│ 渲染层 ─ 内核 ─ 闸门 ──┼──────────────────────────→│ 控制面 control-plane ├──────→│ 签名服务（内网） │
│ （本机执行法律任务）    │                              │ 账号·会话·路由登记·  │        └────────────┘
│                      │   ② 模型请求（席位令牌）      │ 用量账本·额度·计费     │
│                      ├──────────────────────────→│ 网关 gateway ────────┼─ 订阅（吊销、暂停设备、路由）
└──────────────────────┘                              │ 动态路由·切换·计量    ├──────────────→ 中软 MaaS（new-api）
运营人员浏览器（运维网段） ③ 运营签名请求（CORS）  ───→│ 控制面 /v1/ops/*     │
        ↑ 静态页 ④ ops.kwl…（nginx，只对运维网段）      └──────────────────┘
```

| 对接线 | 谁连谁 | 鉴权 | 配置位置 |
|---|---|---|---|
| ① 账号与设备 | exe 闸门 → 控制面 `https://cp…` | 设备签名 + 账号会话（`x-kwl-session`）；注册登录本身只靠密码 | exe 内置 `release.json` 的 `control_plane_base` 与钉住值 |
| ② 模型调用 | exe 闸门 → 网关 `https://gw…/v1` | 席位令牌（控制面签发；账号停用 / 退出登录 15 秒内经订阅暂停） | `release.json` 的 `gateway_base`；网关 → MaaS 的路由在控制台配 |
| ③ 运营 | 浏览器 → 控制面 `/v1/ops/*` | 运营人员私钥在浏览器内签名；来源须在 `ops.allow_cidrs`、页面来源须在 `ops.console_origins` | 控制面配置 `ops` 段；控制台 `config.json` |
| ④ 控制台静态页 | 浏览器 → nginx | nginx 只放行运维网段 | `/srv/kwl-ops-console/` |

## 1. 服务器与网络

| 角色 | 规格（试点 ≤ 20 家律所、≤ 200 名律师） | 端口 | 对外 |
|---|---|---|---|
| 签名服务 cp-signer | 2 vCPU / 2 GB | 8443（mTLS） | **只许控制面访问** |
| 控制面 control-plane | 2 vCPU / 4 GB / 40 GB SSD | 443 | 律师与运维网段 |
| 网关 gateway | 4 vCPU / 8 GB | 443 | 律师；出网到 MaaS |
| 检索 search（法律检索，可与网关同机另一端口） | 2 vCPU / 4 GB | 443 | 律师；出网到检索上游 |
| 控制台静态页（nginx） | 可与控制面同机 | 443（另一个域名） | **只对运维网段** |

- 系统 Ubuntu 24.04 LTS；Node.js **24.15 以上**（建议与 CI 同为 26.8.1）；`chrony` 时间同步必须开（运营签名允许 5 分钟偏差，签名服务只允许 5 秒）。
- 域名：`cp.kwl.example.com`、`gw.kwl.example.com`、`search.kwl.example.com`、`ops.kwl.example.com`（签名服务用内网名 `cp-signer.internal`）。
- **TLS 终止在服务进程**，前面只能是四层负载均衡（直通、保留源地址）；不要放 WAF / CDN / 七层代理（客户端钉住服务证书公钥，限速与运营网段按源地址判断）。nginx 只用来托管控制台静态页。
- 防火墙（ufw 示例）：

```bash
# 控制面与网关服务器
sudo ufw default deny incoming && sudo ufw allow 22/tcp from 10.20.0.0/24 && sudo ufw allow 443/tcp && sudo ufw enable
# 签名服务服务器：只许控制面所在地址
sudo ufw default deny incoming && sudo ufw allow from <控制面内网地址> to any port 8443 proto tcp && sudo ufw enable
```

## 4. TLS 证书

每个对外域名一张证书（公共 CA 或中软自有 CA），另为每个域名预先生成一对**备用密钥**用于“备份钉住”（续期时只能复用当前密钥或换成备用密钥，否则已安装的 exe 连不上）：

```bash
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out /secure/backup/cp.backup.key
openssl pkey -in /secure/backup/cp.backup.key -pubout -out /secure/backup/cp.backup.pub.pem
# gw 同样做一份
```

签名服务用内部 CA：服务端证书（SAN `DNS:cp-signer.internal`）+ 给控制面的客户端证书（SAN `URI:spiffe://kwl/prod/cp-api`）。

```bash
# 内部 CA（离线保管私钥）
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout internal-ca.key -out internal-ca.crt -days 3650 -subj "/CN=kwl internal CA"
# 签名服务端证书
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout signer.key -out signer.csr -subj "/CN=cp-signer.internal"
openssl x509 -req -in signer.csr -CA internal-ca.crt -CAkey internal-ca.key -CAcreateserial -days 825 -out signer.crt -extfile <(printf "subjectAltName=DNS:cp-signer.internal")
# 控制面的客户端证书
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout cp-api-client.key -out cp-api-client.csr -subj "/CN=cp-api"
openssl x509 -req -in cp-api-client.csr -CA internal-ca.crt -CAkey internal-ca.key -CAcreateserial -days 825 -out cp-api-client.crt -extfile <(printf "subjectAltName=URI:spiffe://kwl/prod/cp-api\nextendedKeyUsage=clientAuth")
```

## 5. 运营名册（安全管理员 + 每位运营人员）

```bash
# 安全管理员（离线电脑）：名册签名密钥，私钥永不上服务器
node scripts/ops-cli.mjs roster-keygen --kid sec-1 --out /secure/offline --keys-file ops-roster-keys.json
node scripts/ops-cli.mjs roster init --deployment prod --sign-key /secure/offline/sec-1.key.pem --sign-kid sec-1 --out ops-roster.json
# 每位运营人员（本人电脑）：生成自己的密钥，把 .pub.pem 与屏幕上的指纹交给安全管理员

node scripts/ops-cli.mjs roster add --roster ops-roster.json --id op_0001 \
  --perms tenant.read,tenant.manage,tenant.terminate,quota.manage,quota.cap,device.revoke,account.manage,route.manage,plan.manage \

node scripts/ops-cli.mjs roster add --roster ops-roster.json --id op_0002 --perms tenant.read,activation.issue \
```

### 6.1 签名服务 `/etc/kwl/cp-signer.json`

```json
{
  "role": "cp-signer",
  "environment": "prod",
  "init_ledger": true,
  "listen": { "host": "0.0.0.0", "port": 8443 },
  "tls": { "cert_file": "/run/secrets/signer.crt", "key_file": "/run/secrets/signer.key", "client_ca_file": "/etc/kwl/internal-ca.crt" },
  "allowed_callers": ["spiffe://kwl/prod/cp-api"],
  "data_dir": "/var/lib/kwl",
  "keys": "（整段替换为 public/signer-keys.json 的内容）",
  "ledger_archive": { "kind": "s3", "endpoint": "https://obs.cn-north-4.myhuaweicloud.com", "bucket": "kwl-prod-signer-ledger", "region": "cn-north-4", "access_key_id_file": "/run/secrets/ledger-ak", "secret_access_key_file": "/run/secrets/ledger-sk", "kms_key_id": "<KMS 编号>" }
}
```

`init_ledger: true` 只在首次部署；之后删掉。`environment: "prod"` 必须配 `ledger_archive`（单独的、开版本控制与对象锁的桶）；试点可先用 `"stg"`。

### 6.2 控制面 `/etc/kwl/control-plane.json`

```json
{
  "role": "control-plane",
  "listen": { "host": "0.0.0.0", "port": 443 },
  "tls": { "cert_file": "/run/secrets/cp.crt", "key_file": "/run/secrets/cp.key" },
  "service_secret_file": "/run/secrets/service-secret",
  "data_dir": "/var/lib/kwl",
  "signer": { "url": "https://cp-signer.internal:8443", "client_cert_file": "/run/secrets/cp-api-client.crt", "client_key_file": "/run/secrets/cp-api-client.key", "ca_file": "/etc/kwl/internal-ca.crt", "servername": "cp-signer.internal" },
  "state_key_file": "/run/secrets/cp-state.key",
  "code_pepper_file": "/run/secrets/cp-code-pepper.key",
  "ops": {
    "deployment": "prod",
    "roster_file": "/etc/kwl/ops-roster.json",
    "roster_keys_file": "/etc/kwl/ops-roster-keys.json",
    "allow_cidrs": ["10.20.0.0/24"],
    "console_origins": ["https://ops.kwl.example.com"]
  },
  "billing": {
    "plans": [
      { "id": "standard", "label": "标准", "quota_unit": "tokens", "seat_quota": 50000000, "period": "month", "seat_price_cny": null, "device_limit": 2, "alert_thresholds": [80, 100] },
      { "id": "trial", "label": "试用", "quota_unit": "tokens", "seat_quota": 20000000, "period": "month", "burst": { "hours": 5, "pct": 50 }, "device_limit": 1 }
    ],
    "default_plan": "standard",
    "registration": { "registration": "open", "trial_plan": "trial", "trial_days": 14, "trial_seats": 1, "default_device_limit": 2 }
  },
  "routing": {
    "bootstrap": { "provider": { "id": "maas", "label": "中软 MaaS", "vendor": "csi-maas", "base_url": "https://maas.jointpilot.com/v1" }, "models": { "legal/k3": "kimi-k3.1-pro", "legal/k2.6": "kimi-k3.1-pro" } },
    "public_key_file": "/etc/kwl/routing-public.txt"
  }
}
```

- `billing` 与 `routing.bootstrap` **只在首次启动导入**状态；之后一律在控制台改（改配置文件不再生效，避免两处口径）。
- `quota_unit`：`tokens`（上游 usage 原样，输入 + 输出）或 `cny`（价目表售价 × 实际 usage，区分未缓存输入、缓存输入、输出；用 cny 前须先在控制台定价）。不再有“点数”。
- 定额度时按实测估：一单常规任务约 24 次模型调用、约 190 万 token（输入九成多命中缓存；2026-11-12 的 57 单中位、11-14 验收一单 187 万）。tokens 套餐里缓存命中的输入也按 1 个 token 计，所以 5,000 万 token ≈ 25 单；金额套餐按价目区分缓存价，更贴近真实成本。试用套餐的 5 小时窗口不要低于 2 单的量（约 400 万 token），否则一单做不完就被拦（11-14 验收的教训）。
- 状态（账号、会话、路由、套餐、告警）在 `<data_dir>/control-plane/state.1|2`（AES-GCM 封装，两代交替）；逐请求用量账本在 `<data_dir>/control-plane/usage/YYYY-MM.jsonl`（只追加、每批 fsync）；运营审计 `audit.jsonl`、运营访问记录 `ops/access.jsonl`。
- 需要一主多备时按《部署-云端生产入口.md》加 `state_store`（PostgreSQL）与 `nonce_store`（Redis）。**注意**：用量账本目前是控制面本机文件，一主多备切换时新主看不到旧主的账本文件——试点用单实例；多实例前要把 `usage/` 放到共享存储或等账本换成数据库表（§12 遗留）。

### 6.3 网关 `/etc/kwl/gateway.json`

```json
{
  "role": "gateway",
  "listen": { "host": "0.0.0.0", "port": 443 },
  "tls": { "cert_file": "/run/secrets/gw.crt", "key_file": "/run/secrets/gw.key" },
  "service_secret_file": "/run/secrets/service-secret",
  "control_plane": { "url": "https://cp.kwl.example.com", "keys_file": "/etc/kwl/cp-public-keys.json" },
  "seat_keys_file": "/etc/kwl/seat-public-keys.json",
  "data_dir": "/var/lib/kwl",
  "upstream": { "base_url": "https://maas.jointpilot.com/v1", "api_key_file": "/run/secrets/maas.key" },
  "routing": { "feed": true, "key_file": "/run/secrets/routing-key.pem", "allow_hosts": ["maas.jointpilot.com"] },
  "tenant_concurrency": 4,
  "queue_timeout_ms": 30000,
  "upstream_header_timeout_ms": 120000,
  "upstream_idle_timeout_ms": 120000
}
```

- `routing.allow_hosts`：**本机上游主机白名单（必填）**。控制台里配的上游地址不在名单内一律不用（状态显示“不在白名单”）——控制面被攻破也不能把律所请求改投到名单外的主机。新增上游前先改这里并重启网关。
- `upstream` 段：从未取到路由订阅时的兜底，以及“密钥用服务器本机文件”（控制台里上游的“使用网关本机密钥”）那把密钥。
- 计量预写日志 `<data_dir>/gateway/meter.jsonl` + 发件箱检查点 `meter.ack`：网关崩溃或重启后自动重放未确认的回报（控制面按请求编号去重，不会重复计费）。SIGTERM 时做最终回报（至多 5 秒）。
- 多个网关实例：每个实例的 `holder` 自动为 `gw-<主机名>-<进程>-<随机>`，各自领租约；租户并发闸按实例计（4 × 实例数）。

### 6.3a 检索 `/etc/kwl/search.json`

```json
{
  "role": "search",
  "listen": { "host": "0.0.0.0", "port": 443 },
  "tls": { "cert_file": "/run/secrets/search.crt", "key_file": "/run/secrets/search.key" },
  "service_secret_file": "/run/secrets/service-secret",
  "control_plane": { "url": "https://cp.kwl.example.com", "keys_file": "/etc/kwl/cp-public-keys.json" },
  "seat_keys_file": "/etc/kwl/seat-public-keys.json",
  "data_dir": "/var/lib/kwl",
  "upstream": { "base_url": "<检索上游，提供 /tools/search 与 /tools/search_pro>", "api_key_file": "/run/secrets/search.key.txt" }
}
```

- 检索服务接受 `POST /search` 与 `POST /v1/search`（第 44 批起两种都收；release.json 写 `https://search.kwl.example.com/v1/search`）。
- **本批演练实测：中软 MaaS 的 `/v1/tools/search` 返回失败（检索服务回 502）**——MaaS 是否提供联网检索、用哪个地址，上线前须与 MaaS 确认；不提供时检索上游要另配（例如月之暗面官方 `https://api.moonshot.cn/v1`），律师端“法律检索”在此之前不可用（本机法规库不受影响）。
- 控制面、网关、检索若用内部 CA 签的证书：在各服务的 systemd 单元加 `Environment=NODE_EXTRA_CA_CERTS=/etc/kwl/internal-ca.crt`（网关、检索经 HTTPS 订阅控制面时要认这个 CA）；律师端只认公共 CA 加钉住，**对外的三个域名请用公共 CA 证书**。

## 8. 上线后的初始化

### 8.1 注册策略与默认额度（控制台 → 套餐与额度）

1. **注册设置**：`open`（律师可在 exe 里自助注册，自动建个人律所、用试用套餐）/ `code`（只能凭开通码或邀请码注册）/ `closed`。
2. **套餐**：每个套餐的单位（tokens / 元）、每席位每期额度、周期（月 / 周）、5 小时频率窗口（可选）、提醒阈值、每账号设备数、席位价。旧版迁移来的套餐标“由旧版计量额度换算，待商务确认”，上线前请商务确认。
3. **价目表**（模型与路由 → 价目表）：每个模型别名的售价与成本价（元 / 百万 token，三档：未缓存输入、缓存输入、输出）。未定价时 tokens 套餐照常可用，账单的用量价值与毛利显示“未定价”；cny 套餐在定价前领不到额度（503 price_unconfigured）。

### 8.2 接入中软 MaaS（控制台 → 模型与路由）

- 首次启动已从 `routing.bootstrap` 导入上游 `maas`（使用网关本机密钥）与两个内置别名：`legal/k3`（主任务）、`legal/k2.6`（子任务）。**别名不能改名、不能删除**（exe 里写死了），只能改它指向哪个上游、哪个型号。
- 改用控制台录入密钥：上游 → 编辑 → 输入密钥。密钥在浏览器里用网关路由公钥加密后才提交，控制面只存密文与尾号（“…ab12”），网关解封后只放内存。
- 加备用线路：新增上游（同一厂商，例如 MaaS 第二个入口）→ 在 `legal/k3` 的目标里加一行、优先级 2。网关只在“还没给客户端写出任何字节”之前切换（连接失败、5xx、429、首包超时），跨厂商切换要显式勾选并同步更新对律所的数据去向说明。
- 切型号（例如高速档）：把 `legal/k3` 的目标型号改为 `kimi-k3.1-pro-highspeed` → 保存；网关 15 秒内生效，不用重打 exe。
- 验证：上游行的“测试连接”（网关下一轮立即探测 `GET {base}/models`），健康列显示正常、延迟；再到“用量 → 逐请求明细”看新请求的“上游 / 上游型号 / 上游请求编号”。

### 8.3 开通律所与账号

- 自助注册（`registration=open`）：律师在 exe 里注册即可，无须运营操作；控制台“客户”里出现“个人律所（自助）”。
- 运营开通：客户 → 开通律所（套餐、席位、订阅天数）→ 另一位有 `activation.issue` 的运营发开通码 → 负责人在 exe“注册 → 我有开通码”。或在“账号 → 代建账号”为负责人建账号，把一次性设置码交给本人（设置密码后登录）。
- 律所成员：负责人在 exe“设置 → 账号与团队 → 邀请成员”发 36 位邀请码，成员凭码注册；同一账号换电脑：在新电脑登录，由已登录的管理员电脑批准（核对 12 位数字）。
- 找回密码：没有配邮件通道时，律师点“忘记密码”会提示找管理员；运营在“账号 → 发重置码”（30 分钟有效，只显示一次）。

### 11.1 升级（第 43 批及以前 → 第 44 批）

1. 先升级控制面，再升级网关（网关新协议依赖控制面的 `/v1/feed/routing` 与租约 v2；顺序反了网关会 503）。停机窗口约 1 分钟。
2. 控制面首次启动：状态自动迁移——旧“内部单位”账本的本期已用冻结为比例（`legacy_used_ratio`，界面注明“含旧计量口径”）、历史月份只留比例、Kimi 账号绑定丢弃；套餐目录按旧配置导入（旧 `seat_monthly_units` 翻译为 token 额度，标待商务确认）；之前开通的律所**不要求账号登录**（控制台“客户 → 套餐与额度 → 账号闸”可打开）。
3. 网关配置加 `routing` 段（`allow_hosts` 必填、`key_file`）；删掉 `Environment=KWL_UPSTREAM_K3`（型号改在控制台配；不删也只作兜底）。
4. 删掉控制面配置里的 `kimi_account`（留着拒绝启动）。
5. 发布新版 exe（含登录页）；旧版 exe 仍能用到席位令牌到期（≤ 96 小时），对 `accounts_required` 的律所旧版 exe 续不了期。
6. 把升级前的真实用量补进账本（旧预写日志里有上游当时给的真实 token 数；按请求编号去重，可重复跑）：

```bash
# 先看每家律所有多少行
node scripts/usage-backfill.mjs /backup/gw1/meter.jsonl /backup/gw2/meter.jsonl --month 2026-11 --dry-run
# 补录；交齐全部网关实例的日志后加 --clear-legacy，清掉“旧口径冻结比例”，本期改按补录的真实用量算
node scripts/usage-backfill.mjs /backup/gw1/meter.jsonl /backup/gw2/meter.jsonl --month 2026-11 --clear-legacy \
  --url https://cp.kwl.example.com --deployment prod --id op_0001 --kid k1 --key ~/.kwl-ops/op_0001.k1.key.pem
```

   需要 `plan.manage` 权限；金额按补录时控制台的价目表算，账本行标“补录”。

### 11.3 排障

| 现象 | 查哪里 | 常见原因 |
|---|---|---|
| exe“连不上中软服务” | exe 设备页的去向记录；控制面 `obs/` 访问日志 | 证书钉住不符（续期换了密钥）、防火墙、时钟偏差 > 5 分钟 |
| “登录已失效” | 控制台账号详情的会话列表 | 退出登录、改了密码、运营强制下线、空闲 30 天 |
| AI 报“额度已用完 / 频率窗口已满 / 个人额度已用完” | 控制台客户 → 用量；账号 → 个人上限 | 本期额度、5 小时窗口、个人上限 |
| 网关 503 `routing_unavailable` / `upstream_unavailable` | 控制台模型与路由的健康列；网关日志 | 网关取不到路由订阅（service-secret 不一致）、上游不在白名单、密钥解不开（控制台公钥编号与网关私钥不配） |
| 网关 503 `price_unconfigured` | 价目表 | 金额套餐的模型没定价 |
| 控制台“运营名册暂不可用” | `/etc/kwl/ops-roster.json` 是否过期 | 名册超过 31 天未重签 |
| 用量不更新 | 网关 `kwl_gw_meter_pending`、`meter.ack` | 网关连不上控制面（恢复后自动重放） |

## 12. 现状与限制（如实）

- 找回密码的邮件 / 短信通道未接（代码留了邮件发送接口，需要 SMTP 服务账号）；目前靠运营发重置码。
- 用量账本是控制面本机文件：单实例可靠（每批 fsync、启动重建去重集）；多实例前要换成数据库表或共享存储。
- 升级前的历史用量：有旧网关预写日志的按真实 token 补录（`usage-backfill.mjs`）；没有日志的只保留比例（不按固定比例换算成 token 或金额）。
- Windows 真机未验证（本批在 macOS 上用开发桥 + 浏览器界面验证；安装包走 GitHub Actions）。
- 与 MaaS 后台的逐条对账需要 MaaS 侧导出（账本已记上游请求编号）；本批只核对了网关预写日志与控制面账本一致。
