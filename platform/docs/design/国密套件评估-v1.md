## 1. 实测：三个运行时各能做什么

`node scripts/gm-probe.mjs`（随包运行时与云端服务用的 Node）与 `ELECTRON_RUN_AS_NODE=1 npx electron scripts/gm-probe.mjs`（Electron 主进程与内核所在的 utilityProcess）：

| 能力 | Node 26.8.1（OpenSSL 3.5.7）：随包运行时的出站闸门、Agent 宿主；云端全部服务 | Electron 44.5.1（BoringSSL）：主进程、内核 |
|---|---|---|
| SM3 | 能（GB/T 32905 示例“abc”一致） | 不能 |
| SM4-CBC / CTR / ECB / CFB / OFB | 能 | 不能 |
| SM4-GCM | **不能**（`Unknown cipher`） | 不能 |
| SM2 签名（`sign("sm3", …)`） | 能（本机自签自验；与其他实现互通、区分标识 ID 的缺省值未核） | 不能（`Invalid EC curve name`） |
| TLS 国密套件（TLCP / RFC 8998） | **没有** | 没有 |

由此解决了云端持久化与 KMS 设计 §5.4 里两项“待核实”：随包 Node **不支持 TLCP**；Node 26 所带 OpenSSL 的 **SM4-GCM 不可用**（PoC-3 的结论：字段加密走 AES-256-GCM，或改用 SM4-CTR + HMAC-SM3 自组 AEAD）。

## 2. 各环节现状与可行路径

| 环节 | 现在用什么 | 国密可行性 | 路径与工作量 |
|---|---|---|---|
| 律师电脑上的数据库（账本） | **ChaCha20-Poly1305**（SQLite3MultipleCiphers 缺省 `chacha20`；本次实测更正：代码注释与驻留面原写“SQLCipher v4”不准确，现已在 `db.ts` 显式钉住并有用例） | 内核在 BoringSSL 里，没有 SM4；驱动的密码算法里也没有 SM4 | 不改。若测评要求“重要数据存储机密性用国密”，只能换存储加密实现（自研 SM4 页加密或换国密版 SQLCipher 分支），评估 ≥ 6 人周，且要放到随包 Node 进程里做——风险高，建议争取按“使用经认证密码产品的密钥由 DPAPI 保护”论证 |
| 设备签名、律所根、管理员签名 | Ed25519（设备签名另可 P-256 低 S，keys 包分派） | 内核侧不能做 SM2；随包 Node 能做 | G2 算法敏捷：设备密钥加 SM2 类型、签名在随包 Node 子进程里做，约 4 人周（与 TPM 设计的签名者接口一起） |
| 控制面信封、席位令牌 | Ed25519（签名服务 cp-signer，A-8） | 签名服务在 Node 上，SM2 能签；客户端内核（BoringSSL）验不了 SM2 | 客户端验签也要挪到随包 Node（或引入纯 JS 的 SM2 验签），与上一项同一个算法敏捷工程；新 kid 带算法标识（设计 §4.5） |
| 云端字段加密（租户盐等） | AES-256-GCM（状态整份封装，A-7） | SM4-GCM 不可用；SM4-CTR + HMAC-SM3 可组 | P-7：先 AES-256-GCM（DEK 由 KMS 的 SM4 主密钥包裹），`alg` 字段记录算法以便迁移；改 SM4 约 1 人周（含互通测试） |
| 完整性 MAC、开通码 HMAC | HMAC-SHA256 | HMAC-SM3 在 Node 上可用 | 约 0.5 人周（双算法过渡：旧码按旧算法核对） |
| 传输（律师电脑 ↔ 中软云端） | TLS 1.2/1.3 标准套件，客户端钉住 SPKI | 双方运行时都没有 TLCP | 不做。若测评要求，只能在云端入口前加经认证的国密网关、客户端换国密 TLS 库（随包 Node 换 Tongsuo 等），≥ 8 人周且影响钉住设计 |
| 审计检查点、签名账 | SHA-256 哈希链（cp-signer 签名账、运营审计流水） | SM3 在 Node 上可用 | 约 0.5 人周（链头标明算法） |

## 3. 结论与建议

1. **云端可以“能用即用”**：签名服务、字段加密、HMAC、哈希链都在 Node（OpenSSL 3.5）上，SM2/SM3/SM4-CBC/CTR 可用；SM4-GCM 不可用，用 SM4-CTR + HMAC-SM3 或继续 AES-256-GCM（主密钥在 KMS 用 SM4）。
2. **客户端是瓶颈**：Electron 的 BoringSSL 没有任何国密算法，内核、数据库加密、设备签名都在里面。客户端国密化 = 把签名与验签挪到随包 Node 子进程（G2 算法敏捷，约 4 人周），数据库加密国密化代价更高（≥ 6 人周），传输层国密（TLCP）现阶段不可行。
3. **建议口径**：首发保持现状（标准算法 + 云端 KMS 用 SM4 主密钥），向测评机构提交本表与 §5.4 的论证；书面意见要求客户端国密时，按“签名验签 → 云端字段加密与 HMAC → 数据库加密 → 传输”的顺序立项，G2 前完成前两项。
4. **待拍板**（并入设计 §9.2）：P-2 Ed25519 是否被接受；P-7 字段加密用 AES-256-GCM 还是 SM4-CTR + HMAC-SM3；是否把 SM2 设备密钥列入 G2。
