# 开通与成员入组设计 v1（S2 身份与登录的首期：开通码 + 邀请码 + 管理员批准）

2026-10-19 · 状态：实施中（v9.3 第 13 批）· 依据：v9.2 §5.1 S2、§4.6 C6；`identity.ts` 文件头“生产：本机生成设备密钥对，管理员签发设备证书”；`devices.ts` 文件头 G0 声明

## 1. 为什么现在做

评审（2026-10-19）核实：

1. **安装包形态没有身份来源**：`kernelChildEnv` 的安装包白名单不含 `ZR_FIRM_SLUG`/`ZR_USER_SLUG`，`loadConfig` 缺省为 `demo-firm`/`demo-lawyer`——每一台装好的电脑都会把自己当成“ten_demo-firm 的 demo-lawyer”。
2. **每台设备首跑自己生成律所根**（`ensureFirmIdentity`）。同一律所第二位律师装好后生成另一把根，向控制面登记即 `root_already_enrolled`；目前多人律所只能手工拷贝 `firm-root.json`——这既不可交付，也把根私钥扩散到每台成员机。
3. **控制面 `/v1/enroll` 先到先得**：知道租户编号的任何人都能抢先登记根公钥（租户抢注）。
4. 律师侧没有任何“激活/登录”界面；验收要求“安装 → 启动 → **登录** → 运行 → 更新 → 卸载”。

## 2. 目标与非目标

目标（首期，可在本机与 CI 全链路验证）：

- 运营给律所开通后得到一个**开通码**，交给律所管理员；管理员在新装的客户端输入开通码 → 本机成为该律所的创始设备（持律所根，沿用 G0 现状，D-41 残余不变）。
- 管理员在“设置 → 管理 → 成员”里**邀请成员**（姓名、角色）→ 得到**邀请码**，经微信/邮件交给同事。
- 同事在新装的客户端输入邀请码 → 本机生成设备密钥、向控制面提交**入组申请**（只含公钥）→ 界面显示“等待管理员批准”与两边都能核对的**核对码** → 管理员在“管理 → 成员”看到申请、核对后批准 → 管理员本机用律所根签发设备证书并经控制面送达 → 同事的客户端收到证书、核验、登记、取得席位，进入正常使用。
- 控制面**不能**自己往律所里加人：设备证书只能由律所根签发（沿用 v9 信任模型：控制面只能收紧）。
- 开通码、邀请码**一次性、有时限、限次尝试**，云端只存 HMAC 摘要；激活后本机身份写入数据根下的 `activation.json`（只有编号与显示名，不含秘密），主进程据此启动内核。

非目标（G1 及以后，本文只留接口）：手机号/扫码登录与管理员双因素（S2 后半）、OIDC/SAML/SCIM（G2）、根私钥离线 2-of-3 分持与 TPM（C6，见 `TPM密钥与根私钥离线分持设计-v1.md`）、管理员转移与多管理员门限下的入组批准、成员退出时的设备回收流程（沿用现有吊销）。

## 3. 角色与数据

| 对象 | 存在哪里 | 内容 | 秘密？ |
|---|---|---|---|
| 开通码 / 邀请码 | 交付给人（一次性） | 20 位 Crockford Base32（100 bit），分 5 组显示，如 `K7QM-9XWD-2RTF-H4PN-8C3E` | 是（只出现一次） |
| 码记录 `activations` | 控制面租户 | `code_mac`（HMAC-SHA256(服务端胡椒, 码)）、类型 founder/member、成员编号与显示名（只用于兑换时回显：提交入组申请、消费、作废或过期即清空）、角色、到期、入组申请次数、状态、认领凭据摘要；结束 31 天后连同入组申请记录删除（复核 A-06/A-16） | 否（只有 MAC） |
| 认领凭据 `claim_secret` | 激活设备本机 `keys/activation-claim.json`（按 dbKey 封装）；控制面只存其 sha256 | 32 字节随机；创始设备登记根公钥、成员设备提交与取回入组申请时出示 | 是 |
| `activation.json` | 本机数据根（`%LOCALAPPDATA%\KimiWorkLegal\activation.json`） | 律所标识、成员标识、租户编号、显示名、角色、类型、激活时刻 | 否 |
| 入组申请 `join_requests` | 控制面租户 | 申请编号、成员编号、设备编号、签名/加密公钥、核对码、状态、证书（批准后） | 否 |

**核对码**：`sha256("kwl-join/1" ‖ tid ‖ device_id ‖ sign_pub ‖ enc_pub)` 取前 40 bit 显示为 4 组 3 位十进制数字（如 `482 019 337 650`）。成员机与管理员机各自独立计算并显示；电话或当面念一遍一致才批准——防控制面把申请换成攻击者自己的公钥。**律所核对码**（根公钥指纹）在成员机取回证书后显示，同样可与管理员核对（首次信任，残余如实登记）。

## 4. 流程

### 4.1 开通（创始设备）

1. 运营：`ops.createTenant(...)` 时带 `activationRequired: true`（生产缺省），再 `ops.issueActivationCode(tid, {kind:"founder", member:{slug,name}})` → 返回码（只此一次）。
2. 客户端首跑（安装包形态没有 `activation.json`）→ 内核以**待激活模式**启动：只开放 `kernel.status`、`onboarding.*`；不连控制面同步、不建业务数据。**如实说明（复核 A-06）**：内核仍按常规启动流程在占位工作区 `pending-activation` 里生成占位账本、占位律所根与设备密钥（按主密钥封装），激活完成按真实身份启动时整个占位目录删除（普通删除）；占位根从不登记、从不签发。
3. 律师输入开通码 → `onboarding.redeem` → 闸门代发 `POST /v1/activation/redeem {code}` → 控制面校验（存在、未用、未过期；码有 100 bit，防猜测靠码长、每源限速与时限，**不做逐码错误计数**——码按 MAC 查找，错误尝试归不到某个码）→ 原子地标记已认领、生成 `claim_secret`（只存 sha256）→ 返回 `{tid, kind, firm:{slug,name}, member:{slug,name,role}, claim_secret}`。
4. 内核把 `claim_secret` 封装写入目标工作区 `keys/activation-claim.json`，写 `activation.json`，广播 `kernel.identity_changed` → 主进程按 `activation.json` 重启内核。
5. 正常启动：创始类型 → `ensureFirmIdentity` 生成律所根（G0 现状）→ 控制面客户端登记根时附 `claim_secret`；控制面对 `activationRequired` 的租户**只接受出示有效创始认领的登记**（关闭租户抢注），成功后认领状态 → `consumed`。

### 4.2 成员入组

1. 管理员（证书角色 `firm_admin`）：`members.invite {name, role}` → 内核分配成员标识（`m-` + 8 位随机）→ 经闸门 `POST /v1/invitations`（设备签名请求，控制面核对签名设备的证书角色是管理员且未吊销）→ 返回邀请码 → 界面显示一次并可复制；邀请记录（不含码）进本机审计。
2. 同事客户端待激活模式 → 输入邀请码 → `onboarding.redeem` 返回成员类型 → 写 `activation.json` 与认领凭据 → 重启。
3. 成员类型正常启动：**不生成律所根**；生成设备密钥（`ensureDevice` 的“无根”分支）→ 设备处于 `pending_join`：`POST /v1/join-requests {tid, member, device_id, sign_pub, enc_pub, claim_secret, proof}`（proof = 设备签名私钥对请求体的签名，证明持有私钥）→ 控制面登记申请（同一认领只能有一个未决申请）。
4. 管理员客户端同步时 `GET /v1/join-requests?status=pending`（设备签名、管理员）→ “管理 → 成员”列出：姓名、角色、申请时刻、核对码 → 批准 → 内核用律所根 `issueDeviceCertificate(...)`（证书里的成员编号与角色取**本机邀请记录**，不取申请自报）→ `POST /v1/join-requests/<id>/approve {cert}` → 控制面核对：证书由本租户根签发、公钥与申请一致、成员与邀请一致 → 申请 `approved`、存证书。拒绝 → `rejected`。
5. 成员客户端轮询 `POST /v1/join-requests/<id>/fetch {claim_secret}` → 取回 `{cert, root_public_key_pem}` → 本机核验证书由该根签发、公钥是自己的 → 写 `firm_identity`（只公钥）、`devices`、`device.json` → 正常 `/v1/devices/register` → 取得席位 → 认领 `consumed`。

### 4.3 失败与恢复

- 码错、过期、已用：只说“开通码不正确或已失效，请向发码人重新获取”（不区分，防枚举）；同一来源每分钟 10 次尝试上限（不做逐码错误计数，见上）；TLS 须终止在本进程或四层负载均衡——置于七层代理之后，按来源限速即失效。
- 成员机在等待期间重启：读 `activation-claim.json` 与本机待决申请编号继续轮询。
- 申请被拒或 7 天未批：界面给“重新申请”（同一邀请码至多提交 3 次申请；成员点“重新输入”时本机请控制面撤回待批准申请）或“换一个邀请码”。
- 激活后要换律所：设置里“退出并清除本机数据”（沿用删除事项的密码学擦除），删除 `activation.json`。

## 5. 安全性质与残余

- 控制面被攻破：可以拒绝服务、可以把申请里的公钥换掉——由核对码挡住（管理员不核对即批准的，按残余登记）；不能凭空签证书。
- 码泄露：一次性 + 时限 + 管理员批准（成员）兜底；创始码泄露在被认领前作废即可（`ops.revokeActivationCode`）。
- 开发与测试形态（未配置控制面）行为不变：仍按 `ZR_FIRM_SLUG`/`ZR_USER_SLUG` 与本机自签根。
- 律所根仍在创始设备（D-41 未变），只是不再扩散到成员机。

## 6. 验收

- 控制面：码一次性、过期、尝试上限、只存 MAC、租户抢注被拒、管理员才能发邀请与批准、证书必须由本租户根签发且与申请公钥一致、状态持久化往返。
- 内核：待激活模式只开放 onboarding 方法；创始激活后重启得到正确租户与成员、根公钥登记成功；成员激活后不生成根、等待批准、取回证书后登记成功并能参与团队事项；核对码两边一致。
- 界面：首跑激活页、等待批准页（含核对码）、管理 → 成员（邀请、待批准、批准/拒绝）。
- 端到端：两台模拟设备（两个数据根）+ 控制面 v0：开通 → 邀请 → 入组 → 批准 → 成员取得席位 → 共享一个事项（复用第 11/12 批中继用例夹具）。
