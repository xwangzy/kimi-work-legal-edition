# 恢复与备份设计 v1（第 14 批 P0；评审 Z4 P0-1 + 主审 X-2）

2026-10-19 初稿 · 2026-10-20 按实现更正（第 14 批第二轮复核 R2A-03）· 状态：**已实施**（第 14 批 + 第二轮复核处置 + 余项；均未在 Windows 真机上验证）· 关联：`开通与成员入组设计-v1.md`、`TPM密钥与根私钥离线分持设计-v1.md`、D-41、D-42、D-61、D-101

> 本稿描述的是**现在代码里的样子**。初稿与实现不一致之处逐条列在第 8 节；恢复包作废与主密钥轮换不在本批，计划见第 7 节（G1）。

## 1. 问题

原有 `recovery.export_device / import_device` 只导出**设备私钥**（口令 scrypt 包裹），并假设原账本还在本机。真实的“电脑坏了 / 被偷了 / 换新电脑”场景里：

1. **数据库主密钥**由主进程经 DPAPI 绑定旧 Windows 账户——新电脑上无论拿到什么备份都打不开账本（SQLCipher）。
2. **数据本身**（账本、块、工作区）没有备份机制；律师自己复制 `%LOCALAPPDATA%` 也没用（同 1）。
3. 创始设备的**律所根与 5 份恢复份额**和数据在同一块硬盘上，硬盘坏了一起丢——律所再也不能加人、也不能做事项的恢复托管解包。
4. 恢复口令由律师自拟（≥ 10 字），实际会被设成弱口令或忘记。
5. 界面没有入口（Z4 P0-1）。

后果：单人律所一次硬盘故障 = 全部事项、成果、审计永久丢失。

## 2. 目标

- 开通后尽快完成一次：系统生成恢复码 → 保存“恢复包” → 当场试解（证明能用）；没做完首页与事项页一直提醒。
- 选一个备份位置（移动硬盘、律所 NAS、律师选定的同步盘——备份里全是密文），**每天自动增量备份**，界面显示最近一次成功时间。
- 新电脑：激活页“从备份恢复” → 选备份位置 + 恢复包 + 输入恢复码 → 恢复到与原机相同的身份与数据 → 重启后照常使用。
- 云端（中软）全程看不到恢复码、恢复包与备份内容。

## 3. 设计（按实现）

### 3.1 恢复码

系统生成 **256 bit** 随机秘密，与 4 字节恢复码集编号（`set_id`，独立随机，不由秘密派生）、1 字节版本、4 字节整体校验一起按 `KWR1`（`keys/share-codec.ts`）编码：
**前缀行 `KWR1` + 3 行 Crockford base32**（24 / 24 / 18 个字符，每 4 字符一组），每行末 1 位行校验字符（按位置加权、含行号，模 32）——抄错能指出是第几行（行号按界面上的编号数，`KWR1` 那一行不计）。
秘密已满熵，包裹密钥用 **HKDF-SHA256**（salt `kwl`、info `kwl-recovery-package/3`）派生，不做口令拉伸。
恢复码**只在 `recovery.create_package` 的那一次应答里出现**：界面只放在组件状态里（不进 localStorage），“收起”即清空；可打印（只打印恢复码卡片，带律所名、生成时刻与 `set_id` 抬头）；内核与磁盘都不保存。

### 3.2 恢复包（单文件，`kind: "kwl-recovery-package"`，`v: 3`）

| 部分 | 内容 |
|---|---|
| 外层明文 | `kind`、`v`、律所显示名、设备编号（`dev_<律所>_<成员>`）、`set_id`、创建时刻——只用于识别，全部进附加数据（改任何一项即解不开） |
| 密文内 | 激活信息（同 activation.json）、**数据库主密钥**（D-101）、设备签名与加密两把私钥及证书、律所根公钥与恢复托管公钥、生成时本机最近一次备份的序号与时刻；**创始设备**另含律所根私钥及其种子与 `recovery-shares/` 下全部 5 份恢复份额（过渡，C6 落地后改离线分持） |

包裹：AES-256-GCM（每个包新秘密、随机 12 字节 IV），附加数据 = 外层明文的规范化 JSON；解开后再核 `device_id` 与外层一致。
包里**没有**备份位置的标识（备份位置不随恢复包或恢复带走，见 3.4）。
`recovery.verify_package` 试解只读、不改状态；`includes_firm_root` 为真时界面另起一段提示“这份恢复包还能恢复本所的管理权限”。文件读取前先 `stat` 限 1 MB。
每次 `recovery.create_package` 都生成新秘密与新包，**旧包仍然有效**（界面写明，并列出最近几次生成的时刻供对照销毁；作废见第 7 节）。

### 3.3 增量备份（格式 v2）

- **位置与目录**：`<备份位置>/KimiWorkLegal-backup/<不透明编号>/`，编号 = HMAC(由数据库主密钥派生的命名密钥, 租户‖设备编号) 的前 32 位十六进制——备份位置上看不出律所与设备；恢复时用恢复包里的主密钥算出同一编号。
- **备份盘标记**（R2B-06）：选定位置时在设备目录里写 `location.kwlm`（16 字节随机编号，不含身份），编号记进本机状态；**每次备份先核对标记、再建目录写文件**——同一盘符换成了别的 U 盘、或原来的备份被移走，即停下并记 `location_changed`，不在那块盘上新建任何东西；重新选回原来的盘沿用它的标记。
- **内容寻址**：`objects/<sha256>`（账本快照也是一个对象），对象只增不改；文件名与目录结构只写在**加密清单**里——网盘服务商只看得到对象数量、大小与写入时间。
- **账本快照**：`wal_checkpoint(TRUNCATE)` 完整完成后同步读入内存（单连接同步驱动，读期间无写入）再异步写出；检查点没有完整完成即本次不备份（不是初稿写的“SQLite 在线备份 API”）。
- **其余文件**：清单里的摘要一律取自**本机源文件**（本机摘要索引 `backup-index.json` 只用来免去重复计算）——能写备份位置的人换掉某个对象，下次恢复按清单核对即失败，不会被本机设备“背书”（R2A-08）。列出后消失的文件（运行中任务的临时文件）跳过。
- **清单**：`manifest-<序号>.kwlb` = { body: AES-256-GCM(清单明文；密钥由主密钥派生；附加数据绑定目录编号), sig: 设备签名(body) }，一个文件、原子改名写入；**保留最近 7 代**，对象只在不被任何保留的清单引用时删除——一次备份中断或源数据损坏，上一代仍可恢复。
- **不进备份**：运行期日志与套接字、临时文件、账本本体（另行快照）、日志盐、入组/认领/设备恢复暂存、设备导出、本机备份状态 `backup.json` 与摘要索引（含备份位置路径，不随恢复带到新电脑）、恢复标记。
- **安全细节**：备份位置不跟随链接与联接点（逐级 `lstat`）、不得在本应用数据目录里（按解析后的真实路径）；临时文件随机命名、独占创建；改名遇 `EPERM/EBUSY/EACCES` 退避重试 3 次。
- **何时备份**：启动后 5～15 分钟先看一次，之后每小时看一次——配置了位置且上次成功已超过 24 小时即备份；删除事项后立即再备份一次（R2A-10，见下条）；“立即备份”按钮。
- **删除事项后**（R2A-10）：状态里记“待清旧代”，立即再备份；这一次成功后**只留新的一代**（保留的旧几代账本快照里还有该事项的密钥包裹，只再备份一次而不清旧代，删除就落空）。删除时正有一次备份在跑，等它结束再备份一次；备份位置当时不可用，标记留到下一次成功。删除回执有“本应用的自动备份”一行写明这些。同一时刻只跑一次，异步执行、每 20 个文件让出事件循环并报进度；退出与安装更新时取消（不写清单，上一代不受影响）。**没有**初稿写的“应用退出时补一次”。
- **提醒**（`lib/recovery-reminder.ts`）：未生成恢复包 → 未设备份位置 → 备份盘不是原来那块 → 上次失败 → 3 天以上没有成功备份，按此顺序只提一件；后三种在首页与事项页都显示（初稿写的是“侧栏底部”）。失败的错误代码只进状态文件与运行记录，律师看到的是一句话。
- **被吊销的设备**不再备份、不再生成恢复包（R2A-16）。

### 3.4 恢复流程（新电脑）

```text
激活页「从备份恢复」→ 选备份位置（选 U 盘本身、KimiWorkLegal-backup 或更里层都能找到）+ 恢复包 → 输入恢复码
→ 内核（待激活模式，onboarding.restore；与兑换开通码互斥）解包；证书按当前时刻核验；激活记录与设备身份逐项一致
→ 本机有以前留下的工作区：须勾选确认（它们此后在本应用里打不开，但不删除；R2A-05）
→ 取最新一代清单：验设备签名、解密，逐个读出对象、核对摘要、写进 <数据根>/.restore-<随机>/ 暂存；不完整就退回上一代
→ 能用的那一代比恢复包生成时的备份还旧：须勾选确认（R2A-12）
→ 写 activation.pending.json（待生效）→ 暂存整体改名为 <数据根>/<律所>
→ 内核广播 kernel.adopt_master_key（只经 utilityProcess 端口，单独写出、不进界面广播）
→ 主进程只在内核此前报告待激活模式时接受：adoptDbKey 用本机 DPAPI 重新包裹（原文件改名留档 ledger-key.prev-<毫秒>，原子替换）
→ 主进程按新身份重启内核 → 启动时用当前主密钥试开恢复出的账本：打得开 → 待生效记录改名为 activation.json；打不开 → 删掉恢复出的工作区与待生效记录、记 restore_incomplete、回到待激活（R2A-15）
→ 恢复出的账本里记一条 device.restored_from_backup 审计；首页提醒“原电脑丢了请找管理员”（R2A-14）
```

任何一步失败都删掉暂存，不留残余；启动时清理进程中途被结束留下的 `.restore-*`。恢复后**备份位置为“未设置”**，请律师重新选（选回原来的盘会沿用其标记接着备份）。

### 3.5 安全性质与残余

- 恢复码 + 恢复包 = 这台电脑的全部能力；创始设备的恢复包另可签发管理员证书、凑齐恢复托管私钥（门限在包内塌缩为 1）。界面写清：两样分开放、不要拍照发微信、创始人的那份按律所公章同等保管。
- 恢复包不能作废、主密钥不能轮换：再生成一份不会让旧的失效（界面写明）——计划见第 7 节。
- 恢复后与旧电脑**同一设备身份**（D-42 设备编号确定性）：控制面不能单独吊销旧电脑，吊销即同时停用恢复出的新电脑——旧电脑丢失或被偷时须由管理员重新办理入组。
- 删除事项后再备份一次并只留新的一代，备份位置上之前的账本快照与该事项的对象随之删除；备份位置若保留旧版本（网盘版本历史、NAS 快照），旧版本连同恢复包与恢复码仍可解开已删事项——删除回执写明，须按律所保留期清理；换过备份位置的，旧位置上的备份不会被清理。
- 驻留面第 28 类（另见第 13、17、20 类）如实登记以上各项。

## 4. 接口（按实现）

内核（正常模式）：`backup.configure {dir}`、`backup.run`、`backup.status`（是否设置、最近成功、错误代码、多少天没成功、进度、文件数与字节数、恢复包生成/试解次数与最近几次时刻、是否已吊销）；
`recovery.create_package {path}` → `{file_name, code_text, set_id, includes_firm_root, created_at, firm_name}`（恢复码只返回这一次）；`recovery.verify_package {file, code}`（试解，不改状态）。
内核（待激活模式）：`onboarding.restore {dir, file, code, legacy_ack?, older_ack?}`。
渲染进程给不出路径：它传的是一次性句柄（`save_handle` / `file_handle` / `folder_handle`），主进程 `file-dialogs.cjs` 换成 `path / file / dir` 再交内核，渲染进程自带的路径字段一律剥掉。
主进程：接收 `kernel.adopt_master_key`（不是初稿的 `kernel.restore_master_key`），只在内核此前报告待激活模式时接受，经 `secret-store.cjs adoptDbKey` 原子替换。

## 6. 已知未处理（去向）

- 同一 Windows 账户上 DPAPI 解封失败（重置本地账户密码等）时进不了“从备份恢复”（复核 R2B-10）：方案是解封失败的对话框给“用恢复包恢复”，把旧数据改名到 `<数据根>/.unreadable-<时刻>/`（不删除）后以待激活模式启动——**待拍板**（v9.3 主文 §9）。
- 设备身份轮换与恢复后单独吊销旧电脑：随 G1“设备编号按安装生成”（D-42）。

## 7. G1 计划：恢复包作废与主密钥轮换（复核 R2A-01、R2A-14）

**为什么现在做不了**：恢复包里是数据库主密钥与设备两把私钥。作废一个已经离线存在的文件，只能让它里面的秘密失效——即换主密钥、换设备密钥，并让控制面不再接受旧身份。设备密钥轮换要求设备编号按安装生成（D-42 G1）、证书重签与事项密钥重新包裹，这三样都在 G1。

**做法**（按依赖顺序）：

| 步 | 内容 | 依赖 | 估算 |
|---|---|---|---|
| G1-R1 主密钥轮换 | 设置 · 恢复与备份“换一套恢复包”：生成新主密钥 → 账本 `PRAGMA rekey` → 按新主密钥重新封装 `keys/*.json` → 主进程经 `adopt` 同一路径原子替换（轮换成功后删除留档）→ 备份目录编号与清单密钥随主密钥改变，立即全量备份到新目录、成功后删除旧目录 → 生成新恢复包、当场试解。中途失败按“待生效”同一套回滚 | — | 2 人周 |
| G1-R2 恢复包登记与作废 | 内核记“当前有效的恢复码集编号”（只存 `set_id`）；`backup.status` 列出有效与已作废；轮换后旧 `set_id` 标作废。控制面按设备记有效 `set_id` 的摘要：用已作废的恢复包恢复出的设备登记时拒绝并告警（离线解开旧备份仍可能——如实写） | 控制面持久化（A-7） | 1 人周 |
| G1-R3 设备身份轮换 | 恢复后与“怀疑泄露”时换设备密钥：设备编号按安装生成（D-42）→ 成员由管理员重签证书、创始设备由律所根自签 → 控制面登记新公钥、吊销旧编号 → 事项密钥重新包裹给新设备公钥 → 团队事项在成员日志（第 12 批）写“设备换钥”事件 | D-42 G1、第 12 批成员日志、控制面 | 3～4 人周 |
| G1-R4 界面与驻留面 | 恢复后首页从“请找管理员”改为“一键换身份”；第 28 类残余改写；删除回执同步 | R1～R3 | 1 人周 |

**验收用例（G1 补）**：轮换后旧恢复包仍能试解，但其中的主密钥打不开新账本与新备份；旧备份目录已删；`backup.status` 只列一个有效 `set_id`；用旧恢复包恢复出的设备控制面登记被拒；设备换钥后旧设备公钥签的成员事件不再被接受、事项内容新设备可读。

**轮换后仍成立的残余**：轮换前的备份副本（网盘版本历史、NAS 快照）仍可被旧恢复包解开；离线的旧电脑上的数据仍受其 Windows 账户 DPAPI 保护。

## 8. 与初稿的差异（复核 R2A-03 逐条）

| 初稿 | 实现 | 处理 |
