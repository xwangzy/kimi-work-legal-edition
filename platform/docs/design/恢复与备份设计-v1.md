# 恢复与备份设计 v1（第 14 批 P0；评审 Z4 P0-1 + 主审 X-2）

2026-10-19 · 状态：设计，待实施 · 关联：`开通与成员入组设计-v1.md`、`TPM密钥与根私钥离线分持设计-v1.md`、D-41、D-61

## 1. 问题

现有 `recovery.export_device / import_device` 只导出**设备私钥**（口令 scrypt 包裹），并假设原账本还在本机。真实的“电脑坏了 / 被偷了 / 换新电脑”场景里：

1. **数据库主密钥**由主进程经 DPAPI 绑定旧 Windows 账户——新电脑上无论拿到什么备份都打不开账本（SQLCipher）。
2. **数据本身**（账本、块、工作区）没有备份机制；律师自己复制 `%LOCALAPPDATA%` 也没用（同 1）。
3. 创始设备的**律所根与 5 份恢复份额**和数据在同一块硬盘上，硬盘坏了一起丢——律所再也不能加人、也不能做事项的恢复托管解包。
4. 恢复口令由律师自拟（≥ 10 字），实际会被设成弱口令或忘记。
5. 界面没有入口（Z4 P0-1）。

后果：单人律所一次硬盘故障 = 全部事项、成果、审计永久丢失。

## 2. 目标

- 开通时**强制**完成一次：系统生成恢复码 → 导出“恢复包” → 当场试解（证明能用）。
- 选一个备份位置（移动硬盘、律所 NAS、律师选定的同步盘——数据本来就是密文），**每天自动增量备份**，界面显示最近一次成功时间。
- 新电脑：激活页“从备份恢复” → 选备份位置 + 恢复包 + 输入恢复码 → 恢复到与原机相同的身份与数据 → 重启后照常使用。
- 云端（中软）全程看不到恢复码、恢复包与备份内容。

## 3. 设计

### 3.1 恢复码

系统生成 128 bit 随机数，按 `KWR1` 行校验编码（第 7 批 `keys/share-codec.ts`）显示为 4 行、每行 8 个字符 + 1 位校验，抄错一行能定位到行。scrypt（N=2^15，因熵已足够）派生包裹密钥。恢复码**只显示一次**，可打印；内核与磁盘都不保存。

### 3.2 恢复包（`kwl-recovery/3`，单文件，口令包裹）

| 字段 | 说明 |
|---|---|
| 外层明文 | 格式名、版本、律所显示名、设备编号、创建时刻（用于识别，不作为信任依据） |
| 包裹内 | `activation`（同 activation.json）、`db_master_key`、设备两把私钥与证书、律所根私钥与恢复码（仅创始设备）、5 份恢复份额（仅创始设备）、备份位置的标识与清单签名公钥指纹 |

包裹：AES-256-GCM（密钥 = scrypt(恢复码)），附加数据 = 外层明文的规范化 JSON。

### 3.3 增量备份

- **账本**：SQLite 在线备份 API 生成快照（SQLCipher 页级密文原样复制，不解密）。
- **块与工作区**：内容寻址、只增不改 → 按文件名增量复制；删除事项后的密码学擦除在备份里同样成立（事项密钥已删，备份里的块解不开），删除回执写明“备份中的副本不可读、不立即删除”。
- **清单**：每次备份写一份清单（文件名、大小、sha256、账本快照序号），由设备签名私钥签名；恢复时先验清单再复制。
- 默认每天一次、应用退出时补一次；失败进本机告警（只记事件码），设置页显示“最近一次成功：X 天前”，超过 3 天在侧栏底部提示。

### 3.4 恢复流程（新电脑）

```text
激活页「从备份恢复」→ 选备份文件夹 + 恢复包 → 输入恢复码
→ 内核（待激活模式）解包、验清单签名、核对设备证书与律所根一致
→ 复制数据到 <数据根>/<律所>、写 activation.json、暂存主密钥
→ 内核发 kernel.restore_master_key（只经 utilityProcess 端口，与 kernel.init 同一信任域）→ 主进程用本机 DPAPI 重新包裹写 ledger-key
→ 主进程按新身份重启内核 → 打开恢复的账本 → 控制面登记（同设备编号、同证书）
```

### 3.5 安全性质与残余

- 恢复码 + 恢复包 = 本机全部能力（与原电脑同权）。界面写清：两样分开放、不要拍照发微信。
- 旧电脑若被偷：恢复后界面建议“吊销旧设备并换新设备身份”。设备编号是确定性的（D-42），换身份要等“按安装生成编号”（G1）——首期如实写残余：恢复后与旧电脑同一设备身份，旧电脑上的数据仍受其 Windows 账户 DPAPI 保护。
- 律所版：创始设备的根私钥进恢复包只是过渡，最终走离线分持（C6）。

## 4. 接口

内核：`backup.configure {dir}`、`backup.run`、`backup.status`；`recovery.create_package {out_handle}` → `{recovery_code_lines}`（只返回一次）；`recovery.verify_package {handle, code}`（试解，不改状态）；待激活模式 `onboarding.restore {backup_dir_handle, package_handle, code}`。
主进程：接收 `kernel.restore_master_key` 后重新包裹（只在待激活模式下的内核发来时接受）。文件路径一律经一次性句柄（第 5 批 `file-dialogs.cjs`）。

## 5. 验收

- 用例：开通 → 生成恢复包 → 备份 → 新数据根 + 新主密钥（模拟新电脑）→ 恢复 → 事项、成果可读；审计链复核通过；控制面登记成功；删除过的事项在恢复后仍不可读。
- 负例：恢复码抄错一行（定位到行）、清单被改、包与备份不属于同一设备、备份比恢复包旧（提示丢失的天数）。
- 驻留面：恢复包与备份位置登记为新数据类；金丝雀扫描备份目录 0 明文命中。
- Windows 实机：U 盘备份 → 另一台电脑恢复。
